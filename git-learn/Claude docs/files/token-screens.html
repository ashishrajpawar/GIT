OTP verification

Four boxes, auto-advance, and — non-negotiable — SMS autofill. Shipping without it adds friction at the exact moment the user is most likely to abandon.

Implementation

A5b—new · decision 4

Guided first mint

Four coach marks over the real interface, producing a real token. Nothing simulated — the fake-buyer idea was rejected precisely because a product built on trust should not put a fake person inside itself.

The four steps
  • 1 · The FAB — "This button mints a token — a door only the person you send it to can use." Advancing opens F1.
  • 2 · Template grid — "Pick what it's for. The rules come pre-set — you can change them later." Highlights Marketplace sale.
  • 3 · Mint & share — "That's it. Two taps and the door exists."
  • 4 · The pass card + share row — "Send this link to one person. Only they can use it, and you can kill it any time." Highlights Copy link.
Interaction rules
  • Each step dims the screen except the target, which keeps a 2.5pt accent ring — the user always taps the real control, never a mock
  • Skip is present on every step and never re-prompts
  • Abandoning mid-flow leaves any real state created so far intact
  • Runs exactly once per account; re-runnable from E4 Settings → Help
What this must not become

Not a tour of the whole app. Four steps, one outcome: a live token he can paste to a real person within ninety seconds. Every additional step measurably reduces completion.

A6—new

App lock

A privacy app that opens straight into readable conversations when the phone is handed to someone is not a privacy app. This is the most commonly skipped screen in this category and the most damaging to omit.

Behaviour
  • Off by default; enabled in E4 with a timing choice — immediately / after 1 min / after 15 min
  • Biometric prompt fires on mount; PIN is the fallback, not an alternative shortcut
  • There is no skip. Failure leaves the app locked
  • When enabled, obscure the app preview in the OS task switcher
Related hardening
  • FLAG_SECURE on E1 (the vault) and on any screen showing an unmasked identity value
  • When App Lock is on, F3 revoke confirmation should also require biometrics — an irreversible action taken by someone holding a borrowed phone is unrecoverable
Implementation

expo-local-authentication or react-native-biometrics; store the PIN hash in Keychain / Keystore, never in AsyncStorage.

D1b—new · decision 1

Edit rules

Your ruling, made concrete: narrowing and expiry changes yes, adding channels no. The permission model only holds if a holder's page can never gain capability without a fresh grant.

What is allowed
  • Remove a channel — takes effect immediately; the holder's page loses that row on next load
  • Shorten expiry — immediate
  • Extend expiry — immediate, including reviving a token in its final hours
  • Narrow reachable hours — immediate
  • Turn on verified-businesses-only — allowed (it narrows)
What is forbidden, and why
  • Adding a channel that was never granted. Ungranted channels render as dashed, locked chips with the explanation: "Locked channels weren't granted when this token was minted. Mint a new one to add them."
  • Turning off business-only — that widens the audience. Also forbidden
  • The rule in one line: a live token may only ever shrink, or live longer. Growth requires a new grant the holder must receive
Feedback & audit
  • Saving writes a timeline entry: "Rules narrowed — SMS removed" or "Expiry extended to 30 days"
  • Toast: "Rules updated — this token can now do less." for narrowing; "Expiry extended." for lifetime
  • Removing the last remaining channel is blocked — offer Pause or Revoke instead
Data

PATCH /tokens/{code} { channels?, expiry?, window?, bizOnly? } — server re-validates that every change is a narrowing or an expiry change and rejects widening with 409 WIDENING_NOT_ALLOWED. Never trust the client for this.

Activity

The ledger of every knock, bounce and lifecycle event — individual events only. This screen is where vanity metrics try to sneak back in, and the answer is always no.

Decision 5 · applied — the quiet-week mechanic
  • No counters, no streaks, no "47 days sealed". Those were killed in the teardown and do not return here
  • The retention loop is a weekly digest push, sent only when something actually happened: "2 attempts bounced this week. Rahul's token expires Friday."
  • A week with zero events sends nothing. An app that stays quiet when nothing happened is exactly the promise — manufacturing a notification to stay top-of-mind would betray it
  • Expiry warnings are the honest nudge: they are real, actionable, and they bring him back to a decision rather than a statistic
Event types
  • shield / red — Contact attempt without a token — bounced
  • chat / blue — Rahul messaged via TOKN-8GH2-LP4X
  • clock / amber — Bluekart token expires in 18 hours
  • lock / green — Token for Old broker revoked — line dead
  • pin — location requested (red) or shared (green)
Behaviour
  • Opening marks all read; the badge clears after ~400ms so the change is visible
  • Unread rows carry an accent border and a dot
  • Retention: 90 days on paid, 7 days on free

E3b—new · decision 2

Downgrade — choose what stays live

Your ruling: the user picks; nothing is auto-revoked. A billing event must never silently sever someone's access — that would make the product's core promise a function of a payment failure.

Decision 2 · applied
  • Triggered when a downgrade (chosen or from a failed renewal) leaves live tokens above the new tier's limit
  • Excess tokens are paused, never revoked — pause is reversible, revoke is not, and the system must never take an irreversible action on the user's behalf
  • Selection is required; the confirm button stays disabled until the count matches the allowance
  • Changes apply at cycle end, with the date shown on the sheet
If the user ignores it
  • No selection by cycle end → the system keeps the most recently active tokens and pauses the rest, then posts an Activity entry naming exactly what was paused
  • Holders of paused tokens see the standard "Paused for now" page — never a billing message. The holder must never learn anything about the owner's account
Channel downgrades

Dropping from Plus to Free also removes voice and SMS. Live tokens carrying those channels are narrowed to chat, not paused — consistent with the D1b rule that a token may shrink at any time. The affected holder simply sees fewer options on their page.

Data

POST /billing/downgrade { plan, keepTokens[] } — server enforces the tier limit and returns the resulting state of every affected token.

KYC verification

v7 fakes this in 1.8 seconds. Real flows through Digio, Signzy or Karza have document capture, liveness, minutes-long processing and — the part prototypes always omit — rejection. This is the largest gap between the prototype and a shippable app.

Flow
  • Intro (shown) — why it is needed, which channels it unlocks, what happens to the documents
  • Document choice — Aadhaar/DigiLocker recommended, PAN, Passport
  • Capture or redirect — partner SDK or web redirect
  • Liveness selfie
  • Processing — must be backgroundable; push on completion
  • Result — verified, or rejected with a reason and one retry path
States the prototype skips
  • Rejected — name mismatch, blurred document, failed liveness. Each needs its own message and a clear next step
  • Pending for minutes — the user must be able to leave the app and come back
  • Partner outage — "Verification is unavailable right now. Your chat and SMS tokens still work."
  • Retry limit — three attempts, then a support route
On success
  • Unlock the Call channel everywhere it appears, including inside F1
  • Update the E1 chip to green Verified
  • Post an Activity event: "KYC complete — voice tokens unlocked"
Entry points

E1 vault row · the inline callout inside F1 (which completes without leaving the mint sheet) · any attempt to add the Call channel.

Mint result — with the message written for him

Your ruling applied. The riskiest moment in the whole product happens outside the app, when a stranger receives an unfamiliar link. The sentence that accompanies it does more for redemption than any interface change available to us — so the app writes it.

Decision 3 · applied
  • An editable message box sits above the share row, pre-written from the template and the token's label
  • Copy both copies message + link together — the default action, because a bare URL is what fails
  • WhatsApp share pre-fills the same text
  • Shorter ↺ swaps in a terse variant for people who find the default too wordy
Template copy
  • Marketplace — "Hi — use this link to reach me about the car. It works without installing anything, and you won't need my number."
  • Delivery — "Delivery contact link for order #4471 — no app needed."
  • Contractor — "Here's my contact link for the site work. Opens in any browser."
  • Shorter variant — "Reach me here — no app needed:"
Rules for this copy
  • Never mention privacy, hiding, or protection. The message must not make the recipient feel distrusted — it explains a convenience, not a defence
  • Never use the words token, mint or vault. The holder doesn't know the product
  • Editable, always. If he rewrites it, remember his version as the default for that template
Metric

This screen owns redemption rate per minted token — the number that tells you whether holders trust the link.

F3sheet-revokebuilt

Revoke confirmation

Mandatory before any revoke, from every entry point. This sheet exists because v4 allowed an irreversible action on a single unconfirmed header tap, one icon away from Report. Never regress this.

Why the card is repeated here

He must be certain which door he is killing. Showing the pass card inside the confirmation removes any chance of revoking the wrong one from a list.

Entry points & post-actions
  • chat → return to the thread and seal it
  • report → same, plus a red Activity entry: "Reported & blocked — token killed"
  • detail → refresh D1 into its dead-token variant
Escape hatch

Pause instead is the second button, not a link — most revoke impulses are temporary irritation. It is hidden when the token is already paused.

Hard rules
  • Revoke is irreversible everywhere. No undo toast, no restore, no support override
  • When App Lock is enabled, require biometrics here too
  • Offline → the button is disabled with "You're offline — token changes need a connection." A revoke must never appear to succeed when it hasn't

F4modal-biobuilt

Biometric confirmation

Gates every reveal of a vault value. In v4 the real number was one unauthenticated tap away — on a privacy product, that is the bug that ends the product.

Production behaviour
  • Call the real API — expo-local-authentication or react-native-biometrics
  • Fall back to device PIN; on repeated failure simply close without revealing and without an error that hints at what's behind it
  • Re-masking never re-authenticates
  • Auto re-mask after 30 seconds or on backgrounding
Required for
  • Vault reveals (real number, real email)
  • Revoke, when App Lock is enabled
  • Account deletion, always

F7sheet-locreqbuilt

Location request

An inbound ask that the owner grants or ignores. The only inbound request the product permits — and it is scoped, timed, and silent when refused.

Rules
  • Live pin only — never saved addresses, never history
  • Duration is mandatory; sharing expires automatically
  • Denial is silent to the requester. They see no "denied" message, only that nothing arrived — consistent with silence being a complete answer
  • An active share shows a persistent banner with a one-tap stop
Audit

Both the request and the outcome write to Activity and to the token's timeline — "Live location shared · 1 hour".

H1webRoot · validbuilt

The holder's page — valid token

The most fragile surface in the product: a stranger's first four seconds with an unfamiliar link. No install, no signup, no cookie wall, under two seconds on 4G.

Why locked rows are shown, not hidden

Displaying the channels this token doesn't grant gives the permission a visible shape. Hiding them makes the page feel arbitrary; showing them makes it feel governed — and governed is what converts suspicion into trust.

Reciprocity

"Bridged line — numbers hidden both ways." The holder's number is protected too. Saying this out loud turns a reluctant participant into a beneficiary, and it is the single highest-leverage line on the page.

Other states
  • Business-gated — "This token opens for verified businesses only" + one-time verification
  • Paused — "Paused for now. It may return — that's their call alone."
  • Revoked / expired — "This token no longer exists."
  • Unknown code — the same dead treatment. Never reveal whether a code ever existed
The rule that governs every state

There is no "request access" control anywhere on this page, ever. An appeal mechanism re-imports exactly the social pressure the product exists to eliminate. The footer closes the door properly: "Ashish is sealed by default. No number to find, no inbox to reach, no way to request one."
