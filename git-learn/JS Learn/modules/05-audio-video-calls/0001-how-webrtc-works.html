Audio & Video Calls · Lesson 1

How WebRTC Works

Peer-to-peer · Offers & answers · ICE candidates · STUN/TURN · Signaling ~45 min Conceptual + code
Why this matters for your WhatsApp clone

When you tap the phone icon in WhatsApp and hear the other person's voice in real time — that's WebRTC. It's the exact same technology used by WhatsApp, Signal, Google Meet, Discord, and FaceTime. Unlike sending messages through a server, WebRTC creates a direct peer-to-peer connection between two phones so audio and video flow directly between them — no server in the middle, no monthly bill, end-to-end encrypted by default. This lesson explains how WebRTC works before you write any code, so the next 7 lessons make complete sense.

1. The big picture — what problem does WebRTC solve?

Sending a text message is simple: Phone A writes to Firestore → Phone B reads from Firestore. There's a server (Firestore) in the middle that stores and forwards data.

But for a voice call, this won't work because:

  • Latency — a round-trip through Firestore takes 200–500ms. In a call, anything over 150ms feels like a delay. You need sub-100ms.
  • Volume — audio generates ~50 tiny packets per second, video generates ~30 frames per second. That's thousands of writes per minute through Firestore — expensive and slow.
  • Privacy — routing audio through your server means you could listen. Users trust WhatsApp because calls go directly between devices.

WebRTC solves all three: it creates a direct tunnel between two phones. Audio/video flows phone-to-phone with no server in between. Latency is as low as your internet connection allows. Cost is zero. Connection is encrypted end-to-end.

// Without WebRTC (text messages):
Phone A  →  Firestore  →  Phone B     (200-500ms, server stores everything)

// With WebRTC (calls):
Phone A  ←────────────→  Phone B      (50-100ms, direct, encrypted, free)

2. The problem: how do two phones find each other?

Your phone doesn't have a public address that another phone can connect to directly. It's behind a router (NAT), a mobile carrier, maybe a VPN. The other phone has the same problem.

This is like two people who want to talk on walkie-talkies but don't know each other's radio frequency. They need a third person to tell them: "You're on channel 5, they're on channel 12."

WebRTC solves this in two steps:

  1. Signaling — a server (Firestore in your case) passes connection instructions between the two phones BEFORE the call starts
  2. ICE/STUN/TURN — a process that discovers each phone's network address and tests which connection path works

3. The WebRTC connection flow — 6 steps

Here's exactly what happens when Priya calls Rahul:

┌─────────────────────────────────────────────────────────────────┐
│  SIGNALING PHASE (uses Firestore — happens once per call)       │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Step 1: Priya creates an "offer"                               │
│          (her audio/video capabilities + network info)          │
│                                                                 │
│  Step 2: Priya writes the offer to Firestore                    │
│          Firestore doc: /calls/{callId}                         │
│                                                                 │
│  Step 3: Rahul's phone reads the offer from Firestore           │
│                                                                 │
│  Step 4: Rahul creates an "answer"                              │
│          (his audio/video capabilities + network info)          │
│                                                                 │
│  Step 5: Rahul writes the answer back to Firestore              │
│                                                                 │
│  Step 6: Both phones exchange ICE candidates via Firestore      │
│          (possible network routes to try)                       │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│  CONNECTION PHASE (direct, no Firestore involved)               │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Step 7: WebRTC tries each ICE candidate pair                   │
│          until a direct path works                              │
│                                                                 │
│  Step 8: Audio/video flows directly between phones              │
│          (peer-to-peer, encrypted, low latency)                 │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

Key insight: Firestore is only used for the initial handshake (steps 1–6). Once the connection is established, Firestore is no longer involved — data flows directly.

4. Offers and Answers — what are they?

An offer and answer are SDP (Session Description Protocol) objects — basically text strings that describe what each phone can do:

// An SDP offer looks something like this (simplified):
{
  type: 'offer',
  sdp: 'v=0\r\n'
     + 'o=- 123456 2 IN IP4 127.0.0.1\r\n'
     + 'm=audio 9 UDP/TLS/RTP/SAVPF 111\r\n'  // "I can send audio"
     + 'a=rtpmap:111 opus/48000/2\r\n'         // "using Opus codec"
     + 'm=video 9 UDP/TLS/RTP/SAVPF 96\r\n'   // "I can send video"
     + 'a=rtpmap:96 VP8/90000\r\n'             // "using VP8 codec"
     + '...'
}

You never need to read or edit SDP strings — WebRTC generates them for you. You just pass them between phones via Firestore.

The conversation between phones goes like this:

  • Offer (Priya): "I can send audio using Opus codec and video using VP8. Here are my network candidates."
  • Answer (Rahul): "Cool, I also support Opus and VP8. Here are MY network candidates. Let's connect."

5. ICE candidates — finding a path through the internet

ICE stands for Interactive Connectivity Establishment. It's the process of finding a network route between two phones.

Each phone generates multiple ICE candidates — these are possible addresses/paths the other phone could use to reach it:

// ICE candidate examples:
{
  candidate: 'candidate:1 1 udp 2113937151 192.168.1.42 54321 typ host',
  // "Try reaching me at 192.168.1.42:54321 (my local WiFi address)"
}

{
  candidate: 'candidate:2 1 udp 1845501695 203.0.113.55 12345 typ srflx',
  // "Try reaching me at 203.0.113.55:12345 (my public IP via STUN)"
}

{
  candidate: 'candidate:3 1 udp 33562367 74.125.197.100 9999 typ relay',
  // "If all else fails, relay through this TURN server"
}

Three types of candidates:

  • host — the phone's local network address (only works if both phones are on the same WiFi)
  • srflx (server reflexive) — the public IP discovered via STUN (works for most calls)
  • relay — a TURN server that relays traffic (fallback when direct connection fails, e.g. strict corporate firewalls)

WebRTC tries all candidates and picks the best working path automatically.

6. STUN servers — discovering your public IP

Your phone knows its local IP (like 192.168.1.42) but not its public IP (the one the outside world sees). A STUN server tells your phone: "When I received your packet, it came from 203.0.113.55:12345 — that's your public address."

// STUN is like calling a friend and asking "what number showed on your caller ID?"
Phone → STUN server: "What's my public address?"
STUN server → Phone: "You're at 203.0.113.55:12345"

// Google runs free STUN servers anyone can use:
const iceServers = [
  { urls: 'stun:stun.l.google.com:19302' },
  { urls: 'stun:stun1.l.google.com:19302' },
];

STUN is free and stateless — it doesn't relay any audio/video, it just tells your phone its public address. Google's STUN servers handle billions of requests and cost you nothing.

7. TURN servers — the fallback relay

Sometimes a direct connection is impossible — both phones are behind strict firewalls (common in offices, universities, some mobile carriers). When STUN fails, TURN relays the audio/video through a server:

// Without TURN (direct):
Phone A  ←──────────→  Phone B   ✅ Fast, free

// With TURN (relayed — only when direct fails):
Phone A  →  TURN server  →  Phone B   ⚠️ Slower, costs bandwidth

// TURN config (coturn — free self-hosted server):
const iceServers = [
  { urls: 'stun:stun.l.google.com:19302' },
  {
    urls: 'turn:your-server.com:3478',
    username: 'webrtc',
    credential: 'your-password',
  },
];

Key facts about TURN:

  • Only ~15% of calls need TURN (most connect directly via STUN)
  • You self-host TURN using coturn — a free, open-source server
  • TURN costs bandwidth on your server but is essential for reliability
  • WhatsApp uses the same architecture: try direct first, fall back to relay
For development: STUN only is fine

While building and testing on your local WiFi or hotspot, STUN is all you need. Both phones are usually on the same network or on direct mobile connections. You'll set up coturn in Module 6 for production reliability.

8. Signaling — why Firestore is perfect

"Signaling" means: how do the two phones exchange offers, answers, and ICE candidates? WebRTC does NOT define how signaling works — you choose any channel. Common options:

  • WebSockets (Socket.io) — requires a running server
  • HTTP polling — slow and wasteful
  • Firebase Firestore — real-time listeners, already in your stack, free tier is generous

Firestore is ideal because:

  1. You already have it set up (Module 3)
  2. onSnapshot gives you real-time updates — no polling
  3. No extra server to deploy or manage
  4. Works even if one phone is on WiFi and the other on mobile data
// Signaling via Firestore — data model:
/calls/{callId}
  ├── callerId: 'uid_priya'
  ├── calleeId: 'uid_rahul'
  ├── offer: { type: 'offer', sdp: '...' }      // Priya writes this
  ├── answer: { type: 'answer', sdp: '...' }    // Rahul writes this
  ├── status: 'ringing' | 'active' | 'ended'
  │
  ├── callerCandidates/ (subcollection)
  │     └── {candidateId}: { candidate: '...' }  // Priya's ICE candidates
  │
  └── calleeCandidates/ (subcollection)
        └── {candidateId}: { candidate: '...' }  // Rahul's ICE candidates

9. The RTCPeerConnection — the core WebRTC object

In code, all of WebRTC revolves around one object: RTCPeerConnection. Here's a preview of how it's used (you'll implement this fully in Lesson 5):

import {
  RTCPeerConnection,
  RTCSessionDescription,
  RTCIceCandidate,
  mediaDevices,
} from 'react-native-webrtc';

// 1. Create the connection object with STUN/TURN servers
const pc = new RTCPeerConnection({
  iceServers: [
    { urls: 'stun:stun.l.google.com:19302' },
  ],
});

// 2. Get local audio stream from microphone
const stream = await mediaDevices.getUserMedia({ audio: true, video: false });
stream.getTracks().forEach((track) => pc.addTrack(track, stream));

// 3. Listen for ICE candidates (send each to the other phone via Firestore)
pc.onicecandidate = (event) => {
  if (event.candidate) {
    // Write to Firestore: /calls/{callId}/callerCandidates
    addDoc(candidatesCollection, event.candidate.toJSON());
  }
};

// 4. Listen for remote audio (the other person's voice)
pc.ontrack = (event) => {
  // event.streams[0] contains the remote audio — play it
  setRemoteStream(event.streams[0]);
};

// 5. Create offer (caller) or answer (callee)
const offer = await pc.createOffer();
await pc.setLocalDescription(offer);
// Write offer to Firestore

// 6. When the other phone's answer arrives from Firestore:
await pc.setRemoteDescription(new RTCSessionDescription(answer));

// 7. When ICE candidates arrive from Firestore:
await pc.addIceCandidate(new RTCIceCandidate(candidate));

Don't memorize this yet — this is a preview so you understand where the pieces fit. Lessons 3–5 will walk through each step in detail.
