Presence & Typing

B5 — Lesson 3 of 3 ~50 min
Why this matters for Token

Presence ("online" / "offline" dots) and typing indicators ("typing...") are ephemeral — they don't need to be stored in the database. They're real-time signals that make a chat feel alive. Without them, you're sending messages into a void. With them, you know the other person is there and about to reply. These are the cheapest features with the highest UX impact.

Ephemeral vs. durable state

StateTypeStorageSurvives restart?
MessagesDurablePostgreSQLYes
Delivery receiptsDurablePostgreSQLYes
Online/offlineEphemeralRedis key with a TTLNo — and that is the design
Typing indicatorEphemeralNot stored anywhereNo
"Last seen" timeSemi-durablePostgreSQL, written when the presence key lapsesYes

Ephemeral state is fire-and-forget. If the server restarts, all presence resets (everyone appears offline until they reconnect). This is fine — clients reconnect within seconds, and presence rebuilds automatically.

Presence tracking

When is a user "online"?

A user is online if they have at least one active WebSocket connection anywhere in the cluster. That last part is what makes the obvious implementation wrong:

// WRONG -- this answers a different question than the one asked.
function isOnline(userId: number): boolean {
  const sockets = clients.get(userId);
  return sockets !== undefined && sockets.size > 0;   // ...on THIS node
}

As 0002 laboured, the local map knows only about this process. Presence is a claim about the user, not about this server, so it lives in Redis as a key with a TTL:

// api/src/ws/presence.ts
const PRESENCE_TTL_SECONDS = 60;

// Called when a socket connects, and again on every heartbeat tick.
export async function markPresent(userId: number) {
  await redis.set(`presence:${userId}`, '1', 'EX', PRESENCE_TTL_SECONDS);
}

export async function isOnline(userId: number): Promise<boolean> {
  return (await redis.exists(`presence:${userId}`)) === 1;
}

Notice there is no markOffline. Going offline is the absence of a refresh, so the key expires on its own. That is not a shortcut — it is the only version that survives a server being killed rather than shut down, and it means no node ever has to decide on another node's behalf that a user has gone.

Broadcasting presence changes

// api/src/ws/presence.ts
import { getClients } from './server';
import { sendTo } from './router';
import { db } from '../db';

export async function handleUserConnected(userId: number) {
  const sockets = getClients().get(userId);

  // Only broadcast if this is their FIRST connection (was offline, now online)
  if (sockets && sockets.size === 1) {
    await broadcastPresence(userId, 'online');
  }
}

export async function handleUserDisconnected(userId: number) {
  const sockets = getClients().get(userId);

  // Only broadcast if this was their LAST connection (now truly offline)
  if (!sockets || sockets.size === 0) {
    await broadcastPresence(userId, 'offline');

    // Update "last seen" in the database
    await db.query(
      'UPDATE users SET last_seen_at = NOW() WHERE id = $1',
      [userId]
    );
  }
}

async function broadcastPresence(userId: number, status: 'online' | 'offline') {
  // Find all users who have conversations with this user
  const result = await db.query(
    `SELECT DISTINCT
       CASE WHEN issuer_id = $1 THEN holder_id ELSE issuer_id END AS other_user_id
     FROM conversations
     WHERE issuer_id = $1 OR holder_id = $1`,
    [userId]
  );

  // Notify each conversation partner who is currently online
  for (const row of result.rows) {
    const partnerSockets = getClients().get(row.other_user_id);
    if (partnerSockets) {
      for (const sock of partnerSockets) {
        sendTo(sock, 'presence:update', { userId, status });
      }
    }
  }
}

Wiring into the connection lifecycle

// In api/src/ws/server.ts — update the connection/close handlers:

wss.on('connection', (ws: AuthenticatedSocket) => {
  // ... existing tracking code ...

  // Broadcast presence after adding to clients Map
  handleUserConnected(ws.userId);
});

ws.on('close', () => {
  clients.get(ws.userId)?.delete(ws);
  if (clients.get(ws.userId)?.size === 0) {
    clients.delete(ws.userId);
  }

  // Broadcast presence after removing from clients Map
  handleUserDisconnected(ws.userId);
});

Who should receive presence updates?

Not everyone in the system — only people who have an active conversation with this user. The query above finds all "conversation partners". This is important for Token's privacy model:

  • A token holder should see when the issuer is online (so they know if they'll get a quick reply)
  • The issuer should see when holders are online
  • Random users who have no conversation should NOT see each other's presence

Typing indicators

Typing indicators are the simplest real-time feature: forward a "user X is typing in conversation Y" event to the other participant. No database, no persistence.

// api/src/ws/handlers/typing.ts
import { getClients } from '../server';
import { sendTo } from '../router';
import { db } from '../../db';
import { WebSocket } from 'ws';

interface AuthenticatedSocket extends WebSocket {
  userId: number;
  isAlive: boolean;
}

interface TypingPayload {
  conversationId: number;
}

export async function handleTypingStart(ws: AuthenticatedSocket, payload: TypingPayload) {
  await forwardTypingEvent(ws, payload.conversationId, true);
}

export async function handleTypingStop(ws: AuthenticatedSocket, payload: TypingPayload) {
  await forwardTypingEvent(ws, payload.conversationId, false);
}

async function forwardTypingEvent(
  ws: AuthenticatedSocket,
  conversationId: number,
  isTyping: boolean
) {
  // Find the other participant
  const conv = await db.query(
    'SELECT issuer_id, holder_id FROM conversations WHERE id = $1',
    [conversationId]
  );

  if (conv.rows.length === 0) return;

  const { issuer_id, holder_id } = conv.rows[0];
  if (ws.userId !== issuer_id && ws.userId !== holder_id) return;

  const recipientId = ws.userId === issuer_id ? holder_id : issuer_id;
  const recipientSockets = getClients().get(recipientId);

  if (recipientSockets) {
    for (const sock of recipientSockets) {
      sendTo(sock, 'typing:update', {
        conversationId,
        userId: ws.userId,
        isTyping,
      });
    }
  }
}

Client-side typing debounce

You don't want to send a WebSocket message on every keystroke. Debounce:

// Client-side (preview — covered fully in A6)
let typingTimeout: ReturnType<typeof setTimeout> | null = null;
let isCurrentlyTyping = false;

function handleTextChange(text: string) {
  setText(text);

  if (!isCurrentlyTyping) {
    isCurrentlyTyping = true;
    ws.send(JSON.stringify({ type: 'typing:start', payload: { conversationId } }));
  }

  // Reset the stop timer on every keystroke
  if (typingTimeout) clearTimeout(typingTimeout);
  typingTimeout = setTimeout(() => {
    isCurrentlyTyping = false;
    ws.send(JSON.stringify({ type: 'typing:stop', payload: { conversationId } }));
  }, 3000);  // stop after 3 seconds of no typing
}

The pattern:

  1. First keystroke → send typing:start
  2. Each subsequent keystroke → reset the 3-second timer
  3. After 3 seconds of silence → send typing:stop
  4. Also send typing:stop when the message is sent

Server-side typing timeout (safety net)

What if the client crashes without sending typing:stop? The recipient would see "typing..." forever. Add a server-side timeout:

// api/src/ws/handlers/typing.ts — enhanced
const typingTimers = new Map<string, ReturnType<typeof setTimeout>>();

export async function handleTypingStart(ws: AuthenticatedSocket, payload: TypingPayload) {
  const key = `${ws.userId}:${payload.conversationId}`;

  // Clear existing timer
  if (typingTimers.has(key)) {
    clearTimeout(typingTimers.get(key)!);
  }

  // Auto-stop after 5 seconds if no typing:stop received
  typingTimers.set(key, setTimeout(() => {
    forwardTypingEvent(ws, payload.conversationId, false);
    typingTimers.delete(key);
  }, 5000));

  await forwardTypingEvent(ws, payload.conversationId, true);
}

export async function handleTypingStop(ws: AuthenticatedSocket, payload: TypingPayload) {
  const key = `${ws.userId}:${payload.conversationId}`;
  if (typingTimers.has(key)) {
    clearTimeout(typingTimers.get(key)!);
    typingTimers.delete(key);
  }
  await forwardTypingEvent(ws, payload.conversationId, false);
}

Redis pub/sub — required, not optional

This section used to say Redis was a "when you grow" problem

It said: for Token v1 on a single VPS, in-memory is correct, add Redis when you need more than one machine. That is the ordinary advice and it is wrong for this project — ADR-0003 is titled "scale out ready, deploy on one box", and the entire point of it is that you build for N replicas and then run one.

The reason is asymmetric cost. Running Redis when you have one node buys nothing today and costs a container. Retrofitting it later means rewriting every place that reasoned from a local Map — which by then is the routing, the presence, the typing indicators and the rate limiting. And the failure it prevents is silent: add a second replica to an in-memory design and messages between users on different nodes are simply dropped, with nothing logged and no error raised.

So Redis is a required dependency from the first commit, alongside Postgres. Not a scaling milestone.

Each server publishes events to Redis; every server subscribes and forwards to whichever sockets it happens to hold.

// api/src/ws/fanout.ts
import Redis from 'ioredis';

const pub = new Redis();
const sub = new Redis();

// When user types on server A:
pub.publish('typing', JSON.stringify({ conversationId, userId, isTyping: true }));

// All servers (including B) receive:
sub.subscribe('typing');
sub.on('message', (channel, message) => {
  const data = JSON.parse(message);
  // Forward to local sockets for users in this conversation
});

Two details this snippet is too short to show, both covered by deliveryPlan in 0002: a subscriber hears its own publishes and must ignore them, and a message that arrived on the channel must never be republished. Neither can happen with one node running, which is exactly why they are worth getting right before there are two.

One thing genuinely does wait: zero-downtime deploys. Those need a second replica actually running, and that is a deployment change rather than a code change — which is the whole dividend of having built this way.

Privacy considerations for presence

Should the holder see when the issuer is online? The usual framing puts convenience against privacy — the holder knows when to expect a reply, against the issuer not wanting their schedule known. Framed that way it looks like a close call.

It is not close, because of who these two people are. The holder is a delivery company, an estate agent, a shop that wanted a phone number. The issuer is a person who declined to give them one. Presence is not a single fact — sampled over a fortnight it is a behavioural profile: when they wake, when they commute, which evenings they are out, when they are away for a week.

Deny by default, because that is what the product is

CLAUDE.md states Token's governing rule: nobody contacts the user unless the user issued them a token. Issuing a token to a courier grants one thing — a way to reach you about a parcel. It is not consent to a live feed of when you are at home.

So: the issuer's presence is not sent to holders. Not shown-by-default with a switch to turn it off. A privacy default that leaks is the behaviour of the product, whatever the settings screen offers — the same argument as ADR-0008, and it lands the same way here.

The asymmetry is deliberate and runs the other way: the issuer does see the holder's presence. The holder redeemed a code to transact with a business relationship they entered knowingly; the issuer is the party the product exists to protect. If that ever feels unfair, notice that the holder can close the page and be gone, while the issuer cannot un-disclose a fortnight of their movements.

// A per-token rule can OPEN this up, never close it -- the closed
// state is the default and needs no rule.
{ "rule_type": "share_presence", "payload": { "share": true } }

// Useful for the case that motivates it: a token issued to a friend
// or a family member, where presence is genuinely wanted.
// Rule storage is a B7 (Token Engine) concern.

Note the rule is named for what it grants. A hide_presence flag would mean the safe state is "no rule present", and a bug that loses the rules row would fail open. Naming the rule for the permission it adds makes a missing rule the safe answer.

Complete presence + typing integration

// api/src/ws/server.ts — final version with presence
import { WebSocketServer, WebSocket } from 'ws';
import { Server as HttpServer } from 'http';
import { verifyWsToken } from './auth';
import { setupHeartbeat } from './heartbeat';
import { handleMessage } from './router';
import { handleUserConnected, handleUserDisconnected } from './presence';
import { registerAllHandlers } from './handlers';

interface AuthenticatedSocket extends WebSocket {
  userId: number;
  isAlive: boolean;
}

const clients = new Map<number, Set<AuthenticatedSocket>>();

export function createWsServer(httpServer: HttpServer) {
  const wss = new WebSocketServer({ noServer: true });

  registerAllHandlers();

  httpServer.on('upgrade', async (request, socket, head) => {
    try {
      const userId = await verifyWsToken(request);
      wss.handleUpgrade(request, socket, head, (ws) => {
        const authWs = ws as AuthenticatedSocket;
        authWs.userId = userId;
        authWs.isAlive = true;
        wss.emit('connection', authWs, request);
      });
    } catch {
      socket.write('HTTP/1.1 401 Unauthorized\r\n\r\n');
      socket.destroy();
    }
  });

  wss.on('connection', (ws: AuthenticatedSocket) => {
    if (!clients.has(ws.userId)) clients.set(ws.userId, new Set());
    clients.get(ws.userId)!.add(ws);
    handleUserConnected(ws.userId);

    ws.on('message', (data) => handleMessage(ws, data));

    ws.on('close', () => {
      clients.get(ws.userId)?.delete(ws);
      if (clients.get(ws.userId)?.size === 0) clients.delete(ws.userId);
      handleUserDisconnected(ws.userId);
    });

    ws.on('pong', () => { ws.isAlive = true; });
  });

  setupHeartbeat(wss);
  return wss;
}

export function getClients() { return clients; }

Now build it yourself

Write canSeePresence(ctx) — the gate every presence broadcast passes through. It is where "deny by default" stops being a principle and becomes a line of code that either has an else returning false, or does not.
