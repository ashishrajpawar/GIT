Message Routing

B5 — Lesson 2 of 3 ~55 min
Why this matters for Token

When a token holder sends a message, it must reach the right user — and only that user. The routing logic maps a conversation to a set of sockets: the token issuer might be on their phone and tablet simultaneously, so the message fans out to both devices. If they're offline, it's stored for later delivery. This is the core of the chat system — the plumbing that makes messages appear instantly on the right screens.

The conversation model

In Token, a conversation is always between two parties: the token issuer (user) and a token holder (person who redeemed the token). Each redeemed token creates one conversation.

// From B2 — the conversations table
CREATE TABLE conversations (
  id            SERIAL PRIMARY KEY,
  token_id      INTEGER NOT NULL REFERENCES tokens(id),
  issuer_id     INTEGER NOT NULL REFERENCES users(id),
  holder_id     INTEGER NOT NULL REFERENCES users(id),
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  UNIQUE(token_id)  -- one conversation per token
);

CREATE TABLE messages (
  id              SERIAL PRIMARY KEY,
  conversation_id INTEGER NOT NULL REFERENCES conversations(id),
  sender_id       INTEGER NOT NULL REFERENCES users(id),
  text            TEXT NOT NULL,
  sent_at         TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  delivered_at    TIMESTAMPTZ,
  read_at         TIMESTAMPTZ
);

Routing a message

When user A sends a message in conversation C, the server must:

  1. Validate: is user A a participant in conversation C?
  2. Store the message in the database
  3. Find the OTHER participant (user B)
  4. Find ALL of user B's active WebSocket connections
  5. Send the message to each connection
  6. Also send to user A's OTHER devices (for multi-device sync)
// api/src/ws/handlers/chat.ts
import { db } from '../../db';
import { getClients } from '../server';
import { sendTo } from '../router';
import { WebSocket } from 'ws';

interface AuthenticatedSocket extends WebSocket {
  userId: number;
  isAlive: boolean;
}

interface ChatSendPayload {
  conversationId: number;
  text: string;
}

export async function handleChatSend(ws: AuthenticatedSocket, payload: ChatSendPayload) {
  const { conversationId, text } = payload;

  if (!conversationId || !text?.trim()) {
    sendTo(ws, 'error', { message: 'conversationId and text are required' });
    return;
  }

  // 1. Validate participation
  const conv = await db.query(
    'SELECT issuer_id, holder_id FROM conversations WHERE id = $1',
    [conversationId]
  );

  if (conv.rows.length === 0) {
    sendTo(ws, 'error', { message: 'Conversation not found' });
    return;
  }

  const { issuer_id, holder_id } = conv.rows[0];
  if (ws.userId !== issuer_id && ws.userId !== holder_id) {
    sendTo(ws, 'error', { message: 'Not a participant in this conversation' });
    return;
  }

  // 2. Store in database
  const result = await db.query(
    `INSERT INTO messages (conversation_id, sender_id, text)
     VALUES ($1, $2, $3)
     RETURNING id, conversation_id, sender_id, text, sent_at`,
    [conversationId, ws.userId, text.trim()]
  );
  const message = result.rows[0];

  // 3. Determine recipient
  const recipientId = ws.userId === issuer_id ? holder_id : issuer_id;

  // 4. Build the outgoing payload
  const outPayload = {
    id: message.id,
    conversationId: message.conversation_id,
    senderId: message.sender_id,
    text: message.text,
    sentAt: message.sent_at,
  };

  // 5. Send to recipient's devices
  deliverToUser(recipientId, 'chat:receive', outPayload);

  // 6. Send to sender's OTHER devices (multi-device sync)
  const senderSockets = getClients().get(ws.userId);
  if (senderSockets) {
    for (const sock of senderSockets) {
      if (sock !== ws) {
        sendTo(sock, 'chat:receive', outPayload);
      }
    }
  }

  // 7. Acknowledge to the sending socket
  sendTo(ws, 'chat:sent', { id: message.id, sentAt: message.sent_at });
}

function deliverToUser(userId: number, type: string, payload: unknown) {
  const sockets = getClients().get(userId);
  if (sockets) {
    for (const sock of sockets) {
      sendTo(sock, type, payload);
    }
  }
  // If no sockets — user is offline. Message is in the DB.
  // They'll fetch it via REST when they come back online.
}

Multi-device fan-out

A user might have the app open on their phone AND their tablet. The clients Map stores a Set of sockets per user — not a single socket:

// Map<userId, Set<AuthenticatedSocket>>
const clients = new Map();

// User 5 connects from phone:
// clients: { 5 => Set([phone-socket]) }

// User 5 connects from tablet:
// clients: { 5 => Set([phone-socket, tablet-socket]) }

// Message arrives for user 5:
// → Send to BOTH phone-socket AND tablet-socket

When the sender sends a message, they also need to see it on their OTHER devices. That's why step 6 sends to the sender's sockets except the one that sent it (they already know — they typed it).

Delivery acknowledgment

When the server successfully stores a message and routes it, it sends back a chat:sent acknowledgment to the sender. This lets the client:

  • Replace a temporary local ID with the server-assigned ID
  • Show a "sent" checkmark (✓)
  • Know the exact sentAt timestamp from the server
// Server → Sender
{ "type": "chat:sent", "payload": { "id": 456, "sentAt": "2026-08-07T12:00:00Z" } }

// Client updates its local message:
// { localId: "temp-123", status: "sending" }
// →
// { id: 456, status: "sent", sentAt: "2026-08-07T12:00:00Z" }

Delivery receipts

When the recipient's device receives the message, it sends back an acknowledgment:

// Client → Server (recipient's device)
{ "type": "chat:delivered", "payload": { "messageId": 456 } }

// Server updates the database and notifies the sender:
export async function handleChatDelivered(ws: AuthenticatedSocket, payload: { messageId: number }) {
  const { messageId } = payload;

  // Update delivery timestamp
  await db.query(
    'UPDATE messages SET delivered_at = NOW() WHERE id = $1 AND delivered_at IS NULL',
    [messageId]
  );

  // Notify the sender (for the ✓✓ checkmark)
  const msg = await db.query(
    'SELECT sender_id, conversation_id FROM messages WHERE id = $1',
    [messageId]
  );

  if (msg.rows.length > 0) {
    deliverToUser(msg.rows[0].sender_id, 'chat:delivery-receipt', {
      messageId,
      conversationId: msg.rows[0].conversation_id,
      deliveredAt: new Date().toISOString(),
    });
  }
}

sending → sent (server acknowledged) → delivered (recipient got it) → read (recipient opened it)

Offline message delivery

If the recipient is offline (no active WebSocket connections), the message is already stored in the database. When they reconnect, the client fetches missed messages via REST:

// Client — on WebSocket connect, fetch messages since last seen
GET /conversations/7/messages?after=2026-08-07T11:00:00Z

// Server returns all messages the client missed
// Client renders them in the thread

For v1, this simple approach works. The client tracks the timestamp of the last received message and fetches everything after it on reconnect. No complex offline queue on the server needed.

Authorization — who can message whom?

Not anyone can message anyone. The rules:

  • A conversation exists only between token issuer and token holder
  • The token must be active (not revoked or paused)
  • Access rules must allow it (time window, channel restrictions)
// Enhanced validation in handleChatSend:
async function validateCanSend(userId: number, conversationId: number): Promise<boolean> {
  const result = await db.query(
    `SELECT c.id, t.status
     FROM conversations c
     JOIN tokens t ON t.id = c.token_id
     WHERE c.id = $1
       AND (c.issuer_id = $2 OR c.holder_id = $2)
       AND t.status = 'active'`,
    [conversationId, userId]
  );

  return result.rows.length > 0;
}

// In handleChatSend, before storing:
const canSend = await validateCanSend(ws.userId, conversationId);
if (!canSend) {
  sendTo(ws, 'error', { message: 'Token is not active or you are not a participant' });
  return;
}

Note: Access rules (time windows, contact limits) are enforced here too — that's covered in B7 (Token Engine). For now, just check token status.

Error handling patterns

// Pattern: always send errors as structured messages, never throw
export async function handleChatSend(ws: AuthenticatedSocket, payload: ChatSendPayload) {
  try {
    // ... routing logic ...
  } catch (err) {

    sendTo(ws, 'error', {
      message: 'Failed to send message',
      code: 'CHAT_SEND_FAILED',
