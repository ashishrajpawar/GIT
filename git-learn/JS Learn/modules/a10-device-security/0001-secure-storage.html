Secure Storage

A10 — Lesson 1 of 2  |  ~35 min

Why this matters for Token: AsyncStorage writes data as plaintext files on the device filesystem. If someone gets physical access to a rooted/jailbroken phone (or even a locked phone with USB debugging enabled), they can read the JWT, refresh token, and any encryption keys you stored there. Token is a privacy app — its credibility depends on actually protecting secrets. expo-secure-store uses iOS Keychain and Android Keystore hardware-backed encryption so that even a rooted device cannot trivially extract these values.

AsyncStorage vs SecureStore

AsyncStorage SecureStore
Encryption None (plaintext JSON file) Hardware-backed (Keychain/Keystore)
Size limit 6 MB (Android default) 2048 bytes per item (iOS)
Use for Preferences, cache, non-sensitive data Refresh token, identity key — not the access token, which stays in memory
Availability Always available May fail after device wipe or restore
Speed Fast (file I/O) Slightly slower (crypto operations)

The rule is simple: if the value is a secret, use SecureStore. If it is a preference or cached UI state, use AsyncStorage.

Installing expo-secure-store

# In your app/ directory
npx expo install expo-secure-store

No additional native configuration needed with Expo managed workflow. The package uses iOS Keychain Services and Android EncryptedSharedPreferences (API 23+) or Keystore (API 18+).

Basic SecureStore API

import * as SecureStore from 'expo-secure-store';

// Store a value (must be a string, max 2048 bytes on iOS)
await SecureStore.setItemAsync('token_refresh', refreshToken);

// Retrieve a value (returns null if not found)
const token = await SecureStore.getItemAsync('token_refresh');

// Delete a value
await SecureStore.deleteItemAsync('token_refresh');

// Options: control when the item is accessible
// The refresh token has to be readable by a background refresh while the
// phone is in a pocket, so WHEN_UNLOCKED is too strict for it.
await SecureStore.setItemAsync('token_refresh', refreshToken, {
  keychainAccessible: SecureStore.AFTER_FIRST_UNLOCK,
});

// The identity private key is different, and the suffix is the whole point:
// THIS_DEVICE_ONLY keeps it out of iCloud Keychain and out of device
// backups. Without it, the key that makes messages unreadable to the server
// is quietly copied to Apple - see "When this breaks".
await SecureStore.setItemAsync('token_identity_key', privateKey, {
  keychainAccessible: SecureStore.WHEN_UNLOCKED_THIS_DEVICE_ONLY,
});

What to Store Where

// MEMORY ONLY — never written anywhere
//   accessToken   lives ~15 minutes. Persisting it creates a second copy
//                 to steal and saves the user nothing: if it is gone, the
//                 refresh token gets another in one request.

// SECURE STORE — secrets that must survive a restart
const SECURE_KEYS = {
  REFRESH_TOKEN: 'token_refresh',       // AFTER_FIRST_UNLOCK: background refresh
  IDENTITY_KEY:  'token_identity_key',  // THIS_DEVICE_ONLY: must never sync
  BIOMETRIC_SECRET: 'token_bio_secret',
};

// ASYNC STORAGE — non-sensitive preferences and cache
const STORAGE_KEYS = {
  THEME: '@token/theme',                // 'light' | 'dark'
  LAST_SYNC: '@token/last_sync',        // ISO timestamp
  ONBOARDING_DONE: '@token/onboarded',  // 'true'
  DRAFT_MESSAGE: '@token/draft',        // unsent message text
  NOTIFICATION_PREFS: '@token/notif',   // JSON of notification settings
};

Building a Secure Storage Wrapper

// app/src/services/secureStorage.ts
import * as SecureStore from 'expo-secure-store';

export class SecureStorageError extends Error {
  constructor(message: string, public readonly key: string) {
    super(message);
    this.name = 'SecureStorageError';
  }
}

/**
 * Wrapper around expo-secure-store with error handling
 * and JSON serialization for objects.
 */
export const secureStorage = {
  async set(key: string, value: string): Promise<void> {
    try {
      // .length counts UTF-16 code units, not bytes. "नमस्ते" is 6 units and
      // 18 bytes; an emoji is 2 units and 4 bytes. For an app built for the
      // Indian market, checking .length against a BYTE limit is a check that
      // passes right up until it fails on a real user's data.
      const bytes = new TextEncoder().encode(value).length;
      if (bytes > 2048) {
        throw new SecureStorageError(
          `Value exceeds the 2048-byte iOS limit (${bytes} bytes)`,
          key
        );
      }
      await SecureStore.setItemAsync(key, value);
    } catch (err) {
      if (err instanceof SecureStorageError) throw err;
      throw new SecureStorageError(
        `Failed to store key "${key}": ${(err as Error).message}`,
        key
      );
    }
  },

  async get(key: string): Promise<string | null> {
    try {
      return await SecureStore.getItemAsync(key);
    } catch (err) {
      // Keychain may be unavailable after device restore
      console.error(`SecureStore read failed for "${key}":`, err);
      return null;
    }
  },

  async remove(key: string): Promise<void> {
    try {
      await SecureStore.deleteItemAsync(key);
    } catch (err) {
      console.error(`SecureStore delete failed for "${key}":`, err);
    }
  },

  async setJSON(key: string, value: unknown): Promise<void> {
    const serialized = JSON.stringify(value);
    await this.set(key, serialized);
  },

  async getJSON<T>(key: string): Promise<T | null> {
    const raw = await this.get(key);
    if (!raw) return null;
    try {
      return JSON.parse(raw) as T;
    } catch {
      return null;
    }
  },
};

Migrating from AsyncStorage to SecureStore

// app/src/services/migrateSensitiveData.ts
import AsyncStorage from '@react-native-async-storage/async-storage';
import { secureStorage } from './secureStorage';

const MIGRATION_FLAG = '@token/secure_migration_v1';

/**
 * One-time migration: moves sensitive keys from AsyncStorage
 * to SecureStore. Safe to call multiple times — checks a flag.
 */
export async function migrateSensitiveData(): Promise<void> {
  const alreadyMigrated = await AsyncStorage.getItem(MIGRATION_FLAG);
  if (alreadyMigrated === 'done') return;

  // Session credentials are NOT migrated. They sat in plain text, so any
  // backup taken since still has them - moving them limits future exposure
  // and un-leaks nothing. Drop them and make the user log in again, which
  // issues fresh ones and lets the server revoke the old.
  await AsyncStorage.multiRemove(['@token/jwt', '@token/refresh']);

  // The identity key cannot be re-issued without losing the message
  // history, so it moves - and the device publishes a replacement key pair,
  // treating the old one as compromised.
  const keysToMigrate = [
    { asyncKey: '@token/e2e_key', secureKey: 'token_identity_key' },
  ];

  for (const { asyncKey, secureKey } of keysToMigrate) {
    const value = await AsyncStorage.getItem(asyncKey);
    if (value) {
      await secureStorage.set(secureKey, value);
      await AsyncStorage.removeItem(asyncKey); // Delete plaintext copy
    }
  }

  await AsyncStorage.setItem(MIGRATION_FLAG, 'done');
  console.log('Sensitive data migration complete');
}

Using SecureStore in the auth context

A4.2 already built AuthProvider, and this lesson deliberately does not build a second one. What changes here is only where the two values live: 

// The access token: a module variable. Gone when the app closes, which
// is fine - restoreSession() trades the refresh token for a new one.
let accessToken: string | null = null;
export const getAccessToken = () => accessToken;
export const setAccessToken = (t: string | null) => { accessToken = t; };

// The refresh token: SecureStore, readable by a background refresh.
export async function saveRefreshToken(token: string) {
  await SecureStore.setItemAsync('token_refresh', token, {
    keychainAccessible: SecureStore.AFTER_FIRST_UNLOCK,
  });
}

That is the whole integration. Everything else — the single in-flight refresh, telling offline apart from logged out, revoking the family on logout — is A3.2 and A4.2's job, and duplicating it here is how two versions drift apart.

Error Handling: When the Keychain is Unavailable

// After a device restore or factory reset, the Keychain may reject reads.
// Your app must handle this gracefully — force re-login.

// A read can fail for two completely different reasons and only one of
// them means the data is gone:
//
//   "not available right now"  - device locked, Keystore busy. TRANSIENT.
//   "not there any more"        - restored to a new device, keys dropped.
//
// Treating the first as the second is how you delete a private key because
// the phone was locked for a moment. Never destroy on a read failure.
async function safeGetRefreshToken(): Promise<string | null> {
  try {
    return await SecureStore.getItemAsync('token_refresh');
  } catch (err) {
    console.error('Keychain read failed:', err);
    return null;          // could not read. NOT the same as "does not exist".
  }
}

// Clearing is something the user asks for - logging out, or deleting their
// account - not something a failed read decides on their behalf.
async function clearSessionSecrets(): Promise<void> {
  // Note what is NOT in this list: the identity key. Deleting it makes every
  // message on this device permanently unreadable, so it is only removed by
  // an explicit "delete my account and my history" flow.
  for (const key of ['token_refresh', 'token_bio_secret']) {
    try {
      await SecureStore.deleteItemAsync(key);
    } catch {
      // Already gone, or unreadable. Either way there is nothing to do.
    }
  }
}

Why this way (and what was rejected)

The access token is not stored at all

Putting it in SecureStore looks strictly safer and is strictly worse. It lives fifteen minutes; persisting it creates a second copy to steal and saves the user nothing, because if it is missing the refresh token produces another one in a single request. A secret you do not write down cannot be read off the disk.

The refresh token is the one worth persisting, because losing it means a password prompt.

THIS_DEVICE_ONLY for the identity key

iOS Keychain items sync to iCloud Keychain by default, and both platforms include ordinary Keychain and Keystore entries in device backups. For a refresh token that is convenient — restore your phone, stay logged in.

For the E2EE identity key it quietly undoes the product's central claim. ADR-0002 says the server cannot read messages; a private key that syncs to iCloud is a key Apple holds a copy of. Nobody attacked anything. The default did it.

So the identity key is written with WHEN_UNLOCKED_THIS_DEVICE_ONLY: it never leaves the phone it was generated on, and a restored device gets no key at all. Which is the right behaviour — and it is exactly why key backup has to be a real, designed, user-controlled feature rather than something the platform does by accident.

A wrapper, not SecureStore everywhere

One module owns the key names, the byte-limit check, and the read/write policy. Scattering SecureStore.setItemAsync through the app means the accessibility flag is set correctly in four places and forgotten in the fifth, and the fifth is the one that ends up in iCloud.

When this breaks

A failed read that deletes a private key

The original error handler caught any read failure and called clearAllSecureData(), which deleted the E2EE key along with the tokens. But a Keychain read fails for two very different reasons:

  • Transient — the device is locked, or the Android Keystore is busy. The data is fine and will be readable in a moment.
  • Permanent — the app was restored onto a new device, so THIS_DEVICE_ONLY items are simply not there.

Treating the first as the second destroys every message on the device, permanently, because the phone was locked when a background task ran. There is no recovery: the key is what made the ciphertext readable. A read failure now returns null and deletes nothing; clearing is something the user asks for.

.length is not bytes

iOS caps a Keychain item at 2048 bytes, and value.length counts UTF-16 code units. नमस्ते is 6 units and 18 bytes; an emoji is 2 units and 4 bytes. A guard written against .length passes everything an English-speaking developer tests with and fails on a real user's data — which for an app built for the Indian market is not an edge case.

Migrating a secret does not un-leak it

The migration moves values out of AsyncStorage and deletes the plaintext. That limits future exposure and does nothing about the past: the value sat unencrypted in the app's sandbox for however long, and any device backup taken in that window still contains it. Deleting a file does not reach into a backup from March.

So a migration for something that was genuinely exposed is only half the job. Assume the old value is compromised and rotate it — force a re-login so every previously-stored refresh token is replaced, and revoke the old ones server-side. Moving it is housekeeping; rotating it is the fix.

The Keystore is unavailable while the device is locked

On Android, a background refresh on a locked phone can fail to read a value stored WHEN_UNLOCKED — a failure that has nothing to do with the network and everything to do with the pocket the phone is in. This is why the refresh token uses AFTER_FIRST_UNLOCK, and why "could not read the token" must not be treated as "the user is logged out".

What this costs you

DecisionWhat you pay
Identity key marked THIS_DEVICE_ONLY A user who restores to a new phone has no key and cannot read a single past message — including their own. That is not a bug to fix here; it is the requirement that makes key backup a v1 feature with a real design behind it (ADR-0002).
Access token in memory Every cold start does a refresh round trip before the first screen can load anything, so the launch path depends on the network. Worth it, and it is why the app needs a real loading state rather than a flash of the login screen.
SecureStore's 2048-byte limit Anything larger — a key bundle, a set of pre-keys, a cached credential blob — cannot go in directly. The pattern is to keep a random key in SecureStore and use it to encrypt the larger blob into ordinary storage, which is one more moving part to get right.
Async reads on both platforms Nothing secret is available synchronously, so startup has an unavoidable await before it knows whether anyone is logged in.
Never clearing on a read error A genuinely corrupted Keychain now leaves the app retrying something that will never work, instead of resetting itself. That is the right trade — a stuck app is recoverable, a deleted key is not — but it means a real "reset this device" action has to exist and be findable.
