FCM + APNs via Expo

B8 — Lesson 1 of 1  |  ~45 min

Why this matters for Token: Your WebSocket connection delivers messages and call signals in real time — but only while the app is open. The moment Ashish locks his phone, the socket dies. Without push notifications, an incoming call or a redeemed token message would vanish silently. FCM (Android) and APNs (iOS) are the OS-level wake-up mechanisms. Expo Notifications wraps both behind a single API so your server sends one request and it reaches both platforms.

How Push Notifications Work

The flow has four actors:

  1. Your app registers with the OS and gets a device-specific push token.
  2. Your server stores that push token in the users table.
  3. An event happens (new message, incoming call) — the server sends a payload to the Expo Push API.
  4. Expo's servers forward it to FCM or APNs, which wake the device and display the notification.
// Simplified flow
App boots → registerForPushNotifications() → push token → POST /api/push-token
Server event → expo push API → FCM/APNs → device notification → user taps → app opens

Registering for Push Notifications

// app/src/services/pushNotifications.ts
import * as Notifications from 'expo-notifications';
import * as Device from 'expo-device';
import Constants from 'expo-constants';
import { Platform } from 'react-native';

// Configure how notifications appear when app is in foreground
Notifications.setNotificationHandler({
  handleNotification: async () => ({
    shouldShowAlert: true,
    shouldPlaySound: true,
    shouldSetBadge: true,
  }),
});

export async function registerForPushNotifications(): Promise<string | null> {
  // Push tokens only work on physical devices
  if (!Device.isDevice) {
    console.warn('Push notifications require a physical device');
    return null;
  }

  // Check existing permission
  const { status: existingStatus } = await Notifications.getPermissionsAsync();
  let finalStatus = existingStatus;

  // Request permission if not already granted
  if (existingStatus !== 'granted') {
    const { status } = await Notifications.requestPermissionsAsync();
    finalStatus = status;
  }

  if (finalStatus !== 'granted') {
    console.warn('Push notification permission denied');
    return null;
  }

  // Get the Expo push token
  const projectId = Constants.expoConfig?.extra?.eas?.projectId;
  const tokenData = await Notifications.getExpoPushTokenAsync({ projectId });

  // Android needs a notification channel
  if (Platform.OS === 'android') {
    await Notifications.setNotificationChannelAsync('default', {
      name: 'Default',
      importance: Notifications.AndroidImportance.MAX,
      vibrationPattern: [0, 250, 250, 250],
      lightColor: '#4F46E5',
    });

    // High-priority channel for calls
    await Notifications.setNotificationChannelAsync('calls', {
      name: 'Incoming Calls',
      importance: Notifications.AndroidImportance.MAX,
      sound: 'ringtone.wav',
      vibrationPattern: [0, 500, 200, 500],
    });
  }

  return tokenData.data; // e.g. "ExponentPushToken[xxxxxx]"
}

Server-Side: Sending Push Notifications

// api/src/services/pushService.ts
import { Expo, ExpoPushMessage } from 'expo-server-sdk';

const expo = new Expo();

interface PushPayload {
  userId: string;            // whose device this is — needed to clear it later
  pushToken: string;
  title: string;
  body: string;
  data?: Record<string, unknown>;
  channelId?: string;
  // ABSOLUTE unread count, not a flag and not an increment. Omit it when
  // you do not know; see the callout below.
  badge?: number;
  sound?: 'default' | string;
  priority?: 'default' | 'high';
  mutableContent?: boolean;  // let the device rewrite title/body
}

export async function sendPushNotification(payload: PushPayload): Promise<void> {
  const { userId, pushToken, title, body, data, channelId, badge, sound, priority } = payload;

  // Validate the token format. Log that it was malformed, never the value:
  // a push token is a capability to put text on someone's lock screen, and
  // ADR-0007's rule about codes in logs is the same rule.
  if (!Expo.isExpoPushToken(pushToken)) {
    logger.warn({ userId, tokenSuffix: pushToken.slice(-6) }, 'malformed push token');
    return;
  }

  const message: ExpoPushMessage = {
    to: pushToken,
    title,
    body,
    data: data || {},
    channelId: channelId || 'default',
    // NOT `badge ?? 1`. See the badge callout below.
    ...(badge === undefined ? {} : { badge }),
    sound: sound || 'default',
    priority: priority || 'high',
    ...(payload.mutableContent ? { mutableContent: true } : {}),
  };

  try {
    const [ticket] = await expo.sendPushNotificationsAsync([message]);

    if (ticket.status === 'error') {
      // A ticket error is a REFUSAL: Expo would not accept the message.
      logger.warn({ userId, detail: ticket.details?.error }, 'push rejected');
      if (ticket.details?.error === 'DeviceNotRegistered') {
        await clearPushToken(userId);
      }
      return;
    }

    // status === 'ok' means ACCEPTED FOR DELIVERY, and nothing more.
    // Whether it arrived is a separate question with a separate answer,
    // which is why the id is written down rather than discarded.
    await db.query(
      `INSERT INTO push_receipts (ticket_id, user_id, created_at)
       VALUES ($1, $2, NOW())`,
      [ticket.id, userId]
    );
  } catch (err) {
    logger.error({ err, userId }, 'expo push api error');
  }
}

// Runs on a schedule, at least 15 minutes behind the sends. This is where
// DeviceNotRegistered actually turns up for a device that uninstalled.
export async function reconcilePushReceipts(): Promise<void> {
  const { rows } = await db.query(
    `SELECT ticket_id, user_id FROM push_receipts
      WHERE created_at < NOW() - interval '15 minutes'
      LIMIT 1000`
  );
  if (rows.length === 0) return;

  const byTicket = new Map(rows.map((r) => [r.ticket_id, r.user_id]));

  for (const chunk of expo.chunkPushNotificationReceiptIds([...byTicket.keys()])) {
    const receipts = await expo.getPushNotificationReceiptsAsync(chunk);

    for (const [ticketId, receipt] of Object.entries(receipts)) {
      if (receipt.status === 'error' &&
          receipt.details?.error === 'DeviceNotRegistered') {
        await clearPushToken(byTicket.get(ticketId)!);
      }
      await db.query('DELETE FROM push_receipts WHERE ticket_id = $1', [ticketId]);
    }
  }
}

// Clear by USER, not by token value: the device may already have
// registered a new token, and matching on the old string would either
// miss the row or wipe whatever replaced it.
async function clearPushToken(userId: string): Promise<void> {
  await db.query('UPDATE users SET push_token = NULL WHERE id = $1', [userId]);
}

The ticket ids have to live somewhere between the send and the reconciliation, so that is a table: 

-- api/migrations/0012_push_receipts.sql
CREATE TABLE push_receipts (
  ticket_id  TEXT PRIMARY KEY,
  user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- The reconciler reads oldest-first and deletes as it goes, so this is
-- the only index it needs.
CREATE INDEX idx_push_receipts_created_at ON push_receipts(created_at);

-- A row here is a question waiting for an answer, never a permanent
-- record. If the reconciler is down for a day the table grows and then
-- drains; if it is down for a month, these are stale and worth dropping
-- rather than querying -- Expo does not keep receipts indefinitely.
A ticket says Expo accepted it. Only the receipt says the device exists.

This function used to check ticket.details?.error for DeviceNotRegistered and stop there. That check is not wrong, it is in the wrong place for the case that matters: Expo cannot know the device is gone at the moment it accepts your message. It finds out from Apple or Google afterwards, and it tells you in a receipt that you have to go and fetch, using the ticket id you were handed and probably threw away.

So the branch fires for a token that was malformed on arrival, and never for the ordinary case — a user who uninstalled the app. Nothing errors, every send reports success, and the dead tokens accumulate for ever, each one costing an API call per notification and slowly turning the push budget into a tax on people who left.

This is a two-phase result, and it has the shape this course keeps meeting: accepted, delivered, and failed are three states, and a ticket only distinguishes the first from the third. The middle one arrives later or not at all, which is exactly why it needs a row in a table rather than a variable in a request handler.

Notification Payloads for Messages vs Calls

// api/src/services/pushService.ts (continued)

export async function notifyNewMessage(
  recipientToken: string,
  holderName: string,        // from the holder JWT — the server DOES know this
  conversationId: string,
  sealed: { ciphertext: string; nonce: string; keyVersion: number },
  unreadCount: number | null
): Promise<void> {
  await sendPushNotification({
    pushToken: recipientToken,
    // The most this server can honestly say. It has never seen the text.
    title: `Message from ${holderName}`,
    body: 'Tap to read',
    data: {
      type: 'message',
      conversationId,
      // Base64 of the same bytes the database holds. Google and Apple
      // route them; only the device can open them.
      ...sealed,
    },
    // iOS: hand the payload to the Notification Service Extension, which
    // decrypts on-device and REWRITES title and body before it is shown.
    // Android: a data-only message plus a local notification posted from
    // the background handler.
    mutableContent: true,
    channelId: 'default',
    sound: 'default',
    badge: unreadCount ?? undefined,
  });
}

export async function notifyIncomingCall(
  recipientToken: string,
  callerName: string,
  callId: string,
  tokenLabel: string          // the LABEL, never the code
): Promise<void> {
  await sendPushNotification({
    pushToken: recipientToken,
    title: 'Incoming Call',
    body: `${callerName} is calling via ${tokenLabel}`,
    data: {
      type: 'call',
      callId,
      conversationId: callId,   // the app looks the rest up itself
    },
    channelId: 'calls',
    sound: 'ringtone.wav',
    priority: 'high',
  });
}
There is no preview, and there never can be — this function used to take one

The old signature was notifyNewMessage(token, senderName, preview, conversationId) and it put preview.substring(0, 100) in the notification body. Nothing on the server can fill that parameter. b2/0002's messages table stores ciphertext BYTEA under a comment that says it plainly: "the server stores these bytes and holds no key for them — everything ABOUT the message, its text, its type, an image's dimensions, is inside here."

So the callout below warns you not to put a token code in a push payload, and this function put the message in one. A leaked code is a capability, and revoking the token takes it back. A leaked message body is the thing ADR-0002 exists to protect, and nothing takes it back.

What this server knows, and what it does not:

  • Knows: the holder's display name — they typed it at redemption and it is already in the holder JWT — the token's label, conversation and token ids, timestamps, and unread counts.
  • Does not know, ever: a single character of any message.

That leaves two honest designs, and Token uses the second: send a generic notification, or send the ciphertext and let the device render it — an iOS Notification Service Extension, or an Android data-only message handled in the background. It is what Signal and WhatsApp do, and it is why mutableContent is set above.

The fallback has to be safe on its own. An extension can time out, run out of memory, or simply not exist on an older build — and what the user sees then is exactly the title and body the server sent. That is why those two fields say "Message from Ravi" and "Tap to read" rather than being left blank for the device to fill in: a notification must be publishable as sent, because sometimes it is sent as written.

It also needs EAS Build. An extension is native code, so Expo Go cannot run it — the same constraint WebRTC imposes in A7.

Never put a token code in a push notification

The earlier version of this function took a tokenCode and put it in two places: the visible body text, and the data payload. Both are wrong, and for different reasons.

The payload goes through Google and Apple. FCM and APNs are the one third party this architecture accepts, and the bargain is narrow: they route bytes and learn that a device received something. Put a token code in there and you have handed a live capability — anything that can read it can redeem it — to a company that is explicitly outside the trust boundary. It is also stored on their servers until the device collects it.

The body appears on a locked screen. "Ravi is calling via MERC-8GH2-KP4X" is readable by anyone who can see the phone, and it goes into the notification history the OS keeps.

Send the label the issuer chose — "courier", "estate agent" — which is what they wanted to see anyway, and identifiers the app can resolve against its own database. The rule from ADR-0007 is that the code is never logged, and a push payload is a log held by someone else.

Handling Notification Taps

// app/src/services/pushNotifications.ts (continued)
import { useEffect, useRef } from 'react';
import { useNavigation } from '@react-navigation/native';

export function useNotificationListeners() {
  const navigation = useNavigation();
  const notificationListener = useRef<any>();
  const responseListener = useRef<any>();

  useEffect(() => {
    // Fires when notification arrives while app is in foreground
    notificationListener.current =
      Notifications.addNotificationReceivedListener((notification) => {
        const data = notification.request.content.data;
        // Update badge or show in-app indicator
        console.log('Foreground notification:', data);
      });

    // Fires when user taps the notification
    responseListener.current =
      Notifications.addNotificationResponseReceivedListener((response) => {
        const data = response.notification.request.content.data;

        if (data.type === 'message') {
          navigation.navigate('Messages', {
            screen: 'MessageThread',
            params: { conversationId: data.conversationId },
          });
        } else if (data.type === 'call') {
          navigation.navigate('Calls', {
            callId: data.callId,
          });
        }
      });

    return () => {
      if (notificationListener.current) {
        Notifications.removeNotificationSubscription(notificationListener.current);
      }
      if (responseListener.current) {
        Notifications.removeNotificationSubscription(responseListener.current);
      }
    };
  }, [navigation]);
}

Badge Count Management

// Reset badge when app opens
import * as Notifications from 'expo-notifications';
import { AppState } from 'react-native';

export function useBadgeReset() {
  useEffect(() => {
    const subscription = AppState.addEventListener('change', (state) => {
      if (state === 'active') {
        Notifications.setBadgeCountAsync(0);
      }
    });

    // Also reset on initial mount
    Notifications.setBadgeCountAsync(0);

    return () => subscription.remove();
  }, []);
}

// The badge is an ABSOLUTE number the OS displays, so the server has to
// send the real count. There is no recipient_id on `messages` -- b2/0002
// gives it conversation_id and sender_type, and a conversation reaches its
// owner through the token. Unread FOR THE OWNER means messages the HOLDER
// sent, which is what the sender_type filter is doing.
export async function getUnreadCount(userId: string): Promise<number> {
  const result = await db.query(
    `SELECT COUNT(*) AS count
       FROM messages m
       JOIN conversations c ON c.id = m.conversation_id
       JOIN tokens t       ON t.id = c.token_id
      WHERE t.user_id = $1
        AND m.sender_type = 'holder'
        AND m.read_at IS NULL`,
    [userId]
  );
  return parseInt(result.rows[0].count, 10);
}
Two defects met in this section, and the second one was sitting four lines from its own fix

The query read messages.recipient_id, which does not exist. b2/0002 gives messages an id, a conversation_id, a sender_type, the sealed body and three timestamps — and no recipient, because a message belongs to a conversation and a conversation belongs to a token. The count has to travel that path. Same shape as b7/0002 reading a tokens.rules column b2/0001 never creates: it type-checks, it reads correctly, and it throws the first time it runs.

And sendPushNotification hardcoded badge: badge ?? 1 — so the badge read "1" with nine messages waiting, while the function that computes the true number sat unused a few lines below. Third time in three days that a lesson has held both the right and the wrong version of the same thing.

Omitting the badge and sending zero are different instructions. Zero clears it; omitting it leaves whatever is there alone. So an unknown count must be left out, never defaulted — the same null-versus-zero distinction as max_uses, arriving as a number the user reads off their home screen.

Silent Notifications for Data Sync

// Silent notification — no alert, just data
export async function sendSilentSync(
  userId: string,
  pushToken: string,
  syncType: string
): Promise<void> {
  await sendPushNotification({
    userId,
    pushToken,
    title: '',
    body: '',
    data: {
      type: 'silent-sync',
      syncType,
      // THIS is what makes it silent on iOS, and it has to be IN the
      // payload. A comment saying it triggers background fetch does not
      // send it.
      _contentAvailable: true,
    },
    // Normal priority keeps the screen dark. High priority on a silent
    // push is also how you get rate-limited by APNs.
    priority: 'default',
    // No badge key at all: a sync is not an unread message, and a badge
    // here would overwrite a count this call knows nothing about.
  });
}

// Client handler for silent notifications
Notifications.setNotificationHandler({
  handleNotification: async (notification) => {
    const data = notification.request.content.data;

    if (data.type === 'silent-sync') {
      // Trigger background data refresh
      await syncLocalDatabase(data.syncType);
      return {
        shouldShowAlert: false,
        shouldPlaySound: false,
        shouldSetBadge: false,
      };
    }

    return {
      shouldShowAlert: true,
      shouldPlaySound: true,
      shouldSetBadge: true,
    };
  },
});
The comment described a field the code did not send

This block carried the line "_contentAvailable triggers background fetch on iOS" directly above a payload that never included _contentAvailable. Without it iOS treats the push as an ordinary alert with an empty title and an empty body — so instead of a silent sync the user gets a blank notification, and the background handler it was written for never runs.

Same shape as b1/0003 creating the redundant index its own next line warned against: a comment beside code is not evidence about the code, and the two drift apart in whichever direction nobody executes.

A push payload leaves your trust boundary twice over — it goes through Google or Apple, and it lands on a lock screen anybody standing nearby can read.
