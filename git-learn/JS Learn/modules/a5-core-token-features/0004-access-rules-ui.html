Access Rules UI

A5 — Lesson 4 of 5 ~55 min
Why this matters for Token

Access rules are what make Token more than a glorified contact card. A user doesn't just share a code — they define what the holder can do with it. Time windows ("only reach me 9am–6pm"), contact limits ("max 3 messages per day"), category restrictions ("text only, no calls"). Rules are enforced server-side (B7), but the UI for setting them lives here. This is where the user feels in control.

The access_rules schema (recap from B2)

From the schema design module, each rule is stored as a row in access_rules:

CREATE TABLE access_rules (
  id          SERIAL PRIMARY KEY,
  token_id    INTEGER NOT NULL REFERENCES tokens(id) ON DELETE CASCADE,
  rule_type   TEXT NOT NULL
              -- 'expiry' is NOT a rule: it is expires_at on the token itself
              -- (B7.1). Two places to set the same thing is two answers to
              -- "when does this stop working?".
              CHECK (rule_type IN ('time_window', 'contact_limit', 'channel_restrict')),
  payload     JSONB NOT NULL,
  enabled     BOOLEAN NOT NULL DEFAULT TRUE,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

The payload is JSONB — each rule type has a different shape:

// time_window
{ "days": [1,2,3,4,5], "start_time": "09:00", "end_time": "18:00", "timezone": "Asia/Kolkata" }

// contact_limit
{ "max_per_day": 3, "type": "messages" }  // or "calls"

// channel_restrict
{ "allowed": ["text"], "blocked": ["voice", "video"] }

// expiry
{ "expires_at": "2026-09-01T00:00:00.000Z" }

TypeScript types for rules

// shared/src/rules.ts

// These names are the contract with the rules engine in B7.2. It reads
// rule.start_time; a client that writes rule.start produces `undefined` on
// the server - see "When this breaks".
export type RuleType = 'time_window' | 'contact_limit' | 'channel_restrict';

export interface TimeWindowPayload {
  days: number[];         // 0=Sun, 1=Mon, ... 6=Sat
  start_time: string;     // "HH:MM" 24h
  end_time: string;       // "HH:MM" 24h - may be EARLIER than start (overnight)
  timezone: string;       // IANA, e.g. 'Asia/Kolkata'
}

export interface ContactLimitPayload {
  max_messages_per_day: number;
  max_calls_per_day: number;
}

// One list, not two. `allowed` and `blocked` can disagree, and then the
// screen and the engine have to decide which wins - a question with no
// good answer that simply should not exist.
export interface ChannelRestrictPayload {
  allow_text: boolean;
  allow_voice: boolean;
  allow_video: boolean;
}

export interface ExpiryPayload {
  expires_at: string;   // ISO 8601
}

export type RulePayload =
  | TimeWindowPayload
  | ContactLimitPayload
  | ChannelRestrictPayload
  | ExpiryPayload;

export interface AccessRule {
  id: number;
  token_id: number;
  rule_type: RuleType;
  payload: RulePayload;
  enabled: boolean;
  created_at: string;
}

The AccessRuleEditor component

This is a modal or bottom sheet where users configure rules for a token. Each rule type has its own form section:

// app/src/components/AccessRuleEditor.tsx
import { useState } from 'react';
import {
  View, Text, Switch, TouchableOpacity, StyleSheet, ScrollView,
} from 'react-native';
import { AccessRule, RuleType } from '@token/shared/rules';

interface AccessRuleEditorProps {
  tokenId: number;
  existingRules: AccessRule[];
  onSave: (rules: AccessRule[]) => void;
  onClose: () => void;
}

export function AccessRuleEditor({ tokenId, existingRules, onSave, onClose }: AccessRuleEditorProps) {
  const [rules, setRules] = useState<AccessRule[]>(existingRules);

  return (
    <ScrollView style={styles.container}>
      <Text style={styles.heading}>Access Rules</Text>
      <Text style={styles.subtext}>
        Control when and how this token's holder can reach you.
      </Text>

      <TimeWindowSection
        rule={rules.find(r => r.rule_type === 'time_window')}
        tokenId={tokenId}
        onUpdate={updated => updateRule(updated)}
      />

      <ContactLimitSection
        rule={rules.find(r => r.rule_type === 'contact_limit')}
        tokenId={tokenId}
        onUpdate={updated => updateRule(updated)}
      />

      <ChannelRestrictSection
        rule={rules.find(r => r.rule_type === 'channel_restrict')}
        tokenId={tokenId}
        onUpdate={updated => updateRule(updated)}
      />

      <TouchableOpacity style={styles.doneButton} onPress={onClose}>
        <Text style={styles.doneButtonText}>Done</Text>
      </TouchableOpacity>
    </ScrollView>
  );

  function updateRule(updated: AccessRule) {
    setRules(prev => {
      const idx = prev.findIndex(r => r.id === updated.id);
      if (idx >= 0) {
        const copy = [...prev];
        copy[idx] = updated;
        return copy;
      }
      return [...prev, updated];
    });
  }
}

Time Window rule editor

The most complex rule UI. Users pick which days and what hours:

// app/src/components/rules/TimeWindowSection.tsx
import { useState } from 'react';
import { View, Text, TouchableOpacity, Switch, StyleSheet } from 'react-native';
import { TimeWindowPayload } from '@token/shared/rules';
import { apiRequest } from '../../api/client';

const DAYS = ['Sun', 'Mon', 'Tue', 'Wed', 'Thu', 'Fri', 'Sat'];

interface TimeWindowSectionProps {
  tokenId: number;
  rule?: { id: number; payload: TimeWindowPayload; enabled: boolean };
  onUpdate: (rule: any) => void;
}

export function TimeWindowSection({ tokenId, rule, onUpdate }: TimeWindowSectionProps) {
  const [enabled, setEnabled] = useState(rule?.enabled ?? false);
  const [days, setDays] = useState<number[]>(rule?.payload.days ?? [1,2,3,4,5]);
  const [start, setStart] = useState(rule?.payload.start ?? '09:00');
  const [end, setEnd] = useState(rule?.payload.end ?? '18:00');

  function toggleDay(day: number) {
    setDays(prev =>
      prev.includes(day) ? prev.filter(d => d !== day) : [...prev, day].sort()
    );
  }

  async function handleSave() {
    const payload: TimeWindowPayload = {
      days,
      start_time: start,
      end_time: end,
      // The token's timezone is stored WITH the rule, not read from the
      // device. A user in London still has their tokens behave on the hours
      // they set at home - see "Why this way".
      timezone: tokenTimezone,
    };

    if (rule) {
      // Update existing
      const res = await apiRequest('PATCH', `/tokens/${tokenId}/rules/${rule.id}`, {
        payload,
        enabled,
      });
      onUpdate(res.data);
    } else {
      // Create new
      const res = await apiRequest('POST', `/tokens/${tokenId}/rules`, {
        rule_type: 'time_window',
        payload,
      });
      onUpdate(res.data);
    }
  }

  return (
    <View style={styles.section}>
      <View style={styles.sectionHeader}>
        <Text style={styles.sectionTitle}>Time Window</Text>
        <Switch
          value={enabled}
          onValueChange={val => { setEnabled(val); if (rule) handleSave(); }}
        />
      </View>
      <Text style={styles.sectionDesc}>
        Only allow contact during specific hours
      </Text>

      {enabled && (
        <View>
          <View style={styles.dayRow}>
            {DAYS.map((name, idx) => (
              <TouchableOpacity
                key={idx}
                style={[styles.dayChip, days.includes(idx) && styles.dayChipActive]}
                onPress={() => toggleDay(idx)}
              >
                <Text style={[styles.dayText, days.includes(idx) && styles.dayTextActive]}>
                  {name}
                </Text>
              </TouchableOpacity>
            ))}
          </View>

          <View style={styles.timeRow}>
            <TimeInput label="From" value={start} onChange={setStart} />
            <Text style={styles.timeSeparator}>to</Text>
            <TimeInput label="Until" value={end} onChange={setEnd} />
          </View>

          <TouchableOpacity style={styles.saveButton} onPress={handleSave}>
            <Text style={styles.saveButtonText}>Save</Text>
          </TouchableOpacity>
        </View>
      )}
    </View>
  );
}

Channel Restrict rule editor

// app/src/components/rules/ChannelRestrictSection.tsx
import { useState } from 'react';
import { View, Text, Switch, StyleSheet } from 'react-native';

const CHANNELS = ['text', 'voice', 'video'] as const;

export function ChannelRestrictSection({ tokenId, rule, onUpdate }) {
  const [enabled, setEnabled] = useState(rule?.enabled ?? false);
  const [allowed, setAllowed] = useState<string[]>(
    rule?.payload.allowed ?? ['text', 'voice', 'video']
  );

  function toggleChannel(channel: string) {
    setAllowed(prev =>
      prev.includes(channel)
        ? prev.filter(c => c !== channel)
        : [...prev, channel]
    );
  }

  return (
    <View style={styles.section}>
      <View style={styles.sectionHeader}>
        <Text style={styles.sectionTitle}>Channel Restrictions</Text>
        <Switch value={enabled} onValueChange={setEnabled} />
      </View>
      <Text style={styles.sectionDesc}>
        Choose which communication channels this token allows
      </Text>

      {enabled && (
        <View style={styles.channelList}>
          {CHANNELS.map(channel => (
            <View key={channel} style={styles.channelRow}>
              <Text style={styles.channelLabel}>
                {channel.charAt(0).toUpperCase() + channel.slice(1)}
              </Text>
              <Switch
                value={allowed.includes(channel)}
                onValueChange={() => toggleChannel(channel)}
              />
            </View>
          ))}
          {allowed.length === 0 && (
            <Text style={styles.warningText}>
              ⚠ No channels allowed — the holder won't be able to contact you at all.
            </Text>
          )}
        </View>
      )}
    </View>
  );
}

Composing rules on the TokenDetail screen

// app/src/screens/TokenDetail.tsx — rules section
import { useState, useEffect } from 'react';
import { View, Text, TouchableOpacity, Modal } from 'react-native';
import { AccessRuleEditor } from '../components/AccessRuleEditor';
import { AccessRule } from '@token/shared/rules';
import { apiRequest } from '../api/client';

function TokenDetailScreen({ route }) {
  const { token } = route.params;
  const [rules, setRules] = useState<AccessRule[]>([]);
  const [showEditor, setShowEditor] = useState(false);

  useEffect(() => {
    apiRequest<{ data: AccessRule[] }>('GET', `/tokens/${token.id}/rules`)
      .then(res => setRules(res.data));
  }, [token.id]);

  return (
    <View>
      {/* ... code, QR, status ... */}

      <View style={styles.rulesSection}>
        <Text style={styles.rulesHeading}>Access Rules</Text>
        {rules.length === 0 ? (
          <Text style={styles.noRules}>No restrictions — holder has full access</Text>
        ) : (
          rules.map(rule => <RuleSummary key={rule.id} rule={rule} />)
        )}
        <TouchableOpacity
          style={styles.editRulesButton}
          onPress={() => setShowEditor(true)}
        >
          <Text style={styles.editRulesText}>Edit Rules</Text>
        </TouchableOpacity>
      </View>

      <Modal visible={showEditor} animationType="slide">
        <AccessRuleEditor
          tokenId={token.id}
          existingRules={rules}
          onSave={setRules}
          onClose={() => setShowEditor(false)}
        />
      </Modal>
    </View>
  );
}

Rule summary display

On the TokenDetail screen, show a compact summary of each active rule:

function RuleSummary({ rule }: { rule: AccessRule }) {
  if (!rule.enabled) return null;

  const summaries: Record<string, string> = {
    time_window: formatTimeWindow(rule.payload as TimeWindowPayload),
    contact_limit: formatContactLimit(rule.payload as ContactLimitPayload),
    channel_restrict: formatChannelRestrict(rule.payload as ChannelRestrictPayload),
    expiry: formatExpiry(rule.payload as ExpiryPayload),
  };

  return (
    <View style={styles.ruleSummary}>
      <View style={styles.ruleIcon}>
        <Text>{ruleIcons[rule.rule_type]}</Text>
      </View>
      <Text style={styles.ruleText}>{summaries[rule.rule_type]}</Text>
    </View>
  );
}

function formatTimeWindow(p: TimeWindowPayload): string {
  const dayNames = ['Sun','Mon','Tue','Wed','Thu','Fri','Sat'];
  const dayStr = p.days.map(d => dayNames[d]).join(', ');
  return `${dayStr} · ${p.start}–${p.end}`;
}

function formatContactLimit(p: ContactLimitPayload): string {
  return `Max ${p.max_per_day} ${p.type}/day`;
}

function formatChannelRestrict(p: ChannelRestrictPayload): string {
  return `${p.allowed.join(', ')} only`;
}

function formatExpiry(p: ExpiryPayload): string {
  return `Expires ${new Date(p.expires_at).toLocaleDateString()}`;
}

Server-side rules endpoints

// api/src/routes/rules.ts
import { Router } from 'express';
import { requireAuth } from '../middleware/auth';
import { db } from '../db';
import { z } from 'zod';

const router = Router();

const ruleSchema = z.object({
  rule_type: z.enum(['time_window', 'contact_limit', 'channel_restrict', 'expiry']),
  payload: z.record(z.unknown()),
  enabled: z.boolean().optional().default(true),
});

// List rules for a token
router.get('/tokens/:tokenId/rules', requireAuth, async (req, res) => {
  const { tokenId } = req.params;

  // Verify token belongs to user
  const token = await db.query(
    'SELECT id FROM tokens WHERE id = $1 AND user_id = $2',
    [tokenId, req.user.id]
  );
  if (token.rows.length === 0) {
    return res.status(404).json({ error: 'Token not found' });
  }

  const rules = await db.query(
    'SELECT * FROM access_rules WHERE token_id = $1 ORDER BY created_at',
    [tokenId]
  );
  res.json({ data: rules.rows });
});

// Add a rule
router.post('/tokens/:tokenId/rules', requireAuth, async (req, res) => {
  const { tokenId } = req.params;
  const parsed = ruleSchema.safeParse(req.body);
  if (!parsed.success) {
    return res.status(400).json({ error: parsed.error.issues[0].message });
  }

  // Verify ownership
  const token = await db.query(
    'SELECT id FROM tokens WHERE id = $1 AND user_id = $2',
    [tokenId, req.user.id]
  );
  if (token.rows.length === 0) {
    return res.status(404).json({ error: 'Token not found' });
  }

  const { rule_type, payload, enabled } = parsed.data;
  const result = await db.query(
    `INSERT INTO access_rules (token_id, rule_type, payload, enabled)
     VALUES ($1, $2, $3, $4)
     RETURNING *`,
    [tokenId, rule_type, JSON.stringify(payload), enabled]
  );

  res.status(201).json({ data: result.rows[0] });
});

// Update a rule
router.patch('/tokens/:tokenId/rules/:ruleId', requireAuth, async (req, res) => {
  const { tokenId, ruleId } = req.params;
  const { payload, enabled } = req.body;

  const result = await db.query(
    `UPDATE access_rules
     SET payload = COALESCE($1, payload), enabled = COALESCE($2, enabled)
     WHERE id = $3 AND token_id = $4
     RETURNING *`,
    [payload ? JSON.stringify(payload) : null, enabled ?? null, ruleId, tokenId]
  );

  if (result.rows.length === 0) {
    return res.status(404).json({ error: 'Rule not found' });
  }
  res.json({ data: result.rows[0] });
});

// Delete a rule
router.delete('/tokens/:tokenId/rules/:ruleId', requireAuth, async (req, res) => {
  const { tokenId, ruleId } = req.params;
  await db.query(
    'DELETE FROM access_rules WHERE id = $1 AND token_id = $2',
    [ruleId, tokenId]
  );
  res.status(204).end();
});

export default router;

UX principles for rule configuration

  1. Off by default — every rule section starts with a toggle OFF. The user opts in to restrictions, not out.
  2. Sensible defaults when enabled — when a user enables "Time Window", pre-fill Mon–Fri 9am–6pm. They can adjust, but the common case is one tap.
  3. Immediate feedback — show a plain-language summary: "Reachable Mon–Fri, 9:00am to 6:00pm IST"
  4. Warn on empty — if all channels are disabled, warn: "This token won't allow any contact." If the time window has no days selected, warn.
  5. Save on change — no "Save All" button at the bottom. Each rule section saves when the user changes it. Reduces data loss if they back-navigate.

Why this way (and what was rejected)

The timezone is stored with the rule, not read from the device

Intl.DateTimeFormat().resolvedOptions().timeZone gives the device's current zone, and using it would be wrong in a way that only appears on holiday. A user sets "contactable 9 to 6" at home in Bengaluru, then flies to London. Read the device and their tokens silently shift five and a half hours — the delivery driver in Bengaluru can now reach them at 2:30pm local, which is not what they agreed to, and nothing on screen has changed.

Storing the zone with the rule means the token keeps behaving the way it was configured. It also means the UI has to show the zone, or the same user will wonder why their rules look wrong while they are away.

Rules only ever narrow

Every rule is combined with AND (B7.2), so adding one can only take access away. That is worth surfacing in the interface, not just the engine: a user experimenting with restrictions can never accidentally grant something, which is what makes it safe to let them experiment.

It also fixes the copy. "Allow calls between 9 and 6" is misleading — the rule does not allow anything. "Block calls outside 9 to 6" is what it does, and the difference matters the moment a second rule exists.

One list of channels, not allowed and blocked

Two lists can disagree — allowed: ['voice'] with blocked: ['voice'] is representable, and then the screen and the engine each have to decide which wins. Three booleans cannot contradict themselves, and the state that cannot exist needs no rule for resolving it.

When this breaks

The client and the engine disagreed about field names

This lesson wrote { start, end }. B7.2 reads rule.start_time and rule.end_time. Both files are internally consistent, both look right in review, and together they produce a rule that does nothing resembling what the user set — the engine compares the current time against undefined, and depending on the comparison either allows everything or blocks everything.

Nothing throws. The user sees their time window saved and displayed correctly on the screen that wrote it. This is the strongest argument in the course for the shape B3.4 describes: one schema in shared/, imported by both sides, so a rename is a compile error rather than a behaviour change.

Shipping a new rule type client-first now denies everything

B7.2 was changed to refuse rule types it does not recognise rather than skip them — the right call, because silently ignoring a restriction the owner set is worse than failing. It creates a deploy-order constraint that this screen is on the wrong end of:

Add a geo_fence editor, ship the app, and every token that gets one is denied by every server that has not been updated — including, for a few minutes during a rolling deploy, some of yours. And app releases cannot be recalled.

Server first, always. The rule type must be understood and deployed everywhere before any client can write it, which for a mobile app means a release or two of distance, not an afternoon.

Optimistic toggles on a privacy control

Flipping a switch and rendering the new state immediately is standard practice and wrong here. A user turns off video, sees it off, and puts the phone down; the request failed on a bad connection. The screen now says something false about who can reach them — and unlike a failed "like", they will not find out.

Rule controls show a pending state until the server confirms, and a failure has to be loud. This is the same rule as the token code in A5.1, for the same reason: optimistic UI is fine when being wrong is cosmetic.

An overnight window the UI will not let you enter

B7.2 now handles 22:00–06:00 — a normal do-not-disturb inverse. A time picker that validates end > start, which is the obvious validation to write, makes that rule impossible to create. The engine supports it and the interface forbids it, so the capability exists and no user can reach it.

Two storage models, and this lesson picked the other one

This lesson describes an access_rules table with one row per rule. B7.2 evaluates tokens.rules, a JSONB column. Both are defensible — rows give you constraints, indexes and history; JSONB gives you one read and no join on the hottest path — and having both is not. Recorded here rather than silently resolved: it belongs to the B2 rewrite, which is already scheduled. What the client sends is the same either way; what it must not do is assume.

What this costs you

DecisionWhat you pay
Rules stored with a timezone The UI has to display it, and a user who genuinely moves must edit every token by hand. The alternative — following the device — is worse in a way they would not notice, which is the deciding factor.
No optimistic toggles The screen feels slower than every other app, on the controls users touch most. That is the correct trade for a control whose whole job is telling the truth about access — and it means the pending state needs designing rather than defaulting to a spinner over the whole page.
Server-first deploys for new rule types A feature is split across two releases with weeks between them, and the client half has to be feature-flagged or held back. That is the cost of the engine refusing what it does not understand, and it is cheaper than the alternative.
Rules that only narrow No "allow this one thing" escape hatch. A user who wants an exception has to express it as a narrower restriction, or issue a second token — which is usually the better answer anyway, and needs saying in the UI.
Each rule editor as its own component Adding a rule type means a component, a payload type, a summary formatter and an engine branch. Four places, and the compiler only catches two of them — which is what the discriminated union in B3.4 is for.
