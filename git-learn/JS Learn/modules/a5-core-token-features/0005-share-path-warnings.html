Share-Path Warnings

A5 — Lesson 5 of 5 ~40 min
Why this matters for Token

Token's entire privacy promise rests on one rule: a token must never travel over a channel that already identifies the user. If you send a token via WhatsApp, the recipient now has both the token AND your phone number — defeating the purpose. The app must actively protect users from accidentally breaking their own privacy. This isn't a nice-to-have; it's the product's immune system.

The product rule — valid vs. dangerous sharing paths

Safe paths (token doesn't leak identity)

MethodWhy it's safe
QR code (show screen)Physical proximity — no digital trail linking to identity
Typed into a form fieldPasted where a site asks for contact info — no phone/email needed
Spoken aloud / read from screenVerbal exchange — no digital record
Printed on card / listingPhysical medium — no electronic identity attached
Request-a-token (reverse flow)Business publishes a link; user's app generates from inside the system

Dangerous paths (token + identity leak together)

MethodWhy it's dangerous
WhatsApp / SMSRecipient sees your phone number in the chat
EmailRecipient sees your email address in the From field
Instagram / Facebook DMRecipient sees your social profile
Telegram (if username visible)Username can often be linked back to identity
AirDrop / Nearby ShareDevice name often contains the user's real name

Detecting the share intent

When a user taps "Share" or "Copy" on a token, we can't always detect where they'll paste it. But we can detect when they use the system share sheet — which reveals the target app:

import * as Sharing from 'expo-sharing';
import * as Clipboard from 'expo-clipboard';

// Copy gets no SHARE-PATH warning: we cannot know the destination, and the
// most valuable destination — a web form asking for a phone number — is the
// safe one. That is not the same as saying the clipboard is harmless; see
// a5/0001, which clears it after 60 seconds because every app on the device
// can read it and both platforms sync it across a user's machines.
async function handleCopyCode(code: string) {
  await Clipboard.setStringAsync(code);
  scheduleClipboardClear(code);   // a5/0001
}

// Share sheet — we CAN detect the target app (on some platforms)
async function handleShare(code: string) {
  // Show warning BEFORE opening share sheet
  showShareWarning(() => {
    Sharing.shareAsync(/* ... */);
  });
}

The limitation

On iOS and Android, the system share sheet doesn't reliably report which app the user selected before the share completes. So we can't conditionally warn based on target. Instead, we warn preemptively:

  • Copy to clipboard — no warning (could be pasted anywhere)
  • QR display — no warning (physical, safe)
  • System share sheet — always show warning before opening

Design decisions in the warning

  1. "Go Back" is primary (blue, prominent) — the safe choice is the easy choice. You want friction on the dangerous path, not the safe one.
  2. "I understand, share anyway" is secondary (muted, small) — the user CAN proceed, but it takes deliberate effort. We're not blocking, just informing.
  3. Explain WHY, not just what — "the recipient will see your phone number" is more compelling than "this is not recommended".
  4. Offer alternatives — don't just say "no", show the better path.
  5. No "don't show again" checkbox — this warning should appear every time. Privacy fatigue is real, but this is the product's core promise.

Integrating the warning into the share flow

// app/src/screens/TokenDetail.tsx — share section
import { useState } from 'react';
import * as Clipboard from 'expo-clipboard';
import * as Sharing from 'expo-sharing';
import { Alert } from 'react-native';
import { ShareWarning } from '../components/ShareWarning';

function TokenDetailScreen({ route }) {
  const { token } = route.params;
  const [showWarning, setShowWarning] = useState(false);

  async function handleCopy() {
    await Clipboard.setStringAsync(token.code);
    Alert.alert('Copied', 'Token code copied to clipboard.');
  }

  function handleSharePress() {
    // Always show warning before system share sheet
    setShowWarning(true);
  }

  async function handleProceedShare() {
    setShowWarning(false);
    const url = `https://tokn.app/t/${token.code.replace(/-/g, '')}`;
    if (await Sharing.isAvailableAsync()) {
      await Sharing.shareAsync(url, {
        dialogTitle: 'Share Token',
      });
    }
  }

  return (
    <View>
      {/* ... token display, QR, etc ... */}

      <View style={styles.shareRow}>
        <TouchableOpacity style={styles.copyButton} onPress={handleCopy}>
          <Text>Copy Code</Text>
        </TouchableOpacity>

        <TouchableOpacity style={styles.shareButton} onPress={handleSharePress}>
          <Text>Share...</Text>
        </TouchableOpacity>
      </View>

      <ShareWarning
        visible={showWarning}
        onCancel={() => setShowWarning(false)}
        onProceed={handleProceedShare}
      />
    </View>
  );
}

The "Request a Token" reverse flow

There's one digital sharing path that IS safe: the reverse flow. Instead of the user sending their token to a business, the business publishes a "Request Token" link. The user clicks it, their app opens, and the app generates + delivers the token through the Token system itself — no identity ever leaves the device.

// Flow:
// 1. Business has a button: "Request customer's Token"
// 2. Button links to: https://tokn.app/request?from=businessName
// 3. User's app opens (deep link) with a prompt:
//    "NoBroker wants you to issue them a token. Create one?"
// 4. User taps "Create" → app generates token + sends code through the API
// 5. Business receives the code server-side — never sees user's phone/email

// This is covered in detail in A8 (Redemption Web Page) and A9 (Deep Linking).
// For now, just know this path exists and is the ONLY safe digital sharing method.

Edge cases

User copies code, then opens WhatsApp manually

We can't detect this. The clipboard is neutral about its destination — not harmless, which is a different claim and the one a5/0001 answers by clearing it after 60 seconds. The share-path warning only triggers on the system share sheet, and that is acceptable here: the user made a deliberate multi-step choice, and the onboarding screen educated them.

Warning on copy as well would cost more than it buys. Pasting into a form field is one of the safe paths — arguably the highest-value one, since it is exactly the "hand a number to a business that will keep it forever" case the product exists for. A warning that fires on the good path teaches the user to dismiss warnings, and then the one that matters is dismissed too.

User screenshots the QR and sends the screenshot

Can't prevent this either. The token code in the screenshot is just text/image — it doesn't carry identity on its own. The danger is only if the screenshot is sent via an identifying channel. But the QR image alone doesn't contain the user's phone number, so it's less dangerous than sending the code in a WhatsApp message.

User shares via AirDrop/Nearby Share

These reveal the device name (often "Ashish's iPhone"). This soft-identifies the user. The system share sheet warning covers this case — AirDrop and Nearby Share appear in the share sheet.

Respecting user agency

The warning is not a block. The user can always proceed. Token is a privacy tool, not a prison. Some valid reasons to share via an identifying channel:

  • The recipient already has your identity (friend, family member)
  • You're testing the app with yourself
  • You're deliberately creating a token for a known contact as a convenience feature (separate from privacy)

The warning says "I understand, share anyway" — not "This is blocked." Informed consent, not paternalism.

First, the decision the modal is downstream of

The modal is markup. The question it exists to ask — does this particular way of getting the code out of the app deserve a warning? — is a function, and it is the one place the product rule is actually enforced. Get it wrong in the safe direction and the app helps the user destroy the thing they installed it for.
