WebSocket Basics on the Client

A6 — Lesson 1 of 3 ~50 min
Why this matters for Token

The WebSocket server is built (B5). Now the app needs to connect to it — and stay connected. Mobile connections drop constantly: tunnels, elevators, switching between WiFi and cellular. The client must reconnect automatically, re-authenticate, and pick up where it left off. This lesson builds the connection layer that every real-time feature in the app depends on.

The browser WebSocket API

React Native uses the same WebSocket API as browsers. No extra library needed:

const ws = new WebSocket('wss://api.tokn.app/ws?token=YOUR_JWT');

ws.onopen = () => { /* connected */ };
ws.onmessage = (event) => { /* event.data is the message */ };
ws.onclose = (event) => { /* event.code, event.reason */ };
ws.onerror = (error) => { /* connection error */ };

// Send a message
ws.send(JSON.stringify({ type: 'chat:send', payload: { ... } }));

Key difference from HTTP: you create the connection once and keep it open. You don't create a new WebSocket for each message.

Connection singleton

The app needs exactly ONE WebSocket connection. Every screen that needs real-time data shares the same connection. We build a singleton:

// app/src/ws/connection.ts
import { getAccessToken } from '../api/client';

const WS_URL = __DEV__
  ? 'ws://localhost:3000/ws'
  : 'wss://api.tokn.app/ws';

type MessageHandler = (type: string, payload: any) => void;

let ws: WebSocket | null = null;
let reconnectAttempts = 0;
let reconnectTimer: ReturnType<typeof setTimeout> | null = null;
let intentionalClose = false;
const listeners = new Set<MessageHandler>();

export function connect() {
  if (ws?.readyState === WebSocket.OPEN || ws?.readyState === WebSocket.CONNECTING) {
    return;
  }

  const token = getAccessToken();
  if (!token) return;

  intentionalClose = false;
  ws = new WebSocket(`${WS_URL}?token=${token}`);

  ws.onopen = () => {
    console.log('WS connected');
    reconnectAttempts = 0;
  };

  ws.onmessage = (event) => {
    try {
      const { type, payload } = JSON.parse(event.data);
      for (const handler of listeners) {
        handler(type, payload);
      }
    } catch {
      console.warn('WS: invalid message received');
    }
  };

  ws.onclose = (event) => {
    console.log(`WS closed: ${event.code} ${event.reason}`);
    ws = null;

    if (!intentionalClose) {
      scheduleReconnect();
    }
  };

  ws.onerror = () => {
    // onclose will fire after onerror — reconnect happens there
  };
}

export function disconnect() {
  intentionalClose = true;
  if (reconnectTimer) {
    clearTimeout(reconnectTimer);
    reconnectTimer = null;
  }
  ws?.close(1000, 'User logged out');
  ws = null;
}

export function send(type: string, payload: unknown) {
  if (ws?.readyState === WebSocket.OPEN) {
    ws.send(JSON.stringify({ type, payload }));
  } else {
    console.warn('WS: cannot send — not connected');
  }
}

export function subscribe(handler: MessageHandler): () => void {
  listeners.add(handler);
  return () => listeners.delete(handler);
}

export function getConnectionState(): 'connected' | 'connecting' | 'disconnected' {
  if (!ws) return 'disconnected';
  if (ws.readyState === WebSocket.OPEN) return 'connected';
  if (ws.readyState === WebSocket.CONNECTING) return 'connecting';
  return 'disconnected';
}

Exponential backoff reconnection

When the connection drops, don't reconnect immediately in a tight loop. Use exponential backoff — each attempt waits longer than the last:

function scheduleReconnect() {
  // Exponential backoff: 1s, 2s, 4s, 8s, 16s, max 30s
  const delay = Math.min(1000 * Math.pow(2, reconnectAttempts), 30000);
  reconnectAttempts++;

  console.log(`WS: reconnecting in ${delay}ms (attempt ${reconnectAttempts})`);

  reconnectTimer = setTimeout(() => {
    reconnectTimer = null;
    connect();
  }, delay);
}

Why backoff? If the server is down and 10,000 clients retry every second, it gets hammered the instant it comes back up. Backoff widens the gap between one client's attempts, so a client that has been failing for a while stops asking so often.

Adding jitter — and what backoff does not fix

The distinction that matters here

Backoff spaces out one client. Only jitter spaces out the herd. It is tempting to say backoff "spreads out reconnection attempts", but look at the table again: every client dropped by the same server restart computes the same delays from the same starting instant. They wait 1s together, then 2s together, then 4s together. The gaps get wider and the crowd stays exactly as tightly packed — arriving in synchronised waves rather than a steady stream.

Randomness is what breaks the lockstep. The useful form is full jitter: treat the backoff value as a window and pick a random point anywhere inside it, rather than nudging the delay slightly either side of a shared value.

function scheduleReconnect() {
  // The window doubles each attempt, capped at 30s...
  const window = Math.min(1000 * Math.pow(2, reconnectAttempts), 30000);
  // ...and the actual delay is a random point INSIDE it.
  const delay = Math.floor(Math.random() * window);

  reconnectAttempts++;
  reconnectTimer = setTimeout(() => connect(), delay);
}

Compare that with a common alternative — adding ±25% wobble around the backoff value. On attempt 5 that scatters clients across 12s–20s; full jitter scatters them across 0s–16s. The second is a far wider spread, and the difference grows with every attempt. Partial jitter keeps the crowd recognisably a crowd.

You will meet this again in a8/0003, where the redemption page builds the complete version as a testable function — the same jitter, plus the close codes that mean "do not retry at all" and a give-up limit. The reconnection rules are the same on both clients; only the auth failure mode differs.

React hook for WebSocket

Components need to know the connection state and react to incoming messages. A custom hook:

// app/src/ws/useWebSocket.ts
import { useEffect, useState, useCallback, useRef } from 'react';
import { AppState, AppStateStatus } from 'react-native';
import { connect, disconnect, subscribe, send, getConnectionState } from './connection';

export function useWebSocket() {
  const [connectionState, setConnectionState] = useState(getConnectionState());

  useEffect(() => {
    connect();

    const unsub = subscribe((type, payload) => {
      // Update connection state on any message (confirms we're alive)
      setConnectionState('connected');
    });

    // Reconnect when app comes back to foreground
    const handleAppState = (state: AppStateStatus) => {
      if (state === 'active') {
        connect();
      }
    };
    const sub = AppState.addEventListener('change', handleAppState);

    return () => {
      unsub();
      sub.remove();
    };
  }, []);

  return { connectionState, send };
}

// Hook for listening to specific message types
export function useWsMessage(type: string, handler: (payload: any) => void) {
  const handlerRef = useRef(handler);
  handlerRef.current = handler;

  useEffect(() => {
    return subscribe((msgType, payload) => {
      if (msgType === type) {
        handlerRef.current(payload);
      }
    });
  }, [type]);
}

AppState — reconnecting on foreground

When the user switches to another app, the OS may kill the WebSocket connection after a few minutes (especially on iOS). When they return, reconnect immediately:

import { AppState } from 'react-native';

AppState.addEventListener('change', (state) => {
  if (state === 'active') {
    // App is back in foreground — ensure WS is connected
    connect();   // ← read the warning below before you copy this
  }
});

iOS behaviour: WebSocket connections are suspended when the app goes to background. After ~30 seconds, iOS may close the TCP connection entirely. On return to foreground, the onclose event fires and reconnection triggers.

Android behaviour: More lenient — connections can survive background for minutes. But battery optimization (Doze mode) will eventually kill them.

That handler has a bug, and it is the exercise

It calls connect() whenever the app comes forward — without asking whether anyone is logged in. Read it together with the logout code in the next section, which disconnects the socket when user becomes null. Log out, switch to another app, switch back, and the socket is open again on behalf of a user who is no longer signed in.

The two handlers are individually reasonable and are written in different files, which is exactly why this survives review. Neither is wrong on its own.

Three states, not two

The other thing the snippet glosses over: AppState reports 'active', 'background' and 'inactive'. That third one is transient and iOS-flavoured — it fires when the notification shade comes down, when a call banner appears, during the app switcher. It does not mean the user has left.

So do not treat "not active" as "tear the socket down". A user glancing at a notification would drop and rebuild their connection for nothing, and on a flaky mobile network rebuilding is the expensive part. Leave the socket alone while the app is away, and let the OS close it if it wants to — the onclose handler already knows what to do.

Connecting on login, disconnecting on logout

// app/src/auth/AuthContext.tsx — integrate WS lifecycle
import { connect as wsConnect, disconnect as wsDisconnect } from '../ws/connection';

export function AuthProvider({ children }) {
  // ... existing auth state ...

  useEffect(() => {
    if (user) {
      // Authenticated — connect WebSocket
      wsConnect();
    } else {
      // Logged out — disconnect
      wsDisconnect();
    }
  }, [user]);

  // ... rest of provider
}

Handling token refresh mid-connection

The access token sent during WebSocket connect expires after 15 minutes. But the WebSocket stays open longer. Two strategies:

Strategy A: Reconnect with fresh token

// When access token refreshes, close and reconnect with new token
// Simple but causes a brief disconnection blip
function onTokenRefreshed() {
  ws?.close(4001, 'Token refreshed');  // custom close code
  connect();  // reconnects with new token immediately
}

Strategy B: Re-auth over the WebSocket (better UX)

// Send a re-auth message over the existing connection
// Server verifies and updates the socket's auth state
// No disconnection — seamless

send('auth:refresh', { token: getAccessToken() });

// registerHandler('auth:refresh', async (ws, payload) => {

For Token v1, Strategy A is simpler and the reconnection is fast enough that the user won't notice.

Connection state UI

Show the user when they're disconnected — a small banner at the top:

// app/src/components/ConnectionBanner.tsx
import { View, Text, StyleSheet } from 'react-native';
import { useWebSocket } from '../ws/useWebSocket';

export function ConnectionBanner() {
  const { connectionState } = useWebSocket();

  if (connectionState === 'connected') return null;

  return (
    <View style={styles.banner}>
      <Text style={styles.text}>
        {connectionState === 'connecting' ? 'Connecting...' : 'Offline — messages will send when connected'}
      </Text>
    </View>
  );
}

const styles = StyleSheet.create({
  banner: {

});

Now build it yourself

Write connectionIntent(context) — the single place that decides whether the socket should be connecting, disconnecting, or left alone. Pulling this decision out of the event handlers is what stops the foreground bug above: two handlers cannot disagree if there is only one rule.
