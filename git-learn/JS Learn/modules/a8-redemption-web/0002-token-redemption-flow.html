Token Redemption Flow

A8 — Lesson 2 of 4 ~55 min
Why this matters for Token

tokn.app/t/CODE is the only way a holder reaches the issuer. This page must validate the token code, ask for the holder's nickname, create their session, and open a conversation — all without requiring sign-up. If this flow is confusing or broken, the holder gives up and the issuer's privacy system fails. The redemption flow is the entire product for holders.

The redemption flow — step by step

When a holder opens tokn.app/t/MERC8GH2KP4X — undashed, as a5/0002 established, because the dashes are display formatting and a shorter URL makes a less dense QR:

  1. URL parsed — React Router extracts the code from the URL
  2. Token validated — POST /api/redeem/check, code in the body, checks the token exists and is redeemable
  3. Nickname prompted — holder enters a display name (no account needed)
  4. Redemption submitted — POST /api/redeem with the code and the nickname
  5. Session created — server returns a holder JWT and session ID
  6. Conversation opened — redirect to the chat page with the session

Flow states

The redemption page has distinct states. Model them explicitly:

type RedeemState =
  | { status: 'loading' }              // checking token validity
  | { status: 'valid'; label: string } // token is active, show nickname form
  | { status: 'entering'; label: string } // holder is typing nickname
  | { status: 'redeeming' }            // POST in progress
  | { status: 'expired' }              // token past expiry date
  | { status: 'revoked' }              // issuer revoked this token
  | { status: 'paused' }               // issuer paused it — may come back
  | { status: 'maxed' }               // max uses reached
  | { status: 'not-found' }           // code doesn't exist
  | { status: 'error'; message: string }; // network or server error

paused was missing from this union until 2026-08-19, and the omission is instructive. a5/0003 treats paused as a first-class state on the issuer's side — it is the one dead-end that is reversible — so a paused token reaching this page had no branch to land in and fell through to error. The holder saw "something went wrong" for a token that is working exactly as its owner intended.

It also earns different copy from the rest. revoked, expired and maxed are final and the honest message is "this will not work again". paused means try later — and it is the only one where telling the holder to come back is true.

The validation API call

Before showing the nickname form, check if the token is redeemable:

The code goes in the body, not the path. ADR-0007 is explicit about this and it is easy to get wrong here, because /api/tokens/:code/status is the obvious REST shape. A path is written to the proxy access log, kept in browser history, sent onward in Referer, and attached to crash reports — four copies of a capability that is supposed to be a secret. A POST body is in none of them.

// POST /api/redeem/check   { "code": "MERC8GH2KP4X" }
// No auth required — this is a public endpoint.
// The code is in the BODY. Never /api/tokens/:code/status.

interface TokenStatus {
  valid: boolean;
  label: string;          // "Amazon Delivery" — helps holder confirm
  reason?: 'expired' | 'revoked' | 'paused' | 'max_uses' | 'not_found';
}

async function checkTokenStatus(code: string): Promise<TokenStatus> {
  const response = await fetch('/api/redeem/check', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ code }),
  });

  if (response.status === 404) {
    return { valid: false, label: '', reason: 'not_found' };
  }

  if (!response.ok) {
    throw new Error(\`Server error: \${response.status}\`);
  }

  return response.json();
}
This is also why the request is not a GET

A GET cannot carry a body in practice, so "code in the body" and "GET" are incompatible. That is a real cost — the check is idempotent and reads nothing, so GET is what it wants to be — and it is paid deliberately. The alternative is a capability in four log files.

The redemption API call

// POST /api/redeem   { "code": "MERC8GH2KP4X", "nickname": "..." }
// No auth required — creates a new holder session.
// Again: the code is in the body.

interface RedeemRequest {
  code: string;
  nickname: string;  // "Delivery Agent Ravi"
}

interface RedeemResponse {
  holderSessionId: string;
  holderJwt: string;         // JWT for this holder session
  conversationId: string;
  // NO issuerId. This response is delivered to the holder's browser, where
  // it is visible in devtools whether or not the UI renders it. WebSocket
  // routing resolves the issuer from conversationId on the SERVER, which is
  // the only place that mapping needs to exist.
}

async function redeemToken(code: string, nickname: string): Promise<RedeemResponse> {
  const response = await fetch('/api/redeem', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ code, nickname }),
  });

  if (!response.ok) {
    const err = await response.json();
    throw new Error(err.error || 'Redemption failed');
  }

  return response.json();
}

Holder identity — no account required

For v1, holders don't create accounts. They provide a nickname and get a JWT scoped to that one token session:

// Server-side: what the holder JWT contains
{
  sub: 'holder_session_abc123',    // unique session ID
  conversationId: 'conv_xyz',      // what the session is FOR
  tokenId: 42,                     // the row id, meaningless to anyone else
  nickname: 'Delivery Agent Ravi',
  iat: 1700000000,
  exp: 1700086400,                 // 24 hours
}

This JWT lets the holder send messages and join calls — but only for this one token conversation. No broader access.

The token code is not in there, and the reason is not the obvious one

It would be easy to assume the code is omitted to keep it from the holder. It is not — the holder typed it in. They know it.

It is omitted because of where a JWT goes. It rides in an Authorization header on every request, and headers are logged by reverse proxies, captured by error trackers alongside stack traces, and pasted whole into bug reports by people trying to be helpful. ADR-0007 says the code is never logged, and "never" has to cover the places you did not think of as logging.

conversationId identifies the session exactly as well and means nothing to whoever reads it. This is the same reasoning as POST /api/redeem taking the code in the body: the question is never "who can see this", it is "where does this end up written down".

Privacy design

The holder JWT contains no information about the issuer (no email, no name, no phone). The holder only sees the token label ("Amazon Delivery") and communicates through the channel. The issuer's identity is never exposed.

Complete RedeemPage component

import { useState, useEffect } from 'react';
import { useParams, useNavigate } from 'react-router-dom';

type RedeemState =
  | { status: 'loading' }
  | { status: 'valid'; label: string }
  | { status: 'entering'; label: string }
  | { status: 'redeeming' }
  | { status: 'expired' }
  | { status: 'revoked' }
  | { status: 'maxed' }
  | { status: 'not-found' }
  | { status: 'error'; message: string };

export function RedeemPage() {
  const { code } = useParams<{ code: string }>();
  const navigate = useNavigate();
  const [state, setState] = useState<RedeemState>({ status: 'loading' });
  const [nickname, setNickname] = useState('');

  // Step 1: Validate the token on mount
  useEffect(() => {
    if (!code) {
      setState({ status: 'not-found' });
      return;
    }

    fetch('/api/redeem/check', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ code }),
    })
      .then(async (res) => {
        if (res.status === 404) {
          setState({ status: 'not-found' });
          return;
        }
        const data = await res.json();
        // redeemState translates. Assigning data.reason straight into status
        // is what this page used to do, and the server's vocabulary is not
        // the UI's: 'max_uses' is not 'maxed', 'not_found' is not
        // 'not-found', and neither renders any branch at all.
        setState(redeemState(data));
      })
      .catch((err) => setState({ status: 'error', message: err.message }));
  }, [code]);

  // Step 2: Submit redemption
  async function handleRedeem(e: React.FormEvent) {
    e.preventDefault();
    if (!nickname.trim() || !code) return;

    setState({ status: 'redeeming' });

    try {
      const res = await fetch('/api/redeem', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ code, nickname: nickname.trim() }),
      });

      if (!res.ok) {
        const err = await res.json();
        throw new Error(err.error);
      }

      const data = await res.json();

      // Store the holder JWT for subsequent API calls
      sessionStorage.setItem('holderJwt', data.holderJwt);
      sessionStorage.setItem('sessionId', data.holderSessionId);

      // Navigate to chat
      navigate(\`/t/\${code}/chat\`);
    } catch (err: any) {
      setState({ status: 'error', message: err.message });
    }
  }

  // Render based on state
  if (state.status === 'loading') {
    return <div className="min-h-screen flex items-center justify-center">
      <p className="text-gray-500">Checking token...</p>
    </div>;
  }

  if (state.status === 'not-found') {
    return <div className="min-h-screen flex items-center justify-center">
      <div className="text-center">
        <h1 className="text-xl font-bold text-red-600">Token Not Found</h1>
        <p className="mt-2 text-gray-600">This token code doesn't exist.</p>
      </div>
    </div>;
  }

  if (state.status === 'expired' || state.status === 'revoked' || state.status === 'maxed') {
    const messages = {
      expired: 'This token has expired.',
      revoked: 'This token has been revoked by the issuer.',
      maxed: 'This token has reached its maximum number of uses.',
    };
    return <div className="min-h-screen flex items-center justify-center">
      <div className="text-center">
        <h1 className="text-xl font-bold text-orange-600">Token Unavailable</h1>
        <p className="mt-2 text-gray-600">{messages[state.status]}</p>
      </div>
    </div>;
  }

  if (state.status === 'error') {
    return <div className="min-h-screen flex items-center justify-center">
      <div className="text-center">
        <h1 className="text-xl font-bold text-red-600">Something went wrong</h1>
        <p className="mt-2 text-gray-600">{state.message}</p>
      </div>
    </div>;
  }

  // Valid token — show nickname form
  return <div className="min-h-screen flex items-center justify-center p-4">
    <div className="w-full max-w-sm">
      <h1 className="text-2xl font-bold text-center">Connect</h1>
      <p className="mt-2 text-center text-gray-600">
        Token: {state.status === 'valid' && state.label}
      </p>
      <form onSubmit={handleRedeem} className="mt-6 space-y-4">
        <input
          type="text"
          value={nickname}
          onChange={(e) => setNickname(e.target.value)}
          placeholder="Your name (visible to token issuer)"
          className="w-full px-4 py-2 border rounded-lg"
          maxLength={50}
          required
        />
        <button
          type="submit"
          disabled={state.status === 'redeeming' || !nickname.trim()}
          className="w-full py-2 bg-blue-600 text-white rounded-lg"
        >
          {state.status === 'redeeming' ? 'Connecting...' : 'Start Conversation'}
        </button>
      </form>
    </div>
  </div>;
}

Why sessionStorage, not localStorage?

The holder JWT is stored in sessionStorage because:

  • It's scoped to one browser tab — closing the tab clears it
  • Holders are ephemeral — no persistent identity
  • If they want to reconnect later, they open the same URL again and get a new session
  • This prevents stale JWTs from accumulating on shared/public devices

First, the translation between two vocabularies

The server answers in its own words — max_uses, not_found — and the UI renders a different set — maxed, not-found. They look near enough to assign one to the other, and this page did exactly that for months: setState({ status: data.reason }). A maxed-out token then set a status no branch matched, and the holder got a blank screen with no error and nothing to do.
