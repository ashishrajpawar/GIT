Universal Links & App Links

A9 — Lesson 1 of 2 ~45 min
Why this matters for Token

tokn.app/t/CODE must open the mobile app if installed, or fall back to the web page if not. This seamless routing is done via Universal Links (iOS) and App Links (Android) — OS-level features that associate your domain with your app. Without this, holders always land on the web page, even if they have the app installed.

How the OS decides where to send a link

When a user taps a tokn.app/t/MERC-8GH2-LP4X link (in a message, email, or anywhere), the operating system checks:

  1. Is there an app installed that claims this domain?
  2. Does the domain confirm that claim? (via a verification file hosted on the domain)
  3. If both yes: open the app directly. If no: open the browser.

The key insight: the domain must confirm the association, not just the app. This prevents malicious apps from hijacking your links.

iOS — Apple App Site Association (AASA)

Apple requires a JSON file at https://tokn.app/.well-known/apple-app-site-association:

// .well-known/apple-app-site-association
// NO file extension — it's served as application/json
{
  "applinks": {
    "apps": [],
    "details": [
      {
        "appIDs": ["TEAM_ID.app.tokn.mobile"],
        "components": [
          {
            "/": "/t/*",
            "comment": "Token redemption links"
          }
        ]
      }
    ]
  }
}

Key points:

  • appIDs uses format: TEAM_ID.bundleIdentifier
  • TEAM_ID comes from your Apple Developer account
  • "apps": [] must be present and empty (legacy requirement)
  • The components array uses pattern matching — /t/* matches any token code
  • File must be served over HTTPS with Content-Type: application/json
  • No redirects allowed — Apple fetches this directly
Critical detail

Apple caches the AASA file. It is NOT fetched every time a link is tapped. iOS checks it when the app is installed or updated. Changes can take hours or days to propagate. Test thoroughly before shipping.

Android — Digital Asset Links (assetlinks.json)

Android uses a similar file at https://tokn.app/.well-known/assetlinks.json:

// .well-known/assetlinks.json
[
  {
    "relation": ["delegate_permission/common.handle_all_urls"],
    "target": {
      "namespace": "android_app",
      "package_name": "app.tokn.mobile",
      "sha256_cert_fingerprints": [
        "14:6D:E9:83:C5:73:06:50:D8:EE:B9:95:2F:34:FC:64:16:A0:83:42:E6:1D:BE:A8:8A:04:96:B2:3F:CF:44:E5"
      ]
    }
  }
]

Key differences from iOS:

  • The file IS named with a .json extension
  • You need the SHA-256 fingerprint of your app's signing certificate
  • package_name matches what's in your app.json
  • For debug builds, use the debug keystore fingerprint. For production, use the upload key fingerprint from Play Console.

Getting your SHA-256 fingerprint

# For EAS-managed builds (production)
eas credentials --platform android

# For local debug keystore
keytool -list -v -keystore ~/.android/debug.keystore -alias androiddebugkey -storepass android

# Look for the SHA256 line:
# SHA256: 14:6D:E9:83:C5:73:06:50:...

Hosting the verification files

Both files live in the .well-known/ directory of your domain. In the Token project, these are served by the web/ container (Vite + React) since it handles tokn.app:

// In web/public/.well-known/apple-app-site-association
// (Vite serves files from public/ as-is at the root path)

// In web/public/.well-known/assetlinks.json
// Same — Vite's public/ folder maps to the root

// Directory structure:
web/
  public/
    .well-known/
      apple-app-site-association    // no extension!
      assetlinks.json

Vite serves everything in public/ at the domain root, so public/.well-known/assetlinks.json becomes https://tokn.app/.well-known/assetlinks.json.

AASA content type

The AASA file has no extension, so your server might not set the right content type. Ensure your hosting (Coolify/nginx) serves it as application/json. In Vite you may need a plugin or a Coolify nginx config block.

Expo linking configuration

Expo needs to know about these associations in app.config.js:

// app/app.config.js
export default {
  expo: {
    name: "Token",
    slug: "token",
    scheme: "tokn",  // for tokn:// custom scheme (fallback)
    ios: {
      bundleIdentifier: "app.tokn.mobile",
      associatedDomains: ["applinks:tokn.app"],
      // This tells iOS: "check tokn.app for an AASA file"
    },
    android: {
      package: "app.tokn.mobile",
      intentFilters: [
        {
          action: "VIEW",
          autoVerify: true,  // triggers assetlinks.json check
          data: [
            {
              scheme: "https",
              host: "tokn.app",
              pathPrefix: "/t/"
            }
          ],
          category: ["BROWSABLE", "DEFAULT"]
        }
      ],
    },
  },
};

Key config explained:

  • scheme: "tokn" — registers a custom URL scheme (tokn://) as a fallback for development
  • associatedDomains — iOS reads this during install to know which domains to check
  • autoVerify: true — tells Android to fetch and verify assetlinks.json at install time
  • pathPrefix: "/t/" — only claim the redemption path, not the entire domain

The full flow — what happens when a link is tapped

// User taps: https://tokn.app/t/MERC-8GH2-LP4X

// iOS flow:
// 1. iOS checks: is tokn.app in any installed app's associatedDomains?
// 2. Yes — iOS already cached the AASA from install time
// 3. AASA says /t/* belongs to TEAM_ID.app.tokn.mobile
// 4. That app IS installed → open it, pass the full URL
// 5. App receives: "https://tokn.app/t/MERC-8GH2-LP4X"

// Android flow:
// 1. Android checks: does any app have an intent filter matching this URL?
// 2. Yes — app.tokn.mobile has autoVerify:true for https://tokn.app/t/*
// 3. Android already verified assetlinks.json at install time
// 4. App IS installed → open it, pass the URL as an intent
// 5. App receives the URL via the Linking API

// Not installed flow (both platforms):
// 1. OS finds no app claiming the domain
// 2. Falls through to the browser
// 3. Browser loads https://tokn.app/t/MERC-8GH2-LP4X
// 4. The web/ app renders the redemption page (built in A8)

Testing deep links

You cannot test Universal Links by typing in Safari's address bar. The link must be tapped from outside the browser:

# Android — simulate a link tap via adb
adb shell am start -a android.intent.action.VIEW \
  -d "https://tokn.app/t/TEST-CODE-1234" \
  app.tokn.mobile

# iOS Simulator — use xcrun
xcrun simctl openurl booted "https://tokn.app/t/TEST-CODE-1234"

# Expo development — use uri-scheme
npx uri-scheme open "https://tokn.app/t/TEST-CODE-1234" --android
npx uri-scheme open "https://tokn.app/t/TEST-CODE-1234" --ios

# Custom scheme (development only)
npx uri-scheme open "tokn://t/TEST-CODE-1234" --android
Development vs Production

During development, Universal Links and App Links won't work because your domain verification files aren't served from the real domain. Use the custom scheme (tokn://) for local testing. Universal/App Links only work with a real HTTPS domain and a production build.

Common pitfalls

  • AASA not updating — Apple caches aggressively. Use Apple's validation tool to check. On-device, delete and reinstall the app.
  • Wrong fingerprint — If you use EAS Build, the signing key is different from your local debug keystore. Use eas credentials to get the right one.
  • Redirect on .well-known — Neither Apple nor Google follows redirects to these files. They must be served directly at the path.
  • Missing autoVerify — Without it, Android shows a disambiguation dialog instead of opening your app directly.
  • Claiming too much — Only claim paths your app handles (/t/). Don't claim the entire domain or the web page won't load for other routes.
