Signalling Server

B6 — Lesson 1 of 2 ~55 min
Why this matters for Token

WebRTC is peer-to-peer — audio and video flow directly between devices. But to establish that direct connection, both sides need to exchange metadata first: "here's my offer", "here's my answer", "here are my network candidates". This metadata exchange is called signalling, and it needs an intermediary. Your WebSocket server is that intermediary. No Firebase, no third-party SDK — just your own server relaying a handful of JSON messages to set up the call.

WebRTC connection — the big picture

┌──────────┐                    ┌──────────┐
│  Caller  │                    │  Callee  │
│ (phone)  │                    │ (phone)  │
└────┬─────┘                    └────┬─────┘
     │                               │
     │  1. call:offer (SDP)          │
     │──────────────┐                │
     │              ▼                │
     │     ┌──────────────┐         │
     │     │  Your Server │         │
     │     │  (WebSocket) │         │
     │     └──────┬───────┘         │
     │            │                  │
     │            │ 2. forward offer │
     │            │─────────────────▶│
     │            │                  │
     │            │ 3. call:answer   │
     │            │◀─────────────────│
     │  4. forward│answer            │
     │◀───────────│                  │
     │            │                  │
     │  5. ICE candidates (both ways)│
     │◀───────────┼─────────────────▶│
     │            │                  │
     │  6. Direct P2P connection     │
     │◀═════════════════════════════▶│
     │    (audio/video flows here)   │

The server's job is steps 1–5 only. Once the peer connection is established (step 6), audio/video flows directly between devices. The server is out of the loop.

Signalling messages

The signalling protocol needs just 5 message types:

TypeDirectionPurpose
call:initiateCaller → Server"I want to call this user"
call:incomingServer → Callee"Someone is calling you"
call:offerCaller → Server → CalleeSDP offer (media capabilities)
call:answerCallee → Server → CallerSDP answer (accepted media)
call:iceBoth → Server → OtherICE candidate (network path)
call:hangupEither → Server → Other"I'm ending the call"
call:rejectCallee → Server → Caller"I declined the call"
call:busyServer → Caller"Callee is already in a call"

SDP — Session Description Protocol

SDP is a text format describing what media a peer can send/receive. You don't write SDP yourself — the browser/RN generates it. But you should understand what's in it:

v=0
o=- 1234567890 2 IN IP4 127.0.0.1
s=-
t=0 0
m=audio 9 UDP/TLS/RTP/SAVPF 111
a=rtpmap:111 opus/48000/2
m=video 9 UDP/TLS/RTP/SAVPF 96
a=rtpmap:96 VP8/90000

Key info in an SDP: "I support Opus audio at 48kHz and VP8 video at 90kHz clock rate." The answer says: "I accept Opus audio and VP8 video" — both sides now know what codec to use.

Your server doesn't parse SDP. It just passes it through as an opaque string from caller to callee and back. The peers interpret it themselves.

ICE — Interactive Connectivity Establishment

ICE candidates are potential network paths between peers. Each candidate is an IP:port pair that might work:

// Types of candidates:
// host      — device's local IP (works on same LAN)
// srflx     — public IP discovered via STUN (works across NATs)
// relay     — TURN server address (always works, but adds latency)

Both peers generate candidates and send them to the other side via signalling. The ICE agent tries each pair until one works. This is called "ICE negotiation" and happens automatically — you just relay the candidates.

Active call tracking

Call state cannot live in one process

A Map here has the same problem the socket registry had in B7.3, and it fails harder. "Is this person already in a call?" answered from one replica's memory is answered wrong whenever the other person is connected elsewhere — so busy detection silently stops working, and the callee's call:incoming is sent to a socket table that does not contain them. Calls between users on different replicas do not connect at all.

ADR-0003 again: nothing shared lives in process memory.

// api/src/ws/calls.ts
import { redis } from '../redis';

interface ActiveCall {
  // The `calls` row this belongs to. Redis holds the live state and
  // forgets it; the row is what b7/0002 counts and b7/0003 ends.
  dbId: string;
  callerId: number;
  calleeId: number;
  conversationId: number;
  tokenId: number;
  startedAt: string;
  type: 'voice' | 'video';
}

const CALL_TTL_SECONDS = 60 * 60;   // a call nobody ended cannot outlive this

export function createCallId(userId1: number, userId2: number): string {
  // Deterministic: always the same ID regardless of who calls whom
  const sorted = [userId1, userId2].sort((a, b) => a - b);
  return `call:${sorted[0]}:${sorted[1]}`;
}

// Two keys per call: the record, and a marker per participant so "is this
// person busy?" is one lookup rather than a scan of every call in the system.
export async function startCall(
  callId: string,
  call: Omit<ActiveCall, 'dbId'>,
  initiatedBy: 'owner' | 'holder',
) {
  // The DURABLE record comes first. Redis is where the call lives; this
  // row is what survives it, and it is the only thing b7/0002 can count.
  const { rows } = await pool.query(
    `INSERT INTO calls (conversation_id, token_id, initiated_by, media)
     VALUES ($1, $2, $3, $4) RETURNING id`,
    [call.conversationId, call.tokenId, initiatedBy, call.type]
  );
  const withId: ActiveCall = { ...call, dbId: rows[0].id };

  await redis
    .multi()
    .set(callId, JSON.stringify(withId), 'EX', CALL_TTL_SECONDS)
    .set(`busy:${call.callerId}`, callId, 'EX', CALL_TTL_SECONDS)
    .set(`busy:${call.calleeId}`, callId, 'EX', CALL_TTL_SECONDS)
    .exec();

  return withId;
}

export async function endCall(callId: string, reason: string) {
  const raw = await redis.get(callId);
  if (!raw) return;
  const call: ActiveCall = JSON.parse(raw);

  // `AND ended_at IS NULL` is the exactly-once guard, in the one place it
  // can actually be enforced. The first ending wins; a revoke arriving
  // after a hangup changes nothing, which is what b7/0003 relies on.
  await pool.query(
    `UPDATE calls SET ended_at = NOW(), end_reason = $1
      WHERE id = $2 AND ended_at IS NULL`,
    [reason, call.dbId]
  );

  await redis.del(callId, `busy:${call.callerId}`, `busy:${call.calleeId}`);
}

export async function isInCall(userId: number): Promise<boolean> {
  return (await redis.exists(`busy:${userId}`)) === 1;
}

The TTL is doing real work. A process killed mid-call never runs its cleanup, and without an expiry both participants are marked busy forever — permanently unable to make or receive a call, with no error anywhere explaining why. Every piece of state that a crash can orphan needs an expiry, chosen as a deliberate upper bound rather than left off.

Until 2026-08-25 nothing here wrote a row, and that is why the daily call limit did not exist

The whole lifecycle lived in Redis behind a one-hour TTL. Nothing ever inserted into calls. Follow that through to the two lessons that read the table:

  • b7/0002 enforces contact_limit with SELECT COUNT(*) FROM calls WHERE token_id = $1 AND initiated_by = 'holder' AND created_at >= $2. Against an empty table that is always 0, so max_calls_per_day permitted an unlimited number of calls — a rule the issuer set, that the UI showed as active, and that could never fire.
  • b7/0003 ends live calls on revoke with UPDATE calls ... WHERE id = $2, passing activeCall.id — which is the Redis key 'call:3:7'. That is not a row id and never was, so against a BIGSERIAL column it does not quietly match nothing, it raises a type error inside the revoke path.

An orphan table is usually read as a table nobody got round to creating. This one was the reverse: the readers existed and the writer never did, so the missing table was the symptom and the missing INSERT was the defect. That is why the audit's orphan-table error is worth keeping loud rather than living with.

Note also what the fix does not do: it does not move call state into Postgres. Redis stays the live registry, because that is what the TTL and the busy markers are for. The row is the part that has to outlive the process, and the two are joined by dbId and nothing else.

The signalling handlers

// api/src/ws/handlers/call.ts
import { getClients } from '../server';
import { sendTo } from '../router';
import { createCallId, startCall, endCall, isInCall, getActiveCall } from '../calls';
import { db } from '../../db';
import { WebSocket } from 'ws';

interface AuthenticatedSocket extends WebSocket {
  userId: number;
  isAlive: boolean;
}

// --- call:initiate ---
// Caller wants to start a call
export async function handleCallInitiate(ws: AuthenticatedSocket, payload: {
  conversationId: number;
  type: 'voice' | 'video';
}) {
  const { conversationId, type } = payload;

  // Validate: is caller part of this conversation?
  const conv = await db.query(
    'SELECT issuer_id, holder_id, token_id FROM conversations WHERE id = $1',
    [conversationId]
  );
  if (conv.rows.length === 0) {
    sendTo(ws, 'error', { message: 'Conversation not found' });
    return;
  }

  const { issuer_id, holder_id } = conv.rows[0];
  if (ws.userId !== issuer_id && ws.userId !== holder_id) {
    sendTo(ws, 'error', { message: 'Not a participant' });
    return;
  }

  const calleeId = ws.userId === issuer_id ? holder_id : issuer_id;

  // The rules engine decides whether this call is allowed AT ALL. Without
  // this, a paused token, a revoked token, one outside its time window, or
  // one whose owner turned video off can still place a call - because
  // redemption happened months ago and nothing has re-asked since.
  const ruleCheck = await evaluateRules(conv.rows[0].token_id,
                                        type === 'video' ? 'video_call' : 'voice_call');
  if (!ruleCheck.allowed) {
    sendTo(ws, 'call:denied', { reason: ruleCheck.reason });
    return;
  }

  // Check if either party is already in a call
  if (await isInCall(ws.userId)) {
    sendTo(ws, 'call:busy', { reason: 'You are already in a call' });
    return;
  }
  if (await isInCall(calleeId)) {
    sendTo(ws, 'call:busy', { reason: 'User is busy' });
    return;
  }

  // Create the call
  const callId = createCallId(ws.userId, calleeId);
  startCall(callId, {
    callerId: ws.userId,
    calleeId,
    conversationId,
    startedAt: new Date(),
    type,
  });

  // Notify the callee
  const calleeSockets = getClients().get(calleeId);
  if (calleeSockets) {
    for (const sock of calleeSockets) {
      sendTo(sock, 'call:incoming', {
        callId,
        callerId: ws.userId,
        conversationId,
        type,
      });
    }
  } else {
    // Callee is offline — end the call
    endCall(callId);
    sendTo(ws, 'call:unavailable', { reason: 'User is offline' });
    // In production: trigger push notification here (B8)
  }
}

// --- call:offer ---
// Caller sends SDP offer (after callee accepts)
export function handleCallOffer(ws: AuthenticatedSocket, payload: {
  callId: string;
  sdp: string;
}) {
  const call = getActiveCallForUser(ws.userId, payload.callId);
  if (!call) {
    sendTo(ws, 'error', { message: 'No active call' });
    return;
  }

  const targetId = call.callerId === ws.userId ? call.calleeId : call.callerId;
  deliverToUser(targetId, 'call:offer', { callId: payload.callId, sdp: payload.sdp });
}

// --- call:answer ---
// Callee sends SDP answer
export function handleCallAnswer(ws: AuthenticatedSocket, payload: {
  callId: string;
  sdp: string;
}) {
  const call = getActiveCallForUser(ws.userId, payload.callId);
  if (!call) {
    sendTo(ws, 'error', { message: 'No active call' });
    return;
  }

  const targetId = call.callerId === ws.userId ? call.calleeId : call.callerId;
  deliverToUser(targetId, 'call:answer', { callId: payload.callId, sdp: payload.sdp });
}

// --- call:ice ---
// Either peer sends ICE candidate
export function handleCallIce(ws: AuthenticatedSocket, payload: {
  callId: string;
  candidate: object;
}) {
  const call = getActiveCallForUser(ws.userId, payload.callId);
  if (!call) return; // silently drop — ICE can arrive after hangup

  const targetId = call.callerId === ws.userId ? call.calleeId : call.callerId;
  deliverToUser(targetId, 'call:ice', {
    callId: payload.callId,
    candidate: payload.candidate,
  });
}

// --- call:hangup ---
// Either party ends the call
export function handleCallHangup(ws: AuthenticatedSocket, payload: { callId: string }) {
  const call = getActiveCallForUser(ws.userId, payload.callId);
  if (!call) return;

  const targetId = call.callerId === ws.userId ? call.calleeId : call.callerId;
  deliverToUser(targetId, 'call:hangup', { callId: payload.callId });
  endCall(payload.callId);
}

// --- call:reject ---
// Callee declines
export function handleCallReject(ws: AuthenticatedSocket, payload: { callId: string }) {
  const call = getActiveCallForUser(ws.userId, payload.callId);
  if (!call) return;

  deliverToUser(call.callerId, 'call:rejected', { callId: payload.callId });
  endCall(payload.callId);
}

// --- Helpers ---
function getActiveCallForUser(userId: number, callId: string) {
  const call = getActiveCall(userId);
  if (!call) return null;
  const expectedId = createCallId(call.callerId, call.calleeId);
  if (expectedId !== callId) return null;
  return call;
}

function deliverToUser(userId: number, type: string, payload: unknown) {
  const sockets = getClients().get(userId);
  if (sockets) {
    for (const sock of sockets) {
      sendTo(sock, type, payload);
    }
  }
}

The complete call flow

  1. Caller sends call:initiate — server checks permissions, creates call state, notifies callee
  2. Callee sees incoming call UI — rings, shows caller info
  3. Callee accepts — both sides create RTCPeerConnection
  4. Caller creates offer — sends SDP via call:offer
  5. Callee receives offer, creates answer — sends SDP via call:answer
  6. Both sides exchange ICE candidates — via call:ice
  7. ICE completes — direct P2P connection established, media flows
  8. Either party hangs up — sends call:hangup, server cleans up state

Cleaning up stale calls

If a user disconnects mid-call (app crash, network loss), the call state lingers. Clean up on disconnect:

// In ws/server.ts — on close handler:
ws.on('close', () => {
  // ... existing cleanup ...

  // If this user was in a call, notify the other party
  const call = getActiveCall(ws.userId);
  if (call) {
    const callId = createCallId(call.callerId, call.calleeId);
    const otherId = call.callerId === ws.userId ? call.calleeId : call.callerId;
    deliverToUser(otherId, 'call:hangup', { callId, reason: 'peer_disconnected' });
    endCall(callId);
  }
});

Call timeout — unanswered calls

// After sending call:incoming, start a 30-second timeout
const RING_TIMEOUT = 30000;

// In handleCallInitiate, after notifying callee:
setTimeout(() => {
  const callId = createCallId(ws.userId, calleeId);
  // If call still exists and hasn't been answered...
  const call = getActiveCall(ws.userId);
  if (call && createCallId(call.callerId, call.calleeId) === callId) {
    deliverToUser(ws.userId, 'call:timeout', { callId });
    deliverToUser(calleeId, 'call:timeout', { callId });
    endCall(callId);
  }
}, RING_TIMEOUT);

Security considerations

  • Validate conversation participation — only conversation participants can initiate calls. Check the conversation table, not just any user ID.
  • Check token status — if the token is paused or revoked, reject the call initiation.
  • Rate limit — prevent call spam. Limit to N call attempts per minute per user.
  • SDP is opaque — don't parse or validate SDP contents. Just relay it. Parsing SDP safely is complex and unnecessary for signalling.
  • ICE candidates contain IP addresses — and for this product that is not a footnote. See below.

Why this way (and what was rejected)

Relay-only ICE, because a call otherwise reveals where you live

WebRTC is peer-to-peer by design, and that is the problem. To connect directly, both sides exchange ICE candidates — and a candidate is an IP address. Your device's, and theirs.

Think about what Token promises. Someone was given a code. They do not know the user's name, number or email — that is the entire product. Then they place a call, and their client logs an IP address that geolocates to a neighbourhood. The stranger the user deliberately kept at arm's length now knows roughly where they are, and nothing was hacked: that is how WebRTC works. 

// Sent to both clients at call setup
{
  iceServers: [
    { urls: 'stun:stun.l.google.com:19302' },
    { urls: 'turn:turn.tokn.app:3478', username: '...', credential: '...' }
  ],
  iceTransportPolicy: 'relay'    // the line that matters
}

'relay' tells the browser to discard host and server-reflexive candidates entirely and use only the TURN server. Each side sees the relay's address and never the other's. It is the difference between a privacy product and a product with a privacy page.

The rejected alternative is the default, 'all': better call quality, lower latency, and no bandwidth bill — paid for with the one thing the user came here to protect.

Our own signalling server, not a third party

Signalling is a handful of JSON messages relayed between two clients — offer, answer, candidates, hangup. Renting that from Firebase or a realtime-as-a-service vendor would work and would hand a third party the one thing E2EE cannot hide anyway: who called whom, when, and for how long. Message contents are encrypted; call metadata is not the sort of thing that can be. Keeping it on hardware you rent is the only way it stays yours.

Relay SDP, never parse it

The server is a postbox. It does not read the SDP, validate it, or rewrite it — parsing an attacker-supplied SDP blob is a real attack surface bought for no benefit, since the server has no decision to make based on its contents. What the server does check is who is allowed to send it, which is a question about the conversation, not the payload.

When this breaks

The other person is on another replica

activeCalls as a process-local Map is the B7.3 failure again and it fails harder here. isInCall(calleeId) consults one replica's memory, so busy detection quietly stops working — and the call:incoming notification is looked up in a local socket table that does not contain the callee. Calls between users on different replicas never connect, with no error on either side: the caller waits, the callee's phone never rings.

A crash marks two people busy forever

Move the state to Redis and a new failure appears: cleanup runs in the hangup handler, and a process killed mid-call never gets there. Without an expiry, both participants keep a busy: marker permanently and can never make or receive another call — and nothing logs anything, because from the system's point of view they are simply on a call that has lasted three weeks.

Every piece of state a crash can orphan needs a TTL, picked as a deliberate upper bound. An hour is not "how long calls last"; it is "how long is it acceptable to be wrong".

The rules engine was never consulted

Nothing in the original initiate handler called evaluateRules. A token whose owner turned video off, or paused it, or restricted it to office hours, or revoked it last week, could still place a call — because the conversation already existed and the call path never re-asked. Redemption checked once, months ago.

Same shape as the B7.2 finding, in a second place. It is worth stating generally: every path that lets a holder reach the user is an authorisation point. Messages, calls, and anything added later. Not just the door they came in through.

A schema contradiction, left for B2

This code reads issuer_id and holder_id from conversations and treats both as user ids. But B7.1 is explicit that holders do not have accounts — they get a JWT scoped to one conversation, and never become a row in users. The two lessons disagree about what a holder is.

B7.1 is the one that is right, and the schema now says so. b2/0002 gives conversations a holder_session_id and no holder user_id at all, so there is no column for this code to be reading. The participants junction table that would have papered over it was deleted from the plan on 2026-08-23 — see c5/0005 — for exactly this reason: a junction table between users and conversations assumed both parties were users, and only one of them ever is.

The calls table

This is the one B2 could not write, because what a call record needs to persist is a signalling question. Two lessons already query it — b7/0002 counts calls to enforce contact_limit, and b7/0003 ends live calls when a token is revoked — so the columns below are derived from what they ask for, not invented. 

-- api/migrations/0009_calls.sql

-- A call belongs to a conversation, and a conversation belongs to exactly
-- one token. token_id here is therefore a SECOND COPY of a fact -- which
-- this course allows only when something refuses to let the copies
-- disagree. That something is the composite foreign key below, so
-- conversations needs a key for it to point at:
ALTER TABLE conversations ADD CONSTRAINT conversations_id_token_uniq
  UNIQUE (id, token_id);

CREATE TABLE calls (
  id              BIGSERIAL PRIMARY KEY,
  conversation_id INTEGER NOT NULL,
  token_id        INTEGER NOT NULL,

  -- Postgres now refuses any call whose token_id disagrees with its
  -- conversation's. The denormalisation cannot drift, which is the only
  -- condition under which it is allowed to exist.
  FOREIGN KEY (conversation_id, token_id)
    REFERENCES conversations (id, token_id) ON DELETE RESTRICT,

  -- b7/0002 filters on this to count only calls the HOLDER started.
  initiated_by    TEXT NOT NULL CHECK (initiated_by IN ('owner', 'holder')),
  media           TEXT NOT NULL CHECK (media IN ('voice', 'video')),

  -- Three states out of two nullable columns:
  --   answered_at NULL, ended_at NULL     -> ringing right now
  --   answered_at NULL, ended_at NOT NULL -> missed, and that is the record
  --   both NOT NULL                       -> a call that happened
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  answered_at     TIMESTAMPTZ,
  ended_at        TIMESTAMPTZ,

  end_reason      TEXT CHECK (end_reason IN (
                    'hangup_owner', 'hangup_holder', 'rejected',
                    'timeout', 'disconnected', 'failed',
                    'token_revoked', 'token_paused')),

  -- A reason without an ending, or an ending without a reason, is not a
  -- state this product has. Same biconditional discipline as b2/0001's
  -- status/revoked_at pair.
  CHECK ((ended_at IS NOT NULL) = (end_reason IS NOT NULL)),
  -- And time only runs forwards.
  CHECK (answered_at IS NULL OR answered_at >= created_at),
  CHECK (ended_at   IS NULL OR ended_at    >= created_at)
);

-- b7/0002 runs on every call attempt:
--   WHERE token_id = $1 AND initiated_by = 'holder' AND created_at >= $2
-- Equality columns first, the range column last -- b1/0003's rule, and
-- the reason this is one index rather than three.
CREATE INDEX idx_calls_token_initiator_created
  ON calls (token_id, initiated_by, created_at);

-- b7/0003 hangs up live calls on revoke. Live calls are a handful of rows
-- out of every call ever made, so this is a partial index over exactly
-- them and stays small for ever.
CREATE INDEX idx_calls_live ON calls (token_id) WHERE ended_at IS NULL;

What is deliberately not in there

  • No SDP and no ICE candidates. They are relayed and never stored, and this is structural rather than tidy: an ICE candidate is an IP address. iceTransportPolicy: 'relay' exists so that neither party learns where the other is — and writing the candidates into a table hands both addresses to anyone who can read the database, which undoes the whole policy from a different direction.
  • No duration column. It is ended_at - created_at. A stored copy is a second version of a fact that can drift, and the reasoning is the same one that killed use_count.
  • No recording, and nowhere to put one. Media never transits the API, so the server could not record a call if it were asked to. That is worth stating in the schema rather than only in an ADR — a table with no column for a thing is a stronger promise than a policy saying you will not use one.
  • No partitioning, unlike messages. Calls are orders of magnitude rarer than messages: a busy user might make a few a day and receives dozens of messages an hour. Partition when the row count justifies the operational cost, not because the table next door is partitioned.
The cost of the composite foreign key, so it can be reversed on evidence

Carrying token_id on calls buys b7/0002 a count with no join, on a query that runs before every single call is allowed to start. It costs a UNIQUE (id, token_id) on conversations — an index that is redundant for lookups, since id alone is already unique, and exists only to be the target of that foreign key.

The alternative was to store only conversation_id and join, which has no duplication at all and is genuinely simpler. It was rejected because the join sits on an authorisation path, and because the composite key makes the duplication impossible to get wrong rather than merely unlikely — which is the bar CLAUDE.md sets. If the extra constraint ever becomes a nuisance, dropping token_id and adding the join is a small migration.

What this costs you

DecisionWhat you pay
iceTransportPolicy: 'relay' Every call's audio and video crosses your TURN server instead of going peer to peer. That is the bandwidth bill B9.2 flags as the most likely surprise on the invoice — a video call is roughly 1–2 Mbit/s each way, through your machine, for its whole duration. It also adds latency and gives you a single point of failure for media.
Running your own signalling You own reconnection, timeouts, busy states, and every edge case a vendor would have handled — the code in this lesson is the cheap part, and the fiddly part is everything that happens when one side's network changes mid-call.
Call state in Redis Two round trips before a call can start, and Redis is now on the critical path for calls as well as sockets. It is already required by ADR-0003, so this adds a dependency on something you had rather than a new one.
Consulting the rules engine per call A database read before the phone rings, which is nothing next to establishing a call — and it means a call can be refused for a reason the caller cannot see. The client has to render call:denied as something a human understands.
One call id per pair Deterministic ids are simple and mean a stale entry blocks that specific pair until it expires. The TTL bounds it; a per-call UUID would remove it entirely at the cost of a lookup.

Now build it yourself: what the call leaves behind

Everything above is about getting two people connected. This is about the single row that survives afterwards — and the row is decided by a stream of events that can arrive twice, out of order, or stop halfway.
