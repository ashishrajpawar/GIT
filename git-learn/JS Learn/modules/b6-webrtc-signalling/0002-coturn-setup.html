coturn Setup

B6 — Lesson 2 of 2 ~50 min
Why this matters for Token

In most WebRTC apps TURN is a fallback for the ~15% of calls that cannot connect directly. In Token it carries all of them. An ICE candidate is an IP address, so any direct path hands a delivery company the issuer's home address — which is what iceTransportPolicy: 'relay' exists to prevent. That makes coturn load-bearing rather than a safety net: if it is down, nobody can call anybody, and its bandwidth is a line item rather than a rounding error. It is the open-source TURN server you run yourself, which is what keeps the media inside your own infrastructure.

Why self-host TURN?

  • No third-party dependency — Token's architecture avoids external services
  • No per-minute fees — Twilio/Xirsys charge per GB of TURN traffic. Self-hosted = your VPS bandwidth cost only
  • Data sovereignty — media never leaves your infrastructure (important for Indian DPDP compliance)
  • Privacy — relay-only is the baseline, not a mode, and it is why TURN sits on the critical path rather than beside it

Installing coturn

coturn is available in most Linux package managers. On your Coolify VPS (Ubuntu/Debian):

# Install coturn
sudo apt update
sudo apt install coturn -y

# Enable it as a service
sudo systemctl enable coturn

Or via Docker (for Coolify)

# docker-compose.yml — add to your existing stack
services:
  coturn:
    image: coturn/coturn:latest
    network_mode: host
    volumes:
      - ./turnserver.conf:/etc/turnserver.conf:ro
    restart: unless-stopped

network_mode: host is important — TURN needs to bind to the host's public IP directly. Docker's default bridge networking breaks TURN because NAT inside Docker confuses ICE.

Configuration

# /etc/turnserver.conf (or ./turnserver.conf for Docker)

# Network

# Bandwidth (per-session limits)
#
# 2 Mbps, not 1. 720p video is ~1.5 Mbps, so a 1 Mbps cap does not
# protect you from abuse -- it throttles every ordinary video call and
# is reported as "the app's video is bad on your network".
max-bps=2000000

# Under relay-only that is two allocations per call, so this number is

# TLS (use Let's Encrypt cert from Coolify)

pkey=/etc/letsencrypt/live/turn.tokn.app/privkey.pem

Temporary credentials (TURN REST API)

You don't want static TURN credentials hardcoded in the app — anyone who decompiles the APK could steal them and relay their own traffic through your server. Instead, generate short-lived credentials for each call:

// api/src/routes/turn.ts
import { Router } from 'express';
import { createHmac } from 'crypto';
import { requireAuth } from '../middleware/auth';

const router = Router();
const TURN_SECRET = process.env.TURN_SECRET!; // same as static-auth-secret in coturn config
const TURN_SERVER = process.env.TURN_SERVER || 'turn.tokn.app';

// requireCaller accepts EITHER an owner's session or a holder's
// conversation-scoped JWT. Both make calls; only one of them is a user.
router.get('/turn/credentials', requireCaller, (req, res) => {
  const ttl = 3600;                                   // one hour, see below
  const timestamp = Math.floor(Date.now() / 1000) + ttl;

  // Namespaced, because a holder on conversation 42 and a user with id 42
  // are different principals and coturn's log has only this string to
  // tell them apart.
  const identity = req.caller.kind === 'holder'
    ? `holder:${req.caller.conversationId}`
    : `owner:${req.caller.userId}`;

  const username = `${timestamp}:${identity}`;

  // HMAC-SHA1 of username with the shared secret
  const credential = createHmac('sha1', TURN_SECRET)
    .update(username)
    .digest('base64');

  res.json({
    data: {
      iceServers: [
        {
          // NO stun: entry, of ours or anybody's. Under relay-only the
          // client never gathers a srflx candidate, so a STUN server is
          // at best a wasted round trip -- and asking one for your public
          // IP is the precise thing this configuration exists to avoid.
          urls: [
            `turn:${TURN_SERVER}:3478?transport=udp`,
            `turn:${TURN_SERVER}:3478?transport=tcp`,
            // TLS on 5349 for networks that block UDP outright, which is
            // most corporate WiFi and some Indian mobile carriers.
            `turns:${TURN_SERVER}:5349?transport=tcp`,
          ],
          username,
          credential,
        },
      ],
      ttl,
    },
  });
});

export default router;
There was a Google STUN server in this list, three lines below "no third-party dependency"

The response used to end with { urls: ['stun:stun.l.google.com:19302'] }, commented "free STUN fallback". The Why self-host TURN? section at the top of this page gives "no third-party dependency" as reason one. Both were true at once for months.

It is wrong twice over, and the second reason is the one that matters:

  • It is a third party in the call path, contacted by every client before every call — so Google learns that this device is about to make one, and from which IP, in a product whose entire proposition is not handing that out.
  • Under relay-only it does nothing at all. STUN's job is to discover your public address so you can offer a srflx candidate. Relay-only suppresses exactly that candidate. So the request is pure disclosure with no function — the worst possible ratio.

"Free" was doing the work in that comment. It was free of money, and the thing being spent was the thing the product sells.

How time-limited credentials work

  1. Client requests GET /turn/credentials before starting a call
  2. Server generates: username = expiry_timestamp:userId, credential = HMAC-SHA1(username, secret)
  3. Client passes these to RTCPeerConnection({ iceServers: [...] })
  4. When the client connects to coturn, coturn independently computes HMAC-SHA1(username, same_secret) and compares
  5. coturn also checks the timestamp — if expired, rejects

The API server and coturn share the same static-auth-secret. They never communicate directly — the credential is self-validating.

req.user.id — and the holder is not a user

This route used to be requireAuth with ${'${timestamp}'}:${'${req.user.id}'}. Half of every Token call is made by a holder, who redeemed a code on the web page and gets a JWT scoped to one conversation. They never become a row in users — that is b7/0001's decision, and b6/0001 spends a whole section on the same defect appearing in the signalling handlers. So req.user is undefined for exactly the caller who is standing outside your door, and the route 500s or mints ...:undefined.

The namespaced identity is not decoration either. Without the prefix, owner 42 and conversation 42 produce the identical TURN username, so coturn's allocation log cannot distinguish them — and a log you cannot attribute is the one you need during an abuse investigation.

Why one hour rather than twenty-four

The TTL here was 86400. A TURN credential is a bearer capability to relay traffic through your server — that is all it is — so its lifetime is how long a stolen one is worth having. The client caches at half the TTL, so an hour costs one extra credential request every thirty minutes of app use, which is nothing next to establishing a call.

The floor is not arbitrary: the credential has to still be valid when a call starts, and b6/0001's Redis registry already uses one hour as its deliberate upper bound on how long a call can be live. Matching them means one number to reason about instead of two that can disagree.

Firewall / ports to open

# Required ports for coturn:
3478/tcp   — STUN/TURN over TCP
3478/udp   — STUN/TURN over UDP (primary)
5349/tcp   — TURN over TLS (for restrictive networks)
49152-65535/udp — relay ports (media traffic range)

The relay port range is large because each TURN session allocates a unique port. With a 100-session quota, you'll use at most 100 ports from this range.

Client-side ICE configuration

// app/src/webrtc/config.ts
import { apiRequest } from '../api/client';

interface IceServer {
  urls: string[];
  username?: string;
  credential?: string;
}

let cachedServers: IceServer[] | null = null;
let cacheExpiry = 0;

export async function getIceServers(): Promise<IceServer[]> {
  // Cache credentials (valid for 24h, refresh every 12h)
  if (cachedServers && Date.now() < cacheExpiry) {
    return cachedServers;
  }

  const res = await apiRequest<{ data: { iceServers: IceServer[]; ttl: number } }>(
    'GET', '/turn/credentials'
  );

  cachedServers = res.data.iceServers;
  cacheExpiry = Date.now() + (res.data.ttl * 500); // refresh at half TTL
  return cachedServers;
}

// const iceServers = await getIceServers();

Bandwidth planning

TURN relays media — it costs bandwidth. Budget for it:

Call typeBitratePer minutePer hour
Voice (Opus)~32 kbps~0.24 MB~14 MB
Video (VP8 480p)~500 kbps~3.75 MB~225 MB
Video (VP8 720p)~1.5 Mbps~11.25 MB~675 MB
Two multipliers this table left out, and the sentence under it was wrong by about seven times

It used to read: "Only ~15% of calls use TURN (the rest connect P2P via STUN). On a typical VPS with 1TB/month transfer, that supports thousands of hours of relay per month." Both halves inherit the default this lesson used to get backwards.

  • 100% of calls use TURN, not 15%. That is what iceTransportPolicy: 'relay' means. The figure is 6.7× what the sentence assumed.
  • Relayed traffic crosses the server twice. It arrives from one peer and leaves to the other, so a 500 kbps stream is 500 kbps in and 500 kbps out. Most hosts bill egress only; some bill both, and either way you are moving double what the bitrate column says.

Worked, for one 480p video call at ~500 kbps: 225 MB/hour per direction per participant, and there are two participants sending. Call it ~900 MB of relay traffic per hour of video call, of which ~450 MB is egress. A 1 TB/month allowance is therefore roughly 2,200 hours of 480p video — not "thousands of hours" as a comfortable margin, but a hard ceiling you can reach with about 70 users doing an hour a day.

At 720p it is under 750 hours. This is the number b9/0002 means when it calls relay bandwidth the likeliest surprise on the invoice, and it is the direct cost of the privacy decision above. Voice-only calls are cheap by comparison — about 30 MB an hour all told — which is worth knowing when you decide what the product nudges people towards.

Relay-only is the baseline, not a mode

Direct P2P connections expose both parties' IP addresses to each other, because an ICE candidate is an IP address — that is what the protocol exchanges. So every Token client, mobile and web, is constructed like this and there is no setting: 

const pc = new RTCPeerConnection({
  iceServers: await getIceServers(),
  iceTransportPolicy: 'relay',  // TURN only. Never a direct path.
});
This section used to call it an option, and default it OFF

The sentence here was: "This should be a user-configurable option. Default to normal ICE (best quality), let privacy-conscious users enable relay-only mode." That is the decided architecture exactly inverted, and it is worth being precise about why it is not a reasonable trade to offer.

The person who bears the cost is not the person who chooses. A token holder is a delivery company, a shop, an estate agent. If either side gathers a host or srflx candidate, the exchange hands the issuer's home IP address to them — and the issuer is the one who went to the trouble of not giving out their phone number. A default that leaks it undoes the hashed codes, the labels and the E2EE in a single call.

It is also not a setting a user can evaluate. "Better call quality" is legible; "the courier learns roughly where you live" is not, and it is not visible when it happens.

And the same inversion made the bandwidth section wrong by nearly seven times — see below. A default nobody notices propagates into the capacity plan, and that is where it finally surfaces, as a bill.

What it costs, stated plainly:

  • Every call is relayed, including two people sitting in the same room. There is no P2P fast path to fall back to.
  • Latency: roughly 50–100 ms extra, on every call.
  • A coturn outage is a total call outage, not a degraded one. With direct paths available, losing TURN costs you the ~15% of calls that need it; here it costs you all of them.
  • Bandwidth is the headline number, and it is 100% of call traffic through your VPS, both directions.

Now build it yourself: mint a TURN credential

A TURN credential is a bearer capability to relay traffic through your server. It is handed to a client you do not control, over a network, and then presented to coturn by something that may or may not be your app. Everything below is about what goes into it and what must not.
