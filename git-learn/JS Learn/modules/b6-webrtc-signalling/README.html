WebRTC Signalling

2 lessons Phase 4 — Real-time
Module goal

Build the signalling server that coordinates WebRTC calls between users. After this module, your WebSocket server can relay offer/answer/ICE messages to establish peer-to-peer voice and video connections — and you'll have a self-hosted TURN server (coturn) for users behind restrictive NATs.

Lessons

  1. Signalling Server

    WebRTC needs an out-of-band channel to exchange offer/answer/ICE candidates before the peer connection opens. Your WebSocket server IS that channel.

  2. coturn Setup

    STUN finds your public IP. TURN relays traffic when direct connections are impossible. Self-hosted coturn gives you relay without third-party dependencies.

What you'll build

  • api/src/ws/handlers/call.ts — signalling message handlers (offer, answer, ice, hangup)
  • api/src/ws/calls.ts — active call state tracking
  • coturn configuration on the VPS (STUN + TURN server)
  • TURN credential generation endpoint

Prerequisites

  • B5 — WebSocket Server (signalling messages travel over your existing WS)
  • Understanding of ICE/STUN/TURN from the old Module 5 theory (or the refresher in A7)
