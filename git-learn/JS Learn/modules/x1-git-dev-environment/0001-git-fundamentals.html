Git Fundamentals

X1 — Lesson 1 of 3 ~45 min
Why this matters for Token

Token lives in one git repo with four folders: app/, web/, api/, and shared/. Every lesson from here on adds code to that repo and commits it. Git is how you track what changed, undo mistakes, and deploy to production. Without it, one bad edit can destroy a week of work with no way back.

What is Git?

Git is a version control system. It takes snapshots of your project at moments you choose. Each snapshot is called a commit. You can go back to any commit, compare two commits, or branch off to try something without risking your working code.

Key concepts:

  • Repository (repo) — a project folder that git is tracking
  • Commit — a saved snapshot with a message describing what changed
  • Branch — a parallel line of development (like a "draft" you can merge back)
  • Staging area — a holding zone where you choose exactly which changes go into the next commit

Installing Git

Check if git is already installed:

git --version

If not installed:

  • Windows: Download from git-scm.com — use the installer. During setup, pick "Git from the command line and also from 3rd-party software".
  • macOS: Run xcode-select --install (includes git), or install via Homebrew: brew install git
  • Linux: sudo apt install git (Debian/Ubuntu) or sudo dnf install git (Fedora)

Configure your identity (git stamps every commit with this):

git config --global user.name "Ashish"
git config --global user.email "your@email.com"

Creating a repository

git init turns any folder into a git repo. Let's create the Token project structure right now:

mkdir token
cd token
git init

mkdir app web api shared

Git creates a hidden .git/ folder inside token/. That's where all history lives. Never edit files inside .git/ manually.

The three areas

Git has three places where your files can be:

  1. Working directory — the files you see and edit
  2. Staging area (index) — changes you've marked for the next commit
  3. Repository (history) — committed snapshots

The flow is always: edit → stage → commit.

# See what's changed
git status

# Stage specific files
git add app/App.tsx
git add shared/types.ts

# Stage everything in the current directory
git add .

# Commit the staged changes
git commit -m "Add initial app structure"

Why stage before committing?

You might have changed five files, but only three are related to the feature you're finishing. Staging lets you group related changes into one meaningful commit and leave the rest for later. This makes your history readable — each commit tells a story.

Viewing history

# Show all commits (newest first)
git log

# Compact one-line view
git log --oneline

# Show what changed in each commit
git log -p

# Show just the last 3 commits
git log -3

Undoing things

Git gives you several "undo" tools depending on what went wrong:

# Unstage a file (keep the edit, remove from staging)
git restore --staged app/App.tsx

# Discard changes to a file (revert to last commit — DESTRUCTIVE)
git restore app/App.tsx

# Amend the last commit message (only if you haven't pushed yet)
git commit --amend -m "Better message"
Warning

git restore <file> without --staged permanently discards your uncommitted edits to that file. There is no undo for this. Always commit or stash before discarding.

Branching

A branch is a movable pointer to a commit. You start on the main branch. Create a new one to work on a feature without risking the stable code:

# Create and switch to a new branch
git checkout -b feature/token-generation

# Or with the newer command
git switch -c feature/token-generation

# List all branches
git branch

# Switch back to main
git switch main

Merging

Once your feature branch works, merge it back into main:

# Switch to the branch you want to merge INTO
git switch main

# Merge the feature branch
git merge feature/token-generation

If both branches edited the same lines, git will report a merge conflict. You open the file, choose which version to keep, remove the conflict markers (<<<<<<<, =======, >>>>>>>), then git add and git commit.

.gitignore

Some files should never be committed: secrets, build output, OS junk. Create a .gitignore at the repo root:

# Node dependencies
node_modules/

# Environment secrets
.env
.env.local

# Build output
dist/
build/

# OS files
.DS_Store
Thumbs.db

# Expo
.expo/

For Token, this one .gitignore at the root covers all four folders. Each subfolder can add its own if needed, but usually the root one is enough.
