Dev Environment

X1 — Lesson 3 of 3 ~50 min
Why this matters for Token

Token uses TypeScript across all four folders. Without consistent tooling — the same Node version, the same formatting rules, the same import paths — you'll spend more time fighting config than writing code. Set this up once, correctly, and it stays out of your way for the entire project.

Node.js version management

Different projects need different Node versions. A version manager lets you switch instantly without reinstalling. Use nvm (Node Version Manager):

# Install nvm (macOS/Linux — see nvm-windows for Windows)
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.39.7/install.sh | bash

# Windows: download nvm-windows from github.com/coreybutler/nvm-windows

# Install and use Node 20 LTS
nvm install 20
nvm use 20
nvm alias default 20

# Verify
node --version   # v20.x.x
npm --version    # 10.x.x

Create a .nvmrc file at the Token repo root so anyone (or any CI) knows which version to use:

20

Then nvm use (with no argument) reads .nvmrc and switches automatically.

VS Code setup

VS Code is the editor for this project. Install these extensions:

  • ESLint — shows errors inline as you type
  • Prettier - Code formatter — auto-formats on save
  • TypeScript + JavaScript — built-in, already there
  • GitLens — see who changed a line, inline blame

Create .vscode/settings.json in the Token repo so these settings apply to everyone who opens this project:

{
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit"
  },
  "typescript.preferences.importModuleSpecifier": "relative"
}

ESLint — catching errors

ESLint finds bugs and bad patterns before you run the code. Install it at the repo root (it covers all four folders):

npm init -y
npm install -D eslint @typescript-eslint/parser @typescript-eslint/eslint-plugin

Create eslint.config.js (flat config — the new standard):

import tseslint from '@typescript-eslint/eslint-plugin';
import tsparser from '@typescript-eslint/parser';

export default [
  {
    files: ['**/*.ts', '**/*.tsx'],
    languageOptions: {
      parser: tsparser,
      parserOptions: {
        ecmaVersion: 'latest',
        sourceType: 'module',
      },
    },
    plugins: {
      '@typescript-eslint': tseslint,
    },
    rules: {
      'no-unused-vars': 'off',
      '@typescript-eslint/no-unused-vars': ['warn', { argsIgnorePattern: '^_' }],
      '@typescript-eslint/no-explicit-any': 'warn',
      'no-console': ['warn', { allow: ['warn', 'error'] }],
    },
  },
];

TypeScript config — the monorepo setup

Each folder has its own tsconfig.json that extends a shared base. This means consistent compiler settings everywhere, but each folder can customize (e.g. app/ needs React Native JSX, api/ doesn't).

Root tsconfig.base.json:

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true,
    "resolveJsonModule": true,
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true,
    "paths": {
      "@token/shared/*": ["./shared/*"]
    }
  }
}

Then api/tsconfig.json:

{
  "extends": "../tsconfig.base.json",
  "compilerOptions": {
    "outDir": "./dist",
    // NOT "./src" — see below. rootDir has to contain every input, and
    // shared/ is an input the moment anything imports it.
    "rootDir": ".."
  },
  "include": ["src/**/*"]
}
rootDir and a shared folder are mutually exclusive

Writing "rootDir": "./src" beside "outDir": "./dist" looks like the tidy, explicit thing to do — it says "compile src/ into dist/". Then the first file does this:

import { TokenCode } from '@token/shared/types';

and the build stops:

error TS6059: File '/token/shared/types.ts' is not under 'rootDir'
'/token/api/src'. 'rootDir' is expected to contain all source files.

The alias is not a trick that copies the file in. It resolves to a real path outside api/, so that file becomes an input to the api build — and rootDir is a promise that every input lives under one directory. The two cannot both be true while shared/ is consumed as source.

So point it at the repo root instead: "rootDir": "..". Both api/src/ and shared/ are underneath it, the error goes away, and the output nests one level deeper — dist/api/src/server.js rather than dist/server.js. Ugly, and you update your start script and Dockerfile once.

Deleting rootDir looks like the tidier fix and is the worse one

Leaving the option out also makes the error go away, because TypeScript then infers rootDir as the longest common ancestor of the actual input files. That is not a setting, it is a calculation — and its inputs change.

Add an import from shared/ to a project that did not have one and the inferred root moves up a level, so every output file moves and the path your start script points at stops existing. Worse, the calculation runs again inside Docker against a different layout: b9/0001 copies api/ to /app and shared/ to /app/shared, so the common ancestor there is /app and the output is dist/src/server.js — a different path from the same source, depending on where it was built.

An inferred value that feeds a hard-coded path is a coincidence waiting to be noticed. Set it explicitly and the answer is the same everywhere.

And app/tsconfig.json:

{
  "extends": "../tsconfig.base.json",
  "compilerOptions": {
    "jsx": "react-native"
  }
}

The @token/shared/* path alias means any folder can import shared types with:

import { TokenCode, AccessRule } from '@token/shared/types';

How paths actually picks a mapping

With one alias this looks like a dictionary lookup. It is not, and the difference shows up the moment there are two. Suppose the base config grows a second entry:

"paths": {
  "@token/*":        ["./*"],
  "@token/shared/*": ["./shared/*"]
}

Now import '@token/shared/types' matches both patterns. Which one wins?

The longest prefix wins — not the first match

TypeScript does not take the first pattern in the object, and it does not take the last. It compares how much literal text sits before the * and takes the most specific: @token/shared/ beats @token/, whichever order they are written in.

An exact pattern — one with no * at all — beats every wildcard.

Assuming first-match-wins resolves @token/shared/types to ./shared/types instead of ./shared/shared/types … or the other way round, depending on which mistake you made. In a monorepo the wrong answer is often a file that exists, so you do not get "cannot find module". You get a type error about a symbol you have never heard of, in a file you did not mean to import.

Two smaller rules that follow from the same place:

  • Each key maps to an array, tried in order, first one that exists wins. That is how you shadow a generated file with a hand-written one.
  • The pattern has a suffix as well as a prefix. "@token/*.css" matches @token/theme.css and not @token/theme — the * captures only what is between them.

Package.json scripts

Add useful scripts to the root package.json:

{
  "scripts": {
    "lint": "eslint . --ext .ts,.tsx",
    "format": "prettier --write .",
    "format:check": "prettier --check .",
    "typecheck": "tsc --noEmit -p app/tsconfig.json && tsc --noEmit -p api/tsconfig.json && tsc --noEmit -p web/tsconfig.json"
  }
}

Now npm run lint, npm run format, and npm run typecheck validate everything at once.
