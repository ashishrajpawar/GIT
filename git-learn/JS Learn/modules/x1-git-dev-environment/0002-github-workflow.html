GitHub Workflow

X1 — Lesson 2 of 3 ~40 min
Why this matters for Token

Your Token repo lives on GitHub. That's where Coolify pulls code from to deploy, where your history is backed up off your laptop, and where you'll manage work through pull requests. If your laptop dies tomorrow, GitHub is how you get everything back in five minutes.

Local vs Remote

So far, git has been tracking changes on your machine only. A remote is a copy of your repo on a server — usually GitHub. The two stay in sync through push (upload your commits) and pull (download new commits).

# Your local repo ←→ GitHub (remote)
#
# git push  → sends your commits to GitHub
# git pull  ← fetches new commits from GitHub to your machine

Creating a GitHub repository

  1. Go to github.com → New repository
  2. Name it token
  3. Leave it empty — no README, no .gitignore (you already have these locally)
  4. Copy the SSH URL: git@github.com:YOUR_USERNAME/token.git

Connect your local repo to GitHub:

# Add the remote (call it "origin" — the conventional name)
git remote add origin git@github.com:YOUR_USERNAME/token.git

# Push your main branch and set it to track the remote
git push -u origin main

The -u flag sets up tracking — after this, plain git push and git pull know which remote branch to use.

SSH keys — passwordless authentication

GitHub needs to verify it's you. SSH keys are the standard approach — no passwords typed every time you push.

# Generate a key pair (press Enter for defaults)
ssh-keygen -t ed25519 -C "your@email.com"

# Copy the public key
cat ~/.ssh/id_ed25519.pub

Then add that public key to GitHub: Settings → SSH and GPG keys → New SSH key. Paste the contents of id_ed25519.pub.

Test it:

ssh -T git@github.com
# Should say: "Hi YOUR_USERNAME! You've successfully authenticated..."

The push/pull cycle

Daily workflow:

# Start of session — get any changes (habit, even if you're the only developer)
git pull

# Do your work...
# ...edit files, test, etc.

# Stage and commit
git add .
git commit -m "Add token generation endpoint"

# Push to GitHub
git push

Pull Requests (PRs)

A pull request is a proposal to merge one branch into another — with a review step in between. Even working solo, PRs give you:

  • A place to describe why you made a change (the PR description)
  • A diff view showing exactly what changed
  • A checkpoint before code reaches main

The workflow:

# 1. Create a feature branch
git switch -c feature/token-generation

# 2. Make commits on that branch
git add .
git commit -m "Implement crypto-random token codes"

# 3. Push the branch to GitHub
git push -u origin feature/token-generation

# 4. On GitHub: open a Pull Request from feature/token-generation → main
# 5. Review the diff, then merge
# 6. Back locally, update main:
git switch main
git pull

Resolving conflicts in PRs

If main has changed since you branched off, you might need to update your branch before merging:

# On your feature branch:
git switch feature/token-generation
git pull origin main

# If there are conflicts, git marks them in the files. Fix them, then:
git diff --check          # refuses to stay quiet about leftover markers
git add app/src/Thing.tsx # name the files you actually resolved
git commit -m "Resolve merge conflicts with main"
git push
Nothing stops you committing a conflict marker

The obvious recipe ends git add . and a commit. Git will stage and commit a file that still contains <<<<<<< without a word. Conflict markers are not special to git once the merge is over — they are just text you left in a file, and git add . stages everything including the file you had not finished.

It usually surfaces as a syntax error in CI, which is the good case. The bad case is a marker inside a string, a Markdown file or a config file, where nothing fails and the text is simply wrong in production.

git diff --check is git's own answer and costs nothing to run. Adding files by name rather than with . is the other half: it makes "which files did I actually resolve?" a question you have to answer.

What a conflict actually looks like, including the part people miss

The familiar shape has three markers:

<<<<<<< HEAD
const MAX_USES = 5;
=======
const MAX_USES = null;
>>>>>>> main

But git has a second conflict style, and newer versions default to it. With merge.conflictStyle = diff3 or zdiff3 there is a fourth marker showing the common ancestor:

<<<<<<< HEAD
const MAX_USES = 5;
||||||| merged common ancestor
const MAX_USES = 1;
=======
const MAX_USES = null;
>>>>>>> main

That base section is genuinely useful — it tells you what both sides changed from, which is often the difference between resolving a conflict and guessing at one. It also means a checker that knows only three markers walks straight past the middle of a diff3 conflict.

Why the marker alone is not evidence

The tempting way to write the check is to search each line for =======. Try that on a repository and it will fire constantly, because seven equals signs is also:

  • a Markdown setext heading underline — the line under a title
  • a separator in a comment banner
  • ASCII table borders, changelog rules, ASCII art

This course has already learned that lesson from the other end. scripts/check-pre-blocks.mjs fired 71 times on its first run and every one was wrong, because shell comments say things like "see what's changed" and it was hunting unbalanced quotes. A check that cries wolf gets switched off, and then the real one goes unread.

So a conflict is a sequence, not a symbol. Only <<<<<<< opens one; everything else is ordinary text until something has opened. That single rule removes every false positive above, because a Markdown underline has no <<<<<<< in front of it.

Useful GitHub features

  • Issues — track bugs and features as a to-do list
  • Branch protection — prevent direct pushes to main (forces PRs)
  • Actions — run tests automatically on every push (CI/CD — covered later)
  • Releases — tag a specific commit as "v1.0" when you ship

Token-specific: one repo, four folders

Your token repo has app/, web/, api/, and shared/. You don't need separate repos because:

  • Changes often span multiple folders (adding an API endpoint + calling it from the app)
  • Shared types in shared/ are imported by all three others
  • One PR can show the full picture of a feature across the stack
  • Coolify can be configured to deploy only api/ or web/ from the same repo

This is called a monorepo without monorepo tooling. You get the organizational benefit without the complexity of Nx, Turborepo, or Lerna. Plain tsconfig path aliases handle cross-folder imports.
