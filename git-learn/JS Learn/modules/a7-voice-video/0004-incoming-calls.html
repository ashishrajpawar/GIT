Incoming Calls (Android + iOS)

A7 — Lesson 4 of 5 ~60 min
Why this matters for Token

The app isn't always in the foreground. When a call comes in and the app is closed or in the background, the phone must ring — just like a regular phone call. iOS requires CallKit (the native call UI) and VoIP push notifications. Android requires a foreground service with a full-screen notification. Without these platform-specific integrations, incoming calls only work when the app is open — useless for a real communication tool.

The problem: app is not running

When user A calls user B, and B's app is in the background:

  • The WebSocket is disconnected (OS killed it after ~30 seconds background)
  • No way to deliver call:incoming via WebSocket
  • Need an alternative wake-up mechanism: push notifications

iOS: CallKit + VoIP Push

How it works

Caller → Your Server → APNs (VoIP push) → iOS → CallKit → Native call UI

// iOS shows the SAME full-screen UI as a real phone call
// Even on the lock screen, even when the phone is asleep

Why CallKit is mandatory

Apple requires CallKit for any app that makes VoIP calls. Without it:

  • Your app can't show the native call screen
  • Calls won't work on the lock screen
  • The app will be rejected from the App Store

// app/src/calls/callkeep.ts
import RNCallKeep from 'react-native-callkeep';
import { Platform } from 'react-native';

export function setupCallKeep() {
  const options = {
    ios: {
      appName: 'Token',
      supportsVideo: true,
    },
    android: {
      alertTitle: 'Permissions required',
      alertDescription: 'Token needs phone account access for incoming calls',
      selfManaged: true,
    },
  };

  RNCallKeep.setup(options);

  // Listen for CallKit events
  RNCallKeep.addEventListener('answerCall', ({ callUUID }) => {
    // User tapped "Accept" on the native call UI
    navigateToCallScreen(callUUID);
  });

  RNCallKeep.addEventListener('endCall', ({ callUUID }) => {
    // User tapped "Decline" or hung up from native UI
    sendRejectOrHangup(callUUID);
  });
}

// Report an incoming call to the system
export function reportIncomingCall(callId: string, callerName: string, hasVideo: boolean) {
  RNCallKeep.displayIncomingCall(
    callId,           // unique UUID
    callerName,       // displayed on the call screen
    callerName,       // localizedCallerName
    'generic',        // handleType
    hasVideo,         // video call?
  );
}

// End a call from your app
export function endCallFromApp(callId: string) {
  RNCallKeep.endCall(callId);
}

How it works

Caller → Your Server → FCM (high priority) → Android → Foreground Service → Full-screen notification

Full-screen intent

// Android: a full-screen intent launches your IncomingCall screen
// even when the phone is locked

// In AndroidManifest.xml (via app.config.js plugin):
// <uses-permission android:name="android.permission.USE_FULL_SCREEN_INTENT" />

// The background handler. FCM carries the message; expo-notifications
// receives it. No Firebase SDK — see the note below.
import * as TaskManager from 'expo-task-manager';

const INCOMING_CALL_TASK = 'token-incoming-call';

TaskManager.defineTask(INCOMING_CALL_TASK, async ({ data, error }) => {
  if (error) return;

  const payload = data?.notification?.data ?? data;
  if (payload?.type !== 'incoming_call') return;

  // Show full-screen notification
  await Notifications.scheduleNotificationAsync({
    content: {
      title: 'Incoming Call',
      body: payload.callerName,
      categoryIdentifier: 'call',
      sound: 'ringtone.wav',
    },
    trigger: null,  // immediate
  });
});

// Register it once, at startup, before any call can arrive
Notifications.registerTaskAsync(INCOMING_CALL_TASK);
FCM the transport, not Firebase the platform

This is the one place the two get confused, so it is worth being exact. Only Apple and Google can wake a backgrounded app — APNs on iOS, FCM on Android. There is no way around that and no open-source substitute, which is why push is the single third party Token accepts.

What Token does not use is the Firebase platform — no Auth, no Firestore, no Storage, no Cloud Functions — and it does not pull in the @react-native-firebase native SDK to receive a push. expo-notifications already speaks to FCM and APNs for you, so the SDK buys nothing and costs you a native dependency, a Google config file in the repo, and an analytics client you did not ask for.

Your server sends a data-only, high-priority message to FCM. Android wakes the app, the task above runs, and your own code decides what the screen shows. Google routes the bytes and learns that a device received a message; it never sees who is calling whom, because that lives in the payload your API built.

The IncomingCall screen

// app/src/screens/IncomingCall.tsx
import { View, Text, TouchableOpacity, StyleSheet } from 'react-native';
import InCallManager from 'react-native-incall-manager';
import RNCallKeep from 'react-native-callkeep';
import { useEffect, useRef, useState } from 'react';
import { send, subscribe } from '../ws/connection';
import { decideIncoming } from '../calls/decideIncoming';

export function IncomingCallScreen({ route, navigation }) {
  const { callId, callerName, type, reported } = route.params;

  // `reported` says whether this call was already shown to CallKit — true
  // when it arrived by VoIP push, false when it came in over the socket
  // with the app already open. Everything below depends on knowing which.
  const callRef = useRef({ status: 'ringing', reported: !!reported, type });

  useEffect(() => {
    InCallManager.startRingtone('_DEFAULT_');

    const unsub = subscribe((msgType, payload) => {
      if (payload.callId !== callId) return;
      if (msgType === 'call:cancel') apply({ kind: 'caller-cancelled' });
      if (msgType === 'call:timeout') apply({ kind: 'timeout' });
    });

    RNCallKeep.addEventListener('answerCall', () => apply({ kind: 'accept-native' }));
    RNCallKeep.addEventListener('endCall', () => apply({ kind: 'decline-native' }));

    return () => {
      unsub();
      RNCallKeep.removeEventListener('answerCall');
      RNCallKeep.removeEventListener('endCall');
      InCallManager.stopRingtone();
    };
  }, []);

  // One place decides; this only carries the decisions out. Every path in
  // and out of a ringing call goes through here, which is what makes
  // "ended exactly once" checkable.
  function apply(event) {
    const { call, actions } = decideIncoming(callRef.current, event);
    callRef.current = call;

    for (const action of actions) {
      if (action === 'stop-ringtone') InCallManager.stopRingtone();
      else if (action === 'report-native') reportIncomingCall(callId, callerName, type === 'video');
      else if (action === 'answer-native') RNCallKeep.answerIncomingCall(callId);
      else if (action === 'end-native') RNCallKeep.endCall(callId);
      else if (action === 'send:call:accept') send('call:accept', { callId });
      else if (action === 'send:call:reject') send('call:reject', { callId });
      else if (action === 'dismiss') navigation.goBack();
      else if (action.startsWith('navigate:')) {
        navigation.replace(action.slice('navigate:'.length), {
          callId,
          conversationId: route.params.conversationId,
          isCaller: false,
          tokenLabel: callerName,
        });
      }
    }
  }

  function handleAccept() {
    apply({ kind: 'accept-in-app' });
  }

  function handleReject() {
    apply({ kind: 'decline-in-app' });
  }

  return (
    <View style={styles.container}>
      <Text style={styles.callerName}>{callerName}</Text>
      <Text style={styles.callType}>
        Incoming {type} call
      </Text>

      <View style={styles.actions}>
        <TouchableOpacity style={styles.rejectBtn} onPress={handleReject}>
          <Text style={styles.btnText}>Decline</Text>
        </TouchableOpacity>
        <TouchableOpacity style={styles.acceptBtn} onPress={handleAccept}>
          <Text style={styles.btnText}>Accept</Text>
        </TouchableOpacity>
      </View>
    </View>
  );
}

const styles = StyleSheet.create({
  container: { flex: 1, backgroundColor: '#1e293b', justifyContent: 'center', alignItems: 'center' },
  callerName: { fontSize: 28, fontWeight: '600', color: '#fff', marginBottom: 8 },
  callType: { fontSize: 16, color: '#94a3b8', marginBottom: 60 },
  actions: { flexDirection: 'row', gap: 48 },
  rejectBtn: { width: 72, height: 72, borderRadius: 36, backgroundColor: '#ef4444', justifyContent: 'center', alignItems: 'center' },
  acceptBtn: { width: 72, height: 72, borderRadius: 36, backgroundColor: '#22c55e', justifyContent: 'center', alignItems: 'center' },
  btnText: { color: '#fff', fontSize: 13, fontWeight: '600' },
});

Six ways a ringing call ends, and one of them must fire exactly once

Look at how many things can finish a call that is currently ringing:

  • The user taps Accept in the app
  • The user taps Accept on the native CallKit screen — a different code path, reached from the lock screen
  • The user taps Decline in the app
  • The user taps Decline on the native screen
  • The caller hangs up before it is answered
  • The 30-second timeout expires

Plus a seventh event that is not an ending: the same call arriving twice, once by VoIP push and once over the WebSocket when the app comes back to the foreground.

Six exits and one duplicate, all racing, and the code above has reportIncomingCall and endCallFromApp with nothing pairing them up. That pairing is the whole problem:

The phantom call — and its mirror image

Report a call to CallKit and never end it, and iOS keeps showing a call. Not a notification you can swipe away: the system call screen, with the green status bar, sometimes surviving until the phone is restarted. It happens the moment a user declines in the app while CallKit is also ringing, because the in-app path never calls endCall.

The obvious fix — always call endCall — creates the opposite bug. When the user declines on the native screen, CallKit has already ended the call itself. Your endCall is a second one, against a UUID the system no longer has.

So the rule is not "always end" or "never end". It is every call reported is ended exactly once, and which events count depends on who ended it. That is a property of a sequence of events, which is exactly the kind of thing you cannot check by reading one handler.

And accepting is a third case again. A call answered from inside the app while CallKit is ringing needs RNCallKeep.answerIncomingCall(callId) — not endCall, which would hang up the call you just took, and not silence either, which leaves the system screen ringing over the top of your call.

Accept was silent and decline was not

One more, easy to miss because the two handlers sit side by side. handleReject sends call:reject. The original handleAccept sent nothing — it just navigated. But look back at 0002's caller side: it subscribes and waits for call:accepted before building its peer connection.

Nobody was sending the message the caller was waiting for. The callee's screen would open and sit at "Connecting…" while the caller never started negotiating at all. Both files read correctly on their own; the gap only exists between them — the same read-the-two-sides-together move that found a8/0004's unsent localId.
