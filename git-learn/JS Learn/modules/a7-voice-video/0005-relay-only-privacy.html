Relay-Only Mode & IP Privacy

A7 — Lesson 5 of 5 ~40 min
Why this matters for Token

In a normal WebRTC call, both peers exchange their IP addresses during ICE negotiation. An IP address can reveal your approximate location and ISP. For a privacy app where the whole point is that holders DON'T know who you are, leaking your IP is a problem. Relay-only mode forces all traffic through your TURN server — neither peer ever learns the other's IP. It's the final layer of Token's privacy promise.

The IP exposure problem

During normal ICE, both sides generate candidates that include IP addresses:

// Candidate from Alice:
candidate: "candidate:1 1 udp 2122260223 192.168.1.5 54321 typ host"
candidate: "candidate:2 1 udp 1686052607 103.45.67.89 12345 typ srflx"

// Bob now knows:
// - Alice's local IP: 192.168.1.5 (not useful externally)
// - Alice's public IP: 103.45.67.89 (reveals ISP, approximate city)

With an IP address, someone can:

  • Determine your approximate location (city/district level)
  • Identify your ISP (Jio, Airtel, BSNL)
  • Potentially correlate with other services (if the IP is static)
  • Target you for network-level attacks

The solution: iceTransportPolicy: 'relay'

// Normal mode (default):
const pc = new RTCPeerConnection({
  iceServers,
  iceTransportPolicy: 'all',  // try host, srflx, then relay
});
// Both peers learn each other's IPs during ICE

// Relay-only mode:
const pc = new RTCPeerConnection({
  iceServers,
  iceTransportPolicy: 'relay',  // ONLY use TURN relay
});
// Neither peer ever sees the other's IP — only the TURN server's IP

What changes

Normal (all)Relay-only
IP privacyBoth IPs exposedBoth IPs hidden
LatencyMinimal (P2P)+50-100ms (extra hop)
Bandwidth costFree (P2P)Server bandwidth
Connection reliability~85% success (may fail behind strict NAT)~99% success (TURN always works)
Audio qualityBest possibleSlightly reduced (jitter from extra hop)

Implementing the user setting

// app/src/settings/privacy.ts
import AsyncStorage from '@react-native-async-storage/async-storage';

const RELAY_ONLY_KEY = 'settings:relay_only';

export async function getRelayOnlyMode(): Promise<boolean> {
  const value = await AsyncStorage.getItem(RELAY_ONLY_KEY);
  return value === 'true';
}

export async function setRelayOnlyMode(enabled: boolean): Promise<void> {
  await AsyncStorage.setItem(RELAY_ONLY_KEY, String(enabled));
}

Integrating into PeerConnection

// app/src/webrtc/PeerConnection.ts — in initialize():
import { getRelayOnlyMode } from '../settings/privacy';

async initialize() {
  const iceServers = await getIceServers();
  const relayOnly = await getRelayOnlyMode();

  this.pc = new RTCPeerConnection({
    iceServers,
    iceTransportPolicy: relayOnly ? 'relay' : 'all',
  });

  // ... rest of initialization
}

Settings UI

// app/src/screens/Settings.tsx — privacy section
import { View, Text, Switch, StyleSheet } from 'react-native';
import { useState, useEffect } from 'react';
import { getRelayOnlyMode, setRelayOnlyMode } from '../settings/privacy';

function PrivacySection() {
  const [relayOnly, setRelayOnly] = useState(false);

  useEffect(() => {
    getRelayOnlyMode().then(setRelayOnly);
  }, []);

  async function handleToggle(value: boolean) {
    setRelayOnly(value);
    await setRelayOnlyMode(value);
  }

  return (
    <View style={styles.section}>
      <Text style={styles.sectionTitle}>Call Privacy</Text>

      <View style={styles.settingRow}>
        <View style={styles.settingInfo}>
          <Text style={styles.settingLabel}>Hide IP Address</Text>
          <Text style={styles.settingDesc}>
            Route all calls through the relay server. The other party
            never sees your IP address. May add slight latency.
          </Text>
        </View>
        <Switch value={relayOnly} onValueChange={handleToggle} />
      </View>
    </View>
  );
}

The trade-off explained to users

The settings screen should be honest about the trade-off. Token is for privacy-conscious users — they can make an informed choice:

// When relay mode is OFF:
"Direct connection — lowest latency, best call quality.
 The other party can see your IP address (approximate location)."

// When relay mode is ON:
"Relay mode — your IP address is hidden from the other party.
 Calls route through our server, which may add slight delay."

When to recommend relay mode

Not all users need relay mode. Recommendations:

  • Tokens for strangers (delivery, service providers) — recommend relay ON. You don't want a random delivery person knowing your IP.
  • Tokens for known contacts (friends, family) — relay OFF is fine. They already know where you live.
  • High-threat users (journalists, activists, domestic abuse survivors) — relay ON is critical.

Future enhancement: per-token relay setting. "This token always uses relay" vs "This token allows direct connection." For now, it's a global setting.

Server-side: can the TURN server see the call content?

No. WebRTC media is encrypted end-to-end with DTLS-SRTP. The TURN server relays encrypted packets — it cannot decrypt them. Even if someone compromises your TURN server, they get encrypted gibberish.

// What the TURN server sees:
// Source IP → TURN → Destination IP
// Encrypted audio/video bytes flowing through
// It knows WHO is calling whom (IP-level routing)
// It CANNOT hear or see the call content

// This is inherent to WebRTC's design — not something you configure

Cost implications

Relay mode means ALL media traffic flows through your server:

// Voice call (Opus 32kbps):
// 32 kbps × 2 directions = 64 kbps through TURN
// 1 hour = ~29 MB through your server

// Video call (VP8 500kbps):
// 500 kbps × 2 = 1 Mbps through TURN
// 1 hour = ~450 MB through your server

// With a 1TB/month VPS transfer limit:
// ~2200 hours of relay voice OR ~2200 hours of relay video
// In practice: most calls are short (1-5 min), and only some users enable relay

For Token v1 with a small user base, this is fine. At scale, you'd monitor TURN bandwidth and potentially charge for relay mode or optimize with bandwidth-adaptive bitrate.
