Relay-Only Calls & IP Privacy

A7 — Lesson 5 of 5 ~40 min
Why this matters for Token

In a normal WebRTC call, both peers exchange their IP addresses during ICE negotiation — that exchange is how the connection gets made. An IP address gives away your approximate location and your ISP. For a product whose entire promise is that the holder learns a label and nothing else, that is not a rough edge, it is the promise failing. Routing every call through your own TURN server closes it: the only address either side sees is the relay's.

This lesson is also the one where you decide something harder than a config value — whether a privacy control with a real cost should be a choice you offer the user, or a property of the product they cannot switch off. Token answers that differently from most apps, and the reasoning matters more than the line of code.

The IP exposure problem

During normal ICE, both sides generate candidates that include IP addresses:

// Candidate from Alice:
candidate: "candidate:1 1 udp 2122260223 192.168.1.5 54321 typ host"
candidate: "candidate:2 1 udp 1686052607 103.45.67.89 12345 typ srflx"

// Bob now knows:
// - Alice's local IP: 192.168.1.5 (not useful externally)
// - Alice's public IP: 103.45.67.89 (reveals ISP, approximate city)

With an IP address, someone can:

  • Determine your approximate location (city/district level)
  • Identify your ISP (Jio, Airtel, BSNL)
  • Potentially correlate with other services (if the IP is static)
  • Target you for network-level attacks

The fix: iceTransportPolicy: 'relay'

One line, and it is worth seeing both values side by side once — but read the first as what every other calling app does, not as a mode Token can be put into:

// The WebRTC default — what a normal video app ships:
const pc = new RTCPeerConnection({
  iceServers,
  iceTransportPolicy: 'all',  // try host, srflx, then relay
});
// Both peers learn each other's IPs during ICE

// Token, on every call, in app/ and web/ alike:
const pc = new RTCPeerConnection({
  iceServers,
  iceTransportPolicy: 'relay',  // ONLY use TURN relay
});
// Neither peer ever sees the other's IP — only the TURN server's IP

What changes

WebRTC default (all)Token (relay)
IP privacyBoth IPs exposedBoth IPs hidden
LatencyMinimal (P2P)+50-100ms (extra hop)
Bandwidth costFree (P2P)Server bandwidth
Connection reliability~85% success (may fail behind strict NAT)~99% success (TURN always works)
Audio qualityBest possibleSlightly reduced (jitter from extra hop)

Why there is no toggle

Your instinct here — it was this lesson's instinct too, for a while — is to make it a setting. A switch in Settings called "Hide IP Address", persisted, honest about the trade-off, letting the user choose. That is what a normal video-calling app does, and it is wrong for Token in a way worth slowing down over.

Ask who the setting would protect, and then ask whether that person can reach it.

A Token call has two ends. One is the user, who has the app, an account and a Settings screen. The other is the holder — someone who scanned a QR code off a parcel and opened a web page. They have no account, no app and no settings. They cannot turn anything on.

So a toggle can only ever be the issuer's. And the address that leaks is also the issuer's. Which means the control and the risk sit with the same person — the one who has to have understood ICE candidates well enough to go looking for a switch, before their first call with a stranger.

A default that leaks is the behaviour of the product

Whatever the toggle says, most people never open Settings. If the default is 'all', then "Token discloses your home IP address to whoever redeems your token" is a true sentence about the product — the toggle does not make it false, it just means you wrote down that you knew.

There is a second, quieter problem with the version of this lesson that shipped a toggle. Its guidance said: tokens for known contacts — friends, family — relay off is fine, they already know where you live. Read that against what Token is for. The product's value is with the delivery company, the estate agent, the job application: people who do not know the user and never should. The exception was being offered as the rule.

And the system cannot check the claim anyway. "These two already know each other" is not something the API can verify — it is something the user asserts, once, in a settings screen, about every call they will ever make.

What the code looks like instead

Simpler than the toggle version, which is usually the sign you have got it right:

// app/src/webrtc/PeerConnection.ts — in initialize():

async initialize() {
  const iceServers = await getIceServers();

  this.pc = new RTCPeerConnection({
    iceServers,
    iceTransportPolicy: 'relay',   // never 'all', never a variable
  });

  // ... rest of initialization
}

No import, no read, no ternary. The one thing to notice is that 'relay' is a literal. The moment it becomes a variable, something somewhere can set it to 'all', and the leak is one stale config value away.

What the user sees instead of a switch

Removing the toggle does not mean saying nothing. It means the Settings screen states a property of the product rather than offering a decision:

// app/src/screens/Settings.tsx — privacy section
import { View, Text, StyleSheet } from 'react-native';

function PrivacySection() {
  return (
    <View style={styles.section}>
      <Text style={styles.sectionTitle}>Call Privacy</Text>

      <View style={styles.settingRow}>
        <Text style={styles.settingLabel}>Your IP address is never shared</Text>
        <Text style={styles.settingDesc}>
          Every Token call is routed through our relay server, so the person
          you are talking to never learns your network address or approximate
          location. This cannot be turned off. Calls may take a moment longer
          to connect than a direct connection would.
        </Text>
      </View>
    </View>
  );
}

Note the last sentence. Not mentioning the latency cost would be the lazy version of this — the user notices it anyway, and a product that only tells you the good half of a trade-off teaches you not to believe the good half either.

The general shape of this decision

You will hit it again, well beyond WebRTC. When a security control has a cost, the tempting move is to make it optional and let the user decide. That is right when the person choosing is the person at risk, and they can tell which setting they need. It is wrong when the risk lands on someone who never sees the screen — and then "optional" is just a way of writing down that you chose the cheaper default on their behalf.

Server-side: can the TURN server see the call content?

No. WebRTC media is encrypted end-to-end with DTLS-SRTP. The TURN server relays encrypted packets — it cannot decrypt them. Even if someone compromises your TURN server, they get encrypted gibberish.

// What the TURN server sees:
// Source IP → TURN → Destination IP
// Encrypted audio/video bytes flowing through
// It knows WHO is calling whom (IP-level routing)
// It CANNOT hear or see the call content

// This is inherent to WebRTC's design — not something you configure

Checking that it actually worked

Setting the policy and having the policy are different claims. A typo, a merge that reintroduced a variable, a browser that ignores the option — the call still connects, sounds fine, and leaks. Nothing visible goes wrong, which is the whole difficulty with this class of bug.

pc.getStats() is how you find out. It returns a pile of report objects; the interesting one is the candidate pair that actually got used:

const reports = [];
(await pc.getStats()).forEach(r => reports.push(r));

const pair = reports.find(
  r => r.type === 'candidate-pair' && r.state === 'succeeded'
);
console.log(pair.localCandidateType, pair.remoteCandidateType);

Three things about that check are easy to get wrong

1. Only localCandidateType tells you whether you are protected. Your policy governs the candidates your ICE agent gathers and sends. The other side runs its own agent under its own policy, and you have no say in it. So a pair reading local relay / remote srflx is not a leak of your address — it means you are covered and they are not. Checking "are both relay?" reports a problem that isn't yours and would send you looking in the wrong file.

2. The state === 'succeeded' filter is load-bearing. ICE tries many pairs. Failed and in-flight ones are still in the stats, and a failed relay pair sitting next to a succeeded host pair is exactly the shape of a real leak. Take the first pair you find and you will read the reassuring one.

3. Finding nothing is not the same as finding relay. If the call is still connecting, or the platform returns no stats, there is no succeeded pair — and an audit that returns "fine" when it learned nothing is worse than no audit, because now something is reassuring you. It has to fail closed.

Where this ends up in the real app

In development, a warning in the console. In production, a counter: if any non-relay pair is ever observed, that is a bug worth an alert, because it means the guarantee this whole lesson is about is not holding for somebody. What you must not do is report the candidate types to the server — those are IP-derived, and shipping them to fix a privacy leak would be its own privacy leak.

Cost implications

Relay mode means ALL media traffic flows through your server:

// Voice call (Opus 32kbps):
// 32 kbps × 2 directions = 64 kbps through TURN
// 1 hour = ~29 MB through your server

// Video call (VP8 500kbps):
// 500 kbps × 2 = 1 Mbps through TURN
// 1 hour = ~450 MB through your server

// With a 1TB/month VPS transfer limit:
// ~38,000 hours of relay voice, but only ~2,400 hours of relay video
// Every call counts — there is no direct path to fall back to

That last line is the part the toggle version of this lesson got wrong. It reasoned that "only some users enable relay", which made the bandwidth look optional. It isn't: 100% of calls are relayed, so this is the real bill, not a worst case.

Notice the gap between the two figures. Voice is cheap enough that you would have to be doing well to notice it. Video is roughly sixteen times worse, and it is what will actually decide when this box stops being enough — ADR-0003 put the single-server ceiling in terms of connections and memory, and relayed video adds a second ceiling in egress that will probably arrive first.

Two things follow, and neither is "make it optional again". Monitor TURN egress from day one, so the trend is visible before the invoice is. And when it does bite, the first thing to reconsider is narrowing relay-only to redemption calls on the web page — where the other party is genuinely a stranger — rather than weakening it everywhere. That trade is written up in ADR-0008 as the named escape hatch.

Now build it yourself

Write relayAudit(reports) — the check that tells you whether the policy actually took effect on a live call. It is a plain function over an array of stats objects, so you can write and test it right here, without a phone or a TURN server.
