Coolify Setup

B9 — Lesson 2 of 3  |  ~55 min

Why this matters for Token: You could deploy with raw docker compose on a VPS — but then you're manually SSHing in for every deploy, handling TLS certificates yourself, and restarting containers by hand when they crash. Coolify gives you a Heroku-like experience on your own hardware: push to git → automatic build → deploy → TLS. It's open source, runs on a single $12/month VPS, and you own everything.

What is Coolify?

Coolify is an open-source, self-hosted PaaS (Platform as a Service). Think Heroku or Vercel, but running on your own VPS. It manages:

  • Builds — detects your Dockerfile, builds images on the server
  • Deploys — zero-downtime deploys with health checks
  • TLS — automatic Let's Encrypt certificates
  • Databases — one-click Postgres, Redis, etc. with backups
  • Domains — custom domain routing with a built-in reverse proxy (Traefik)
  • Environment variables — encrypted secrets stored in Coolify's database

Step 2: Install Coolify

SSH into your VPS and run the one-line installer:

# SSH in
ssh root@your-vps-ip

# Install Coolify (one command)
curl -fsSL https://cdn.coollabs.io/coolify/install.sh | bash

# This installs:
# - Docker
# - Docker Compose
# - Coolify itself (as a Docker container)
# - Traefik (reverse proxy)
# - A PostgreSQL instance for Coolify's own data

After installation, Coolify's dashboard is at http://your-vps-ip:8000. Create your admin account on first visit.

Step 3: Connect Your Git Repository

In Coolify's dashboard:

  1. Go to Sources → Add GitHub
  2. Authorize Coolify's GitHub App on your Token repository
  3. Coolify can now pull your code and detect pushes

Step 4: Deploy the Database Services

Deploy Postgres and Redis as Coolify-managed services (not from your Dockerfile):

Postgres

  1. Resources → New → Database → PostgreSQL
  2. Version: 16-alpine
  3. Database name: token_prod
  4. Set a strong password (Coolify generates one by default)
  5. Enable Persistent Storage
  6. Do NOT expose to the internet — only internal network access

Redis

  1. Resources → New → Database → Redis
  2. Version: 7-alpine
  3. Enable persistent storage
  4. Do NOT expose to the internet

After deploying, Coolify shows you the internal connection URLs. Copy these — you'll put them in the API's environment variables.

Step 5: Deploy the API

  1. Resources → New → Application
  2. Source: your GitHub repo
  3. Branch: main
  4. Build Pack: Dockerfile
  5. Dockerfile location: api/Dockerfile
  6. Port: 3000

Environment Variables

In the application settings, add:

DATABASE_URL=postgres://token:GENERATED_PASSWORD@pgbouncer:6432/token_prod
REDIS_URL=redis://redis-container:6379
JWT_SECRET=generate-a-64-char-random-string
JWT_REFRESH_SECRET=different-64-char-random-string
NODE_ENV=production
CORS_ORIGIN=https://tokn.app
EXPO_ACCESS_TOKEN=your-expo-token-for-push-notifications

# ADR-0007. Without these the API cannot look up or display a single token
# code, so it must refuse to start rather than come up half working.
TOKEN_CODE_PEPPER=64-hex-chars   # hashed into every code_hash
TOKEN_CODE_KEY=base64-32-bytes   # AES-256-GCM key for code_enc

Generating secrets:

# 64 hex characters, for the JWT secrets and the pepper
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

# A 32-byte AES key, base64 - a different encoding for a different job
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"

Refuse to start without them. A container that boots with a missing secret and fails on the first request that needs it turns a configuration mistake into an incident: 

// api/src/config.ts - runs before anything listens on a port
const SPEC = {
  DATABASE_URL:       { required: true, kind: 'url', schemes: ['postgres:', 'postgresql:'] },
  REDIS_URL:          { required: true, kind: 'url', schemes: ['redis:', 'rediss:'] },
  JWT_SECRET:         { required: true, kind: 'hex',    bytes: 32 },
  JWT_REFRESH_SECRET: { required: true, kind: 'hex',    bytes: 32 },
  TOKEN_CODE_PEPPER:  { required: true, kind: 'hex',    bytes: 32 },
  TOKEN_CODE_KEY:     { required: true, kind: 'base64', bytes: 32 },
  CORS_ORIGIN:        { required: true, kind: 'url', schemes: ['https:'] },
};

const { ok, problems } = checkEnv(process.env, SPEC);
if (!ok) {
  // Names and reasons only. NEVER the values - this line goes to a deploy
  // log that more people can read than can read the database.
  for (const p of problems) console.error('config: ' + p.name + ' - ' + p.problem);
  process.exit(1);          // health check never passes, old container stays
}
Present is not the same as usable

The version everybody writes is REQUIRED.filter((k) => !process.env[k]) — is it set? That catches the variable you forgot and misses the one you got wrong, and the one you got wrong is the likelier mistake, because you had to be thinking about it to set it at all.

Here is the specific way it happens. The pepper is 64 hex characters and the key is base64. Both are "32 random bytes", both come from a one-line crypto.randomBytes(32) command, and the two commands differ only in the encoding at the end. Paste the hex one into TOKEN_CODE_KEY and you have 48 bytes of perfectly valid base64. It is present, it is non-empty, the check passes, the container starts, the health check goes green — and createCipheriv throws on the first token anybody tries to create.

Which is exactly the incident the paragraph above promises to prevent. A startup check that only asks "is it set?" turns a missing variable into a clean refusal and a malformed one into a 3am page.

And the message must not contain the value

The obvious helpful message is "TOKEN_CODE_KEY must decode to 32 bytes, got 48" — followed, helpfully, by the offending string. That prints a production secret into a deploy log, which is read by more people than the database is, kept for longer than anybody intends, and shipped to whatever collects your build output.

ADR-0007 makes this point about token codes in log lines, and it generalises: a diagnostic about a secret may name the variable and describe the problem, and must never quote the value. "expected 32 bytes, got 48" is entirely sufficient to fix it.

These two secrets are not like the others

Lose JWT_SECRET and everyone is logged out — annoying, and they log back in. Lose TOKEN_CODE_PEPPER or TOKEN_CODE_KEY and every token ever issued is permanently unusable: no code can be matched to its hash, and no stored code can be decrypted to show the owner. There is no recovery and no support process. The database is intact and worthless.

So they belong in the disaster-recovery plan alongside the database — and stored somewhere the database backups are not, because a backup that contains both the data and the keys to it is a single thing to lose and a single thing to steal.

Domain & TLS

  1. In application settings → Domain: api.tokn.app
  2. Coolify automatically provisions a Let's Encrypt certificate
  3. Point your DNS A record to the VPS IP

Health Check

// api/src/routes/health.ts
import { Router } from 'express';
import { db } from '../db';
import { isReady } from '../lifecycle';

const router = Router();

router.get('/health', async (req, res) => {
  // Read the shutdown flag FIRST. b9/0001's handler calls setNotReady() and
  // then waits, and this is the only thing that makes that wait mean
  // anything - without it the proxy keeps sending work to a container that
  // is closing its database pool.
  if (!isReady()) {
    return res.status(503).json({ status: 'shutting_down' });
  }

  try {
    await db.query('SELECT 1');
    res.json({ status: 'ok', timestamp: new Date().toISOString() });
  } catch (err) {
    res.status(503).json({ status: 'unhealthy', error: 'database unreachable' });
  }
});

export default router;

Configure Coolify to use /health as the health check path. It will only route traffic to the new container after it responds 200.

Without that first check, the graceful shutdown's first step does nothing

b9/0001's handler opens with "fail readiness first, so the proxy stops sending new requests BEFORE we start refusing them", calls setNotReady(), and waits two seconds for the proxy to notice. The endpoint above, as it was originally written, never read that flag. So the proxy noticed nothing, kept routing traffic for the whole two seconds, and then kept routing it while the pool was closing.

Neither file is wrong on its own. The handler sets a flag; the endpoint answers a question. They simply never agreed that it was the same flag — and the cost is that the most carefully reasoned step in the shutdown sequence was a two-second pause that achieved nothing.

Web Environment Variables

# These are build-time variables (Vite embeds them at build time)
VITE_API_URL=https://api.tokn.app

Important: Vite environment variables are embedded at build time, not runtime. If you change VITE_API_URL, you need to redeploy (rebuild) for it to take effect.

Step 7: DNS Configuration

At your domain registrar, add these A records:

# DNS records (replace 203.0.113.50 with your actual VPS IP)
tokn.app        A    203.0.113.50
api.tokn.app    A    203.0.113.50

After DNS propagates (usually 5–30 minutes), Coolify's Traefik will route:

  • https://tokn.app → web container
  • https://api.tokn.app → API container

Automatic Deploys

With the GitHub integration, every push to main triggers:

  1. Coolify pulls the latest code
  2. Builds a new Docker image using your Dockerfile
  3. Starts the new container alongside the old one
  4. Runs the health check on the new container
  5. If healthy: routes traffic to the new container, stops the old one
  6. If unhealthy: keeps the old container running, marks deploy as failed

This is zero-downtime deployment — users never see an error page during deploys.

Running Migrations on Deploy

Your API needs to run database migrations before it starts serving traffic. Add a pre-start script:

// api/package.json
{
  "scripts": {
    "start": "node dist/server.js",
    "prestart": "node dist/migrate.js",
    "build": "tsc"
  }
}
# Or use a custom start command in the Dockerfile
CMD ["sh", "-c", "node dist/migrate.js && node dist/server.js"]

Warning: If a migration fails, the container won't start, the health check won't pass, and Coolify will keep the old container running. This is the safe behavior — a failed migration never reaches users.

Two replicas, two migrators

prestart runs in every container. With one replica that is fine and invisible. With two, both start together and both begin applying the same migration — and "add a column" run twice is an error at best and a half-applied schema at worst.

Postgres has the tool for this built in. One advisory lock, held for the duration, and the second migrator waits and then finds nothing to do: 

// api/src/migrate.ts
await client.query('SELECT pg_advisory_lock($1)', [MIGRATION_LOCK_ID]);
try {
  await applyPendingMigrations(client);   // the second replica finds none
} finally {
  await client.query('SELECT pg_advisory_unlock($1)', [MIGRATION_LOCK_ID]);
}

Deploy on one box today and this is dead code. Add a replica in a year and it is the difference between a deploy and an outage — which is ADR-0003 in one paragraph: build for N, run one.

Backups — the step this lesson used to skip

Everything above deploys a database onto a single VPS with a single disk. Without the next few lines, the whole system is one hardware failure, one mistaken DROP, or one bad migration away from gone. 

# A nightly dump, kept off the machine that made it
0 3 * * * docker exec postgres-container pg_dump -U token token_prod   | gzip > /backups/token-$(date +\%F).sql.gz

# Then push it somewhere else entirely. A backup on the same disk as the
# database is not a backup - it is a second copy of the thing that failed.
#
# `sync`, not `copy`. `rclone copy` never deletes at the destination, so the
# remote quietly becomes a permanent archive of every dump you ever took -
# including the ones your retention policy destroyed here. b9/0003 has the
# argument; b10/0002 has the sentence it breaks.
rclone sync /backups remote:token-backups

Three things that are easy to skip and are the whole point:

  • Restore, do not just back up. An untested backup is a belief. Restore into a scratch container and run the API against it — quarterly, and written down as a runbook, because the day you need it is not the day to work out the command.
  • The secrets are not in the dump. pg_dump captures code_hash and code_enc and nothing that makes them meaningful. Restoring the database without TOKEN_CODE_PEPPER and TOKEN_CODE_KEY gives you a table of unusable rows.
  • And they must not be stored with it. Which is the awkward part: the two must be recoverable together and kept apart. A password manager entry, or a sealed envelope, is a legitimate answer at this scale — what is not legitimate is "they are in the Coolify UI", because that is on the machine you are backing up.

Why this way (and what was rejected)

One box, an architecture built for more

Coolify on a VPS was chosen over a managed platform (Render, Railway, Fly) and over AWS. The managed platforms are genuinely easier and cost four to ten times more at this size; AWS is cheaper at large scale and much more to learn. Neither was rejected for the money alone — the deciding factor is that Token self-hosts things a platform will not run for you: coturn for TURN relay, and a Postgres you control the extensions and the partitioning of.

ADR-0003 is the reason this does not paint you into a corner. Nothing above assumes a single process: no in-memory sessions, no node-local socket registry, Redis for anything shared. Adding a second replica is a number in the Coolify UI, not a rewrite.

pgbouncer between the API and Postgres

Connecting the API straight to Postgres works and stops working quietly. Postgres allocates a process per connection and defaults to about 100; a pool of 20 per replica plus migrations plus a psql session gets there faster than expected, and the failure is new connections being refused while the ones already open are fine — so the API looks healthy and half the requests fail.

pgbouncer in transaction mode multiplexes hundreds of client connections onto a handful of real ones. It goes in now because moving to it later means re-testing every query that assumed a session — prepared statements, SET, advisory locks held across statements.

Health checks that distinguish "restart me" from "do not send traffic"

The obvious health check tests every dependency. It is a trap: if /health fails when Redis blips, the orchestrator kills containers because a dependency is unwell, and now the API is down too. A dependency outage becomes an application outage, with extra restarts on top.

Liveness asks "is this process wedged?" and should test almost nothing — if it fails, the answer is a restart. Readiness asks "should this instance receive traffic right now?" and may check Postgres, because an API with no database genuinely cannot serve. Redis belongs in neither: sockets degrade without it, HTTP does not, and killing the API over it makes things worse.

When this breaks

The disk fails and there was never a backup

This lesson previously deployed a database and never mentioned backing it up. On managed hosting that omission is survivable because someone else made the decision for you. On a VPS it is total: one disk, one machine, no snapshots unless you asked. The section above exists because "we will set up backups later" is how it actually goes wrong.

The backup restores and the tokens are all dead

Specific to ADR-0007 and easy to miss until it matters: pg_dump gives you code_hash and code_enc, both of which are meaningless without two values that live only in the environment. Restore the database onto a new VPS without them and every token is unusable — the data is intact and inert. The restore runbook has to list the secrets as an input, not an afterthought.

Two replicas migrate at once

prestart runs per container. Two start together, both apply the same migration, and you get a duplicate-column error at best or a half-applied schema at worst — on the deploy where you also added the second replica, so the cause is not obvious.

Vite bakes the API URL in at build time

Already in the lesson and worth repeating here because it breaks deploys in a confusing way: changing VITE_API_URL in Coolify and restarting does nothing. The value is compiled into the bundle. It needs a rebuild, which means the web app has environment-specific builds, not environment-specific config.

Secrets are visible to anyone with the box

Coolify's environment variables are readable in its UI and via docker inspect. That is acceptable — they have to reach the process somehow — as long as it is understood: anyone with root on that VPS has every secret, so VPS access is the security boundary, and rotating a leaked secret means a rotation plan. For TOKEN_CODE_PEPPER, rotation is a migration that rewrites every row (ADR-0007), not a value you can quietly change.
