Logs, Backups & Monitoring

B9 — Lesson 3 of 3  |  ~45 min

Why this matters for Token: Your app is live. Users are issuing tokens, redeeming them, and chatting through your WebSocket server. When something breaks at 2 AM, you need three things: logs that tell you what went wrong, backups so you don't lose data, and alerts so you know it happened without users telling you. This lesson sets up all three.

Structured Logging

Console.log is for development. In production, you need structured logs — JSON objects with consistent fields that can be searched, filtered, and aggregated.

Why JSON Logs?

// ❌ Unstructured — hard to parse, impossible to filter
console.log("User 42 redeemed token MERC-8GH2 at 2024-03-15T10:30:00Z");

// ✓ Structured — machine-readable, searchable
{
  "level": "info",
  "msg": "token redeemed",
  "userId": 42,
  "tokenId": 42,
  "timestamp": "2024-03-15T10:30:00.123Z",
  "requestId": "req-abc-123",
  "duration_ms": 45
}

Building a Logger with pino

pino is the fastest Node.js JSON logger — 10x faster than winston because it writes JSON directly without formatting overhead.

# Install
npm install pino pino-http
// api/src/logger.ts
import pino from 'pino';

export const logger = pino({
  level: process.env.LOG_LEVEL || 'info',
  // In production, output raw JSON (for log aggregators)
  // In development, use pino-pretty for readable output
  transport: process.env.NODE_ENV !== 'production'
    ? { target: 'pino-pretty', options: { colorize: true } }
    : undefined,
  // Base fields included in every log line
  base: {
    service: 'token-api',
    version: process.env.npm_package_version,
  },
});

// Child loggers inherit parent fields and add their own
export function createChildLogger(context: Record<string, unknown>) {
  return logger.child(context);
}

Request Logging with Correlation IDs

Every HTTP request gets a unique ID. All log lines during that request include it — so you can trace a single request across your entire system.

// api/src/middleware/requestLogger.ts
import { randomUUID } from 'crypto';
import pinoHttp from 'pino-http';
import { logger } from '../logger';

export const requestLogger = pinoHttp({
  logger,
  genReqId: (req) => {
    // Use client-provided ID if present, otherwise generate one
    return (req.headers['x-request-id'] as string) || randomUUID();
  },
  customProps: (req) => ({
    requestId: req.id,
  }),
  // Don't log health check spam
  autoLogging: {
    ignore: (req) => req.url === '/health',
  },
  // What to include in the request log
  serializers: {
    req: (req) => ({
      method: req.method,
      url: req.url,
      // Don't log authorization header (contains JWT)
      headers: { 'user-agent': req.headers['user-agent'] },
    }),
    res: (res) => ({
      statusCode: res.statusCode,
    }),
  },
});

// Usage in Express
// app.use(requestLogger);
// Now every request logs: method, url, statusCode, duration, requestId

Application-Level Logging

// In your route handlers, use the request's logger
// (it already has requestId attached)

import { Request, Response } from 'express';

export async function redeemToken(req: Request, res: Response) {
  // POST /api/redeem, with the code in the BODY. Never req.params:
  // a path reaches the proxy access log, browser history, Referer and
  // crash reports before your handler ever sees it (ADR-0007).
  const { code } = req.body;

  // req.log is added by pino-http — it includes requestId automatically.
  // NOTE what is NOT in this line. There is nothing to identify the
  // attempt by yet, and wanting one is exactly the pressure that puts
  // a capability into a log file.
  req.log.info('token redemption attempt');

  try {
    const token = await findTokenByCodeHash(codeHashInput(code));

    // ONE refusal, one shape. b7/0001: a code that never existed and a
    // code revoked yesterday must be indistinguishable from outside,
    // or the error handler gives back the keyspace the code cost.
    if (!token || token.revoked_at || hasExpired(token)) {
      // The real reason goes in the LOG, where it is useful to you and
      // invisible to whoever is guessing. tokenId is null when there
      // was no token -- which is itself the finding.
      req.log.warn(
        { tokenId: token?.id ?? null, refusal: refusalReason(token) },
        'redemption refused'
      );
      return res.status(404).json({ error: 'not available' });
    }

    const event = await createRedemptionEvent(token.id, req.ip);
    req.log.info({ tokenId: token.id, eventId: event.id }, 'token redeemed');

    res.json({ success: true, conversationId: event.conversation_id });
  } catch (err) {
    req.log.error({ err }, 'token redemption failed');
    res.status(500).json({ error: 'internal error' });
  }
}
This handler broke three rules at once, and it is the logging lesson

Until 2026-08-23 it read the code from req.params, logged it on four separate lines, and answered 404 for "no such token" and 410 for "revoked". Each of those is forbidden somewhere else in this course, and all three were here together — in the lesson that teaches production logging, which is the worst place for any of them.

  • The code was in the path. ADR-0007 puts it in a POST body precisely because a path reaches the proxy access log before your code runs. Logging carefully in the handler is pointless if nginx already wrote it.
  • The code was in four log lines. A token code is not an identifier, it is the capability — so those lines are live credentials in a file designed to be copied to a log aggregator. x2/0002 makes the same argument from the debugging side.
  • 404 and 410 are a code oracle. A 404 means keep guessing, a 410 means you found one. Sixth layer, after b7/0001, a8/0002, b3/0004, b4/0001 and a9/0002.

The interesting part is the first log line, because it is the one with nothing in it. At that point the token has not been found, so there is no tokenId to record — and the pull towards writing something identifying is exactly how the code got there. The honest answer is that requestId is enough: it ties this line to the refusal that follows, which does carry an id when there is one.

And tokenId: null in the refusal is not a gap. It says no token matched, which is a different finding from this token was refused — the same distinction c5/0004 draws between gone and not-fetched, kept where the operator can see it and the caller cannot.

In production, set LOG_LEVEL=info. Switch to debug when investigating an issue. Never run trace in production — the volume will fill your disk.

Database Backups

Your users' tokens, messages, and access rules live in Postgres. If the database is lost, everything is lost. Automated backups are non-negotiable.

pg_dump — The Standard Backup Tool

# Full database dump (custom compressed format)
pg_dump -U token -d token_prod -Fc > backup_2024-03-15.dump

# Restore from backup
pg_restore -U token -d token_prod --clean backup_2024-03-15.dump

# SQL-format dump (readable, larger)
pg_dump -U token -d token_prod > backup_2024-03-15.sql

Automated Backup Script

#!/bin/bash
# api/scripts/backup.sh
# Runs daily via cron — dumps Postgres and keeps 7 days of backups

set -euo pipefail

BACKUP_DIR="/backups/postgres"
RETENTION_DAYS=7
TIMESTAMP=$(date +%Y-%m-%d_%H-%M-%S)
FILENAME="token_prod_${TIMESTAMP}.dump"

# Create backup directory if it doesn't exist
mkdir -p "$BACKUP_DIR"

# Dump the database (using Docker exec into the Postgres container)
docker exec token-postgres pg_dump \
  -U token \
  -d token_prod \
  -Fc \
  > "${BACKUP_DIR}/${FILENAME}"

# Verify the backup is non-empty
if [ ! -s "${BACKUP_DIR}/${FILENAME}" ]; then
  echo "ERROR: Backup file is empty!" >&2
  exit 1
fi

# Report size
BACKUP_SIZE=$(du -h "${BACKUP_DIR}/${FILENAME}" | cut -f1)
echo "Backup created: ${FILENAME} (${BACKUP_SIZE})"

# Delete backups older than the retention period.
#
# Note the -1. `find -mtime +N` means "more than N whole days old", and this
# script runs once a day -- so a row deleted just after the 03:00 dump sits
# in that dump until the prune that is a whole day past the promise. Two
# rounding errors in the same direction, against a number b10/0002 gives to
# users in writing. RETENTION_DAYS stays the ONE number; the mechanism runs
# a day ahead of it.
find "$BACKUP_DIR" -name "*.dump" -mtime +$((RETENTION_DAYS - 1)) -delete
echo "Cleaned up local backups older than ${RETENTION_DAYS} days"

Scheduling with cron

# SSH into your VPS, then:
crontab -e

# Add this line — runs backup at 3:00 AM daily
0 3 * * * /opt/token/scripts/backup.sh >> /var/log/token-backup.log 2>&1

# Verify it's scheduled
crontab -l

Off-Site Backups

A backup on the same server as the database doesn't protect against disk failure or a compromised server. Copy backups off-site:

# Option 1: rsync to a second VPS or NAS.
# --delete makes the destination MIRROR the source, so the prune that ran
# above reaches here too. Without it this is a copy that only ever grows.
rsync -az --delete /backups/postgres/ backup-user@other-server:/backups/token/

# Option 2: Upload to S3-compatible storage (Backblaze B2, ~$0.005/GB)
# Install rclone, configure a remote, then:
#   `rclone copy` NEVER deletes at the destination. `rclone sync` does.
rclone sync /backups/postgres/ b2:token-backups/postgres/

# ...and if the bucket has versioning or a lifecycle rule of its own, the
# delete above only hides the object. Expire it at the bucket too:
#   B2:  lifecycle rule, daysFromHidingToDeleting = 1
#   S3:  lifecycle rule on noncurrent versions

# Option 3: Coolify's built-in backup feature (if using managed Postgres)
# Configure in Coolify → Database → Backups → Enable S3
# Set the retention there as well — it is a third copy with its own clock.
The copy you made so it would survive things is the copy nobody expires

Until 2026-08-25 this section said rclone copy and rsync -az. Neither deletes anything at the destination — that is what makes them safe to run, and it is the reason they are what everyone reaches for. So the script above pruned /backups/postgres faithfully every night, and every dump it deleted was already sitting in Backblaze, for ever.

On its own that is a storage bill. What makes it a defect is b10/0002, which tells users in a published privacy notice: "Copies in our encrypted backups are overwritten within 7 days." That sentence is a statement about every copy, and the retention that backed it existed in exactly one of the three places a dump ends up.

A retention policy is a property of the data, not of a directory. Every location holding a dump needs the same clock — the server, the off-site remote, the bucket's own versioning, and Coolify's built-in backups if you also switched those on. This is CLAUDE.md's rule about a value modelled in two places, arriving as four copies of a file: the one you forget is the one that outlives the promise, and nothing anywhere errors.

It is also why the exercise below prunes a list of backups rather than a folder. Location is something a copy has; it is never a reason for that copy to expire on a different schedule.

Testing Restores

A backup you've never restored from is not a backup. Test quarterly:

# Restore to a temporary database (not production!)
createdb -U token token_restore_test
pg_restore -U token -d token_restore_test /backups/postgres/latest.dump

# Verify data is intact
psql -U token -d token_restore_test -c "SELECT COUNT(*) FROM users;"
psql -U token -d token_restore_test -c "SELECT COUNT(*) FROM tokens;"

# Clean up
dropdb -U token token_restore_test

Record the result, because it is a third state and not a boolean. A dump is verified once it has restored, corrupt once it has failed to, and unchecked until one of those happens — which is what almost every dump you own is, almost all of the time. Those are the three values the exercise below works from, and collapsing the middle one into either neighbour is the whole of its third rule: unchecked is not a promise that the file is fine, and it is not an accusation that it is broken.

Health Checks & Uptime Monitoring

You need to know when your app is down before your users tell you.

Internal Health Checks

You already wrote /health in the previous lesson. Extend it to check all dependencies:

// api/src/routes/health.ts
import { Router } from 'express';
import { db } from '../db';
import { redisClient } from '../redis';
import { isReady } from '../lifecycle';

const router = Router();

// LIVENESS — is the process running?
// This must keep answering 200 during a graceful shutdown. It is the answer
// to "should you restart me", and the whole point of a graceful shutdown is
// that you should NOT: the process is draining on purpose.
router.get('/health/live', (req, res) => {
  res.json({ status: 'ok' });
});

// READINESS — should the proxy send this container new work?
router.get('/health/ready', async (req, res) => {
  // The shutdown flag comes FIRST, and it is not a formality. b9/0001's
  // handler calls setNotReady() and then waits two seconds for the proxy to
  // notice; b9/0002's /health was given this same check on 2026-08-24 and
  // this endpoint was not. Postgres and Redis are still perfectly reachable
  // during those two seconds, so every check below passes and the answer is
  // a confident 200 from a container that is closing its pool.
  if (!isReady()) {
    return res.status(503).json({ status: 'shutting_down' });
  }

  const checks: Record<string, 'ok' | 'fail'> = {};

  try {
    await db.query('SELECT 1');
    checks.database = 'ok';
  } catch {
    checks.database = 'fail';
  }

  try {
    await redisClient.ping();
    checks.redis = 'ok';
  } catch {
    checks.redis = 'fail';
  }

  const allOk = Object.values(checks).every(v => v === 'ok');
  const statusCode = allOk ? 200 : 503;

  res.status(statusCode).json({
    status: allOk ? 'healthy' : 'degraded',
    checks,
    timestamp: new Date().toISOString(),
    uptime: process.uptime(),
  });
});

export default router;
Splitting the endpoint is the fix, not the decoration — a single /health cannot express the state a shutdown lives in

There are three answers, not two: alive and ready, alive but not taking work, and not alive. A graceful shutdown spends its entire life in the middle one, and that is exactly the state one endpoint cannot report. b9/0002 has a single /health, so its 503 during shutdown is simultaneously telling the proxy stop routing (right) and telling anything watching liveness restart me (wrong — it is closing the pool on purpose).

So the split is load-bearing, and the direction of each is the part that gets written backwards. Liveness must ignore the flag; readiness must read it. Swap them and you get an orchestrator that kills the container mid-drain, which is the ungraceful exit the whole sequence exists to avoid.

This lesson shipped /health/ready without the flag until 2026-08-25 — the same defect b9/0002 was fixed for a day earlier, in the file that introduces the better-shaped endpoint and tells you to point external monitoring at it. Neither file was wrong alone. One sets a flag, two others answer a question, and the fix to one of them was never carried to the other.

External Uptime Monitoring

An external service pings your health endpoint every minute. If it fails, you get an alert. Free options:

  • UptimeRobot — 50 free monitors, 5-min intervals, email/SMS/Slack alerts
  • Uptime Kuma — self-hosted (run it on your VPS), 1-min intervals
  • Betterstack (formerly Better Uptime) — free tier with status pages

Basic Alerting Pattern

For a solo developer, the simplest alerting is a webhook that sends to your phone:

// api/src/services/alerting.ts
import { logger } from '../logger';

const ALERT_WEBHOOK = process.env.ALERT_WEBHOOK_URL; // Slack, Discord, or Telegram

interface Alert {
  severity: 'warning' | 'critical';
  title: string;
  detail: string;
}

export async function sendAlert(alert: Alert): Promise<void> {
  if (!ALERT_WEBHOOK) {
    logger.warn(alert, 'alert triggered but no webhook configured');
    return;
  }

  try {
    await fetch(ALERT_WEBHOOK, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({
        text: `[${alert.severity.toUpperCase()}] ${alert.title}\n${alert.detail}`,
      }),
    });
  } catch (err) {
    // Don't throw — alerting failure shouldn't crash the app
    logger.error({ err, alert }, 'failed to send alert');
  }
}

// Usage examples:
// sendAlert({ severity: 'critical', title: 'Database unreachable', detail: 'SELECT 1 timed out after 5s' });
// sendAlert({ severity: 'warning', title: 'High memory usage', detail: 'RSS: 450MB / 512MB limit' });

Monitoring Key Metrics

Even without a full monitoring stack (Prometheus/Grafana), you can track essential metrics in your logs:

// api/src/middleware/metrics.ts
import { logger } from '../logger';

// Log slow requests
export function slowRequestLogger(thresholdMs = 1000) {
  return (req: any, res: any, next: any) => {
    const start = Date.now();

    res.on('finish', () => {
      const duration = Date.now() - start;
      if (duration > thresholdMs) {
        req.log.warn({
          duration_ms: duration,
          threshold_ms: thresholdMs,
          method: req.method,
          url: req.url,
        }, 'slow request detected');
      }
    });

    next();
  };
}

// Periodic health report (every 5 minutes)
setInterval(async () => {
  const memUsage = process.memoryUsage();
  logger.info({
    memory: {
      rss_mb: Math.round(memUsage.rss / 1024 / 1024),
      heap_used_mb: Math.round(memUsage.heapUsed / 1024 / 1024),
      heap_total_mb: Math.round(memUsage.heapTotal / 1024 / 1024),
    },
    uptime_hours: Math.round(process.uptime() / 3600 * 10) / 10,
  }, 'periodic health report');
}, 5 * 60 * 1000);

Docker Log Rotation

Without rotation, container logs grow forever and fill your disk. Configure Docker's log driver to auto-rotate:

// /etc/docker/daemon.json (on your VPS)
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "50m",
    "max-file": "5"
  }
}

// Each container keeps at most 5 log files of 50MB each = 250MB max per container
// Restart Docker after changing: sudo systemctl restart docker

Putting It All Together

//
// ✓ Structured JSON logging (pino)
// ✓ Request correlation IDs (every log line traceable)
// ✓ Health check endpoints (liveness + readiness)

Now build it yourself: prune the backups

Everything above decides what to write. This decides what to destroy — and it is the only decision in the lesson that is wrong in both directions. Delete too little and you break the sentence b10/0002 publishes to users. Delete too much and the thing you delete is the last copy of their data.

Which is why it is a list of backups and not a folder: the shell script could only ever see one of the places a dump lives.
