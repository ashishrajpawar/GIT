Docker Fundamentals

B9 — Lesson 1 of 3  |  ~50 min

Why this matters for Token: Your API works perfectly on your laptop. But the production server runs a different OS, different Node version, different file paths. Docker packages your app with its entire runtime — same binary everywhere. When you deploy Token to a VPS, you're not installing Node and running npm start — you're shipping a container image that works identically whether it runs on your laptop, a $5 VPS, or a $50,000 Kubernetes cluster. Portability means you're never locked in.

What Problem Does Docker Solve?

Without Docker, deploying a Node.js app means:

  1. SSH into the server
  2. Install the right Node version
  3. Clone the repo
  4. Run npm install (hope the native dependencies compile)
  5. Set up environment variables
  6. Configure a process manager (PM2, systemd)
  7. Pray that the server's OpenSSL version is compatible with yours

With Docker: push one image, pull it on the server, run it. Everything your app needs is inside the image. The server only needs Docker installed — nothing else.

Core Concepts

Image vs Container

An image is a read-only blueprint — like a class definition. A container is a running instance of that image — like an object instantiated from the class.

// Analogy in JavaScript terms
class TokenApi {          // ← image (the blueprint)
  constructor(env) { }
  listen(port) { }
}

const instance1 = new TokenApi(prodEnv);   // ← container 1
const instance2 = new TokenApi(stagingEnv); // ← container 2
// Same image, different config, running in parallel

Layers

A Docker image is built in layers. Each instruction in a Dockerfile creates one layer. Layers are cached — if nothing changed in an early layer, Docker reuses it instead of rebuilding. This makes subsequent builds fast.

# Each of these lines creates a layer:
FROM node:20-alpine       # Base layer: Alpine Linux + Node 20
WORKDIR /app              # Layer: creates /app directory
COPY package*.json ./     # Layer: copies package files
RUN npm ci                # Layer: installs dependencies (CACHED if package.json unchanged)
COPY . .                  # Layer: copies source code
RUN npm run build         # Layer: compiles TypeScript

Volumes

Containers are ephemeral — when you remove one, its data is gone. Volumes persist data outside the container lifecycle. Postgres uses a volume so your data survives container restarts.

Networks

Containers are isolated by default. A network connects containers to each other. Your API container needs to reach the Postgres container, but the outside world should only reach the API.

Writing a Dockerfile for Token's API

A Dockerfile is a recipe. Each instruction adds a layer to the image. Here's the production Dockerfile for api/:

# api/Dockerfile

# --- Stage 1: Build ---
FROM node:20-alpine AS builder

WORKDIR /app

# Copy package files first (layer caching: only re-install if deps change)
COPY package.json package-lock.json ./
COPY shared/package.json shared/

# Install ALL dependencies (including devDeps for TypeScript compilation)
RUN npm ci

# Copy source code
COPY tsconfig.json ./
COPY shared/ shared/
COPY src/ src/

# Compile TypeScript
RUN npm run build

# --- Stage 2: Production ---
FROM node:20-alpine AS production

WORKDIR /app

# Only install production dependencies
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

# Copy compiled output from builder stage
COPY --from=builder /app/dist ./dist

# Non-root user for security
RUN addgroup -S token && adduser -S token -G token
USER token

# Metadata
EXPOSE 3000
ENV NODE_ENV=production

# Start the server
CMD ["node", "dist/server.js"]

Why Multi-Stage?

The builder stage has TypeScript, devDependencies, and source files — all things you don't need in production. The production stage only has the compiled JS and production dependencies. Result: a much smaller image (often 3–5× smaller) with less attack surface.

# Comparison
# Single-stage: ~350MB (includes TypeScript, all devDeps, source)
# Multi-stage:  ~80MB  (only compiled JS + production deps)

Dockerfile for Token's Web Page

# web/Dockerfile

# --- Stage 1: Build ---
FROM node:20-alpine AS builder

WORKDIR /app

COPY package.json package-lock.json ./
COPY shared/package.json shared/

RUN npm ci

COPY tsconfig.json vite.config.ts ./
COPY shared/ shared/
COPY src/ src/
COPY index.html ./
COPY public/ public/

RUN npm run build

# --- Stage 2: Serve with nginx ---
FROM nginx:alpine AS production

# Copy built static files to nginx's serve directory
COPY --from=builder /app/dist /usr/share/nginx/html

# Custom nginx config for SPA routing
COPY nginx.conf /etc/nginx/conf.d/default.conf

EXPOSE 80

CMD ["nginx", "-g", "daemon off;"]

nginx config for single-page app routing

# web/nginx.conf
server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;

    # SPA fallback: any route that doesn't match a file → index.html
    location / {
        try_files $uri $uri/ /index.html;
    }

    # Cache static assets aggressively
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # Health check endpoint
    location /health {
        return 200 'ok';
        add_header Content-Type text/plain;
    }
}

Docker Compose for Local Development

You don't want to run docker build and docker run with 10 flags every time you start developing. Docker Compose defines your entire local stack in one file:

# docker-compose.yml (project root)
version: "3.8"

services:
  api:
    build:
      context: .
      dockerfile: api/Dockerfile
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://token:token_dev@db:5432/token_dev
      REDIS_URL: redis://redis:6379
      JWT_SECRET: dev-secret-do-not-use-in-production
      NODE_ENV: development
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_started
    volumes:
      # Mount source for hot-reload during development
      - ./api/src:/app/src
      - ./shared:/app/shared

  web:
    build:
      context: .
      dockerfile: web/Dockerfile
    ports:
      - "5173:80"
    depends_on:
      - api

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: token
      POSTGRES_PASSWORD: token_dev
      POSTGRES_DB: token_dev
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U token"]
      interval: 5s
      timeout: 3s
      retries: 5

  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"
    volumes:
      - redisdata:/data

volumes:
  pgdata:
  redisdata:

Key Compose Concepts

ConceptWhat it doesToken example
servicesEach service is a containerapi, web, db, redis
portsMaps host:container ports3000:3000 exposes the API
depends_onStart order + health gatesAPI waits for Postgres to be ready
volumesPersists data / mounts codepgdata survives restarts
environmentSets env vars inside containerDATABASE_URL, JWT_SECRET
healthcheckVerifies a service is readypg_isready before API starts

Essential Docker Commands

# Build and start everything
docker compose up --build

# Start in background (detached)
docker compose up -d

# See running containers
docker compose ps

# View logs (follow mode)
docker compose logs -f api

# Stop everything
docker compose down

# Stop and DELETE volumes (⚠️ destroys database data)
docker compose down -v

# Rebuild just one service
docker compose build api

# Run a one-off command inside a running container
docker compose exec db psql -U token token_dev

# Run migrations against the running database
docker compose exec api node dist/migrate.js

.dockerignore

Like .gitignore but for Docker. Prevents unnecessary files from being copied into the image (which would bloat it and break layer caching):

# .dockerignore
node_modules
dist
.git
.env
.env.*
*.md
.vscode
coverage
.DS_Store

Environment Variables — The Twelve-Factor Way

Never bake secrets into images. Pass them at runtime via environment variables:

# Development: use .env file (NOT committed to git)
# docker-compose.yml reads from environment: or env_file:

# Production: set via Coolify's UI (encrypted at rest)
# The container receives them as regular env vars

# Your code reads them the same way in both cases:
const dbUrl = process.env.DATABASE_URL;
const jwtSecret = process.env.JWT_SECRET;

Rule: if a value changes between environments (dev/staging/prod) or is secret, it goes in an environment variable. If it's the same everywhere, it goes in code.
