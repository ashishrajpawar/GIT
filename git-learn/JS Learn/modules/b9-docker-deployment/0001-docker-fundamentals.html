Docker Fundamentals

B9 — Lesson 1 of 3  |  ~50 min

Why this matters for Token: Your API works perfectly on your laptop. But the production server runs a different OS, different Node version, different file paths. Docker packages your app with its entire runtime — same binary everywhere. When you deploy Token to a VPS, you're not installing Node and running npm start — you're shipping a container image that works identically whether it runs on your laptop, a $5 VPS, or a $50,000 Kubernetes cluster. Portability means you're never locked in.

What Problem Does Docker Solve?

Without Docker, deploying a Node.js app means:

  1. SSH into the server
  2. Install the right Node version
  3. Clone the repo
  4. Run npm install (hope the native dependencies compile)
  5. Set up environment variables
  6. Configure a process manager (PM2, systemd)
  7. Pray that the server's OpenSSL version is compatible with yours

With Docker: push one image, pull it on the server, run it. Everything your app needs is inside the image. The server only needs Docker installed — nothing else.

Core Concepts

Image vs Container

An image is a read-only blueprint — like a class definition. A container is a running instance of that image — like an object instantiated from the class.

// Analogy in JavaScript terms
class TokenApi {          // ← image (the blueprint)
  constructor(env) { }
  listen(port) { }
}

const instance1 = new TokenApi(prodEnv);   // ← container 1
const instance2 = new TokenApi(stagingEnv); // ← container 2
// Same image, different config, running in parallel

Layers

A Docker image is built in layers. Each instruction in a Dockerfile creates one layer. Layers are cached — if nothing changed in an early layer, Docker reuses it instead of rebuilding. This makes subsequent builds fast.

# Each of these lines creates a layer:
FROM node:20-alpine       # Base layer: Alpine Linux + Node 20
WORKDIR /app              # Layer: creates /app directory
COPY package*.json ./     # Layer: copies package files
RUN npm ci                # Layer: installs dependencies (CACHED if package.json unchanged)
COPY . .                  # Layer: copies source code
RUN npm run build         # Layer: compiles TypeScript

Volumes

Containers are ephemeral — when you remove one, its data is gone. Volumes persist data outside the container lifecycle. Postgres uses a volume so your data survives container restarts.

Networks

Containers are isolated by default. A network connects containers to each other. Your API container needs to reach the Postgres container, but the outside world should only reach the API.

Writing a Dockerfile for Token's API

A Dockerfile is a recipe. Each instruction adds a layer to the image. Here's the production Dockerfile for api/:

# api/Dockerfile

# --- Stage 1: Build ---
FROM node:20-alpine AS builder

WORKDIR /app

# Copy package files first (layer caching: only re-install if deps change)
COPY package.json package-lock.json ./
COPY shared/package.json shared/

# Install ALL dependencies (including devDeps for TypeScript compilation)
RUN npm ci

# Copy source code
COPY tsconfig.json ./
COPY shared/ shared/
COPY src/ src/

# Compile TypeScript
RUN npm run build

# --- Stage 2: Production ---
FROM node:20-alpine AS production

WORKDIR /app

# Only install production dependencies
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

# Copy compiled output from builder stage
COPY --from=builder /app/dist ./dist

# Non-root user for security
RUN addgroup -S token && adduser -S token -G token
USER token

# Metadata
EXPOSE 3000
ENV NODE_ENV=production

# Start the server.
#
# NOTE THE PATH. x1/0003 sets "rootDir": ".." so that shared/ can be an
# input, and TypeScript mirrors the tree below rootDir into outDir. The
# build context here is api/ with shared/ copied in beside src/, so the
# compiled entry point is dist/api/src/server.js -- not dist/server.js.
CMD ["node", "dist/api/src/server.js"]
The entry path is decided by a tsconfig two folders away

dist/server.js is what everybody writes, and it is right only for a project whose sources all sit under one directory. Token shares shared/ as source, so rootDir has to sit above both folders and the output mirrors the tree beneath it. Change rootDir and this CMD breaks, with a container that builds cleanly and exits instantly on MODULE_NOT_FOUND.

This is the argument for rootDir being set explicitly rather than inferred, which x1/0003 makes at length: an inferred root is computed from whichever files are inputs, and it comes out differently inside this Dockerfile than it does on your laptop, because the layout being copied in is not the repo layout.

Why Multi-Stage?

The builder stage has TypeScript, devDependencies, and source files — all things you don't need in production. The production stage only has the compiled JS and production dependencies. Result: a much smaller image (often 3–5× smaller) with less attack surface.

# Comparison
# Single-stage: ~350MB (includes TypeScript, all devDeps, source)
# Multi-stage:  ~80MB  (only compiled JS + production deps)

Dockerfile for Token's Web Page

# web/Dockerfile

# --- Stage 1: Build ---
FROM node:20-alpine AS builder

WORKDIR /app

COPY package.json package-lock.json ./
COPY shared/package.json shared/

RUN npm ci

COPY tsconfig.json vite.config.ts ./
COPY shared/ shared/
COPY src/ src/
COPY index.html ./
COPY public/ public/

RUN npm run build

# --- Stage 2: Serve with nginx ---
FROM nginx:alpine AS production

# Copy built static files to nginx's serve directory
COPY --from=builder /app/dist /usr/share/nginx/html

# Custom nginx config for SPA routing
COPY nginx.conf /etc/nginx/conf.d/default.conf

EXPOSE 80

CMD ["nginx", "-g", "daemon off;"]

nginx config for single-page app routing

# web/nginx.conf
server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;

    # SPA fallback: any route that doesn't match a file → index.html
    location / {
        try_files $uri $uri/ /index.html;
    }

    # Cache static assets aggressively
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # Health check endpoint
    location /health {
        return 200 'ok';
        add_header Content-Type text/plain;
    }
}

Docker Compose for Local Development

You don't want to run docker build and docker run with 10 flags every time you start developing. Docker Compose defines your entire local stack in one file:

# docker-compose.yml (project root)
version: "3.8"

services:
  api:
    build:
      context: .
      dockerfile: api/Dockerfile
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://token:token_dev@db:5432/token_dev
      REDIS_URL: redis://redis:6379
      JWT_SECRET: dev-secret-do-not-use-in-production
      NODE_ENV: development
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_started
    volumes:
      # Mount source for hot-reload during development
      - ./api/src:/app/src
      - ./shared:/app/shared

  web:
    build:
      context: .
      dockerfile: web/Dockerfile
    ports:
      - "5173:80"
    depends_on:
      - api

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: token
      POSTGRES_PASSWORD: token_dev
      POSTGRES_DB: token_dev
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U token"]
      interval: 5s
      timeout: 3s
      retries: 5

  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"
    volumes:
      - redisdata:/data

volumes:
  pgdata:
  redisdata:

Essential Docker Commands

# Build and start everything
docker compose up --build

# Start in background (detached)
docker compose up -d

# See running containers
docker compose ps

# View logs (follow mode)
docker compose logs -f api

# Stop everything
docker compose down

# Stop and DELETE volumes (⚠️ destroys database data)
docker compose down -v

# Rebuild just one service
docker compose build api

# Run a one-off command inside a running container
docker compose exec db psql -U token token_dev

# Run migrations against the running database
docker compose exec api node dist/migrate.js

Environment Variables — The Twelve-Factor Way

Never bake secrets into images. Pass them at runtime via environment variables:

# Development: use .env file (NOT committed to git)
# docker-compose.yml reads from environment: or env_file:

# Production: set via Coolify's UI (encrypted at rest)
# The container receives them as regular env vars

# Your code reads them the same way in both cases:
const dbUrl = process.env.DATABASE_URL;
const jwtSecret = process.env.JWT_SECRET;

Rule: if a value changes between environments (dev/staging/prod) or is secret, it goes in an environment variable. If it's the same everywhere, it goes in code.

Shutting down without dropping every conversation

This is the part a Dockerfile makes possible and does not do for you. Every deploy stops the running container, and Token's containers are holding live WebSocket connections — people mid-conversation, calls in progress. What happens to them is decided by twenty lines of your code.

The sequence Docker uses is fixed: SIGTERM, wait, then SIGKILL. The wait defaults to 10 seconds. 

// api/src/server.ts
const server = app.listen(PORT);

let shuttingDown = false;

async function shutdown(signal: string) {
  if (shuttingDown) return;         // a second SIGTERM must not restart this
  shuttingDown = true;
  logger.info({ signal }, 'shutting down');

  // Everything below has to finish inside Docker's grace period. planShutdown
  // divides it up and, crucially, hands the leftover to the drain.
  const plan = planShutdown(Number(process.env.STOP_GRACE_MS) || 10000);

  // 1. Fail readiness first, so the proxy stops sending new requests
  //    BEFORE we start refusing them. Out of rotation, then closing.
  setNotReady();
  await sleep(plan.readinessMs);

  // 2. Tell WebSocket clients to reconnect. They will land on another
  //    replica - or on the new container a moment later.
  for (const ws of allSockets()) {
    ws.send(JSON.stringify({ type: 'server_shutdown', reconnect: true }));
    ws.close(1012, 'server restarting');    // 1012 = Service Restart
  }

  // 3. Stop accepting connections and let in-flight requests finish.
  //
  //    server.close() waits for every open connection, and a keep-alive
  //    socket sitting idle counts as open - so on its own this can wait
  //    for ever. Both halves are needed: hurry the idle ones along, and
  //    put a hard ceiling on the rest.
  server.closeIdleConnections();
  await Promise.race([
    new Promise<void>((resolve) => server.close(() => resolve())),
    sleep(plan.drainMs),
  ]);

  // 4. Now the dependencies, in the order that cannot strand work.
  //    This runs whether or not the drain finished, because a pool closed
  //    late is better than a pool not closed at all.
  await pool.end();
  await redis.quit();

  process.exit(0);
}

process.on('SIGTERM', () => shutdown('SIGTERM'));   // Docker / Coolify
process.on('SIGINT', () => shutdown('SIGINT'));     // Ctrl-C locally
Without that handler, SIGTERM does nothing at all

Not "nothing much" — nothing. The kernel treats PID 1 specially: signals with no registered handler are discarded rather than applying their default action. CMD ["node", "dist/server.js"] makes Node PID 1, so a container with no SIGTERM listener ignores the polite request entirely.

Docker then waits its ten seconds and sends SIGKILL, which cannot be caught. Every deploy takes ten seconds longer than it should and ends by shooting the process — sockets severed with no close frame, in-flight requests abandoned, database connections dropped rather than returned. It looks like it works, because the new container comes up.

A shutdown sequence without a total is not a plan

Read those four steps again as a stopwatch rather than a list. Docker sends SIGKILL ten seconds after SIGTERM, and SIGKILL cannot be caught. So the sequence has a budget, and the first version of it above quietly exceeded the budget in two different ways.

await sleep(2000) is fine on its own. Then server.close() waits for every open connection to finish — and an idle keep-alive socket counts as open. A browser that made one request and is holding the connection for the next keeps the server "busy" indefinitely, so on its own this step can wait for ever. That is why the corrected version does two things: hurry the idle connections along with closeIdleConnections(), and race the whole drain against a hard ceiling.

The handler exits the way it exists to prevent

With no ceiling, one slow request or one idle keep-alive socket means server.close() has not resolved at the ten-second mark. pool.end() and redis.quit() are still queued behind it. SIGKILL arrives, and you get exactly the ungraceful exit the handler was written to avoid — sockets severed with no close frame, database connections dropped rather than returned — with the added insult that it took the full ten seconds first.

And it looks like it works, because the new container comes up. Deploys that consistently take a fraction over ten seconds are the symptom, and nobody reads a deploy timing as a bug report.

Which phases may be shortened is a real design question, and the answer is not "shorten them equally":

  • The readiness wait is an optimisation and fully compressible. It exists so the proxy takes us out of rotation before we start refusing anything. Cut it to nothing and some in-flight requests fail — bad, not corrupting.
  • Closing the pool and Redis is not compressible. That is the step that stops work being stranded, and it is the whole reason for a graceful shutdown in the first place. It gets its budget first.
  • Leftover time belongs to the drain, not to a longer wait. Extra seconds spent finishing real requests are worth more than extra seconds spent standing still.

Why this way (and what was rejected)

Multi-stage, so the toolchain never ships

The builder needs TypeScript, the source, and every devDependency. None of it is needed to run node dist/server.js, and all of it is attack surface sitting in production: a compiler, a package manager with a network, and your source code. Copying just dist/ forward is a smaller image and, more usefully, a container with almost nothing in it to use.

A non-root user, even inside a container

"It is isolated anyway" is the argument for skipping USER token, and it holds right up until it does not. Container escapes exist, volume mounts cross the boundary by design, and root in the container is root on the host for anything shared. Two lines to make an escape land as an unprivileged user is a good trade at any odds.

Alpine, with a caveat worth testing rather than trusting

Alpine is small because it uses musl instead of glibc, and that is exactly where it bites. Native modules — argon2 is the one this project depends on — publish prebuilt binaries compiled against glibc. On Alpine they are rejected and npm falls back to compiling from source, which needs a toolchain the image does not have. The failure appears during docker build, which is the good outcome; the bad one is a build that quietly succeeds against a different fallback and behaves oddly at runtime. 

# If argon2 or any native dep fails to install on Alpine
RUN apk add --no-cache --virtual .build python3 make g++ \
 && npm ci \
 && apk del .build            # remove the toolchain from the layer

# Or use the Debian-slim image and accept ~40MB more for a quieter life:
# FROM node:20-slim

When this breaks

The timezone the rules engine depends on

B7.2 evaluates time-window rules with Intl.DateTimeFormat(..., { timeZone: 'Asia/Kolkata' }). That needs timezone data inside the container, and slim base images have historically shipped without the full set — with a failure mode of falling back to UTC rather than throwing.

Which would mean a rule reading "contactable 09:00–18:00" silently enforcing 09:00–18:00 UTC: five and a half hours out, every day, for every user. The token works at the wrong times and nothing anywhere reports an error.

Do not take anyone's word for which images are affected — check the image you are actually shipping: 

docker run --rm node:20-alpine node -e \
  "console.log(new Intl.DateTimeFormat('en-GB',{timeZone:'Asia/Kolkata',hour:'2-digit',minute:'2-digit'}).format(new Date()))"

# Correct: the current time in India (UTC+5:30)
# Wrong:   UTC, or a RangeError about an invalid time zone
# If wrong:  RUN apk add --no-cache tzdata   (and re-run the check)

Worth making a habit of: any behaviour your app depends on that comes from the operating system rather than your code — timezones, locales, certificates, fonts — is a thing to verify in the image, not to assume from the base tag.

.dockerignore is not optional, and its absence is silent

Without it, COPY . . takes the local node_modules — built for your laptop's OS, overwriting the ones installed for Alpine — along with .git and any .env sitting in the directory. The .env is the one that matters: it is now a layer in an image, and anyone who can pull that image can read every secret in it, including from a registry, months later. Deleting the file in a later layer does not remove it; layers are additive.

Layer caching that never hits

COPY package*.json ./ before RUN npm ci exists so that editing a source file does not reinstall every dependency. Put COPY . . first and every build downloads the internet again — two minutes instead of five seconds, on every push, forever. It is the single highest-leverage line ordering in the file.

What this costs you

DecisionWhat you pay
Multi-stage builds A longer, less obvious Dockerfile, and npm ci --omit=dev runs a second time in the production stage rather than copying node_modules forward — slower builds, in exchange for a production image that provably contains no devDependency.
Alpine musl. Native modules need a toolchain or a different base, and a class of bug exists that only appears on Alpine. The ~40MB saved over node:20-slim is rarely worth an afternoon.
Graceful shutdown Deploys take longer by design — you are waiting for connections to drain rather than cutting them. That is the trade, and it is why the readiness flag flips first: the wait should be spent draining, not receiving new work.
Running as a non-root user The container cannot bind ports below 1024, cannot write outside the paths you granted, and file permissions become something you think about. All correct, all occasionally irritating.
Config through environment variables Nothing is validated by the platform. A typo in a variable name is a value of undefined at runtime — which is why B9.2 validates the whole set at startup and exits rather than discovering it on the first request that needs one.
