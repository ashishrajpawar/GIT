Store Submission

A11 — Lesson 5 of 5  |  ~45 min

Why this matters for Token: This is the finish line. Token is built, tested, deployed. But users can't install it until it's on the Play Store and App Store. The submission process has specific requirements — screenshots, privacy policy, content rating, age declaration — and any mistake means a rejection that costs days. EAS Submit automates the binary upload, but the metadata, compliance, and policy work is on you.

Building for Production with EAS

# Build both platforms
eas build --profile production --platform all

# Or build separately
eas build --profile production --platform ios
eas build --profile production --platform android

EAS Build:

  • Resolves APP_ENV=production from eas.json
  • Injects EAS Secrets as env vars
  • Compiles native code (WebRTC, secure-store, etc.)
  • Signs the binary (iOS: provisioning profile + certificate; Android: upload key)
  • Returns a download URL for the .ipa / .aab

For iOS, EAS manages certificates and provisioning profiles automatically. On first build, it will prompt you to log in with your Apple Developer credentials.

Submitting with EAS Submit

# Submit the latest production build to both stores
eas submit --platform all --latest

# Or submit a specific build

The fourth bullet used to read "No phone number shared, ever", and the description had no closing paragraph. Both are the collapsed claim from the callout above. Read literally by a reviewer holding your App Privacy form — which says you collect a phone number — "no phone number shared, ever" looks like a contradiction, and a listing that contradicts its own privacy declaration is a rejection with no obvious fix.

The replacement is stronger, not weaker. "Nobody you give a token to ever sees your number" is a precise, checkable promise about the thing the user is worried about, and it survives contact with the form. Vague claims are not safer than specific ones — they are just harder to defend.

Privacy Policy

Both stores require a privacy policy URL. For Token, it must cover:

  • What data is collected (a hash of the phone number, display name, token metadata, message ciphertext)
  • What is NOT collected (contacts, location, browsing history, email)
  • How messages are stored (end-to-end encrypted — the server holds no key)
  • Third-party services (FCM for push notifications — disclose this)
  • Data retention, including the backup tail — see b10/0002
  • User rights (delete account, export data)
  • DPDP Act 2023 compliance (India's data protection law)

Host at https://tokn.app/privacy — the redemption web app already runs on this domain, so add a /privacy route.

This lesson used to declare email, and Token has never had one

Every list below said email address. Look at what the database actually holds (b2/0001):

CREATE TABLE users (
  id            SERIAL PRIMARY KEY,
  phone_hash    TEXT NOT NULL UNIQUE,
  display_name  TEXT NOT NULL,
  avatar_url    TEXT,
  ...
);

No email column, and email is on this course's out-of-scope list — no relay, no bridge, no transactional email. So the declaration named a field that does not exist and left out the one that does.

Both halves of that are a problem, and the second is the serious one. Declaring data you do not collect is merely embarrassing. Failing to declare data you do collect is what gets an app removed — Data Safety and App Privacy are binding statements, not marketing, and both stores re-check them against what the binary actually does.

Hashing it does not take it off the form

The tempting argument: we only store phone_hash, not the number, so there is nothing to declare. It does not hold, for the reason b3/0001 already gives about a different column. An Indian mobile is ten digits with a known prefix — a space small enough to enumerate completely. A hash of a value you can enumerate is a lookup key, not an anonymisation.

Google's own guidance agrees: collection is about what leaves the device, and the number leaves the device to be hashed on the way in. Both stores treat "we transform it after receiving it" as collection.

So the accurate sentence — the one that goes in the policy, the listing and the onboarding, settled on 2026-08-22 — is "we store a scrambled version of your phone number, used only to sign you in."

Two claims keep getting collapsed into one, and only one of them was ever in doubt:

ClaimTrue?Where it belongs
What a token holder learns about you: nothing — not the number, not the identity Yes. This is the product The listing, the description, onboarding
What the company collects: a hashed number and a display name No, if you say "nothing" Data Safety, App Privacy, the privacy policy

When you meet the phrase "no phone number" anywhere in this course, check which of the two it means before either trusting it or rewriting it. Most instances are the first and are correct.

Content Rating & Declarations

Google Play — Content Rating Questionnaire

Answer honestly. For Token:

  • Violence: No
  • Sexual content: No
  • Language: Users can type anything → "Users can exchange unfiltered content"
  • Controlled substances: No
  • Interactive elements: "Users interact" + "Shares location: No" + "Digital purchases: No"

Result: likely PEGI 12 or equivalent (due to unfiltered user communication).

Apple — Age Rating

Similar questionnaire in App Store Connect. Token will likely get 12+ for "Infrequent/Mild Mature/Suggestive Themes" (because users can message freely).

Data Safety (Google Play)

Declare what Token collects. Read this off the schema, never off memory — the same rule b10/0002 applies to the erasure order:

  • Phone number → Account management → Required → collected, not shared (hashed on receipt; still collection)
  • Name (display_name) → Account management → Required
  • Photos (avatar_url, if the user sets one) → Account management → Optional
  • Messages → App functionality → Required → end-to-end encrypted
  • Crash logs → Analytics → Optional
  • Device identifiers (FCM token) → Push notifications → Required

Tick the end-to-end encryption box, and tick it honestly. Google distinguishes "encrypted in transit" from end-to-end, and they are very different claims: the first means TLS to a server that can read your message, the second means the server cannot. ADR-0002 gives Token the second. Claiming it while holding a key is the kind of misdeclaration that ends an app; claiming only the first, when you have earned the second, throws away the one thing that distinguishes the product.

App Privacy (iOS)

Similar to Google's Data Safety. Declare:

  • Contact Info (phone number) → linked to identity
  • User Content (messages) → linked to identity
  • Identifiers (FCM token) → not linked to identity
  • Usage Data (crash logs) → not linked to identity

Note linked to identity for the phone number: it is the account key, so by definition it is linked. There is no reading of the form on which a unique login identifier is unlinked.

Post-submission: Updates with EAS Update

Once the app is live, bug fixes don't always need a full store review. EAS Update sends JavaScript-only changes over-the-air (OTA):

# Push a JS-only fix to production users
eas update --branch production --message "Fix token list refresh bug"

What OTA can update: JS code, images, JSON — anything in the JS bundle.

What requires a new build: Native code changes (new native modules, updated native dependencies, changes to app.config.js that affect the binary).

For Token, adding a new chat feature (JS only) → OTA update. Adding a new native payment module → new build + store submission.

runtimeVersion — the gate that decides who receives an update

The exercise config below sets this, and it is the single most consequential line in the file:

runtimeVersion: { policy: 'appVersion' },

runtimeVersion names the native contract a JS bundle expects. An update is delivered only to installed binaries whose runtimeVersion matches it exactly. There is no negotiation and no fallback — a mismatch means the device simply never sees the update.

The appVersion policy makes runtimeVersion equal to version. That one equality produces two rules that point in opposite directions, which is why people get it wrong:

You are shippingversionBecause
A native change (new module, native dep bump) Must change Otherwise the new binary shares a runtimeVersion with every old one, and a later OTA aimed at the new native code lands on binaries that do not have it
A JS-only fix, over the air Must not change Bumping it changes runtimeVersion, so the update targets a binary nobody has installed yet. The publish succeeds, the dashboard is green, and zero users receive it
"Let's call it 1.1.0" is a decision about who gets the fix

This is where it bites in practice. A JS-only feature lands, it feels like a minor release, someone bumps version to 1.1.0 and runs eas update. Under the appVersion policy that update has runtimeVersion: '1.1.0' and every installed copy is running 1.0.0. It reaches nobody, and nothing reports an error — the update exists, it is just addressed to a binary that has never been built.

So: asking for a new version number is asking for a new build. Those are the same request, and the version field is the place the two get confused. If the marketing number must change, the release goes through the store; if the fix must reach today's users today, the number stays.

The two counters, and only one of them ever resets

FieldPlatformRule
android.versionCode Android An integer that must be strictly greater than every value ever uploaded, for the lifetime of the app. It never resets and a value is never reusable — not even one from a release you deleted or rolled back
ios.buildNumber iOS Must increase within a given version, and resets to 1 when version changes

The mistake is applying the iOS rule to Android. Reset versionCode alongside buildNumber on a version bump and Play rejects the upload — and the only way out is to burn numbers upward past the highest you ever used. You cannot reclaim the range, apologise for it, or ask support to clear it. It is the one number in this lesson with no undo, which puts it in the same family as revoked_at in 0001.

An OTA channel can silently replace the encryption code

ADR-0002 says the server stores ciphertext and holds no key. That guarantee lives in JavaScript on the client — and eas update replaces client JavaScript, on demand, with no review, no store record, and no user prompt.

This is not a reason to avoid OTA; it is a reason to be honest about what it is. The threat model of an end-to-end encrypted app has to include whoever can push code to it, and for Token that set now includes anyone holding the Expo account credentials. Two consequences worth adopting before the first release rather than after an incident:

  • Changes to key handling, storage or the crypto envelope ship as a store build, never as an OTA. A reviewed, signed, versioned artefact exists afterwards, and that is the whole point.
  • The Expo account is a production credential. It belongs in the same tier as TOKEN_CODE_PEPPER, with 2FA — not in the tier a sourcemap upload token lives in. This is 0004's rule, who needs it and when, applied to a service rather than a secret.

Try it yourself — this one is broken on purpose

The release rule as most teams first write it, run against six real releases. Two of the six are rejected by Play forever, and one reaches nobody.

The Full Release Flow

1. Code complete → merge to main
2. eas build --profile production --platform all
3. Test the production build on real devices
4. eas submit --platform all --latest
5. Fill metadata in App Store Connect / Play Console
6. Submit for review
7. Wait (Apple: 24–48h, Google: a few hours to 7 days)
8. Approved → goes live
9. Subsequent JS fixes → eas update --branch production
