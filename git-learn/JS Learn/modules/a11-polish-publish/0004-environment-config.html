Environment Config

A11 — Lesson 4 of 5  |  ~35 min

Why this matters for Token: During development, your app hits http://localhost:3000. In staging, it hits https://staging-api.tokn.app. In production, https://api.tokn.app. If you hardcode the URL, you have to manually change it before every build — and one forgotten change means the Play Store version talks to your dev server. Environment config lets EAS Build inject the right values at build time without touching code.

The Three Environments

EnvironmentAPI URLWhen
developmenthttp://localhost:3000Running on your machine via Expo Go or dev build
staginghttps://staging-api.tokn.appTesting on real devices before release
productionhttps://api.tokn.appUsers download from the store

Beyond the API URL, environments differ in:

  • TURN server address
  • Push notification credentials (FCM sender ID)
  • Feature flags (e.g. voice/video disabled in staging)
  • Log level (verbose in dev, errors-only in production)

app.config.js (Dynamic Config)

Expo supports a dynamic config file that can read environment variables at build time:

// app/app.config.js
export default ({ config }) => {
  const ENV = process.env.APP_ENV || 'development';

  const envConfig = {
    development: {
      apiUrl: 'http://localhost:3000',
      turnServer: 'turn:localhost:3478',
      logLevel: 'debug',
    },
    staging: {
      apiUrl: 'https://staging-api.tokn.app',
      turnServer: 'turn:staging-turn.tokn.app:3478',
      logLevel: 'warn',
    },
    production: {
      apiUrl: 'https://api.tokn.app',
      turnServer: 'turn:turn.tokn.app:3478',
      logLevel: 'error',
    },
  };

  return {
    ...config,
    name: ENV === 'production' ? 'Token' : \`Token (\${ENV})\`,
    slug: 'token',
    version: '1.0.0',
    extra: {
      ...envConfig[ENV],
      appEnv: ENV,
      eas: {
        projectId: process.env.EAS_PROJECT_ID,
      },
    },
    ios: {
      ...config.ios,
      bundleIdentifier: ENV === 'production'
        ? 'app.tokn.token'
        : \`app.tokn.token.\${ENV}\`,
    },
    android: {
      ...config.android,
      package: ENV === 'production'
        ? 'app.tokn.token'
        : \`app.tokn.token.\${ENV}\`,
    },
  };
};

Key points:

  • Different bundle IDs per environment — you can have dev, staging, and prod installed simultaneously on the same device
  • The app name shows the environment in non-production builds (helps testers know which version they're running)
  • extra is where custom config lives — accessible at runtime via expo-constants

Reading Config at Runtime

# Already installed with Expo
npx expo install expo-constants
// app/src/config/env.ts
import Constants from 'expo-constants';

interface AppConfig {
  apiUrl: string;
  turnServer: string;
  logLevel: 'debug' | 'warn' | 'error';
  appEnv: 'development' | 'staging' | 'production';
}

const extra = Constants.expoConfig?.extra as AppConfig;

export const config: AppConfig = {
  apiUrl: extra?.apiUrl || 'http://localhost:3000',
  turnServer: extra?.turnServer || 'turn:localhost:3478',
  logLevel: extra?.logLevel || 'debug',
  appEnv: extra?.appEnv || 'development',
};

export const isDev = config.appEnv === 'development';
export const isProd = config.appEnv === 'production';

Now every file in the app imports from one place:

import { config, isDev } from '../config/env';

const response = await fetch(\`\${config.apiUrl}/tokens\`);

if (isDev) {
  console.log('Response:', response.status);
}

EAS Build Profiles

EAS Build uses profiles in eas.json to set environment variables for each build type:

// app/eas.json
{
  "cli": {
    "version": ">=5.0.0"
  },
  "build": {
    "development": {
      "developmentClient": true,
      "distribution": "internal",
      "env": {
        "APP_ENV": "development"
      }
    },
    "staging": {
      "distribution": "internal",
      "env": {
        "APP_ENV": "staging"
      },
      "channel": "staging"
    },
    "production": {
      "env": {
        "APP_ENV": "production"
      },
      "channel": "production",
      "autoIncrement": true
    }
  },
  "submit": {
    "production": {
      "ios": {
        "ascAppId": "YOUR_APP_STORE_CONNECT_APP_ID"
      }
    }
  }
}

Build commands:

# Development build (installs on your device via QR)
eas build --profile development --platform ios

# Staging build (internal testers)
eas build --profile staging --platform all

# Production build (for store submission)
eas build --profile production --platform all

EAS Secrets: Protecting Sensitive Values

Some values should never be in code or git:

  • FCM server key
  • TURN server credentials
  • Sentry DSN
  • Any API keys for third-party services

EAS Secrets stores these encrypted on Expo's servers and injects them as environment variables during builds:

# Set a secret (stored encrypted, never in git).
# NOTE the example: a SOURCEMAP UPLOAD TOKEN, used by the build itself and
# never written into the app. Read the callout below before you put
# anything here that the running app needs.
eas secret:create --name SENTRY_AUTH_TOKEN --value "sntrys_..." --scope project

# List secrets
eas secret:list

# Use in app.config.js
// NOT turnPassword. The app asks the API for a short-lived one when it
// starts a call -- see the callout above.
turnCredentialUrl: process.env.TURN_CREDENTIAL_URL,
There are no secrets in a client app. EAS Secrets does not change that.

The rule this section used to end with was: if it's a credential, it goes in EAS Secrets. That is wrong in a way that is easy to miss, because EAS Secrets really does protect the value — it is encrypted at rest on Expo's servers and never enters git.

What it protects is the pipeline, not the artefact. The value is injected as an environment variable during the build, and anything the app reads at runtime was baked into the bundle to get there. That bundle is an .apk or an .ipa sitting on a stranger's phone. Unzipping it and grepping the JavaScript is a two-minute job, and no obfuscation changes the arithmetic: if the running app can read it, so can whoever holds the app.

So the real question is not "is this sensitive" but who needs it, and when:

  • The build needs it, the app does not — a sourcemap upload token, a signing credential. EAS Secrets is exactly right. The value does its job and never reaches the artefact.
  • The app needs it at runtime — then it cannot be a secret, and the design has to change rather than the storage. The app authenticates, and asks your API for a short-lived credential when it needs one.

The example that was here is the one that matters

This section used to create TURN_PASSWORD as an EAS secret. TURN is the relay every Token call goes through — under ADR-0008, every call, with no direct path — so that password is the key to your relay bandwidth. Shipped in the bundle, it is extractable by anyone who installs the app, and relay bandwidth is metered and billed to you. There is no revocation story either: rotating it means shipping a new build and waiting for people to update.

a7/0001 already says what to do instead, and this lesson contradicted it: short-lived TURN credentials from the API. The coturn REST convention is that a credential is HMAC-SHA1(shared_secret, "expiry:username"), so your server mints one valid for a few hours from a secret that never leaves it, and the app asks for a fresh one when it starts a call. An extracted credential is then worth hours rather than for ever, and revoking it is a server-side change.

The corrected rule: structural config (bundle ID, version) goes in app.config.js; URLs and feature flags go in eas.json env; build-time-only credentials go in EAS Secrets; and anything the running app needs and must not reveal does not go in the app at all — it is fetched, briefly, from something that can say no.

Local Development: .env Files

When running locally with npx expo start, EAS isn't involved. Use a .env file for local overrides:

# app/.env (git-ignored)
APP_ENV=development
TURN_CREDENTIAL_URL=http://localhost:3000/api/turn-credential

Expo reads .env automatically in SDK 49+. Earlier versions need dotenv:

// top of app.config.js (only needed for SDK < 49)
require('dotenv').config();

Add to .gitignore:

# app/.gitignore
.env
.env.local
.env.*.local

Feature Flags by Environment

// app/src/config/features.ts
import { config } from './env';

export const features = {
  voiceVideo: config.appEnv !== 'staging', // disabled while TURN staging is flaky
  pushNotifications: config.appEnv !== 'development', // no FCM in simulator
  analytics: config.appEnv === 'production',
  devTools: config.appEnv === 'development',
} as const;
// Usage in a component
import { features } from '../config/features';

{features.voiceVideo && (
  <Tab.Screen name="Calls" component={CallsScreen} />
)}

Validating Config at Startup

Catch misconfigurations early — fail loudly at app launch, not 5 screens in:

// app/src/config/env.ts (add to the bottom)
import { z } from 'zod';

const configSchema = z.object({
  apiUrl: z.string().url(),
  turnServer: z.string().min(1),
  logLevel: z.enum(['debug', 'warn', 'error']),
  appEnv: z.enum(['development', 'staging', 'production']),
});

// Validates on import — crashes immediately if config is wrong
configSchema.parse(config);

Now build it yourself

Write placeConfig(entry) — decide where a single configuration value belongs. It is the rule from the callout above, written down, and it is the one decision in this lesson that cannot be undone by shipping a fix: a credential that has been in a released bundle is disclosed, whatever you do next.
