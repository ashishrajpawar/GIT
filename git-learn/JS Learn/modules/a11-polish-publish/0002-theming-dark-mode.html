Theming & Dark Mode

A11 — Lesson 2 of 5  |  ~40 min

Why this matters for Token: A privacy app signals trust through clean, consistent design. Users in India often use OLED phones where dark mode saves significant battery. Supporting system theme preference (and a manual override) isn't a luxury — it's expected. A scattered colour palette with hardcoded hex values makes this impossible to maintain. A theme system gives you one source of truth for every colour in the app.

The Problem with Hardcoded Colours

// Scattered across 30 files:
<View style={{ backgroundColor: '#fff' }}>
<Text style={{ color: '#333' }}>
<View style={{ borderColor: '#e0e0e0' }}>

To add dark mode, you'd have to find and conditionally replace every single one. Instead, define colours once and reference them everywhere through a context.

export type ThemeColors = typeof colors.light;

Both palettes have identical keys. Any component that uses theme.colors.text works in both modes without conditional logic.

Every number above is measured, and the light palette was the broken one

Until 2026-08-22 this palette was chosen by eye. Running the contrast formula over it — which is what the exercise at the end of this lesson builds — gives a result worth sitting with:

Colour on #FFFFFFWasNeedsVerdict
warning2.194.5fail
textMuted2.074.5fail
success2.874.5fail
accent3.154.5fail
danger3.824.5fail

The dark palette passed almost everything. That is the reverse of the usual worry, and there is a reason for it: dark palettes are built by picking colours that stand out against near-black, so you are choosing for contrast whether you mean to or not. Light palettes get picked for how they look next to white, which is a question about taste, not legibility. The mode nobody tests is the one people use in daylight.

Where this lands for Token specifically. a5/0003 derives five states — revoked, expired, exhausted, paused, active — and the badge renders them with success, warning and danger. Those were the three worst colours in the palette. "Is this token still live?" is the single most important question this app answers, and in daylight it was being answered at 2.19:1.

Three things fell out of measuring rather than eyeballing:

  • A colour is not accessible; a pair is. The old textSecondary was 4.69 on background and 4.45 on surface — the same colour, passing and failing, depending on which card it landed in. Audit every background a colour actually appears on.
  • Amber cannot carry white text. No usable shade of warning reaches 4.5 against white; darkening it far enough stops it being amber. The fix is not a darker fill, it is dark text on it — hence onWarning, and hence the on* keys generally. When one colour cannot be fixed, fix the pair.
  • textMuted could not be saved. Any grey light enough to read as "muted" on white is below 4.5, and the first one that passes is already textSecondary. So it is now documented as disabled-and-decorative only — WCAG exempts disabled controls — and the rule is that no information may live in it. A palette that cannot express a distinction is better than one that expresses it illegibly.

What is still not compliant, stated rather than hidden: border is 1.19 in light and 1.55 in dark. That is fine for a divider, which WCAG treats as decorative, and not fine for anything whose boundary tells you where a control is — so inputBorder exists separately at 3.19 and 4.12. If you find yourself outlining a pressable with border, that is the bug this split is here to make visible.

Building the Theme Context

// app/src/theme/ThemeContext.tsx
import { createContext, useContext, useState, useEffect, ReactNode } from 'react';
import { useColorScheme } from 'react-native';
import AsyncStorage from '@react-native-async-storage/async-storage';
import { colors, ThemeColors } from './colors';
import { spacing } from './spacing';
import { typography } from './typography';

type ThemeMode = 'light' | 'dark' | 'system';

interface ThemeContextValue {
  mode: ThemeMode;
  isDark: boolean;
  colors: ThemeColors;
  spacing: typeof spacing;
  typography: typeof typography;
  setMode: (mode: ThemeMode) => void;
}

const ThemeContext = createContext<ThemeContextValue | null>(null);

const STORAGE_KEY = 'token_theme_mode';

export function ThemeProvider({ children }: { children: ReactNode }) {
  const systemScheme = useColorScheme();
  const [mode, setModeState] = useState<ThemeMode>('system');

  useEffect(() => {
    AsyncStorage.getItem(STORAGE_KEY).then((stored) => {
      if (stored === 'light' || stored === 'dark' || stored === 'system') {
        setModeState(stored);
      }
    });
  }, []);

  const setMode = (newMode: ThemeMode) => {
    setModeState(newMode);
    AsyncStorage.setItem(STORAGE_KEY, newMode);
  };

  const isDark = mode === 'system'
    ? systemScheme === 'dark'
    : mode === 'dark';

  const value: ThemeContextValue = {
    mode,
    isDark,
    colors: isDark ? colors.dark : colors.light,
    spacing,
    typography,
    setMode,
  };

  return (
    <ThemeContext.Provider value={value}>
      {children}
    </ThemeContext.Provider>
  );
}

export function useTheme(): ThemeContextValue {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error('useTheme must be used within ThemeProvider');
  return ctx;
}

Wiring It Into the App

// app/App.tsx
import { GestureHandlerRootView } from 'react-native-gesture-handler';
import { ThemeProvider } from './src/theme/ThemeContext';
import { StatusBar } from 'expo-status-bar';
import { useTheme } from './src/theme/ThemeContext';
import { Navigation } from './src/navigation';

function ThemedApp() {
  const { isDark } = useTheme();
  return (
    <>
      <StatusBar style={isDark ? 'light' : 'dark'} />
      <Navigation />
    </>
  );
}

export default function App() {
  return (
    <GestureHandlerRootView style={{ flex: 1 }}>
      <ThemeProvider>
        <ThemedApp />
      </ThemeProvider>
    </GestureHandlerRootView>
  );
}

No StyleSheet.create for themed styles — you build them inline from context values. This avoids stale cached styles when the theme changes.

The Theme Picker Component

// app/src/components/ThemePicker.tsx
import { View, Text, Pressable, StyleSheet } from 'react-native';
import { useTheme } from '../theme/ThemeContext';

const OPTIONS: Array<{ label: string; value: 'light' | 'dark' | 'system' }> = [
  { label: '☀️ Light', value: 'light' },
  { label: '🌙 Dark', value: 'dark' },
  { label: '📱 System', value: 'system' },
];

export function ThemePicker() {
  const { mode, setMode, colors, spacing } = useTheme();

  return (
    <View style={{ flexDirection: 'row', gap: spacing.sm }}>
      {OPTIONS.map((option) => {
        const isActive = mode === option.value;
        return (
          <Pressable
            key={option.value}
            onPress={() => setMode(option.value)}
            style={[
              styles.chip,
              {
                backgroundColor: isActive ? colors.primary : colors.surface,
                borderColor: isActive ? colors.primary : colors.border,
              },
            ]}
          >
            <Text style={{
              color: isActive ? '#fff' : colors.text,
              fontSize: 14,
              fontWeight: isActive ? '600' : '400',
            }}>
              {option.label}
            </Text>
          </Pressable>
        );
      })}
    </View>
  );
}

const styles = StyleSheet.create({
  chip: {
    paddingVertical: 8,
    paddingHorizontal: 16,
    borderRadius: 20,
    borderWidth: 1,
  },
});

Animating Theme Transitions

An abrupt colour change feels jarring. Use Reanimated to smoothly transition background colours:

import Animated, {
  useAnimatedStyle,
  withTiming,
  useSharedValue,
  useDerivedValue,
} from 'react-native-reanimated';
import { useTheme } from '../theme/ThemeContext';

export function AnimatedBackground({ children }) {
  const { colors } = useTheme();

  const bgColor = useDerivedValue(() =>
    withTiming(colors.background, { duration: 300 })
  );

  const animatedStyle = useAnimatedStyle(() => ({
    backgroundColor: bgColor.value,
    flex: 1,
  }));

  return (
    <Animated.View style={animatedStyle}>
      {children}
    </Animated.View>
  );
}

Note: Reanimated can animate colour strings directly (it interpolates the RGB components). This works for backgroundColor, borderColor, and color.

Navigation Theming

React Navigation has its own theme system. Sync it with yours:

import { NavigationContainer, DefaultTheme, DarkTheme } from '@react-navigation/native';
import { useTheme } from '../theme/ThemeContext';

export function Navigation() {
  const { isDark, colors } = useTheme();

  const navTheme = {
    ...(isDark ? DarkTheme : DefaultTheme),
    colors: {
      ...(isDark ? DarkTheme.colors : DefaultTheme.colors),
      primary: colors.primary,
      background: colors.background,
      card: colors.surface,
      text: colors.text,
      border: colors.border,
    },
  };

  return (
    <NavigationContainer theme={navTheme}>
      {/* stacks and tabs */}
    </NavigationContainer>
  );
}

Common Mistakes

  • Hardcoding #fff / #000 alongside theme colours — everything visual must come from the theme. The one exception: shadows (which are always dark regardless of mode).
  • Using StyleSheet.create for themed styles — the styles are cached at create time and won't update when the theme changes. Use inline styles from useTheme(), or re-create the stylesheet inside a useMemo keyed on isDark.
  • Forgetting the StatusBar — dark text on a dark background makes the clock/battery invisible.
  • Not persisting the choice — if the user picks "Dark", it should survive an app restart. That's why we use AsyncStorage for the mode.
  • Choosing colours by eye — the only objective thing about a colour pair is its contrast ratio, and it takes twenty lines to compute. Everything above this line was wrong in light mode until someone measured it.
  • Using colour as the only carrier of a state — see below. This one survives every theme review, because the reviewer can see the colours.
A green badge and a red badge are the same badge to 1 in 12 men

Red-green colour blindness affects roughly 8% of men and 0.5% of women. Token's status badge uses success for active and danger for revoked — the single worst pair to distinguish, carrying the single most important fact in the app.

Fixing the contrast does not touch this. A 5.38:1 green and a 5.44:1 red are both perfectly legible and still identical to each other. WCAG 1.4.1 is a separate rule: colour must never be the only visual means of conveying information.

For Token the fix costs nothing, because the work is already done. a5/0003's displayStatus already returns one of five words. Render the word:

// Colour AND text. Either one alone is enough to read the state.
<View style={{ backgroundColor: colors[fillFor(status)] }}>
  <Text style={{ color: colors[inkFor(status)] }}>{label}</Text>
</View>

// Not this -- the state exists only as a hue:
<View style={{ backgroundColor: colors.success, width: 8, height: 8 }} />

The test is one you can run without any tooling: screenshot the screen, convert it to greyscale, and see whether you can still tell what your tokens are doing. If you cannot, neither can a substantial number of your users — and unlike a contrast failure, they will not know what they are missing.
