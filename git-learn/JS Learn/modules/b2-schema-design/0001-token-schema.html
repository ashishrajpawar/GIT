Token Schema

B2 — Lesson 1 of 3 ~55 min
Why this matters for Token

This is the real schema — the one you'll run in production. Every design decision here shapes what the app can do: how tokens are issued, what rules are enforced, how revocation propagates. A schema mistake early on means painful migrations later. We design it right, once, with constraints that enforce Token's privacy promise at the database level.

Design principles

  1. Constraints over code — if a rule must always hold (revoked tokens stay revoked), enforce it in the database, not only in application code.
  2. Normalize first — one fact in one place. If a user changes their name, it changes everywhere because it's stored once.
  3. Use the right types — timestamps for time, integers for counts, JSONB for flexible payloads.
  4. Plan for queries — think about what the app needs to ask, then design tables that answer those questions efficiently.

The users table

CREATE TABLE users (
  id            SERIAL PRIMARY KEY,
  phone_hash    TEXT NOT NULL UNIQUE,
  display_name  TEXT NOT NULL,
  avatar_url    TEXT,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

Design notes:

  • phone_hash — not the raw phone number. Token is privacy-first: store a one-way hash. You can verify "is this the same phone?" without storing the actual number.
  • TIMESTAMPTZ — timestamp with timezone. Always use this over plain TIMESTAMP — it stores UTC internally and converts to the user's timezone on display. India has one timezone (IST), but this is correct practice for any app.
  • updated_at — tracks when the row was last modified. Useful for sync and caching.

Auto-updating updated_at

CREATE OR REPLACE FUNCTION update_updated_at()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = NOW();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER users_updated_at
BEFORE UPDATE ON users
FOR EACH ROW
EXECUTE FUNCTION update_updated_at();

This trigger automatically sets updated_at on every UPDATE — you never need to remember to set it in your API code.

The tokens table

CREATE TABLE tokens (
  id          SERIAL PRIMARY KEY,
  code_hash   TEXT NOT NULL UNIQUE,   -- SHA-256(normalised code + pepper)
  code_enc    BYTEA NOT NULL,          -- AES-256-GCM, for showing it once more
  user_id     INTEGER NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
  label       TEXT NOT NULL,
  status      TEXT NOT NULL DEFAULT 'active'
              CHECK (status IN ('active', 'paused', 'revoked')),
  max_uses    INTEGER            -- NULL = unlimited. 0 = no uses at all.
              CHECK (max_uses >= 0),
  use_count   INTEGER NOT NULL DEFAULT 0
              CHECK (use_count >= 0),
  expires_at  TIMESTAMPTZ,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  revoked_at  TIMESTAMPTZ,
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  -- Business rule: revoked_at must be set when status is 'revoked'
  CHECK (
    (status != 'revoked') OR (revoked_at IS NOT NULL)
  ),
  -- Business rule: when a limit is SET, use_count can't exceed it.
  -- IS NULL, not = 0 -- 0 is a real limit meaning "no uses permitted".
  CHECK (
    max_uses IS NULL OR use_count <= max_uses
  )
);
There is no code column, and that is the point

Every other table in this course stores what it is about. This one does not: the token code is never written to the database in the clear. Two derived columns stand in for it (ADR-0007), and they exist for different jobs.

code_hash — SHA-256 of the normalised code plus a server-side pepper. This is the only way a token is looked up. Redemption hashes what the holder typed and matches on this column, so the database never sees the code and a stolen dump contains no usable capabilities.

code_enc — AES-256-GCM of the same code. This exists for exactly one feature: the owner asking to see a code they have lost. It is decrypted for one token at a time, on request, and the request is logged. It is never touched by a list query.

Why a plain hash, and not bcrypt or argon2

Password hashing is the obvious instinct here and it is wrong for this column. bcrypt and argon2 salt randomly, per row — which is exactly what you want for passwords, because you look a user up by their email and then verify one hash. Here there is nothing to look up by: the code is all the holder has. A random salt would mean hashing the candidate against every row in the table to find a match.

A pepper gives you what a salt gives you — the same code in someone else's database hashes differently, and a rainbow table is useless — while keeping the hash deterministic, so it can be a UNIQUE index and an O(1) lookup. The reason the slowness of bcrypt is not missed is that a 3112 keyspace is not brute-forceable at any speed; the threat model is a database dump, not a weak secret.

Two environment variables you can never lose

TOKEN_CODE_PEPPER and TOKEN_CODE_KEY are required at startup and the server should refuse to boot without them. Lose them and every token ever issued becomes permanently unusable — no code will hash to a stored value, and no code_enc will decrypt. There is no recovery path, because the design has deliberately left itself none.

So they belong in the disaster-recovery plan, stored somewhere the database backups are not. A backup that contains both the rows and the keys has quietly undone the whole arrangement.

What this forces on everything downstream

  • GET /tokens returns no code field at all. Serving one would mean decrypting every row on every scroll.
  • The code is returned exactly once, in the reply to POST /tokens. Showing it again is a separate, logged request.
  • You cannot search tokens by code, sort by it, or put it in a log line — there is nothing to search.

Those are real costs. They are the same costs a password column imposes, and nobody argues about that one.

The one column on this table that is easy to get backwards

NULL means unlimited. 0 means no uses at all. Opposite meanings, and the tempting schema — INTEGER NOT NULL DEFAULT 0 — breaks both ends of it: NOT NULL makes "unlimited" impossible to write down, and DEFAULT 0 makes every token created without an explicit limit permit nothing. Issued and instantly unusable.

So the column is nullable and has no default. There is no safe default here, and the database declining to guess is the point: a token's limit is a decision the caller has to make.

Notice what this does to the constraint. "Use count cannot exceed the limit" only applies when there is a limit, which is max_uses IS NULL OR use_count <= max_uses. Writing max_uses = 0 OR … instead reads 0 as the unlimited case and quietly inverts the whole rule — a token capped at zero would accept uses forever.

The same trap follows the value out of the database. In JavaScript only one of the two is falsy:

// WRONG -- 0 is falsy, so "no uses permitted"
// is read as "no limit set".
if (token.max_uses) { checkLimit(); }

// RIGHT -- asks the question actually being asked.
if (token.max_uses != null) { checkLimit(); }

expires_at one row below behaves the same way: NULL means never expires, and new Date(null) is 1 January 1970 — comfortably in the past — so parsing before checking for null marks every never-expiring token as expired.

Let's unpack the decisions:

  • code_hash and code_enc — and no code column. This is the one row of this table that is not obvious; the callout below is the whole reason.
  • label — who the token is for ("Amazon Delivery", "NoBroker Agent"). The user names them.
  • status — only three valid values, enforced by CHECK. You cannot invent a fourth state by accident.
  • max_uses NULL means unlimited; any number is a cap, and 0 is the cap that permits nothing. See the callout below — this is the single easiest thing on this table to get backwards.
  • use_count — how many times the token has been redeemed. Simpler than counting redemption_events every time.
  • expires_at — nullable. If set, the token auto-expires. Your API checks this on every redemption.
  • ON DELETE RESTRICT — you can't delete a user who has tokens. Explicit cleanup first.
  • CHECK constraints — the database enforces that revoked tokens have a revoked_at timestamp, and use_count never exceeds max_uses.

The access_rules table

CREATE TABLE access_rules (
  id          SERIAL PRIMARY KEY,
  token_id    INTEGER NOT NULL REFERENCES tokens(id) ON DELETE CASCADE,
  rule_type   TEXT NOT NULL
              CHECK (rule_type IN ('time_window', 'call_limit', 'category', 'cooldown')),
  payload     JSONB NOT NULL,
  is_active   BOOLEAN NOT NULL DEFAULT true,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  UNIQUE(token_id, rule_type)
);

Design notes:

  • ON DELETE CASCADE — when a token is deleted, its rules are automatically removed. Rules can't exist without a token.
  • UNIQUE(token_id, rule_type) — one rule of each type per token. Simplifies the API and enables UPSERT.
  • JSONB payload — each rule type has different fields. Time windows need start/end hours; call limits need max_per_day; categories need an allowed list. JSONB handles this without one table per rule type.
  • is_active — lets users disable a rule without deleting it (they might want to re-enable later).

Payload shapes by rule_type

-- time_window
{"start_hour": 9, "end_hour": 18, "timezone": "Asia/Kolkata", "days": [1,2,3,4,5]}

-- call_limit
{"max_per_day": 2, "max_per_week": 10}

-- category
{"allowed": ["delivery", "support"], "blocked": ["marketing", "spam"]}

-- cooldown
{"min_minutes_between": 30}

The redemption_events table

CREATE TABLE redemption_events (
  id          SERIAL PRIMARY KEY,
  token_id    INTEGER NOT NULL REFERENCES tokens(id) ON DELETE RESTRICT,
  holder_ip   TEXT,
  holder_name TEXT,
  user_agent  TEXT,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

This is an append-only audit log — you never UPDATE or DELETE rows here. Every redemption is recorded permanently. This is how the user sees "who used this token and when."

ON DELETE RESTRICT because you'd never want to accidentally erase redemption history by deleting a token.

Indexes for Token's queries

-- Token list for a user (the main screen)
CREATE INDEX idx_tokens_user_id ON tokens(user_id);

-- Token lookup at redemption: by HASH, never by the code itself.
-- Already covered by the UNIQUE constraint on code_hash.
--   SELECT ... FROM tokens WHERE code_hash = $1   -- $1 = hashCode(code)

-- Active tokens only (partial index — smaller, faster)
CREATE INDEX idx_tokens_active ON tokens(user_id)
WHERE status = 'active';

-- Rules by token
CREATE INDEX idx_rules_token_id ON access_rules(token_id);

-- Redemption history by token
CREATE INDEX idx_redemptions_token_id ON redemption_events(token_id);

-- Recent redemptions (for the dashboard)
CREATE INDEX idx_redemptions_created_at ON redemption_events(created_at DESC);

The partial index on active tokens is clever: it only indexes rows where status = 'active'. Since most queries on the token list filter by active status, this index is smaller and faster than indexing all tokens.

Now build it yourself

Write codeHashInput(raw) — the normalisation that turns what a holder typed into the exact string that gets hashed. It is the smallest function in this module and the one with the least room to change its mind later: every hash in the table was computed by whatever this function did on the day it ran.
