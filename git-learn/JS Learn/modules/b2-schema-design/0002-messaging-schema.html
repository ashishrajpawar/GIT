Messaging Schema

B2 — Lesson 2 of 3 ~50 min
Why this matters for Token

When a holder redeems a token and sends a message, that message must be stored, delivered, and displayed — with read receipts, ordering, and the ability to stop all communication by revoking the token. The messaging schema must handle conversations between a token holder (anonymous) and the token owner, tied to a specific token. This is different from typical chat schemas because the parties aren't "users" — one side is anonymous.

Token's messaging model

Unlike WhatsApp (user ↔ user), Token's messaging is token-scoped:

  • A conversation is tied to a specific token + specific holder session
  • The owner (the user who issued the token) sees messages in their app
  • The holder (whoever redeemed the token) messages through the web page
  • If the token is revoked, the conversation is closed — no more messages
  • One token can have multiple conversations (different people redeeming it)

The conversations table

CREATE TABLE conversations (
  id            SERIAL PRIMARY KEY,
  token_id      INTEGER NOT NULL REFERENCES tokens(id) ON DELETE RESTRICT,
  holder_session_id TEXT NOT NULL UNIQUE,
  holder_name   TEXT,
  status        TEXT NOT NULL DEFAULT 'open'
                CHECK (status IN ('open', 'closed', 'blocked')),
  -- WHY it closed. The client renders its own sentence from this, because
  -- the server cannot write one into messages -- it holds no key.
  closed_reason TEXT CHECK (closed_reason IN ('revoked', 'expired', 'exhausted', 'blocked')),
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  last_message_at TIMESTAMPTZ
);

Design notes:

  • holder_session_id — a unique identifier for this holder's session (generated when they redeem). Not a user ID — holders are anonymous.
  • holder_name — optional. The holder may provide a name ("Delivery Agent") but doesn't have to.
  • status — 'open' (active), 'closed' (ended normally or token revoked), 'blocked' (user blocked this holder).
  • last_message_at — denormalized for sorting. The conversation list shows most recent first without joining messages.

The messages table

CREATE TABLE messages (
  id              BIGSERIAL,
  conversation_id INTEGER NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
  sender_type     TEXT NOT NULL CHECK (sender_type IN ('owner', 'holder')),

  -- The body, sealed on the sender's device. The server stores these
  -- bytes and holds no key for them. Everything ABOUT the message --
  -- its text, its type, an image's dimensions -- is inside here.
  ciphertext      BYTEA NOT NULL,
  nonce           BYTEA NOT NULL,          -- unique per message, never reused
  key_version     SMALLINT NOT NULL,       -- which key sealed it

  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  delivered_at    TIMESTAMPTZ,
  read_at         TIMESTAMPTZ,

  -- Postgres requires the partition key in the primary key.
  PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

-- One partition per month, created ahead of time by a job.
CREATE TABLE messages_2026_08 PARTITION OF messages
  FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');
CREATE TABLE messages_2026_09 PARTITION OF messages
  FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');

Design notes:

  • sender_type — 'owner' or 'holder'. Not a user ID for the holder, because holders aren't users in the system.
  • ciphertext / nonce / key_version — the envelope. See the callout below; this is the shape of the whole table's argument.
  • delivered_at / read_at — timestamps for delivery and read receipts. NULL = not yet delivered/read. These are outside the envelope because the server sets them.
  • ON DELETE CASCADE — if a conversation is removed, its messages go with it.
  • No content_type, no metadata — both used to be columns, and both describe the content. See below.
What is outside the envelope is exactly what the server needs, and nothing else

ADR-0002 commits Token to end-to-end encryption from v1: the server stores ciphertext and has no key. This table is where that stops being a policy and becomes a set of columns.

The useful way to design it is to ask, of every column, does the server need this to do its job? Its job is narrow — route a message to a conversation, order it, and record delivery. So:

OutsideWhy the server needs it
conversation_idto route it
sender_typeto route it to the other party
created_atto order it, and to partition
delivered_at, read_atthe server sets these itself
nonce, key_versionthe recipient needs them to decrypt, and neither reveals anything

Everything else went inside. content_type and metadata were columns and are now fields in the plaintext, because both describe the content. "This message is an image, 1920×1080, 2.3 MB" is not routing information — it is a description of what was sent, and a server that can read it can tell a delivery company's message from a doctor's.

Nothing is lost: the client seals a small JSON object rather than a string, and unseals it to render. The cost is that you cannot add a content type without a client release, because the server no longer knows what a message is.

The nonce is not optional and must never repeat

AES-GCM catastrophically fails on nonce reuse: encrypt two different messages under the same key and nonce, and anyone holding both ciphertexts recovers the XOR of the plaintexts without touching the key. So the nonce is stored per message and generated randomly per message — never a counter that resets, never derived from the message id.

Why key_version exists before it is needed

Keys get rotated — after a device is lost, or on a schedule. Without a version, a rotation makes every older message undecryptable, and there is no migration you can run because the server cannot read them to re-encrypt. A SMALLINT costs two bytes now and is impossible to add later.

Partitioned from the first migration, not when it hurts

PARTITION BY RANGE (created_at) is in the original CREATE TABLE deliberately. ADR-0003's rule is that anything you cannot retrofit goes in from day one, and partitioning is the clearest example: converting a large live messages table into a partitioned one means copying every row, and you do it under exactly the load that made you want it.

Two things it buys, and the second is the one people forget:

  • Retention is a DROP TABLE. Deleting a year of old messages with DELETE writes every row to the WAL, bloats the table and leaves the space to VACUUM. Dropping a partition is instant and returns the disk immediately.
  • Queries touch one partition. A chat view asks for recent messages, and Postgres skips the months it can prove are irrelevant.

Notice what partitioning forces: PRIMARY KEY (id, created_at), because Postgres requires the partition key to be part of every unique constraint. A plain SERIAL PRIMARY KEY is rejected outright on a partitioned table — which is a good thing, since it means you cannot half-adopt this.

The partitions themselves are created ahead of time by a scheduled job. A month with no partition takes inserts and fails them, so that job failing silently is a total outage on the first of the month — it belongs in monitoring, not in a cron nobody watches.

System messages — the thing E2EE quietly takes away

The obvious way to tell a holder that a token was revoked is to insert a message saying so. Look at what that requires: the server writing readable text into a table whose entire design is that the server cannot write readable text. It has no key. It could not encrypt that row if it wanted to.

So a system message is not a message. It is an event, and each client renders its own text from it:

-- Not a row in messages. The conversation's own state is the event.
UPDATE conversations
   SET status = 'closed', closed_reason = 'revoked', updated_at = NOW()
 WHERE token_id = $1;

The client sees status: 'closed' with a reason and draws the grey "This token has been revoked" line itself. Three things fall out of that, and they are all improvements:

  • It is translated, because the client knows the user's language and the server does not.
  • It cannot desynchronise from the truth. A stored system message is a claim about state that was true when it was written; a rendered one is read from the state itself.
  • It does not consume a message id or a partition row for something nobody sent.

The general rule, and it will come up again: under end-to-end encryption, anything the server wants to say has to be said in structured state rather than in prose. Every "just insert a system message" instinct needs converting into "record the event, let the client write the sentence".

Read receipts

Token shows read receipts — the sender knows when their message was seen. The schema handles this with the read_at timestamp:

-- Mark all messages in a conversation as read by the owner
UPDATE messages
SET read_at = NOW()
WHERE conversation_id = 42
  AND sender_type = 'holder'
  AND read_at IS NULL;

-- Mark as delivered (WebSocket confirms receipt)
UPDATE messages
SET delivered_at = NOW()
WHERE id = 123
  AND delivered_at IS NULL;

Querying conversations

-- Get all open conversations for a user's tokens (the inbox)
SELECT
  c.id,
  c.holder_name,
  c.last_message_at,
  t.code AS token_code,
  t.label AS token_label
FROM conversations c
INNER JOIN tokens t ON c.token_id = t.id
WHERE t.user_id = 1
  AND c.status = 'open'
ORDER BY c.last_message_at DESC NULLS LAST;

-- Get messages for a conversation (paginated).
-- The server hands back the envelope; the client decrypts it.
SELECT id, sender_type, ciphertext, nonce, key_version, created_at, read_at
FROM messages
WHERE conversation_id = 42
ORDER BY created_at ASC
LIMIT 50 OFFSET 0;

-- Unread count per conversation
SELECT
  c.id,
  COUNT(m.id) AS unread_count
FROM conversations c
LEFT JOIN messages m ON m.conversation_id = c.id
  AND m.sender_type = 'holder'
  AND m.read_at IS NULL
WHERE c.status = 'open'
GROUP BY c.id;

Closing conversations on revocation

When a token is revoked, all its conversations must close. A database trigger handles this automatically:

CREATE OR REPLACE FUNCTION close_conversations_on_revoke()
RETURNS TRIGGER AS $$
BEGIN
  IF NEW.status = 'revoked' AND OLD.status != 'revoked' THEN
    UPDATE conversations
    SET status = 'closed', updated_at = NOW()
    WHERE token_id = NEW.id AND status = 'open';

    -- NO system message is inserted. The server has no key, so it could
    -- not encrypt one -- and it does not need to. The status change above
    -- IS the event; each client renders its own sentence from it.
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER token_revoked_close_conversations
AFTER UPDATE ON tokens
FOR EACH ROW
EXECUTE FUNCTION close_conversations_on_revoke();

Indexes for messaging queries

-- Conversation list for a token
CREATE INDEX idx_conversations_token_id ON conversations(token_id);

-- Messages by conversation, newest first -- this is the chat view's query.
-- Declared on the parent; Postgres creates it on every partition, and on
-- each new one automatically.
CREATE INDEX idx_messages_conversation_id
  ON messages(conversation_id, created_at DESC);

-- Unread messages (for badge counts). A partial index, so it stays small.
CREATE INDEX idx_messages_unread ON messages(conversation_id)
WHERE sender_type = 'holder' AND read_at IS NULL;

-- Sort conversations by last activity
CREATE INDEX idx_conversations_last_message ON conversations(last_message_at DESC NULLS LAST);

Now build it yourself

Write partitionsToCreate(existing, now, monthsAhead) — the decision the scheduled job makes every time it runs. It is the function whose silent failure is a total outage at midnight on the first of the month, and it is pure arithmetic, so you can hold it to account here.
