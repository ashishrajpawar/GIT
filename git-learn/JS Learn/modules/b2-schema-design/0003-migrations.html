Migrations

B2 — Lesson 3 of 3 ~40 min
Why this matters for Token

Your schema will change — you'll add columns, create tables, modify constraints. In production, you can't just DROP and recreate tables (you'd lose all user data). Migrations let you evolve the schema incrementally: each change is a numbered script that runs in order. Your production database knows which migrations it has already applied and only runs the new ones.

What is a migration?

A migration is a SQL file that changes the database schema. Migrations are:

  • Numbered sequentially — 001, 002, 003... so they run in order
  • Immutable once applied — never edit a migration that's been run in production. Write a new one.
  • Reversible — each migration has an "up" (apply) and "down" (undo) direction
  • Tracked — the database records which migrations have run

Token's migration folder structure

api/
  migrations/
    001_initial_schema.sql
    002_messaging.sql
    003_add_token_description.sql
    ...
  migrate.js          ← simple script that runs pending migrations

Building a simple migration runner

You don't need a heavy tool for this. A simple Node script that:

  1. Creates a schema_migrations table to track what's been applied
  2. Lists all .sql files in the migrations folder
  3. Skips the ones already recorded
  4. Runs the remaining ones in order
// api/migrate.js
const { Pool } = require('pg');
const crypto = require('crypto');
const fs = require('fs');
const path = require('path');

const pool = new Pool({
  connectionString: process.env.DATABASE_URL || 'postgres://localhost:5432/token_dev',
});

async function migrate() {
  const client = await pool.connect();

  try {
    // Only one deploy may migrate at a time. Two servers starting together
    // would otherwise both see the same pending list and both run it.
    await client.query('SELECT pg_advisory_lock($1)', [727272]);

    await client.query(`
      CREATE TABLE IF NOT EXISTS schema_migrations (
        id SERIAL PRIMARY KEY,
        filename TEXT NOT NULL UNIQUE,
        checksum TEXT NOT NULL,
        applied_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
      )
    `);

    const { rows: applied } = await client.query(
      'SELECT filename, checksum FROM schema_migrations ORDER BY filename'
    );

    const migrationsDir = path.join(__dirname, 'migrations');
    const available = fs.readdirSync(migrationsDir)
      .filter(f => f.endsWith('.sql'))
      .sort()
      .map(f => ({
        name: f,
        checksum: sha256(fs.readFileSync(path.join(migrationsDir, f))),
      }));

    // All the deciding happens here, with no database in it. This is the
    // exercise at the bottom of the lesson.
    const plan = planMigrations(applied, available);

    if (plan.error) {
      throw new Error(
        `refusing to migrate: ${plan.error.kind} (${plan.error.name})`
      );
    }

    for (const file of plan.toRun) {
      console.log(`  applying: ${file.name}...`);
      const sql = fs.readFileSync(path.join(migrationsDir, file.name), 'utf8');

      // The migration AND the record of it, in one transaction. If these
      // can come apart, a crash between them leaves a migration that ran
      // and is not recorded -- so it runs again on the next deploy.
      await client.query('BEGIN');
      try {
        await client.query(sql);
        await client.query(
          'INSERT INTO schema_migrations (filename, checksum) VALUES ($1, $2)',
          [file.name, file.checksum]
        );
        await client.query('COMMIT');
      } catch (err) {
        await client.query('ROLLBACK');
        throw err;
      }

      console.log(`  done: ${file.name}`);
    }

    console.log('All migrations applied.');
  } finally {
    client.release();   // releases the advisory lock too
    await pool.end();
  }
}

function sha256(buf) {
  return crypto.createHash('sha256').update(buf).digest('hex');
}

migrate().catch(err => {
  console.error('Migration failed:', err);
  process.exit(1);
});
Three things this runner does that the obvious one does not

The four-line version — list the files, skip the applied ones, run the rest — works for months and then fails in ways that are very hard to diagnose, because by the time you notice, the evidence is a schema that does not match another environment's and no record of why.

1. A checksum, because files get edited after they run

Someone fixes a typo in 003_add_index.sql after it has already been applied in staging. The runner sees the filename in schema_migrations and skips it — forever. Staging has the old index, a fresh database gets the new one, and the two schemas diverge silently and permanently.

Storing a hash of the file turns that into a loud failure on the next deploy. The rule it enforces is the one migration systems live by: an applied migration is immutable. Fix it forward with a new file; never edit one that has run.

2. Refusing out-of-order files

Two people branch on Monday. Both write 005_*.sql. One merges, deploys, and 005 is applied. The other rebases, renames to 006 — or does not, and now there is a second 005.

Worse is the quiet case: a migration numbered below the highest one already applied shows up in a merge. The naive runner applies it happily, and the resulting schema depends on the order the branches merged in. A database whose shape depends on merge order is not reproducible, which is the entire thing migrations exist to provide. Refuse and make a human look.

3. One transaction per migration, covering the bookkeeping

The obvious version runs the SQL, then inserts the tracking row as a separate statement. A crash in that gap leaves a migration that ran and is not recorded, so the next deploy runs it again — and CREATE TABLE the second time is an error that stops the deploy with the database half-migrated.

Wrapping both means the outcome is always "applied and recorded" or "neither".

Postgres lets you do this; not every database does

DDL inside a transaction is a Postgres luxury. MySQL commits implicitly on CREATE TABLE, so a half-failed migration there really is half-applied and you clean it up by hand. Worth knowing before you assume the pattern travels.

Two Postgres exceptions of its own: CREATE INDEX CONCURRENTLY and ALTER TYPE ... ADD VALUE cannot run inside a transaction block. A migration needing either has to be its own file, run outside the wrapper — which is why real tools have a "no-transaction" flag.

And the lock

pg_advisory_lock stops two servers deploying at the same instant from both reading the same pending list and both running it. It costs one line and the failure it prevents is a duplicate CREATE TABLE during a rolling deploy — which is to say, exactly when you are least able to think about it.

Run it with:

node api/migrate.js

Writing a new migration

Say you want to add a description field to tokens. Don't edit 001_initial_schema.sql — write a new migration:

-- api/migrations/003_add_token_description.sql

BEGIN;

ALTER TABLE tokens ADD COLUMN description TEXT;

-- Backfill: set existing tokens' description to their label
UPDATE tokens SET description = label WHERE description IS NULL;

COMMIT;

Rules for writing migrations

  • One concern per migration — don't mix "add a column" with "create a new table" unless they're tightly coupled.
  • Wrap in a transaction — BEGIN/COMMIT ensures the migration either fully applies or not at all.
  • Think about existing data — if you add NOT NULL, you need a DEFAULT or a backfill.
  • Never delete data implicitly — dropping a column destroys its data. Be explicit about what's lost.

Common migration patterns

Adding a column

-- Safe: nullable column, no default needed
ALTER TABLE tokens ADD COLUMN description TEXT;

-- Safe: with a default (Postgres fills existing rows instantly)
ALTER TABLE tokens ADD COLUMN is_public BOOLEAN NOT NULL DEFAULT false;

-- DANGEROUS: NOT NULL without a default on a table with existing rows
-- ALTER TABLE tokens ADD COLUMN required_field TEXT NOT NULL;
-- This FAILS if any rows exist! Add a default or backfill first.

Removing a column

-- api/migrations/004_remove_deprecated_field.sql
BEGIN;

-- Step 1: remove the column
ALTER TABLE tokens DROP COLUMN IF EXISTS deprecated_field;

COMMIT;

Renaming a column

ALTER TABLE tokens RENAME COLUMN issued_to TO label;
Rename with caution

Renaming a column breaks any running code that references the old name. In production, the safe approach is: (1) add the new column, (2) backfill data from the old column, (3) deploy code that uses the new column, (4) drop the old column in a later migration. For Token at this stage (no production users yet), a simple RENAME is fine.

Adding a constraint to existing data

-- api/migrations/005_add_status_check.sql
BEGIN;

-- First, fix any invalid data
UPDATE tokens SET status = 'active' WHERE status NOT IN ('active', 'paused', 'revoked');

-- Then add the constraint
ALTER TABLE tokens ADD CONSTRAINT tokens_status_check
CHECK (status IN ('active', 'paused', 'revoked'));

COMMIT;

Creating an index (without locking)

-- CONCURRENTLY doesn't lock the table during index creation
-- (Important on large tables in production)
CREATE INDEX CONCURRENTLY idx_tokens_expires_at ON tokens(expires_at)
WHERE expires_at IS NOT NULL;

Note: CREATE INDEX CONCURRENTLY can't run inside a transaction (BEGIN/COMMIT). It's one of the few cases where you skip the transaction wrapper.

Down migrations (rollback)

A "down" migration undoes the "up". For simple projects, you can keep them in the same file or a separate folder:

-- api/migrations/003_add_token_description.sql

-- UP
ALTER TABLE tokens ADD COLUMN description TEXT;

-- DOWN (in case you need to roll back)
-- ALTER TABLE tokens DROP COLUMN description;

For Token, keep the DOWN as a comment. You'll rarely need it in development, and in production you'd write a new migration to undo changes (going forward, not backward).

Add the migration script to package.json

{
  "scripts": {
    "migrate": "node api/migrate.js",
    "migrate:fresh": "dropdb token_dev && createdb token_dev && node api/migrate.js"
  }
}

npm run migrate applies pending migrations. npm run migrate:fresh rebuilds from scratch (development only — never in production).

Now build it yourself

Write planMigrations(applied, available) — the function the runner above calls before it touches anything. Every check that stops a bad deploy lives in it, and none of them needs a database, which is why it is worth pulling out.
