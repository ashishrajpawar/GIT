Trust Boundaries

C0 — Lesson 1 of 2  |  ~45 min

Why this matters for Token

Every product you have used describes itself by what it does. Token is easier to describe by where its data is not allowed to go.

A holder must never learn a phone number. A server must never hold a key that opens a message. A log must never contain a token code. A call record must never contain a network address. Those are not four features. They are four lines, and the whole system is the shape those lines make.

By the end of this lesson you will have written the function that enforces them — and, more usefully, you will know why it has to refuse things it has never heard of.

1 · A trust boundary is a line data changes form to cross

The phrase sounds abstract. It is not. A trust boundary is any point where data moves from somewhere you control to somewhere you control less — and the question at every boundary is the same: what form must this be in to cross?

Token has four zones. Learn these four names; the rest of the course uses them.

The log is a zone, and that is the point of drawing it separately

Nobody designs a log. It accumulates. It gets shipped to a third-party error tracker that attaches request bodies by default, copied into a support ticket, grepped on a laptop, and retained long after the row it describes was deleted.

Treating “the log” as a destination with its own rules is the single highest- value idea in this lesson, because the log is where sensitive data ends up without anyone deciding it should. Three separate lessons in this course once taught writing a token code into a log line, each of them in a lesson about something else.

Three rows are worth stopping on, because each one is a decision that could plausibly have gone the other way and did not.

The phone number is allowed to reach a vendor and not a log

That looks backwards the first time you see it. A vendor is a company we do not control; a log is a file on our own server.

But the SMS aggregator cannot deliver a one-time code without dialling the number. The disclosure is inherent to the purpose, it is bounded by a contract, and it is the reason that vendor exists. The log has no such need. Nobody ever wrote a log line that required a phone number to do its job — they wrote it because the number was in scope and printing it was convenient.

The rule that generalises: a boundary is crossed for a reason, or not at all. “It was available” is not a reason.

The holder's IP may reach the server and not the user's export

The user's data export is a compliance feature. It exists so a person can get a copy of their data. A naive export is written from the schema: find every row connected to this user and serialise it.

Redemption records are connected to this user — they belong to tokens the user issued — and they contain the holder's IP address, the name they typed, and their browser. Exporting those hands one person another person's rough location, through a privacy feature, on request.

The holder is a different person who never signed up and never agreed to be disclosed. What belongs in the user's export is that a redemption happened, and when.

“A row in my table” and “my personal data” are different sets

This is the sentence to remember from this lesson. An export written from the schema ships the difference between those two sets; an export written from the question whose data is this? does not.

Notice that the boundary here is not a technical one. Nothing stops the code. The line exists only because someone asked the question, which is exactly why it needs to be written down in a function rather than remembered.

An ICE candidate may not reach the server at all

When two people set up a call, their devices exchange candidate network paths. An ICE candidate is an IP address.

Token relays every call through its own server precisely so that neither party learns the other's address — so a delivery company cannot discover roughly where a user lives. If those candidates were then written into a call record, the policy would be defeated from the far side, in a table nobody thinks of as sensitive.

This is the most easily lost of the five, because storing them is useful. They are excellent debugging material. The rule survives only if the absence of the column is treated as the feature it is.

The recovery phrase — the twelve words that are the only thing standing between a stolen phone number and a user's entire message history — is cleared for export to a third party, because the function was written as a list of things to stop and that list is finite.

A deny-list is a promise about the past

Every rule in a deny-list was written by somebody who had already thought of the problem. The set of things you have thought of does not grow when someone adds a database column.

An allow-list is the opposite: a field that nobody has classified cannot move. The new column breaks the build, or fails a check, or shows up in a review — which is annoying exactly once, at the moment it is cheap.

This same argument appears three more times in this course, and it is worth noticing that it is always the same argument: an allow-list for what goes in a log, an allow-list for the fields in a push payload, and the rule that an unknown access-rule type is refused rather than ignored. Absence of a known-bad is never evidence of good.

The same function, inverted

Three things that small change bought:

  • The unknown field is refused, and the reason says why. Someone reading the log of refusals learns that a field needs classifying.
  • The answer is not a boolean. “May a message body reach the server?” has no yes-or-no answer — it may, sealed. A function returning true has thrown away the only part that mattered.
  • Two different refusals are distinguishable. Unclassified is a gap in the policy; not_permitted is the policy working. They need different responses from a human, so they need different reasons.

5 · Where the boundaries came from

None of the five rows in the table was invented for this lesson. Each is an architecture decision with a written record in the Token repo, and lesson 2 is about how those records work.

RuleDecided inThe cost it accepted
Messages sealed before the serverADR-0002No server-side search, no server-side moderation, no message recovery from a phone number alone
Token codes hashed and encrypted, never plainADR-0007Two derived columns instead of one; lose the keys and every token ever issued is dead
No network addresses in call recordsADR-0008Every call is relayed, so relay bandwidth is a real bill and a coturn outage is a total call outage
An identical refusal for every dead codeADR-0010Support cannot tell a holder which case they are in
Event-only analytics, no per-user timelinesADR-0012No funnel tooling, ever

Notice that every row has a cost, and that the cost is written down next to the decision. That is not humility. A decision recorded with its cost can be overturned when the evidence changes; one recorded without can only be re-argued — which is why the same questions come back every few months in most projects.
