Release & QA for a Non-Engineer

F1 — Lesson 10 of 16  |  the founder’s highest-leverage engineering contribution

Why this matters for Token

You are not going to write code. You are going to be the person who uses the product the way a stranger would, on the phone a real Indian user actually has, on the connection they actually have — and that is a role the person who built it cannot fill, because they know where to tap.

It matters more here than in an ordinary app because several of Token’s guarantees are only true if the build is right. Revoke must be irreversible in the built app. A block must follow the person in the built app. Those are promises made to users and to two app stores, and reading the code is not evidence.

1 · Write a bug report a developer can act on

The single skill in this lesson with the best return. A bad bug report costs three messages and a day; a good one costs one message and is fixed before you look again.

WHAT HAPPENED
One sentence. The observed behaviour, not your theory.

STEPS
1. Signed in as <which account>
2. Tapped Tokens, then the token labelled "Sofa listing"
3. Tapped Revoke, confirmed
4. Opened the redemption page in Chrome on the same phone

EXPECTED   The page refuses -- "this code no longer works"
ACTUAL     The page loaded the conversation and let me send
           a message

WHERE
  App version <n> (build <n>), Android 12,
  Redmi <model>, on mobile data
  Time: 2026-08-26 14:32 IST

HOW OFTEN
  3 out of 3 attempts. Also happened on the other phone.

EVIDENCE
  Screen recording attached. Token id <id> -- NOT the code.

ANYTHING ELSE
  The token list still shows it as Revoked, so it is the
  page that is wrong, not the app.

Six rules behind that template:

  • Observed, not diagnosed. “The API is caching” sends the developer down your guess. “The page loaded and let me send a message” sends them to the fact.
  • Expected and actual, as two separate lines. Half of all disagreements are about what was supposed to happen.
  • Exact steps from a known starting state. “Sometimes when I revoke a token” is not reproducible.
  • How often. Three out of three and one out of twenty are different bugs with different causes.
  • Device, version, network, time. The time lets them find it in the logs.
  • Never paste a token code into a bug report. Bug trackers are third-party systems with broad access. Paste the token id — it identifies the row for anyone who can query the database and is worth nothing to anyone who cannot.

2 · The manual QA checklist

Cover every flow in the product. Written as things to check, with the answer written down each time, so that two runs a month apart are comparable.

ACCOUNT
[ ] Sign up with a new number; the one-time code arrives
    within a minute
[ ] Wrong code is rejected with a useful message
[ ] Display-name screen appears and cannot be skipped
[ ] Sign in again on a second device; the old device is
    handled the way the design says it is
[ ] Sign out, sign back in; tokens and conversations return

ISSUING
[ ] Create a token with a label; the code is shown ONCE
[ ] Leaving the screen and returning does not show the code
    again
[ ] Set a time window; set a per-day limit; set text-only
[ ] Set an expiry; set a maximum number of uses
[ ] Set maximum uses to 0 -- the token permits NO uses.
    (Not "unlimited". This is the one everybody gets wrong)
[ ] Leave max uses empty -- unlimited
[ ] QR code renders and scans from another device

REDEEMING
[ ] Open the link in a browser; type a name; connect
[ ] The holder never sees a phone number anywhere
[ ] A wrong code is refused
[ ] A code that does not exist gives the SAME response as
    a valid code that is revoked -- see the warning below
[ ] Send a message each way; both arrive
[ ] Voice call connects; video call connects

STATE
[ ] Pause: contact stops. Resume: contact returns
[ ] Revoke: contact stops permanently; no undo anywhere
[ ] Expired token refuses, and the badge says Expired
[ ] A token that is BOTH paused and expired reads
    "Expired", not "Paused" -- and offers no Resume button
[ ] Use limit reached: the badge says the right thing
[ ] Revoked beats everything else in the badge

SAFETY
[ ] Report from the app; report from the browser page
[ ] The report ARRIVES somewhere a human sees
[ ] Block: the person cannot reach you on a NEW token
[ ] Share sheet warns before sending a code through a
    channel that already identifies you
[ ] An unrecognised share target also warns

DATA
[ ] Export downloads and opens; contains no token codes
    and no holder IP addresses
[ ] In-app delete works
[ ] Web deletion page works WITHOUT the app installed
[ ] After deletion, the holder's page refuses
Two checks in that list are easy to test wrongly

The identical response. A code that never existed and a code that was revoked must produce the same answer, with the same wording and roughly the same timing. If they differ, anyone can work out which codes are real by trying them — and that turns a huge code space into a guessing game with feedback. Check the wording, and ask the technical founder whether the timings match too.

The paused-and-expired token. Five states get derived from three stored ones, in a fixed order of precedence: revoked, then expired, then used-up, then paused, then active. Paused deliberately comes last of those four, because a token that is paused and expired showing “Paused” offers the user a Resume button that would achieve nothing. Construct one on purpose and look at it.

3 · Test on the phones people actually have

  • A low-end Android, two or three years old, with a full storage bar and forty other apps installed. Not a flagship. This is what most of your users have, and it is where the app will be slow, drop the camera, or get killed in the background.
  • A slow connection. Throttle it, or go somewhere with two bars. Watch what the app does while waiting — a spinner with no timeout is a hang.
  • Offline. Airplane mode, then use the app. Then come back online and check nothing was lost or duplicated.
  • Interrupted. A real phone call arrives mid-token-creation. Battery saver kicks in during a voice call. The app is backgrounded for an hour.
  • The holder page on old browsers. The holder does not choose your app; they use whatever browser their phone came with. Test the default browser on an old Android, and an older iOS Safari. This half of the product has no install step and therefore no minimum version.

4 · Hindi and accessibility

Hindi rendering

Check every screen, not the two you translated first. What breaks:

  • Hindi text is longer than English. Buttons wrap, labels truncate, tab bars overflow.
  • Devanagari needs more vertical space; fixed-height rows clip the top of characters.
  • Numbers, times and dates inside translated sentences.
  • Anything built by joining fragments together will produce nonsense in Hindi even when each fragment is correct.
  • The consent notice and the deletion page above all. Those two are where a translation failure is a legal problem, not a cosmetic one.

Accessibility

CheckHow
Touch targetsEvery tappable thing comfortably hittable with a thumb. Swipe-to-revoke needs a visible alternative
ContrastText against its background, in both light and dark themes. The state badges especially — they carry meaning by colour
Screen readerTurn on TalkBack or VoiceOver and complete the three key flows: issue, redeem, revoke
Meaning not carried by colour aloneA revoked token must say “Revoked”, not merely be red
Large textSet the system font to its largest and look for clipping

5 · The guarantees that must be re-proved every release

Three behaviours are promises rather than features. Re-test them on every build that touches them, and keep the results — they are your store evidence.

  1. Revoke is genuinely irreversible in the built app. Revoke, then try everything: reopen, resume, restart, sign out and in, restore from a backup of the phone. If any path brings it back, the promise is false.
  2. A block follows the person across tokens. The test script in lesson 0006, including the different-browser step.
  3. Every destructive confirmation behaves as specified. Revoke, delete account, remove a device. Each must be hard to do by accident and must say what it will destroy — and must not be so hard that it becomes a retention maze, which is the dark-pattern problem in lesson 0013.

6 · The release gate

PRE-RELEASE SMOKE TEST -- 15 minutes, every build

[ ] Fresh install, sign up, display name, first token
[ ] Redeem it in a browser, message each way
[ ] Revoke; the page refuses
[ ] Report and block, from both sides
[ ] Deletion page loads

RELEASE APPROVAL -- who signs off

[ ] Smoke test passed, on a real low-end device
[ ] The three guarantees in section 5 re-proved
[ ] Anything touching data: privacy policy, RoPA and BOTH
    store declarations reviewed
[ ] Help content reviewed for anything that changed
[ ] Crash-free rate from the previous release is acceptable
[ ] Named person signs off. One name, written down
  • Crash reporting review — look at it weekly, not only after a release. A crash that affects 2% of sessions will not be reported by anyone; it will just quietly cost you those users.
  • Force-upgrade policy — decide in advance what justifies forcing everyone onto a new version. A security fix or a privacy defect does; a redesign does not. Users hate it, and the mechanism has to exist before the day you need it.
  • 🔁 Post-release monitoring for 48 hours — crash rate, error volume, support inbox, and the activation number. Roll back or ship a fix rather than waiting to see.

What this costs you

  • Half a day per release, more when store declarations are involved.
  • Buying an old phone on purpose, and keeping it. Worth every rupee.
  • Being the person who says no. A release gate is only a gate if it has stopped something. Expect friction, and expect it with your co-founder.
  • Testing that feels wasteful — re-proving the same three guarantees every release. They are the promises, and a promise verified only once is a promise that was true once.
