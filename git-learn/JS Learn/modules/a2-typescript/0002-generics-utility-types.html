Generics & Utility Types

A2 — Lesson 2 of 3 ~45 min
Why this matters for Token

Your API returns paginated lists, wrapped responses, and partial updates. Generics let you type these patterns once — ApiResponse<Token[]>, Paginated<Message> — and reuse them across every endpoint without losing type safety. Utility types like Partial<Token> model the "update only the fields you're changing" pattern.

The problem generics solve

Imagine writing an API response wrapper. Without generics, you'd need a separate type for every endpoint:

// Without generics — repetitive and fragile
interface TokenResponse {
  data: Token;
  success: boolean;
  error?: string;
}

interface MessageResponse {
  data: Message;
  success: boolean;
  error?: string;
}

// For EVERY new type, you'd copy-paste this.
// 20 endpoints = 20 nearly-identical interfaces.

Generics — parameterized types

A generic is a type that takes a parameter — like a function takes arguments:

// One definition, works for any data type
interface ApiResponse<T> {
  data: T;
  success: boolean;
  error?: string;
}

// Now use it:
type TokenResponse = ApiResponse<Token>;
type MessageListResponse = ApiResponse<Message[]>;
type UserResponse = ApiResponse<{ id: string; name: string }>;

T is a placeholder. When you write ApiResponse<Token>, TypeScript replaces every T with Token. The result is fully typed.

Generic functions

// A function that works with any array type
function firstItem<T>(items: T[]): T | undefined {
  return items[0];
}

const firstToken = firstItem(['MERC-8GH2', 'KART-4KN9']);  // string
const firstCount = firstItem([3, 7, 12]);                    // number
// TypeScript infers T from the argument — no annotation needed at the call site.

Constraints — limiting what T can be

Sometimes T needs specific properties. Use extends to constrain:

interface HasId {
  id: string;
}

function findById<T extends HasId>(items: T[], id: string): T | undefined {
  return items.find(item => item.id === id);
}

// Works — Token has an id field
const token = findById(tokens, 'abc-123');

// Error — plain strings don't have an id property
// findById(['a', 'b'], 'a');  // TS Error!

Token's API patterns with generics

// Paginated responses
interface Paginated<T> {
  items: T[];
  cursor: string | null;
  hasMore: boolean;
}

// Every list endpoint returns this shape:
type TokenListResponse = ApiResponse<Paginated<Token>>;
type MessageListResponse = ApiResponse<Paginated<Message>>;

// The fetch function:
async function fetchPaginated<T>(
  url: string,
  cursor?: string
): Promise<Paginated<T>> {
  const params = cursor ? \`?cursor=\${cursor}\` : '';
  const res = await fetch(url + params);
  return res.json();
}

Built-in utility types

TypeScript ships with types that transform other types. The most useful for Token:

Partial<T> — all fields optional

interface Token {
  id: number;
  code: string;          // present ONLY in the reply to POST /tokens
  label: string;
  status: 'active' | 'paused' | 'revoked';
  maxUses: number | null;   // null = unlimited, 0 = none
}

// When updating a token, you only send the fields that changed:
type TokenUpdate = Partial<Token>;

// This is valid — only updating one field:
const update: TokenUpdate = { status: 'paused' };
Partial<T> makes fields optional, and optional is not nullable

Partial<Token> turns maxUses: number | null into maxUses?: number | null — which now has three states where the column had two, and the extra one is the whole point of a PATCH:

What you sendWhat the server must do
{ } — maxUses absentLeave it alone. This edit is not about that field
{ maxUses: null }Set it to unlimited. null is a value, and it is the one the user just chose
{ maxUses: 5 }Set it to five

Collapse the first two and "unlimited" becomes unsendable. A client that builds its PATCH body by dropping empty values — if (value) body[key] = value, or the slightly better-looking if (value != null) — can set a limit and can never remove one. The user unticks "limit uses", presses Save, the request succeeds, and the limit is still there. Nothing errors, so the bug is reported as "saving doesn't work sometimes".

This is the same distinction c5/0004 drew between gone and not fetched, and b1/0001 between NULL and ''. Here it has a name in the type system: ? means the key may be absent; | null means the value may be null. They are different questions and Partial<T> only answers the first.

Pick<T, Keys> — select specific fields

// The token list screen only needs these fields:
type TokenListItem = Pick<Token, 'id' | 'label' | 'status'>;

// Equivalent to: { id: number; label: string; status: TokenStatus }
Notice which field is not picked

Pick looks like a convenience — fewer fields over the wire, less to render. Here it is doing something stronger: GET /tokens returns no code field at all, and TokenListItem is where that becomes a compile error rather than a code review comment.

ADR-0007 returns a token code exactly once, in the reply to POST /tokens. After that the database holds only a hash for lookup and an encrypted copy for display, so serving codes in a list would mean decrypting every row on every scroll — and each of those is a deliberately logged event. A list shows the label and the state, which is what a list is for.

This is the useful habit with Pick and Omit: they are not only about payload size. A type that cannot hold a secret is a place the secret cannot leak from.

Omit<T, Keys> — exclude specific fields

// When creating a token, the server generates 'code' — don't include it:
type CreateTokenInput = Omit<Token, 'code' | 'status'>;

// Equivalent to: { label: string; maxUses: number | null }

Record<K, V> — typed dictionaries

// Map token status to a display color:
const statusColors: Record<TokenStatus, string> = {
  active: '#16a34a',
  paused: '#d97706',
  revoked: '#dc2626',
};
// If you add a new status to the union, TS forces you to add it here too.

Required<T> — all fields required

// Make every optional field mandatory (useful for database row types)
type TokenRow = Required<Token>;

Enums — named constants

// Const enum — inlined at compile time, zero runtime cost
const enum HttpStatus {
  OK = 200,
  Created = 201,
  BadRequest = 400,
  Unauthorized = 401,
  Forbidden = 403,
  NotFound = 404,
}

function handleResponse(status: HttpStatus) {
  if (status === HttpStatus.Unauthorized) {
    // refresh token...
  }
}

For Token status, prefer the string literal union ('active' | 'paused' | 'revoked') over an enum — it's simpler, JSON-serializable, and readable in logs.

Now build it yourself

The types file is declarations and is erased before anything runs. What survives compilation is the function that builds the object those types describe — and Partial<T> is a promise about a shape that something has to actually construct.
