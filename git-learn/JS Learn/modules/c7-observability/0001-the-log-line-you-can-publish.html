The Log Line You Can Publish

C7 — Lesson 1 of 4  |  ~50 min

Why this matters for Token

A log line is the most widely copied artefact any company produces. It gets pasted into chat, attached to tickets, screenshotted, shipped to a collector, and read by whoever is awake. Write logs as though they will be published, because in practice most of them are.

Token has one field that must never appear in one. A token code is a working credential: anyone holding it can redeem it, and it stays valid until the token is revoked. The database does not even store it in the clear — ADR-0007 keeps a peppered hash and an encrypted copy precisely so that reading the table gives you nothing. Putting it in a log undoes all of that with one string concatenation.

This is not hypothetical. A sweep on 2026-08-23 found it in three lessons at once, including the one whose own callout forbids it.

1 · Structured, because you will need to search it

A log line built by concatenation is readable by a person and useless to a machine:

console.log("redeem failed for token " + id + " after " + ms + "ms");

You cannot ask that "how many redemptions failed in the last hour" without writing a parser for your own prose. The structured version is the same information as fields:

log.warn({ event: "redeem_failed", requestId, tokenId: id, durationMs: ms });

Now it is queryable, and — the part that matters here — every value has a name, so a rule can be written about names. That is what makes the rest of this lesson possible at all; you cannot allow-list a sentence.

2 · An allow-list, not a redaction list

The obvious way to keep a secret out of a log is to remove it:

const safe = { ...fields };
delete safe.code;
delete safe.password;      // there are no passwords in Token, but the habit arrives anyway
log.info(safe);

This is the same shape as the sanitiser in C3/0001 and it is wrong for the same reason: it removes the fields you thought of, on the day you wrote it, and passes everything a future caller adds. The allow-list inverts the default:

const ALLOWED = ["event", "tokenId", "conversationId", "durationMs", "outcome"];
const line = {};
for (const name of ALLOWED) {
  if (Object.prototype.hasOwnProperty.call(fields, name)) line[name] = fields[name];
}

Note what that loop iterates. Walking ALLOWED rather than fields is what makes an invented field unreachable rather than merely unwanted — there is no path through the code by which it can be copied.

3 · Log the id, never the code

The replacement for a code in a log is the row's id. It has exactly the property an identifier in a log should have:

  • It identifies the row for anybody who can already query the database.
  • It is worth nothing to anybody who cannot. An id is not a credential; possessing it grants no access to anything.
The dangerous line is the one with nothing to put in it

At “redemption attempt” the token has not been found yet, so there is no id — and the pull towards writing something identifying is exactly how the code got into three lessons at once. There is a real question being answered (“which request was this?”) and the honest answer to it is requestId.

A request id is enough on its own, and it is enough deliberately. It ties every line of one request together, it survives across services, and it identifies precisely nothing about a person. When there is nothing safe to add, adding nothing is the answer.

4 · The field that is dangerous at any depth

Here is where a top-level allow-list stops being sufficient. Suppose token is on the list, because logging the token is obviously useful:

log.info({ event: "redeem_ok", requestId, token: tokenRow });

tokenRow came from the database or from a service layer, and one of its properties is code. The allow-list allowed the container; nobody allowed what was inside it. The line is emitted, the code is in it, and every review of the allow-list will keep saying it looks fine — because it does.

Two defences, and you want both:

  • Log scalars, not objects. Pass tokenId: token.id rather than token. This is the fix, and it is a discipline — which means it holds until somebody is in a hurry.
  • A tripwire on the way out. Token codes have a known shape: twelve characters from a 31-letter alphabet, in three groups of four. That is specific enough to detect, so the logger can walk what it is about to emit and refuse anything containing one.
Why a tripwire earns its keep even though the discipline is the real fix

A structural rule and a value-shaped rule fail in different ways, which is exactly why running both is worth the duplication. The allow-list cannot see inside an allowed object. The tripwire cannot see a code that has been mangled, encoded or split across two fields. Neither is sufficient and their blind spots do not overlap.

State the tripwire's limit honestly rather than trusting it: it catches a well-formed code, which is the case that actually happens, because the code got there by being copied rather than by being transformed.

5 · What a dropped field is worth

A field that did not survive the allow-list should be reported, not silently discarded. Not in the log line itself — that would put the value back — but as a count or a list of names.

The reason is the same one that gave every exclusion in C3/0001 a reason. A caller repeatedly trying to log code is a bug somebody needs to fix, and it is invisible if the logger quietly does the right thing. The safe behaviour and the visible behaviour are different requirements, and doing only the first is how a defect survives for months.
