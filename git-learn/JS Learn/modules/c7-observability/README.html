Observability

Track C

Phase 3 — 4 lessons  |  extends B9, because a deployment you cannot see is a deployment you cannot operate

Module goal

B9 gets Token running on a box. This module is about being able to answer questions about it afterwards — is it up, is it slow, what broke, and who do we wake.

And it is the module where Token's privacy promises meet the tools that habitually break them. An error tracker attaches request bodies by default. A metrics label per user is a behavioural record. A log line is the most-shared artefact in any company. Every one of those is a sensible default somewhere else and a leak here.

Lessons

  1. The Log Line You Can Publish — structured logs, an allow-list rather than a redaction list, and the field that is dangerous at any depth
  2. Errors, and the Body the Tracker Attaches by Default — self-hosted error tracking, grouping, and mapping a crash back to a commit
  3. Metrics That Answer a Question — the few worth watching, why a label per user is both a bill and a privacy problem, and the TURN bandwidth line that has to be watched from the first deploy
  4. Alerts, and the Page Nobody Answers — symptom over cause, page versus ticket, runbooks, and on-call arithmetic for a company of two
Everything here is self-hosted, and that is a constraint not a preference

Token's telemetry describes a privacy product's users. Sending it to a hosted service moves that description onto somebody else's disk, which is the same objection that rules out the third-party comms SDKs.

The cost is real and is not hidden: you now operate the thing that watches the thing. A self-hosted error tracker is another container, another database, another backup, and its own opportunity to go down at the worst moment.

What you'll build

  • buildLogLine(fields, allow, config) — the log line assembled from a list of permitted fields rather than filtered down from everything, with a tripwire that refuses to emit anything shaped like a token code however deeply it is buried

What this module does not repeat

X2/0002 covers the debugger, breakpoints and reading a stack trace — the tools you reach for when you already know something is wrong and can reproduce it. This module is about the part before that: knowing something is wrong at all, on a machine you are not sitting at, for a request that happened twenty minutes ago.

Prerequisites

  • B9 — Docker & Deployment — there has to be something deployed to observe
  • C2 — CI/CD & Release Engineering — a crash report is only useful if the build it names can be mapped to a commit
