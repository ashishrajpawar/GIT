Errors, and the Body the Tracker Attaches by Default

C7 — Lesson 2 of 4  |  ~50 min

Why this matters for Token

ADR-0007 moved the token code out of the URL and into the request body. A path reaches the proxy's access log, browser history, Referer and crash reports, so POST /api/redeem takes { code } in the body instead.

An error tracker attaches the request body by default. Install it, deploy, and the first failed redemption sends that code to the very place the decision was made to keep it out of — a crash report. The library is not misbehaving; attaching the body is the right default almost everywhere, which is exactly why nobody notices it here.

A default that is sensible in general and wrong for you is the hardest kind to catch, because there is no error, no warning, and a review of your own code shows nothing at all.

1 · What a tracker gives you that a log does not

Logs are a stream. A tracker is a set of issues, and the difference is grouping:

  • Ten thousand occurrences of one bug are one issue with a count, rather than ten thousand lines to scroll past.
  • First seen, last seen, and which release it started in.
  • A stack trace, mapped back through source maps to the line you actually wrote.
  • Context — the request, the environment, the breadcrumbs leading up to it.

That last one is the useful bit and the dangerous bit, and they are the same feature.

Self-hosted, and what it costs

Token's crash reports describe a privacy product's users at the moment things went wrong. Sending them to a hosted service puts that on somebody else's disk, which is the objection that rules out the third-party comms SDKs. So: a self-hosted tracker, open source, on the same VPS.

You now operate the thing that watches the thing. Another container, another database, another backup, and a real chance it is down at the exact moment you need it — which is a reason to keep logs working independently rather than routing everything through one system.

2 · Grouping, and the message that creates an issue per user

A tracker groups by a fingerprint, and by default the fingerprint comes from the error type and the stack trace — with the message contributing. So this is fine:

throw new NotFoundError("token not found");

and this quietly destroys the tool:

throw new NotFoundError(`token ${id} not found for user ${userId}`);

Every distinct pair of ids is a different message and therefore a different issue. One bug becomes forty thousand issues, the dashboard is unreadable, and the alert that should have said “this is happening 40,000 times an hour” says “a new issue” forty thousand times.

The rule that falls out: the message identifies the kind of failure; the fields identify the instance. Exactly the split structured logging asks for in the previous lesson, arriving from a different direction.

3 · Normalising a message, and the order that matters

You do not always control the message. A driver error, a validation library, somebody else's thrown string — all arrive with values already baked in. So the last thing before sending normalises it: replace the varying parts with placeholders, and group on the result.

4 · The request, rebuilt rather than filtered

The tracker wants to attach the request. Give it one you constructed:

  • Method and URL — safe, and safe because ADR-0007 keeps codes out of paths. If codes were still in the URL this field would be the leak instead.
  • Headers, allow-listed — and header names are case-insensitive over the wire, so the comparison has to be too. Authorization and Cookie are the obvious ones to keep out, and an allow-list keeps out the ones you have not thought of yet.
  • The body: never. Not filtered, not redacted, not truncated — absent. It is where the code lives by design, and a body you are carefully redacting is one redaction bug away from the thing you moved it there to avoid.

5 · Not everything that fails is an error

A redemption of a dead code returns the same refusal whatever killed it — revoked, expired, exhausted, never existed (ADR-0010). That is the product working exactly as designed, and it will happen constantly.

Send those to the tracker and the tracker fills with them. Then the same thing happens that happened to this course's own audit: everybody learns that the dashboard is noise, and the real error arrives in a list nobody opens. A tracker full of expected failures is a tracker nobody reads, which is worse than not having one, because it occupies the space where a working one would go.

Try it yourself — broken on purpose

Read the error. It happens for every failure that did not come from a request.

6 · Stamp the release, or the stack trace is decoration

C2/0004 made the point from the release side: a crash report naming a build you cannot map to a revision is a crash you cannot fix. From this side it means every event carries a release, and a build with no release attached still gets sent — tagged unknown, visibly, rather than dropped or silently blank.

Visibly is the point. An unknown release on a dashboard is a question somebody will eventually ask; an empty field is one nobody notices.
