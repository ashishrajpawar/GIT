Reporting Without Reading

C3 — Lesson 1 of 3  |  ~50 min

Why this matters for Token

Both app stores require a working way to report objectionable content. A review fails without one, so this is not a feature that can wait.

And Token cannot build the normal version of it. The usual report button sends a message id to a server that looks the message up and shows it to a moderator. Token's server holds ciphertext and no key — there is nothing to look up and nothing to show. The row is there and it is unreadable, by design, and that is the guarantee the whole product is sold on.

So the report has to be assembled somewhere else: on the reporter's own device, which is the one place the message exists in the clear. Everything awkward about this lesson comes from that one relocation.

1 · The report is built by the reporter, not fetched by the server

When a user reports a message, their phone decrypts what it already has and sends a package:

  • The plaintext of the reported message.
  • The sender's public key and the message signature, so authorship can be proved.
  • Whatever surrounding context the reporter chooses to include.
  • The token the sender redeemed, and its redemption record — by id.

Nothing about the server changed. It did not gain the ability to decrypt anything; a user voluntarily disclosed one conversation they were already part of. This is how Signal and WhatsApp do it, and it is a solved problem — with one condition attached that is easy to miss and impossible to fix later.

The signature has to be in the message format from v1

A signature cannot be added retroactively to a message that has already been sent. If the format ships without one, then every message in existence when you finally build reporting is unverifiable — not merely inconvenient to check, permanently unverifiable, because the evidence that would have proved authorship was never created.

This is the same shape as the version endpoint in C2/0004 and the key backup in C5: a mechanism added after the fact does not reach what predates it. The difference is that here the thing that predates it is every message anyone has ever sent.

2 · The author field is a claim until the signature makes it a fact

This is the part that decides the whole design, so it is worth being blunt about. The report arrives as JSON that the reporter's client constructed:

{
  "reportedUserId": 4102,
  "items": [
    { "messageId": 88, "authorId": 4102, "keyVersion": 2,
      "plaintext": "...", "signature": "..." }
  ]
}

authorId: 4102 is not evidence of anything. It is a number a client put in a field, and a modified client can put any number there. Without a signature check, the report mechanism is a way to have anyone you like suspended by typing their id into a form.

The signature is what converts it. Verified against the public key the directory held for that user at that version, it says: this exact text was signed by the holder of that private key. Which is why the checks have to run in a particular order.

3 · The order of the checks, and why it is not arbitrary

Each item in a report goes through three gates, and they have to run in this order:

#GateExcluded as
1Does the directory hold that author's key at that version?unknown_key
2Does the signature verify against it?bad_signature
3Is the author one of the two parties this report is about?third_party

Gate 1 before gate 2 is obvious once said: with no key there is nothing to verify against, and calling a verifier with undefined either throws or, worse, returns something.

Gate 2 before gate 3 is the interesting one. Gate 3 asks a question about the author — is this person party to the conversation? — and until the signature verifies, the author field is a lie you have not caught yet. Checking it first means reasoning about an attribute of a claim rather than of a fact. Get the order wrong and a forged item attributed to an uninvolved stranger is reported as "a message from a third party", which sounds like a filing mistake, when what actually happened is that somebody tried to fabricate evidence.

Why an exclusion carries a reason at all

A dropped item and a dropped item are not the same thing. unknown_key usually means a client bug or an old message; bad_signature means either data corruption or somebody attempting a fabrication, and those two go to different places. A pipeline that silently discards what it cannot use throws away the most interesting signal it will ever receive.

4 · The reporter's own messages are context, not evidence

A report of one line is usually unreadable. “Fine, send it” means nothing without what came before, so the reporter picks a few surrounding messages — and some of those are their own.

Those belong in the package and are not evidence against anyone. Keeping them in a separate role does two jobs: a reviewer can see at a glance which lines are being complained about, and a report that turns out to contain only the reporter's own messages is recognisably a report of nothing rather than a mysterious empty one.

And a report of nothing is still recorded

It is tempting to discard a report with no usable evidence. Do not. A pattern of reports is itself one of the few abuse signals available to a system that cannot read content — a reporter who files repeatedly against different people, with nothing in any of them, is the clearest thing you will see all week.

So the verdict is actionable: false, and the row is written anyway. That distinction — cannot be acted on versus should be forgotten — recurs in ADR-0011, where the reporter who repeatedly triggers automatic suspensions is himself the signal.

5 · What comes out is built key by key

The client sends an object. The server does not store that object — it builds a new one from the fields it wants:

// Yes. Nothing arrives that is not named here.
admitted.push({
  messageId: item.messageId,
  authorId: item.authorId,
  role: role,
  plaintext: item.plaintext
});

// No. This keeps whatever the client happened to send.
const copy = Object.assign({}, item);
delete copy.signature;
admitted.push(copy);

The second version is wrong even though it looks careful, and the reason is general: the absence of one dangerous field is not evidence of an allow-list. It removes the fields you thought of, on the day you wrote it, and passes everything a future client version adds.

Token has a specific field in mind here. A report is about a token, and the token is referred to by id — never by its code. Codes never go in a log, and a report ends up in a review queue, an export and probably an email. A client that helpfully attaches code to each item should find it has gone nowhere.
