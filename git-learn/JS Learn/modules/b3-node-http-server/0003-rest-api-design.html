REST API Design

B3 — Lesson 3 of 4 ~45 min
Why this matters for Token

Token's API serves two clients — the mobile app and the redemption web page. Both need a predictable, consistent interface. REST conventions mean your app developer (you) always knows what URL to call, what method to use, what the response looks like, and what status code to expect. No guesswork, no documentation lookups mid-coding.

REST fundamentals

REST maps resources (nouns) to URLs and HTTP methods (verbs):

Action Method URL Body
List tokens GET /api/tokens —
Get one token GET /api/tokens/:id —
Create token POST /api/tokens JSON
Update token PATCH /api/tokens/:id JSON (partial)
Revoke token POST /api/tokens/:id/revoke —

Status codes — what they mean

// Success
200 OK              — request succeeded, here's the data
201 Created         — resource created (POST)
204 No Content     — success but no body to return (DELETE)

// Client errors
400 Bad Request    — invalid input (missing field, wrong format)
401 Unauthorized   — no auth or expired token
403 Forbidden      — authenticated but not allowed (not your token)
404 Not Found      — resource doesn't exist
409 Conflict       — duplicate (e.g. token code already exists)
422 Unprocessable  — input is well-formed JSON but fails validation
429 Too Many Requests — rate limited

// Server errors
500 Internal Server Error — something broke on our end

Token API — full endpoint design

Tokens (authenticated — requires JWT)

GET    /api/tokens             — list user's tokens (paginated)
GET    /api/tokens/:id         — get token details + rules
GET    /api/tokens/:id/code    — reveal the code again (decrypts, logs)
POST   /api/tokens             — create a new token
PATCH  /api/tokens/:id         — update label, max_uses, rules
POST   /api/tokens/:id/revoke  — revoke a token
POST   /api/tokens/:id/pause   — pause a token
POST   /api/tokens/:id/resume  — resume a paused token

Note what is not in those URLs: the token code. These are addressed by database id. The reason is in Why this way below, and it is the most Token-specific decision in this lesson.

Redemption (public — no auth required)

POST   /api/redeem             — redeem a token; the code goes in the JSON body
POST   /api/redeem/check       — is this code usable? code in the body

The holder does have to send the code — they have nothing else. It travels in the request body rather than the path, which keeps it out of every log line and every browser history entry between them and the server.

Messages (authenticated)

GET    /api/conversations            — list conversations (inbox)
GET    /api/conversations/:id        — get messages (paginated)
POST   /api/conversations/:id/read   — mark as read

Response envelope

All responses follow the same shape — your TypeScript ApiResponse<T> from the shared types:

// Success
{
  "data": { ... },       // the actual result
  "success": true
}

// Error
{
  "error": "Token not found",
  "success": false
}

// List with pagination
{
  "data": {
    "items": [...],
    "cursor": "eyJpZCI6NDJ9",
    "hasMore": true
  },
  "success": true
}

Pagination — cursor-based

Token uses cursor-based pagination (not page numbers). Why: page numbers break when items are added/removed between requests. Cursors always point to a stable position.

// Client request:
GET /api/tokens?limit=20
GET /api/tokens?limit=20&cursor=eyJpZCI6NDJ9  // next page

// Server implementation:
router.get('/', async (req, res, next) => {
  try {
    const limit = Math.min(parseInt(req.query.limit || '20', 10), 100);
    const cursor = req.query.cursor
      ? JSON.parse(Buffer.from(req.query.cursor, 'base64url').toString())
      : null;

    // Never SELECT * on a list. This table holds code_hash and code_enc,
    // and both would go straight into the JSON below. ADR-0007: a list
    // returns no code field at all, in any form.
    let query = `SELECT id, label, status, max_uses, expires_at, created_at
                   FROM tokens WHERE user_id = $1`;
    const params = [req.user.id];

    if (cursor) {
      query += ' AND id < $2';
      params.push(cursor.id);
    }

    query += ' ORDER BY id DESC LIMIT $' + (params.length + 1);
    params.push(limit + 1);  // fetch one extra to know if there's more

    const { rows } = await pool.query(query, params);
    const hasMore = rows.length > limit;
    const items = hasMore ? rows.slice(0, -1) : rows;
    const nextCursor = hasMore
      ? Buffer.from(JSON.stringify({ id: items[items.length - 1].id })).toString('base64url')
      : null;

    res.json({
      data: { items, cursor: nextCursor, hasMore },
      success: true,
    });
  } catch (err) { next(err); }
});
SELECT * is a list endpoint's most common leak

The version of this query that shipped said SELECT * FROM tokens, and it was fine right up until b2/0001 added code_hash and code_enc to that table. From that moment the list endpoint was returning both to the client, in every page, forever — and nothing would have failed.

That is what makes SELECT * different from ordinary laziness: it is a promise to return whatever a future migration adds. The person who adds a column is not looking at this file, and the person who wrote this file is not there when they do.

Naming the columns turns a schema change into a compile-or-review question rather than a silent one. It costs a line and it is the only version that is safe to leave alone for a year.

code_enc being encrypted is not a defence worth leaning on either. It is a ciphertext of a live capability, sent to a client that never needs it, over and over — and its safety then depends entirely on a key that has to stay secret for as long as any of those responses might still exist in a log or a cache.

Consistent error responses

// api/src/utils/api-error.ts
export class ApiError extends Error {
  status: number;

  constructor(status: number, message: string) {
    super(message);
    this.status = status;
  }

  static badRequest(msg: string) { return new ApiError(400, msg); }
  static unauthorized(msg = 'Authentication required') { return new ApiError(401, msg); }
  static forbidden(msg = 'Access denied') { return new ApiError(403, msg); }
  static notFound(msg = 'Not found') { return new ApiError(404, msg); }
  static conflict(msg: string) { return new ApiError(409, msg); }
}

// Usage in routes:
import { ApiError } from '../utils/api-error.js';

router.get('/:id', async (req, res, next) => {
  try {
    const token = await getTokenById(req.params.id);
    if (!token) throw ApiError.notFound('Token not found');
    if (token.user_id !== req.user.id) throw ApiError.forbidden();
    res.json({ data: token, success: true });
  } catch (err) { next(err); }
});

API versioning

For Token v1, prefix all routes with /api. If you ever need breaking changes, add a version: /api/v2/tokens. The v1 routes keep working for existing clients.

Don't over-plan versioning. Start with /api/ and version only when you need to break compatibility.

Why this way (and what was rejected)

Addressed by id, because a code in a URL is a capability in a log file

The obvious REST design is /api/tokens/MERC-8GH2-KP4X. The resource is the token, the code identifies it, and it reads beautifully. It was rejected, and this is the decision worth understanding because it is not about REST at all.

A URL is the least private part of a request. The path is written down, repeatedly, by things you do not control:

  • the reverse proxy's access log, in plain text, rotated to disk
  • the browser's history and address bar, on a shared or borrowed device
  • the Referer header sent to any third party the next page loads
  • crash reporters and APM traces, which capture the URL by default and the body almost never
  • a CDN or WAF in front of the API, keeping its own logs elsewhere

Bodies get none of that treatment. Nothing logs a POST body by default, because bodies are assumed to hold the sensitive part.

This is the same decision as ADR-0007, one layer up

The database deliberately does not store the code — only a hash for lookup and an encrypted copy for display. Putting the code in the URL path would write it, in plain text, into the web server's access log on the same machine. The care taken at the database would be undone by the routing table.

So owner-facing endpoints take :id, which is meaningless without the account it belongs to. The redemption endpoints take the code in a POST body, because the holder genuinely has nothing else to identify themselves with. The redemption page is still tokn.app/t/CODE — a person has to be able to type it — but the page reads the code from the path and sends it onward in a body.

POST /revoke, not DELETE

DELETE /api/tokens/:id is the conventional REST answer and it is the wrong shape here. Revocation does not remove the token: the row stays, revoked_at is set, and every redemption attempt after it is recorded against that row. That history is the point — it is how an owner sees that someone kept trying after being cut off.

A method whose name means "remove this" describing an operation that deliberately keeps everything invites exactly one bug: someone implementing it later writes the DELETE the verb promised. POST /revoke also sits consistently beside /pause and /resume, which are the same kind of state change and could never have been methods.

Cursors, not page numbers

?page=2 is computed as OFFSET 20, and offset means "count twenty rows and throw them away". Two consequences: it gets slower the deeper you go, because the database still walks the rows it discards; and it is wrong under writes. Issue a token while the user is reading page 1 and everything shifts down one — the first row of page 2 is the row they already saw, and one row is skipped entirely.

A cursor says "everything after id 42", which stays true no matter what was inserted. Same query plan at page 1 and page 100.

The envelope, and the part of it that is redundant

{ data, success } earns its place on the error path: every failure has the same shape, so the client has one place that reads error rather than a guess per endpoint.

Be honest that success itself carries no information the status line does not. It is kept for one reason — the client's fetch wrapper checks a single field rather than a range of status codes — and that is a defensible choice, not a free one. If it ever disagrees with the status code, the status code is right.

When this breaks

403 tells a stranger the token exists

This is in the code above and it is the sharpest bug in the lesson: 

if (!token) throw ApiError.notFound('Token not found');
if (token.user_id !== req.user.id) throw ApiError.forbidden();   // leaks

Two different answers for "does not exist" and "exists but is not yours" is an oracle. Any authenticated account can walk ids and learn exactly which ones are real tokens on the platform. It is the enumeration problem from error handling, wearing a status code instead of a message.

A resource you are not allowed to see does not exist. Scope the query by owner and return 404 for both cases: 

const { rows } = await pool.query(
  'SELECT * FROM tokens WHERE id = $1 AND user_id = $2',
  [req.params.id, req.user.id]
);
if (!rows[0]) throw ApiError.notFound('Token not found');

403 is still the right answer when the client already knows the resource exists — a shared conversation, a team object. It is wrong whenever knowing a thing exists is itself the information.

A malformed cursor is a 500

const cursor = req.query.cursor
  ? JSON.parse(Buffer.from(req.query.cursor, 'base64url').toString())
  : null;

That line takes a string from a stranger and runs JSON.parse on it. ?cursor=hello throws, the error reaches the handler, and the response is 500 — the status code that means "we have a bug". Bad input from a client is a 400, and the difference matters when you are looking at a graph of 500s trying to work out whether production is on fire.

There is a second half: even valid JSON is not a valid cursor. {"id":"abc"} parses, reaches id < $2, and Postgres rejects the comparison — another 500. The cursor is untrusted input and needs the same validation as a request body.

PATCH cannot express "clear this field"

COALESCE($1, label) means "if the client sent null, keep the old value". So a client that wants to remove a token's expiry by sending {"expires_at": null} gets nothing — silently. Omitting a field and setting it to null are indistinguishable once the body is parsed into an object.

Either document that null means "no change" and provide a separate way to clear (POST /tokens/:id/expiry/clear), or check 'expires_at' in req.body to tell absent from null. What does not work is leaving it ambiguous and finding out from a bug report.

The generated code in the exercise is not a Token code

The solution below originally built codes with randomBytes(9).toString('base64url').toUpperCase(). Base64url is A-Z a-z 0-9 - _; upper-casing it yields 0, O, 1, I, L, underscores and hyphens in the middle of groups. Every code it produced was one the rest of the system rejects. Generation belongs in one place — B7's engine — and every other lesson should import it rather than write a fourth version.

What this costs you

DecisionWhat you pay
Ids in URLs, not codes The client has to hold ids, and a URL is no longer something a human can construct or read. Support conversations get harder: "which token?" is answered with a label, never a URL.
Cursor pagination No "page 5 of 20", no total count, and no jumping. Getting a count means a second query that gets slower as the table grows — which is why most APIs that show totals stop showing them eventually.
The response envelope Every response carries a wrapper the client must unwrap, and every endpoint must remember to use it. One forgotten res.json(rows) and a client parsing body.data gets undefined.
404 instead of 403 Your own debugging gets harder — "not found" no longer distinguishes a typo in an id from a permissions bug. Log the real reason server-side; the response stays vague.
/api with no version Cheap now, and the day a breaking change is needed you run two route trees at once. The alternative — versioning from day one — costs a path segment and a duplicated router for a break that may never come.
