Input Validation & Error Handling

B3 — Lesson 4 of 4 ~50 min
Why this matters for Token

Every request to your API comes from the internet. Attackers send malformed data, SQL injection attempts, and garbage payloads. Your API must reject invalid input immediately — before it reaches the database, before it corrupts state, before it exposes errors that leak your schema. Validation is the security boundary between the outside world and your system.

The principle: never trust client input

Even your own mobile app can send bad data (stale cache, network corruption, bugs). The API must validate independently:

  • Type — is it actually a string/number/array?
  • Required fields — are all mandatory fields present?
  • Format — is the email valid? Is the date ISO format?
  • Range — is maxUses at least 1? (0 would be a token nobody can use)
  • Length — is the label under 200 characters?

Zod — schema validation for TypeScript

Zod defines validation schemas that also give you TypeScript types. One schema, shared between client and server:

npm install zod
// shared/schemas/tokens.ts
import { z } from 'zod';

export const createTokenSchema = z.object({
  label: z.string().min(1).max(200),
  // null means unlimited. 0 would be a token nobody can ever use, which
  // is never what anyone meant - so the schema refuses it rather than
  // letting the engine reject it later.
  maxUses: z.number().int().min(1).max(10000).nullable().default(null),
  expiresAt: z.string().datetime().optional(),
});

// TypeScript type derived from the schema (no duplication!)
export type CreateTokenInput = z.infer<typeof createTokenSchema>;
// = { label: string; maxUses: number | null; expiresAt?: string }

The same schema works on both the client (form validation) and server (API validation). Define once in shared/, import everywhere.

Using Zod in route handlers

import { createTokenSchema } from '@token/shared/schemas/tokens.js';
import { ApiError } from '../utils/api-error.js';

router.post('/', async (req, res, next) => {
  try {
    // Validate and parse — throws ZodError if invalid
    const input = createTokenSchema.parse(req.body);
    // input is fully typed and validated at this point

    const token = await createToken(req.user.id, input);
    res.status(201).json({ data: token, success: true });
  } catch (err) {
    if (err instanceof z.ZodError) {
      return res.status(400).json({
        error: 'Validation failed',
        details: err.errors.map(e => ({
          field: e.path.join('.'),
          message: e.message,
        })),
        success: false,
      });
    }
    next(err);
  }
});

Validation middleware

Instead of repeating Zod parsing in every route, create a middleware:

// api/src/middleware/validate.ts
import { ZodSchema, ZodError } from 'zod';

export function validate(schema: ZodSchema) {
  return (req, res, next) => {
    try {
      req.body = schema.parse(req.body);
      next();
    } catch (err) {
      if (err instanceof ZodError) {
        return res.status(400).json({
          error: 'Validation failed',
          details: err.errors.map(e => ({
            field: e.path.join('.'),
            message: e.message,
          })),
          success: false,
        });
      }
      next(err);
    }
  };
}

// Usage:
import { validate } from '../middleware/validate.js';
import { createTokenSchema } from '@token/shared/schemas/tokens.js';

router.post('/', validate(createTokenSchema), async (req, res, next) => {
  // req.body is already validated and typed
  const token = await createToken(req.user.id, req.body);
  res.status(201).json({ data: token, success: true });
});

All of Token's validation schemas

// shared/schemas/tokens.ts
import { z } from 'zod';

export const createTokenSchema = z.object({
  label: z.string().min(1, 'Label is required').max(200),
  maxUses: z.number().int().min(1).max(10000).nullable().default(null),
  expiresAt: z.string().datetime().optional(),
});

// PATCH: absent means "leave it alone", null means "clear it". Those are
// different instructions, and .optional() alone cannot tell them apart -
// see "When this breaks".
export const updateTokenSchema = z.object({
  label: z.string().min(1).max(200).optional(),
  maxUses: z.number().int().min(1).max(10000).nullable().optional(),
  expiresAt: z.string().datetime().nullable().optional(),
}).refine(data => Object.keys(data).length > 0, {
  message: 'At least one field must be provided',
});

// The redemption endpoint's only input, and the one that faces strangers.
// The alphabet lives in one constant; this is where it is enforced.
export const redeemSchema = z.object({
  code: z.string()
    .transform(v => v.trim().toUpperCase())
    .pipe(z.string().regex(
      /^[23456789ABCDEFGHJKMNPQRSTUVWXYZ]{4}(-[23456789ABCDEFGHJKMNPQRSTUVWXYZ]{4}){2}$/,
      'That code cannot be used.'          // same wording as every other denial
    )),
  holderName: z.string().min(1).max(80),
});

// Access rule payload schemas
export const timeWindowPayload = z.object({
  startHour: z.number().int().min(0).max(23),
  endHour: z.number().int().min(0).max(23),
  timezone: z.string().default('Asia/Kolkata'),
  days: z.array(z.number().int().min(0).max(6)).optional(),
});

export const callLimitPayload = z.object({
  maxPerDay: z.number().int().min(1).max(100),
  maxPerWeek: z.number().int().min(1).max(1000).optional(),
});

export const cooldownPayload = z.object({
  minutesBetweenContacts: z.number().int().min(1).max(60 * 24),
});

// A discriminated union, not z.record(z.unknown()). "Validated later in the
// service layer" means validated nowhere the day someone forgets - and the
// type system cannot help, because unknown accepts anything.
export const createRuleSchema = z.discriminatedUnion('ruleType', [
  z.object({ ruleType: z.literal('time_window'), payload: timeWindowPayload }),
  z.object({ ruleType: z.literal('call_limit'),  payload: callLimitPayload }),
  z.object({ ruleType: z.literal('cooldown'),    payload: cooldownPayload }),
]);

Error handling strategy

Token's error handling has three layers:

  1. Validation layer (Zod) — catches malformed input → 400
  2. Business logic layer (ApiError) — catches rule violations → 403, 404, 409
  3. Catch-all layer (error handler) — catches unexpected errors → 500
// api/src/middleware/error-handler.ts
import { ZodError } from 'zod';
import { ApiError } from '../utils/api-error.js';

export function errorHandler(err, req, res, next) {
  // Known validation errors
  if (err instanceof ZodError) {
    return res.status(400).json({
      error: 'Validation failed',
      details: err.errors.map(e => ({ field: e.path.join('.'), message: e.message })),
      success: false,
    });
  }

  // Known business errors
  if (err instanceof ApiError) {
    return res.status(err.status).json({
      error: err.message,
      success: false,
    });
  }

  // Unknown errors — log but don't expose internals
  console.error('Unhandled error:', err);
  res.status(500).json({
    error: process.env.NODE_ENV === 'development'
      ? err.message
      : 'Internal server error',
    success: false,
  });
}

Query parameter validation

// Validate query params (they're always strings from the URL)
// The cursor is base64url JSON that WE issued - and it still arrives from
// a stranger. Decoding it inside the schema means a malformed one is a 400
// from the validator, not a 500 from JSON.parse further down.
const cursorSchema = z.string().transform((raw, ctx) => {
  try {
    const parsed = JSON.parse(Buffer.from(raw, 'base64url').toString());
    if (typeof parsed?.id !== 'number') throw new Error('bad shape');
    return parsed as { id: number };
  } catch {
    ctx.addIssue({ code: z.ZodIssueCode.custom, message: 'Invalid cursor' });
    return z.NEVER;
  }
});

const paginationSchema = z.object({
  limit: z.coerce.number().int().min(1).max(100).default(20),
  cursor: cursorSchema.optional(),
  status: z.enum(['active', 'paused', 'revoked']).optional(),
});

router.get('/', async (req, res, next) => {
  try {
    const { limit, cursor, status } = paginationSchema.parse(req.query);
    // limit is now a number (coerced from string), validated
    // ...
  } catch (err) { next(err); }
});

z.coerce.number() converts the string "20" to the number 20 before validating. Query parameters are always strings from the URL.

Validate on the way in, escape on the way out

The tempting next step is "sanitize" — strip anything dangerous-looking out of the text before storing it: 

// Do NOT do this
function sanitize(input: string): string {
  return input.replace(/<[^>]*>/g, '').trim();
}

Two things are wrong with it, and the second is the serious one.

It does not work. That regex is a decade-old arms race that the regex loses; <img src=x onerror=… without a closing bracket, or a payload built from entities, walks straight past it. A filter that stops the examples you thought of is not a boundary, it is a speed bump you have chosen to trust.

It destroys data. A user whose label is Mum <3 gets Mum stored, permanently, and nobody finds out until they ask why. Input validation decides whether to accept a value. It should not quietly rewrite it.

The rule that does work has two halves, and they live in different places:

  • Validate on input — type, length, range, format. Reject what is wrong; store what is right, exactly as it was sent.
  • Escape on output, and escape for the specific place it is going. The escaping that makes text safe in HTML is not the escaping that makes it safe in a URL, a shell argument, a CSV cell, or an SQL string.

Which is why the same value needs no work in three of the four places Token sends it: React escapes text nodes, so Mum <3 renders correctly and inertly; parameterised queries ($1) mean the database never parses it as SQL; and JSON encoding handles the API response. The one place that needs deliberate care is anywhere you build HTML or a URL by hand.

And for messages, the server cannot sanitize even if it wanted to

Message bodies are encrypted before they leave the sender's device (ADR-0002). The server stores ciphertext and cannot read it, so there is no server-side filtering of message content — not as a policy choice, as a fact about the architecture. Anything that has to happen to message text happens on the device that decrypts it.

Why this way (and what was rejected)

One schema, in shared/, not two that agree

The alternative is validation written twice — a form check in the app and a separate check in the API. It is rejected for the obvious reason and one less obvious one. The obvious: two copies drift, and the drift is silent until a user hits it. The less obvious: the client's copy is not validation at all. It is a courtesy that saves a round trip. Anyone can send whatever they like straight to the API with curl, so the server's schema is the only one that is load bearing — the client's exists to make the form nicer.

Sharing one schema gets the courtesy for free and leaves exactly one definition to keep correct.

Parse, do not validate-then-use

schema.parse(req.body) returns a new, typed value, and the handler uses that rather than req.body. It sounds like a formality; it is the whole benefit. A validator that returns a boolean leaves you holding the same untyped object you started with, and nothing stops the next line reading a field nobody checked. A parser hands back a value whose type is proof it was checked.

Validation runs after rate limiting and auth, not before

Order the middleware by cost, cheapest first: rate limiter, then authentication, then validation, then the handler. Zod parsing a 200 KB body is real work, and doing it for a request that was going to be rejected as unauthenticated is work an attacker gets for free.

When this breaks

.optional() cannot express "clear this field"

This is the PATCH ambiguity from B3.3, and Zod does not solve it for you. Once { "expiresAt": null } has been parsed into an object, "the client sent null" and "the client did not send it" look identical to anything that checks for undefined.

So the schema allows .nullable().optional() — null is a legal, meaningful value — and the handler distinguishes the two cases with 'expiresAt' in req.body, which asks about the key rather than the value. Get this wrong and clearing an expiry silently does nothing, which is a bug report that will read "the app ignored me".

A validator that throws a 500

cursor: z.string().optional() looks like validation. It checks that a string is a string, and hands ?cursor=hello onward to JSON.parse, which throws, and the client sees 500 Internal Server Error — the code that means "we have a bug" — for a request that was simply malformed.

Anything that gets decoded, parsed or converted after validation is still unvalidated input. Doing the decode inside the schema, as above, is what makes the 400 come from the validator.

Error details describe your schema to strangers

{ "error": "Validation failed",
  "details": [{ "field": "holderName", "message": "String must contain at most 80 character(s)" }] }

Perfect for your own app's form. On the public redemption endpoint it hands an attacker your field names and limits for free. Keep the detailed shape for authenticated routes; on the public ones, return the message and nothing else — the same principle as the single denial message, applied to validation errors.

The 500 nobody can trace

console.error('Unhandled error:', err) writes to a log with no way back to the user who hit it. When someone writes in saying "it failed around 3pm", there is nothing to search for. A request id generated at the edge, returned in the error body and logged with the stack, turns that conversation into one grep. C7 builds it properly; the hole is worth seeing now.

What this costs you

DecisionWhat you pay
Zod schemas in shared/ A runtime dependency in the bundle that ships to phones, and every schema change is a change both clients import — which, since you cannot force an app update, means old builds keep sending the old shape. Schemas must stay permissive about extra fields and strict about the ones they know.
Parsing before the handler CPU on every request, including the ones you reject. Bounded by putting the limiter and auth in front, and by a body-size limit — Zod will happily try to parse 10 MB of JSON if Express hands it over.
Storing text exactly as sent Every consumer becomes responsible for escaping in its own context. That is correct, and it means a future non-React consumer — an email, a CSV export, a server-rendered page — is a new place to get it right rather than something the database already handled.
Discriminated unions for rule payloads Adding a rule type means touching the union, the payload schema and the engine — three places instead of one. In exchange the compiler will not let you forget the third.
