Node.js Fundamentals

B3 — Lesson 1 of 4 ~50 min
Why this matters for Token

Token's API server runs on Node.js — the same JavaScript you already know, but running on a server instead of in a browser. Node handles HTTP requests from your mobile app and web page, queries the database, manages WebSocket connections, and sends push notifications. Understanding how Node works under the hood prevents the most common server bugs.

What is Node.js?

Node.js is JavaScript running outside the browser. It uses the V8 engine (same as Chrome) but replaces browser APIs (DOM, window) with server APIs (filesystem, network, processes).

  • Browser JS: document, window, fetch, localStorage
  • Node JS: fs (filesystem), http (server), path, process, crypto
  • Both: console, setTimeout, Promise, JSON, Array, String

The event loop — Node's core concept

Node is single-threaded but handles thousands of concurrent connections. How? The event loop:

  1. Your code runs top-to-bottom
  2. When it hits an async operation (DB query, file read, network request), Node hands it off to the OS
  3. Node continues running other code (serving other requests)
  4. When the async operation completes, its callback is queued
  5. The event loop picks up the callback and runs it

This means: never block the event loop. A heavy CPU computation or synchronous file read blocks ALL other requests. Everything I/O must be async.

Modules — organizing code

Node uses modules to split code across files. Token uses ES modules (the modern standard):

// api/src/utils/token-code.ts
// Shown for the import/export shape. B7 replaces the body with
// crypto.randomBytes and rejection sampling.
export function generateTokenCode(prefix: string): string {
  const chars = '23456789ABCDEFGHJKMNPQRSTUVWXYZ';   // 31 - no 0, O, 1, I, L
  let code = '';
  for (let i = 0; i < 8; i++) {
    code += chars[Math.floor(Math.random() * chars.length)];
  }
  return `${prefix}-${code.slice(0, 4)}-${code.slice(4)}`;
}

// api/src/routes/tokens.ts
import { generateTokenCode } from '../utils/token-code.js';

To use ES modules, set "type": "module" in api/package.json.

Environment variables

Configuration that changes between environments (dev vs production) lives in environment variables — never hardcoded:

// Access via process.env
const port = process.env.PORT || 3000;
const dbUrl = process.env.DATABASE_URL || 'postgres://localhost:5432/token_dev';
const jwtSecret = process.env.JWT_SECRET;  // must be set, no fallback for secrets

if (!jwtSecret) {
  console.error('JWT_SECRET is required');
  process.exit(1);
}

Store them in a .env file (never committed to git):

# api/.env
PORT=3000
DATABASE_URL=postgres://localhost:5432/token_dev
JWT_SECRET=dev-secret-change-in-production

Load them with dotenv:

npm install dotenv
// api/src/server.ts — first line
import 'dotenv/config';
Check them all at startup, and check them properly

The snippet above checks one variable and exits. Real startup checks look at every required variable at once, for a reason worth knowing: a deploy that fails on JWT_SECRET, gets fixed, and then fails on DATABASE_URL is two outages instead of one. Report all of them together.

And if (!process.env.X) is not enough on its own. Three things that are all "set" and all useless:

  • JWT_SECRET= — present in the file, empty string. Common when someone comments out a value by deleting it.
  • JWT_SECRET=undefined — a template or a shell interpolated a missing value and wrote the word. process.env holds strings, so this is a perfectly good seven-character secret as far as any truthiness test is concerned.
  • JWT_SECRET=dev-secret-change-in-production — the value from the example .env three code blocks above, which is exactly how it reaches production.

ADR-0007 adds two more that must be checked here: TOKEN_CODE_PEPPER and TOKEN_CODE_KEY. Losing them makes every token ever issued permanently unusable, so a server that starts without them is a server quietly issuing codes it will never be able to verify.

Writing that check is the exercise at the bottom of this lesson.

The built-in http module

Node can create an HTTP server with zero dependencies:

import { createServer } from 'http';

const server = createServer((req, res) => {
  // req = incoming request (URL, method, headers, body)
  // res = your response (status code, headers, body)

  if (req.method === 'GET' && req.url === '/health') {
    res.writeHead(200, { 'Content-Type': 'application/json' });
    res.end(JSON.stringify({ status: 'ok' }));
    return;
  }

  res.writeHead(404);
  res.end('Not found');
});

server.listen(3000, () => {
  console.log('Server running on http://localhost:3000');
});

This works, but it's tedious for a real API. That's why we use Express or Fastify — they handle routing, parsing, and middleware. But understanding the raw http module helps when debugging.

Filesystem operations

import { readFile, writeFile } from 'fs/promises';
import { join } from 'path';

// Read a file (async — doesn't block)
const content = await readFile(join(process.cwd(), 'config.json'), 'utf8');
const config = JSON.parse(content);

// Write a file
await writeFile('output.json', JSON.stringify(data, null, 2));

For Token, you'll rarely read files at runtime — data lives in Postgres. But you'll use fs for migrations and configuration loading.

The process object

// Current working directory
console.log(process.cwd());

// Environment variables
console.log(process.env.NODE_ENV);

// Command line arguments
console.log(process.argv);  // ['node', 'script.js', ...args]

// Exit the process
process.exit(1);  // 1 = error, 0 = success

// Handle graceful shutdown
process.on('SIGTERM', () => {
  console.log('Shutting down...');
  server.close();
  pool.end();  // close DB connections
  process.exit(0);
});

Graceful shutdown is important for Token's production server — you want to finish serving active requests and close database connections cleanly before the process exits.

Crypto — secure random values

import { randomBytes, createHash } from 'crypto';

// Random bytes, and nothing clever done to them.
const sessionId = randomBytes(32).toString('hex');

// Hashing a code for lookup needs a server-side pepper -- see ADR-0007
// and b2/0001. A bare sha256 of a low-entropy input is not a one-way
// function in any useful sense; see the callout below.
function hashCode(code: string): string {
  return createHash('sha256')
    .update(code + process.env.TOKEN_CODE_PEPPER)
    .digest('hex');
}

Always use crypto.randomBytes for security-sensitive values (session IDs, nonces). Never use Math.random() — it's predictable.

Two things this section used to do, and why both were wrong

It generated token codes with base64url

The old version was randomBytes(9).toString('base64url').slice(0, 12).toUpperCase(), which looks careful — a CSPRNG, the right length, no Math.random() anywhere. It is broken twice.

It emits characters that are not in the alphabet. base64url is A–Z a–z 0–9 - _; upper-casing it leaves A–Z 0–9 - _. Token's alphabet is thirty-one characters — 23456789ABCDEFGHJKMNPQRSTUVWXYZ — with 0 O 1 I L excluded because they are unreadable off a label, and no punctuation at all. So this generator produces codes containing 0, 1, - and _, every one of which b2/0001's codeHashInput rejects. The server would be issuing codes its own validator refuses.

And .toUpperCase() throws away half the randomness. Nine random bytes are 72 bits. Case-folding maps a and A to the same character, so the output space collapses from 64 symbols to 38 — and the collapse is not uniform, because letters now arrive twice as often as digits. You cannot fix biased output by generating more of it.

The right generator is in 01/0013: draw a byte, discard it if it is 248 or higher, take the remainder mod 31. That is rejection sampling, and the discarding is what keeps every character equally likely. It is not in this lesson because this lesson is about Node's standard library, and the interesting part of code generation is not randomBytes.

It hashed a phone number with a bare sha256

A plain createHash('sha256').update(phone) reads like privacy and is not. A hash is only one-way if the input is unguessable, and an Indian mobile number is ten digits with a known prefix — a few billion candidates, which is minutes of work. Given the hash, you get the number back.

The same reasoning applies to token codes and is why hashCode above takes a pepper: 3112 is genuinely unguessable, but a pepper means an attacker who steals the database cannot even begin without also stealing an environment variable stored somewhere else.

The wider point for this product: if a column makes you reach for a hash to feel comfortable, ask first whether the column should exist. Reaching for a mitigation is a sign you have already accepted the thing being mitigated.

That question was asked about this exact column on 2026-08-22, and the answer was that it stays. The number is how a user gets back into their account after losing their phone, and the alternative — a passphrase and nothing else — makes a forgotten passphrase an unrecoverable account. So users.phone_hash exists deliberately, peppered, and b4/0001 is where it gets built.

This paragraph used to end "Token's answer to a phone number is not to hash it, it is not to have it." Right instinct, wrong conclusion, and it is worth seeing why: the argument above is about what a hash protects you from; the decision is about what the product needs in order to work. A rule derived from the first cannot settle the second. What survives is the narrower and more useful claim — a hashed phone number is a lookup key, not an anonymisation — which is exactly why the privacy policy says "we store a scrambled version of your phone number, used only to sign you in" rather than "we do not collect your phone number".
