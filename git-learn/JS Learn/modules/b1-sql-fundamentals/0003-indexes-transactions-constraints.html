Indexes, Transactions, Constraints

B1 — Lesson 3 of 4 ~50 min
Why this matters for Token

When someone redeems a token, the database must do three things atomically: validate the token, record the redemption event, and decrement the remaining uses. If any step fails, none of them should happen — otherwise you'd have an invalid state (redemption recorded but token still shows old count). Transactions guarantee this. Indexes make the lookup fast. Constraints make invalid states impossible.

Indexes — making queries fast

Without an index, Postgres reads every row in the table to find your data (a "sequential scan"). With an index, it jumps straight to the matching rows — like a book's index vs reading every page.

-- This query scans ALL tokens to find the matching code:
SELECT * FROM tokens WHERE code = 'MERC-8GH2-KP4X';
-- With 100,000 tokens, this is slow.

-- Create an index on the code column:
CREATE INDEX idx_tokens_code ON tokens(code);
-- Now the same query uses the index — nearly instant regardless of table size.

When to create indexes

  • Always index: columns you filter on frequently (WHERE), columns you join on, columns you sort by (ORDER BY)
  • Already indexed: PRIMARY KEY and UNIQUE columns get automatic indexes
  • Don't over-index: each index slows down INSERT/UPDATE (it must update the index too). Only index what you query.

For Token, these indexes matter on day one:

-- Token lookup by code (the redemption path — must be fast)
CREATE INDEX idx_tokens_code ON tokens(code);
-- Already covered by UNIQUE constraint — no need!

-- Tokens by user (the token list screen)
CREATE INDEX idx_tokens_user_id ON tokens(user_id);

-- Messages by token (loading a conversation)
CREATE INDEX idx_messages_token_id ON messages(token_id);

-- Redemption events by token
CREATE INDEX idx_redemptions_token_id ON redemption_events(token_id);

Checking if an index is used

-- EXPLAIN shows the query plan (how Postgres will execute it)
EXPLAIN SELECT * FROM tokens WHERE code = 'MERC-8GH2-KP4X';

-- EXPLAIN ANALYZE actually runs it and shows timing
EXPLAIN ANALYZE SELECT * FROM tokens WHERE user_id = 1;

Look for "Index Scan" (good) vs "Seq Scan" (bad on large tables).

Transactions — all or nothing

A transaction groups multiple SQL statements into one atomic operation. Either ALL succeed or ALL are rolled back — no partial state.

-- Token redemption: three things must happen together
BEGIN;

-- 1. Verify the token is active
SELECT id, status, max_uses FROM tokens
WHERE code = 'MERC-8GH2-KP4X' AND status = 'active'
FOR UPDATE;  -- lock this row so no other connection changes it

-- 2. Record the redemption event
INSERT INTO redemption_events (token_id, holder_name, holder_ip)
VALUES (1, 'Delivery Person', '192.168.1.1');

-- 3. If max_uses reached, auto-revoke
UPDATE tokens
SET status = 'revoked', revoked_at = NOW()
WHERE code = 'MERC-8GH2-KP4X'
AND (SELECT COUNT(*) FROM redemption_events WHERE token_id = 1) >= max_uses
AND max_uses IS NOT NULL;   -- NULL is unlimited. 0 is a limit, not the absence of one.

COMMIT;  -- all three succeed together

If any statement fails (or you call ROLLBACK), everything since BEGIN is undone:

BEGIN;
UPDATE tokens SET status = 'revoked' WHERE code = 'MERC-8GH2-KP4X';
-- Oops, wrong token!
ROLLBACK;  -- undoes the UPDATE — nothing happened

FOR UPDATE — row locking

SELECT ... FOR UPDATE locks the selected rows until the transaction ends. This prevents two people from redeeming the same token simultaneously and both succeeding when max_uses = 1.

Real-world scenario

Two delivery people scan your QR code at the same time. Without FOR UPDATE, both SELECT the token, both see it's active, both INSERT a redemption event — even though max_uses was 1. With FOR UPDATE, the second connection waits for the first to finish, then sees the updated state.

Constraints — the database as guardian

You've seen NOT NULL, UNIQUE, and CHECK. Here's the full picture:

NOT NULL — field must have a value

-- A token must always have an issued_to — who is it for?
issued_to TEXT NOT NULL

UNIQUE — no duplicates

-- Two tokens can't have the same code
code TEXT NOT NULL UNIQUE

-- Composite unique: one user can't have two tokens with the same issued_to
ALTER TABLE tokens ADD CONSTRAINT unique_user_issued
UNIQUE (user_id, issued_to);

CHECK — custom validation rules

-- Status must be one of three values
CHECK (status IN ('active', 'paused', 'revoked'))

-- max_uses must be non-negative when it is set at all.
-- NULL passes a CHECK constraint, which is what we want here: unlimited.
CHECK (max_uses >= 0)

-- allowed hours must be valid
CHECK (allowed_start >= 0 AND allowed_start <= 23)
CHECK (allowed_end >= 0 AND allowed_end <= 23)

FOREIGN KEY — referential integrity

-- Every token must belong to a real user
user_id INTEGER NOT NULL REFERENCES users(id)

-- What happens if you delete a user? Options:
-- RESTRICT (default): block the delete if tokens exist
-- CASCADE: delete all their tokens too
-- SET NULL: set token.user_id to NULL

user_id INTEGER REFERENCES users(id) ON DELETE CASCADE

For Token, use RESTRICT (the default) — you'd never want to silently delete a user's tokens. Force an explicit cleanup first.

DEFAULT — automatic values

status TEXT NOT NULL DEFAULT 'active'
created_at TIMESTAMP NOT NULL DEFAULT NOW()
max_uses INTEGER   -- nullable: NULL is unlimited, 0 permits nothing

Putting it together — Token's safety net

-- The database enforces these rules regardless of application bugs:
-- 1. Every token has an owner (FOREIGN KEY)
-- 2. Token codes are unique (UNIQUE)
-- 3. Status is always valid (CHECK)
-- 4. Required fields are never empty (NOT NULL)
-- 5. Redemption is atomic (TRANSACTION)
-- 6. Concurrent access is safe (FOR UPDATE)

-- Even if your Node.js code has a bug, these constraints
-- prevent invalid data from ever reaching the database.
