Indexes, Transactions, Constraints

B1 — Lesson 3 of 4 ~50 min
Why this matters for Token

When someone redeems a token, the database must do three things atomically: validate the token, record the redemption event, and decrement the remaining uses. If any step fails, none of them should happen — otherwise you'd have an invalid state (redemption recorded but token still shows old count). Transactions guarantee this. Indexes make the lookup fast. Constraints make invalid states impossible.

Indexes — making queries fast

Without an index, Postgres reads every row in the table to find your data (a "sequential scan"). With an index, it jumps straight to the matching rows — like a book's index vs reading every page.

-- This query scans ALL tokens to find the matching code:
SELECT * FROM tokens WHERE code = 'MERC-8GH2-KP4X';
-- With 100,000 tokens, this is slow.

-- Create an index on the code column:
CREATE INDEX idx_tokens_code ON tokens(code);
-- Now the same query uses the index — nearly instant regardless of table size.
The code column here is B1's labelled simplification

Token never stores a code in the clear. b1/0001 says so and explains why the whole module does it anyway: you are here to learn what an index is, and WHERE code = 'MERC-8GH2-KP4X' reads better than WHERE code_hash = '9f2a…' while you do it. B2 replaces it with code_hash for lookup and code_enc for the one time the owner asks to see it. Every rule on this page applies unchanged to the hash column — it is still UNIQUE, so it is still already indexed.

When to create indexes

  • Index what you query, in the order you query it — not simply "every column that appears in a WHERE". See the leftmost-prefix rule below; it is the difference between an index and an index-shaped file the planner never opens.
  • Already indexed: PRIMARY KEY and UNIQUE columns get automatic indexes. Creating your own on top is pure cost.
  • Don't over-index: each index slows down INSERT/UPDATE (it must update the index too). One well-ordered composite index usually replaces three single-column ones.

For Token, these indexes matter on day one:

-- Token lookup by code (the redemption path — must be fast).
-- NOTHING TO DO: `code TEXT NOT NULL UNIQUE` already created an index.
-- Adding CREATE INDEX idx_tokens_code here would build a second copy of
-- the same B-tree, doubling the write cost of every INSERT to buy nothing.

-- Tokens by user (the token list screen)
CREATE INDEX idx_tokens_user_id ON tokens(user_id);

-- Messages by token (loading a conversation)
CREATE INDEX idx_messages_token_id ON messages(token_id);

-- Redemption events by token. Load-bearing rather than an optimisation:
-- there is no use_count column, so the redemption transaction COUNTs
-- these rows while holding a lock, on every single redemption.
CREATE INDEX idx_redemptions_token_id ON redemption_events(token_id);

A comment does not undo the statement above it, and anyone pasting the block got exactly the redundant index the same page warns about in the bullet directly overhead. The demonstration and the warning were in the same code block, pointing opposite ways.

The leftmost-prefix rule — why a correct-looking index is never used

A composite index is one sorted list, ordered by its first column, then by its second within each value of the first, and so on. That is the whole data structure, and every rule below is a consequence of it. 

CREATE INDEX idx_tokens_user_status ON tokens(user_id, status);

-- USES IT. user_id is the first column, so the index narrows straight down.
SELECT * FROM tokens WHERE user_id = 7 AND status = 'active';

-- USES IT, partially. Everything for one user is contiguous.
SELECT * FROM tokens WHERE user_id = 7;

-- CANNOT USE IT AT ALL. Sequential scan.
SELECT * FROM tokens WHERE status = 'active';

The last one is the whole lesson. status is in the index, and the index is useless for it — the active tokens are scattered through the list, a few under every user. An index can only be entered from the left. There is no error, no warning and no difference in the query; you find out from EXPLAIN, or from the query getting slower every month.

Two more consequences worth knowing before you design a schema:

  • The first inequality ends the usable prefix. With (user_id, created_at, status), a query filtering user_id = 7 AND created_at > '2026-01-01' AND status = 'active' uses the first two columns and then stops. Within a range of created_at, status is not sorted — so put your equality columns first and your range column last.
  • An index can also supply the ORDER BY, which turns a sort into nothing at all — but only where the sort columns follow the equality-filtered ones, in index order. A backwards scan is free, so ORDER BY a DESC, b DESC is fine; a ASC, b DESC is not, because no single pass through one sorted list produces it.

Six queries against one index. Predict each answer before you press Run — the ones people get wrong are the fourth and the sixth.

Checking if an index is used

-- EXPLAIN shows the query plan (how Postgres will execute it)
EXPLAIN SELECT * FROM tokens WHERE code = 'MERC-8GH2-KP4X';

-- EXPLAIN ANALYZE actually runs it and shows timing
EXPLAIN ANALYZE SELECT * FROM tokens WHERE user_id = 1;

Look for "Index Scan" (good) vs "Seq Scan" (bad on large tables).

Transactions — all or nothing

A transaction groups multiple SQL statements into one atomic operation. Either ALL succeed or ALL are rolled back — no partial state.

-- Token redemption. The ORDER of these steps is the whole thing:
-- lock, COUNT, decide, and only then insert.
BEGIN;

-- 1. Lock the row. Take the id from here and use it below -- the whole
--    point of the lock is that this row cannot change underneath you.
SELECT id, status, max_uses FROM tokens
WHERE code = 'MERC-8GH2-KP4X' AND status = 'active'
FOR UPDATE;
-- => id = 1. No row means paused, revoked or no such code: ROLLBACK.

-- 2. COUNT BEFORE YOU INSERT. This is the step that enforces the limit,
--    and it only works while the token row above is locked.
--    NULL max_uses is unlimited and skips this entirely; 0 is a real
--    limit that permits nothing, and 0 >= 0 refuses the first attempt.
SELECT COUNT(*) FROM redemption_events WHERE token_id = 1;
-- => if max_uses IS NOT NULL AND count >= max_uses: ROLLBACK.

-- 3. Only now does the redemption exist.
INSERT INTO redemption_events (token_id, holder_name, holder_ip)
VALUES (1, 'Delivery Person', '192.168.1.1');

-- 4. If that was the last permitted use, retire the token.
--    paused_at = NULL because a revoked token is not a paused one --
--    b2/0001's CHECK constraints refuse the row otherwise.
UPDATE tokens
SET status = 'revoked', revoked_at = NOW(), paused_at = NULL
WHERE id = 1
AND max_uses IS NOT NULL
AND (SELECT COUNT(*) FROM redemption_events WHERE token_id = 1) >= max_uses;

COMMIT;
Counting after the INSERT gives a max_uses = 0 token exactly one free redemption

Until 2026-08-25 step 3 came before step 2: insert the event, then count, then auto-revoke if the count had reached the limit. Every individual statement is correct and the transaction is properly atomic. It still lets through the one thing it exists to prevent.

Walk a token with max_uses = 0 through it. The status is active, so the SELECT returns the row. The INSERT runs — the redemption has now happened. The count is 1, 1 >= 0 is true, so the token is revoked. Final state: a token that permits no uses at all has been used once, and is now correctly marked as exhausted, so nothing downstream will ever report it.

CLAUDE.md is explicit that NULL is unlimited and 0 permits nothing, and b7/0001's canRedeem gets the order right: lock, count, decide, insert. An atomic transaction guarantees that all your steps happen together. It does not check that they are in the right order — and a limit enforced after the fact is not a limit, it is a cleanup.

If any statement fails (or you call ROLLBACK), everything since BEGIN is undone:

BEGIN;
UPDATE tokens
SET status = 'revoked', revoked_at = NOW(), paused_at = NULL
WHERE code = 'MERC-8GH2-KP4X';
-- Oops, wrong token!
ROLLBACK;  -- undoes the UPDATE — nothing happened
Why the timestamps travel with the status, even in a throwaway example

This example used to be SET status = 'revoked' and nothing else, which is the natural way to write it and which b2/0001's schema rejects. State is stored twice on purpose — status is what you read, revoked_at and paused_at are what you write — and two biconditional constraints refuse any row where the two disagree: 

CHECK ((status = 'revoked') = (revoked_at IS NOT NULL)),
CHECK ((status = 'paused')  = (paused_at  IS NOT NULL))

Note paused_at = NULL in the revoke. Pausing a token and then revoking it is an ordinary sequence, and without that clause the row claims to be both. The state machine's exclusivity is a database fact here, not a convention — which is the entire argument of this lesson, so an example that would not survive the constraints is the wrong example to learn from.

FOR UPDATE — row locking

SELECT ... FOR UPDATE locks the selected rows until the transaction ends. This prevents two people from redeeming the same token simultaneously and both succeeding when max_uses = 1.

Real-world scenario

Two delivery people scan your QR code at the same time. Without FOR UPDATE, both SELECT the token, both see it's active, both INSERT a redemption event — even though max_uses was 1. With FOR UPDATE, the second connection waits for the first to finish, then sees the updated state.

Constraints — the database as guardian

You've seen NOT NULL, UNIQUE, and CHECK. Here's the full picture:

NOT NULL — field must have a value

-- A token must always have a label — what is it for? "Blinkit delivery"
label TEXT NOT NULL

NOT NULL rejects NULL and nothing else. It does not reject '', and b1/0001 spends a section on the difference — an empty label satisfies this column and then renders as a blank row, because ?? 'Unnamed' catches null and not ''.

UNIQUE — no duplicates

-- Two tokens can't have the same code
code TEXT NOT NULL UNIQUE

-- Composite unique: one user can't have two tokens with the same label
ALTER TABLE tokens ADD CONSTRAINT unique_user_label
UNIQUE (user_id, label);

CHECK — custom validation rules

-- Status must be one of three values
CHECK (status IN ('active', 'paused', 'revoked'))

-- max_uses must be non-negative when it is set at all.
-- NULL passes a CHECK constraint, which is what we want here: unlimited.
CHECK (max_uses >= 0)

-- And the two that make the duplicated state safe rather than merely
-- tolerated. Read them as "these two facts must agree, in BOTH
-- directions" -- see the ROLLBACK callout above.
CHECK ((status = 'revoked') = (revoked_at IS NOT NULL))
CHECK ((status = 'paused')  = (paused_at  IS NOT NULL))
A CHECK does not imply NOT NULL

CHECK (status IN ('active', 'paused', 'revoked')) accepts a NULL status happily. A check rejects only what it can prove false, and a comparison against NULL is unknown, which is not false. The same three-valued logic is why CHECK (max_uses >= 0) lets NULL through — there it is exactly what we want, and one line above it is a hole. b1/0001 has the full table.

Time windows are rows, not columns

This section used to carry CHECK (allowed_start >= 0 AND allowed_start <= 23), against a pair of columns on tokens. A token's rules do not live on the token: they are access_rules rows, one per rule, with a constrained rule_type and a payload JSONB. There are exactly three types — time_window, contact_limit and channel_restrict — and the deciding argument for rows was precisely this one: rule_type can be a constrained column, so the database can refuse a rule the engine cannot evaluate. A pair of hour columns has no layer at which that is catchable. b2/0001 builds it.

FOREIGN KEY — referential integrity

-- Every token must belong to a real user
user_id INTEGER NOT NULL REFERENCES users(id)

-- What happens if you delete a user? Options:
-- RESTRICT (default): block the delete if tokens exist
-- CASCADE: delete all their tokens too
-- SET NULL: set token.user_id to NULL

user_id INTEGER REFERENCES users(id) ON DELETE CASCADE

For Token, use RESTRICT (the default) — you'd never want to silently delete a user's tokens. Force an explicit cleanup first.

DEFAULT — automatic values

status TEXT NOT NULL DEFAULT 'active'
created_at TIMESTAMP NOT NULL DEFAULT NOW()
max_uses INTEGER   -- nullable: NULL is unlimited, 0 permits nothing

Putting it together — Token's safety net

-- The database enforces these rules regardless of application bugs:
-- 1. Every token has an owner (FOREIGN KEY)
-- 2. Token codes are unique (UNIQUE)
-- 3. Status is always valid (CHECK)
-- 4. Required fields are never empty (NOT NULL)
-- 5. Redemption is atomic (TRANSACTION)
-- 6. Concurrent access is safe (FOR UPDATE)

-- Even if your Node.js code has a bug, these constraints
-- prevent invalid data from ever reaching the database.
