Joins & Relationships

B1 — Lesson 2 of 4 ~50 min
Why this matters for Token

Token's data is spread across multiple tables: users, tokens, access_rules, messages, redemption_events. When the app shows a token list, it needs data from tokens joined with users. When displaying a chat, it joins messages with tokens and redemption_events. Joins are how you combine related data from different tables in a single query.

Why multiple tables?

You could put everything in one giant table — but that leads to duplicated data, inconsistencies, and impossible constraints. Instead, relational databases split data by entity and link them with keys:

-- Bad: one flat table with duplicated user info
-- If Ashish changes their display_name, you'd need to update EVERY token row

-- Good: separate tables linked by user_id
-- Change the name once in users, all tokens automatically "see" the new name

Relationships

The three relationship types:

  • One-to-many — one user has many tokens. Each token has one user_id.
  • One-to-one — one user has one profile. (Less common.)
  • Many-to-many — many tokens can have many access rules. (Uses a junction table.)

Token's core relationships:

users (1) ──→ (many) tokens
tokens (1) ──→ (many) access_rules
tokens (1) ──→ (many) redemption_events
tokens (1) ──→ (many) messages

INNER JOIN

An INNER JOIN returns rows only where both tables have matching data:

-- Get tokens with their owner's display name
SELECT
  tokens.code,
  tokens.issued_to,
  tokens.status,
  users.display_name AS owner_name
FROM tokens
INNER JOIN users ON tokens.user_id = users.id;

Result:

code            | issued_to       | status | owner_name
----------------+-----------------+--------+-----------
MERC-8GH2-LP4X | Amazon Delivery | active | Ashish
SHOP-4KN9-RT2M | Flipkart        | active | Ashish
RENT-2WX7-JP8N | NoBroker Agent  | paused | Ashish

ON tokens.user_id = users.id is the join condition — it tells Postgres which rows to match.

Table aliases

Writing tokens.code and users.display_name everywhere gets verbose. Use aliases:

SELECT t.code, t.issued_to, t.status, u.display_name
FROM tokens t
INNER JOIN users u ON t.user_id = u.id
WHERE t.status = 'active';

t is short for tokens, u for users. Same query, easier to read.

LEFT JOIN

A LEFT JOIN returns all rows from the left table, even if there's no match in the right table (unmatched fields become NULL):

-- All tokens, plus their most recent redemption (if any)
SELECT
  t.code,
  t.issued_to,
  r.redeemed_at,
  r.holder_name
FROM tokens t
LEFT JOIN redemption_events r ON r.token_id = t.id;

Tokens that have never been redeemed still appear — their redeemed_at and holder_name will be NULL.

When to use which join

  • INNER JOIN — you only want rows where both sides exist. "Show me tokens with their owner" (every token has an owner, so this always matches).
  • LEFT JOIN — you want all rows from the left table, even without matches. "Show all tokens and their redemptions, including tokens never redeemed."

Joining more than two tables

-- Token detail view: token + owner + access rules
SELECT
  t.code,
  t.issued_to,
  t.status,
  u.display_name AS owner,
  ar.max_calls_per_day,
  ar.allowed_hours
FROM tokens t
INNER JOIN users u ON t.user_id = u.id
LEFT JOIN access_rules ar ON ar.token_id = t.id
WHERE t.code = 'MERC-8GH2-LP4X';

You can chain as many JOINs as needed. Each one adds columns from another table.

Token's tables — building the full picture

Let's add the tables referenced above:

CREATE TABLE access_rules (
  id              SERIAL PRIMARY KEY,
  token_id        INTEGER NOT NULL REFERENCES tokens(id),
  allowed_start   INTEGER NOT NULL DEFAULT 0,   -- hour 0-23
  allowed_end     INTEGER NOT NULL DEFAULT 23,
  max_calls_per_day INTEGER NOT NULL DEFAULT 0, -- 0 = unlimited
  categories      TEXT[] DEFAULT '{}',          -- Postgres array
  created_at      TIMESTAMP NOT NULL DEFAULT NOW()
);

CREATE TABLE redemption_events (
  id          SERIAL PRIMARY KEY,
  token_id    INTEGER NOT NULL REFERENCES tokens(id),
  holder_name TEXT,
  holder_ip   TEXT,
  redeemed_at TIMESTAMP NOT NULL DEFAULT NOW()
);

Subqueries

A query inside another query — useful when you need to filter based on computed values:

-- Find tokens that have been redeemed more than 3 times
SELECT code, issued_to
FROM tokens
WHERE id IN (
  SELECT token_id
  FROM redemption_events
  GROUP BY token_id
  HAVING COUNT(*) > 3
);

-- Find the user with the most tokens
SELECT display_name, token_count
FROM (
  SELECT u.display_name, COUNT(t.id) AS token_count
  FROM users u
  LEFT JOIN tokens t ON t.user_id = u.id
  GROUP BY u.display_name
) counts
ORDER BY token_count DESC
LIMIT 1;

Aggregate functions with GROUP BY

-- Count tokens per status
SELECT status, COUNT(*) AS count
FROM tokens
GROUP BY status;

-- Count tokens per user
SELECT u.display_name, COUNT(t.id) AS token_count
FROM users u
LEFT JOIN tokens t ON t.user_id = u.id
GROUP BY u.display_name;

-- Find users with more than 5 active tokens
SELECT u.display_name, COUNT(t.id) AS active_count
FROM users u
INNER JOIN tokens t ON t.user_id = u.id
WHERE t.status = 'active'
GROUP BY u.display_name
HAVING COUNT(t.id) > 5;

HAVING is like WHERE but for aggregated results. WHERE filters rows before grouping; HAVING filters after.
