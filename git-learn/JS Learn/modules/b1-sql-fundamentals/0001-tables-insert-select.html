Tables, INSERT, SELECT

B1 — Lesson 1 of 4 ~50 min
Why this matters for Token

Every token, user, message, and access rule lives in a PostgreSQL database. When someone redeems a token, it's a SQL query that checks if it exists, whether it's revoked, and what rules apply. You write every query yourself — no ORM hides the database from you. This is where your data lives, and SQL is how you talk to it.

What is a relational database?

A relational database stores data in tables — like spreadsheets with strict rules. Each table has:

  • Columns — the fields (name, type, constraints)
  • Rows — the actual data entries
  • Primary key — a column that uniquely identifies each row

PostgreSQL (often called "Postgres") is the database Token uses. It's open source, battle-tested, and handles everything from startups to enterprises.

Setting up Postgres locally

# macOS (via Homebrew)
brew install postgresql@16
brew services start postgresql@16

# Windows (download installer from postgresql.org)
# Or use Docker (covered in B9):
docker run --name token-db -e POSTGRES_PASSWORD=dev -p 5432:5432 -d postgres:16

# Create a database for Token
createdb token_dev

# Connect to it
psql token_dev

You're now in the psql shell — everything you type here is SQL, sent directly to Postgres.

CREATE TABLE

Let's create the first table Token needs — users:

CREATE TABLE users (
  id          SERIAL PRIMARY KEY,
  phone_hash  TEXT NOT NULL UNIQUE,
  display_name TEXT NOT NULL,
  created_at  TIMESTAMP NOT NULL DEFAULT NOW()
);

Breaking this down:

  • SERIAL PRIMARY KEY — auto-incrementing integer, unique identifier for each row
  • TEXT NOT NULL — text column that can't be empty (null)
  • UNIQUE — no two rows can have the same value
  • DEFAULT NOW() — if you don't provide a value, use the current timestamp

Now the tokens table:

CREATE TABLE tokens (
  id          SERIAL PRIMARY KEY,
  code        TEXT NOT NULL UNIQUE,
  user_id     INTEGER NOT NULL REFERENCES users(id),
  issued_to   TEXT NOT NULL,
  status      TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active', 'paused', 'revoked')),
  max_uses    INTEGER,   -- NULL means unlimited; 0 means no uses at all
  created_at  TIMESTAMP NOT NULL DEFAULT NOW(),
  revoked_at  TIMESTAMP
);

New concepts here:

  • REFERENCES users(id) — a foreign key. This token must belong to a real user. Postgres rejects inserts with a non-existent user_id.
  • CHECK (status IN (...)) — a constraint. Only these three values are allowed. The database enforces this, not your app code.
  • revoked_at TIMESTAMP — no NOT NULL, so it can be null (token not yet revoked)
  • max_uses INTEGER — deliberately nullable, and deliberately without a default. See the callout below; this is the one column on this table where getting the nullability wrong changes what the product can express.
Why constraints matter

A revoked token must never be honoured. If that rule lives only in application code, a bug can bypass it. If it's a database constraint, it's physically impossible to violate — the database rejects the invalid state before it's stored. Token's privacy promise depends on this.

Why max_uses is nullable, and why it has no default

The obvious definition is INTEGER NOT NULL DEFAULT 0. It is tidy, it removes a null from the schema, and it is wrong twice over.

In Token, NULL means unlimited and 0 means no uses at all. Those are opposite meanings. So NOT NULL makes "unlimited" impossible to write down, and DEFAULT 0 makes every token that does not name a limit default to permitting nothing — issued and instantly unusable.

There is no default because there is no safe one. A token without a stated limit is a decision the caller has to make, and the database declining to guess is the point.

It bites in application code too, and the trap is that only one of the two values is falsy:

// WRONG -- max_uses of 0 is falsy, so this reads
// "no uses permitted" as "no limit set".
if (token.max_uses) { checkLimit(); }

// RIGHT -- asks the question actually being asked.
if (token.max_uses != null) { checkLimit(); }

The same shape appears one column over. expires_at null means never expires — and new Date(null) is 1 January 1970, comfortably in the past, so parsing before checking for null marks every never-expiring token as expired.

In SQL the equivalent slip is WHERE max_uses > 0 to mean "has a limit". Zero is a limit. The test for whether a limit exists is IS NOT NULL.

INSERT — adding data

-- Insert a user
INSERT INTO users (phone_hash, display_name)
VALUES ('sha256_abc123', 'Ashish');

-- Insert a token (user_id 1 = the user we just created)
INSERT INTO tokens (code, user_id, issued_to, max_uses)
VALUES ('MERC-8GH2-KP4X', 1, 'Amazon Delivery', 3);

-- Insert multiple tokens at once
INSERT INTO tokens (code, user_id, issued_to, max_uses) VALUES
  ('KART-4KN9-RT2M', 1, 'Flipkart', 5),
  ('RENT-2WX7-JP8N', 1, 'NoBroker Agent', 1);

Notice: we didn't provide id, status, or created_at — they use their defaults (auto-increment, 'active', NOW()).

SELECT — reading data

-- Get all tokens
SELECT * FROM tokens;

-- Get specific columns
SELECT code, issued_to, status FROM tokens;

-- Filter with WHERE
SELECT * FROM tokens WHERE status = 'active';

-- Multiple conditions
SELECT * FROM tokens WHERE status = 'active' AND max_uses > 1;

-- Sort results
SELECT * FROM tokens ORDER BY created_at DESC;

-- Limit results (pagination preview)
SELECT * FROM tokens ORDER BY created_at DESC LIMIT 10;

WHERE operators

-- Equality
SELECT * FROM tokens WHERE code = 'MERC-8GH2-KP4X';

-- Not equal
SELECT * FROM tokens WHERE status != 'revoked';

-- Greater/less than (works with numbers and dates)
SELECT * FROM tokens WHERE max_uses > 3;
SELECT * FROM tokens WHERE created_at > '2025-01-01';

-- NULL checks (use IS NULL, not = NULL)
SELECT * FROM tokens WHERE revoked_at IS NULL;      -- not revoked
SELECT * FROM tokens WHERE revoked_at IS NOT NULL;  -- revoked

-- Pattern matching
SELECT * FROM tokens WHERE issued_to LIKE '%Delivery%';

-- IN — match any value in a list
SELECT * FROM tokens WHERE status IN ('active', 'paused');
NULL is special

WHERE revoked_at = NULL does NOT work — it always returns zero rows. NULL represents "unknown", and nothing equals unknown. Always use IS NULL or IS NOT NULL.

UPDATE — modifying data

-- Revoke a token
UPDATE tokens
SET status = 'revoked', revoked_at = NOW()
WHERE code = 'MERC-8GH2-KP4X';

-- Pause all tokens for a user
UPDATE tokens
SET status = 'paused'
WHERE user_id = 1 AND status = 'active';
Always include WHERE

UPDATE tokens SET status = 'revoked' without a WHERE clause revokes every token in the table. Always double-check your WHERE before running an UPDATE or DELETE.

DELETE — removing data

-- Delete a specific token
DELETE FROM tokens WHERE code = 'RENT-2WX7-JP8N';

-- Delete all revoked tokens older than 30 days
DELETE FROM tokens
WHERE status = 'revoked'
AND revoked_at < NOW() - INTERVAL '30 days';

In Token's case, you'll rarely DELETE — you'll revoke (set status) instead. Keeping revoked tokens means you have an audit trail.

Counting and aggregating

-- How many tokens does a user have?
SELECT COUNT(*) FROM tokens WHERE user_id = 1;

-- How many active vs revoked?
SELECT status, COUNT(*) FROM tokens GROUP BY status;

-- Average max_uses across all tokens
SELECT AVG(max_uses) FROM tokens;
