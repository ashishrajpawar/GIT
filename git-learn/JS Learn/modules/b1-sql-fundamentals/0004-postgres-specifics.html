Postgres Specifics

B1 — Lesson 4 of 4 ~45 min
Why this matters for Token

Token's access rules are flexible — different time windows, call limits, category restrictions. A rigid relational schema can't easily handle "any combination of rules." JSONB solves this: store the rule payload as structured JSON inside a Postgres column, with the ability to query and index it. LISTEN/NOTIFY lets your WebSocket server react instantly when a token is revoked.

JSONB — flexible structured data

Postgres has a JSONB type that stores JSON documents inside a column. You can query into it, index it, and validate it:

-- Access rules with a JSONB payload
CREATE TABLE access_rules (
  id        SERIAL PRIMARY KEY,
  token_id  INTEGER NOT NULL REFERENCES tokens(id),
  rule_type TEXT NOT NULL,
  payload   JSONB NOT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT NOW()
);

-- Insert a time-window rule
INSERT INTO access_rules (token_id, rule_type, payload) VALUES
(1, 'time_window', '{"start_hour": 9, "end_hour": 18, "timezone": "Asia/Kolkata"}');

-- Insert a call-limit rule
INSERT INTO access_rules (token_id, rule_type, payload) VALUES
(1, 'call_limit', '{"max_per_day": 2, "max_per_week": 10}');

-- Insert a category restriction
INSERT INTO access_rules (token_id, rule_type, payload) VALUES
(1, 'categories', '{"allowed": ["delivery", "support"], "blocked": ["marketing"]}');

Querying JSONB

-- Get the start_hour from a time_window rule
SELECT payload->>'start_hour' AS start_hour
FROM access_rules
WHERE token_id = 1 AND rule_type = 'time_window';

-- -> returns JSON (still a JSON object/array)
-- ->> returns TEXT (the value as a string)

-- Filter on a JSONB field
SELECT * FROM access_rules
WHERE payload->>'timezone' = 'Asia/Kolkata';

-- Check if a JSONB array contains a value
SELECT * FROM access_rules
WHERE payload->'allowed' ? 'delivery';

-- Cast to number for comparison
SELECT * FROM access_rules
WHERE (payload->>'max_per_day')::integer > 1;

Indexing JSONB

-- GIN index lets you query ANY key in the JSONB efficiently
CREATE INDEX idx_rules_payload ON access_rules USING GIN (payload);

-- Now queries like payload @> '{"timezone": "Asia/Kolkata"}' use the index
SELECT * FROM access_rules WHERE payload @> '{"timezone": "Asia/Kolkata"}';

When to use JSONB vs columns

  • Use columns when the shape is fixed and you query/sort by it often (status, code, user_id)
  • Use JSONB when the shape varies between rows (different rule types have different fields) or when the structure might change without a migration

Token uses both: rigid columns for the core data (tokens, users) and JSONB for the flexible rule payloads.

Arrays

Postgres supports array columns — useful when a field naturally holds multiple values:

-- Categories as a text array
ALTER TABLE tokens ADD COLUMN tags TEXT[] DEFAULT '{}';

-- Insert with array values
UPDATE tokens SET tags = ARRAY['delivery', 'commerce']
WHERE code = 'MERC-8GH2-LP4X';

-- Check if array contains a value
SELECT * FROM tokens WHERE 'delivery' = ANY(tags);

-- Array length
SELECT code, array_length(tags, 1) AS tag_count FROM tokens;

LISTEN/NOTIFY — real-time events from the database

Postgres can broadcast events to connected clients. This is how Token's WebSocket server knows instantly when a token is revoked — without polling:

-- Any connection can listen on a channel:
LISTEN token_events;

-- Another connection (or a trigger) sends a notification:
NOTIFY token_events, '{"action": "revoked", "code": "MERC-8GH2-LP4X"}';

-- The listening connection receives it instantly.

Trigger + NOTIFY = automatic alerts

-- A trigger function that fires when a token is revoked
CREATE OR REPLACE FUNCTION notify_token_revoked()
RETURNS TRIGGER AS $$
BEGIN
  IF NEW.status = 'revoked' AND OLD.status != 'revoked' THEN
    PERFORM pg_notify('token_events',
      json_build_object(
        'action', 'revoked',
        'code', NEW.code,
        'user_id', NEW.user_id
      )::text
    );
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- Attach it to the tokens table
CREATE TRIGGER token_revoked_trigger
AFTER UPDATE ON tokens
FOR EACH ROW
EXECUTE FUNCTION notify_token_revoked();

Now whenever a token is revoked (by any means — your API, a cron job, a manual query), the WebSocket server is notified and can immediately disconnect active sessions using that token.

Postgres vs SQLite — dialect differences

Token uses Postgres on the server and SQLite on the mobile app (local cache). Most SQL is the same, but key differences:

Feature Postgres SQLite
Auto-increment SERIAL or GENERATED ALWAYS AS IDENTITY INTEGER PRIMARY KEY (auto)
JSON JSONB (indexed, queryable) TEXT (store as string, parse in app)
Arrays Native TEXT[], INTEGER[] Not supported (use JSON or junction table)
LISTEN/NOTIFY Built-in real-time events Not available
Timestamp TIMESTAMP, TIMESTAMPTZ TEXT or INTEGER (store as ISO string or unix epoch)
Concurrency Full MVCC, multiple writers Single writer (OK for local cache)

The rule: write your server queries for Postgres. On the mobile app, SQLite is just a cache — simpler queries, no JOINs with the server data, no LISTEN/NOTIFY.

RETURNING — get data back from INSERT/UPDATE

-- Insert a token and get the generated id back in one query
INSERT INTO tokens (code, user_id, issued_to, max_uses)
VALUES ('NEW1-ABCD-EFGH', 1, 'New Service', 5)
RETURNING id, code, created_at;

-- Update and get the new state
UPDATE tokens
SET status = 'revoked', revoked_at = NOW()
WHERE code = 'MERC-8GH2-LP4X'
RETURNING *;

This avoids a second SELECT after every write — important for performance and for keeping your Node.js code simple.

UPSERT — insert or update

-- If a rule already exists for this token + type, update it.
-- Otherwise, insert a new one.
INSERT INTO access_rules (token_id, rule_type, payload)
VALUES (1, 'time_window', '{"start_hour": 10, "end_hour": 20}')
ON CONFLICT (token_id, rule_type)
DO UPDATE SET payload = EXCLUDED.payload;

Requires a UNIQUE constraint on (token_id, rule_type) for the conflict detection.
