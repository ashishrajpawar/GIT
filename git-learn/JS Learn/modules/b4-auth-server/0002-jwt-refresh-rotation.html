JWT & Refresh Rotation

B4 — Lesson 2 of 3 ~55 min
Why this matters for Token

Once the number is verified, the mobile app needs to make API requests without asking for a new SMS code every time. JWTs (JSON Web Tokens) are the standard: the server issues a signed token, the client sends it with every request, the server verifies the signature without a database lookup. But JWTs can't be revoked once issued — so we pair a short-lived access token with a longer-lived refresh token that can be rotated and revoked.

How JWT works

A JWT has three parts separated by dots: header.payload.signature

// Header: algorithm and token type
{ "alg": "HS256", "typ": "JWT" }

// Payload: your data (claims)
{ "sub": "42", "iat": 1700000000, "exp": 1700000900 }

// That is the whole payload. There is no email to put in it, and the phone
// number must never go in one: a JWT is base64, not encrypted, and it lands
// in logs, crash reports and proxy traces routinely.

// Signature: HMAC of header + payload using your secret
// If anyone modifies the payload, the signature won't match → rejected

The server signs it with a secret. Anyone can READ the payload (it's just base64), but nobody can MODIFY it without the secret. The server verifies the signature on every request.

Access token + Refresh token pattern

Access Token Refresh Token
Lifetime 15 minutes Until revoked — no expiry
Stored in Memory (client) Secure storage (Keychain/Keystore)
Sent with Every API request (Authorization header) Only to /api/auth/refresh
Revocable? No (expires naturally) Yes (stored in DB, can be deleted)

The flow:

  1. User logs in → server issues access token + refresh token
  2. Client sends access token with every request
  3. Access token expires (15 min) → client sends refresh token to get a new pair
  4. Old refresh token is invalidated, new pair issued (rotation)
  5. If refresh token is stolen and used, rotation detects it (both tokens are invalid)

Issuing tokens on login

// api/src/services/auth.ts
import jwt from 'jsonwebtoken';
import { randomBytes, createHash } from 'crypto';   // ESM: import it, do not require() it
import { pool } from '../db/pool.js';

const ACCESS_SECRET = process.env.JWT_SECRET!;
const ACCESS_EXPIRY = '15m';
const REFRESH_EXPIRY_DAYS = 7;

interface TokenPayload {
  sub: string;  // user id, and nothing else
}

// A JWT is SIGNED, not encrypted. Anyone holding one can base64-decode it,
// and access tokens land in proxy logs and crash reports routinely -- so a
// claim earns its place by being needed on every request AND cheap to be
// wrong about. sub qualifies. The phone number never would.
export function signAccessToken(userId: number): string {
  return jwt.sign(
    { sub: String(userId) } as TokenPayload,
    ACCESS_SECRET,
    { expiresIn: ACCESS_EXPIRY }
  );
}

// A refresh token is 40 random bytes - 320 bits. Plain SHA-256 is the right
// hash here and argon2 would be wrong: slow hashing exists to make GUESSING
// expensive, and nobody guesses a 320-bit random value. The database stores
// the hash so a dump yields nothing usable. (ADR-0007 calls this "hash-only",
// the option token codes could not take because a code must be re-showable.)
function hashToken(token: string): string {
  return createHash('sha256').update(token).digest('hex');
}

// familyId ties every rotation of one login together. It is what makes reuse
// detection possible - see "When this breaks".
export async function createRefreshToken(
  client: PoolClient, userId: number, familyId?: string, deviceLabel?: string
): Promise<string> {
  const token = randomBytes(40).toString('hex');

  // No expiresAt. A refresh token dies when it is revoked or superseded,
  // never on a clock -- see "Sessions do not expire" below.
  await client.query(
    `INSERT INTO refresh_tokens (user_id, family_id, token_hash, device_label)
     VALUES ($1, COALESCE($2, gen_random_uuid()), $3, $4)`,
    [userId, familyId ?? null, hashToken(token), deviceLabel ?? 'Unknown device']
  );

  return token;
}

The refresh_tokens table

-- Migration: 005_refresh_tokens.sql
CREATE TABLE refresh_tokens (
  id          SERIAL PRIMARY KEY,
  user_id     INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  -- One family per login. Every rotation adds a row with the same family_id,
  -- so "this session" is a thing you can revoke without touching the others.
  family_id   UUID NOT NULL,
  token_hash  TEXT NOT NULL UNIQUE,
  -- No expires_at. A refresh token dies by revocation, not by clock.
  -- What the user needs instead is enough to RECOGNISE the session:
  device_label  TEXT        NOT NULL,
  last_used_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  revoked_at    TIMESTAMPTZ,
  -- Set when this row is rotated away. Distinct from revoked_at, and the
  -- distinction is what separates a retry from a theft -- see below.
  superseded_at TIMESTAMPTZ
);

CREATE INDEX idx_refresh_tokens_user   ON refresh_tokens(user_id);
CREATE INDEX idx_refresh_tokens_family ON refresh_tokens(family_id);
-- token_hash is already UNIQUE, which indexes it. A second index on the same
-- column costs writes and buys nothing.

Store the hash of the refresh token, not the token itself. If the database is breached, attackers can't use the hashed values as refresh tokens.

Sessions do not expire, so the device list is not a nicety

Token has no password. You verify your number once per device and stay signed in — which means revocation is the only way a session ever ends, and a revocation nobody can reach is not a control.

The family-based logout further down is correct and, on its own, unusable: it revokes a family, and nothing so far lets a user say which. That is what device_label and last_used_at are for — a settings screen reading "Pixel 7 — last used 3 minutes ago" next to "iPhone — last used 4 months ago", each with a Revoke button. Building indefinite sessions without that screen means the only way out of a compromised session is to delete the account.

Two columns rather than one, deliberately: revoked_at means someone ended this, and superseded_at means this rotated into its successor. Both make a row unusable and they are not the same event, which the reuse-detection section depends on entirely.

Where the session starts

There is no login route here. b4/0001's POST /auth/verify-code is the only thing that creates a session, and this is the part that gets added to the end of it, inside the same transaction that consumes the OTP:

// ... inside POST /auth/verify-code, after the OTP is consumed
// and the user row is upserted.

const accessToken = signAccessToken(user.id);

// A fresh verification starts a new family - no familyId passed.
// deviceLabel comes from the client and is for the USER to read, not
// for us to trust: it is displayed on their device list and nowhere
// else, so a lie in it deceives only the person who sent it.
const refreshToken = await createRefreshToken(
  client, user.id, undefined, req.body.deviceLabel
);

await client.query('COMMIT');

res.json({
  data: {
    user: { id: user.id, displayName: user.display_name },
    needsDisplayName: user.display_name === PLACEHOLDER_NAME,
    accessToken,
    refreshToken,
  },
  success: true,
});

Note what is not in that response: no email, because there is none, and no phone number, because the client already knows it and the server has only a hash. Every field in an auth response should be something the caller needs and cannot already compute.

Refresh endpoint with rotation

router.post('/refresh', async (req, res, next) => {
  try {
    const { refreshToken } = req.body;
    if (!refreshToken) throw ApiError.unauthorized('Refresh token required');

    const tokenHash = hashToken(refreshToken);
    const client = await pool.connect();

    try {
      await client.query('BEGIN');

      // Look it up WITHOUT filtering on revoked_at or superseded_at. A
      // dead row is the whole point: it means this token was used before.
      // No JOIN to users -- the access token carries only sub, so nothing
      // from that table is needed here any more.
      const { rows } = await client.query(
        `SELECT * FROM refresh_tokens
          WHERE token_hash = $1
          FOR UPDATE`,
        [tokenHash]
      );

      // The whole decision, as a pure function -- see the exercise below.
      const outcome = refreshOutcome(toRecord(rows[0]), {
        now: Date.now(),
        graceMs: 10_000,
      });

      if (outcome.revokeFamily) {
        await client.query(
          `UPDATE refresh_tokens SET revoked_at = NOW()
            WHERE family_id = $1 AND revoked_at IS NULL`,
          [rows[0].family_id]
        );
      }

      if (outcome.action === 'reject') {
        // COMMIT rather than ROLLBACK: if a family was just revoked, that
        // revocation must survive. When nothing was written it is a no-op.
        await client.query('COMMIT');
        throw ApiError.unauthorized('Invalid refresh token');
      }

      if (outcome.action === 'replay') {
        // A retry of a request whose response was lost. Hand back the
        // successor that already exists instead of rotating again --
        // rotating here would fork the chain and turn the NEXT genuine
        // refresh into a reuse.
        await client.query('COMMIT');
        return res.json({
          data: {
            accessToken: signAccessToken(rows[0].user_id),
            refreshToken: outcome.replayToken,
          },
          success: true,
        });
      }

      // Rotate. Both statements are in one transaction: superseding the old
      // token and issuing the new one must succeed or fail together, or a
      // failed insert leaves the user with nothing.
      await client.query(
        'UPDATE refresh_tokens SET superseded_at = NOW(), last_used_at = NOW() WHERE id = $1',
        [rows[0].id]
      );

      const newAccessToken = signAccessToken(rows[0].user_id);
      const newRefreshToken = await createRefreshToken(
        client, rows[0].user_id, rows[0].family_id, rows[0].device_label
      );

      await client.query('COMMIT');

      res.json({
        data: { accessToken: newAccessToken, refreshToken: newRefreshToken },
        success: true,
      });
    } catch (err) {
      await client.query('ROLLBACK').catch(() => {});
      throw err;
    } finally {
      client.release();
    }
  } catch (err) { next(err); }
});

FOR UPDATE inside the transaction is what stops two refreshes racing: the second waits for the first to commit, then sees a revoked row and treats it as reuse. Without the lock both could read revoked_at IS NULL and both rotate, leaving two live tokens in one family — which is exactly the state rotation exists to prevent.

Auth middleware — verifying access tokens

// api/src/middleware/auth.ts
import jwt from 'jsonwebtoken';
import { ApiError } from '../utils/api-error.js';

export function requireAuth(req, res, next) {
  const header = req.headers.authorization;
  if (!header?.startsWith('Bearer ')) {
    throw ApiError.unauthorized();
  }

  const token = header.slice(7);

  try {
    // Pin the algorithm. Without this, verify() accepts whatever the token's
    // own header claims - which is how "alg: none" and RS256-to-HS256
    // confusion attacks worked. Never let the token choose how it is checked.
    const payload = jwt.verify(token, process.env.JWT_SECRET!, {
      algorithms: ['HS256'],
    }) as { sub: string };
    req.user = { id: parseInt(payload.sub, 10) };
    next();
  } catch (err) {
    if (err.name === 'TokenExpiredError') {
      throw ApiError.unauthorized('Token expired');
    }
    throw ApiError.unauthorized('Invalid token');
  }
}

Logout — revoking refresh tokens

// No requireAuth. The access token is 15 minutes old at most, and a user
// pressing "Log out" after leaving the app open overnight has an expired
// one - demanding a valid access token means logout fails exactly when it
// matters. The refresh token in the body is the credential here.
router.post('/logout', async (req, res, next) => {
  try {
    const { refreshToken } = req.body;
    if (!refreshToken) throw ApiError.badRequest('refreshToken is required');

    // Revoke THIS session's family, not every session the user has.
    // Logging out on the phone should not sign them out of the web page.
    await pool.query(
      `UPDATE refresh_tokens SET revoked_at = NOW()
        WHERE family_id = (SELECT family_id FROM refresh_tokens WHERE token_hash = $1)
          AND revoked_at IS NULL`,
      [hashToken(refreshToken)]
    );

    // Always 204, whether or not the token existed. "That token was not
    // real" is not information a stranger needs.
    res.status(204).end();
  } catch (err) { next(err); }
});

// Logging out everywhere is a different, deliberate action - and this one
// does need proof of identity.
router.post('/logout-all', requireAuth, async (req, res, next) => {
  try {
    await pool.query(
      'UPDATE refresh_tokens SET revoked_at = NOW() WHERE user_id = $1 AND revoked_at IS NULL',
      [req.user.id]
    );
    res.status(204).end();
  } catch (err) { next(err); }
});

Why this way (and what was rejected)

Two tokens, because one cannot be both

A single long-lived JWT is simpler and it cannot be taken back. The server verifies a signature; there is no lookup, so there is nowhere to record that this one is no longer welcome. Someone who copies it has access until it expires, and if it expires quickly the user logs in every hour.

A single opaque session token in the database is revocable and costs a query on every request — which contradicts the stateless API in ADR-0003 only mildly (the query is cheap) but does put the database on the path of every call.

The pair takes the useful half of each: a signed access token verified with no lookup, short enough that a stolen one is a nuisance rather than a breach, plus a refresh token that is a database row and can be killed. The cost is honest and worth stating: revocation is not instant. It stops the next refresh, so there is a window of up to the access token's lifetime — 15 minutes — where a revoked session still works.

Rotation, and the family that makes it mean something

Rotating on every refresh is what turns a stolen refresh token from a week of access into a detectable event. The mechanism is not the rotation itself, though — it is that the old token stays in the table, marked revoked, instead of being deleted.

A deleted row and a token that never existed look identical. A revoked row is evidence: the only way to present one is to have held a copy that was already exchanged. Either the thief is using their copy after the real client rotated, or the real client is using theirs after the thief did. The server cannot tell which — so it kills the whole family, and both of them have to sign in again. The legitimate user has the phone. That is the whole recovery path, and it is why this trade is affordable here: killing a family costs a real user one SMS, not a forgotten-password support ticket.

Plain SHA-256 for the refresh token, a pepper for the phone

Using a fast hash on a credential looks like the mistake b4/0001 spends a section warning about. It is not, and the difference is where the value came from. A phone number is ten digits with a known prefix and an OTP is six digits — both small enough to enumerate, which is why both are peppered. A refresh token is 40 bytes from the CSPRNG — 320 bits, unguessable at any speed. Slow hashing or a pepper would add cost to every refresh and defend against nothing.

The rule, rather than the three cases: how you store a secret is decided by the size of the space it was drawn from, never by how important it feels. A refresh token is far more powerful than a phone number and needs far less protection at rest, because guessing it is not a strategy anyone can pursue.

When this breaks

The reuse detection that detected nothing

This lesson shipped with a comment promising theft detection and code that could not deliver it: 

WHERE rt.token_hash = $1 AND rt.revoked_at IS NULL AND rt.expires_at > NOW()
// ...
if (!rows[0]) {
  // "possible theft — revoke ALL user's tokens"
  UPDATE refresh_tokens SET revoked_at = NOW() WHERE token_hash = $1 AND revoked_at IS NULL
}

Two failures stacked on top of each other:

  • The lookup filters out revoked rows, so a reused token produces no row — indistinguishable from a token that was never issued. The one signal worth having is discarded before it is read.
  • The "revoke all" query matches on the same hash with revoked_at IS NULL — the condition that just failed. It updates zero rows, every time. The comment describes an action the code does not take.

Both are fixed by looking the token up unconditionally, treating revoked_at IS NOT NULL as the theft signal, and revoking by family_id — which is why the family column exists.

Rotation without a transaction can log the user out

Revoke-then-insert as two separate statements has a gap. If the insert fails — a constraint, a dropped connection, the process being restarted mid-deploy — the old token is revoked and no new one exists. The user's session is gone, and nothing anywhere logged an error that explains it. One transaction, so both happen or neither does.

The retry that looks exactly like theft

This is the uncomfortable one, and it is why A3.2's timeout matters here. The client sends a refresh, the server rotates and replies, and the reply is lost on a bad connection. The client times out and retries with the only token it has — the old one, which the server has already revoked. That is reuse, and the family gets killed. A user on a poor connection is logged out for doing nothing wrong.

Nobody has a perfect answer. The mitigation, and this lesson now implements it rather than describing it: a short grace window. Remember the token that replaced each superseded one, and if a superseded token arrives within a few seconds of its rotation, hand back the same successor again instead of declaring theft. It makes replay possible inside that window, which is a real cost — and a smaller one than logging people out on a train.

Two things about it are easy to get wrong and both are in the exercise. First, the replay must return the existing successor, not rotate again: issuing a fresh token on a retry forks the chain, so the client ends up holding one token while the newest row is another, and the next genuine refresh is then reported as reuse. Second, the grace window is measured from when the token was superseded, not from when it was created — a session refreshed every fifteen minutes for a month would otherwise be permanently outside any window you pick.

This is also why superseded_at and revoked_at are separate columns. A token that was rotated away and a token someone deliberately killed are both unusable and mean opposite things. Presenting the first is probably a retry; presenting the second is not, and it must never revoke the family — the user already ended that session on purpose, and punishing them for it would log out every device they kept.

Verifying a token the token gets to describe

jwt.verify(token, secret) with no options lets the token's own header say how it should be checked. That is the shape of the alg: none and RS256-to-HS256 confusion attacks. The library guards against the worst of it now, and pinning algorithms: ['HS256'] costs one line and does not depend on the library staying careful.

Logging out of one device logged you out of all of them

The original revoked every refresh token the user had. Signing out on a phone would end the session on the redemption web page mid-conversation. Logout revokes the family; logout-all exists separately for when that is what someone means.

It also sat behind requireAuth, so logging out required a valid access token — which the user does not have if the app has been closed for an hour. Logout failing precisely when the session is stale is the wrong way round. The refresh token in the body is the credential.

What this costs you

DecisionWhat you pay
Access tokens verified by signature They cannot be revoked. Every "kill this session" is really "kill it within 15 minutes", and anything needing instant effect — a revoked token's live WebSocket, an account being locked — has to be enforced somewhere other than the JWT.
Rotation A write on every refresh, and a table that grows by one row per refresh per user. At 15-minute access tokens that is ~96 rows per user per day; expired rows need a periodic sweep or the table becomes the biggest thing in the database.
Family-wide revocation on reuse Every false positive is a forced logout. A flaky network produces false positives, which is the grace window's whole reason for existing — and the grace window in turn is a few seconds where a stolen token still works.
FOR UPDATE on refresh Concurrent refreshes of the same session serialise. Harmless at Token's scale, and a reason the client should not be firing several at once — which is what A3.2's single-flight refresh is for.
A refresh token that never expires A device you stopped using two years ago still holds a live session until someone revokes it. There is no clock cleaning up after you, which is exactly why the device list is part of the feature rather than a later addition. The alternative — a fixed lifetime — bought nothing here: the re-verification SMS costs money and the attacker holding the phone receives the code too.

Try it yourself — this one is broken on purpose
