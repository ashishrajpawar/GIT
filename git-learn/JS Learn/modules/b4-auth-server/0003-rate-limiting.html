Rate Limiting

B4 — Lesson 3 of 3 ~40 min
Why this matters for Token

Without rate limiting, an attacker can try millions of passwords per hour against your login endpoint (brute-force). They can also flood your server with requests to make it unresponsive (DoS). Rate limiting caps how many requests a single IP or account can make in a time window. Auth endpoints are the #1 attack surface — they need the strictest limits.

What rate limiting prevents

  • Brute-force attacks — trying thousands of passwords against one account
  • Credential stuffing — testing leaked email/password pairs from other breaches
  • Account enumeration — checking which emails are registered
  • API abuse — a buggy or malicious client sending thousands of requests per second
  • Denial of service — overwhelming the server so legitimate users can't connect

Token's rate limiting strategy

Endpoint Limit Window Key
POST /auth/login 5 attempts 15 minutes IP + email
POST /auth/register 3 accounts 1 hour IP
POST /auth/refresh 10 requests 15 minutes IP
General API 100 requests 1 minute User ID or IP
POST /api/redeem 10 attempts 1 hour IP

Read the last row again, because it is the one that is load-bearing for the whole product. Every token code is one of roughly 7.9 × 1017, and that number is the reason guessing is hopeless — at a given rate. Ten attempts an hour is what turns "hopeless in theory" into "hopeless in practice". Without it, the arithmetic is just arithmetic.

Implementation with express-rate-limit

npm install express-rate-limit rate-limit-redis ioredis

Redis is not optional here (ADR-0003). The default store counts in the process's own memory, which means every replica keeps its own tally — five attempts becomes five per replica — and a deploy resets all of them. The counter has to live somewhere all replicas share. 

// api/src/middleware/rate-limit.ts
import rateLimit from 'express-rate-limit';
import RedisStore from 'rate-limit-redis';
import Redis from 'ioredis';

const redis = new Redis(process.env.REDIS_URL!);

const store = (prefix: string) => new RedisStore({
  prefix,
  sendCommand: (...args: string[]) => redis.call(...args),
});

const TOO_MANY = {
  error: 'Too many attempts. Please try again later.',
  success: false,
};

// Two limiters on login, not one. Both must pass.
//
//   by IP      - stops one host working through many accounts
//   by email   - stops many hosts working on one account
//
// A single key of `ip:email` does neither: the attacker controls both
// halves, so changing either one buys a fresh allowance.

export const loginByIp = rateLimit({
  windowMs: 15 * 60 * 1000,
  max: 20,                       // one host, all accounts
  message: TOO_MANY,
  standardHeaders: true,
  legacyHeaders: false,
  store: store('rl:login:ip:'),
});

export const loginByAccount = rateLimit({
  windowMs: 15 * 60 * 1000,
  max: 5,                        // one account, all hosts
  message: TOO_MANY,
  standardHeaders: true,
  legacyHeaders: false,
  store: store('rl:login:acct:'),
  keyGenerator: (req) => String(req.body?.email || '').trim().toLowerCase(),
  skip: (req) => !req.body?.email,   // no email: the IP limiter still applies
});

export const registerLimiter = rateLimit({
  windowMs: 60 * 60 * 1000,
  max: 3,
  message: TOO_MANY,
  store: store('rl:register:'),
});

export const apiLimiter = rateLimit({
  windowMs: 60 * 1000,
  max: 100,
  message: { error: 'Rate limit exceeded. Please slow down.', success: false },
  store: store('rl:api:'),
});

// The enumeration defence. Keyed by IP only - keying by code would let an
// attacker have a fresh allowance for every code they try, which is
// precisely the thing being defended against.
export const redeemLimiter = rateLimit({
  windowMs: 60 * 60 * 1000,
  max: 10,
  message: TOO_MANY,
  store: store('rl:redeem:'),
});

Applying rate limiters

// api/src/server.ts
import {
  loginByIp, loginByAccount, registerLimiter, apiLimiter, redeemLimiter
} from './middleware/rate-limit.js';

// Express must know it is behind Coolify's proxy, or every request appears
// to come from the proxy and shares one bucket. See "When this breaks".
app.set('trust proxy', 1);

// General limit on all API routes
app.use('/api', apiLimiter);

// Both login limiters apply, in order. The body has to be parsed before
// loginByAccount can read the email from it.
app.use('/api/auth/login', loginByIp, loginByAccount);
app.use('/api/auth/register', registerLimiter);
app.use('/api/redeem', redeemLimiter);

// Routes
app.use('/api/auth', authRoutes);
app.use('/api/tokens', requireAuth, tokenRoutes);

Rate limit response headers

When standardHeaders: true, the response includes:

RateLimit-Limit: 5          // max requests allowed
RateLimit-Remaining: 3      // requests left in this window
RateLimit-Reset: 1700001234 // when the window resets (Unix timestamp)

The mobile app reads these headers to show "try again in X minutes" without guessing.

Account lockout

Beyond rate limiting, lock accounts after repeated failures:

// In the login handler, track failures per account.
const MAX_FAILURES = 10;
const LOCKOUT_MINUTES = 30;

// One message for every way this can fail. Anything more specific tells a
// stranger whether an email is registered on the platform.
const SAME_ANSWER = 'Invalid email or password';

// A hash of a value nobody will ever type, verified against when the account
// does not exist. Without it, "no such user" returns in a millisecond while a
// real account spends ~100ms in argon2 - and the clock answers the question
// the message refused to.
const DUMMY_HASH = await argon2.hash(crypto.randomUUID());

router.post('/login', async (req, res, next) => {
  try {
    const { email, password } = loginSchema.parse(req.body);

    const { rows } = await pool.query(
      'SELECT * FROM users WHERE email = $1', [email]
    );
    const user = rows[0];

    // Always do the work, whether or not the account exists.
    const valid = await argon2.verify(user?.password_hash ?? DUMMY_HASH, password);

    if (!user) throw ApiError.unauthorized(SAME_ANSWER);

    const locked = user.locked_until && new Date(user.locked_until) > new Date();
    if (locked || !valid) {
      if (!locked) {
        // Atomic: read-then-write loses increments when attempts overlap,
        // and overlapping attempts are exactly what this counts.
        await pool.query(
          `UPDATE users
              SET failed_login_attempts = failed_login_attempts + 1,
                  locked_until = CASE
                    WHEN failed_login_attempts + 1 >= $2
                    THEN now() + ($3 || ' minutes')::interval
                    ELSE locked_until
                  END
            WHERE id = $1`,
          [user.id, MAX_FAILURES, LOCKOUT_MINUTES]
        );
      }
      throw ApiError.unauthorized(SAME_ANSWER);
    }

    // Success — reset failure count
    await pool.query(
      'UPDATE users SET failed_login_attempts = 0, locked_until = NULL WHERE id = $1',
      [user.id]
    );

    // Issue tokens...
  } catch (err) { next(err); }
});
Everything about a failed login is the same answer

Wrong password, no such account, and locked account all return the identical message, and all take roughly the same time. Telling someone "account locked" is friendlier and it confirms the email is registered — which is the first half of credential stuffing, and something the person who owns that email never agreed to publish.

This is the same rule as the redemption page's single denial message, applied to accounts instead of tokens. In both places the useful detail goes to the logs, where the owner can see it and a stranger cannot.

Why this way (and what was rejected)

Two limiters, because one composite key defends nothing

The tempting design is a single limiter keyed by `${req.ip}:${req.body.email}`, described as "IP + email so we cover both". It covers neither, and the reason is worth sitting with: the attacker supplies both halves of that key.

  • Trying many accounts from one host? Change the email each time. Every request is a different key, so every request gets a fresh allowance of five. The limiter never fires.
  • Trying one account from a botnet? Every host is a different IP, so again every request is a different key. The limiter never fires.

Two independent limiters, both of which must pass, do what the composite key claimed to: one keyed by IP alone caps how much any single host can try in total, and one keyed by the account alone caps how much punishment any single account can take no matter how many hosts are involved. The attacker can only vary the half that the other limiter is counting.

Redis, because the limit has to be one number

express-rate-limit counts in the process's memory by default, and that is wrong here for two separate reasons. Run three replicas and "five attempts" is fifteen, because each process counts its own. Deploy, and every counter resets to zero — so the way past a lockout is to wait for a release.

This is ADR-0003 in miniature: the API is stateless, and anything that needs to be true across replicas lives in Redis. A rate limit that each replica interprets privately is not a rate limit.

The redemption limiter is keyed by IP, never by code

It looks natural to limit attempts per token code. It is exactly backwards: someone guessing codes uses a different code every time, so a per-code key hands them an unlimited budget. The thing to count is the thing they cannot cheaply vary, which is the host making the requests.

Lockout, and why it is not the first line

Locking an account after ten failures is the classic answer and it comes with a gift for attackers: anyone who knows your email can lock you out of your own account, on demand, forever, by failing to log in. A protection that a stranger can trigger against you is also a weapon.

So rate limiting is the primary defence and lockout is the backstop, with a deliberately long threshold (10, not 3) and a short duration (30 minutes, not "until support unlocks it"). The alternative worth knowing about is exponential backoff per account — 1s, 2s, 4s, 8s — which makes automated guessing impossible while never fully closing the door on the real owner.

When this breaks

trust proxy, in both directions

Behind Coolify's proxy, every request arrives from the proxy's address. Forget app.set('trust proxy', 1) and all users share one bucket: the fifth failed login anywhere in the world locks out everybody. The limiter appears to work perfectly in development, where there is no proxy.

Now the other direction, which is worse because it looks like the fix. Setting trust proxy to true tells Express to believe the whole X-Forwarded-For chain — including the part the client wrote. An attacker sends a different forged value on every request and has an unlimited number of buckets. The number matters: 1 means "trust exactly one proxy in front of me".

Carrier-grade NAT, which is most of your users

An IP address is not a person. On Indian mobile networks in particular, thousands of subscribers share one public address through CGNAT — and a corporate office, a college campus or a café is the same story at smaller scale. An IP limit of five logins per fifteen minutes can lock out an entire neighbourhood because one person mistyped their password.

This is why the IP limiter is set at 20 rather than 5 while the per-account limiter holds the strict number. The account limiter is the one doing the security work; the IP limiter is a coarse net for obvious floods, and it has to be loose enough not to catch a shared exit.

The lockout message and the clock both answer the question

Two leaks in the original handler, and the second one survives fixing the first. "Account locked, try again after 14:32" confirms the email is registered — that is the obvious one. Less obvious: if (!user) throw returns in about a millisecond, while a real account spends ~100ms inside argon2. Timing answers the question the message refused to. Hence verifying against a dummy hash so both paths cost the same.

Counting failures with read-then-write

const newCount = (user.failed_login_attempts || 0) + 1;   // read
await pool.query('UPDATE users SET failed_login_attempts = $1 ...');  // write

Two attempts arriving together both read 4, both write 5, and one failure vanishes. The counter that exists to notice a burst of attempts undercounts precisely when attempts come in a burst. SET x = x + 1 in the database is atomic; the read-modify-write in application code is not.

IPv6, where an attacker owns 18 quintillion addresses

Limiting per exact IPv6 address is close to no limit at all — a typical residential allocation is a /64, which is 264 addresses to rotate through. IPv6 keys need truncating to the /64 (or /56) before counting. Express's req.ip gives you the full address, so this is something you do deliberately or not at all.

What this costs you

DecisionWhat you pay
Redis on the login path A hard dependency on the most important request in the system, and a decision you must make deliberately: if Redis is down, does login fail open or closed? Fail open and an outage becomes an unlimited brute-force window. Fail closed and a Redis restart logs nobody in. Token fails closed on auth and open on the general API limiter — the general one is protecting capacity, and refusing all traffic to protect capacity is just the outage arriving sooner.
Two limiters instead of one Two Redis round trips per login, two sets of counters to reason about, and a support question that is genuinely harder to answer: "which limit did I hit?" The response is deliberately vague about that, so the logs have to say.
Constant-time login Every login attempt with an unknown email now costs a full argon2 verification — deliberately expensive work, done on behalf of someone typing nonsense. That is a small amplification lever, and it is why the IP limiter sits in front of it.
Account lockout A denial-of-service lever pointed at your own users, in exchange for a backstop against slow guessing. Bounded by keeping the duration short and the threshold high.
standardHeaders The response tells the caller the limit, what is left, and when it resets — including callers who are attacking you, who can now pace themselves perfectly. Accepted: a legitimate client that can say "try again in 12 minutes" is worth more than the small obscurity given up.
