Rate Limiting

B4 — Lesson 3 of 3 ~40 min
Why this matters for Token

Without rate limiting, an attacker can try millions of passwords per hour against your login endpoint (brute-force). They can also flood your server with requests to make it unresponsive (DoS). Rate limiting caps how many requests a single IP or account can make in a time window. Auth endpoints are the #1 attack surface — they need the strictest limits.

What rate limiting prevents

  • Brute-force attacks — trying thousands of passwords against one account
  • Credential stuffing — testing leaked email/password pairs from other breaches
  • Account enumeration — checking which emails are registered
  • API abuse — a buggy or malicious client sending thousands of requests per second
  • Denial of service — overwhelming the server so legitimate users can't connect

Token's rate limiting strategy

Endpoint Limit Window Key
POST /auth/login 5 attempts 15 minutes IP + email
POST /auth/register 3 accounts 1 hour IP
POST /auth/refresh 10 requests 15 minutes IP
General API 100 requests 1 minute User ID or IP
POST /redeem/:code 10 attempts 1 hour IP

Implementation with express-rate-limit

npm install express-rate-limit
// api/src/middleware/rate-limit.ts
import rateLimit from 'express-rate-limit';

// Strict limiter for auth endpoints
export const authLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,  // 15 minutes
  max: 5,                      // 5 attempts per window
  message: {
    error: 'Too many attempts. Please try again in 15 minutes.',
    success: false,
  },
  standardHeaders: true,       // Return rate limit info in headers
  legacyHeaders: false,
  keyGenerator: (req) => {
    // Key by IP + email to prevent targeting one account from many IPs
    return `${req.ip}:${req.body?.email || 'unknown'}`;
  },
});

// Registration limiter
export const registerLimiter = rateLimit({
  windowMs: 60 * 60 * 1000,   // 1 hour
  max: 3,                       // 3 registrations per IP per hour
  message: {
    error: 'Too many registrations. Please try again later.',
    success: false,
  },
});

// General API limiter
export const apiLimiter = rateLimit({
  windowMs: 60 * 1000,         // 1 minute
  max: 100,                     // 100 requests per minute
  message: {
    error: 'Rate limit exceeded. Please slow down.',
    success: false,
  },
});

Applying rate limiters

// api/src/server.ts
import { authLimiter, registerLimiter, apiLimiter } from './middleware/rate-limit.js';

// General limit on all API routes
app.use('/api', apiLimiter);

// Strict limits on auth
app.use('/api/auth/login', authLimiter);
app.use('/api/auth/register', registerLimiter);

// Routes
app.use('/api/auth', authRoutes);
app.use('/api/tokens', requireAuth, tokenRoutes);

Rate limit response headers

When standardHeaders: true, the response includes:

RateLimit-Limit: 5          // max requests allowed
RateLimit-Remaining: 3      // requests left in this window
RateLimit-Reset: 1700001234 // when the window resets (Unix timestamp)

The mobile app reads these headers to show "try again in X minutes" without guessing.

Account lockout

Beyond rate limiting, lock accounts after repeated failures:

// In the login handler, track failures per account:
const MAX_FAILURES = 10;
const LOCKOUT_MINUTES = 30;

router.post('/login', authLimiter, async (req, res, next) => {
  try {
    const { email, password } = loginSchema.parse(req.body);

    const { rows } = await pool.query(
      'SELECT * FROM users WHERE email = $1', [email]
    );
    const user = rows[0];
    if (!user) throw ApiError.unauthorized('Invalid email or password');

    // Check if account is locked
    if (user.locked_until && new Date(user.locked_until) > new Date()) {
      throw ApiError.unauthorized(
        `Account locked. Try again after ${new Date(user.locked_until).toLocaleTimeString()}`
      );
    }

    const valid = await argon2.verify(user.password_hash, password);

    if (!valid) {
      // Increment failure count
      const newCount = (user.failed_login_attempts || 0) + 1;
      const lockUntil = newCount >= MAX_FAILURES
        ? new Date(Date.now() + LOCKOUT_MINUTES * 60 * 1000)
        : null;

      await pool.query(
        `UPDATE users SET failed_login_attempts = $1, locked_until = $2 WHERE id = $3`,
        [newCount, lockUntil, user.id]
      );

      throw ApiError.unauthorized('Invalid email or password');
    }

    // Success — reset failure count
    await pool.query(
      'UPDATE users SET failed_login_attempts = 0, locked_until = NULL WHERE id = $1',
      [user.id]
    );

    // Issue tokens...
  } catch (err) { next(err); }
});

COMMIT;

Production considerations

  • Redis store — in production with multiple server instances, use Redis instead of the default in-memory store so rate limits are shared across all servers.
  • IP behind proxy — if behind Nginx/Cloudflare, set app.set('trust proxy', 1) so Express reads the real IP from X-Forwarded-For.
  • Distributed attacks — IP-based limiting doesn't stop botnets (thousands of IPs). Account-based limiting (per email) is the second defense layer.
// Trust proxy (required behind Nginx/Coolify)
app.set('trust proxy', 1);
