Phone Sign-up & One-Time Codes

B4 — Lesson 1 of 3 ~50 min
Why this matters for Token

Token has no passwords. You sign in with your phone number and a six-digit code, and the device remembers you afterwards. That decision removes a whole category of work — no password rules, no reset flow, no argon2 — and replaces it with a smaller, sharper one: proving that the person holding the phone is the person who owns the number, and doing it without telling strangers which numbers have accounts.

This lesson used to be about password hashing

It taught argon2 over an email and password, and it was rewritten on 2026-08-22 when sign-in was settled as phone-only. If you are looking for the argon2 material, it is gone deliberately: there is no user-chosen secret in Token for it to hash.

Worth knowing why that is not a loss. Every password system is really two systems — the password, and the thing you fall back on when the user forgets it. That fallback is almost always a code sent to a phone or an email. Token has no email, so the fallback would have been an SMS code regardless. Building the password on top of the SMS code adds a secret users forget without removing the one they don't.

The number is the account

The users table already has what it needs, from b2/0001. Nothing is added here:

CREATE TABLE users (
  id            SERIAL PRIMARY KEY,
  phone_hash    TEXT NOT NULL UNIQUE,
  display_name  TEXT NOT NULL,
  avatar_url    TEXT,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

No email, no password_hash. A previous version of this lesson added both with an ALTER TABLE; they are not coming back.

A hash of a phone number is not an anonymisation

b3/0001 makes this argument about a different column and it applies here exactly. An Indian mobile is ten digits with a known prefix — on the order of a billion candidates, which is minutes of computation. Given a bare sha256(phone), you get the number back.

So phone_hash uses a server-side pepper, for the same reason and in the same shape as code_hash under ADR-0007:

// api/src/auth/phone.ts
import { createHash } from 'node:crypto';

const PEPPER = process.env.PHONE_HASH_PEPPER;
if (!PEPPER) throw new Error('PHONE_HASH_PEPPER is required');

export function phoneHashInput(raw) {
  // Normalisation is part of the STORED FORMAT, not a convenience.
  // Every hash ever written was produced by whatever this did on the
  // day it ran, so changing it later orphans every existing account.
  const digits = String(raw).replace(/[\s\-()]/g, '');
  const national = digits
    .replace(/^\+91/, '')     // +91XXXXXXXXXX
    .replace(/^91(?=\d{10}$)/, '')  // 91XXXXXXXXXX
    .replace(/^0/, '');       // 0XXXXXXXXXX, the STD-dialling habit

  if (!/^[6-9]\d{9}$/.test(national)) return null;  // not an Indian mobile
  return national;
}

export function phoneHash(raw) {
  const input = phoneHashInput(raw);
  if (input === null) return null;
  return createHash('sha256').update(input + PEPPER).digest('hex');
}
Lose PHONE_HASH_PEPPER and every account is unreachable

It sits in exactly the same tier as TOKEN_CODE_PEPPER and TOKEN_CODE_KEY: required at startup, validated at startup, and stored somewhere the database backups are not. Without it no one can sign in, and there is no recovery path — the whole point of a pepper is that the database alone is not enough.

Note also that +91 98765 43210, 09876543210 and 9876543210 must all reach the same row. They are one number typed three ways, and a user who signs up on one and returns on another has, as far as an un-normalised system is concerned, two accounts and no way to merge them.

Requesting a code

The OTP gets its own table. Note two columns that look ordinary and are load-bearing:

CREATE TABLE otp_requests (
  id           SERIAL PRIMARY KEY,
  phone_hash   TEXT        NOT NULL,
  code_hash    TEXT        NOT NULL,   -- the CODE is not stored either
  attempts     INTEGER     NOT NULL DEFAULT 0,
  expires_at   TIMESTAMPTZ NOT NULL,   -- NOT NULL, unlike tokens.expires_at
  consumed_at  TIMESTAMPTZ,            -- set once, never cleared
  created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_otp_phone_hash ON otp_requests (phone_hash, created_at DESC);
Two columns that mean the opposite of what they mean elsewhere
  • expires_at is NOT NULL here. On tokens, NULL means never expires and is a legitimate, common state. On an OTP there is no such thing as a code that never expires — a null expiry is a bug, not a policy, so the schema refuses to store one. Same column name, opposite meaning, because the domains are different. Carrying the tokens habit across is the single easiest mistake to make in this lesson, and the exercise below is built around it.
  • code_hash, not code. A six-digit code is trivially enumerable, so this is peppered the same way. It matters less than the token code — the thing expires in five minutes — but a database dump should not hand over every in-flight login, and the cost of doing it right is one function call.
// api/src/routes/auth.ts
import { Router } from 'express';
import { randomInt, createHash } from 'node:crypto';
import { z } from 'zod';
import { pool } from '../db/pool.js';
import { phoneHash } from '../auth/phone.js';
import { sendOtpSms } from '../sms/client.js';

const router = Router();

const OTP_TTL_MS = 5 * 60 * 1000;

const requestSchema = z.object({
  phone: z.string().min(1),
});

router.post('/auth/request-code', async (req, res, next) => {
  try {
    const { phone } = requestSchema.parse(req.body);
    const hash = phoneHash(phone);

    // randomInt, not Math.random. Six digits is a small enough space that a
    // predictable generator is genuinely guessable, and randomInt is
    // rejection-sampled for you so there is no modulo bias to reason about.
    const code = String(randomInt(0, 1000000)).padStart(6, '0');

    if (hash !== null) {
      await pool.query(
        `INSERT INTO otp_requests (phone_hash, code_hash, expires_at)
         VALUES ($1, $2, NOW() + $3::interval)`,
        [hash, hashCode(code), OTP_TTL_MS + ' milliseconds']
      );
      await sendOtpSms(phone, code);
    }

    // Identical response whether or not the number is valid or registered.
    // See the callout below -- this is the part that is easy to get wrong
    // and impossible to notice.
    res.json({ data: { sent: true }, success: true });
  } catch (err) { next(err); }
});

padStart is not cosmetic: randomInt(0, 1000000) can return 7, and a code displayed as 7 rather than 000007 is both confusing and, if you ever compare lengths, a bug.

The denial oracle, for the fifth time

"Is this number registered?" must be unanswerable

This same rule has now had to be applied at five separate layers: b7/0001's redemption endpoint, a8/0002's redemption page, b3/0004's error handler, the login below, and here. Each looked like a different problem and they are one rule: you may explain yourself to someone who has proved who they are.

It bites harder on a phone number than anywhere else in this system, because the identifier space is enumerable. There are only so many Indian mobile numbers. An endpoint that distinguishes "code sent" from "no such account" is a machine for listing every Token user, and Token's whole proposition is that being a user is not something strangers get to learn.

The trap: the message is identical and the timing is not

Here is the version this lesson shipped for months, from the old password login. Read it before reading the criticism:

// Constant-time response: don't reveal whether email exists
if (!user) {
  throw ApiError.unauthorized('Invalid email or password');
}

const valid = await argon2.verify(user.password_hash, password);
if (!valid) {
  throw ApiError.unauthorized('Invalid email or password');
}

The comment says constant-time. The message is genuinely identical on both paths. And it leaks the answer anyway, because the two paths do different amounts of work:

RequestWork doneResponse time
No such accountone indexed SELECT~1 ms
Account exists, wrong passwordSELECT + argon2 verify~200 ms

Two hundred milliseconds is not a subtle signal. It is visible over a home broadband connection, on the first attempt, without statistics. The lesson had a section called "Timing attacks" three screens below this code, explaining the concept in terms of string comparison, while its own login was timing-distinguishable in a way you could see by eye.

The general form is worth more than the specific fix: an early return is a disclosure. Whenever two branches are supposed to be indistinguishable, they have to do the same work, not just say the same words. In the OTP flow the same trap appears as skipping the SMS send for an unknown number — the response body is identical, and it comes back a great deal sooner.

The fix is to make the paths symmetric rather than to make one of them faster:

// Do the work either way. The dummy hash is a real, valid record
// with a code nobody has, so verification runs to completion and takes
// the same time as the genuine path.
const record = await findLatestOtp(hash) ?? DUMMY_OTP_RECORD;
const outcome = verifyOtp(record, submitted, Date.now());

// Only now does the answer diverge -- and only in what we LOG.
if (!outcome.accept) {
  logAuthFailure(outcome.reason);          // for us
  return res.status(400).json(REFUSAL);    // identical for everyone
}

Note the shape: one refusal object, constructed once, returned for every failing reason. This is the same structure canRedeem uses in b7/0001, and for the same reason — if the response is built per-branch, the branches drift apart the first time someone adds a helpful detail to one of them.

The SMS itself: DLT is not a signup form

Sending a transactional SMS in India requires registration on a DLT (Distributed Ledger Technology) platform, mandated by TRAI. Three consequences that shape the code rather than the paperwork:

  • The template is pre-registered and approved. You do not compose the message at send time. You register Your Token code is {#var#}. Valid 5 minutes., get a template ID, and send variables against it. A message that does not match an approved template is rejected by the operator, not by your code — so it fails in production, for real users, and never in development.
  • The sender header is registered separately — a six-character ID like TOKNAP. It is not free text and it is not per-message.
  • Approval takes time. Registration, header approval and template approval are measured in weeks, not minutes. This is the one part of Token that cannot be hurried at the end, which is why it is worth starting before it is on the critical path.

The practical effect on the API: sendOtpSms takes a template ID and a variable, never a composed string. Any lesson or code that builds the message body inline is describing a system that cannot ship in India.
