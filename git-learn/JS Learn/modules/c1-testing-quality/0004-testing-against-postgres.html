Testing Against Real Postgres

C1 — Lesson 4 of 5  |  ~50 min

Why this matters for Token

The last lesson handed the database to the handler as findByCode, and everything got easy. That was honest as far as it went, and it moved the problem rather than solving it: something still has to run the query, and the query is where a whole class of Token's bugs actually live.

Here is one that was in this course for months. The rules query has to be a LEFT JOIN, and enabled has to sit in the join condition rather than the WHERE. Both look like style. Both are load-bearing, and getting either wrong means a token with no rules — the most permissive kind — is reported as not existing at all, because the engine recognises “no such token” by getting no rows.

No mock catches that. A mock returns whatever you told it to return, and what you told it was your belief about the query — which is the thing that was wrong.

1 · The query is the part that is hard to get right

The rules lookup, written the way it must be written:

SELECT t.id, t.status, t.expires_at, t.max_uses,
       r.id AS rule_id, r.rule_type, r.payload
  FROM tokens t
  LEFT JOIN access_rules r
    ON r.token_id = t.id
   AND r.enabled                 -- in the JOIN, not the WHERE
 WHERE t.code_hash = $1;

Two decisions, both invisible:

  • LEFT JOIN rather than JOIN. An inner join returns no rows for a token that has no rules. A left join returns one row with the rule columns null.
  • AND r.enabled in the join condition. Moved into the WHERE, it filters out the null row that the left join just produced — doing exactly what the inner join did, for a token whose only rule is switched off.

And the reason both matter is one line in the engine:

if (rows.length === 0) return { allowed: false, reason: "no_such_token" };
Deny-by-default makes both failures silent and total

A token with no restrictions at all is the most useful token in the product, and either mistake turns it into one that does not exist. There is no error, no log, no exception — the holder is told the code is invalid, and the user, looking at their own screen, sees a healthy active token.

This is the general shape of a database bug: it is not a crash, it is a wrong answer that the rest of the system faithfully acts upon. Which is why the query needs a test, and the test needs a database.

2 · Isolation: one transaction per test, rolled back

Two tests sharing a database interfere, and the symptom is the worst one in testing: tests that pass alone and fail together, or the reverse, depending on order.

The cheapest fix that actually works:

import { test, before, beforeEach, afterEach } from "node:test";

let client;

before(async () => {
  client = await pool.connect();
  await migrate(client);          // once, for the whole run
});

beforeEach(async () => { await client.query("BEGIN"); });
afterEach(async () =>  { await client.query("ROLLBACK"); });

test("a token with no rules is found", async () => {
  await client.query("INSERT INTO tokens ...");
  const rows = await findByCodeHash(client, "abc");
  assert.equal(rows.length, 1);
});

Every test starts from the same database and leaves no trace. Nothing is deleted, because nothing was ever committed — a rollback is faster than a TRUNCATE and cannot forget a table someone added last week.

What this costs, stated plainly

The test must use that client. Anything reaching for a connection of its own is outside the transaction: it cannot see the rows the test inserted, and whatever it writes survives the rollback. So the connection has to be a parameter, exactly like the clock and the byte source in lesson 2 — same technique, third time.

Real concurrency cannot be tested this way. Two simultaneous redemptions of a one-use token is a question about two transactions, and it needs two connections. That is a different and slower kind of test, and it is worth writing for exactly the few places where FOR UPDATE is doing the work.

3 · Fixtures that lie

Every self-check in this course has a helper like this:

const DEFAULTS = { status: "active", expiresAt: null, maxUses: null, rules: [] };
function makeToken(over) {
  return Object.assign({}, DEFAULTS, over);
}

It is nearly right, and the flaw is one level down. Object.assign copies the top level, so every token built without an explicit rules gets the same array. One test pushes a rule onto its token, and the token in the next test has it too.

4 · The pure half, and it is the half that was wrong

A query is two things joined together: fetching rows, which needs a database, and turning rows into an object, which does not. The second half is where the LEFT JOIN decision is finally interpreted — and it is a plain function.

// A token with two rules comes back as two rows:
{ token_id: "t1", status: "active", rule_id: "r1", rule_type: "time_window",    payload: {...} }
{ token_id: "t1", status: "active", rule_id: "r2", rule_type: "contact_limit",  payload: {...} }

// A token with NO rules comes back as one row, with the rule columns null:
{ token_id: "t1", status: "active", rule_id: null, rule_type: null, payload: null }

// A code nobody has ever issued comes back as nothing at all:
// (no rows)

Three shapes, three different answers, and only two of them are “found”.
