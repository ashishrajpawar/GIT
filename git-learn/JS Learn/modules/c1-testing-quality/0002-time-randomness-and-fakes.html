Time, Randomness and Fakes

C1 — Lesson 2 of 5  |  ~50 min

Why this matters for Token

Three things in Token cannot be tested by calling the function and looking at what comes back, because the answer depends on something the test does not own:

  • The clock. Whether a token has expired depends on what time it is. A test written today passes today.
  • Randomness. A token code is twelve random characters. You cannot assert what generate() returns, because that is the point of it.
  • The network. The OTP goes through an SMS aggregator. A test suite that sends real messages costs money and needs a phone.

All three have the same fix, and it is not a mocking library. It is that the function stops reaching out for the thing and is handed it instead. That change turns a function you cannot test into a function you cannot get wrong quietly — and, as a side effect, it is how you prove that the token generator does not have the modulo bias this course keeps warning about.

1 · The clock: Date.now() is an input pretending to be a fact

Here is the natural way to write it, and it is untestable:

function isExpired(token) {
  if (token.expiresAt === null) return false;
  return new Date(token.expiresAt) <= new Date();   // <-- reaches out for the clock
}

To test the expired case you need a token whose expiresAt is in the past, which is fine. To test the not expired case you need one in the future — so you write "2030-01-01", and your test suite acquires an expiry date of its own. It will start failing, for real, on a Tuesday in 2030, and whoever is on call will spend an hour on it.

The fix is one parameter:

function isExpired(token, now) {
  if (token.expiresAt === null) return false;
  return new Date(token.expiresAt) <= now;
}

The caller passes new Date(). The test passes whatever moment it wants to talk about. Nothing is mocked, nothing is patched, and the function got shorter.

Token's actual trap: new Date(null) is 1 January 1970

In Token, expires_at being null means never expires. And new Date(null) is not an error and is not Invalid Date — it is the epoch, which is before every date you will ever compare it to.

So an isExpired without the null guard reports that a token which never expires expired 56 years ago. Deny-by-default means the holder is refused, the user sees a live token, and the two of them argue about it.

This is why the guard comes before the parse, and it is the same rule as max_uses: null means unlimited, 0 means no uses at all, and only one of the two is falsy.

2 · Randomness: own the source and it stops being random

Token codes are twelve characters from a 31-character alphabet:

23456789ABCDEFGHJKMNPQRSTUVWXYZ    // 31 characters
// 36 alphanumerics minus the five that look like each other: 0 O 1 I L

You cannot assert what a generator returns. You can assert everything else about it, the moment the randomness arrives as a parameter instead of being fetched:

function makeCodeGenerator(nextByte) {
  // nextByte() returns 0-255. In production it comes from crypto.
  // In a test it comes from a list you wrote.
}

Now a test can say “given these exact bytes, the code must be exactly this”, which is not a statement about randomness at all. It is a statement about the mapping — and the mapping is where the bugs are.

The bug that hides in %, and why it is not paranoia

The obvious mapping is ALPHABET[byte % 31]. It is biased, and the arithmetic is small enough to do by hand: 256 ÷ 31 is 8 remainder 8.

Bytes 0–247 cover the alphabet exactly eight times each. The eight left over — 248 to 255 — wrap round and land on the first eight characters again. So 2 through 9 come up nine times in 256 and the other twenty-three come up eight. Every digit is 12.5% more likely than every letter.

Nobody sees this. Every code looks fine, the format is right, no test fails. It is visible only as a statistical property of many codes — which is exactly the kind of thing a test can check once the byte source is yours, and cannot check at all while it is real randomness.

The fix is rejection sampling: throw away any byte of 248 or more and draw again. You discard 3% of your bytes and the remaining ones are uniform.

Try it yourself

Count them. The first eight characters of the alphabet are the ones to look at.

3 · The network: a fake records what you sent

The third uncontrollable thing is the SMS aggregator, and it differs from the other two in an important way: you usually care more about what was sent than about what came back.

Token's OTP is subject to two rules from earlier in the course, and both are assertions about the outgoing call rather than about the response:

  • The response to “send me a code” must be identical whether or not the number is registered. Otherwise the endpoint is a list of who has an account, across a phone-number space small enough to enumerate completely.
  • A message body never carries anything but the six digits. No token code, no name.

A fake — a stand-in that remembers how it was called — makes both of those a one-line test.

Try it yourself

Fake, not mock — and why this course does not reach for a library

A fake is a real object with a simpler implementation: an in-memory SMS sender, a byte source reading from a list, a now you passed in. A mock is usually a library reaching into the module system to replace something a function is going to fetch.

The difference that matters here: a fake is only possible if the function accepts its dependency, so reaching for fakes pushes the design towards handing things in. Mocking libraries exist precisely so you do not have to make that change — which means they let a function keep reaching out for the clock, the database and the network, and that function stays hard to reason about long after its tests are green.
