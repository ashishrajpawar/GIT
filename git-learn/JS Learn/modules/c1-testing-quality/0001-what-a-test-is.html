What a Test Is

C1 — Lesson 1 of 5  |  ~45 min

Why this matters for Token

You have written a test in every single lesson of this course. Scroll to the bottom of any exercise and you will find the line // --- Self-check: leave everything below this line alone --- and, under it, a function called check. That is a test suite. Nobody called it one.

This lesson is about turning that habit into the real thing, because the API you are about to build has behaviour that cannot be checked by looking at it. A revoked token and a token that never existed must produce byte-identical responses. A redemption must be counted exactly once even when two requests arrive together. A rule the engine does not recognise must be refused, not permitted. None of those are visible on a screen. All of them are one assertion each.

By the end you will have written the runner that the rest of this module uses — and you will know why the first thing it has to do is survive a test that explodes.

1 · You have been doing this since lesson one

Here is the self-check from 01/0004, reduced to its skeleton:

function check(label, passed, detail) {
  console.log((passed ? "PASS  " : "FAIL  ") + label);
  if (!passed && detail) console.log("      " + detail);
}

check("a revoked token is revoked",
      checkAccess(token({ revokedAt: "2026-08-15" })) === "revoked",
      "got: " + checkAccess(token({ revokedAt: "2026-08-15" })));

Three things are going on, and every test ever written does the same three:

  • Arrange — build the world the behaviour needs. token({ revokedAt: "2026-08-15" }).
  • Act — do the one thing under test. checkAccess(...).
  • Assert — state what should now be true, and fail loudly if it is not. === "revoked".

The fourth thing is the one people skip, and it is why check takes a third argument: a failing test must say what it actually got. A test that prints FAIL a revoked token is revoked tells you a fact you already knew from the word FAIL. A test that prints got: paused tells you which branch ran, and usually that is the whole debugging session.

The name is documentation, so write it as a sentence

"a revoked token is revoked" is a claim about the system. "test 3" and "checkAccess works" are not. When a suite of forty tests fails at 2am, the names are the only thing you read — and a good name means you often know the cause before you open the file.

2 · The real tool is already installed

Node has had a test runner built in since v18. There is nothing to install, which suits this project: the course has no package.json on purpose, and the Token API will pick up dependencies only when they earn their place.

// api/src/access.test.js
import { test } from "node:test";
import assert from "node:assert/strict";

import { checkAccess } from "./access.js";

const token = (over) => ({
  revokedAt: null, isPaused: false, timesUsed: 0, maxUses: 5, ...over
});

test("a fresh token is allowed", () => {
  assert.equal(checkAccess(token()), "allowed");
});

test("revoking beats pausing", () => {
  assert.equal(checkAccess(token({ revokedAt: "2026-08-15", isPaused: true })), "revoked");
});

Run it with node --test. You get the pass and fail counts, and for a failure, the expected and actual values — the third argument of check, done for you.

Import node:assert/strict, never bare node:assert

The default assert.equal compares with ==. So this passes:

assert.equal(token.timesUsed, 3);   // passes when timesUsed is the STRING "3"

That is the exact bug 01/0002 is about, and a test written with loose equality is blind to it. Worse than blind: it is evidence that the field is a number, filed away and trusted by the next person.

node:assert/strict makes every comparison strict. There is no reason to use anything else, and the failure mode of forgetting is a green suite over a real defect.

3 · A test only tests the case someone thought of

This is not a warning about laziness. It is the single most reliable way a test suite lies to you, and it happened in this course, in the lesson you have already done.

checkAccess has four rules in a fixed order: revoked, then paused, then the use limit, then allowed. The self-check in 01/0004 tested that revoked beats paused and stopped there. So this implementation passed every check:

function checkAccess(token) {
  if (token.revokedAt !== null)              return "revoked";
  else if (token.timesUsed >= token.maxUses) return "limit reached";   // <-- swapped
  else if (token.isPaused === true)          return "paused";          // <-- swapped
  else                                       return "allowed";
}

Every token with a single state comes out right. Only a token that is paused and at its limit is wrong — it reports "limit reached", a state the user cannot clear, which hides the Resume button that would actually fix it.

Four rules in order have three adjacent pairs, and one test is not three

The suite checked one pair out of three and called it precedence. That is the general shape: the author tests the case they were thinking about, and the case they were not thinking about is the bug.

When behaviour is “these rules, in this order”, the test list is not one case per rule. It is one case per rule plus one case per pair that can be true at once, and you write them by reading the order, not by imagining scenarios.

4 · The trap that decides how a runner is written

A test does not report a failure by returning false. It reports one by throwing — that is what assert does. Which means a test runner spends its whole life handling exceptions, and the naive loop has a defect that is much worse than it looks:

for (const t of tests) {
  t.fn();                 // an assertion failure throws out of the whole loop
  console.log("PASS " + t.name);
}

The second test throws. Tests three through forty never run. The output shows one pass and a stack trace, and the honest reading of that output is “I know one thing passed and I know nothing at all about the other thirty-nine.”

This project has been caught by it three times, most recently this week

The self-checks in this course are one long try block. When a wrong answer throws rather than returning the wrong value, every check below the throw is skipped — so the suite reports the crash and stays silent about the eight things it never got to.

It reads exactly like a broken test runner, which is why it wastes an afternoon each time. A test that fails must not be able to take another test with it. That single requirement is most of the design of the exercise below.

5 · What a runner has to get right

Four things, and only the first is obvious:

  1. Run every test, whatever the ones before it did.
  2. Report what failed and why — name and message, not just a count. A suite that prints 37 passed, 3 failed and nothing else has told you to go and find them yourself.
  3. Keep the order the tests were written in. Failures read as a story: the first one is usually the cause and the rest are consequences.
  4. Survive a test that throws something that is not an Error. throw "boom" is legal JavaScript, and a runner that reads err.message without checking reports undefined as the reason for the failure — which is worse than reporting nothing, because it looks like a bug in the runner.
