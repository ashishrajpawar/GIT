Testing an HTTP Handler

C1 — Lesson 3 of 5  |  ~50 min

Why this matters for Token

POST /api/redeem is the endpoint a stranger reaches. It takes a code and answers one of two things: here is your conversation, or no.

The interesting requirement is not that it works. It is that the “no” must be the same “no” every time. A revoked token, an expired one, one that has been used up, one that never existed, and one whose owner has deleted their account must all produce a byte-identical response. Any difference at all turns the endpoint into a machine that answers questions nobody should be able to ask: does this code exist? did someone close their account?

You cannot see that requirement on a screen and you cannot check it by hand, because it is a statement about five responses being the same. It is four lines of test — and the only reason it is four lines is that the handler is a function you can call.

1 · A handler is a function; the server is wiring

The version that needs a server to test looks like this:

app.post("/api/redeem", async (req, res) => {
  const token = await db.query("SELECT * FROM tokens WHERE code_hash = $1", [hash(req.body.code)]);
  if (!token) return res.status(404).json({ error: "invalid_or_expired" });
  const conversation = await db.query("INSERT INTO conversations ...");
  logger.info("redeemed", { tokenId: token.id });
  res.json({ conversationId: conversation.id });
});

To test it you need a running Postgres, a port, an HTTP client, and a logger you can read back. Most people write two of those and give up, which is how an endpoint ends up with no tests at all.

The same logic, separated from its wiring:

// The decision — a plain function. Everything it needs, it is given.
export function handleRedeem(req, deps) { /* returns { status, body } */ }

// The wiring — written once, and boring on purpose.
app.post("/api/redeem", async (req, res) => {
  const result = await handleRedeem(req, { findByCode, createConversation, now: new Date(), log });
  res.status(result.status).json(result.body);
});
What you gain, stated honestly

You are not testing that Express parsed the JSON body, that the route path is right, or that the status code reached the socket. Those are real things and they can break. What you get instead is every decision the endpoint makes, callable in a microsecond, including the six cases that are tedious to arrange over HTTP and the one — identical denials — that is nearly impossible to check any other way.

The wiring is then three lines that are the same on every route, and a single test that the server starts and answers one request covers all of it.

Try it yourself

No server, no port, no client. A request is an object.

2 · The denial oracle, and what makes a difference safe

Here are five responses a reasonable developer writes, each of them helpful:

{ status: 404, body: { error: "no_such_code" } }         // never existed
{ status: 410, body: { error: "revoked" } }              // revoked
{ status: 410, body: { error: "expired" } }              // expired
{ status: 429, body: { error: "use_limit_reached" } }    // exhausted
{ status: 404, body: { error: "account_closed" } }       // owner deleted

Together they are a search engine for other people's business. Feed it codes and it tells you which ones are real. Feed it one code repeatedly and it tells you when the owner revoked it, when their token expired, and — the worst of the five — that somebody exercised their right to erasure.

The rule is one response:

{ status: 404, body: { error: "invalid_or_expired" } }   // all five, always
Not every difference leaks — and knowing which is the actual skill

Refusing a malformed code with a different answer is fine, and this lesson does exactly that. HELLO is not a token code: it is the wrong length and uses letters the alphabet excludes. The client can work that out without asking, so telling it nothing it could not already compute reveals nothing.

The test is not “are these responses different”. It is “could the caller have worked this out without asking us?” Shape: yes. Existence: no. Getting this backwards in the cautious direction has its own cost — an API that answers everything with 400 is one nobody can debug.

Try it yourself

The oracle, made concrete. Count how many distinct answers come back.

3 · What the log must not contain

The code moved into the request body precisely so it would stay out of the URL, the proxy's access log, browser history and Referer. Writing it into your own application log on the way past undoes all of that in one line.

So: log the token's id. It identifies the row for anyone who can already query the database and is worth nothing to anyone who cannot, which is the property an identifier in a log should have.

The dangerous log line is the one with nothing to put in it

At “redemption denied” there is often no token — that is what being denied means. There is no id, and the pull towards writing something identifying is exactly how the code ends up in the log. requestId is enough: it ties the line to the rest of the request without saying anything about the token.

There is a second reason the denial log must carry nothing about the token, and it is the same one as the response: a log that says tokenId on some denials and not on others is the denial oracle again, written down for whoever reads the logs later. The five cases have to be indistinguishable in both places.

Try it yourself — broken on purpose

Read the error. Then notice that the line which crashes is the line trying to be helpful.

Now build it yourself

The wiring, for completeness

This part is not tested by the suite above, and is written once:

import express from "express";
import { handleRedeem } from "./redeem.js";

const app = express();
app.use(express.json());

app.post("/api/redeem", async (req, res) => {
  const result = await handleRedeem(req, {
    findByCode: (code) => tokens.findByCode(code),
    createConversation: (tokenId) => conversations.create(tokenId),
    now: new Date(),
    log: logger.info.bind(logger)
  });
  res.status(result.status).json(result.body);
});

// Note the route: the code is in the BODY, never in the path. A path
// reaches the proxy access log, browser history and Referer, which is
// exactly what hashing the code in the database was for.
app.listen(3000);
