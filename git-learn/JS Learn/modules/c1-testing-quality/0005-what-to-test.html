What to Test

C1 — Lesson 5 of 5  |  ~50 min

Why this matters for Token

Four lessons have been about how. This one is about the question that decides whether any of it was worth doing: which sentences are worth writing down?

The usual answer is a number. Line coverage is easy to measure, hard to argue with, and it is measuring the wrong thing — it counts lines your tests executed, and says nothing about what they checked. This course has a worked example of the gap, found this week, in a lesson four steps from the beginning.

What replaces the number is a short list of properties that keep going wrong in this specific product, and one technique for checking a property against many inputs instead of one.

1 · The number that lies

Here is checkAccess again, with the use limit and the pause the wrong way round:

function checkAccess(token) {
  if (token.revokedAt !== null)              return "revoked";
  if (token.timesUsed >= token.maxUses)      return "limit reached";
  if (token.isPaused === true)               return "paused";
  return "allowed";
}

Now four tests, one per state: a fresh token, a revoked one, a paused one, a spent one. All four pass. Every line of the function has been executed. Coverage is 100%. The function is wrong.

The bug needs a token that is paused and at its limit, and no line of the function is unvisited when that case is missing — because the case is not a line. It is a path: the combination of one branch being false while another is true.

What coverage is actually good for, which is not nothing

It answers one question well: is there code here that no test touches at all? A file at 12% is telling you something true and worth acting on.

It is useless as a target. The moment a number is a goal, the cheapest way to raise it is to execute more lines without asserting anything — and a test with no assertion runs every line it visits. A suite can be driven to 100% by a person who never once thought about whether the code is right.

Read it as a floor, never as a score. Low coverage is evidence. High coverage is not.

Try it yourself

The tally is real: every line runs, and the suite is green over a wrong answer.

2 · What is worth testing: properties, not examples

An example says this input gives that output. A property says something that must be true of every input, and it is usually one sentence. Six of them have caused real defects in this course, and they generalise past it:

PropertyIn TokenWhat went wrong
Precedence — when several rules apply, one wins, in a fixed order revoked → expired → exhausted → paused Four tests, one per state, and the order untested. Found this week
Exactly once — an effect happens one time, however many requests arrive a redemption counts against max_uses once Needs two connections and FOR UPDATE; a single-threaded test cannot see it
Deny by default — input nobody planned for is refused, not permitted an unrecognised rule_type Fell through to allowed. A rule the engine cannot evaluate was a rule it ignored
Null is not zero — absent and empty are different answers max_uses: null unlimited, 0 none if (token.maxUses) made a token that permits nothing permit everything
Indistinguishability — several causes produce one identical answer the five ways a redemption fails Only visible across the set; each response alone looks correct
Conservation — the parts add up to the whole active + revoked + paused === total A token counted in two states, hidden by another being uncounted
How to find them without a table

Two questions do most of the work.

“What must be true no matter what?” The answers are properties. They are usually already written down somewhere in prose — in an ADR, in a code comment, in a sentence someone said in review — and turning that sentence into an assertion is most of the job.

“Which of these can be true at the same time?” Every pair that can co-occur is a test, and it is the pairs rather than the states that catch precedence bugs. Four states in a fixed order have three adjacent pairs; a suite with one test per state has covered none of them.

3 · Checking a property against many inputs

Once you have a property, testing it against one example is a waste of a good sentence. The technique is to generate many inputs and check the property against each — and, when one fails, to report the input, because that is the entire value of the exercise.

const result = forAll(everyTokenState, (t) => ONE_OF.includes(checkAccess(t)), 100);
// { ok: false, checked: 7, counterExample: { isPaused: true, timesUsed: 5, ... } }

The generator is a function of an index, so the run is deterministic — the same idea as the byte source in lesson 2, for the same reason. A property test that finds a counter-example only sometimes is a rumour rather than a bug report.

4 · What this does not do

Real property-testing libraries do one more thing, and it is worth knowing the name because you will want it eventually. Shrinking: having found a failing input, they repeatedly simplify it and re-check, so a counter-example that arrives as a 400-character object is reported as the three fields that actually matter.

That is genuinely useful and it is not the part that finds bugs. The part that finds bugs is writing down a sentence that must always be true and then not trusting it — which is forty lines and no dependency.

The honest limit of this whole module

Every technique here tests what someone thought to write down. Lesson 1 said a green suite proves only that the cases someone imagined behave as that person expected, and nothing in the four lessons since has changed it — property tests widen the set of inputs, not the set of ideas.

What actually moves the line is the habit underneath: when you find a bug, ask what sentence it violated, and add that sentence rather than that example. The precedence bug in 01/0004 produced one new assertion. The sentence it violated — “when two states are true at once, the earlier rule wins” — is worth more, because it is a question you can now ask of every other function in the product.
