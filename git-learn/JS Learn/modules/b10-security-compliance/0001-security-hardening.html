Security Hardening

B10 — Lesson 1 of 2  |  ~55 min

Why this matters for Token: Token's core promise is privacy. If your server is compromised, every user's contact graph, messages, and tokens are exposed. A single SQL injection or leaked secret undoes everything the product stands for. This lesson covers the defences that prevent that from happening.

SQL Injection — The #1 Rule

Never concatenate user input into SQL strings. Always use parameterised queries.

// ❌ VULNERABLE — string concatenation
async function getToken(code: string) {
  // An attacker sends: code = "'; DROP TABLE tokens; --"
  const result = await db.query(
    `SELECT * FROM tokens WHERE code = '${code}'`
  );
  return result.rows[0];
}

// ✓ SAFE — parameterised query
async function getToken(code: string) {
  // The $1 placeholder is never interpreted as SQL
  const result = await db.query(
    'SELECT * FROM tokens WHERE code = $1',
    [code]
  );
  return result.rows[0];
}

Why Parameterised Queries Are Safe

The database driver sends the query template and values separately. The database compiles the template first, then binds the values as data — never as SQL syntax. Even if the value contains '; DROP TABLE, it's treated as a literal string, not a command.

// What the database sees with parameterised queries:
// Template: "SELECT * FROM tokens WHERE code = $1"
// Values:   ["'; DROP TABLE tokens; --"]
// Result:   looks for a token with code literally "'; DROP TABLE tokens; --"
//           (finds nothing, attacks nothing)

Auditing Your Codebase

// Search for potential injection vulnerabilities:
// grep for template literals or string concatenation in .query() calls

// Red flags:
db.query(`SELECT * FROM ${table} WHERE id = ${id}`)     // ❌
db.query("SELECT * FROM " + table + " WHERE id = " + id) // ❌
db.query(\`UPDATE tokens SET name = '\${name}'\`)          // ❌

// Safe patterns:
db.query('SELECT * FROM tokens WHERE id = $1', [id])     // ✓
db.query('SELECT * FROM tokens WHERE code = $1 AND user_id = $2', [code, userId]) // ✓

Secret Rotation

// If a secret is compromised, you need to rotate it without downtime.
// Strategy: support TWO secrets simultaneously during rotation.

// api/src/auth/verifyToken.ts
import jwt from 'jsonwebtoken';

const JWT_SECRETS = [
  process.env.JWT_SECRET,           // Current secret
  process.env.JWT_SECRET_PREVIOUS,  // Previous secret (during rotation)
].filter(Boolean) as string[];

export function verifyAccessToken(token: string): JwtPayload | null {
  for (const secret of JWT_SECRETS) {
    try {
      return jwt.verify(token, secret) as JwtPayload;
    } catch {
      continue; // Try next secret
    }
  }
  return null; // None worked — token is invalid
}

// Rotation process:
// 1. Generate new secret
// 2. Set JWT_SECRET = new, JWT_SECRET_PREVIOUS = old
// 3. Deploy — new tokens signed with new secret, old tokens still verify
// 4. Wait for all old tokens to expire (access tokens: 15 min)
// 5. Remove JWT_SECRET_PREVIOUS

CORS — Cross-Origin Resource Sharing

CORS controls which websites can make requests to your API. Without it, any website could make requests to api.tokn.app using a logged-in user's cookies/credentials.

// api/src/middleware/cors.ts
import cors from 'cors';

const ALLOWED_ORIGINS = [
  'https://tokn.app',              // Production web client
  'http://localhost:5173',         // Local Vite dev server
  'http://localhost:19006',        // Expo web (development only)
];

export const corsMiddleware = cors({
  origin: (origin, callback) => {
    // Allow requests with no origin (mobile apps, server-to-server)
    if (!origin) return callback(null, true);

    if (ALLOWED_ORIGINS.includes(origin)) {
      callback(null, true);
    } else {
      callback(new Error(`Origin ${origin} not allowed by CORS`));
    }
  },
  credentials: true, // Allow cookies/auth headers
  methods: ['GET', 'POST', 'PUT', 'DELETE', 'PATCH'],
  allowedHeaders: ['Content-Type', 'Authorization', 'X-Request-ID'],
  maxAge: 86400, // Cache preflight for 24 hours
});

Why Mobile Apps Don't Need CORS

CORS is a browser security mechanism. React Native apps make HTTP requests directly (like a server would) — they don't send an Origin header. That's why we allow requests with no origin.

Security Headers

HTTP headers that instruct browsers to enable security features:

# Install helmet (sets security headers automatically)
npm install helmet
// api/src/app.ts
import helmet from 'helmet';

app.use(helmet({
  // Content Security Policy — controls what resources the page can load
  contentSecurityPolicy: {
    directives: {
      defaultSrc: ["'self'"],
      scriptSrc: ["'self'"],
      styleSrc: ["'self'", "'unsafe-inline'"],  // Needed for some UI frameworks
      imgSrc: ["'self'", "data:", "https:"],
      connectSrc: ["'self'", "wss://api.tokn.app"],
    },
  },
  // Strict Transport Security — force HTTPS for 1 year
  hsts: {
    maxAge: 31536000,
    includeSubDomains: true,
    preload: true,
  },
  // Prevent clickjacking (embedding in iframes)
  frameguard: { action: 'deny' },
  // Don't reveal server software
  hidePoweredBy: true,
  // Prevent MIME type sniffing
  noSniff: true,
  // Referrer Policy — don't leak URLs to third parties
  referrerPolicy: { policy: 'strict-origin-when-cross-origin' },
}));

Input Validation at the Boundary

You already use zod for validation (from B3). Here's the security perspective — validate everything at the API boundary, even if the client already validated it:

// api/src/routes/tokens.ts
import { z } from 'zod';

const createTokenSchema = z.object({
  label: z.string()
    .min(1)
    .max(100)
    .trim(),
  rules: z.object({
    maxRedemptions: z.number().int().positive().max(1000).optional(),
    expiresAt: z.string().datetime().optional(),
    allowedCategories: z.array(z.string().max(50)).max(20).optional(),
  }).optional(),
});

// In the route handler:
export async function createToken(req: Request, res: Response) {
  const parsed = createTokenSchema.safeParse(req.body);

  if (!parsed.success) {
    return res.status(400).json({
      error: 'validation_error',
      details: parsed.error.flatten(),
    });
  }

  // parsed.data is now typed AND validated — safe to use
  const { label, rules } = parsed.data;
  // ...
}

Output Encoding

When storing user-generated content (token labels, messages), encode it before rendering in HTML contexts to prevent stored XSS:

// The redemption web page displays the token holder's name.
// If that name contains <script>alert('xss')</script>, you have a problem.

// React handles this automatically for JSX content:
// <p>{holderName}</p>  ← React escapes this by default ✓

// BUT: dangerouslySetInnerHTML bypasses it:
// <div dangerouslySetInnerHTML={{ __html: holderName }} /> ← ❌ NEVER with user data

// On the server side, if you ever generate HTML:
import { encode } from 'html-entities';
const safeName = encode(holderName); // "<script>" becomes "&lt;script&gt;"

Broken Access Control

The most critical check: does this user own this resource?

// ❌ VULNERABLE — no ownership check
router.get('/tokens/:id', async (req, res) => {
  const token = await db.query('SELECT * FROM tokens WHERE id = $1', [req.params.id]);
  res.json(token.rows[0]); // Any logged-in user can read ANY token
});

// ✓ SAFE — ownership enforced, and only the columns the client needs
router.get('/tokens/:id', authenticateJWT, async (req, res) => {
  const token = await db.query(
    `SELECT id, label, status, max_uses, expires_at, created_at
       FROM tokens WHERE id = $1 AND user_id = $2`,
    [req.params.id, req.user.id]  // Only returns if user owns it
  );

  if (!token.rows[0]) {
    // 404, not 403. See below: "not yours" and "does not exist" must be
    // one answer, or this endpoint enumerates other people's token ids.
    return res.status(404).json({ error: 'not found' });
  }

  res.json(token.rows[0]);
});
Two things that example does deliberately

It names its columns. The version above it says SELECT * and then res.json(row), which was harmless until b2/0001 added code_hash and code_enc to that table. From that moment the endpoint returned both, to every caller, and nothing failed. SELECT * in a handler is a standing promise to return whatever a future migration adds, made by someone who will not be there when it is added.

It answers 404 and not 403. A 403 says "this exists and it is not yours", which turns the endpoint into an id enumerator: walk the integers, and 403s map out other people's tokens while 404s map the gaps. Because the query is scoped by user_id, the handler genuinely cannot tell the two apart — the safe answer falls out of the query shape rather than having to be remembered. That is the version to aim for: not a rule you apply, a structure in which the rule cannot be broken.

The Pattern: Always Include user_id in Queries

// Every query that reads or modifies user data should include the ownership clause:

// Read user's tokens
'SELECT * FROM tokens WHERE user_id = $1'

// Update a specific token (owned by user)
'UPDATE tokens SET label = $2 WHERE id = $1 AND user_id = $3'

// Delete (revoke) a token (owned by user)
'UPDATE tokens SET revoked_at = NOW() WHERE id = $1 AND user_id = $2'

// Read messages in a conversation this user owns the token for.
// The chain is message -> conversation -> token -> owner, and it is
// the relationship that actually exists: a conversation exists
// BECAUSE a token was redeemed.
`SELECT m.*
   FROM messages m
   JOIN conversations c ON c.id = m.conversation_id
   JOIN tokens t        ON t.id = c.token_id
  WHERE m.conversation_id = $1
    AND t.user_id = $2`
There is no participants table, and that is a decision rather than an omission

This query used to join a participants(user_id, conversation_id) junction table, which no migration has ever created. It was resolved on 2026-08-23 by deleting it from the plan — see c5/0005.

A junction table records a membership that can vary. Here nothing varies: a conversation has exactly two parties, conversations.token_id determines both, there are no group conversations, and the holder is not a user at all — b2/0002 identifies them by holder_session_id, so half of every row in that table could never have been filled in.

The ownership rule is unchanged and the chain is longer. Two joins instead of one is the honest price of not having a table that would have been permanently half-empty.

Preventing Common Attacks

Timing Attacks on Token Lookup

// When checking if a token code is valid, use constant-time comparison
// to prevent attackers from guessing codes character by character.

import { timingSafeEqual } from 'crypto';

function safeCompare(a: string, b: string): boolean {
  if (a.length !== b.length) return false;
  return timingSafeEqual(Buffer.from(a), Buffer.from(b));
}

// For database lookups, this is less relevant (the DB handles comparison),
// but for API key validation or HMAC verification, always use timingSafeEqual.

Request Size Limits

// Prevent denial of service via oversized payloads
import express from 'express';

app.use(express.json({ limit: '1mb' }));  // Reject bodies > 1MB
app.use(express.urlencoded({ limit: '1mb', extended: true }));

// For file uploads (if you ever add them), use streaming with size limits
// Never buffer an entire upload in memory

The two decisions this product's security actually rests on

Everything above is general — parameterised queries, CORS, headers, ownership checks. They apply to any API and you should do all of them. Neither of the two decisions that make Token's security specific is on that list, and both are the kind that cannot be added later.

1. The token code is never stored, and never explained

A token code is a capability: whoever reads it can use it. That makes it unlike a password, which identifies someone who then has to prove other things too. There is no second factor behind a code — the code is the access.

Two consequences run through the whole codebase (ADR-0007):

  • It is not in the database. tokens holds code_hash — SHA-256 of the normalised code plus a server-side pepper, which is the only way a token is ever looked up — and code_enc, decrypted for one token at a time when the owner asks to see it, and logged when that happens. A dump of this database is not a pile of working tokens.
  • It is never in a URL, a log line, a JWT or a push payload. Each of those is a place a capability gets copied to somewhere you did not choose — a proxy access log, browser history, a Referer header, an error tracker's breadcrumbs, Google's servers.

The pepper is the part people leave out. A hash of a low-entropy input is not one-way in any useful sense — a phone number is ten digits and a few minutes of work. A token code is not low-entropy (3112 is about 7.9 × 1017), so the pepper is not protecting against brute force. It protects against a stolen database being useful on its own: without the environment variable, the hashes match nothing.

2. A refusal never explains itself to a stranger

This one has had to be applied at three separate layers, and it is worth seeing all three together because each looked like a different problem at the time:

LayerThe tempting versionWhat it gives away
b7/0001 — the redemption endpoint 404 "not found" vs 403 "revoked" whether a code exists
a8/0002 — the redemption page separate screens for expired, revoked, exhausted the same thing, in plain English
b3/0004 — the error handler 400 with field details vs 404 without whether the code was well-formed

b7/0001 derives that guessing a code would take about 25,000 years. That figure holds only while each guess teaches the attacker nothing. Every distinguishable response is roughly a bit per attempt handed to whoever is asking, and you do not get to choose which measurement they use — they will use the cheapest one.

So: one status, one message, for every refusal on a public endpoint. The real reason goes in the log, where it is useful to you and invisible to them. And the rule that makes this tractable rather than paranoid — you may explain yourself to someone who has proved who they are. An authenticated owner gets field-level validation errors and a precise 403; a stranger with a code gets one sentence.

It costs real usability, and that is not a reason to skip it

A holder whose token genuinely expired is told only that the link is unavailable. That is annoying and it is the correct trade, because the page cannot tell them apart from someone typing codes in a loop. The person who can be told is the issuer, on a screen that required a login.

The secret this system leaks most easily: its own logs

Trace what has already been done to protect a token code. It is kept out of URLs, because a path is written into access logs, browser history and the Referer header (B3.3). It is kept out of the database, stored as a hash for lookup and an encrypted copy for display (ADR-0007). Backups are handled so the two never travel together (B9.2).

Then one line of ordinary, sensible middleware undoes all of it: 

// This is a normal thing to write and it is a disaster here
app.use((req, _res, next) => {
  logger.info({ method: req.method, path: req.path, body: req.body });
  next();
});

// POST /api/redeem  { "code": "MERC-8GH2-KP4X", "holderName": "Ravi" }
//                                ^^^^^^^^^^^^^^
// now in a plain-text file, on the same box as the database, for as long
// as the log retention policy says - and in every copy of those logs.

The body became the sensitive part precisely because we moved the code there. The decision that protected it from one exposure moved it into another, and the second one is easier to make by accident.

Redact by allow-list, never by deny-list

// api/src/logger.ts
import pino from 'pino';

export const logger = pino({
  redact: {
    paths: [
      'req.body.code', 'req.body.password', 'req.body.refreshToken',
      'req.headers.authorization', 'req.headers.cookie',
    ],
    censor: '[redacted]',
  },
});

That list is a deny-list, and a deny-list is a list of the mistakes you have already thought of. The field added next month is not on it. Prefer logging chosen fields: 

// Nothing is logged unless it is named here.
logger.info({
  method: req.method,
  path: req.path,
  status: res.statusCode,
  durationMs,
  userId: req.user?.id,
  requestId: req.id,
});
Your error tracker captures bodies too

Sentry and GlitchTip attach request data to exceptions by default. An unhandled error inside the redeem handler therefore ships the code to the error tracker — a second system, with its own retention, its own access list, and possibly its own operator.

Configure the beforeSend scrubbing when the tracker goes in (C7), not after the first incident. And treat "which systems have seen a token code?" as a question you should be able to answer: the API's memory, the log pipeline, and the error tracker are three different answers with three different blast radii.

Why this way (and what was rejected)

Parameterised queries, and the one place they do not reach

$1 is not escaping — the value never becomes part of the SQL text, so there is no parser for it to confuse. That is why it is a rule rather than a recommendation, and why "sanitise the input first" is the weaker answer to a problem that has an exact one.

The gap worth knowing: the rules JSONB column holds structured data the database will not check for you. A parameterised insert stops SQL injection into that column and does nothing about the contents being nonsense. That is what the discriminated union in B3.4 is for — and why B7.2 refuses rule types it does not recognise rather than skipping them.

Security headers are for the browser, not the API

Helmet on the API is close to decoration: the mobile app is not a browser and ignores every one of these headers. They matter on tokn.app, the redemption page — which is the part of the system a stranger actually loads in a browser, and therefore the only part with an XSS or clickjacking story at all.

One header there deserves a different value from the API's. The redemption page is tokn.app/t/CODE — a code in a URL, unavoidably, because a person has to type it. strict-origin-when-cross-origin sends only the origin to other sites, which is fine, and the full URL on same-origin navigations, which is not what you want for a page whose path is a capability. no-referrer on that route removes the question.

CORS is not access control

This is worth being blunt about because the name suggests otherwise. CORS tells a browser which origins may read a response. It does nothing about curl, a script, or a mobile app, all of which ignore it entirely. It stops a malicious website making authenticated requests using a logged-in user's credentials; it does not stop anyone talking to your API. Authentication and rate limiting do that.

When this breaks

npm audit is not supply-chain security

It checks installed versions against a database of known, published vulnerabilities. The realistic supply-chain attack on a small project is the opposite shape: a maintainer account is compromised, a new version is published, and it runs a postinstall script on your machine and in your CI — with your permissions and your environment variables — before anyone has reported anything to report. 

# Install scripts do not run. Nothing in this project needs them,
# and the day one does, that is worth noticing rather than automating.
npm ci --ignore-scripts

# And pin: package-lock.json is committed, CI uses `ci` not `install`,
# and a lockfile change is a diff to read rather than a line to skim.

HSTS preload is close to permanent

preload: true is an instruction to hard-code your domain into browsers as HTTPS-only, shipped in Chrome, Firefox and Safari. Removal is a request, a review, and then the next browser release cycle — months, during which old browsers still refuse plain HTTP to your domain and every subdomain.

That is the right setting for tokn.app, and it is one to make deliberately, with the subdomains understood, rather than by copying a config snippet.

A CSP that gets weakened until it does nothing

styleSrc: ["'self'", "'unsafe-inline'"] is already in the config above, with the honest comment "needed for some UI frameworks". That is how CSP usually degrades: something breaks, the fastest fix is one more unsafe-, and the policy becomes a header that passes scanners and blocks nothing.

Inline styles are a small hole; 'unsafe-inline' in scriptSrc is the whole door, and it is the next one someone reaches for. If a framework needs inline anything, nonces are the answer that keeps the policy meaningful.

Ownership checks that live in the handler

The WHERE user_id = $2 pattern in this lesson is right, and its weakness is that it is a habit rather than a mechanism: one query written without it is a broken access control bug, and nothing fails until someone finds it. Every ownership check in this course is written that way, which is a real risk worth naming — the durable fix is row-level security in Postgres, which belongs with the B2 rewrite.

What this costs you

DecisionWhat you pay
Allow-list logging Debugging is harder. The field you want during an incident is the one nobody thought to add, and adding it means a deploy. That is the correct trade for a system holding capabilities — but it means logging what you do need has to be deliberate, not left to a catch-all.
A strict CSP Real breakage in the web app, usually at the worst moment, and a policy that has to be maintained as the page changes. Its value is entirely in not weakening it under pressure.
HSTS with preload HTTPS forever, for the domain and every subdomain, effectively irreversibly. A future subdomain that cannot do TLS is simply unreachable.
--ignore-scripts Packages that genuinely need a build step stop working, and you find out at install time. Which is the point, and it is still an interruption.
Security headers on the API Almost nothing, and almost no benefit — the clients that matter are not browsers. Keep them because the cost is a middleware, but do not mistake them for the work; the redemption page is where they earn anything.
