India's DPDP Act

B10 — Lesson 2 of 2  |  ~50 min

Why this matters for Token: The Digital Personal Data Protection Act (2023) is India's equivalent of GDPR. Token is a privacy product by definition — its entire value proposition is controlling who can contact you. The DPDP Act isn't an obstacle; it's the legal framework that validates your product's design. Token already does most of what the law requires. This lesson maps the legal requirements to your implementation.

DPDP Act — The Key Concepts

The Act was passed in August 2023. Its rules are being notified in phases. Here's what matters for Token:

Legal termPlain EnglishToken equivalent
Data PrincipalThe person whose data it isYour user (the token issuer)
Data FiduciaryThe entity that decides how data is usedYou (the app developer/company)
Data ProcessorEntity that processes data on behalf of fiduciaryYour VPS provider, Expo (for push)
ConsentPermission to process data, for a stated purposeThe user signing up and issuing tokens
Purpose limitationData used only for the stated purposeMessages only for communication, not ads/profiling
Data minimisationCollect only what you needNo email, no real name; a phone number is hashed at sign-up and never disclosed to anyone the user issues a token to

The Seven Obligations

The DPDP Act imposes these obligations on Data Fiduciaries (you). Here's how Token implements each:

1. Lawful Purpose & Consent

You must have a lawful basis for processing personal data, and consent must be:

  • Free — not coerced
  • Specific — for a stated purpose
  • Informed — the user knows what they're consenting to
  • Unconditional — not bundled with other terms
// Implementation: clear consent screen during registration

2. Right to Withdraw Consent

The user can withdraw consent at any time, and withdrawal must be as easy as granting it.

// api/src/routes/consent.ts
router.delete('/consent/:purpose', authenticateJWT, async (req, res) => {
  const { purpose } = req.params;
  const userId = req.user.id;

  // Record withdrawal
  await db.query(
    'UPDATE consent_records SET withdrawn_at = NOW() WHERE user_id = $1 AND purpose = $2',
    [userId, purpose]
  );

  // Act on withdrawal immediately
  if (purpose === 'push_notifications') {
    // Delete push token — stop sending notifications
    await db.query('UPDATE users SET push_token = NULL WHERE id = $1', [userId]);
  }

  if (purpose === 'data_processing') {
    // Withdrawing the consent the whole service rests on IS an erasure
    // request. Do not invent a second, softer meaning for it.
    await eraseAccount(userId);   // the transaction in section 5
  }

  req.log.info({ userId, purpose }, 'consent withdrawn');
  res.json({ withdrawn: true, effectiveImmediately: true });
});

3. Right to Access (Data Portability)

The user can request a copy of all their personal data in a machine-readable format.

// api/src/routes/dataExport.ts
router.get('/me/data-export', authenticateJWT, async (req, res) => {
  const userId = req.user.id;

  // Every column below is named on purpose. Check each one against
  // migrations/001 before adding to this list -- see the callout after.
  const [user, tokens, messages, consents, redemptions] = await Promise.all([
    // No SELECT * -- that would ship password_hash.
    db.query('SELECT id, display_name, avatar_url, created_at FROM users WHERE id = $1', [userId]),

    // No 'code' column exists (ADR-0007), and no decryption happens here.
    db.query('SELECT id, label, status, max_uses, expires_at, created_at, paused_at, revoked_at FROM tokens WHERE user_id = $1', [userId]),

    // messages has no sender_id -- holders are not users, so the column is
    // sender_type ('owner' | 'holder'). A message is reached through its
    // conversation, which is reached through the token you own.
    db.query(
      `SELECT m.id, m.conversation_id, m.sender_type, m.ciphertext, m.nonce,
              m.key_version, m.created_at, m.delivered_at, m.read_at
         FROM messages m
         JOIN conversations c ON c.id = m.conversation_id
         JOIN tokens t       ON t.id = c.token_id
        WHERE t.user_id = $1`,
      [userId]
    ),

    db.query('SELECT purpose, granted, granted_at, withdrawn_at FROM consent_records WHERE user_id = $1', [userId]),

    // holder_ip, holder_name and user_agent are deliberately NOT selected.
    // They describe the HOLDER, not the person asking -- see the callout.
    db.query(
      `SELECT r.id, r.token_id, r.created_at
         FROM redemption_events r
         JOIN tokens t ON t.id = r.token_id
        WHERE t.user_id = $1`,
      [userId]
    ),
  ]);

  const exportData = {
    exportedAt: new Date().toISOString(),
    format: 'DPDP-compliant-export-v1',
    user: user.rows[0],
    tokens: tokens.rows,
    messages: messages.rows,        // ciphertext; the app decrypts on download
    consentRecords: consents.rows,
    redemptionEvents: redemptions.rows,
    notes: {
      messages:
        'Message bodies are end-to-end encrypted. The server cannot decrypt ' +
        'them. Open this file in the Token app on a device holding your keys ' +
        'to read them.',
      tokenCodes:
        'Token codes are not included. Request an individual code from the ' +
        'token detail screen; each disclosure is logged.',
      redemptionEvents:
        'We record that a token was redeemed and when. The IP address, name ' +
        'and browser of the person who redeemed it are their personal data, ' +
        'not yours, so they are not in this file.',
    },
  };

  // Return as downloadable JSON
  res.setHeader('Content-Type', 'application/json');
  res.setHeader('Content-Disposition', 'attachment; filename="token-data-export.json"');
  res.json(exportData);
});

5. Right to Erasure (Account Deletion)

The user can request complete deletion of their data. This must be actual deletion, not soft-delete.

// api/src/routes/account.ts
router.delete('/me', authenticateJWT, async (req, res) => {
  const userId = req.user.id;
  const client = await pool.connect();

  req.log.info({ userId }, 'account erasure requested');

  try {
    await client.query('BEGIN');

    // The order is read off the foreign keys, not off intuition.
    // conversations.token_id and redemption_events.token_id are both
    // ON DELETE RESTRICT, and tokens.user_id is too -- so a parent row
    // cannot go until every row pointing at it has gone first.
    await client.query('DELETE FROM consent_records WHERE user_id = $1', [userId]);

    // messages cascades from conversations. Written out anyway: a cascade
    // you did not write is a cascade you will forget you are relying on.
    await client.query(
      `DELETE FROM messages
        WHERE conversation_id IN (
          SELECT c.id FROM conversations c
            JOIN tokens t ON t.id = c.token_id
           WHERE t.user_id = $1)`,
      [userId]
    );

    await client.query(
      `DELETE FROM conversations
        WHERE token_id IN (SELECT id FROM tokens WHERE user_id = $1)`,
      [userId]
    );

    await client.query(
      `DELETE FROM redemption_events
        WHERE token_id IN (SELECT id FROM tokens WHERE user_id = $1)`,
      [userId]
    );

    await client.query(
      `DELETE FROM access_rules
        WHERE token_id IN (SELECT id FROM tokens WHERE user_id = $1)`,
      [userId]
    );

    await client.query('DELETE FROM tokens WHERE user_id = $1', [userId]);
    await client.query('DELETE FROM users WHERE id = $1', [userId]);

    // The LIVE database is clean here. The backups are not, for another
    // seven days -- see the callout below. Record the tail so the promise
    // made to the user has a date on it.
    await client.query(
      `INSERT INTO deletion_queue (erased_user_id, requested_at, live_erased_at, backups_clear_at)
       VALUES ($1, NOW(), NOW(), NOW() + interval '7 days')`,
      [userId]
    );

    await client.query('COMMIT');

    req.log.info({ userId }, 'live rows erased; backup tail recorded');
    res.json({ erased: true, backupsClearInDays: 7 });
  } catch (err) {
    await client.query('ROLLBACK');
    req.log.error({ err, userId }, 'account erasure failed');
    res.status(500).json({ error: 'erasure failed — please contact support' });
  } finally {
    client.release();
  }
});

The queue row is what makes the promise checkable. It is deliberately the thinnest possible table — and note what it cannot have:

-- api/migrations/016_deletion_queue.sql

CREATE TABLE deletion_queue (
  id               SERIAL PRIMARY KEY,

  -- A plain integer, NOT a foreign key. The row it would reference is
  -- the one we just deleted, which is the entire point. This is a
  -- tombstone: it says an account with this id existed and was erased.
  erased_user_id   INTEGER NOT NULL,

  requested_at     TIMESTAMPTZ NOT NULL,
  live_erased_at   TIMESTAMPTZ,      -- when the live rows went
  backups_clear_at TIMESTAMPTZ NOT NULL,  -- when the last backup holding
                                          -- them rolls over
  completed_at     TIMESTAMPTZ       -- set by the job that checks the above
);

CREATE INDEX idx_deletion_queue_pending ON deletion_queue(backups_clear_at)
  WHERE completed_at IS NULL;

-- No display_name, no phone_hash, no labels. If this table held anything
-- ABOUT the person, it would be the place the erasure leaked to.
“Once done, the data is gone” is not true, and the fix is not more deleting

This lesson's own retention table says backups: 7 days. So the moment the transaction above commits, the erased rows still exist in up to seven nightly snapshots. Nobody is going to restore seven snapshots, edit one user out of each, and re-take them — and a backup you have been editing is not a backup any more.

Every real erasure therefore has a tail: a period after you told the user “deleted” during which the data is still recoverable by you. Pretending otherwise is the actual compliance failure. Saying “live records erased immediately, backup copies roll off within 7 days” is both true and defensible; that is what backups_clear_at is for.

Now the part that only works because of ADR-0002. Ask what is actually sitting in those seven snapshots:

  • Message bodies — ciphertext. The server had no key on the day the backup was taken and has none now. That data was never readable by the fiduciary, so its survival in a backup discloses nothing. The tail on sealed data is zero.
  • Everything the server keeps in the clear — display_name, avatar_url, token labels, timestamps, who talked to whom and when. This is fully readable, and this is what the seven days are for.

So the length and the seriousness of your erasure tail is decided entirely by how much you kept in the clear — a choice you made years earlier, at schema-design time, and cannot revisit once a user asks. Data minimisation is not a legal box to tick; it is the mechanism that makes erasure achievable at all. That is the honest version of “Token's natural compliance advantage” in the table below: not that the law happens to like the product, but that a server holding less has less that outlives a delete.

What this does not buy you. Encryption is not a general erasure excuse. It works here only because the server never held the key. code_enc is the counter-example in this very schema: the API does hold TOKEN_CODE_KEY, so an encrypted token code in a backup is readable by you, and it counts as clear data for this purpose. And the holder's copy of the conversation sits on the holder's device, where your erasure cannot reach at all — the export and the deletion both stop at your own storage, and the privacy policy should say so rather than imply a reach you do not have.

Whose data is it? The redemption log has two people in it

redemption_events holds holder_ip, holder_name and user_agent. Those describe the person who redeemed the token — a different Data Principal, who never signed up and never consented to anything.

That makes the row awkward in both directions, and the awkwardness is real rather than a technicality:

  • It is not the issuer's to export. Putting holder_ip into the issuer's download hands one person another person's location, through a compliance feature, on request. The issuer's data is that a redemption happened, and when.
  • It is not entirely the issuer's to erase either. The event is an append-only security record; it is also the only trace the holder has. Deleting the token's events on account closure is defensible because the record exists to protect the issuer — but it is a decision, not an obvious consequence.

The general rule: “a row in my table” and “my personal data” are different sets, and an export endpoint written from the schema rather than from that question will quietly ship the difference.

If personal data is breached, you must notify the Data Protection Board of India (DPBI) and affected users.

Data portability meets end-to-end encryption

An export endpoint is where two of this system's commitments pull against each other, and the obvious implementation quietly breaks both.

Messages. ADR-0002 means the server stores ciphertext and holds no key. So SELECT content does not return the user's messages — it returns bytes the API cannot read. There are two honest options: ship the ciphertext with an explanation of how to read it, or build the export on the device, where the keys are. This lesson does the first because it keeps one export endpoint; the second is better, and is what the app should do once key backup exists.

What you must not do is add a server-side decrypt "just for exports". That would mean the server holds keys — the entire guarantee gone, traded for a convenience in a compliance feature.

Token codes. There is no code column; ADR-0007 stores a hash for lookup and an encrypted copy for display. A bulk export would decrypt every code the user has ever issued and write them into one downloadable file — which then sits in a Downloads folder, gets emailed to an accountant, or is handed to whoever asked for it. A file of live capabilities is a worse artefact than the database it came from, and it undoes the point of never storing them in the clear. So the export carries labels, states and timestamps; codes stay a per-token, logged disclosure.

Neither of these is a loophole in the DPDP Act. The right is to your personal data in a portable form. Ciphertext you hold the key to is your data, and the fact that your provider cannot read it is the feature you were sold. Saying that plainly inside the export file — which is why notes is in the payload above — is what makes it a compliant answer rather than an evasive one.

Token's Natural Compliance Advantage

Token's privacy-first design means you're already mostly compliant:

DPDP requirementToken already does this
Data minimisationNo email, no real name; the phone number is hashed at sign-up, used only to log in, and never shown to a token holder
Purpose limitationData used only for communication (no ads, no profiling)
ConsentEvery token is an explicit consent grant from the user
Right to withdrawToken revocation IS consent withdrawal
Security safeguardsEnd-to-end encrypted from v1 (ADR-0002); token codes hashed with a pepper and never stored in the clear (ADR-0007)
The row above used to be false, and the fix was to the sentence

Until 2026-08-22 that row read "no phone number, no email, no real name required". The schema this course teaches says users(phone_hash, display_name, avatar_url). Both claims cannot be true, and the difference is the kind that ends up in a legal filing.

  • phone_hash is not the absence of a phone number. An Indian mobile is ten digits with a known prefix, so the space is small enough to enumerate exhaustively — anyone holding the database can hash all of them and match. That makes it a lookup key, not an anonymisation. b3/0001 makes the same argument about a different column.
  • display_name is mandatory in the table (TEXT NOT NULL). "Need not be a real name" is a property of the policy, not something the schema enforces.

Two ways out, and the choice was deliberate. Either stop keeping it — move sign-up to a passphrase or passkey so there is no number to hash — or keep it and describe it accurately. Token chose the second, on 2026-08-22, because the number is doing real work (it is how you get back into your account) and because passphrase-only sign-up means a lost passphrase is a lost account with no recovery path.

So the sentence is now "we store a scrambled version of your phone number, used only to sign you in". Note what did not change: nobody you issue a token to ever learns it. That was always the product's actual promise, and it was never the thing in doubt — the false claim was about what the company collects, not about what a token holder sees, and those had been quietly collapsed into one line.

The transferable part: a compliance document is the last place a hopeful description of your own schema should survive. Read every row of a table like this against the migration, not against what you remember intending.

The product IS the compliance mechanism. A token is a consent artifact — it represents the user's decision to allow contact, with specific rules, revocable at any time. This is exactly what the DPDP Act envisions.

Privacy Policy — What to Include

Your privacy policy must be in clear language (not legalese) and state:

// Required sections for Token's privacy policy:

// 1. What data you collect
//    Name the COLUMN, not the intention. Read this list off migrations/001.
//    - A scrambled (hashed) version of your phone number — used only to sign
//      you in. Never shown to anyone you issue a token to.
//    - A display name, and optionally an avatar (need not be your real name)
//    - Messages — stored end-to-end encrypted; we hold no key and cannot
//      read them (say this here, not only in the marketing copy)
//    - Token metadata: labels, state, rules, and the times of redemptions
//    - Token codes, hashed for lookup and encrypted for one-time display
//    - Device push tokens (for notifications)
//    - IP addresses of people who redeem your tokens (retained 30 days)

// 2. Why you collect it (purpose)
//    - Account management
//    - Delivering messages between token issuers and holders
//    - Push notifications for new messages and calls
//    - Security (rate limiting, abuse prevention)

// 3. Who you share it with
//    - No third parties (no ads, no analytics services, no data brokers)
//    - Expo (only push tokens, for notification delivery)
//    - VPS provider (data at rest on their hardware)

// 4. How long you retain it
//    - Account data: until you delete your account
//    - Messages: until you delete your account
//    - Server logs: 30 days
//    - Backups: 7 days (then overwritten)
//
//    And the sentence most policies leave out, which is the one that makes
//    the four above true rather than aspirational:
//    - "When you delete your account we erase your records immediately.
//       Copies in our encrypted backups are overwritten within 7 days.

// 5. How to exercise your rights

Children's Data

// Option 1 (simplest): Declare the app is for 18+ users

Cross-Border Data Transfer

If your server is outside India (e.g., Singapore VPS), you're transferring data cross-border. The DPDP Act allows this to countries not blacklisted by the government. Singapore is fine. If the government blacklists a country, you'd need to move your data.

// Best practice: document where data lives
// - Primary database: Hetzner Singapore
// - Backups: [your backup location]
// - Push notification relay: Expo (US-based)
// - No other third parties

// If you choose a VPS in India (e.g., Mumbai region on AWS/DigitalOcean),
// cross-border transfer isn't an issue at all.
