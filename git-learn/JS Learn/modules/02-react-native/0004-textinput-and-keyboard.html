React Native · Lesson 4

TextInput & Keyboard

TextInput · KeyboardAvoidingView · useState preview ~30 min Hands-on
Why this matters for Token

Every interaction where a user types something — naming a token, messaging a holder, and above all typing a token code into the redemption screen — goes through TextInput. And one of the most annoying bugs in any messaging app is the keyboard covering the composer when it opens. This lesson teaches both: how to capture text, and how to make sure the keyboard never hides your UI.

The code entry field is the one that has to be perfect. A holder who mistypes KART-4KN9-RT2M and gets a blank error learns nothing; the field has to do the work for them.

1. TextInput — the basics

TextInput is the component that renders a text field the user can type into. It works very differently from an HTML <input> — in React Native you control the value yourself through state (covered fully in Lesson 5). For now, focus on the props.

import { View, TextInput, StyleSheet } from 'react-native';

export default function App() {
  return (
    <View style={styles.container}>
      <TextInput
        style={styles.input}
        placeholder="Type a message..."
        placeholderTextColor="#999"
      />
    </View>
  );
}

const styles = StyleSheet.create({
  container: { flex: 1, padding: 16, justifyContent: 'flex-end' },
  input: {
    backgroundColor: '#fff',
    borderRadius: 24,
    paddingHorizontal: 16,
    paddingVertical: 10,
    fontSize: 16,
    borderWidth: 1,
    borderColor: '#e0e0e0',
  },
});

Run this. You'll see a styled text field at the bottom of the screen. Tap it — the keyboard opens and you can type.

2. The most important TextInput props

Controlling the keyboard type

{/* Default — full keyboard */}
<TextInput keyboardType="default" />

{/* Numbers only — for OTP / phone PIN */}
<TextInput keyboardType="numeric" />

{/* Phone number — includes + and - */}
<TextInput keyboardType="phone-pad" />

{/* Email — includes @ and . */}
<TextInput keyboardType="email-address" />

Secure text — for passwords

<TextInput
  placeholder="Password"
  secureTextEntry={true}   {/* hides characters as user types */}
  autoCapitalize="none"    {/* don't capitalise first letter */}
  autoCorrect={false}      {/* don't autocorrect passwords */}
/>

Multi-line — for the message input bar

<TextInput
  placeholder="Type a message..."
  multiline={true}          {/* allows multiple lines */}
  maxLength={4096}          {/* a sane cap for one message */}
  style={styles.messageInput}
/>

const styles = StyleSheet.create({
  messageInput: {
    maxHeight: 100,    {/* grows up to 100dp, then scrolls internally */}
    minHeight: 40,
    paddingTop: 10,    {/* extra top padding needed for multiline on iOS */}
    paddingHorizontal: 12,
    fontSize: 16,
  },
});
multiline needs extra top padding on iOS

On iOS, multiline TextInput ignores vertical centering — text appears at the top of the field. Add paddingTop to match the visual centre you'd expect. This is a known React Native quirk and you'll see it mentioned in almost every Stack Overflow answer about multiline inputs.

Return key behaviour

{/* In the composer, pressing Return sends the message */}
<TextInput
  returnKeyType="send"       {/* changes the Return key label to "Send" */}
  onSubmitEditing={handleSend}  {/* called when user presses Return/Send */}
  blurOnSubmit={false}       {/* keep keyboard open after sending */}
/>

{/* Other returnKeyType values: 'done', 'go', 'next', 'search' */}

Useful callbacks

<TextInput
  onChangeText={(text) => console.log('User typed:', text)}
  onFocus={() => console.log('Input focused — keyboard opened')}
  onBlur={() => console.log('Input blurred — keyboard closed')}
  onSubmitEditing={() => console.log('User pressed Send/Return')}
/>
onChangeText is the key one

onChangeText fires every time the text changes — on every keystroke. It gives you the full current value as a string. This is how you capture what the user is typing and store it in state (Lesson 5). It replaces the need to read event.target.value like you would in HTML forms.

3. useRef — controlling the input programmatically

Sometimes you need to control the TextInput from code — focus it automatically when a screen opens, or clear it after sending a message. useRef gives you a direct reference to the component.

import { useRef } from 'react';
import { View, TextInput, Pressable, Text, StyleSheet } from 'react-native';

export default function App() {
  const inputRef = useRef(null);

  function handleSend() {
    // Clear the input after sending
    inputRef.current.clear();
    // Keep focus on the input so keyboard stays open
    inputRef.current.focus();
    console.log('Message sent!');
  }

  return (
    <View style={styles.container}>
      <TextInput
        ref={inputRef}                        {/* attach the ref */}
        style={styles.input}
        placeholder="Type a message..."
        returnKeyType="send"
        onSubmitEditing={handleSend}
        blurOnSubmit={false}
        autoFocus={true}                      {/* focus immediately on mount */}
      />
      <Pressable style={styles.sendBtn} onPress={handleSend}>
        <Text style={styles.sendBtnText}>Send</Text>
      </Pressable>
    </View>
  );
}

const styles = StyleSheet.create({
  container: { flex: 1, flexDirection: 'row', alignItems: 'flex-end', padding: 8 },
  input:      { flex: 1, backgroundColor: '#fff', borderRadius: 24, paddingHorizontal: 16, paddingVertical: 10, fontSize: 16, borderWidth: 1, borderColor: '#e0e0e0', marginRight: 8 },
  sendBtn:    { backgroundColor: '#25D366', width: 44, height: 44, borderRadius: 22, alignItems: 'center', justifyContent: 'center' },
  sendBtnText:{ color: '#fff', fontWeight: '700' },
});

4. The keyboard problem — and how to fix it

Here is the most frustrating bug new React Native developers hit: when the keyboard opens on a phone, it slides up from the bottom and covers the input bar. The user can't see what they're typing.

React Native has a built-in solution: KeyboardAvoidingView. It automatically shifts or resizes your layout when the keyboard appears.

import { KeyboardAvoidingView, Platform } from 'react-native';

{/* Wrap your screen in KeyboardAvoidingView */}
<KeyboardAvoidingView
  style={{ flex: 1 }}
  behavior={Platform.OS === 'ios' ? 'padding' : 'height'}
>
  {/* your screen content */}
</KeyboardAvoidingView>
Why Platform.OS — Android and iOS behave differently

iOS and Android handle keyboard appearance differently at the OS level. On iOS, behavior="padding" works — it adds padding to push content up. On Android, behavior="height" works better — it shrinks the view. Platform.OS is a built-in React Native value that returns 'ios' or 'android' at runtime, so you can write one piece of code that handles both correctly.

import { Platform } from 'react-native';

console.log(Platform.OS);           // 'ios' or 'android'
console.log(Platform.Version);      // iOS version number or Android API level

// Common pattern — different values per platform
const shadowStyle = Platform.select({
  ios: {
    shadowColor: '#000',
    shadowOffset: { width: 0, height: 2 },
    shadowOpacity: 0.1,
    shadowRadius: 4,
  },
  android: {
    elevation: 4,   // Android uses elevation instead of shadow props
  },
});
Shadows work differently on Android and iOS

iOS uses shadowColor, shadowOffset, shadowOpacity, shadowRadius. Android uses elevation. If you only set the iOS shadow props, you'll see no shadow on Android — and vice versa. Always use Platform.select for shadows.

5. Full example — the token thread composer

This is the complete, production-quality composer for a token's message thread — the one at the bottom of every thread screen. It handles keyboard avoidance on both platforms, multi-line growth, send on return, and programmatic clearing after send.

Replace your App.js with this and run it on your phone. Open the keyboard and watch the input bar stay visible above it.

import { useRef, useState } from 'react';
import {
  View, Text, TextInput, Pressable, ScrollView,
  KeyboardAvoidingView, Platform, StyleSheet
} from 'react-native';

const MY_USER_ID = 'user-ashish-01';

const initialMessages = [
  { id: 'm1', from: 'holder', text: 'Out for delivery, 2-4pm.', time: '10:01' },
  { id: 'm2', senderId: MY_USER_ID,        text: 'Good! Just got to work.', time: '10:02' },
  { id: 'm3', from: 'holder', text: 'Guard is not at the desk.', time: '10:03' },
];

function MessageBubble({ message }) {
  const isMe = message.senderId === MY_USER_ID;
  return (
    <View style={[styles.bubbleRow, isMe ? styles.myRow : styles.theirRow]}>
      <View style={[styles.bubble, isMe ? styles.myBubble : styles.theirBubble]}>
        <Text style={styles.bubbleText}>{message.text}</Text>
        <Text style={styles.timeText}>{message.time}</Text>
      </View>
    </View>
  );
}

export default function App() {
  const [messages, setMessages] = useState(initialMessages);
  const [inputText, setInputText]   = useState('');
  const inputRef   = useRef(null);
  const scrollRef  = useRef(null);

  function handleSend() {
    const trimmed = inputText.trim();
    if (!trimmed) return;   // don't send empty messages

    const newMessage = {
      id:       'm' + (messages.length + 1),
      senderId: MY_USER_ID,
      text:     trimmed,
      time:     new Date().toLocaleTimeString([], { hour: '2-digit', minute: '2-digit' }),
    };

    setMessages(prev => [...prev, newMessage]);
    setInputText('');
    inputRef.current?.focus();

    // Scroll to bottom after new message
    setTimeout(() => {
      scrollRef.current?.scrollToEnd({ animated: true });
    }, 50);
  }

  return (
    {/* KeyboardAvoidingView wraps the whole screen */}
    <KeyboardAvoidingView
      style={styles.screen}
      behavior={Platform.OS === 'ios' ? 'padding' : 'height'}
      keyboardVerticalOffset={Platform.OS === 'ios' ? 0 : 0}
    >
      {/* Header */}
      <View style={styles.header}>
        <Text style={styles.headerTitle}>Flipkart delivery</Text>
        <Text style={styles.headerSub}>online</Text>
      </View>

      {/* Messages */}
      <ScrollView
        ref={scrollRef}
        style={styles.messageList}
        contentContainerStyle={styles.messageListContent}
        onContentSizeChange={() => scrollRef.current?.scrollToEnd({ animated: false })}
      >
        {messages.map(msg => (
          <MessageBubble key={msg.id} message={msg} />
        ))}
      </ScrollView>

      {/* Input bar */}
      <View style={styles.inputBar}>
        <TextInput
          ref={inputRef}
          style={styles.input}
          placeholder="Type a message..."
          placeholderTextColor="#999"
          value={inputText}
          onChangeText={setInputText}
          multiline={true}
          maxLength={4096}
          returnKeyType="send"
          onSubmitEditing={handleSend}
          blurOnSubmit={false}
        />
        <Pressable
          style={[styles.sendBtn, !inputText.trim() && styles.sendBtnDisabled]}
          onPress={handleSend}
          disabled={!inputText.trim()}
        >
          <Text style={styles.sendBtnText}>➤</Text>
        </Pressable>
      </View>

    </KeyboardAvoidingView>
  );
}

const styles = StyleSheet.create({
  screen: { flex: 1, backgroundColor: '#ECE5DD' },

  header: {
    backgroundColor: '#075E54',
    paddingTop: 48,
    paddingBottom: 12,
    paddingHorizontal: 16,
  },
  headerTitle: { color: '#fff', fontSize: 18, fontWeight: '700' },
  headerSub:   { color: '#b2dfdb', fontSize: 13, marginTop: 1 },

  messageList:        { flex: 1 },
  messageListContent: { paddingVertical: 8 },

  bubbleRow:   { paddingHorizontal: 8, marginVertical: 2 },
  myRow:       { alignItems: 'flex-end' },
  theirRow:    { alignItems: 'flex-start' },
  bubble:      { maxWidth: '75%', paddingVertical: 6, paddingHorizontal: 10, borderRadius: 8 },
  myBubble:    { backgroundColor: '#DCF8C6' },
  theirBubble: { backgroundColor: '#fff' },
  bubbleText:  { fontSize: 15, color: '#303030', lineHeight: 20 },
  timeText:    { fontSize: 11, color: '#999', alignSelf: 'flex-end', marginTop: 2 },

  inputBar: {
    flexDirection: 'row',
    alignItems: 'flex-end',
    paddingHorizontal: 8,
    paddingVertical: 8,
    backgroundColor: '#f0f2f5',
    borderTopWidth: 1,
    borderTopColor: '#e0e0e0',
  },
  input: {
    flex: 1,
    backgroundColor: '#fff',
    borderRadius: 24,
    paddingHorizontal: 16,
    paddingTop: Platform.OS === 'ios' ? 10 : 8,
    paddingBottom: 8,
    fontSize: 16,
    maxHeight: 120,
    minHeight: 44,
    marginRight: 8,
  },
  sendBtn: {
    width: 44,
    height: 44,
    borderRadius: 22,
    backgroundColor: '#25D366',
    alignItems: 'center',
    justifyContent: 'center',
  },
  sendBtnDisabled: { backgroundColor: '#b2dfdb' },
  sendBtnText: { color: '#fff', fontSize: 18 },
});

Type a message and press Send. Your message appears as a green bubble on the right. The keyboard stays open, the input clears, and the list scrolls to the new message. This is a real, functional chat input.

What's new in this example that you haven't formally learned yet
  • useState — const [messages, setMessages] = useState(...) stores data that changes. When you call setMessages, React Native re-renders the screen with the new data. You'll learn this fully in Lesson 5.
  • scrollToEnd — calling a method on a ref to programmatically scroll the list.
  • disabled prop on Pressable — greys out the send button when input is empty.
  • setTimeout(..., 50) — a small delay lets the new message render before scrolling to it.

Don't worry if useState feels magic right now — Lesson 5 will make it completely clear.

6. KeyboardDismissMode — dismissing the keyboard by scrolling

When the user scrolls up through the thread, the keyboard should dismiss automatically. This is one small prop:

<ScrollView
  keyboardDismissMode="on-drag"   {/* dismiss keyboard when user starts scrolling */}
  keyboardShouldPersistTaps="handled"  {/* taps inside scroll don't dismiss keyboard */}
>
  {/* messages */}
</ScrollView>
keyboardShouldPersistTaps — important for message threads

Without keyboardShouldPersistTaps="handled", tapping a message bubble while the keyboard is open will first dismiss the keyboard instead of triggering the tap. With "handled", taps on interactive elements work normally and only non-interactive taps dismiss the keyboard — which is the behaviour users expect from every messaging app.

7. The field that has to be perfect — typing a token code

Everything above applies to any text field. This one is different, because it is the field the whole product runs through: a holder types KART-4KN9-RT2M into the redemption screen, and either they get in or they do not.

They will not type it the way you imagine. They will type it in lower case, with spaces instead of hyphens, or with no separators at all, pasted from a WhatsApp message with a trailing newline. All of those are the right code, and all of them must work.

<TextInput
  value={raw}
  onChangeText={setRaw}
  placeholder="XXXX-XXXX-XXXX"
  autoCapitalize="characters"   {/* codes are upper case */}
  autoCorrect={false}           {/* never autocorrect a code */}
  spellCheck={false}
  keyboardType="visible-password" {/* Android: no suggestions strip */}
  maxLength={17}                {/* 12 characters + 2 hyphens, plus slack */}
/>
autoCorrect={false} is not optional here

Leave autocorrect on and the keyboard will helpfully rewrite fragments of a code into words. The user sees their own typing replaced, retypes it, watches it happen again, and concludes the code is broken. It is the single most avoidable support ticket in the product.

The prop settings above only shape what the keyboard offers. The real work happens on the string the user actually produced:

Try it yourself — this one is broken on purpose

Now the validation. This looks reasonable and is dangerously wrong. Run it and read which codes it accepts:

It accepts KART-4KN9-RTL0, which contains an L and a zero — and Token's alphabet contains neither. The pattern /^[A-Z0-9]+$/ means "letters and digits", not "characters this product can issue".

Why accepting too much is worse than rejecting too much

A code containing L cannot exist — the generator can never produce one. So a validator that accepts it sends a lookup to the server that is guaranteed to miss, and the user is told "no such token" for a code they may have typed perfectly, having simply confused 1 with L. The right answer is to reject it at the field, and say which character is the problem.

Those five characters — 0 O 1 I L — are excluded from the alphabet precisely because humans confuse them. Dropping them from the validator throws away the entire benefit.
