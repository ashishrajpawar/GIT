React Native · Lesson 7

FlatList

Performant lists · keyExtractor · ListEmptyComponent ~30 min Hands-on
Why this matters for Token

A heavy user issues hundreds of tokens. A token's thread can hold thousands of messages. If you render all of them at once with ScrollView, the app becomes slow and eats memory — you'd feel it on a mid-range Android phone immediately. FlatList solves this by only rendering the items currently visible on screen, recycling off-screen items as the user scrolls. It's the component behind every performant list in every serious React Native app.

1. ScrollView vs FlatList — when to use each

ScrollView FlatList
Renders All children at once Only visible items (+ a small buffer)
Performance Fine for <20 items Handles thousands of items smoothly
Memory Keeps all items in memory Recycles off-screen items
Built-in features None Pull-to-refresh, load more, empty state, headers, separators
Use for Settings screens, profile forms, short static content Token list, message thread, redemption history, search results

Rule of thumb: if the number of items can grow (comes from a database, a search result, user-generated), use FlatList. If it's a fixed short form, use ScrollView.

2. Basic FlatList

FlatList needs three required props: data, renderItem, and keyExtractor.

import { FlatList, View, Text, StyleSheet } from 'react-native';

const tokens = [
  { id: '1', label: 'Flipkart delivery', code: 'KART-4KN9-RT2M' },
  { id: '2', label: 'Gym membership',    code: 'GYMX-7PQ8-VN3K' },
  { id: '3', label: 'Flat viewing',      code: 'RENT-2WX7-HJ5D' },
];

export default function App() {
  return (
    <FlatList
      data={tokens}
      keyExtractor={item => item.id}
      renderItem={({ item }) => (
        <View style={styles.row}>
          <Text style={styles.name}>{item.label}</Text>
          <Text style={styles.preview}>{item.code}</Text>
        </View>
      )}
    />
  );
}

const styles = StyleSheet.create({
  row:     { padding: 16, borderBottomWidth: 1, borderBottomColor: '#f0f2f5' },
  name:    { fontSize: 16, fontWeight: '600' },
  preview: { fontSize: 14, color: '#667781', marginTop: 2 },
});

Breaking down the three required props:

  • data — the array to render. When this array changes (a token is revoked, a message arrives), FlatList re-renders only the affected rows.
  • keyExtractor — a function that returns a unique string key for each item. React Native uses this to track which items changed. Always use a stable unique ID — never the array index.
  • renderItem — a function that receives { item, index } and returns the JSX for one row.
Never use the array index as a key

Using keyExtractor={(item, index) => index.toString()} seems harmless but causes subtle bugs — when items are added, removed, or reordered, React Native gets confused about which component is which and can render stale data. Always use a stable unique ID from your data: item.id, item.uid, or the primary key the API returned.

Try it yourself — this one is broken on purpose

The warning above is easy to nod along to and hard to feel. Here it is happening. The user revokes the first token, and the list re-renders:

Every surviving row got a different key than it had before. React matches rows by key, so it concludes that row 0 changed from "Flipkart delivery" to "Gym membership", row 1 changed, row 2 changed — and re-uses the wrong component instance for each. Any state living in those rows, such as a half-open swipe or a focused input, moves to the wrong token.

With item.id, the keys of the surviving rows do not change at all. React sees one row removed and leaves the rest alone.

4. Pull-to-refresh

Pulling down to refresh the token list is something users expect. FlatList has it built in — no extra library needed.

import { useState } from 'react';

export default function TokenListScreen() {
  const [tokens, setTokens]           = useState([]);
  const [isRefreshing, setIsRefreshing] = useState(false);

  async function handleRefresh() {
    setIsRefreshing(true);
    try {
      const fresh = await fetchChats();
      setTokens(fresh);
    } finally {
      setIsRefreshing(false);
    }
  }

  return (
    <FlatList
      data={tokens}
      keyExtractor={item => item.id}
      renderItem={({ item }) => <TokenRow token={item} />}
      refreshing={isRefreshing}
      onRefresh={handleRefresh}
      {/* Pull down → shows spinner → calls handleRefresh → updates list */}
    />
  );
}

5. inverted — for message threads

A token's message thread shows the newest messages at the bottom and scrolls up for older ones. The cleanest way to achieve this is the inverted prop — it flips the list so the last item appears first, and you reverse your data array.

// Pass messages in reverse order + inverted prop
<FlatList
  data={[...messages].reverse()}   // newest first in the array
  keyExtractor={item => item.id}
  renderItem={({ item }) => <MessageBubble message={item} />}
  inverted={true}                   // flips the list visually
  contentContainerStyle={{ paddingVertical: 8 }}
/>

{/* Result: newest message appears at the bottom */}
{/* New messages added to the messages array automatically appear at the bottom */}
{/* No need to scroll to end programmatically — it starts there */}
inverted is the professional way to build message threads

Using inverted with a reversed array is simpler and more reliable than trying to scrollToEnd manually every time a new message arrives. It also handles the keyboard appearing correctly — the list stays anchored to the bottom when the keyboard opens.

6. onEndReached — loading more messages

You don't load a whole thread at once — you load the last 20, then load more as the user scrolls up (pagination). onEndReached fires when the user scrolls near the end of the list.

export default function MessageThread({ tokenId }) {
  const [messages, setMessages]     = useState([]);
  const [isLoadingMore, setIsLoadingMore] = useState(false);
  const [hasMore, setHasMore]       = useState(true);

  async function loadMoreMessages() {
    if (isLoadingMore || !hasMore) return;
    setIsLoadingMore(true);

    try {
      const older = await fetchOlderMessages(tokenId, messages[messages.length - 1]?.id);
      if (older.length === 0) {
        setHasMore(false);  // no more messages to load
      } else {
        setMessages(prev => [...prev, ...older]);
      }
    } finally {
      setIsLoadingMore(false);
    }
  }

  return (
    <FlatList
      data={[...messages].reverse()}
      keyExtractor={item => item.id}
      renderItem={({ item }) => <MessageBubble message={item} />}
      inverted
      onEndReached={loadMoreMessages}
      onEndReachedThreshold={0.3}  // trigger when 30% from the end
      ListFooterComponent={isLoadingMore ? (
        <ActivityIndicator style={{ padding: 16 }} color="#075E54" />
      ) : null}
    />
  );
}
onEndReachedThreshold

A value between 0 and 1. 0.3 means "trigger when the user is 30% of the list height from the bottom". Lower values trigger later (closer to the end). 0.3 is a good default — it starts loading before the user actually hits the end, so they never see a gap.

7. Performance tips

For a smooth 60fps scroll on mid-range Android phones — the ones most of your users will have — keep these in mind:

Extract renderItem into a separate component

// BAD — inline renderItem creates a new function on every render
<FlatList
  data={tokens}
  renderItem={({ item }) => <View><Text>{item.name}</Text></View>}
/>

// GOOD — separate named component
function TokenRow({ item }) {
  return <View><Text>{item.name}</Text></View>;
}

<FlatList
  data={tokens}
  renderItem={({ item }) => <TokenRow item={item} />}
/>

getItemLayout — for fixed-height rows

{/* If every row is the same height, tell FlatList upfront */}
{/* This lets it skip measuring and makes scrolling much faster */}
const ITEM_HEIGHT = 72;

<FlatList
  data={tokens}
  keyExtractor={item => item.id}
  renderItem={({ item }) => <TokenRow token={item} />}
  getItemLayout={(data, index) => ({
    length: ITEM_HEIGHT,
    offset: ITEM_HEIGHT * index,
    index,
  })}
/>

removeClippedSubviews

{/* On Android — detaches off-screen views from the native view hierarchy */}
{/* Small memory and performance win for very long lists */}
<FlatList
  data={messages}
  keyExtractor={item => item.id}
  renderItem={({ item }) => <MessageBubble message={item} />}
  removeClippedSubviews={true}
/>

Now build it yourself

Everything FlatList shows comes from the data array, so the interesting work is in producing that array. When a second page arrives from the API, something has to decide what the new list looks like — and it is a plain function.
