Continuous Integration

C2 — Lesson 1 of 4  |  ~45 min

Why this matters for Token

You now have tests. This module is about the machine that runs them when you forget to — and about the failure mode that machine has, which is not the one people expect.

The expected failure is a pipeline that goes red and blocks you. The real one is a pipeline that is always red, or always green, and therefore says nothing. This course has a first-hand example: its own audit exited FAIL on the same three problems every single run for weeks. Everyone learned to read the output and ignore the exit code — and then a new error landed in a build nobody was reading, and two checks were lost that way.

A check that is ignored is worse than no check, because it occupies the space where a working one would go.

1 · Three words: the same checks, on every push, in a clean place

Continuous integration is not complicated, and each of those three words is doing work.

  • The same checks. If CI runs different commands from the ones you run locally, it is testing a different thing, and the two will disagree at the worst moment. Put the commands in one place — a script both of you call — so they cannot drift.
  • On every push. Not nightly, not before release. The value of the signal collapses with distance from the change that caused it: an hour later you remember what you did; three days later you are reading your own diff like a stranger.
  • In a clean place. Your machine has installed packages, environment variables you set in March, and a database with your test data in it. A fresh container has none of that, which is the entire point — it is what turns “works on my machine” from an argument into a build log.

For Token, the checks are the ones you already have:

# .github/workflows/ci.yml
name: CI
on: [push, pull_request]

jobs:
  check:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env: { POSTGRES_PASSWORD: postgres }
        options: >-
          --health-cmd pg_isready --health-interval 10s --health-retries 5
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '22' }
      - run: npm ci
      - run: npm run check          # the SAME script you run locally
        env:
          TEST_DATABASE_URL: postgres://postgres:postgres@localhost:5432/postgres

And npm run check is one line that does everything, so there is exactly one answer to “what does CI run?”

2 · The exit code is the whole interface

Every CI system on earth reduces your build to one number. Zero means success. Anything else means failure. That is the complete contract, and almost every “why is my build green?” mystery is a place where the number got lost.

node --test ; node scripts/audit.mjs        # ; runs both, and reports only the LAST
node --test && node scripts/audit.mjs      # && stops at the first failure
node --test | tee test.log                 # exit code is tee's, which always succeeds
The classic: a script that ends by printing something

A build script whose last line is echo "done" exits 0 whatever happened above it, because echo succeeded. The output is full of failures and the build is green.

The same trap wears several costumes: a pipe (the exit code belongs to the last command in it), a loop that runs a command per package and never checks the result, and a try/catch in a Node script that logs the error and lets the process end normally. In all four the work failed, was reported as failing, and exited 0.

Try it yourself

3 · A build that is always red is not a check

This is the part people get wrong, and it is a human problem wearing a technical costume.

A pipeline that fails for a reason everybody has agreed to live with trains everybody to ignore the result. After a fortnight, “the build is red” carries no information, and the next real failure arrives in a message nobody opens. The check has not been weakened — it has been switched off, by people, without anyone deciding to.

The fix is not to delete the check or lower it to a warning. It is to acknowledge the known problem explicitly, with two things attached:

  • A why — what this is, and why it cannot be fixed now.
  • A gate — the condition under which it must be fixed. “When B2 lands”, not “later”.

Acknowledged problems still print, under their own heading, so they stay visible. They just stop holding the build red.

The half of this that people leave out

An acknowledgement list needs to be kept honest from both ends:

  • An error that is not acknowledged fails the build. Obviously.
  • An acknowledgement that no longer matches any real error also fails the build, as stale.

Without the second rule the file becomes where problems go to be forgotten: someone fixes the bug, the entry stays, and it silently covers the next thing that produces a similar error. An entry is not a fix, and the list has to be able to tell you when it has stopped describing reality.

4 · Required and advisory are different things

Not every step should stop a release. A formatter complaining about a blank line and a test proving the redemption endpoint leaks are not the same event, and treating them the same produces one of two bad outcomes: people start ignoring failures, or people start deleting checks.

So each step is either required (its failure fails the build) or advisory (its failure is reported and the build continues). The distinction has to be written down per step rather than decided in the moment.

A step that did not run is not a step that passed

This is the one that catches people. A required step can be skipped — a dependency failed, a path filter did not match, a runner died — and the natural way to write the check treats a missing result as a fine one:

if (step.exitCode) failed.push(step.name);   // null is falsy. It "passed".

Same shape as if (token.maxUses), and the same reason: absent and zero are different, and only one of them is falsy. Deny by default applies to your build too — a check whose result you do not have is a check that did not pass.

The extreme case is a pipeline where nothing ran, because a path filter was too clever. Every step green, zero steps executed, and a green tick on a change nobody verified.
