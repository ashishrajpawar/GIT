CI/CD & Release Engineering

Track C

Phase 3 — 4 lessons  |  after C1, because there is nothing to automate until tests exist

Module goal

C1 gave you checks. This module is about the machine that runs them when you forget to, the secrets that machine needs and must never print, and the two things that make shipping Token different from shipping a website:

A migration is not a deploy. You can put the old container back in thirty seconds. You cannot put the old column back once the new code has been writing to its replacement for an hour.

You cannot roll back a phone. An app someone installed stays installed, and store review takes days. Whatever the API promised the oldest client in the wild, it goes on promising.

Lessons

  1. Continuous Integration — the same checks on every push in a clean place, the exit code as the whole interface, and why a build that is always red is not a check at all
  2. Secrets and Environments — validating at boot rather than at 3am, why an empty string is a different diagnosis from a missing one, and the error message that must not contain what it is complaining about
  3. Migrations You Can Deploy — both versions of the code run at once during a deploy, expand and contract, and why the risky step is never the one that ships the code
  4. Releasing to Two Stores — version skew, and the client you cannot take back

What you'll build

  • pipelineOutcome(steps) — the single verdict a build reports, where a step that never ran is not a step that passed and an empty pipeline is not a pass
  • validateEnv(env, spec) — the check that runs before anything listens, reporting every problem at once and never printing any part of the value it is complaining about
  • reviewPlan(steps) — the read of a migration plan before anyone runs it, which answers two separate questions: is this safe to apply in this order, and which of its steps is the point of no return
The failure mode this module is really about

People expect automation to fail by breaking loudly. It mostly fails by reporting confidently and being ignored — a build that is always red, a check whose exit code was swallowed by a pipe, a suppression list nobody prunes, a pipeline that ran zero steps and showed a green tick.

This course has a first-hand example. Its audit exited FAIL on the same three problems every run for weeks; everyone learned to read the output and ignore the exit code; and a new error then landed in a build nobody was opening. Two checks were lost that way. A check that is ignored is worse than no check, because it occupies the space where a working one would go.

Prerequisites

  • C1 — Testing & Quality — automation runs checks, so there have to be checks
  • X1 — Git & Dev Environment — a pipeline is triggered by a push, and reads a repository
