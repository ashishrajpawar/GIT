Secrets and Environments

C2 — Lesson 2 of 4  |  ~45 min

Why this matters for Token

Two environment variables in Token are not like the others.

TOKEN_CODE_PEPPER is mixed into the SHA-256 of every code before it is stored, and TOKEN_CODE_KEY is the AES key the encrypted copy is sealed with. Between them they are the reason the database holds no token code in the clear.

Lose them and every token ever issued becomes permanently unusable. Not degraded — unusable. No redemption can ever be matched again, and no stored code can ever be shown to its owner again. They belong in the disaster-recovery plan, written down somewhere the database backups are not, because a backup and the key that opens it in the same bucket is one bucket.

This lesson is about the boring machinery that keeps a value like that in exactly the places it belongs and out of every place it does not — starting with the one everybody forgets, which is your own error messages.

1 · Validate at startup, not at first use

The natural way to read configuration is at the moment you need it:

function codeHash(code) {
  return sha256(code + process.env.TOKEN_CODE_PEPPER);   // read here, used here
}

This deploys perfectly. The container starts, health checks pass, traffic arrives — and the first person to redeem a token at 3am gets a 500, because undefined concatenated into a string is the word “undefined” and now every hash is wrong.

The same mistake, made at boot instead:

// api/src/config.js — imported first, before anything listens
const problems = validateEnv(process.env, REQUIRED);
if (problems.length > 0) {
  for (const p of problems) console.error(`config: ${p.name} ${p.problem}`);
  process.exit(1);
}

Now the container refuses to start, the deploy fails, and the old one keeps serving. Nobody is woken up.

The general shape, worth naming

Move the failure from where it hurts to where it is cheap. The bug is identical in both versions — a missing variable — and the difference is entirely in when it is noticed. A deploy that never takes traffic is a non-event; a failed redemption at 3am is an incident, a support ticket, and a user who thinks the product is broken.

This is the same argument as the deploy pipeline in the previous lesson and as NOT NULL in a schema: the cheapest failure is the earliest one.

Try it yourself

2 · Missing and empty are different failures

An environment variable that was never set and one that was set to nothing look nearly identical and have completely different causes:

process.env.TOKEN_CODE_PEPPER   // undefined  -> nobody configured it
process.env.TOKEN_CODE_PEPPER   // ""         -> something DID configure it, with nothing

The empty string is the interesting one, because it is what a CI secret expands to when it does not resolve. A workflow referencing ${{ secrets.TOKEN_CODE_PEPPER }} on a fork, or with the name misspelt, or in an environment the secret is not scoped to, does not error — it substitutes an empty string and carries on.

And so if (!value) is the wrong check twice over

It collapses the two cases into one message, so “nobody set it” and “your CI secret is not reaching this job” produce the same line and you debug the wrong one for an hour.

Worse, it is the falsy test again — the same one that made max_uses: 0 mean unlimited. For a secret the values are strings so 0 is not in play, but the habit is, and the next variable you validate will be MAX_UPLOAD_MB or RETENTION_DAYS, where 0 is a real setting that means something specific.

A value of pure whitespace counts as empty too. That is a secret pasted with a trailing newline, and it is always a mistake — but note the asymmetry: whitespace-only is rejected, and a value with real content is never trimmed, because a pepper with a trailing space genuinely is a different pepper and silently changing it would break every hash you have already stored.

3 · The error message must not contain the value

This is the one people write wrong on the first try, every time, because it is genuinely helpful:

throw new Error(`TOKEN_CODE_PEPPER is too short: got "${value}"`);

Startup logs are the most widely shared logs there are. They get pasted into a chat when a deploy fails, attached to a support ticket, screenshotted, and shipped to whatever collects container output. That line has now put the pepper in all four.

The useful version says everything except the thing it must not say:

TOKEN_CODE_PEPPER: too short (needs 32 characters, got 8)

The name, the requirement, and the measured length. Enough to fix it in one attempt, and nothing an attacker can use. A length is not a secret; a prefix is. Resist “starts with abc…” helpfulness — for a 32-character key, the first four characters are 1/8th of it.

Try it yourself

4 · Report every problem, not the first one

A first deploy to a new environment is missing four variables, not one. Validation that throws on the first missing name turns that into four rounds of edit, redeploy, wait, read the log — twenty minutes of finding out one fact at a time.

Collect everything, print it all, then exit. Note this is the opposite of the property checker in C1/0005, which stops at the first counter-example, and the reason for the difference is worth holding on to: there, later failures were probably the same bug; here, each one is a separate fact you will otherwise have to discover in its own deploy.

Try it yourself — broken on purpose

Read the error. Then notice that the crash happens on the case validation exists for.

5 · Where the values actually live

  • Never in the repository. Not in a committed .env, not in the workflow file, not in a comment. Git keeps history, so a secret committed once and removed in the next commit is still in the repository — and this one is public.
  • .env.example, committed, with names and no values. It is the documentation of what has to exist, and it is what a new machine copies.
  • Locally: a .env that is in .gitignore.
  • In CI: repository or environment secrets, injected per step. Note the sharp edge: a pull request from a fork does not get them, which is correct and means those builds must skip the steps that need them rather than failing mysteriously.
  • In production: Coolify's environment settings, and a copy of TOKEN_CODE_PEPPER and TOKEN_CODE_KEY somewhere the database backups are not.
Why these two cannot simply be rotated

Most secrets can be changed on a bad day: a database password, a JWT signing key, an API credential. You update it in two places and move on.

TOKEN_CODE_PEPPER cannot. It is baked into the hash of every code ever issued, and the hash is the only way a code is looked up — there is nothing to recompute from, because the codes themselves are not stored in the clear. Changing it invalidates every token simultaneously.

TOKEN_CODE_KEY is slightly better: the encrypted copies could in principle be decrypted with the old key and re-encrypted with a new one, which is a migration you would have to write and run over every row.

A secret you cannot rotate is a different kind of object from one you can, and it deserves to be treated like the crown jewels rather than like configuration.
