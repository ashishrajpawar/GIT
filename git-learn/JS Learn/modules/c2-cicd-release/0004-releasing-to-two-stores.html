Releasing to Two Stores

C2 — Lesson 4 of 4  |  ~50 min

Why this matters for Token

The previous lesson's asymmetry was that you cannot put a dropped column back. This one is worse, because the thing you cannot take back is on somebody else's phone.

Token's clients set iceTransportPolicy: 'relay' so that a call never takes a direct path — an ICE candidate is an IP address, and a direct path would hand a delivery company the issuer's home IP. Suppose a build ships without it. You notice within the hour. There is nothing you can do from the server: the policy is decided by the client, the fix is a new build, the build needs review, and the phones that already have the old one keep it until their owner chooses to update.

The API can be fixed in a deploy. The app cannot. Everything in this lesson follows from that, including the uncomfortable part: the oldest version still in use decides what your server is allowed to stop doing.

1 · An installed app stays installed

Three facts, none of which have a workaround:

  • You cannot uninstall a build. Removing it from the store stops new installs. Every phone that already has it still has it, and still talks to your API.
  • A fix takes days, not minutes. Apple's review is usually a day and sometimes several; Google's is usually faster and occasionally not. Neither is a deploy pipeline, and neither can be hurried on the day you need it hurried.
  • The user decides when to update. Automatic updates are common and not universal, and a phone that is short of storage quietly stops taking them.

The only real control is slowing the spread: Play's staged rollout releases to a percentage of users, the App Store's phased release does the same over seven days, and both can be halted. Halting stops the next installs. It does nothing about the ones that already happened, which is why the first few percent is where the bug has to be found.

Two stores means two of everything, permanently

Two review queues on different clocks, so the same release is live on one platform and pending on the other for a day or more — every release has a window where the two platforms are on different versions, and it is not an edge case, it is every single time.

So the minimum supported version is per platform. A single global number forces an update on people who cannot yet get it, which is the one failure in this lesson that turns a working app into a dead one.

2 · Version skew: the API keeps every promise it ever made

At any moment your API is serving several versions of the app at once — the current one, last month's, and someone's six-month-old install. Which means the rule from the migrations lesson reappears one layer up, in the same shape:

Change to the APISafe?Why
Add a new response fieldYesAn old client ignores what it does not read
Add an optional request fieldYesAn old client that omits it still gets the old behaviour
Add a new endpointYesNothing old calls it
Remove a response fieldNoOld code reads undefined and usually renders it
Make a request field requiredNoEvery old client's request becomes a 400
Change what a value meansNoThe worst kind: nothing errors and everything is wrong

Token has a live example of the last row. max_uses is null for unlimited and 0 for none at all — opposite meanings, one of them falsy. Redefining which is which on the server would leave every installed app confidently showing the wrong thing, with no error anywhere.

3 · The two things that reach a phone without a store

Not everything has to wait for review, and knowing which half is which is most of release planning:

  • Over-the-air JavaScript updates (expo-updates). Token is an Expo app, so a bug in JS or in a screen can be published straight to installed apps, in minutes. This is the closest thing to a rollback that mobile has.
  • The redemption web page at tokn.app is a normal web app. It deploys like the API and has no version skew of its own — there is exactly one version and everybody has it on the next page load.

What an OTA update cannot touch is native code, and Token has more of that than most apps: react-native-webrtc, the iOS Notification Service Extension that decrypts push previews on the device, expo-secure-store's Keychain and Keystore access. A change to any of those is a new binary, which is a store review.

The skew nobody plans for: user versus holder

Because web/ updates instantly and the app does not, the two sides of a Token conversation drift apart. A courier on today's redemption page is talking to an issuer on a three-month-old app, over a WebSocket and a shared encryption scheme.

The web page is the side that has to bend, precisely because it is the side you can change. It is tempting to ship the clever new thing on the surface you control and wait for the app to catch up; that is exactly backwards.

4 · The force-upgrade lever, and how to not brick anyone

Eventually a version really is too old to serve — a security fix, or a message format the server can no longer produce. The lever is a policy the client asks about at launch:

{
  "ios":     { "minSupported": "1.4.0", "latest": "1.7.2", "storeUrl": "https://apps.apple.com/app/id..." },
  "android": { "minSupported": "1.4.0", "latest": "1.7.0", "storeUrl": "https://play.google.com/store/apps/details?id=..." }
}

Two design points, both of which have to be right before you ever need them:

  • The endpoint has to be one the oldest client already calls. A force- upgrade check that shipped in 1.5 cannot reach a phone running 1.2. In practice it belongs in the very first release, and it is the reason to ship a version endpoint on day one.
  • A forced update must have somewhere to go. Blocking the app while the policy carries no store link for that platform is a screen with no button on it. If the link is missing, the honest fallback is to ask rather than to insist — an app that is annoying beats an app that is dead.

Try it yourself — broken on purpose

Read the error. It happens for a client the policy simply does not describe, which is every future platform and every request with a typo in it.

The second bug is the comparison. "1.10.0" < "1.9.0" is true, because string comparison reads character by character and "1" comes before "9". Every version scheme survives this until the day the minor number reaches 10, and then a force-update rule starts firing on the newest build in the wild.

5 · Build numbers, and being able to find the code again

  • Android versionCode is an integer that must always increase, and a value that has been uploaded can never be uploaded again — not even after deleting the build. Same for the iOS build number within a version.
  • The user-facing version is separate and is allowed to stay put across several builds.
  • Every build must be traceable to a commit. A crash report naming a build you cannot map to a revision is a crash you cannot fix, and "it was roughly that Tuesday" is not a map. Stamp the commit into the build and into whatever the app reports.
