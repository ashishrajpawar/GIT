Migrations You Can Deploy

C2 — Lesson 3 of 4  |  ~50 min

Why this matters for Token

A deploy that goes wrong is a thirty-second problem. You put the old container back and the site is exactly as it was.

A migration that goes wrong is not. Token's rules used to live in a tokens.rules JSONB column and now live as access_rules rows, one per rule. Moving them meant creating a table, copying the data across, shipping an engine that reads the rows, and eventually dropping the column. The moment that column is dropped, every rule a user set is only in the new table — and if the copy was wrong, the evidence is gone with it.

Putting the old container back does not put the old column back. That asymmetry is the whole lesson, and it has one consequence worth stating up front: the risky step is never the one that ships the code. It is the one that ran quietly before the containers even started.

1 · During a deploy, both versions are running

This is the fact everything else follows from, and it is easy to miss because nothing on a dashboard shows it. A deploy is not a switch. For some window — seconds if you are lucky, minutes if a container is slow to drain — the old code and the new code are both connected to the same database, serving real requests.

So consider the most natural migration anybody ever writes:

ALTER TABLE tokens RENAME COLUMN rules TO legacy_rules;

It is one line, it is instant, and it is atomic. It is also the single most dangerous migration in common use, because the instant it commits, every running instance of the old code — which is still serving requests — is querying a column that no longer exists. Not slowly degraded. Erroring on every request, until the new containers finish starting.

And the rollback is worse. Rolling back means deploying the old code again, against the schema you just changed, and the old code has no idea the column was renamed.

Two questions, asked about every migration

Does the code that is currently deployed survive this change? If not, the migration breaks production the moment it commits, before the new code is anywhere near ready.

Does the new code survive without this change? If not, the migration has to come first, which is why migrations run before containers start.

A rename answers no to the first. That is the definition of an unsafe migration, and it is why the fix is never "deploy faster" — there is no speed at which the two versions stop overlapping.

2 · Expand and contract

The alternative is to never change anything — only to add, and much later, to remove. A rename becomes four steps spread across two releases:

PhaseWhat it doesOld code survives?
expandAdd the new table or nullable column. Nothing reads it yetYes — it does not know it exists
backfillCopy the existing data into the new shape, in batchesYes — still reading the old shape
codeShip the version that uses the new shapeYes — the old shape is still there
contractDrop the old column, in a later releaseNo — which is why it waits

For Token's rules move, that is:

-- Release 1, expand
CREATE TABLE access_rules (
  id          BIGSERIAL PRIMARY KEY,
  token_id    BIGINT NOT NULL REFERENCES tokens(id) ON DELETE CASCADE,
  rule_type   TEXT NOT NULL CHECK (rule_type IN ('time_window', 'contact_limit', 'channel_restrict')),
  payload     JSONB NOT NULL,
  enabled     BOOLEAN NOT NULL DEFAULT true
);

-- Release 1, backfill: one batch, repeated until it copies nothing
INSERT INTO access_rules (token_id, rule_type, payload)
SELECT id, key, value FROM tokens, jsonb_each(tokens.rules)
 WHERE tokens.id BETWEEN $1 AND $2;

-- Release 1, code: the engine reads access_rules and writes both shapes

-- Release 2, contract, and only once release 1 is known good
ALTER TABLE tokens DROP COLUMN rules;

The contract step sits in a later release, not merely later in the file. That is the part people compress, and compressing it puts the drop in the same window where the old code is still running.

Why the gap is worth the inconvenience

Between the two releases, the old column is still there and still correct. If the new engine turns out to read the rules wrongly — and b7/0002 had exactly that class of bug, an unknown rule type falling through to allowed — you can put release 1's predecessor back and everything works, because nothing was destroyed.

Once the drop runs, that option is gone. The release gap is not caution for its own sake; it is the window in which the migration can still be found to be wrong.

3 · The steps that lock the table

An unsafe migration is not always unsafe because of what it removes. Some are unsafe because of how long they hold the table:

  • CREATE INDEX without CONCURRENTLY takes a lock that blocks every write to the table for as long as the index takes to build. On conversations that is every redemption in the country, waiting.
  • ADD COLUMN ... NOT NULL with no default is rejected outright if any row exists. With a constant default, modern Postgres does it instantly; with a volatile default such as now() it rewrites the whole table.
  • Adding a CHECK constraint scans every existing row, and fails if a single one disagrees. Token's biconditional constraints — CHECK ((status = 'revoked') = (revoked_at IS NOT NULL)) — are exactly the kind that will refuse to be added to a table with historical rows that were never held to them.
  • An unbatched backfill is one transaction over millions of rows: a long lock, a very large write-ahead log, and a replica falling behind.

The pattern for all four is the same. Split the fast, exclusive part from the slow, scanning part: add the constraint NOT VALID so it applies to new rows immediately, then VALIDATE CONSTRAINT in its own statement, which takes a much weaker lock.

4 · A migration runs exactly once, in order

Every migration tool keeps a table of what it has applied, and applies each file once. That part is easy to get right because the tool does it. The part that is easy to get wrong is what "in order" means:

Try it yourself — broken on purpose

Read the error. The bug is in one word, and the fix is in how the files are named.

Sorting strings puts 10_ before 9_, because "1" is less than "9". The answer is to zero-pad the names — 0009_, 0010_ — so that the ordering you want and the ordering you get are the same thing. A timestamp prefix does the same job and additionally stops two people on two branches from both writing 0007_.

And the migration you already applied is not editable

A migration file that has run somewhere is finished. Editing it changes nothing on the machine that already applied it, and the tool will not notice, so your laptop and production now have different schemas from the same repository.

The fix for a wrong migration is another migration. This is the same rule as the ADRs in token/docs/adr/, which are append-only for the same reason: what has already been acted on cannot be quietly revised.

5 · "Down" migrations mostly do not exist

Migration tools invite you to write a down beside every up, and for an expand step that is honest — the down for CREATE TABLE access_rules is DROP TABLE access_rules, and nothing is lost because nothing was there.

For a contract step it is a lie:

-- up
ALTER TABLE tokens DROP COLUMN rules;

-- down
ALTER TABLE tokens ADD COLUMN rules JSONB;   -- the column is back. It is empty.

Try it yourself

The useful thing to write is not a fictional down. It is a note on the step saying this one cannot be undone, so that whoever runs the release knows which of its steps is the point of no return. That is what the exercise below reports.
