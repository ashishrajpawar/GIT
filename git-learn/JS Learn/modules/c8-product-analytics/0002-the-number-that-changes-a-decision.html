The Number That Changes a Decision

C8 — Lesson 2 of 2  |  ~50 min

Why this matters for Token

The previous lesson built a report that is safe to publish. This one is about the step before it: deciding that a number should be collected at all.

Under the DPDP Act that is not a preference. Personal data is collected for a specified purpose, and "it might be useful later" is not one. So the question what decision does this number feed stops being a product-management nicety and becomes the thing that makes the collection lawful.

1 · The metric nobody has ever looked at

Every product accumulates them. Somebody instrumented a screen during a launch, the dashboard has forty panels, and nobody has changed a decision because of thirty of them.

In most companies that is waste. Here it is also a growing pile of personal data whose stated purpose was never written down, retained under a policy nobody set, and disclosed on a Play Data Safety form that has to be accurate.

Note what happens to average session length. It is a perfectly good number, it is on every analytics dashboard in the world, and if you ask what you would do differently at forty seconds versus four minutes, there is no answer. That is the test.

2 · A decision, and a value at which you would act

Two fields, and they fail differently.

  • No decision is disqualifying. There is no purpose to specify, so there is nothing to collect it under.
  • No threshold is a warning. You genuinely may be exploring — establishing what normal looks like before you can say what would surprise you.

The threshold is worth writing down even when it is a guess, for the reason c7/0004 gave about alerts: a number with no action attached becomes a number people look at and feel something about. "Below 20% of shares we drop the scanner" can be wrong, and being wrong in public beats being vague in private.

3 · The question you cannot answer without a subject

Sooner or later somebody asks the most reasonable question in product work: do people come back?

Retention needs to link one person across two days. There is no clever aggregation that avoids it — linking is what the question is. So there are three answers and they are not all the same size:

AnswerWhat it costs
Store a stable device id per eventYou get retention, cohorts and funnels — and a per-user timeline by another name, which reopens ADR-0012's age decision along with it
Compute it on the device and report an aggregateReal work: on-device state, a reporting schedule, and a number you cannot audit or recompute
Do not answer itYou will be asked for it repeatedly, by people who are right that it is useful
The decision, and the number it buys instead

Token measures daily actives and not retention. The daily count is taken over a device hash salted with a per-day secret that is destroyed at the end of the day, so the same device produces an unrelated value tomorrow.

What that buys: a real daily-active figure, from data in which yesterday's rows cannot be joined to today's by anybody, including you.

The cost, stated: retention, week-one cohorts and any funnel spanning days are unavailable, permanently and by construction. That is the single most-requested growth number and you will not have it.

The alternative rejected: a stable device identifier, which supplies all of it. It is a pseudonymous per-user record, so it makes the analytics store a behavioural profile and pulls the age decision back open. Reversible only by making that trade explicitly, which is the point of writing it down here.

4 · A device id is a subject

The word "anonymous" gets attached to device identifiers constantly, and it is worth being precise about why it does not apply.

The identifier does not need to be a name. It needs only to be the same one next time, and everything you attach to it accumulates against a person. So the metric register admits one value for a subject: none.

5 · Consent that stops collection

Analytics is not necessary to deliver Token. A user who declines it gets the same product, so the lawful basis is consent, and consent under DPDP must be as easy to withdraw as it was to give.

The implementation detail that matters: withdrawal has to stop the collection, not the reporting. An opt-out that keeps writing rows and filters them out of a dashboard has changed nothing about what you hold; it has changed a view.

This is also why the previous lesson ruled out a vendor SDK before any configuration question. A library that identifies the device when it initialises has already collected before your dialog has rendered, and there is no opt-out that reaches backwards.

6 · Retention, and the convention that does not flip

retainDays takes the values this course has been careful about since 01/0011:

The convention is exactly the one max_uses uses: null is unbounded, zero is none. What changes between the two is not the meaning but whether unbounded is the outcome you want — an unlimited token is a feature, and unlimited retention is a liability.

That is worth separating carefully, because "the rule is reversed here" is the kind of thing people remember wrongly. The rule is not reversed. Only the desirability of one end of it is.

7 · An undeclared cardinality is not a small one

A metric declares how many values it expects each dimension to take. If a dimension has no declared count, the honest reading is that it is unbounded.

Compare that with c6/0001, which insisted an unmeasured capacity limit must not be treated as unlimited. Two opposite readings of the same missing information, and the principle that produces both is the one this course keeps arriving at:

Ask which way the error hurts. Assuming an unknown capacity limit is infinite makes the box look bigger than it is. Assuming an unknown cardinality is small makes the label look safer than it is. In both cases the safe reading is the one that assumes the worse outcome, and the two happen to point in opposite directions.

8 · Blocking and advisory, and where the line goes

The review has two severities, and the split is not by how bad the number feels.

BlockingAdvisory
A subject, an unlisted dimension, no decision, the wrong lawful basis, unbounded or over-long retentionNo threshold yet, and a cell count over budget
Each is a fact about whether you may collect thisEach is a fact about whether it is worth what it costs

Note where identifiability sits, because this is where the split is easy to get wrong. A high cell count is advisory, and c7/0003 warned that the cost argument alone misleads: a cheap label with fifty values can still single a person out. The thing protecting identity here is the allow-list, which is blocking. The budget protects the bill. Keeping them in different severities is what stops somebody arguing their way past the first by pointing at the second.

9 · Broken on purpose

The validator falls over on the metric it exists to reject, which is the ordinary shape of a validation bug: the well-formed input is the one that gets tested. Guard the type before the value — and note that the empty string has to be caught too, since a11/0003 found exactly that hole in a display name that passed validation and rendered as nothing.
