Product Analytics

Track C

Phase 3 — 2 lessons  |  after C7, because the tools are the same and the rules are not

Module goal

C7 answered is it up, is it slow, what broke. This module answers is anybody using it, and which part. The plumbing is almost identical — counters, labels, a dashboard — and that similarity is the trap, because the rules governing the two are not.

Operational telemetry describes a system. Product analytics describes people. One of those is about your machines and the other is personal data under the DPDP Act, and the code looks the same either way.

Lessons

  1. An Event With No Subject — counts rather than timelines, the key built from an allow-list, small cells, and why suppressing one of them suppresses none
  2. The Number That Changes a Decision — purpose limitation as a function you can run, the question you cannot answer without a subject, and consent that stops collection rather than reporting
This module is constrained by a decision it did not make

ADR-0012 set Token's minimum age at 18 with no under-18 flow and no verifiable-parental-consent surface. Part of what makes that affordable is recorded in CLAUDE.md: DPDP's outright ban on behavioural tracking of children is satisfied for free by analytics being self-hosted event counts with no per-user timelines.

So the consequence, stated plainly because it is easy to trip over: a growth experiment that adds behavioural tracking reopens the age decision, not just the analytics one. The cheapest-looking change in this module is the one that costs a verifiable-parental-consent flow.

What you'll build

  • aggregate(events, spec, policy) — one report from one event stream: the key built from a validated allow-list rather than from the event, cells below a minimum suppressed, a second cell suppressed alongside a lone one, and the case where the honest output is no number at all
  • reviewMetric(metric, policy) — a metric definition read against purpose limitation: what decision it feeds, at what value you would act, how long it is kept, and whether it needs a subject to compute

What this module does not repeat

C7/0003 owns cardinality as a cost argument — a label per user is a bill. It also states the sentence this module is built on top of: the cardinality rule and the privacy rule coincide. That is convenient, because one rule serves both, and dangerous, because somebody who knows only the cost argument will add a cheap label with fifty values that still singles a person out.

F1 owns the compliance obligations themselves — the RoPA, consent, the Data Safety form. Where they touch, F1 states what must be true and this module writes the code that makes it true.

Prerequisites

  • C7 — Observability — the same counters, and the argument about labels that this module inherits
  • B10 — Security & DPDP — what personal data is, and what saying so commits you to
