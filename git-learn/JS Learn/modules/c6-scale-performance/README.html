Scale & Performance

Track C

Phase 3 — 5 lessons  |  alongside the B-track, not after it

Module goal

ADR-0003 committed Token to an unusual shape: built to scale out, deployed on one box. The architecture assumes N replicas; the deployment runs one until traffic says otherwise. This module is where that sentence turns into code.

The reason it is not a later module is in its own plan row: you cannot defer what you are building for. Retrofitting statelessness is a rewrite. Adding a replica is a config change. Which of those you are doing in eighteen months was decided by things you typed this month.

Lessons

  1. The Ceiling Is a Minimum, Not a Number — capacity as arithmetic you can do before you buy anything, and why the limit that binds is rarely the one being watched
  2. One Node's Memory Is Not the System's State — the socket registry that works perfectly until the second replica, and the fan-out that fixes it without delivering everything twice
  3. A Limit That Holds on One Node Is Not a Limit — shared counters, the fixed window that permits double its own ceiling, and the gap a daily cap leaves open
  4. The Cache That Outlives a Revocation — what may be cached about a token and what may never be, and why the cache key is an ADR-0007 decision
  5. The Query on the Authorisation Path — N+1 as a spender of the resource lesson one said binds first, and the index that is load-bearing rather than an optimisation
Performance work has a specific failure mode, and it is not slowness

Every lesson here makes something faster or cheaper, and every one of them can make Token wrong instead. A shared counter that falls back to a local one still returns a number. A cache serving a revoked token returns a token. A skipped query returns the answer it had.

That is why this module sits after C1 and C7 in practice even though its plan row puts it alongside the B-track: the optimisations here are exactly the kind whose defects are invisible from inside, and the tests and the telemetry are how you see them at all.

What you'll build

  • capacityCeiling(box, workload) — how many concurrent connections one box holds, reported as the smallest of several limits together with which one it was, because the binding limit is the only one worth raising
  • planDelivery(message, sockets, self) — who this node writes to and whether it publishes, written so that adding a second replica changes nothing and so that neither replica delivers the same message twice
  • checkLimit(bucket, now, policy) — a sliding window over timestamps with an injected clock, next to the fixed window it replaces and the boundary burst that motivates it
  • planTokenRead(request, cached, now, policy) — the decision of whether a cached answer may be served at all, where the purpose of the read decides and anything on the authorisation path never may
  • reviewAccessPath(trace, policy) — a request's queries read as a sequence: the one issued once per row, the one that scans, the one that was never needed, and what the whole set costs in the resource that runs out first

What this module does not repeat

C7 built the measurements — percentiles, error rates, the scrape summary. This module is what you do with them. The order matters and is the reason C6 waited: tuning without measurement is guessing, and a guess that happens to help is indistinguishable from one that does nothing.

B2 owns the schema itself. Where a lesson here names an index, it is arguing about when the index is consulted, not about how to declare one.

Prerequisites

  • B5 — WebSocket Server — lesson two is about the registry that server keeps
  • C7 — Observability — you cannot tune what you cannot see
