The Query on the Authorisation Path

C6 — Lesson 5 of 5  |  ~55 min

Why this matters for Token

Lesson one worked out which resource runs out first. On a box whose descriptor limit has been raised — a one-line change — the answer is the Postgres pool. This lesson is about what spends it.

And it closes the module by connecting the two ends: an N+1 is usually described as slow. It is worse than slow. It is a request holding the binding resource for five times as long as it needs to, on the path that runs before a message is delivered — so when it finally matters, every user is queueing behind it at once.

1 · Not all queries are equal, and the difference is not size

Token's redemption and message paths run a small set of queries before anything is allowed to happen: find the token by code_hash, count its conversations, load its rules. None of them returns much. All of them run before the request has done anything useful.

A slow query on that path is a denial of service you built yourself. Not because it is slow — because it is slow while holding a pooled connection, and the pool is a fixed, small number that every other request is also waiting for.

Nothing about that is a database problem. The pool is a queue, and how long each request holds a slot is the whole of its capacity.

2 · An index that is load-bearing, not an optimisation

CLAUDE.md records a deliberate decision: there is no use_count column. A stored counter is a second copy of a fact, and every way it drifts ends with a token permitting the wrong number of uses, silently.

The cost of that decision is named in the same paragraph, and it lands exactly here:

Enforcement lives in the redemption transaction, which takes FOR UPDATE on the token row, counts, then inserts. idx_conversations_token_id is load-bearing rather than an optimisation.

Read that carefully, because it is a category most indexes do not belong to. An ordinary index makes a screen feel quicker; drop it and somebody complains. This one is the only reason a correctness mechanism is affordable. Drop it and the count becomes a sequential scan inside a row lock, on the redemption path, at which point the honest description is not "slow" but "the use limit no longer works at any reasonable traffic".

Which is why the review has to know the path

An unindexed query on a settings screen is a performance ticket. The identical query on the authorisation path is a correctness and availability problem. The same SQL, and two different severities, decided entirely by where it runs.

Same shape as the previous lesson: the purpose of the read decided whether it could be cached, and nothing about the data itself did.

3 · N+1, and why counting repetitions is enough

The classic: one query returns N rows, and then one query per row.

A detector for this can be simple, and it is worth being honest about what the simple version actually knows: it detects repetition, not causation. Seeing the same query label twelve times in one request does not prove it was driven by a previous result set. It is still the right thing to report, because there is no good reason for it either way — twelve identical queries want to be one query with an IN (...) or a join, whatever produced them.

A detector that tried to prove causation would need the parameters, and the parameters are the values you spent c7/0001 learning not to keep.

4 · The fix that makes it worse

Faced with 201 sequential queries, the obvious improvement is to stop doing them one after another:

const holders = await Promise.all(rows.map(r => findHolder(r.holderId)));

This is why the review reports peak concurrent connections rather than a query count. A count says how much work was done; the peak says how much of the binding resource was held at once, and lesson one established that the binding resource is what a capacity number is made of.

The actual fix is neither: one query returning the twenty rows. It holds one connection, for about as long as one of the twenty did.

5 · OFFSET gets slower the further in you go

LIMIT 20 OFFSET 4000 does not skip 4,000 rows. It produces 4,000 rows and throws them away.

The alternative is keyset pagination: instead of "skip 4,000", say "after this one", with a WHERE (created_at, id) < ($1, $2) that an index can seek straight to. Every page then costs the same.

Note the second column. A cursor on created_at alone breaks when two rows share a timestamp — rows are skipped or repeated across pages, silently, exactly the class of bug a3/0004 dealt with on the client. The tiebreaker has to be something unique.

6 · The query that is fine today

SELECT * FROM conversations WHERE token_id = $1 with no LIMIT is perfectly reasonable, and stays reasonable right up until one token has been redeemed by eight hundred people.

This is the one finding in the review that is about the future, and it is worth keeping separate from the others for that reason. An unindexed query on the auth path is wrong now. An unbounded query is a decision that nothing will grow, written down in a place where nobody will ever read it as a decision.

7 · Half-open intervals, for the third time

Peak concurrency is an overlap question, and overlap needs an edge rule. A query that ends at exactly the millisecond another begins did not overlap it.

The rate limiter's window was half-open. The cache's freshness test was half-open. This is the same convention and it is the third place in one module, which is the point: one convention applied everywhere is worth more than each site choosing the fairer edge.

8 · Broken on purpose

A request that ran no queries is not an error and is not rare — a cache hit from the previous lesson produces exactly that trace. reduce without an initial value throws on an empty array, so the tooling that watches for slow requests falls over on the fastest ones.
