The Ceiling Is a Minimum, Not a Number

C6 — Lesson 1 of 5  |  ~50 min

Why this matters for Token

ADR-0003 says Token is built to scale out and deployed on one box. CLAUDE.md even names the ceiling: a few thousand concurrent WebSocket connections and low tens of thousands of users, bounded by memory and file descriptors first, then Postgres connections.

That sentence is worth almost nothing until you can derive it. A ceiling you were told is a number you will defend or panic about; a ceiling you computed is a list of config lines with your own arithmetic beside each one, and you know which to change.

1 · A box does not have "a capacity"

The question how many users can this server handle? has no answer, because a server does not run out of one thing. It runs out of several, at different moments, and it stops at the first.

For Token's API, three of them matter and they are not interchangeable:

  • Memory. Every open WebSocket costs kilobytes — the socket, its buffers, and whatever your process hangs off it.
  • File descriptors. On Linux every socket is a file descriptor, and a process has a hard cap on how many it may hold.
  • Database connections. Not one per user — that is what pgbouncer is for — but a fraction of one, held for as long as a query runs.

Three limits, three ceilings, and the one that matters is the smallest.

Fourteen thousand, one thousand, one thousand four hundred and forty. The box holds a thousand connections — and it has memory for fourteen times that, sitting unusable.

2 · The number nobody chose

Look at what is binding. It is not memory, which you paid for and can see on a dashboard. It is 1024 — the default open-file limit on a great many Linux systems, a value that arrived with the operating system and that nobody involved in Token ever typed.

The binding limit is very often a default, and defaults are invisible in exactly the way this course keeps meeting: rclone copy that never deletes, an error tracker that attaches the request body, a metrics library that will happily label by user id. Nothing errors. Nothing warns. It is just quietly true.

Which is why the useful output of a capacity calculation is not the number. It is the name.

One line of configuration and the ceiling goes from 1,000 to 1,440. Not from 1,000 to 14,298 — because raising the binding limit does not give you the next-largest number, it gives you the next-smallest limit. The database is now what stops you, and the conversation moves to pgbouncer.

This is why the name is the deliverable

"We can hold a thousand" invites the wrong follow-up — buy a bigger box. "File descriptors bind at a thousand and the pool binds at 1,440 behind it" tells you the first change is free, the second is a pgbouncer setting, and neither of them is a purchase.

3 · Subtract before you divide

A box with 4 GB does not have 4 GB for sockets. The operating system needs some. On a Coolify single-box deployment, Postgres and Redis are containers on the same machine and need a great deal more.

4 · Floor, never round

The memory calculation comes out at 14,298.76. There is no such thing as three quarters of a connection, and rounding up admits one the box cannot hold.

One connection is not a crisis. The habit is the point: every rounding decision in a capacity calculation goes downwards, because the cost of being wrong is not symmetric. Too low and you buy a bigger box a month early. Too high and the box falls over at the moment it is busiest, which is the moment you least want to be reading a stack trace.

5 · An unknown limit is not an unlimited one

A ceiling computed from two limits out of three is not a ceiling. It is an upper bound on a number you have not worked out, and the honest thing for the function to do is hand back both the figure and the list of what it could not see.

There is exactly one place Infinity is the right answer

An unknown limit is not infinite — you simply have not looked.

A zero cost genuinely is. If a workload holds no file descriptor per connection — plain HTTP requests that open and close rather than a persistent socket — then descriptors do not bind that workload at any number, and available / 0 giving Infinity is arithmetic telling the truth.

The two look alike in a result object and mean opposite things. Keep them in different fields.

6 · The thesis

Read back over the four mistakes in this lesson.

  • Dividing the whole box instead of the spare part — too big.
  • Rounding instead of flooring — too big.
  • Treating an unmeasured limit as no limit — too big.
  • Quoting the memory number because it is the one on the dashboard — too big.

Every casual error in a capacity calculation makes the number larger. Nobody accidentally under-estimates. That asymmetry is not a coincidence — each of these mistakes is a step you skipped, and skipping a step can only remove a constraint.

So the working assumption for the rest of this module: a capacity figure you did not derive is too high, and by an unknown factor.

7 · When two limits are close together

One last piece of the report. If descriptors bind at 1,000 and the pool binds at 1,056, raising the descriptor limit buys you 5.6%, and then you are back in the same conversation having spent an afternoon.

A capacity report that says "file descriptors bind, and the database is right behind it" is telling you to fix both or neither.

8 · Broken on purpose
