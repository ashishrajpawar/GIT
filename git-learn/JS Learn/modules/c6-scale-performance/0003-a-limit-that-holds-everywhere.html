A Limit That Holds on One Node Is Not a Limit

C6 — Lesson 3 of 5  |  ~55 min

Why this matters for Token

Three things in Token are protected by a rate limit and by nothing else, and they fail in three different currencies.

  • The OTP endpoint costs money. Every request is an SMS through an aggregator, billed. An unlimited one is somebody else spending your balance.
  • The redemption endpoint is guessable. 3112 is far too large to exhaust, but a limit is what makes that arithmetic the relevant arithmetic rather than a comfort.
  • The message send path is C3's contact_limit — a product rule the user chose, not an infrastructure concern, and one whose enforcement is the same machinery.

1 · The limit that multiplies by the replica count

The previous lesson's registry lived in one process's heap. So does this:

const hits = new Map();   // key -> timestamps

function allow(key, limit, windowMs) {
  const now = Date.now();
  const recent = (hits.get(key) || []).filter(t => t > now - windowMs);
  if (recent.length >= limit) return false;
  recent.push(now);
  hits.set(key, recent);
  return true;
}

With one replica this is a correct limiter. With three, each process enforces the limit against its own third of the traffic:

Notice that nothing had to go wrong for this to happen. Nobody misconfigured anything, no request failed, and the limiter did its job perfectly on every node. The defect is that "its job" was defined over the wrong population.

Which is why ADR-0003 lists rate limiting as one of the three reasons Redis is required rather than optional, alongside socket fan-out and presence. All three are the same fact in different clothes: a number that has to be true of the system cannot live in one process.

2 · The fixed window lets through double

Now move the counter into Redis, and use the obvious primitive — a key per window:

const bucketKey = `otp:${phoneHash}:${Math.floor(now / 60000)}`;
const count = await redis.incr(bucketKey);
await redis.expire(bucketKey, 60);
return count <= limit;

This is genuinely shared, genuinely cheap, and permits twice the limit:

The window boundary is a fixed instant that the counter resets on, and the counter has no memory of what happened just before it. Every fixed-window limiter permits up to twice its stated limit across a boundary, and there is no configuration that fixes it — it is what the design is.

Sometimes that is acceptable and you write it down. For an SMS bill it is a doubling of the worst case, and for the redemption endpoint it doubles an attacker's rate at the one moment they can predict, since window boundaries are just clock time.

3 · The sliding window, and what it costs

Keep the timestamps instead of a count. Then "the last minute" means the last minute from now, and there is no boundary to sit on.

The cost is honest and worth stating: you now store one timestamp per request instead of one integer per window. For a limit of ten that is nothing. For a limit of ten thousand it is a different decision, and this is where a token bucket — a count plus a refill rate — starts to look better.

4 · The comparison is >, not >=

A hit sitting exactly on the window edge is out, not in. This is the half-open window, and the course has already made the argument once, in c3/0002: with >= a hit at precisely now - windowMs stays in the window forever if the clock happens to land there, and more usefully, one convention consistently applied is worth more than an argument about which edge is fairer.

5 · The clock that runs fast

Replicas do not share a clock. NTP keeps them close, but a timestamp written by one node and read by another can be slightly in the future.

c3/0002 met the same anomaly and made the opposite decision — future events were counted as ignored and used for nothing. That is not an inconsistency, and the reason is worth having exactly:

There, a future timestamp was evidence about a sender, and evidence you cannot trust should not count towards flagging somebody.

Here, a hit is a charge already made — an SMS that has been sent, a redemption already attempted. Discarding it does not withhold a judgement, it refunds a request.

The same anomaly gets the opposite treatment because the direction of the harm is opposite. Dropping evidence is cautious; dropping a charge grants access. When you meet a rule that seems to contradict one from another lesson, that is the question to ask: which way does the error let somebody through?

6 · Unlimited and none are different, and only one of them is falsy

Token has met this before, and CLAUDE.md keeps it near the top for a reason: max_uses of null is unlimited, 0 permits nothing.

Rate policies have the same shape — an uncapped internal endpoint, and an endpoint switched off during an incident — and the same trap:

The truthiness test gets one of the three wrong, and it is the one that matters: an endpoint deliberately closed is thrown wide open, during an incident, which is when somebody turned it off.

7 · When the shared counter is not there

Redis is a network service and will occasionally be unreachable. Three answers exist and two of them are wrong:

AnswerWhat actually happens
Fail open — allow the requestEvery limit in the product is off simultaneously, at the moment infrastructure is already unhappy. The SMS bill is unbounded during the exact window nobody is watching a dashboard.
Fall back to a local counterWorse than either. It returns a plausible number, so nothing anywhere reports a problem — and it is the per-node limiter from section 1, which is the bug this whole lesson exists to remove.
Fail closed — refuse, with a short retryA Redis blip becomes a user-visible failure. That is a real cost and it is the one to accept.
The decision, with the cost stated

Fail closed. When the shared store cannot be reached, the limiter refuses and asks the client to retry shortly.

The cost: a Redis outage becomes a login outage rather than a degraded one. ADR-0003 already accepts that — Redis is required, so an unreachable Redis is an outage whether or not the limiter pretends otherwise. Pretending changes which failure you get, not whether you have one.

Why the local fallback is the worst option, and this is the README's warning about this whole module: it still returns a number. A refusal is visible. A wrong answer that looks right is not.

8 · What a rate limit is not

C3's contact_limit caps messages per day. CLAUDE.md records the gap it leaves, in the note explaining why cooldown was dropped for v1:

A limit constrains a total over a period. It says nothing about distribution, and the thing a user actually objects to is usually the distribution. Adding cooldown later is one value in a CHECK list — which is the concrete payoff of rules being rows rather than a JSONB blob — but until then the gap is real and should not be described as covered.

9 · Broken on purpose

Run it. The error is the lesson: it is what "the shared store was unreachable" looks like when nobody decided what should happen.

It crashes, which by accident fails closed — the request errors and no SMS is sent. That is the right outcome reached the wrong way: a 500 with a stack trace instead of a retry hint, an entry in the error tracker for something that is not a bug, and behaviour nobody chose and nobody can find in the code.
