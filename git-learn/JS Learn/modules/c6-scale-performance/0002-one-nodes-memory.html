One Node's Memory Is Not the System's State

C6 — Lesson 2 of 5  |  ~55 min

Why this matters for Token

The previous lesson worked out when one box runs out. This one is about the change you make next — and ADR-0003 exists because that change has to be a config edit rather than a rewrite.

The thing standing between those two outcomes is a single JavaScript Map. Almost every WebSocket tutorial keeps its connections in one. It works flawlessly on your laptop, flawlessly in staging, flawlessly in production — and then the day somebody sets replicas to 2, roughly half of all messages stop arriving, with no error anywhere.

1 · The registry every tutorial writes

A WebSocket server has to remember who is connected. The obvious way:

const sockets = new Map();   // socketId -> ws

wss.on("connection", (ws, req) => {
  const id = newSocketId();
  sockets.set(id, ws);
  ws.on("close", () => sockets.delete(id));
});

This is correct. It is also node-local, which is a property nothing in the code announces. sockets lives in one process's heap, and a second process has its own, containing entirely different people.

Note what did not occur. Nothing threw. Nothing logged. The send returned normally and the sender's own screen shows the message, because their client displayed it optimistically. The only party who finds out is the recipient, later, by not having been contacted.

2 · The fix, and the bug inside the fix

The standard answer is Redis pub/sub, which is why CLAUDE.md says Redis is required, not optional. The node that accepts a message writes to whichever recipients it happens to hold, and publishes the message on a channel; every other node receives it and does the same with its own.

Now the bug. Write it the way it reads naturally:

The early return is an optimisation that is exactly right on one node, because on one node "nobody here wanted it" and "nobody wanted it" are the same sentence. On two nodes they come apart, and the message is dropped by the branch that exists to avoid pointless work.

The rule

Whether to publish must not depend on whether there were local recipients. A node's own registry is not evidence about the system. It is evidence about the node.

This is the whole reason ADR-0003 says built to scale out, deployed on one box. The single-box deployment is fine; what is not fine is code that is only correct because there is one box, since nothing distinguishes it from code that is correct.

3 · Redis publishes to you as well

Redis pub/sub delivers a published message to every subscriber on the channel — including the process that published it. So the node that just wrote to its local sockets receives its own message back a millisecond later, and if the receive handler does what the receive handler does, it writes to them again and publishes again.

Two separate defects come out of the same missing check, and they fail at different speeds. Re-publishing is a loop, which is loud and will be found in minutes. Re-delivering is a duplicate, which is quiet, looks like a client bug, and is reported as "sometimes messages appear twice" three weeks later.

So the envelope carries the id of the node that first accepted it, and two rules fall out:

  • Something arriving from the bus is never published onward, whoever sent it.
  • Something arriving from the bus that this node published is dropped entirely — it was already delivered on the way out.

4 · A registry that lies about itself

Mobile clients reconnect constantly — a tunnel, a lift, a switch from wifi to 4G. The old socket's close event can arrive after the new socket has registered, and for a moment the registry holds two entries claiming to be the same client.

Two things are being fixed there and they are not the same kind of problem. Writing to a closed socket throws, so it is noisy and self-announcing. Writing to a duplicate succeeds, and the user sees the message twice.

Exactly-once keeps arriving in this course — the redemption transaction in b7/0001, the first ending winning in the calls table, one page per incident in c7/0004. It is the same shape every time: the second occurrence is not an error, which is precisely why nothing catches it.

5 · Two fields that both say who you are

A Token socket has a principal, and the shape depends on which side it is:

  • owner:<userId> — the person who issued the token, signed in with their phone.
  • holder:<conversationId> — whoever redeemed it. There is no account behind this one. The holder JWT is { conversationId, tokenId, holderName }, so the socket already knows its conversation before the first message.

Which means a holder socket carries its conversation twice: once in the registry entry and once inside the principal. Normally they agree. If they ever do not:

The temptation is to pick one and carry on, because one of them is presumably right. Do not. When two fields both answer the same question and disagree, you have no reason to prefer either, and the cheap options here are a message delivered into the wrong conversation — on a product whose entire promise is that the wrong person cannot reach you.

Deny-by-default is the house style and it applies here: drop the socket, record that you did, and let somebody find out why.

6 · The envelope carries no code

CLAUDE.md records this one as a swept defect rather than a theory: a8/0004 sent the token code over the WebSocket on every chat message, so it reached the socket log and the Redis pub/sub payload.

The reasoning is worth having exactly, because "do not put the code in the payload" sounds like a taste:

Re-sending an identifier the connection already carries is how a credential ends up somewhere nobody designed.

The socket is already authenticated and already scoped to a conversation. A code in the envelope answers a question that was settled at connect time, and answers it in a weaker way — and then it travels through Redis, which is a component nobody thinks of as a place where secrets are stored.

So the fan-out planner refuses an envelope carrying one, and refuses it before it looks at anything else. A refusal whose correctness depends on other checks having run first is a refusal you cannot reason about.

7 · Presence, and what absence is not

Presence in a stateless system is a Redis key with a TTL — online:u-1, set on connect, refreshed on a heartbeat, gone when it expires. Which makes the key's absence ambiguous in a way worth naming:

All three of those states are reported to a user interface as "offline", and that is fine — a grey dot is allowed to be approximate. What is not fine is letting the same fact reach a storage decision. Never skip persisting a message because the recipient looked offline. Presence is a hint about a socket; the message is a fact about a conversation, and the two have different lifetimes.
