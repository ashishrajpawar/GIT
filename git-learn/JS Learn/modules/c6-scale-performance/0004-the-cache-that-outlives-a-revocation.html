The Cache That Outlives a Revocation

C6 — Lesson 4 of 5  |  ~55 min

Why this matters for Token

Everything Token sells is one sentence: the user can revoke at any time. Not "can stop future tokens", not "can ask us to stop" — can end it, now, from their phone.

A cache is a promise that an answer stays true for a while. Put one on the path that decides whether a holder may contact somebody, and you have changed the product's central claim from revoke to revoke within sixty seconds — in a config value, with no discussion, and with nothing in the interface that says so.

1 · Caching is a statement about time

The reason to cache a token is obvious: code_hash lookups happen on every message and every call, and none of the fields change often. Textbook material.

That window is not a bug in the cache. It is the definition of a cache, applied to a fact whose entire value is that it changes instantly.

2 · Two reads that look identical and are not

Token asks about a token in two quite different situations, and almost every field is shared between them, which is exactly why they get written as one function.

The purpose of the read decides, not the shape of the data. This is the same move as c7/0002's expected errors are refused — two things that are structurally identical and are treated differently because of what they are for.

Note what the rule is not. It is not "cache the cheap fields and not the expensive ones", and it is not "cache everything except status". Both of those are decisions made per field, and a field-by-field rule is one somebody has to remember every time a column is added.

3 · The key is an id, and never a code

ADR-0007 says the token code is never stored in the clear. It is easy to read that as being about the tokens table, and the table is where it is enforced — code_hash and code_enc, no code column.

A cache key is storage too, and it is storage nobody lists as storage:

redis.set(`token:MERC-8GH2-KP4X`, JSON.stringify(row), "EX", 60);

That code is now in Redis, which has no encryption at rest by default, appears in MONITOR output, in SLOWLOG entries, in keyspace notifications, and in an rdb snapshot that gets backed up alongside everything else. CLAUDE.md already lists the four places a code must not go — a URL path, a log line, a list response, a socket payload. A cache key is the fifth, and it is the one nobody writes down because it does not feel like a place.

So the read plan refuses a code-shaped key outright, before it considers anything else — the same reasoning as c6/0002's envelope check. A refusal that only holds while the checks above it are right is not a refusal.

4 · The cache that answers faster when the code exists

Now the part that is specific to this product, and is a new instance of a rule the course has now applied at five layers.

ADR-0010: a dead code says the same thing however it died. Revoked, expired, exhausted, never-existed and account-deleted all produce one identical response, so that the redemption page cannot be used to find out which codes are real.

Put a cache in front of it, and the responses stay identical while the timings stop being:

The bodies are byte-identical and the defence is gone. An enumerator does not need to read the response; they need any measurable difference, and latency is a channel nobody diffs.

Both problems — the revocation window and the timing oracle — are removed by one rule rather than two mechanisms: the redemption path is an authorise read, and authorise reads do not touch the cache. Note that this is worth having as an argument even though the conclusion was already reached in section 2. A rule with two independent reasons survives somebody disagreeing with one of them.

5 · Invalidate on write; the TTL is the backstop

If display reads are cacheable, what stops the token list showing Active for a minute after a revoke?

Not the TTL. The TTL is what happens when the invalidation fails — a dropped Redis command, a crash between the database commit and the delete, a code path somebody added that updates the row and does not know the cache exists.

Two mechanisms, and they are not alternatives
  • Invalidation on write is the mechanism. Every path that changes a token bumps its version — revoke, pause, resume, edit label, add a rule.
  • The TTL is the bound on how wrong you can be when the mechanism did not run. Setting it to an hour because "we invalidate anyway" is trusting the thing you added the TTL because you could not trust.

The version is what makes a stale entry detectable as a fact rather than as an age. An entry written five seconds ago is not fresh if the row changed four seconds ago, and only a version comparison knows that.

6 · A cache holds objects your old code wrote

This is the part people meet in production rather than in a tutorial. A cache entry was serialised by the version of your code that was running when it was written — which, during a rolling deploy, is a version you are actively replacing.

c2/0003 made the same point about the database: both versions of the code run at once. A cache is the same hazard with none of the schema's protection, because Redis will happily hand you a shape from three releases ago and nothing declares what shape that was.

The version field covers this too, which is why it is a version of the entry and not only of the row.

7 · Clock skew, and which way the error goes

An entry can carry a storedAt in the future, for the reason the last lesson gave: replicas do not share a clock. The age then comes out negative, and a negative age is smaller than any TTL, so a naive freshness test declares it fresh — possibly for hours.

Ask the question from c6/0003: which way does the error grant access? Serving a stale entry is the permissive direction, so the conservative answer here is to refetch. In the limiter the same anomaly was kept, because there discarding it would have refunded a request. Same anomaly, opposite handling, one principle.

8 · Stale-while-revalidate, and why it is display-only

One more state worth having. Just past the TTL, an entry can be served and refreshed in the background, so a burst of traffic at expiry does not become a burst of database queries — a stampede where hundreds of requests all miss at the same instant and all go to Postgres, which lesson one told you is the limit that binds after descriptors.

It is a good idea and it is display-only, for a reason worth saying out loud rather than deriving each time: stale-while-revalidate is the deliberate choice to serve an answer you already believe is out of date. That is a fine trade for a badge and an unacceptable one for a decision about whether somebody may reach a person.

9 · Broken on purpose

An entry written by last week's code, read by this week's.

The crash is the friendly version. The unfriendly one is a shape that still reads — entry.rules exists, so a check written as if (entry.rules) passes, and a token is evaluated against a rules object the engine no longer understands. Which is the same defect b7/0002 shipped: an unknown rule type falling through to allowed.
