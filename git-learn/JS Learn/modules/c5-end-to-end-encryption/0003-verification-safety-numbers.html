Verification & Safety Numbers

C5 — Lesson 3 of 5 ~45 min
Why this matters for Token

0002 ended with a gap it could not close: the first time you fetch someone's key there is nothing to compare it against, so you pin what the server gives you and hope. Pinning makes a later substitution visible; it does nothing about a substitution that was there from the start.

This lesson closes it, and the mechanism is not cryptographic. Two people compare a number through a channel the server does not control — out loud, in person, on a QR code held up to a camera. That is the only information in the entire system that does not pass through infrastructure someone else runs.

What a safety number is

A short, human-comparable rendering of both public keys in a conversation:

Ravi                                   You

  38471  90233  17756  40182
  55019  73846  22910  68374
  11295  84061  39572  20648

Compare these numbers. If they match on both phones,
nobody is between you.

Sixty digits in groups of five. It is a hash, truncated and formatted for a human to read aloud in about twenty seconds. Nothing about it is secret — you can shout it across a room. Its only job is to be infeasible for an attacker to reproduce while being possible for two people to compare, and those two requirements pull in opposite directions, which is what makes the length a real decision rather than a detail.

The bug that makes verification impossible, and it is one line

Both devices must compute the identical number. The obvious implementation does not:

// On MY phone
hash(myKey + theirKey)

// On THEIR phone -- same function, same two keys
hash(myKey + theirKey)   // ...but "my" and "their" are swapped

Each side puts its own key first, so each side hashes a different string and sees a different number. The two people compare, find they do not match, and conclude they are being attacked.

What makes this worse than an ordinary bug is how it fails. It is not that verification stops working — it is that verification always reports an attack. Every user who tries it is told something is wrong. The feature that exists to build confidence spends its life destroying it, and the natural response from support is "ignore that screen, it's known to be buggy" — which is the worst possible outcome, because now nobody checks the one thing that would catch a real interception.

The fix is to put the two keys in a canonical order before hashing — sort them, so both sides feed the function the same bytes regardless of who is asking:

const [first, second] = [myKey, theirKey].sort();
const number = hash(first + second);

The general form is worth more than the fix: any value two parties must agree on cannot depend on which of them is computing it. Sorting is the usual way to make that true, and the test is a one-liner — f(a, b) === f(b, a).

Why it must contain both keys

A tempting simplification is to show a fingerprint of the other person's key alone. It is shorter and it seems to say the same thing. It does not:

  • It only verifies one direction. You confirm you hold Ravi's real key. Ravi learns nothing about whether he holds yours — so an attacker intercepting one side of the conversation survives the check.
  • It is the same for everyone. Ravi's fingerprint is Ravi's fingerprint, so it says nothing about this conversation. A number that binds the pair changes if either key changes, which is what makes it a statement about a channel rather than about a person.

How long is long enough

Truncation is not free. If the displayed number is short, an attacker can generate keypairs until one produces a matching number and then substitute that key — the comparison passes and the interception succeeds.

Digits shownWork to find a matchVerdict
8~108 — seconds on a laptopWorse than nothing
16~1016 — expensive but reachableNot enough
32~1032The floor
60~1060What Token shows

"Worse than nothing" is the important row. A short safety number does not merely fail to protect — it produces a green tick the user has been taught to rely on, for a channel that is compromised. A feature that gives false assurance is worse than the same feature absent, because the absent one does not stop the user being careful.

So safetyNumber below refuses to produce a number at all when asked for too few digits. It does not quietly return a short one. That is the same rule as everywhere else in this module: when you cannot do the secure thing, stop.

The QR path, which Token already has

Reading sixty digits aloud works and almost nobody does it. The practical form is a QR code on one screen, scanned by the other camera — and Token already owns both halves: a5/0001 generates QR codes for token sharing and the app already asks for camera permission for redemption scanning.

Scanning is stronger than reading, and only because of the channel

The digits and the QR encode the same value. Scanning is better for two reasons that have nothing to do with cryptography: people actually do it, and it removes the failure mode where someone compares the first group, sees a match, and stops.

What it does not change is the requirement that the two phones be in the same room. A QR code sent through a chat app is a QR code that passed through a server — which is the thing being verified. If the channel can be tampered with, so can the code on it, and the check proves nothing.

This is the same rule as Token's own sharing policy in CLAUDE.md: a token must never travel over a channel that already identifies the user. Here the parallel is sharper — a verification must never travel over the channel it is verifying.

What "verified" means, and what it does not

// The pin record from 0002, now with the verification recorded.
{
  publicKey: 'Kx1...',
  keyVersion: 3,
  verifiedAt: 1699000000,   // set only by a successful comparison
}
  • It means: the key I hold for this person is the key their device holds. That is all, and it is enough — it is exactly the claim a substituting server needs to be false.
  • It does not mean the person is who they say they are. Verification confirms a key matches a device. Whether the human holding that device is really Ravi is a question about the world, and comparing numbers in person answers it only because you can see him.
  • It expires when the key changes, which 0002's verificationLost already reports. A fingerprint checked last year says nothing about a key that appeared this morning.

Note the storage: verifiedAt lives in the client's pin store and is never sent to the server. It is a statement about whether you trust the server's answer — telling the server would be both useless and slightly absurd.
