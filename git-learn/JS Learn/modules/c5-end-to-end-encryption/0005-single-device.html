Single-Device, and What a Second Would Cost

C5 — Lesson 5 of 5 ~45 min
Why this matters for Token

Token v1 is one phone per account (decided 2026-08-23). This lesson was planned as how to build multi-device and is instead about why it is not being built — which is more useful, because the reasoning decides things you are about to build anyway.

The short version: under ADR-0002 the server holds no key, so a second device is not a setting. It is a key distribution problem, and it reaches the message schema, the send path, the sync path and the recovery flow. Not yet is a legitimate answer; we'll add it later without knowing the price is not.

Why it is not a setting

Everything else in Token comes back from a phone number, because it is server-side and unencrypted — 0004 made that case in detail. The private key is the exception, and 0001 put it in the Keychain with WHEN_UNLOCKED_THIS_DEVICE_ONLY, which deliberately excludes it from iCloud, from Google backup, and from every other mechanism that would carry it to a second device on its own.

That was the right call and it is exactly what makes this hard. There is nothing to sync from. A second device has to obtain a key some other way, and there are only two ways.

A — share one identityB — a key per device
How Device 1 transfers its private key to device 2 over a channel the server cannot read — a QR code scanned in person Device 2 generates its own keypair and publishes it to the directory from 0002, as another row for the same user
The directory Unchanged. One public key per user Many keys per user, each with its own version and retired_at
Sending a message Unchanged. Encrypt once Encrypt once per device, on both sides — see below
Losing device 2 Rotate the shared identity, on every device you still have Retire that one key. The others are untouched
The real cost The private key now exists in two places, and a compromise of either is a compromise of the identity. There is no way to say that device is no longer trusted Message fan-out, a schema change, and a sync path — all described below

A is cheap and wrong. It looks attractive because nothing downstream changes, and it gives up the one property that makes per-device keys worth having: the ability to revoke a device rather than an identity. A stolen tablet you cannot individually untrust is a stolen identity. B is what Signal does, and B is what the rest of this lesson costs out.

The cost is fan-out, and it lands on the message table

b2/0002 stores one row per message: ciphertext, nonce, key_version. That shape assumes one recipient key.

Under per-device keys there is no single ciphertext. A message to someone with three devices is three ciphertexts, sealed to three different public keys, and the server — which cannot read any of them — must store and route all three. So the row becomes a row per envelope:

-- What multi-device would require. NOT the v1 schema.
CREATE TABLE message_envelopes (
  message_id  INTEGER NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
  device_id   INTEGER NOT NULL REFERENCES device_keys(id),
  ciphertext  BYTEA   NOT NULL,
  nonce       BYTEA   NOT NULL,
  PRIMARY KEY (message_id, device_id)
);

Read that against b2/0002's partitioning and the cost is not the table, it is the multiplier: message volume is now messages × devices, on a table already partitioned by time because it was expected to be the largest one in the system.

And the fan-out is on both sides. Your own other devices need a copy of what you sent, or your sent messages are missing from the conversation everywhere except the phone you typed them on. That is the part everyone forgets, and it is the exercise below.

Three more things that stop being simple

  • A new device starts empty. It cannot decrypt anything sent before its key existed, because those envelopes were sealed to keys it does not have. So "add a device" needs a history transfer from an existing device — a second protocol, over a channel the server cannot read, for a mailbox that may be years long.
  • The device list is a race. You fetch someone's devices, compose a message, and send. If they added a device in between, that device gets no envelope and silently never sees the message. There is no error — you sent successfully to the devices you knew about. planEnvelopes below refuses a list that is too old rather than pretending a stale answer is a current one.
  • Every trust decision multiplies. 0003's safety number binds two keys. With three devices each side that is nine pairs, and the number changes whenever anyone adds a device. Signal solves this with a per-identity key that signs per-device keys; that is a third layer this course has not built.
The redemption page is not a second device

The obvious objection: a8 has holders talking to Token through a browser, so multi-device clearly already works.

It does not, and the distinction matters. The browser is the other party to a conversation, not another device of your account. It holds the holder's key for that one conversation, and b2/0002 is explicit that a holder is not a user at all — conversations identifies them by holder_session_id, and there is no user_id anywhere on that side.

Two parties to a conversation is not the same shape as two devices for one party. The first is what Token is; the second is what this lesson is declining to build.

So participants is deleted, not designed

A participants table — (user_id, conversation_id), the classic many-to-many junction — has been queried by one lesson and created by none since the schema was first written. It has been blocked on this module for weeks. **It is now resolved by deletion**, and the argument is worth following because it generalises.

A junction table exists to record a membership that can vary. In Token, nothing varies:

  • A conversation has exactly two parties, and conversations.token_id already determines both — the token's owner on one side, the holder of that conversation on the other.
  • There are no group conversations, so a party set never grows.
  • The holder is not a user and has no user_id, so half of every row in that table could never have been filled in. The junction shape assumed both parties were users, and in Token only one of them ever is.
  • Per-device fan-out was the last thing that might have needed a membership set, and this lesson is why it is not being built.

The correct ownership query walks the relationship that actually exists — message, to conversation, to token, to owner:

-- Read messages in a conversation this user owns the token for.
SELECT m.*
  FROM messages m
  JOIN conversations c ON c.id = m.conversation_id
  JOIN tokens t        ON t.id = c.token_id
 WHERE m.conversation_id = $1
   AND t.user_id = $2;

The general form: an orphan table is sometimes a feature that was never decided, not a schema that was never written. Three tables were parked as "queried but never created" and the three ended differently — deletion_queue was defined once a policy existed (b10/0002), calls is still waiting on B6, and this one turned out to describe a product Token is not building. Writing it anyway would have produced a table that is always exactly two rows, one of which cannot be filled in.
