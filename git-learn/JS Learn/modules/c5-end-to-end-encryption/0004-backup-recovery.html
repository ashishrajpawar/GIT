Backup & Recovery

C5 — Lesson 4 of 5 ~50 min
Why this matters for Token

0001 put the private key in the Keychain with THIS_DEVICE_ONLY, which deliberately excludes it from every backup Apple and Google offer. So the phone going in the river is not a hypothetical — it is a state the design guarantees will be unrecoverable unless this lesson exists.

ADR-0002 calls it key loss is data loss and requires the answer at launch rather than later, for a reason that is easy to miss: a backup mechanism added in v1.4 cannot protect the keys of anyone who signed up in v1.0. Their keys were generated before there was anywhere to put a copy.

The shape of the answer was decided on 2026-08-23, and it is a split

Not "everything comes back" and not "write these words down or lose your account". Almost everything comes back from the phone number alone; the words are needed for one thing.

Restores from an OTP aloneNeeds the recovery phrase
Token list, labels, access rules, expiry, max uses, status Message bodies. That is the whole list.
Redemption history, conversation list, timestamps
Display name, avatar

A user who skips the phrase loses old message text on a new device and nothing else. They get their entire working product back with nothing to write down — and that is not a compromise someone invented to end an argument. Read on: it is what the schema already was.

The split is a fact about the schema, not a policy

Go back to what B2 actually stores and ask one question of every column: can the server read this?

TableServer can readServer cannot read
tokens label, status, expires_at, max_uses, paused_at, revoked_at code_hash is one-way and code_enc is encrypted with a key the API holds — so for this purpose the API can read it
conversations All of it — token_id, created_at, closed_reason —
redemption_events All of it —
users display_name, avatar_url —
messages conversation_id, sender_type, created_at, receipts, key_version ciphertext and nonce

One cell in that table is encrypted to a user key, and it is the last one. Everything else is ordinary rows the server serves to an authenticated client every day. So "what needs the phrase" was never a product decision — it was settled in b2/0002, the morning someone decided which columns stay outside the ciphertext, and nobody had gone back and read it.

This is worth doing before designing any recovery flow

The instinct is to design backup as a feature and then work out what it has to carry. The cheaper order is the reverse: list what is encrypted, and the backup requirement is whatever is left. Do it the other way round and you end up designing a recovery phrase that protects a token list the server would hand over anyway — all of the user-facing cost, none of the security.

Why the phone number cannot bring the messages back, stated exactly

The first answer to this question was "once logged in with the same number, data is auto restored". It is the right instinct and it cannot be built. The argument is two sentences:

For message bodies to return from a phone number alone, the server must be able to release the key to whoever proves the number. A server that can release the key can release it to itself.

That is not weakened end-to-end encryption. It is its absence — the guarantee in ADR-0002 is precisely the server holds no key it can use, and there is no version of "auto-restore from an OTP" that leaves that sentence true. It is also not a private matter any more: b10/0002 and a11/0005 both declare end-to-end encryption to Google Play and the App Store, and both stores re-check declarations against the binary.

The second reason is the one that decides it even for someone relaxed about the first. Sign-in is OTP-only, so whoever controls the SIM controls the account. That is an accepted cost for the account itself — a SIM-swapper gets a token list, and every token in it is revocable. It is not an acceptable cost for the message history, which is not revocable, not replaceable, and is the thing users would actually mind. So:

The key backup must never be recoverable by SMS alone. Anything that lets a fresh SIM-swapped device decrypt old messages hands the whole guarantee to whoever ports the number.

Two designs, and why only one of them is skippable

There are two honest ways to survive a lost phone without the server holding a usable key.

A — the phrase is the keyB — the phrase wraps the key
How 12 words → seed → identity keypair, derived deterministically. Nothing is uploaded at all The key is generated on-device as in 0001. The phrase derives a wrapping key, which encrypts the private key; the ciphertext is uploaded
Server stores Nothing A blob it cannot open
Can it be offered later? No. The phrase must exist before the key does Yes — at sign-up, from settings, or after a nudge six months in
Can it be skipped? No. There is no key until the user has accepted one Yes. The key already works; backup is an extra
Rotation (0002) A new key means a new phrase, so every rotation is a user-facing event Re-wrap and re-upload. The user never sees it

Token uses B, and the two "no" cells are why. The decision was that the phrase is offered at sign-up and skippable, and design A cannot be skipped — under A, the twelve words are a wall in front of the first screen of the app, for a product whose entire pitch is that you can start using it immediately.

Design A is not a bad design; it is what cryptocurrency wallets use, and there the trade is right because there is nothing to do with the app until you have a key you can restore. Token is the other case: there is a great deal to do, and most of it does not need the phrase at all.

The phrase is generated by the app, never chosen by the user

This looks like a usability preference and it is a security requirement, because of where the blob lives. The wrapped key sits on the server. Anyone who signs in with the SIM can download it. From that moment the attack is offline — no rate limit, no lockout, no "too many attempts", just a file and as much hardware as they care to rent.

What protects the blobEntropyVerdict
A passphrase a person invented Typically under 40 bits, and often far less Falls to an offline attack. Days on rented hardware, even with a slow KDF
12 words from a 2048-word list 132 bits (128 of entropy plus a 4-bit checksum) Not reachable at any speed, by anyone

The gap is not a factor of ten. It is roughly ninety bits, which is why no amount of KDF tuning rescues the first row — a slow hash multiplies the attacker's cost by a constant, and a constant does not close a gap of 290. The only lever that works is the entropy of the secret itself, and the only reliable way to get it is to stop asking humans for it.

Then why bother with Argon2id, if 128 bits is already unbreakable?

Two reasons, and neither is the usual one.

  • Phrases leak partially. A photo of a page with three words obscured, a phrase read aloud in a room, a note where the last line is smudged. A memory-hard KDF is what makes the remaining space expensive rather than instant.
  • The parameters must travel with the blob. A blob wrapped in 2026 has to open in 2034, when the defaults have moved on twice. So kdf, kdf_salt and kdf_params are columns, not constants in the client. A constant in the client is a value you can never change without orphaning every backup made before the change.

The one to avoid is a plain SHA-256 of the phrase. It is fast by design, which is the property you want everywhere except here.

What the server stores

-- Migration: 011_key_backups.sql
CREATE TABLE key_backups (
  user_id      INTEGER     PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,

  -- EVERY identity key this user has ever held, sealed as one blob.
  -- Not just the current one -- see the callout below.
  wrapped      BYTEA       NOT NULL,

  -- The KDF parameters travel WITH the blob. They are not secret, and a
  -- backup made today must still open when the defaults have moved on.
  kdf          TEXT        NOT NULL,          -- 'argon2id'
  kdf_salt     BYTEA       NOT NULL,
  kdf_params   JSONB       NOT NULL,          -- { m, t, p }

  -- Which key versions are inside, so a restore can tell whether it has
  -- what it needs for the messages it is about to try to read.
  key_versions INTEGER[]   NOT NULL,

  created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

One row per user, so re-wrapping is an UPDATE and turning backup off is a DELETE. That DELETE is irreversible in the strongest sense in this course — worse than a revoked token, which at least only destroys a capability — so it belongs behind the same kind of explicit confirmation a11/0001 argued for, and for the same reason: there is no undo to fall back on.

Two rules the API inherits from elsewhere and must not relax here:

  • wrapped never goes in a log. Same rule as the token code in ADR-0007, and the error tracker attaches request bodies by default — so the scrubbing config is part of shipping this endpoint, not a follow-up.
  • Serving the blob requires a verified session, even though the phrase is what actually protects it. Handing ciphertext to unauthenticated callers converts "you must swap the SIM first" into "you must guess a user id", and defence in depth is exactly the kind of thing that gets dropped because the layer underneath it is strong.
A backup of the current key is not a backup

0002 made the key directory append-only because old messages were sealed to old keys, and b2/0002 put key_version on the messages table for exactly that. Now read that against a backup blob containing one key.

A user rotates on Tuesday — new phone, reinstall, whatever 0002's "different key, higher version" row describes. The client re-wraps and uploads. The blob now holds v4. In March they lose the phone, restore, type the phrase correctly, and get back every message sent since Tuesday and none of the two years before it.

Nothing errors. The restore reports success, because it did succeed — it recovered the key it was given. The failure is silent, it is discovered weeks later, and by then the bytes that would have fixed it are gone from a phone in a river.

So the blob is a set, and re-wrapping is additive. A rotation adds v4 to the blob; it never replaces v3. key_versions exists so a restore can say "this backup covers versions 1–3, and you have messages at version 4" — which is a sentence worth being able to say, and impossible without the column.

The general shape has appeared before in this course and will again: a backup that keeps only the current state is a backup of the present, and the thing you lost is the past. Same family as UPDATE public_key in 0002 and revoked_at in b2/0001 — a history recorded, never expressed by absence.

Showing the words is not backing them up

The screen displays twelve words. The user taps Done. What just happened?

Almost certainly nothing. They glanced at it, they meant to come back to it, and the app has now recorded a successful backup. Six months later the phone is gone and the phrase was never written anywhere — and worse than the loss itself, the app told them they were protected, so they were less careful than they would have been with no backup feature at all.

That is the same argument as the eight-digit safety number in 0003: a feature that gives false assurance is worse than the same feature absent, because the absent one does not stop the user being careful. Third lesson in this module to arrive at it.

  • Confirm before recording. Ask for three of the twelve back, at positions the app picks. Only then write created_at and only then show the backed-up state.
  • Do not accept a screenshot as the answer. A screenshot lands in Google Photos or iCloud Photos, which is a server-held copy of the thing protecting the key — the exact outcome the design exists to avoid, arriving through the camera roll. Set FLAG_SECURE on Android and mark the screen non-capturing on iOS, and say write it on paper in words.
  • Never send the phrase or the wrapping key anywhere, including to your own analytics, including in a crash report. This is the one screen where an ordinary breadcrumb is a catastrophe.

Try it yourself — this one is broken on purpose

The restore planner as it is usually first written, run against four real states a returning user can be in. Three of the four tell someone their history is destroyed when it is not, and the fourth shows an empty app to a user whose entire token list is sitting on the server waiting to be drawn.

Now build it yourself

Argon2id, the wrapping and the two screens all need a device. What does not is the decision they hang off: given what came back from the server and whether the user has supplied a phrase, what is readable, what is waiting, and what is actually gone.
