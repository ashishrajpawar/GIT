End-to-End Encryption

5 lessons Phase 3 — after B4
Module goal

ADR-0002 says the server stores ciphertext and holds no key. Every schema decision in B2 was made to honour that, and every lesson touching messages has had to respect it. This is the module where it stops being a constraint and becomes code. Keys get generated on the device, published, fetched, verified, backed up and moved to a second device — and each of those is a place the guarantee can be quietly broken by a server that decides to lie.

Where this sits, and why the plan said otherwise

TOKEN-TRACK.md says C5 must precede B2, because the schema stores ciphertext. B2 was written first anyway — and the dependency was still met, because b2/0002 did the E2EE schema rewrite up front: ciphertext, nonce, key_version, and no content column. The prerequisite was satisfied by anticipation rather than by ordering.

What was genuinely missing is everything about the keys themselves, which is what these five lessons are.

Lessons

  1. Keys on the Device — X25519 identity keys, why expo-secure-store and never AsyncStorage, and why a key that will not load must be refused rather than regenerated
  2. Publishing & Fetching Public Keys — the directory, and what a malicious server can do with one (not written yet)
  3. Verification — safety numbers, and why both devices must derive the identical one (not written yet)
  4. Backup & Recovery — a v1 feature, and it must not be a server-held copy (not written yet)
  5. Multi-device — explicit key sharing, because there is nothing on the server to sync from (not written yet)
Two constraints this module inherits and cannot relax
  • Key loss is data loss (ADR-0002). Backup must exist at launch and must not be a server-held copy of the key, or the guarantee is theatre. That is lesson 4, and it is a product surface rather than a nicety.
  • Whoever controls the SIM controls the account (decided 2026-08-22, when sign-in became OTP-only). That is tolerable for the account — an attacker gets a token list, which is revocable — and it is not tolerable for message history. So the key backup must never be recoverable by SMS alone. Lesson 4 has to answer this; it is the first question it faces.

After this module

You'll have:

  • An identity keypair generated on-device, with the private half in the Keychain / Keystore and never anywhere else
  • A public-key directory in the API, and a client that treats it as untrusted
  • A verification screen users can actually use
  • A backup path that survives losing the phone without handing the server a key
  • The participants table, which has been blocked on this module since it was first written
