Publishing & Fetching Public Keys

C5 — Lesson 2 of 5 ~45 min
Why this matters for Token

0001 made a key the server has never seen. Now the app has to find out which key to encrypt to when the user opens a conversation — and the only thing that knows is the server.

That is the whole attack surface of an end-to-end encrypted system. The server cannot read your messages, and it does not need to: it can hand your client a key it controls, and your client will encrypt to it, correctly, with no error anywhere. Everything in this lesson exists because the directory has to be treated as an untrusted input.

The table, and why it is append-only

-- Migration: 010_device_keys.sql
CREATE TABLE device_keys (
  id           SERIAL      PRIMARY KEY,
  user_id      INTEGER     NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  public_key   TEXT        NOT NULL,
  key_version  INTEGER     NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  -- Set when a newer key supersedes this one. The row NEVER goes away.
  retired_at   TIMESTAMPTZ,

  -- One key per version per user. This is what stops a rotation racing
  -- itself and producing two "version 3" keys.
  UNIQUE (user_id, key_version)
);

CREATE INDEX idx_device_keys_user ON device_keys (user_id, key_version DESC);
Never UPDATE public_key, never DELETE

The obvious design is one row per user with the current key in it, updated on rotation. It is smaller and it destroys information you cannot recreate.

  • Old messages were sealed to old keys. b2/0002 put key_version on the messages table for exactly this, and it only means something while the key it names still has a row.
  • A key change is a security event and needs a history. "This user's key changed three times last Tuesday" is a sentence you can only say if the rows are still there.
  • Retiring is not deleting. A retired key must not be offered to peers, and it must still be identifiable — which is a retired_at timestamp, not a missing row.

Same shape as revoked_at in b2/0001 and superseded_at in b4/0002: a state change is recorded, never expressed by absence. A deleted row and a row that never existed are indistinguishable, and the difference is often the thing you most need to know.

Publishing

// api/src/routes/keys.ts
router.post('/keys', requireAuth, async (req, res, next) => {
  try {
    const { publicKey } = publishSchema.parse(req.body);

    const client = await pool.connect();
    try {
      await client.query('BEGIN');

      // Lock the user's key history so two devices publishing at once
      // cannot both compute the same next version.
      const { rows } = await client.query(
        `SELECT COALESCE(MAX(key_version), 0) AS current
           FROM device_keys WHERE user_id = $1 FOR UPDATE`,
        [req.user.id]
      );

      const nextVersion = rows[0].current + 1;

      // Retire whatever was current. The rows stay.
      await client.query(
        `UPDATE device_keys SET retired_at = NOW()
          WHERE user_id = $1 AND retired_at IS NULL`,
        [req.user.id]
      );

      await client.query(
        `INSERT INTO device_keys (user_id, public_key, key_version)
         VALUES ($1, $2, $3)`,
        [req.user.id, publicKey, nextVersion]
      );

      await client.query('COMMIT');
      res.status(201).json({ data: { keyVersion: nextVersion }, success: true });
    } catch (err) {
      await client.query('ROLLBACK');
      throw err;
    } finally {
      client.release();
    }
  } catch (err) { next(err); }
});

The version is assigned by the server, not sent by the client. A client-supplied version is a client-supplied claim, and the next lesson's rollback check depends on the number only ever going up. Letting a caller pick it hands them the ability to publish "version 1" forever.

Fetching

router.get('/keys/:userId', requireAuth, async (req, res, next) => {
  try {
    const { rows } = await pool.query(
      `SELECT public_key, key_version
         FROM device_keys
        WHERE user_id = $1 AND retired_at IS NULL
        ORDER BY key_version DESC
        LIMIT 1`,
      [req.params.userId]
    );

    // No key published yet. Say so plainly -- and see the callout: what
    // the CLIENT does with this answer is the dangerous part.
    if (!rows[0]) {
      return res.json({ data: { publicKey: null, keyVersion: null }, success: true });
    }

    res.json({
      data: { publicKey: rows[0].public_key, keyVersion: rows[0].key_version },
      success: true,
    });
  } catch (err) { next(err); }
});

What a dishonest server can do, stated plainly

It can hand you its own key, and nothing will break

The server generates a keypair, returns its public half when your client asks for someone else's, and reads everything you send. Your client encrypts correctly. The recipient — who gets a re-encrypted copy — reads it normally. There is no error, no warning, and no cryptographic failure anywhere, because nothing has failed: you encrypted to exactly the key you were given.

This is not a flaw in this design. It is the unavoidable shape of every system where a directory tells you who someone is — Signal, WhatsApp and iMessage all have it, and all answer it the same way. There is no protocol fix, because the problem is not in the protocol: it is that "which key belongs to Ravi" is a fact about the world, and a server is a poor witness to facts about the world.

So there are exactly two defences, and this lesson is the first:

  1. Pin the key you first saw and notice when it changes. A server that substitutes a key for an existing conversation has to change it, and a change is visible. That is classifyPeerKey below.
  2. Let two humans compare fingerprints out of band. That is lesson 3, and it is the only thing that closes the first contact.
Token uses the first defence and does not surface it — a deliberate product decision

Decided 2026-08-23. A key change is accepted silently: no warning, no banner, no fingerprint prompt. The reasoning is specific to this product rather than general. Most Token conversations are with a delivery driver or a shop who redeemed a token. You will never compare a safety number with them, so the warning would be dismissed every time — and a warning users are trained to dismiss is worse than none, because it is the same tap as the one that matters.

The honest consequence, and it belongs in the same paragraph as the decision:

Token is end-to-end encrypted against a server that stores and does not attack. The server holds ciphertext and no key, so it cannot read messages. It is not protected against a server that actively substitutes a key, because nothing tells the user that happened.

That is a real posture, not a euphemism — iMessage was exactly this until Contact Key Verification shipped in 2023. It is also not a false store declaration: the data genuinely is end-to-end encrypted, which is what Google's Data Safety form asks. What you must not write is "nobody can intercept your messages". What you can write is "we store only ciphertext and hold no key".

Two things survive the decision, and removing them would turn it from a trade into a hole:

  • The rollback block stays. A different key at the same or a lower version is still refused outright. That is a refusal, not a notification — the user sees a send that did not go through, never a dialog about keys — and no honest path produces it.
  • The classification stays; only the policy moved. classifyPeerKey still returns warn, because a key change is a key change. The send path pins and logs rather than prompting. That the product decision was a four-line edit to the caller, and no edit at all to the function, is the argument for having separated them.

Lesson 3's verification screen still exists and is reachable from settings. It is never prompted.

Trust on first use, and its honest weakness

The first time you fetch someone's key there is nothing to compare it against. You pin what you are given and hope. That is a real weakness and it should be named rather than glossed: a server that wants to intercept a conversation is best off doing it before the two people have ever talked, because after that any substitution shows up as a change.

What TOFU buys is that the attack has to be sustained and early. A server that behaves honestly and later turns malicious cannot quietly start reading — it has to push a key change, which is exactly the event the client is watching for.

Rotation increments; substitution does not

This is the part that turns a vague "warn on change" into something with a rule in it. A genuine rotation goes through POST /keys, which assigns MAX(key_version) + 1. So:

FetchedMeansClient does
Same key bytes Nothing changed Proceed. Versions are metadata; the bytes are the identity
Different key, higher version A rotation — new device, reinstall, or a real key change Warn. Legitimate and indistinguishable from an attack, so the human decides
Different key, same or lower version Not a rotation. The server is substituting or replaying Block. No honest path produces this

The third row is worth dwelling on. A rollback is how a server reuses a key you have already retired — and you may have retired it because it was compromised. Accepting an old key at an old version is accepting the one key most likely to be in someone else's hands.

The downgrade: "no key published" must never mean "send it in the clear"

GET /keys/:userId can legitimately return publicKey: null — the peer has not finished setting up. There is exactly one correct response, and it is to refuse to send.

The tempting alternative writes itself: "we cannot encrypt, so send it unencrypted and mark it somehow." That converts a server which cannot read your messages into a server that reads any message it wants, by returning null. The strongest cryptography in the world sits behind an if statement that the attacker controls the input to.

The general rule, and it is the same one 0001 reached from the other direction: when the secure path is unavailable, stop — do not fall back to the insecure one. A feature that degrades gracefully under attack is a feature that can be attacked into degrading.
