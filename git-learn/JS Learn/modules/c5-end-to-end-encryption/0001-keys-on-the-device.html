Keys on the Device

C5 — Lesson 1 of 5 ~45 min
Why this matters for Token

Every lesson touching messages has said the server cannot read them. b2/0002 built a schema with no content column to prove it meant that. None of it is true until a key exists that the server has never seen — and that key is made here, on the phone, in the first seconds after sign-in.

It is also the one piece of Token that cannot be fixed later. A password can be reset and a token can be revoked; a private key that leaks was never private, and a private key that is lost takes every message with it.

What gets generated, and when

One long-term identity keypair per device, made the first time the app runs after a successful sign-in. X25519, per ADR-0002:

// app/src/crypto/identity.ts
import sodium from 'react-native-libsodium';

export async function generateIdentity() {
  await sodium.ready;

  // X25519. The private half must never leave this function's caller,
  // and never leaves the device at all.
  const pair = sodium.crypto_box_keypair();

  return {
    publicKey: sodium.to_base64(pair.publicKey),
    privateKey: sodium.to_base64(pair.privateKey),
  };
}
Why a library, and why this one

Nothing here is hand-rolled and nothing should be. libsodium is the standard answer: it exposes a small number of correct operations and does not offer you the ones that are easy to misuse. The whole skill in applied cryptography is choosing the right pre-built thing and then not being clever with it.

Note the shape of the API — crypto_box_keypair, not "pick a curve, pick a mode, pick a padding". Every one of those choices is a place to be wrong, so a good library removes them.

import * as SecureStore from 'expo-secure-store';

const IDENTITY_KEY = 'token.identity.v1';

export async function storeIdentity(privateKey: string) {
  await SecureStore.setItemAsync(IDENTITY_KEY, privateKey, {
    keychainAccessible: SecureStore.WHEN_UNLOCKED_THIS_DEVICE_ONLY,
  });
}

WHEN_UNLOCKED_THIS_DEVICE_ONLY is doing two jobs, and both are deliberate:

  • WHEN_UNLOCKED — the key is unreadable while the phone is locked. A background push arriving at 3am cannot decrypt anything, which is a real constraint on how notifications are designed. b8/0001 already sends the label rather than the content, so this costs nothing here — but it would have, if that lesson had gone the other way.
  • THIS_DEVICE_ONLY — the key is excluded from iCloud Keychain and device backups. It cannot be restored onto a new phone, by design: a key that syncs to Apple's servers is a key Apple has, and the whole claim is that nobody else has it.
This is why lesson 4 exists, and it is not optional

Read those two together and the consequence is unavoidable: losing the phone loses every message on it. Not "until you restore a backup" — there is no backup, because we just excluded the key from all of them on purpose.

ADR-0002 states this as "key loss is data loss" and requires a backup mechanism at launch, not later. That mechanism is lesson 4, and it has one hard constraint from the auth decisions: since sign-in is OTP-only, whoever controls the SIM controls the account — so the key backup must not be recoverable by SMS alone, or a SIM-swap hands over the message history as well as the account.

Do not build the app expecting to add this afterwards. A backup designed after launch cannot protect the keys of users who signed up before it.

Startup: the decision that looks trivial

Every launch, the app asks the same question: do I already have an identity? There are only four answers, and one of them is a trap.

// app/src/crypto/init.ts
export async function initIdentity() {
  const stored = await SecureStore.getItemAsync(IDENTITY_KEY);
  const plan = planKeyInit(stored, { expectedBytes: 32 });

  switch (plan.action) {
    case 'reuse':
      return plan;

    case 'generate': {
      const pair = await generateIdentity();
      await storeIdentity(pair.privateKey);
      await publishPublicKey(pair.publicKey);   // lesson 2
      return plan;
    }

    case 'refuse':
      // NOT 'generate'. See the callout.
      throw new IdentityUnreadableError(plan.reason);
  }
}
A key that will not load must be refused, never regenerated

The tempting version is three lines shorter and reads as robust:

const stored = await SecureStore.getItemAsync(IDENTITY_KEY);
if (!isValid(stored)) {
  // "Something's wrong with the stored key - make a fresh one."
  return generateAndStore();
}

It recovers from a corrupt key without troubling the user, and it silently destroys every conversation they have ever had. A new identity key cannot decrypt anything sealed to the old one. The messages are still on the device, still in the SQLite cache, and permanently unreadable — and the app looks like it is working, because a new key is a perfectly good key for messages that have not been sent yet.

Worse, it is unrecoverable in a way the corrupt key was not. A key that fails to parse might be a truncated read, a Keychain access error, a migration bug, or a device that was locked at the moment of the call. Every one of those is potentially fixable while the bytes still exist. Overwriting them removes the option.

So the rule this lesson exists for, and it is the fifth lesson to reach it from a different direction: when a value cannot be understood, refuse it — do not substitute a default. Refusing shows the user an error and keeps their data. Regenerating shows them nothing and destroys it.

Try it yourself — this one is broken on purpose

The startup check as it is usually first written, run against six real states a device can be in. Three of them destroy the user's history.

What the public key is for

The private half never moves. The public half is uploaded, and this is the seam where a server could attack the whole scheme:

// Lesson 2 builds this properly. The shape, for now:
POST /api/keys
{ "publicKey": "Vc3n...", "deviceId": 4 }

// And to talk to someone:
GET /api/keys/:userId  ->  { "publicKey": "Xk91...", "keyVersion": 1 }

The server hands you the key you will encrypt to. If it hands you its own key instead, it reads everything, and nothing in the code above would notice. That is not a flaw in this design — it is the unavoidable shape of any system where a directory tells you who someone is, and it is why lessons 2 and 3 exist. The answer is not to trust the directory less; it is to let users compare fingerprints out of band.

Note what this means for key_version, which b2/0002 put on the messages table and which has looked like over-engineering ever since: it is what lets a message record which key sealed it, so a key change is survivable rather than a cliff. Without it, rotating a key makes every past message undecryptable even when you still hold the old key.

Now build it yourself

The generation and the Keychain both need a device. The decision the app makes at startup is a pure function, and it is the one that can silently destroy a user's history.
