Build & Publish to Android

EAS Build · Signing key · Google Play Console · Store listing · Release ~60 min Step-by-step
Why this matters for your WhatsApp clone

This is it — you're putting your app on the Google Play Store where anyone with an Android phone can download it. The process takes your Expo project, builds a signed production binary (.aab file) in the cloud, and uploads it to Google Play. No Android Studio needed, no Mac needed, no manual signing headaches. One command builds it, one command submits it. By the end of this lesson, your WhatsApp clone will be live on the Play Store.

2. Setting up your Google Play Console

  1. Go to play.google.com/console and sign in with your Google account
  2. Pay the $25 one-time registration fee
  3. Complete identity verification (takes 1–3 days for new accounts)
  4. Click "Create app"
  5. Enter your app details:
    • App name: WhatsApp Clone (or your chosen name)
    • Default language: English
    • App type: Application
    • Free or paid: Free
  6. Accept the declarations and click Create app
App name considerations

Don't literally call it "WhatsApp Clone" on the store — Meta/WhatsApp will issue a takedown. Use your own name: "ChatApp", "Messenger Pro", or whatever you choose. For learning purposes the internal name doesn't matter, but the store listing name must be original.

3. Configuring eas.json for production builds

Your project needs an eas.json file that tells EAS Build how to build for different environments:

{
  "cli": {
    "version": ">= 7.0.0"
  },
  "build": {
    "development": {
      "developmentClient": true,
      "distribution": "internal"
    },
    "preview": {
      "distribution": "internal",
      "android": {
        "buildType": "apk"
      }
    },
    "production": {
      "android": {
        "buildType": "app-bundle"
      }
    }
  },
  "submit": {
    "production": {
      "android": {
        "serviceAccountKeyPath": "./google-service-account.json",
        "track": "internal"
      }
    }
  }
}

Three build profiles:

  • development — for testing on your device (dev client, hot reload)
  • preview — APK file you can install directly for testing (no store)
  • production — AAB file for the Play Store (signed, optimised)

4. App signing — how it works with EAS

Every Android app must be signed with a cryptographic key before it can be installed. This proves the app comes from you and hasn't been tampered with.

With EAS Build, signing is automatic:

# First time you build for production, EAS asks:
# "Would you like to generate a new Android Keystore?"
# Answer: Yes

eas build --platform android --profile production

# EAS generates a keystore, stores it securely on Expo's servers,
# and signs your app automatically. You never touch the keystore file.

Google Play App Signing: Google also manages a signing key on their side. When you first upload to Play Console, you'll opt into "Play App Signing" — Google re-signs your app with their key for distribution. This means even if your upload key is compromised, Google can issue a new one without affecting your users.

Never lose your upload key

EAS stores your keystore securely, but if you ever need it (switching build services, etc.), you can download it with eas credentials. Keep a backup in a safe place. If you lose it and leave EAS, you cannot update your app on the Play Store.

5. Building the production AAB

The production build creates an .aab (Android App Bundle) — Google's required format for Play Store submissions:

# Log in to your Expo account
eas login

# Build the production AAB
eas build --platform android --profile production

This takes 10–20 minutes. EAS builds your app in the cloud — you don't need any Android SDK or Java installed locally. When done, you get a URL to download the .aab file.

What happens during the build:

  1. Expo uploads your JavaScript bundle and assets
  2. EAS installs all native dependencies (react-native-webrtc, etc.)
  3. Gradle compiles the Android native code
  4. Hermes compiles your JS to bytecode
  5. The .aab is signed with your keystore
  6. You get a download link

6. Setting up EAS Submit (automatic upload)

Instead of manually downloading the .aab and uploading to Play Console, EAS can submit directly. You need a Google service account:

  1. In Google Play Console → Setup → API access
  2. Click "Create new service account" (links to Google Cloud Console)
  3. In Google Cloud Console:
    • Create service account with name "eas-submit"
    • Grant role: Service Account User
    • Create a JSON key → download it
  4. Back in Play Console → API access → Grant the service account "Release manager" permission
  5. Save the JSON key as google-service-account.json in your project root
Don't commit the service account key!

Add google-service-account.json to your .gitignore. This key has write access to your Play Console. Never push it to a public repository.

Now you can submit in one command:

# Build AND submit to Play Console:
eas build --platform android --profile production --auto-submit

# Or submit an existing build:
eas submit --platform android --latest

8. Completing the required store sections

Before you can publish, Play Console requires you to complete several sections. Here's each one for your app:

App content (Play Console → Policy → App content):

  • Privacy policy: Enter your hosted URL
  • Ads: Select "No, my app does not contain ads"
  • App access: Select "All functionality is restricted" → provide demo login credentials
  • Content rating: Complete the IARC questionnaire (Lesson 4)
  • Target audience: Select 13+ (messaging app)
  • Data safety: Complete the form (Lesson 4)

App settings (Play Console → Grow → Store settings):

  • App category: Communication
  • Contact email: Your support email
  • External marketing: Optional website URL

9. Release tracks — internal → closed → open → production

Google Play has four release tracks. You progress through them:

Track Who can see it Review? Use for
Internal testing Up to 100 testers (by email) No review Quick team testing
Closed testing Invited testers only Yes (faster) Beta testing
Open testing Anyone can join Yes Public beta
Production Everyone on Play Store Yes (1–3 days) Live release

Recommended path for your first release:

  1. Upload to Internal testing first (no review, instant availability)
  2. Install on your phone from the internal track to verify everything works
  3. When confident, promote to Production

10. Uploading your first build

Option A — EAS Submit (automated):

# Submit the latest production build to the internal track:
eas submit --platform android --latest

# EAS reads your eas.json submit config and uploads the .aab directly

Option B — Manual upload:

  1. Download the .aab from the EAS build URL
  2. In Play Console → Release → Testing → Internal testing
  3. Click "Create new release"
  4. Upload the .aab file
  5. Add release notes (e.g. "Initial release — messaging, calls, and status features")
  6. Click "Review release" → "Start rollout to Internal testing"

11. Testing the internal release

  1. In Play Console → Internal testing → Testers tab
  2. Create a testers list and add your email
  3. Copy the opt-in URL (looks like play.google.com/apps/testing/com.yourname.app)
  4. Open that URL on your Android phone
  5. Accept the invitation → you'll see the app in Play Store (marked "Internal testing")
  6. Install it and verify: login works, messages send, calls connect, notifications arrive

12. Promoting to production

Once you've verified the internal build works:

  1. Go to Play Console → Release → Production
  2. Click "Create new release"
  3. Select "Add from library" → pick the .aab you already uploaded
  4. Add release notes for users: 
    What's new:
• Send text messages, photos, and voice messages
• HD voice and video calls
• Group chats
• Status updates (stories)
• Push notifications
  5. Click "Review release"
  6. Fix any warnings (missing screenshots, etc.)
  7. Click "Start rollout to Production"

Google reviews your app (typically 1–3 days for the first submission, sometimes up to 7 days). You'll get an email when it's approved or if there are issues.

13. After publishing — versioning and updates

When you want to release an update:

// 1. Bump the version in app.json:
{
  "expo": {
    "version": "1.1.0",        // User-visible version
    "android": {
      "versionCode": 2          // Must increment by at least 1 each upload
    }
  }
}

// 2. Build the new version:
eas build --platform android --profile production

// 3. Submit to Play Store:
eas submit --platform android --latest

Version rules:

  • version — what users see ("1.0.0", "1.1.0", "2.0.0")
  • versionCode — integer that must increase with every upload (1, 2, 3, 4...)
  • Play Store rejects uploads where versionCode isn't higher than the last one

14. OTA updates with EAS Update (bonus)

For JavaScript-only changes (bug fixes, new features that don't need native code), you can push updates instantly without going through the Play Store review:

# Push an over-the-air update:
eas update --branch production --message "Fix message ordering bug"

# Users get the update next time they open the app (no store download needed)

When OTA works: JS changes, style changes, new screens, bug fixes

When OTA does NOT work: New native libraries, new permissions, changes to app.json native config → need a full EAS Build + store submission

15. Complete command summary

# ─── One-time setup ───────────────────────────────────────
npm install -g eas-cli
eas login
eas build:configure          # generates eas.json

# ─── Build for Play Store ─────────────────────────────────
eas build --platform android --profile production

# ─── Submit to Play Store ─────────────────────────────────
eas submit --platform android --latest

# ─── Build + Submit in one step ───────────────────────────
eas build --platform android --profile production --auto-submit

# ─── Push OTA update (JS only) ───────────────────────────
eas update --branch production --message "Description of changes"

# ─── Check build status ──────────────────────────────────
eas build:list
Your app is on the Play Store!
