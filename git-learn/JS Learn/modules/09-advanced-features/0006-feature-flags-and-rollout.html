Advanced Features · Lesson 6

Feature Flags & Staged Rollout

Firebase Remote Config · Percentage rollout · A/B testing · Kill switch · No-rebuild changes ~60 min Hands-on
Why this matters for your WhatsApp clone

You've built a new "Disappearing Messages" feature. It works perfectly in testing. But what if it crashes for users on slow Android phones? Or what if users hate it? Without feature flags, you'd have to push a new build to remove it — a process that takes days through app store review. With feature flags, you flip a switch in Firebase Console and the feature disappears instantly for all users. Or you show it to just 5% of users first, watch for crashes, and gradually roll it out to everyone. WhatsApp does this for every major feature — they test with a small percentage in India or Brazil before going global.

1. What are feature flags?

A feature flag is a remote on/off switch for a feature in your app. The flag's value lives on a server (Firebase Remote Config) — your app reads it at launch and decides whether to show or hide the feature.

// The concept — pseudocode:
if (remoteConfig.get('disappearing_messages_enabled') === true) {
  showDisappearingMessagesUI();
} else {
  // Feature is hidden — as if it doesn't exist
}

// You control the value from Firebase Console:
// Turn it ON → feature appears for users
// Turn it OFF → feature vanishes instantly (no new app build!)

What feature flags enable

Use caseHow it works
Kill switchDisable a broken feature instantly without a new build
Percentage rolloutShow to 5% → 20% → 50% → 100% of users gradually
A/B testing50% see design A, 50% see design B — measure which is better
Beta featuresShow to internal testers only
Regional launchEnable for India first, then expand to other countries
Time-based launchEnable after a specific date (holiday features)

import { initializeApp } from 'firebase/app';
import {
  getRemoteConfig,
  fetchAndActivate,
  getValue,
  getBoolean,
  getNumber,
  getString,
} from 'firebase/remote-config';

const app = initializeApp(firebaseConfig);
const remoteConfig = getRemoteConfig(app);

// Set minimum fetch interval (12 hours in production, 0 in dev)
remoteConfig.settings.minimumFetchIntervalMillis = __DEV__
  ? 0           // Fetch every time in development (for testing)
  : 43200000;   // 12 hours in production (Firebase free tier limit)

// Default values — used when the app can't reach Firebase
// (offline, first launch before config is fetched, etc.)
remoteConfig.defaultConfig = {
  disappearing_messages_enabled: false,
  new_chat_ui_enabled: false,
  max_group_size: 256,
  maintenance_mode: false,
  maintenance_message: 'We are performing scheduled maintenance. Back soon!',
  onboarding_variant: 'control',
  video_call_enabled: true,
};

// Fetch and activate remote values
export async function initRemoteConfig() {
  try {
    await fetchAndActivate(remoteConfig);
    console.log('Remote Config fetched and activated');
  } catch (error) {
    console.log('Remote Config fetch failed, using defaults:', error);
    // App continues with default values — never crashes
  }
}

// Helper functions to read flag values
export function getFlag(key) {
  return getBoolean(remoteConfig, key);
}

export function getFlagString(key) {
  return getString(remoteConfig, key);
}

export function getFlagNumber(key) {
  return getNumber(remoteConfig, key);
}

3. Using flags in your components

Now wrap features in simple if checks using the flag values.

// hooks/useFeatureFlag.js — Custom hook for feature flags

import { useState, useEffect } from 'react';
import { getRemoteConfig, getValue, onConfigUpdated } from 'firebase/remote-config';
import { remoteConfig } from '../config/remoteConfig';

// Hook: returns the current value of a boolean feature flag
export function useFeatureFlag(flagName) {
  const [enabled, setEnabled] = useState(() => {
    // Read current value synchronously (from last fetch)
    return getValue(remoteConfig, flagName).asBoolean();
  });

  useEffect(() => {
    // Listen for real-time config updates (if supported)
    // This lets you toggle flags without users restarting the app
    const unsubscribe = onConfigUpdated(remoteConfig, () => {
      const newValue = getValue(remoteConfig, flagName).asBoolean();
      setEnabled(newValue);
    });

    return () => unsubscribe();
  }, [flagName]);

  return enabled;
}

// Hook: returns a string flag value (for A/B test variants)
export function useFeatureVariant(flagName) {
  const [variant, setVariant] = useState(() => {
    return getValue(remoteConfig, flagName).asString();
  });

  useEffect(() => {
    const unsubscribe = onConfigUpdated(remoteConfig, () => {
      setVariant(getValue(remoteConfig, flagName).asString());
    });
    return () => unsubscribe();
  }, [flagName]);

  return variant;
}

4. Percentage rollout — showing to some users

Firebase Remote Config supports conditions — rules that decide which users see which value. The most powerful condition is percentage-based rollout.

Setting it up in Firebase Console

  1. Go to Firebase Console → Remote Config
  2. Add a parameter: disappearing_messages_enabled
  3. Set default value: false
  4. Click "Add condition"
  5. Name it "5% Rollout"
  6. Choose condition type: "User in random percentile"
  7. Set range: 0% to 5%
  8. Set value for this condition: true
  9. Click "Publish changes"

Now 5% of users will see the feature. To roll out further:

  • Day 1: 5% (watch crash reports)
  • Day 3: 20% (check user feedback)
  • Day 7: 50% (monitor performance)
  • Day 10: 100% (full launch!)
// You don't need to change ANY app code during rollout!
// Just edit the percentage in Firebase Console.
// The same useFeatureFlag('disappearing_messages_enabled') hook
// will return true for more users as you increase the percentage.

// The percentage is STICKY — the same user always gets the same value
// (based on a hash of their device ID). They won't flip between
// "has feature" and "doesn't have feature" on every app launch.

Other condition types

6. Kill switch — disabling a broken feature instantly

The most critical use of feature flags: emergency shutdown. A bug in your video call feature is crashing the app for 10% of users. Without a kill switch, you'd need to publish a new build (1–3 days for Apple review). With a kill switch, you disable it in 30 seconds.

// The kill switch pattern — wrap the entire feature

import { useFeatureFlag } from '../hooks/useFeatureFlag';

function CallButton({ recipientId, recipientName }) {
  // If this flag is set to false in Firebase Console,
  // the call button disappears instantly for all users
  const videoCallEnabled = useFeatureFlag('video_call_enabled');

  if (!videoCallEnabled) {
    return null; // Feature completely hidden
  }

  return (
    <Pressable
      onPress={() => startVideoCall(recipientId)}
      accessibilityLabel={`Video call ${recipientName}`}
      accessibilityRole="button"
      style={styles.callBtn}
    >
      <Text style={styles.callIcon}>📹</Text>
    </Pressable>
  );
}
// Maintenance mode — block the entire app temporarily

function MaintenanceGate({ children }) {
  const maintenanceMode = useFeatureFlag('maintenance_mode');
  const maintenanceMessage = useFeatureVariant('maintenance_message');

  if (maintenanceMode) {
    return (
      <View style={styles.maintenance}>
        <Text style={styles.maintenanceIcon}>🔧</Text>
        <Text style={styles.maintenanceTitle}>Under Maintenance</Text>
        <Text style={styles.maintenanceMsg}>{maintenanceMessage}</Text>
      </View>
    );
  }

  return children;
}

Emergency response playbook

  1. Crash reports spike → identify the feature causing it
  2. Open Firebase Console → Remote Config
  3. Set the feature's flag to false
  4. Click "Publish changes"
  5. Within minutes, users relaunch the app and the feature is gone
  6. Fix the bug, test thoroughly, then re-enable gradually (5% → 20% → 100%)

8. Best practices for feature flags

Naming conventions

// Use clear, consistent naming:
// [feature]_[what]_enabled  (for booleans)
// [feature]_[what]_value    (for strings/numbers)

// Good:
disappearing_messages_enabled
video_call_enabled
max_group_size
chat_header_variant
maintenance_mode

// Bad:
flag1
newFeature
test123
enableThing

Always have defaults

// The app MUST work if Remote Config is unreachable
// (no internet, Firebase outage, first launch)

remoteConfig.defaultConfig = {
  // Safe defaults — features are OFF until explicitly enabled
  disappearing_messages_enabled: false,
  new_chat_ui_enabled: false,
  // Critical features are ON by default
  video_call_enabled: true,
  // Sensible numbers
  max_group_size: 256,
  message_cooldown_ms: 1000,
};

Clean up old flags

// Once a feature is 100% rolled out and stable (4+ weeks),
// REMOVE the flag from your code and hardcode the feature as always-on.
// Dead flags accumulate and make code confusing.

// Before cleanup:
if (useFeatureFlag('reactions_enabled')) {
  showReactions();
}

// After cleanup (feature is permanent now):
showReactions();

// Also delete the parameter from Firebase Console.

Don't nest flags

// ❌ Bad: nested flags create impossible-to-debug combinations
if (flagA && flagB && !flagC) {
  // What combination is the user seeing? Hard to reason about.
}

// ✅ Good: one flag per feature, flat checks
if (disappearingMessagesEnabled) {
  showDisappearingMessages();
}
if (reactionsEnabled) {
  showReactions();
}

Feature flags work beautifully with the tools from Lessons 2 and 3:

// The safe feature launch workflow:
//
// 1. Develop the feature behind a flag (flag = false in production)
//    - Code ships to users, but feature is hidden

//
// 2. Enable for internal testers via Firebase condition
//    - Condition: user_property "role" == "tester"

function ChatScreen() {

    return (
      <View style={styles.header}>
        <Text style={styles.headerTitle}>Rahul</Text>

          {videoCallEnabled && <Text style={styles.headerIcon}>📹</Text>}

11. Key takeaways

  • Feature flags = remote on/off switches — control features without new builds
  • Firebase Remote Config — free, built into your existing Firebase stack
  • Always set defaults — app must work even if Remote Config is unreachable
  • Kill switch — disable broken features in 30 seconds, not 3 days
  • Percentage rollout — 5% → 20% → 50% → 100% (same user stays in their group)
  • A/B testing — show different UIs to different users, measure which performs better
  • Dynamic config values — change max group size, API URLs, rate limits without a build
  • Clean up old flags — remove flags 4+ weeks after 100% rollout to avoid dead code
  • Don't nest flags — one flag per feature, flat checks
  • Combine with OTA + CI/CD — ship code behind a flag, enable remotely when ready
