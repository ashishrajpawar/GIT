Advanced Features · Lesson 2

CI/CD Pipeline

GitHub Actions · Automated tests · EAS Build from CI · Staged rollouts · Version bumping ~70 min Hands-on
Why this matters for your WhatsApp clone

Right now, every time you want to release an update, you manually run eas build and eas submit from your laptop. What if you forget to run tests first and ship a bug that crashes the app for all users? What if your laptop dies mid-build? CI/CD (Continuous Integration / Continuous Delivery) automates this: every time you push code to GitHub, a server automatically runs your tests, builds the app, and (optionally) submits it to the stores — no manual steps, no forgotten tests, no broken releases.

1. What CI/CD means

TermWhat it doesWhatsApp clone example
CI (Continuous Integration) Automatically runs tests and checks every time you push code When Priya pushes a new message feature, tests run automatically to catch bugs
CD (Continuous Delivery) Automatically builds and deploys the app after tests pass After tests pass on main, EAS Build creates a new app binary and submits to stores

The pipeline we'll build

2. Setting up GitHub Actions

GitHub Actions is free for public repos and has generous free minutes for private repos. It reads workflow files from .github/workflows/ in your repo.

Step 1: Create the workflow file

# .github/workflows/ci.yml
# This file tells GitHub Actions what to do when you push code

name: CI — Test & Lint

# When does this run?
on:
  push:
    branches: [main, develop]   # Run on pushes to these branches
  pull_request:
    branches: [main]            # Run on PRs targeting main

jobs:
  test:
    name: Lint, Type Check & Test
    runs-on: ubuntu-latest      # Free Linux server from GitHub

    steps:
      # 1. Check out your code
      - name: Checkout code
        uses: actions/checkout@v4

      # 2. Set up Node.js
      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'          # Cache node_modules for speed

      # 3. Install dependencies
      - name: Install dependencies
        run: npm ci              # Clean install (faster than npm install)

      # 4. Run ESLint (code style)
      - name: Lint
        run: npx eslint . --ext .js,.jsx,.ts,.tsx

      # 5. Type checking (if using TypeScript)
      - name: Type check
        run: npx tsc --noEmit

      # 6. Run tests
      - name: Run tests
        run: npm test -- --coverage --watchAll=false

What each step does

  • actions/checkout@v4 — downloads your repo onto the CI server
  • actions/setup-node@v4 — installs Node.js (same version you use locally)
  • npm ci — installs exact versions from package-lock.json (reproducible, faster than npm install)
  • npx eslint — checks code style (catches missing imports, unused variables, etc.)
  • npx tsc --noEmit — verifies types without producing output files
  • npm test — runs your Jest test suite

3. Triggering EAS Build from CI

Once tests pass, we want to automatically build the app using EAS Build — the same command you'd run locally, but now it happens on GitHub's servers.

# .github/workflows/build.yml
# Triggers a production build after CI passes on main

name: Build & Deploy

on:
  push:
    branches: [main]            # Only build from main (not feature branches)

jobs:
  # First, run tests (reuse the CI job)
  test:
    name: Run Tests
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'
      - run: npm ci
      - run: npm test -- --watchAll=false

  # Then, build the app (only if tests pass)
  build:
    name: EAS Build
    needs: test               # Wait for test job to pass first!
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Setup EAS CLI
        uses: expo/expo-github-action@v8
        with:
          eas-version: latest
          token: ${{ secrets.EXPO_TOKEN }}   # Your Expo access token

      # Build for both platforms in parallel
      - name: Build Android
        run: eas build --platform android --profile production --non-interactive

      - name: Build iOS
        run: eas build --platform ios --profile production --non-interactive

Setting up the EXPO_TOKEN secret

  1. Go to expo.dev → Account Settings → Access Tokens
  2. Create a new token (name it "GitHub Actions")
  3. In your GitHub repo: Settings → Secrets and variables → Actions → New repository secret
  4. Name: EXPO_TOKEN, Value: paste the token from step 2
Why --non-interactive?

When EAS Build runs on a CI server, there's no human to answer prompts. The --non-interactive flag tells EAS to use defaults and fail loudly instead of waiting for input that will never come.

4. Environment variables and secrets management

Your app has sensitive values (Firebase config, API keys) that must never be committed to git. Here's how to handle them properly in CI.

The problem

// DON'T do this — anyone who reads your repo sees your keys!
const firebaseConfig = {
  apiKey: 'AIzaSyD_REAL_KEY_HERE',  // ← exposed!
  ...
};

The solution: environment variables

// app.config.js — Expo config that reads from environment variables
export default {
  name: 'ChatApp',
  slug: 'chatapp',
  version: '1.0.0',
  extra: {
    firebaseApiKey: process.env.FIREBASE_API_KEY,

    firebaseProjectId: process.env.FIREBASE_PROJECT_ID,

    firebaseMessagingSenderId: process.env.FIREBASE_MESSAGING_SENDER_ID,

5. EAS Build profiles — internal, beta, production

You don't want every build to go straight to the public store. EAS Build profiles let you create different build types for different stages.

// eas.json — build profiles for staged rollouts
{
  "cli": {
    "version": ">= 12.0.0"
  },
  "build": {
    "development": {
      "developmentClient": true,
      "distribution": "internal",
      "ios": {
        "simulator": true
      }
    },
    "preview": {
      "distribution": "internal",
      "channel": "preview"
    },
    "production": {
      "channel": "production",
      "autoIncrement": true
    }
  },
  "submit": {
    "production": {
      "android": {
        "serviceAccountKeyPath": "./google-service-account.json",
        "track": "internal"
      },
      "ios": {
        "appleId": "you@example.com",
        "ascAppId": "1234567890",
        "appleTeamId": "ABC123XYZ"
      }
    }
  }
}

The three stages

ProfileWho gets itPurpose
development You only (your phone/simulator) Day-to-day development with dev client
preview Your team / beta testers Internal testing before public release (distributed via link)
production All users via App Store / Play Store The real release

Staged rollout workflow

# Feature branch → develop → main

# 1. Push to feature branch → CI runs tests only
# 2. Merge to develop → builds "preview" profile → team tests it
# 3. Merge to main → builds "production" → submits to stores

# In .github/workflows/build.yml:
on:
  push:
    branches:
      - develop    # → preview build
      - main       # → production build

jobs:
  build:
    steps:
      - name: Determine build profile
        id: profile
        run: |
          if [ "${{ github.ref }}" = "refs/heads/main" ]; then
            echo "profile=production" >> $GITHUB_OUTPUT
          else
            echo "profile=preview" >> $GITHUB_OUTPUT
          fi

      - name: Build
        run: eas build --platform all --profile ${{ steps.profile.outputs.profile }} --non-interactive

6. Auto-submitting to the stores

After a production build completes, EAS Submit can automatically send it to Google Play and the App Store.

# Add this step AFTER the build step in your workflow:

      - name: Submit to stores
        if: github.ref == 'refs/heads/main'
        run: |
          # Submit the latest production build to both stores
          eas submit --platform android --profile production --latest --non-interactive
          eas submit --platform ios --profile production --latest --non-interactive

Android: Google Play Service Account

  1. Go to Google Play Console → Setup → API access
  2. Create a service account with "Release Manager" permissions
  3. Download the JSON key file
  4. Add the JSON content as a GitHub secret (GOOGLE_SERVICE_ACCOUNT_KEY)
  5. In CI, write it to a file before the submit step:
      - name: Create Google service account file
        run: echo '${{ secrets.GOOGLE_SERVICE_ACCOUNT_KEY }}' > ./google-service-account.json

iOS: App Store Connect API Key

  1. Go to App Store Connect → Users and Access → Keys
  2. Generate a new API key with "App Manager" role
  3. Add these as GitHub secrets: APPLE_API_KEY_ID, APPLE_API_ISSUER_ID, APPLE_API_KEY_P8
  4. EAS reads these from environment variables:
      - name: Submit to iOS
        env:
          EXPO_APPLE_API_KEY_ID: ${{ secrets.APPLE_API_KEY_ID }}
          EXPO_APPLE_API_ISSUER_ID: ${{ secrets.APPLE_API_ISSUER_ID }}
          EXPO_APPLE_API_KEY_PATH: ./apple-api-key.p8
        run: |
          echo '${{ secrets.APPLE_API_KEY_P8 }}' > ./apple-api-key.p8
          eas submit --platform ios --profile production --latest --non-interactive

7. Automated version bumping

Every store submission needs a higher version number. Instead of manually editing app.json every time, automate it.

// eas.json already handles build numbers with autoIncrement:
{
  "build": {
    "production": {
      "autoIncrement": true    // Bumps buildNumber (iOS) / versionCode (Android)
    }
  }
}

For the user-visible version (1.0.0 → 1.1.0 → 2.0.0), use a script:

// scripts/bump-version.js — Run before release
const fs = require('fs');
const path = require('path');

const appJsonPath = path.join(__dirname, '..', 'app.json');
const appJson = JSON.parse(fs.readFileSync(appJsonPath, 'utf8'));

// Bump patch version: 1.0.0 → 1.0.1
const parts = appJson.expo.version.split('.');
parts[2] = String(Number(parts[2]) + 1);
appJson.expo.version = parts.join('.');

fs.writeFileSync(appJsonPath, JSON.stringify(appJson, null, 2) + '\n');
console.log(`Version bumped to ${appJson.expo.version}`);
# In your workflow, bump version before building:
      - name: Bump version
        run: node scripts/bump-version.js

      - name: Commit version bump
        run: |
          git config user.name "GitHub Actions"
          git config user.email "actions@github.com"
          git add app.json
          git commit -m "chore: bump version to $(node -p "require('./app.json').expo.version")"
          git push

Semantic versioning for your app

Change typeVersion bumpExample
Bug fixPatch (x.x.1)1.2.0 → 1.2.1
New featureMinor (x.1.0)1.2.1 → 1.3.0
Breaking change / major redesignMajor (2.0.0)1.3.0 → 2.0.0

10. Full working example — App.js with environment variables

Here's your App.js updated to read Firebase config from environment variables (via app.config.js) instead of hardcoded strings. This is how a CI/CD-friendly app is structured.

// App.js — CI/CD-Ready Chat App
// Firebase config comes from environment variables, not hardcoded strings

import React, { useState, useEffect } from 'react';
import {
  View, Text, TextInput, FlatList, Pressable,
  StyleSheet, Alert, ActivityIndicator, Platform,
  KeyboardAvoidingView,
} from 'react-native';
import Constants from 'expo-constants';
import { initializeApp } from 'firebase/app';
import { getAuth, signInWithEmailAndPassword } from 'firebase/auth';
import {
  getFirestore, collection, doc, addDoc,
  query, orderBy, limit, onSnapshot, serverTimestamp,
  writeBatch,
} from 'firebase/firestore';

// ─── Firebase config from environment (set in app.config.js) ─
const firebaseConfig = {
  apiKey: Constants.expoConfig.extra.firebaseApiKey,
  authDomain: Constants.expoConfig.extra.firebaseAuthDomain,
  projectId: Constants.expoConfig.extra.firebaseProjectId,
  storageBucket: Constants.expoConfig.extra.firebaseStorageBucket,
  messagingSenderId: Constants.expoConfig.extra.firebaseMessagingSenderId,
  appId: Constants.expoConfig.extra.firebaseAppId,
};

const app = initializeApp(firebaseConfig);
const auth = getAuth(app);
const db = getFirestore(app);

// ─── App version display (from app.json, auto-bumped by CI) ──
const APP_VERSION = Constants.expoConfig.version;

// ─── WhatsApp colours ────────────────────────────────────────
const COLORS = {
  darkGreen: '#075E54',
  lightGreen: '#25D366',
  bubbleGreen: '#DCF8C6',
  chatBg: '#ECE5DD',
  white: '#FFFFFF',
};

// ─── Send message ────────────────────────────────────────────
async function sendMessage(chatId, text) {
  const userId = auth.currentUser.uid;
  const trimmed = text.trim();

  if (trimmed.length === 0 || trimmed.length > 4096) {
    throw new Error('Message must be 1–4096 characters');
  }

  const batch = writeBatch(db);

  const msgRef = doc(collection(db, 'chats', chatId, 'messages'));
  batch.set(msgRef, {
    senderId: userId,
    text: trimmed,
    createdAt: serverTimestamp(),
  });

  const rateLimitRef = doc(db, 'rateLimits', userId);
  batch.set(rateLimitRef, { lastWrite: serverTimestamp() });

  const chatRef = doc(db, 'chats', chatId);
  batch.update(chatRef, {
    lastMessage: trimmed.substring(0, 100),
    lastMessageAt: serverTimestamp(),
  });

  try {
    await batch.commit();
  } catch (error) {
    if (error.code === 'permission-denied') {
      throw new Error('Message blocked by security rules.');
    }
    throw error;
  }
}

// ─── Chat Screen ─────────────────────────────────────────────
function ChatScreen({ chatId }) {
  const [messages, setMessages] = useState([]);
  const [input, setInput] = useState('');
  const [sending, setSending] = useState(false);

  useEffect(() => {
    const q = query(
      collection(db, 'chats', chatId, 'messages'),
      orderBy('createdAt', 'desc'),
      limit(50)
    );

    const unsubscribe = onSnapshot(q, (snapshot) => {
      const msgs = snapshot.docs.map((msgDoc) => ({
        id: msgDoc.id,
        ...msgDoc.data(),
      }));
      setMessages(msgs);
    });

    return unsubscribe;
  }, [chatId]);

  const handleSend = async () => {
    if (!input.trim() || sending) return;
    setSending(true);
    try {
      await sendMessage(chatId, input);
      setInput('');
    } catch (error) {
      Alert.alert('Send failed', error.message);
    } finally {
      setSending(false);
    }
  };

  const userId = auth.currentUser?.uid;

  const renderMessage = ({ item }) => {
    const isMine = item.senderId === userId;
    return (
      <View style={[styles.bubble, isMine ? styles.myBubble : styles.theirBubble]}>
        <Text style={styles.messageText}>{item.text}</Text>
        <Text style={styles.timeText}>
          {item.createdAt?.toDate?.()
            ? item.createdAt.toDate().toLocaleTimeString([], {
                hour: '2-digit', minute: '2-digit',
              })
            : 'Sending...'}
        </Text>
      </View>
    );
  };

  return (
    <KeyboardAvoidingView
      style={styles.container}
      behavior={Platform.OS === 'ios' ? 'padding' : 'height'}
    >
      {/* Header with version */}
      <View style={styles.header}>
        <Text style={styles.headerTitle}>Priya</Text>
        <Text style={styles.headerSubtitle}>v{APP_VERSION} • online</Text>
      </View>

      {/* Messages */}
      <FlatList
        data={messages}
        renderItem={renderMessage}
        keyExtractor={(item) => item.id}
        inverted
        style={styles.messageList}
        contentContainerStyle={{ paddingVertical: 10 }}
      />

      {/* Input bar */}
      <View style={styles.inputBar}>
        <TextInput
          style={styles.input}
          value={input}
          onChangeText={setInput}
          placeholder="Type a message"
          maxLength={4096}
          multiline
        />
        <Pressable
          style={[styles.sendBtn, sending && { opacity: 0.5 }]}
          onPress={handleSend}
          disabled={sending}
        >
          {sending
            ? <ActivityIndicator color={COLORS.white} size="small" />
            : <Text style={styles.sendText}>Send</Text>
          }
        </Pressable>
      </View>
    </KeyboardAvoidingView>
  );
}

// ─── Main App ────────────────────────────────────────────────
export default function App() {
  const [user, setUser] = useState(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    signInWithEmailAndPassword(auth, 'reviewer@yourapp.com', 'ReviewTest2026!')
      .then((cred) => setUser(cred.user))
      .catch((err) => Alert.alert('Login failed', err.message))
      .finally(() => setLoading(false));
  }, []);

  if (loading) {
    return (
      <View style={styles.center}>
        <ActivityIndicator size="large" color={COLORS.darkGreen} />
      </View>
    );
  }

  if (!user) {
    return (
      <View style={styles.center}>
        <Text>Not logged in</Text>
      </View>
    );
  }

  return <ChatScreen chatId="chat1" />;
}

// ─── Styles ──────────────────────────────────────────────────
const styles = StyleSheet.create({
  container: { flex: 1, backgroundColor: COLORS.chatBg },
  center: { flex: 1, justifyContent: 'center', alignItems: 'center' },
  header: {
    backgroundColor: COLORS.darkGreen,
    paddingTop: Platform.OS === 'ios' ? 50 : 30,
    paddingBottom: 12,
    paddingHorizontal: 16,
  },

11. Key takeaways

  • CI runs tests on every push — catches bugs before they reach users
  • CD builds and deploys automatically — no more manual eas build from your laptop
  • GitHub Actions is free — for public repos or within generous private limits
  • Never hardcode secrets — use environment variables + GitHub Secrets
  • EAS Build profiles — development → preview → production (staged rollouts)
  • --non-interactive — required for CI (no human to answer prompts)
  • Auto-increment build numbers — "autoIncrement": true in eas.json
  • Submit to stores from CI — eas submit --latest --non-interactive
  • Notifications on failure — Slack/Discord webhook so you know immediately
  • needs: test — the build job waits for tests to pass first
The golden rule of CI/CD

If the tests are red (failing), the build should never deploy. The needs: test keyword enforces this — your production build is physically impossible until tests pass. This single rule prevents most catastrophic releases.
