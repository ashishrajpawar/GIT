Revocation & Pause

B7 — Lesson 3 of 3 • ~45 min

Why this matters for Token

When a user revokes a token, ALL active sessions must end immediately. Not "on next request" — immediately. Active WebSocket conversations disconnect, ongoing calls hang up, pending messages are blocked. This is the nuclear option, and it must work flawlessly. Pause is softer — it temporarily rejects new actions but also drops existing connections. The difference: pause is reversible, revoke is permanent.

Status Transitions

A token has three statuses. The transitions are strictly controlled: 

// Valid status transitions:
// active  -> paused    (user pauses)
// active  -> revoked   (user revokes)
// paused  -> active    (user resumes)
// paused  -> revoked   (user revokes while paused)
// revoked -> (nothing) (permanent, cannot undo)

type TokenStatus = 'active' | 'paused' | 'revoked';

const VALID_TRANSITIONS: Record<TokenStatus, TokenStatus[]> = {
  active: ['paused', 'revoked'],
  paused: ['active', 'revoked'],
  revoked: []  // Terminal state — no way back
};

POST /tokens/:id/revoke — and why it is not PATCH

B3.3 settled the shape: POST /tokens/:id/revoke, /pause and /resume rather than a status field on PATCH. These are actions with consequences — sockets close, calls end — not a field being edited, and naming them separately means each can be authorised and rate limited on its own terms.

State is timestamps, not an enum: revoked_at and paused_at, matching B7.1 and B7.2. A timestamp answers "when", which an audit needs, and it cannot drift out of step with a derived status the way a stored one can. 

// api/src/routes/tokens.ts
router.post('/tokens/:id/revoke', authenticate, async (req, res, next) => {
  const client = await pool.connect();
  try {
    await client.query('BEGIN');

    // Scoped by owner, so "not yours" and "does not exist" are one 404.
    // Only sets revoked_at if it is not already set - so calling this twice
    // is not an error, it is the same outcome. A user hammering the revoke
    // button on a bad connection must not get a failure for an action that
    // already succeeded.
    const { rows } = await client.query(
      `UPDATE tokens SET revoked_at = NOW()
        WHERE id = $1 AND user_id = $2 AND revoked_at IS NULL
        RETURNING id, paused_at`,
      [req.params.id, req.user.id]
    );

    if (rows.length === 0) {
      // Either it is not theirs, it does not exist, or it was already
      // revoked. Confirm the end state rather than reporting a conflict.
      const { rows: check } = await client.query(
        'SELECT revoked_at FROM tokens WHERE id = $1 AND user_id = $2',
        [req.params.id, req.user.id]
      );
      await client.query('ROLLBACK');
      if (check.length === 0) return res.status(404).json({ error: 'Token not found' });
      return res.status(204).end();      // already revoked: still success
    }

    await client.query(
      `INSERT INTO revocation_events (token_id, action, created_at)
       VALUES ($1, 'revoked', NOW())`,
      [req.params.id]
    );

    await client.query('COMMIT');

    // After the commit, never inside it. Holding a transaction open across a
    // network call to Redis is how one slow dependency becomes a lock nobody
    // else can get past.
    await propagateStatusChange(Number(req.params.id), 'revoked');

    res.status(204).end();
  } catch (err) {
    await client.query('ROLLBACK').catch(() => {});
    next(err);
  } finally {
    client.release();
  }
});

/pause is the same shape against paused_at, and /resume clears it — but only when revoked_at is null, which is what makes revocation terminal. The transition table becomes a WHERE clause rather than a lookup in application code, and a WHERE clause cannot be raced.

Propagation to Active WebSocket Connections

When a token is revoked or paused, every active WebSocket connection for that token's conversations must be notified and disconnected. 

// api/src/engine/propagate.ts
import { getSocketsByTokenId } from '../ws/registry';
import { endCallByTokenId } from '../signalling/calls';

export async function propagateStatusChange(
  tokenId: number,
  newStatus: 'paused' | 'revoked'
): Promise<void> {
  // Publish once. Every replica - including this one - receives it and
  // closes whichever sockets it happens to be holding.
  await broadcastStatusChange(tokenId, newStatus);

  // Calls travel the same way, for the same reason: the two peers may be
  // connected to two different replicas.
  await redis.publish('call:end', JSON.stringify({ tokenId, reason: newStatus }));
}

// IMPORTANT: this is the FAST path, not the correct one.
//
// Closing a socket does not stop the holder reconnecting a second later
// with a JWT that is still perfectly valid. What actually enforces
// revocation is the check on the way IN - and that check is the reason
// this works even if a replica was restarting when the message went out.
export async function authoriseSocketConnect(tokenId: number) {
  const { rows } = await pool.query(
    'SELECT revoked_at, paused_at FROM tokens WHERE id = $1',
    [tokenId]
  );
  const t = rows[0];
  if (!t || t.revoked_at !== null || t.paused_at !== null) {
    throw new Error('token not usable');
  }
}

The Socket Registry — local map, global broadcast

A local Map is not a registry

Each replica only ever holds the sockets connected to it. If the owner's revoke lands on replica A and the holder's socket is on replica B, a local lookup finds nothing and returns successfully — the connection stays open and the revoke silently does nothing.

ADR-0003 names this directly: the API is stateless, there is no node-local socket registry, and Redis is required rather than optional. This is the exact case it was written for.

Each replica keeps a local map of its own sockets — it has to, they are objects in its memory — and revocation is broadcast over Redis so every replica checks its own map. 

// api/src/ws/registry.ts
import { WebSocket } from 'ws';
import { redis, redisSub } from '../redis';

// This replica's own connections. Never treated as the whole picture.
const localSockets = new Map<number, Set<WebSocket>>();

export function registerSocket(tokenId: number, ws: WebSocket): void {
  if (!localSockets.has(tokenId)) localSockets.set(tokenId, new Set());
  localSockets.get(tokenId)!.add(ws);

  ws.on('close', () => {
    const sockets = localSockets.get(tokenId);
    if (!sockets) return;
    sockets.delete(ws);
    if (sockets.size === 0) localSockets.delete(tokenId);
  });
}

// Called by whichever replica handled the revoke.
export async function broadcastStatusChange(tokenId: number, status: string) {
  await redis.publish('token:status', JSON.stringify({ tokenId, status }));
}

// Every replica subscribes at startup, including the one that published -
// so the publisher needs no special case.
redisSub.subscribe('token:status');
redisSub.on('message', (_channel, payload) => {
  const { tokenId, status } = JSON.parse(payload);
  closeLocalSockets(tokenId, status);
});

function closeLocalSockets(tokenId: number, status: string) {
  const sockets = localSockets.get(tokenId);
  if (!sockets) return;                 // not on this replica - fine

  const message = JSON.stringify({ type: 'token_status_changed', status });
  for (const ws of sockets) {
    // Close AFTER the write flushes. ws.send() is asynchronous; closing on
    // the next line can drop the message the holder needs to see.
    ws.send(message, () => ws.close(1000, 'token ' + status));
  }
  localSockets.delete(tokenId);
}

Ending Active Calls

Voice/video calls use WebRTC. The signalling server must send a hangup signal to both peers when a token is revoked. 

// api/src/signalling/calls.ts
import { getActiveCallByTokenId } from './callRegistry';

export async function endCallByTokenId(
  tokenId: number,
  reason: 'paused' | 'revoked'
): Promise<void> {
  const activeCall = getActiveCallByTokenId(tokenId);
  if (!activeCall) return;

  // Send hangup signal to both peers
  const hangupMessage = JSON.stringify({
    type: 'call_ended',
    reason: `Token ${reason} — call terminated`,
    initiatedBy: 'system'
  });

  if (activeCall.callerSocket?.readyState === WebSocket.OPEN) {
    activeCall.callerSocket.send(hangupMessage);
  }
  if (activeCall.receiverSocket?.readyState === WebSocket.OPEN) {
    activeCall.receiverSocket.send(hangupMessage);
  }

  // Record call end in database
  await pool.query(
    `UPDATE calls SET ended_at = NOW(), end_reason = $1
     WHERE id = $2 AND ended_at IS NULL`,
    [`token_${reason}`, activeCall.id]
  );

  // Remove from active call registry
  removeActiveCall(activeCall.id);
}

Pause vs. Revoke — The Key Differences

// Comparison table as code comments:
//
// | Aspect              | Pause                    | Revoke                     |
// |---------------------|--------------------------|----------------------------|
// | Reversible?         | Yes (resume to active)   | No (permanent)             |
// | Active connections  | Dropped immediately      | Dropped immediately        |
// | New redemptions     | Blocked                  | Blocked                    |
// | New messages        | Blocked                  | Blocked                    |
// | Conversation data   | Retained                 | Retained (for audit)       |
// | Token visible in UI | Yes (with paused badge)  | Yes (with revoked badge)   |
// | Can reuse code?     | No (code stays reserved) | No (code stays reserved)   |
// | User intent         | "Not now, maybe later"   | "Never again"              |

Why this way (and what was rejected)

Closing sockets is the fast path. The connect check is the real one.

It is tempting to read this lesson as "revocation works because we close the sockets". It does not. A holder whose socket is closed can reconnect a second later with a holder JWT that is still perfectly valid and does not expire for seven days — B7.1 issued it and nothing has taken it back.

What enforces revocation is the check performed when a connection is established, and on every action after it (B7.2). The socket close is a courtesy that makes the effect immediate and visible; the database check is what makes it true. Get that the wrong way round and you build a system whose security property depends on a broadcast being delivered.

Which is also why it survives failure. If a replica is mid-restart when the Redis message goes out, it never closes that socket — and the next thing the holder does is refused anyway.

Redis fan-out, because a local map is one replica's opinion

The registry has to be local — the sockets are objects in one process's memory and cannot be anywhere else. The decision to close them cannot be. Publishing to Redis and letting every replica check its own map is the shape ADR-0003 requires, and the reason "build to scale out, deploy on one box" costs almost nothing here: with one replica the publish is a local round trip, and the day there are three, nothing changes.

Idempotent, because the button gets pressed twice

The original returned 400 Cannot transition from 'revoked' to 'revoked'. Consider when that happens: a user on a bad connection taps Revoke, sees nothing, and taps again. The first request succeeded, the response was lost, and the app now shows an error for the most safety-critical action in the product. They will reasonably conclude it did not work.

WHERE revoked_at IS NULL plus a 204 for the already-revoked case means the answer to "revoke this" is always "it is revoked".

Timestamps, not a status enum

revoked_at and paused_at match B7.1 and B7.2, and they answer when — which an audit trail needs and a status column cannot. The transition rules become WHERE clauses (resume only applies WHERE revoked_at IS NULL), so they are enforced by the database rather than by a lookup table in application code that two concurrent requests can both pass.

When this breaks

One replica hears the revoke. The others do not.

The original registry was a Map in one process. Revoke arrives at replica A; the holder's socket is on replica B; getSocketsByTokenId finds nothing, returns an empty set, the loop does nothing, and the endpoint responds 200 OK. The owner is told their token is revoked and the conversation is still live.

Nothing errors. Nothing logs. It works perfectly on a laptop with one process and fails the first time a second replica exists — which is exactly the class of bug ADR-0003 exists to prevent, and why "no node-local socket registry" is written down rather than left to judgement.

The message that never left

ws.send(message);
ws.close(1000, 'Token revoked');    // may close before the send flushes

ws.send is asynchronous. Closing on the next line can discard the frame, so the holder's screen shows a disconnection with no explanation and the app reconnects thinking it was a network blip. Close in the send callback.

Propagation is not transactional, and must not be

The publish happens after COMMIT, which is correct — holding a transaction open across a call to Redis turns one slow dependency into a lock everyone else queues behind. The cost is a real window: if the process dies between the commit and the publish, the token is revoked in the database and the sockets stay open until something else closes them.

Which is survivable only because of the connect-time and per-action checks. They are not belt-and-braces; they are the belt.

Pause drops connections, and the client must not treat that as an error

A paused token closes sockets exactly like a revoked one. The difference is what happens next: the holder's client sees a normal close with a status of paused, and must show "this conversation is paused" rather than retrying forever. A reconnect loop against a paused token is an accidental denial-of-service on your own API — and the rate limiter will eventually treat that client as an attacker.

What this costs you

DecisionWhat you pay
Redis on the revoke path Another dependency in the most safety-critical action in the product. If Redis is down the database write still succeeds and enforcement still holds — the connection simply closes late, on the holder's next action rather than instantly. Degraded, not broken, which is the only acceptable shape here.
Checking token state on every socket connect A query on every reconnect, and mobile clients reconnect constantly — every tunnel, every wifi handover. It is one indexed primary-key lookup, and it is the check the whole guarantee rests on.
Revocation being terminal No undo. A user who revokes the wrong token issues a new one and re-shares it — which is cheap for a delivery driver and painful for a token printed on a business card. The alternative, an undo window, means "revoked" would not quite mean revoked.
Keeping revoked tokens and their conversations Storage that never shrinks, and a privacy question of its own: the audit trail that proves someone kept trying after being cut off is also a record of them. That tension belongs to the retention policy in C9, not here.
Codes stay reserved forever A revoked code can never be reissued, so the keyspace only shrinks. At 7.9 × 1017 that will never matter — but it is the reason the collision check exists at all.

The Audit Trail

Every status change is recorded. This gives the user a full history and supports any future dispute resolution. 

-- Migration: create revocation_events table
CREATE TABLE revocation_events (
  id            SERIAL PRIMARY KEY,
  token_id      INTEGER NOT NULL REFERENCES tokens(id),
  previous_status VARCHAR(10) NOT NULL,
  new_status    VARCHAR(10) NOT NULL,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  metadata      JSONB DEFAULT '{}'
);

CREATE INDEX idx_revocation_events_token ON revocation_events(token_id);

-- Query: get full lifecycle of a token
SELECT
  re.previous_status,
  re.new_status,
  re.created_at,
  re.metadata
FROM revocation_events re
WHERE re.token_id = $1
ORDER BY re.created_at ASC;

Preventing Actions on Non-Active Tokens

The rules engine (lesson 2) handles per-action checks, but we also need a gate at the top of every handler: if the token is not active, reject immediately without even evaluating rules. 

// api/src/middleware/tokenActive.ts
export async function requireActiveToken(tokenId: number): Promise<void> {
  const { rows } = await pool.query(
    'SELECT status FROM tokens WHERE id = $1',
    [tokenId]
  );

  if (rows.length === 0) {
    throw new TokenError('Token not found', 404);
  }

  if (rows[0].status === 'paused') {
    throw new TokenError('Token is currently paused', 403);
  }

  if (rows[0].status === 'revoked') {
    throw new TokenError('Token has been permanently revoked', 403);
  }
}

// Usage in a handler:
async function handleIncomingMessage(tokenId, content) {
  await requireActiveToken(tokenId);        // Gate check
  const ruleCheck = await evaluateRules(tokenId, 'message');  // Rule check
  if (!ruleCheck.allowed) throw new RuleDeniedError(ruleCheck.reason);
  // ... proceed with message
}
