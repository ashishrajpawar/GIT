Access Rules Engine

B7 — Lesson 2 of 3 • ~50 min

Why this matters for Token

Rules are what make Token more than a contact form. A user can say "this delivery driver can message me only between 9 AM and 6 PM, only text, max 5 messages per day." The rules are stored as JSONB in the tokens table — the engine evaluates them on every message or call attempt. If the engine is wrong, privacy erodes. Deny-by-default: if a rule cannot be evaluated, the action is blocked.

The Rules Schema

Rules live in the rules JSONB column of the tokens table. The structure supports multiple rule types that are evaluated together — ALL must pass for an action to be allowed. 

// The rules JSONB structure
interface TokenRules {
  time_window?: {
    days: number[];        // 0=Sun, 1=Mon, ..., 6=Sat
    start_time: string;    // "09:00" (24h format)
    end_time: string;      // "18:00"
    timezone: string;      // "Asia/Kolkata"
  };
  contact_limit?: {
    max_messages_per_day: number;
    max_calls_per_day: number;
  };
  channel_restrict?: {
    allow_text: boolean;
    allow_voice: boolean;
    allow_video: boolean;
  };
}

// Example rules stored in the database:
{
  "time_window": {
    "days": [1, 2, 3, 4, 5],
    "start_time": "09:00",
    "end_time": "18:00",
    "timezone": "Asia/Kolkata"
  },
  "contact_limit": {
    "max_messages_per_day": 10,
    "max_calls_per_day": 2
  },
  "channel_restrict": {
    "allow_text": true,
    "allow_voice": true,
    "allow_video": false
  }
}

The Core evaluateRules Function

This is the heart of the token engine. Every action (send message, initiate call) passes through this function. It returns either { allowed: true } or { allowed: false, reason: string }. 

// api/src/engine/rules.ts
import { pool } from '../db';

type Action = 'message' | 'voice_call' | 'video_call';

interface RuleResult {
  allowed: boolean;
  reason?: string;
}

// Every rule type this engine understands. Anything in the rules column
// that is NOT in here is a rule we cannot evaluate - which under
// deny-by-default means the action is refused, not ignored.
const KNOWN_RULES = ['channel_restrict', 'time_window', 'contact_limit'] as const;

export async function evaluateRules(
  tokenId: number,
  action: Action
): Promise<RuleResult> {
  try {
    // The token's STATE comes back with its rules. Evaluating rules without
    // checking whether the token is still alive is how a revoked token keeps
    // working on a conversation that already exists.
    const { rows } = await pool.query(
      `SELECT rules, revoked_at, paused_at, expires_at, max_uses, uses
         FROM tokens WHERE id = $1`,
      [tokenId]
    );

    if (rows.length === 0) {
      return { allowed: false, reason: 'Token not found' };
    }

    const token = rows[0];

    // 1. Is this token usable at all? Checked first, and independently of
    //    any rule the owner did or did not set.
    if (token.revoked_at !== null) return { allowed: false, reason: 'revoked' };
    if (token.paused_at !== null) return { allowed: false, reason: 'paused' };
    if (token.expires_at !== null && new Date(token.expires_at) <= new Date()) {
      return { allowed: false, reason: 'expired' };
    }

    const rules = token.rules;

    // 2. An empty rules object means the owner chose not to restrict, and
    //    that is a real answer. A rules column that is not an object at all
    //    means something is wrong, and "something is wrong" is not consent.
    if (rules === null || rules === undefined) return { allowed: true };
    if (typeof rules !== 'object' || Array.isArray(rules)) {
      return { allowed: false, reason: 'unreadable rules' };
    }

    // 3. Refuse what we do not understand. An older server meeting a rule
    //    type added by a newer client must not silently ignore it.
    const unknown = Object.keys(rules).filter(k => !KNOWN_RULES.includes(k as any));
    if (unknown.length > 0) {
      return { allowed: false, reason: 'unsupported rule: ' + unknown[0] };
    }

    // 4. Every rule present must pass.
    if (rules.channel_restrict) {
      const result = evaluateChannelRestrict(rules.channel_restrict, action);
      if (!result.allowed) return result;
    }

    if (rules.time_window) {
      const result = evaluateTimeWindow(rules.time_window);
      if (!result.allowed) return result;
    }

    if (rules.contact_limit) {
      const result = await evaluateContactLimit(rules.contact_limit, tokenId, action);
      if (!result.allowed) return result;
    }

    return { allowed: true };
  } catch (err) {
    // Deny-by-default has to include the case where the engine itself
    // failed. A thrown exception that propagates is an unhandled path, and
    // an unhandled path in an authorisation check is an open door.
    logger.error({ err, tokenId, action }, 'rule evaluation failed');
    return { allowed: false, reason: 'could not evaluate rules' };
  }
}

Channel Restriction Evaluation

The simplest rule — a direct boolean check against the action type. 

function evaluateChannelRestrict(
  rule: { allow_text: boolean; allow_voice: boolean; allow_video: boolean },
  action: Action
): RuleResult {
  switch (action) {
    case 'message':
      if (!rule.allow_text) {
        return { allowed: false, reason: 'Text messages are not allowed on this token' };
      }
      break;
    case 'voice_call':
      if (!rule.allow_voice) {
        return { allowed: false, reason: 'Voice calls are not allowed on this token' };
      }
      break;
    case 'video_call':
      if (!rule.allow_video) {
        return { allowed: false, reason: 'Video calls are not allowed on this token' };
      }
      break;
  }
  return { allowed: true };
}

Time Window Evaluation

Checks the current time in the token owner's timezone against the allowed window. This handles day-of-week and time range. 

function evaluateTimeWindow(
  rule: { days: number[]; start_time: string; end_time: string; timezone: string }
): RuleResult {
  // Get current time in the token owner's timezone
  const now = new Date();
  const options: Intl.DateTimeFormatOptions = {
    timeZone: rule.timezone,
    hour: '2-digit',
    minute: '2-digit',
    hour12: false,
    weekday: 'short'
  };

  const formatter = new Intl.DateTimeFormat('en-US', options);
  const parts = formatter.formatToParts(now);

  // Extract day of week (0-6)
  const dayFormatter = new Intl.DateTimeFormat('en-US', {
    timeZone: rule.timezone,
    weekday: 'short'
  });
  const dayStr = dayFormatter.format(now);
  const dayMap: Record<string, number> = {
    Sun: 0, Mon: 1, Tue: 2, Wed: 3, Thu: 4, Fri: 5, Sat: 6
  };
  const currentDay = dayMap[dayStr];

  // Check day is allowed
  if (!rule.days.includes(currentDay)) {
    return { allowed: false, reason: 'Contact not allowed on this day' };
  }

  // Extract current time as HH:MM
  const hourPart = parts.find(p => p.type === 'hour')?.value || '00';
  const minutePart = parts.find(p => p.type === 'minute')?.value || '00';
  const currentTime = `${hourPart}:${minutePart}`;

  // Compare as strings - HH:MM sorts correctly. But a window is not always
  // start < end: "22:00 to 06:00" is a perfectly ordinary do-not-disturb
  // inverse, and the naive comparison rejects every minute of it.
  const inWindow = rule.start_time <= rule.end_time
    ? (currentTime >= rule.start_time && currentTime < rule.end_time)
    // Overnight window: allowed if after the start OR before the end.
    : (currentTime >= rule.start_time || currentTime < rule.end_time);

  if (!inWindow) {
    return {
      allowed: false,
      reason: `Contact allowed only between ${rule.start_time} and ${rule.end_time} (${rule.timezone})`
    };
  }

  return { allowed: true };
}

Contact Limit Evaluation

Counts today's actions in the database. This requires a query on each check, but correctness matters more than speed here. Caching would risk allowing messages past the limit. 

// Midnight in a named timezone, as an instant. Intl knows the offset for
// that date, which is what makes this survive a DST change - somewhere that
// has one. India does not, which is exactly why this is easy to get wrong
// here and then break in the first market that does.
function startOfDayIn(timeZone: string): Date {
  const parts = new Intl.DateTimeFormat('en-CA', {
    timeZone, year: 'numeric', month: '2-digit', day: '2-digit'
  }).formatToParts(new Date());
  const get = (t: string) => parts.find(p => p.type === t)!.value;
  // 'en-CA' formats as YYYY-MM-DD, which is why it is used here.
  return new Date(new Date(`${get('year')}-${get('month')}-${get('day')}T00:00:00`)
    .toLocaleString('en-US', { timeZone }));
}

async function evaluateContactLimit(
  rule: { max_messages_per_day: number; max_calls_per_day: number },
  tokenId: number,
  action: Action
): Promise<RuleResult> {
  // "Per day" means the OWNER's day. Counting from UTC midnight resets the
  // allowance at 05:30 in Asia/Kolkata - so a holder who used up their ten
  // messages at 9pm gets ten more at half past five the next morning, and
  // the owner's "10 a day" quietly became more.
  const todayStart = startOfDayIn(rule.timezone ?? 'Asia/Kolkata');

  if (action === 'message') {
    const { rows } = await pool.query(
      `SELECT COUNT(*)::int as cnt FROM messages m
       JOIN conversations c ON m.conversation_id = c.id
       WHERE c.token_id = $1
         AND m.sender_role = 'holder'
         AND m.created_at >= $2`,
      [tokenId, todayStart.toISOString()]
    );

    if (rows[0].cnt >= rule.max_messages_per_day) {
      return {
        allowed: false,
        reason: `Daily message limit reached (${rule.max_messages_per_day})`
      };
    }
  }

  if (action === 'voice_call' || action === 'video_call') {
    const { rows } = await pool.query(
      `SELECT COUNT(*)::int as cnt FROM calls
       WHERE token_id = $1
         AND initiated_by = 'holder'
         AND created_at >= $2`,
      [tokenId, todayStart.toISOString()]
    );

    if (rows[0].cnt >= rule.max_calls_per_day) {
      return {
        allowed: false,
        reason: `Daily call limit reached (${rule.max_calls_per_day})`
      };
    }
  }

  return { allowed: true };
}

Integrating into Chat and Call Handlers

Every incoming message or call request passes through evaluateRules before being processed. 

// In your WebSocket message handler:
ws.on('message', async (data) => {
  const { type, conversationId, content } = JSON.parse(data);

  if (type === 'chat_message') {
    // Get tokenId from conversation
    const { rows } = await pool.query(
      'SELECT token_id FROM conversations WHERE id = $1',
      [conversationId]
    );
    const tokenId = rows[0].token_id;

    // Evaluate rules BEFORE processing
    const ruleCheck = await evaluateRules(tokenId, 'message');
    if (!ruleCheck.allowed) {
      ws.send(JSON.stringify({
        type: 'error',
        code: 'RULE_DENIED',
        reason: ruleCheck.reason
      }));
      return;  // Message blocked
    }

    // Rules passed — save and broadcast message
    await saveMessage(conversationId, content);
    broadcastToConversation(conversationId, content);
  }
});

Deny-by-Default Principle

If anything goes wrong during rule evaluation — a database error, an unexpected rule format, a missing timezone — the action is DENIED. Bugs should restrict access, never grant it.

That is easy to state and it is four separate things to build. The version of this engine that existed before this lesson was deepened had a evaluateRulesSafe wrapper that caught exceptions — and the integration code called evaluateRules directly, so the wrapper never ran. A safe version that can be bypassed is not a safe version. The try/catch now lives inside the one function everyone calls, and there is no unsafe one to reach for.

The gapWhat it granted
Exception escapes the evaluator An unhandled path in an authorisation check. A bad timezone string makes Intl throw a RangeError, and the caller has no answer at all.
Unknown rule type ignored A rule the owner set and this server does not understand is skipped rather than obeyed. An older replica mid-deploy silently ignores a restriction.
Unreadable rules treated as "no rules" Corruption reads as consent. "No restrictions" and "we could not tell" must not be the same answer.
Token state never checked The big one — see below.

Why this way (and what was rejected)

State first, rules second

The original evaluator selected one column — rules — and never asked whether the token was still alive. Redemption checks revoked_at, so this looked covered. It is not, and the gap is the one that matters most:

Redemption happens once. Messages happen forever. A holder who redeemed a token in March has a conversation, a holder JWT, and a live socket. Revoking the token in June sets revoked_at and changes nothing about that conversation, because nothing on the message path ever reads it. The owner presses the button that the entire product is built around, sees the token disappear from their list, and the messages keep arriving.

So the state check is not a rule among rules — it comes first, it is not optional, and it runs on every action rather than once at the door.

Evaluated on every message, and deliberately not cached

A query per message is real cost, and caching rules for even sixty seconds would remove most of it. It is rejected because ARCHITECTURE.md lists "revocation is immediate and enforced server-side" as one of four properties everything else follows from. A sixty-second cache makes revocation take up to sixty seconds — which is not immediate, and the difference between those two words is the product.

If the read cost ever matters, the answer is a faster read of the truth — a covering index, or the token row in Redis invalidated on write — never a timer that lets a stale answer stand.

ALL rules must pass

Rules are combined with AND, not OR. Each one the owner adds can only narrow access, never widen it, which means a user adding a rule can never accidentally grant something. It also means the engine can stop at the first failure — and that the order of evaluation is a free optimisation: the cheap in-memory checks run before the ones that hit the database.

When this breaks

The overnight window that allowed nothing

if (currentTime < rule.start_time || currentTime >= rule.end_time) deny();

Correct for 09:00–18:00 and wrong for every window that crosses midnight. "22:00 to 06:00" — an ordinary night-shift or do-not-disturb-inverted window — makes that condition true at every minute of the day, so the token is dead and the owner cannot see why. Windows need the wrap-around case handled explicitly.

A day that starts at 05:30

The daily counter used setUTCHours(0,0,0,0) while the time window used the owner's timezone. In Asia/Kolkata that is 05:30 local — so a holder who spent all ten of their messages at 9pm gets ten more at half past five the next morning, and "10 per day" quietly means up to 20 in one Indian day. Any per-day rule has to use the same day the user means.

Counting, then allowing

SELECT COUNT(*), compare, then insert. Two messages arriving together both count nine of ten, both pass, and eleven get through. It is the same shape as the max_uses race in B7.1 and the fix is the same shape too: make the database do the counting and the deciding in one statement, or take a row lock for the duration.

The comment in this lesson said "correctness matters more than speed here" directly above the racy version, which is worth noticing — believing you have chosen correctness is not the same as having it.

A rule type the server has never heard of

Deploys are not atomic. For a few minutes, a new client writing {"geo_fence": …} talks to old replicas that do not know what a geo-fence is. Skipping the unknown key means the restriction the owner just set is not enforced, silently, on a subset of requests — which is worse than an error, because nobody sees it.

The calls table does not exist

evaluateContactLimit queries calls, which no migration in this course creates — one of three tables the audit flags as queried-but-never-created. It is left as a known gap rather than invented here: it belongs to the B2 schema rewrite, and guessing at a shape now would give B2 something wrong to be consistent with.

What this costs you

DecisionWhat you pay
Evaluating on every action Two to three queries per message — conversation to token, token row, and a count for limits. At Token's scale that is nothing; it is also the first thing to show up in a slow trace, and the fix must be a faster read rather than a cached one.
No caching of rules You give up the easiest performance win in the system to keep revocation instant. Stated plainly so nobody adds a five-minute cache in a hurry and quietly breaks the product's central promise.
Denying on unknown rule types Deploy order now matters: the server must understand a rule type before any client can write it. Ship the server first, always — which is a release-process constraint, not a code one.
Rules as JSONB Flexible to add to, and the database cannot check any of it. Everything that would be a CHECK constraint on a real column becomes a Zod schema and a code review, and a malformed payload is only caught when someone tries to use the token.
Timezone-aware everything Every rule now needs a timezone, and the owner's timezone can change when they travel. The rule stores the timezone rather than reading the device's, so a user in London still has their tokens behave on Kolkata hours — which is right, and is the sort of thing that has to be explained in the UI.
