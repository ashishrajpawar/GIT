Token Generation & Redemption

B7 — Lesson 1 of 3 • ~45 min

Why this matters for Token

A token code like MERC-8GH2-KP4X is the single point of contact between a user and the outside world. If generation is predictable, an attacker can guess codes. If redemption skips validation, revoked tokens still let people in. This lesson builds the server-side generation with collision retry and the redemption endpoint that creates conversations — the two most critical paths in the entire system.

Generating Secure Token Codes

Token codes must be short enough to speak aloud, yet random enough to resist brute-force. We use Node's crypto.randomBytes — not Math.random() — because cryptographic randomness is essential.

This is the server-side twin of the issuer you built at the end of Module 01. Same alphabet, same rejection rule, same arithmetic — the only thing that changes is that the result now goes into Postgres. 

// api/src/engine/generate.ts
import crypto from 'crypto';
import { pool } from '../db';

// 31 characters: 36 alphanumerics minus 0, O, 1, I and L — the pairs that
// get misread when a code is spoken down a phone line or copied off a card.
const CHARSET = '23456789ABCDEFGHJKMNPQRSTUVWXYZ';
const CODE_LENGTH = 12;

// 256 / 31 = 8 remainder 8, so bytes 248-255 would land on the first eight
// characters a ninth time, making them 12.5% more likely than the other 23.
// Throw those bytes away and draw again.
const REJECT_AT = 248;

export function generateTokenCode(): string {
  let letters = '';

  while (letters.length < CODE_LENGTH) {
    // Draw in blocks rather than one byte at a time: a syscall per character
    // is a syscall you did not need.
    const bytes = crypto.randomBytes(CODE_LENGTH);
    for (const byte of bytes) {
      if (letters.length === CODE_LENGTH) break;
      if (byte >= REJECT_AT) continue;
      letters += CHARSET[byte % CHARSET.length];
    }
  }

  return letters.slice(0, 4) + '-' + letters.slice(4, 8) + '-' + letters.slice(8, 12);
}
The alphabet is not a style choice

31 characters, and the five that are missing stay missing. A code containing L is a code this system can never issue, so every validator in the app and the web page will reject it — and a generator that emits one produces tokens that fail at the moment someone tries to use them. It is the one constraint in this course that cannot be fixed after the fact: codes already handed out cannot be un-issued.

Storing it: hash to find, encrypt to show

The bare code never reaches the database. Two small helpers derive what does — the reasoning is in Why this way below, and in ADR-0007. 

// api/src/engine/codeStore.ts
import crypto from 'crypto';

const PEPPER = process.env.TOKEN_CODE_PEPPER!;   // 32+ random bytes, from the environment
const KEY = Buffer.from(process.env.TOKEN_CODE_KEY!, 'base64');  // 32 bytes

export function normaliseCode(raw: string): string {
  return String(raw ?? '').trim().toUpperCase();
}

// Deterministic on purpose: the same code must always give the same hash,
// or it could not be found by an indexed lookup.
export function hashCode(code: string): Buffer {
  return crypto.createHash('sha256').update(normaliseCode(code) + PEPPER).digest();
}

// Authenticated encryption, so a tampered column fails loudly instead of
// decrypting to nonsense. iv || authTag || ciphertext, all in one bytea.
export function encryptCode(code: string): Buffer {
  const iv = crypto.randomBytes(12);
  const cipher = crypto.createCipheriv('aes-256-gcm', KEY, iv);
  const enc = Buffer.concat([cipher.update(normaliseCode(code), 'utf8'), cipher.final()]);
  return Buffer.concat([iv, cipher.getAuthTag(), enc]);
}

export function decryptCode(stored: Buffer): string {
  const iv = stored.subarray(0, 12);
  const tag = stored.subarray(12, 28);
  const decipher = crypto.createDecipheriv('aes-256-gcm', KEY, iv);
  decipher.setAuthTag(tag);
  return decipher.update(stored.subarray(28)).toString('utf8') + decipher.final('utf8');
}

Collision Retry

Even with a large keyspace, collisions are theoretically possible. Rather than asking whether a code is taken and then inserting it — two round trips, and a race between them — let the database's UNIQUE constraint answer, and retry when it says no. 

const MAX_RETRIES = 5;

export async function insertTokenWithFreshCode(client, userId: number, opts): Promise<{ code: string; row: any }> {
  for (let attempt = 0; attempt < MAX_RETRIES; attempt++) {
    const code = generateTokenCode();
    try {
      const { rows } = await client.query(
        `INSERT INTO tokens (user_id, code_hash, code_enc, label, expires_at, max_uses, rules)
         VALUES ($1, $2, $3, $4, $5, $6, $7)
         RETURNING id, label, expires_at, max_uses, uses, created_at`,
        [userId, hashCode(code), encryptCode(code),
         opts.label ?? null, opts.expires_at ?? null, opts.max_uses ?? null, opts.rules ?? {}]
      );
      // The plaintext exists only here, in memory, on its way to the response.
      return { code, row: rows[0] };
    } catch (err: any) {
      if (err.code !== '23505') throw err;    // 23505 = unique_violation
      // Astronomically unlucky. Draw again.
    }
  }
  throw new Error('Could not generate an unused code after ' + MAX_RETRIES + ' attempts');
}

POST /tokens — Creating a Token

The authenticated user creates a token, optionally setting expiry, max uses, and access rules. 

// api/src/routes/tokens.ts
import { Router } from 'express';
import { authenticate } from '../middleware/auth';
import { insertTokenWithFreshCode } from '../engine/generate';
import { hashCode } from '../engine/codeStore';
import { pool } from '../db';

const router = Router();

router.post('/tokens', authenticate, async (req, res) => {
  const userId = req.user.id;
  const { label, expires_at, max_uses, rules } = req.body;

  const { code, row } = await insertTokenWithFreshCode(pool, userId, {
    label, expires_at, max_uses, rules
  });

  // The code travels back in this response and is never stored in readable
  // form. The database holds only the hash and the encrypted copy.
  res.status(201).json({ token: { ...row, code } });
});

export default router;

POST /tokens/:code/redeem — The Redemption Endpoint

A holder visits tokn.app/t/CODE, enters a display name, and redeems the token. The server must validate status, expiry, and use count before creating a conversation. 

router.post('/tokens/:code/redeem', async (req, res) => {
  const { code } = req.params;
  const { holder_name } = req.body;

  if (!holder_name || holder_name.trim().length === 0) {
    return res.status(400).json({ error: 'holder_name is required' });
  }

  // Look up by hash, never by the code itself.
  // NOTE: FOR UPDATE through pool.query does nothing — see "When this
  // breaks" below. The exercise solution shows the correct transaction.
  const { rows: tokenRows } = await pool.query(
    'SELECT * FROM tokens WHERE code_hash = $1 FOR UPDATE',
    [hashCode(code)]
  );

  if (tokenRows.length === 0) {
    return res.status(404).json({ error: 'Token not found' });
  }

  const token = tokenRows[0];

  // Validation checks
  if (token.status !== 'active') {
    return res.status(403).json({ error: 'Token is not active' });
  }

  if (token.expires_at && new Date(token.expires_at) < new Date()) {
    return res.status(403).json({ error: 'Token has expired' });
  }

  if (token.max_uses !== null) {
    const { rows: countRows } = await pool.query(
      'SELECT COUNT(*) as cnt FROM conversations WHERE token_id = $1',
      [token.id]
    );
    if (parseInt(countRows[0].cnt) >= token.max_uses) {
      return res.status(403).json({ error: 'Token has reached maximum uses' });
    }
  }

  // Create conversation and holder entry
  const { rows: convRows } = await pool.query(
    `INSERT INTO conversations (token_id, holder_name, created_at)
     VALUES ($1, $2, NOW())
     RETURNING id`,
    [token.id, holder_name.trim()]
  );

  // Issue a holder JWT (no user account — just a session)
  const holderJwt = signHolderToken({
    conversationId: convRows[0].id,
    tokenId: token.id,
    holderName: holder_name.trim()
  });

  res.status(201).json({
    conversation_id: convRows[0].id,
    holder_token: holderJwt
  });
});

The Holder JWT

Holders do not have user accounts. They receive a short-lived JWT scoped to a single conversation. This JWT lets them send messages through that one channel without knowing who is on the other end. 

import jwt from 'jsonwebtoken';

interface HolderPayload {
  conversationId: number;
  tokenId: number;
  holderName: string;
}

export function signHolderToken(payload: HolderPayload): string {
  return jwt.sign(
    { ...payload, role: 'holder' },
    process.env.JWT_SECRET!,
    { expiresIn: '7d' }
  );
}

export function verifyHolderToken(token: string): HolderPayload & { role: string } {
  return jwt.verify(token, process.env.JWT_SECRET!) as any;
}

Keyspace Analysis

Understanding the math behind the code format: 

// CHARSET has 31 characters, codes are 12 long
// 31^12 = 787,662,783,788,549,761  (~7.9 x 10^17)
//
// At a million guesses a second - far more than any server would answer -
// working through the whole space takes about 25,000 years.
//
// With 1 million active tokens, the chance a fresh code collides:
//   1,000,000 / 7.9e17 = 1.3e-12
// 5 retries turns "essentially never" into "handled".

Try it yourself — the bias, measured

The rejection rule is the part people accept without believing. This runs both versions over every byte value once and counts the characters.

Why this way (and what was rejected)

31 characters, not 32

A 32-character alphabet is genuinely tempting, and this lesson taught one until it was corrected. 256 divides by 32 exactly, so byte % 32 is unbiased with no rejection loop and no wasted draws — the code is shorter and the arithmetic is clean.

It was rejected because the only way to reach 32 is to put back one of the five characters that were removed for being misread. That trades a permanent, product-wide human-error cost against four lines of code. The rejection loop is the cheaper side of that trade by a wide margin.

The database's unique index, not the retry loop

A generator that checks for a collision before inserting looks careful. That check is a courtesy, not a guarantee: between the SELECT and the INSERT, another request can insert the same code. The window is tiny and the odds are 1.3 × 10-12, but "tiny window, astronomically unlikely" is how you end up with a bug you cannot reproduce.

The guarantee is UNIQUE on tokens.code. The retry loop exists to turn a constraint violation into a fresh code instead of a 500, so the correct shape is to let the insert fail and retry rather than to look before leaping: 

for (let attempt = 0; attempt < MAX_RETRIES; attempt++) {
  try {
    return await insertToken(generateTokenCode(), ...);
  } catch (err) {
    if (err.code !== '23505') throw err;   // 23505 = unique_violation
    // else: astronomically unlucky, or the code space is exhausted. Try again.
  }
}
throw new Error('Could not generate an unused code after ' + MAX_RETRIES + ' attempts');

Same number of round trips in the happy path — one instead of two — and it is correct under concurrency rather than nearly correct.

Holders get a JWT, not an account

The alternative was a lightweight guest account. It was rejected because an account is a record of a person, and the product's promise is that the holder never has to become one. A JWT scoped to a single conversation carries the authorisation and nothing else — there is no row to leak, no profile to correlate, and no account to delete later under DPDP.

The code is never stored as the code

A token code is not like a username. It is the entire authorisation — no password behind it, no account, no second factor. Whoever holds MERC-8GH2-KP4X can reach the person who issued it.

So storing it as text makes a copy of the database a set of live keys. Not hashed passwords somebody would have to crack — working capabilities, usable immediately. And the ways a copy escapes are ordinary rather than exotic: a backup file on a laptop, a snapshot in object storage with the wrong permissions, a pg_dump pasted into a support ticket, a staging environment restored from production and left open.

It also sits badly beside the decision that message bodies are encrypted so the server cannot read them. Encrypting the letters while keeping the front door keys in the same drawer is not a security posture.

Two derived columns, and never the bare code (ADR-0007):

CREATE TABLE tokens (
  id          bigserial PRIMARY KEY,
  code_hash   bytea UNIQUE NOT NULL,   -- SHA-256(normalised code || pepper)
  code_enc    bytea NOT NULL,          -- AES-256-GCM(normalised code)
  ...
);
  • Lookup normalises what was typed, hashes it with the pepper, and matches code_hash. One indexed equality probe — exactly the same cost as before.
  • Display decrypts code_enc, and only when the owner asks to see that one token. Never for a whole list by default.
  • The pepper and the encryption key live in the container's environment, supplied by Coolify. Never in a migration, a seed file, or the repo.
Why SHA-256 and not bcrypt or argon2

Those are the right tools for passwords and the wrong ones here, because they salt every hash randomly. A random salt means two hashes of the same code do not match — so you could not find a row by its code without reading every row in the table and testing each one.

The pepper does the job the salt would: an attacker holding only the database cannot test guesses without it. And the slow-hashing that bcrypt exists to provide buys nothing against a code drawn from 3112 possibilities — that is not a human-chosen password, and it is not brute-forceable in the first place.

The option not taken was hashing alone, with no encrypted copy. It is the simpler and slightly stronger choice, and it was rejected on product grounds rather than security ones: a one-way hash cannot be reversed, so the code could never be shown again — no re-displaying a QR for a second person, no reading it out over the phone, and a lost code recoverable only by revoking and issuing a new one. Hash-only remains correct for anything nobody ever needs to see twice, which is why refresh tokens will use it.

The payoff is the one endpoint hash-only could not have. Note that it returns a single token, asked for by id, by its owner — never a list with every code decrypted into it: 

// "Show me that code again" — one token, its owner, on request
router.get('/tokens/:id/code', authenticate, async (req, res) => {
  const { rows } = await pool.query(
    'SELECT code_enc FROM tokens WHERE id = $1 AND user_id = $2',
    [req.params.id, req.user.id]
  );
  if (rows.length === 0) return res.status(404).json({ error: 'Not found' });

  // Turning stored data back into a live capability is worth recording.
  await logCodeReveal(req.user.id, req.params.id);

  res.json({ code: decryptCode(rows[0].code_enc) });
});

What it costs, stated plainly: the pepper and the key become critical operational state. Lose them and every stored code is unreadable and unmatchable — every token in the system is dead. They belong in the disaster-recovery plan, backed up somewhere the database backups are not. And rotating the pepper rewrites every row, which is possible only because the plaintext stays recoverable; under hash-only it would be impossible.

When this breaks

FOR UPDATE outside a transaction does nothing

This is the trap in the redemption code above, and it is invisible in testing because it only shows under concurrency: 

// WRONG - the lock is taken and released immediately
const { rows } = await pool.query('SELECT * FROM tokens WHERE code_hash = $1 FOR UPDATE', [hashCode(code)]);

A row lock lives for the length of a transaction. pool.query runs a single statement in its own implicit transaction, which commits the moment the statement finishes — so the lock is gone before you have read token.max_uses, let alone acted on it. Worse, the next query goes to a different connection from the pool, so even an explicit BEGIN sent through pool.query would not apply.

The exercise solution gets this right: pool.connect() to pin one client, BEGIN, everything on that client, then COMMIT and release(). Use it as the model, not the snippet above.

Two redemptions of the last remaining use

max_uses is checked by counting conversations and comparing. With two requests in flight, both can count 2 of 3, both pass, and both insert — three uses become four. The count-then-insert pattern has exactly the same shape as the collision check, and unlike the collision it is likely: a token posted publicly gets simultaneous redemptions as a matter of course.

The row lock fixes it, provided it is really held. The alternative that needs no lock is to make the database do the arithmetic in one statement — a counter on the token row, incremented conditionally: 

UPDATE tokens
   SET uses = uses + 1
 WHERE code_hash = $1
   AND revoked_at IS NULL
   AND (expires_at IS NULL OR expires_at > now())
   AND (max_uses  IS NULL OR uses < max_uses)
RETURNING id, user_id;

Zero rows back means denied; one row means the use is already counted. It is atomic because a single UPDATE takes its own row lock, and it cannot be raced.

Two clocks

new Date(token.expires_at) < new Date() compares a timestamp from Postgres against the clock of whichever API container happened to serve the request. Those are different machines. A container with a clock a few seconds fast expires tokens early; one running slow honours them late, which is the direction that actually matters. Use now() in the query and there is one clock, which is also the clock the row was written by.

The holder JWT outlives the token

A holder JWT is valid for seven days and is verified by signature alone. Revoking the token does not invalidate it — nothing checks the token's state once a session exists. So "revoke" means "no new redemptions", not "this person is gone", which is not what the button says. B7.3 is where that gets resolved; the important part here is knowing you have created the problem.

What this costs you

DecisionWhat you pay
Rejection sampling About 3% of random bytes are discarded. Drawing in blocks of 12 makes it one syscall per code in almost every case, so the real cost is four lines of code and a paragraph of explanation.
UNIQUE index on a random code Random keys have no locality, so every insert lands in a different part of the B-tree. At a few million rows that is measurably more write amplification than an ordered key — the correctness is worth it, but it is not free, and it is a reason not to index anything else by code.
Row lock on redemption Redemptions of the same token serialise. Fine at Token's scale, and a reason never to do slow work — a network call, an email, image processing — inside that transaction. The conditional UPDATE above avoids the lock entirely.
Codes stored in plain text A database dump is a set of working tokens. Backups inherit the same property, which makes backup access a security boundary rather than an ops detail.
12 characters The human cost of the whole design. Long enough to be unguessable, short enough to read aloud — and that is the ceiling. If the keyspace ever needs to grow, the code gets longer and every printed card, QR label and support script changes with it.
