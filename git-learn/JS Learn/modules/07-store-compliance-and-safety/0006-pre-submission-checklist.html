Store Compliance · Lesson 6

Pre-Submission Checklist & Demo Accounts

Demo accounts · Reviewer notes · IPv6 testing · Airplane mode · Final walkthrough ~45 min Hands-on
Why this matters for your WhatsApp clone

You've built everything — block/report, moderation, security, consent, data export. Now it's time to submit. But most first-time submissions fail on preventable issues: the demo account doesn't work, reviewers can't test calls because they only have one device, or the app crashes on airplane mode. This lesson walks through every check you must pass before hitting "Submit for Review." Think of it as a pre-flight checklist — skip one item and the plane doesn't fly.

1. Creating demo accounts for store reviewers

Both Apple and Google require demo credentials for apps that need login. For a messaging app, you need two accounts with an existing conversation between them — reviewers can't test messaging with one account.

Step 1: Create two test accounts

// Create these accounts in your live Firebase project
// (NOT in the emulator — reviewers test on the production build)

Account 1 (for the reviewer to log in as):
  Email:    reviewer@yourapp.com
  Password: ReviewTest2026!
  Name:     "App Reviewer"

Account 2 (the conversation partner):
  Email:    demo@yourapp.com
  Password: DemoAccount2026!
  Name:     "Priya Sharma"

Step 2: Pre-populate a conversation

Log into both accounts and create a realistic chat history. Include:

  • 10-15 text messages between the two accounts (mix of short and long)
  • 1-2 images sent (proves image sending works)
  • 1 voice message (proves audio works)
  • A group chat with both accounts + a third dummy account
  • One contact to block/report — create a third account "Spam User" so reviewers can test block/report without affecting the main demo chat

Step 3: Verify both accounts work

// Test checklist for demo accounts:
✓ Can log in with reviewer@yourapp.com on a fresh install
✓ Chat list shows existing conversations immediately
✓ Can open the chat with "Priya Sharma" and see message history
✓ Can send a new message and it appears instantly
✓ Can send an image
✓ Can make a voice call to the other account
✓ Can block "Spam User" from the chat menu
✓ Can report "Spam User"
✓ Can access Settings → Download My Data
✓ Can access Settings → Delete Account (but DON'T actually delete)
✓ Password reset works for reviewer@yourapp.com

2. Writing Apple reviewer notes

Apple's "App Review Information" section has a notes field. This is your chance to explain how to test features that aren't obvious. Be specific and helpful:

DEMO ACCOUNT CREDENTIALS:

Account 1 (log in with this):
  Email: reviewer@yourapp.com
  Password: ReviewTest2026!

Account 2 (already has a conversation with Account 1):
  Email: demo@yourapp.com
  Password: DemoAccount2026!

HOW TO TEST KEY FEATURES:

1. MESSAGING:
   - Log in with Account 1
   - You'll see a chat with "Priya Sharma" — tap to open
   - Send a message — it appears instantly
   - To test with two devices: log in as Account 2 on a second device

2. VOICE/VIDEO CALLS:
   - Calls require two devices signed into different accounts
   - From Account 1, open the chat with "Priya Sharma" and tap the phone icon
   - If testing on one device: the call UI will show and timeout after 30s

3. BLOCK & REPORT:
   - Open the chat with "Spam User"
   - Tap the ⋮ menu → "Block" or "Report"
   - Blocked users can be unblocked in Settings → Blocked Contacts

4. DATA EXPORT:
   - Settings → Download My Data
   - Generates a JSON file with all account data

5. ACCOUNT DELETION:
   - Settings → Account Security → Delete Account
   - Requires password re-entry for confirmation
   - (Please do not delete the demo account)

BACKGROUND MODES:
   - voip: Used for incoming call notifications via CallKit/PushKit
   - audio: Voice message playback continues in background
   - remote-notification: Push notifications for new messages
   - fetch: Periodic sync of unread message count for badge

PUSH NOTIFICATIONS:
   - Send a message from Account 2 to Account 1 while Account 1
     is in the background — a push notification will appear

WEBRTC / CALLS:
   - Uses react-native-webrtc (peer-to-peer, no third-party SDK)
   - STUN: Google free servers
   - TURN: coturn self-hosted (IPv4 + IPv6 supported)
   - iOS uses CallKit for incoming call UI

3. Verifying IPv6 compatibility

Apple's review lab uses an IPv6-only network. If any part of your app requires IPv4, it will fail during review. Here's what to check:

What's automatically IPv6-compatible:

  • Firebase services — all Google infrastructure supports IPv6
  • Expo push notifications — Expo's servers are IPv6-ready
  • React Native networking — uses the OS network stack (IPv6-safe)

What might NOT be IPv6-compatible:

  • Self-hosted TURN server (coturn) — if your server only has an IPv4 address, calls will fail on Apple's review network
  • Custom API endpoints — if you point to an IPv4-only server

How to make coturn IPv6-compatible:

# On your coturn server, ensure it listens on both IPv4 and IPv6:
# turnserver.conf

listening-ip=0.0.0.0        # IPv4
listening-ip=::             # IPv6

relay-ip=YOUR_IPv4_ADDRESS
relay-ip=YOUR_IPv6_ADDRESS

# Verify your server has an AAAA DNS record:
dig AAAA turn.yourapp.com

# Should return something like:
# turn.yourapp.com.  300  IN  AAAA  2001:db8::1

If your hosting provider doesn't offer IPv6 (rare but possible), use a provider that does: DigitalOcean, Vultr, AWS, Google Cloud, and Hetzner all provide IPv6 by default.

Testing IPv6 on your Mac (if you have one):

# Create a NAT64 network to simulate Apple's review environment:
# System Preferences → Sharing → Internet Sharing
# Share: Wi-Fi, To: Thunderbolt Bridge
# Check "Create NAT64 Network"
# Connect your test iPhone to this shared network
# Now test your app — if calls work, you're IPv6-safe

No Mac? Verify your TURN server's AAAA record exists and trust that Firebase/Expo handles the rest. Most rejection issues are the TURN server, not the app itself.

4. Testing on airplane mode

Apple tests what happens when the network drops. Your app must not crash or show a blank screen. Test these scenarios:

Scenario Expected behaviour Common failure
Launch app in airplane mode Shows cached data or "No internet connection" banner Blank screen / infinite spinner
Send message with no network Message appears locally with clock icon (pending) App crashes / error alert pops up
Open chat list with no network Shows cached chat list (Firestore offline persistence) Empty list / crash
Try to make a call with no network Shows "No internet connection" alert App hangs / crash
Network returns after airplane mode Pending messages send automatically, real-time updates resume Must force-quit and reopen

Quick fix for the most common crash — Firestore offline persistence:

// In your Firebase initialization file, enable offline persistence:
import { initializeFirestore, persistentLocalCache, persistentMultipleTabManager } from 'firebase/firestore';

const db = initializeFirestore(app, {
  localCache: persistentLocalCache({
    tabManager: persistentMultipleTabManager(),
  }),
});

// This ensures Firestore serves cached data when offline
// and queues writes to sync when connectivity returns

With persistence enabled, your chat list and messages will show even without network. New messages queue locally and send when the connection returns.

5. Verifying all background modes

In Module 5 and 6, you declared these UIBackgroundModes in your app.json:

"UIBackgroundModes": ["voip", "audio", "fetch", "remote-notification"]

Apple rejects apps that declare background modes they don't use. Verify each one is actually exercised:

Mode What uses it How to verify
voip PushKit/CallKit for incoming calls Receive a call while app is backgrounded → CallKit UI appears
audio Voice message playback, active call audio Play a voice message → switch to another app → audio continues
fetch Background badge count update Receive a message while app is killed → badge count updates
remote-notification Silent push + visible push notifications Receive a push notification while app is backgrounded

If you don't use fetch (you haven't implemented background badge sync), remove it from the array. Declaring unused modes is a rejection reason.

6. Testing CallKit (iOS) one more time

The #1 call-related rejection: your app shows a custom incoming call screen instead of the native CallKit UI. Verify:

  • When a call comes in while the app is in the background → the native iOS call screen appears (same look as a regular phone call)
  • When a call comes in while the app is killed/terminated → the native iOS call screen still appears (VoIP push wakes the app)
  • When the user answers via CallKit → your app opens and connects the call
  • When the user declines via CallKit → the caller sees "call declined"

If any of these fail, revisit Module 5 Lesson 8 (Incoming Calls on iOS).

9. Common first-submission rejections and how to avoid them

Rejection reason How to prevent
Demo account doesn't work Test credentials on a fresh install 24 hours before submitting
No way to test messaging (need 2 users) Pre-populate a conversation; explain in reviewer notes
VoIP app doesn't use CallKit (Guideline 4.2) Verify incoming calls show native iOS call UI
Permission purpose too vague "AppName needs camera to take photos for chat messages" not "Camera access needed"
No account deletion Settings → Delete Account (built in Lesson 3)
No block/report (Guideline 1.2) Built in Lesson 1 — verify from reviewer notes
App crashes on launch Test production build on a real device (not just dev build)
Data Safety form doesn't match actual behaviour Audit: what you collect must match what you declared
Guideline 4.3 Spam — name too similar to WhatsApp Don't name it "WhatsApp Clone" — use your own brand name

10. The 24-hour pre-submission ritual

Do this exactly 24 hours before you hit "Submit":

24 Hours Before Submission:

1. BUILD FRESH
   eas build --platform ios --profile production
   eas build --platform android --profile production

2. TEST ON REAL DEVICE
   - Install the production build (not dev client)
   - Complete the full user journey (Section 7)
   - Test on airplane mode for 2 minutes
   - Test push notifications (background + killed)

3. VERIFY DEMO ACCOUNTS
   - Log in as reviewer@yourapp.com on the production build
   - Verify chat history is visible
   - Send a test message — confirm it arrives
   - Delete the test message so reviewer sees clean history

4. CHECK EXTERNAL SERVICES
   - Privacy policy URL loads in a browser
   - Terms of Service URL loads in a browser
   - TURN server responds: curl -v turn.yourapp.com:3478
   - Push notifications arrive within 5 seconds

5. TAKE SCREENSHOTS
   - Use the production build for screenshots (not dev)
   - Capture: chat list, message thread, call screen, settings
   - Both 6.7" and 5.5" sizes for Apple

6. FINAL REVIEW OF STORE LISTING
   - Read your description out loud — any typos?
   - Verify all URLs are correct and not expired
   - Check age rating answers match your actual app

11. What happens after submission

Apple (1-3 days, sometimes longer)

  • In Review — a human reviewer is testing your app
  • Approved — congratulations! Release manually or automatically
  • Rejected — check Resolution Centre for the specific guideline. Fix it, rebuild, resubmit

Google (1-7 days for first submission)

  • Under Review — automated + manual review in progress
  • Approved — app appears on Play Store within hours
  • Rejected — check Policy Status for violation details. Fix and resubmit

If rejected, don't panic. Read the rejection reason carefully. It's always a specific guideline with a fix. Most rejections are resolved in one resubmission. Reply in the Resolution Centre (Apple) or Policy Status (Google) if the rejection seems wrong.

12. Keeping demo accounts alive

A common pitfall: demo accounts stop working after some time. Prevent this:

// Issues that can break demo accounts:
// 1. Firebase Auth disables accounts after 1 year of inactivity
// 2. You accidentally delete them during testing
// 3. Password gets changed
// 4. Chat history gets deleted

// Prevention:
// - Log into demo accounts once per month (set a calendar reminder)
// - Never use demo accounts for actual development/testing
// - Document the credentials in a secure place (not in code)
// - If your app has message expiry, exclude demo accounts

// If Apple resubmission is needed and demo account broke:
// Just create new demo accounts and update the reviewer notes

13. Full example — automated demo account setup script

Run this once to set up your demo environment. You can run it again if accounts need to be recreated:

// setupDemoAccounts.js — run with: node setupDemoAccounts.js
// (Requires firebase-admin, run from your local machine, not the app)

const admin = require('firebase-admin');
const serviceAccount = require('./google-service-account.json');

admin.initializeApp({
  credential: admin.credential.cert(serviceAccount),
});

const db = admin.firestore();
const auth = admin.auth();

async function setupDemoAccounts() {
  console.log('Creating demo accounts...');

  // Create Account 1 (Reviewer)
  let user1;
  try {
    user1 = await auth.createUser({
      email: 'reviewer@yourapp.com',
      password: 'ReviewTest2026!',
      displayName: 'App Reviewer',
    });
  } catch (e) {
    // Account exists — get it
    user1 = await auth.getUserByEmail('reviewer@yourapp.com');
  }

  // Create Account 2 (Demo partner)
  let user2;
  try {
    user2 = await auth.createUser({
      email: 'demo@yourapp.com',
      password: 'DemoAccount2026!',
      displayName: 'Priya Sharma',
    });
  } catch (e) {
    user2 = await auth.getUserByEmail('demo@yourapp.com');
  }

  // Create Account 3 (Spam user for block/report testing)
  let user3;
  try {
    user3 = await auth.createUser({
      email: 'spamuser@yourapp.com',
      password: 'SpamTest2026!',
      displayName: 'Spam User',
    });
  } catch (e) {
    user3 = await auth.getUserByEmail('spamuser@yourapp.com');
  }

  console.log('Creating user profiles...');

  // Write Firestore profiles
  const profiles = [
    { uid: user1.uid, displayName: 'App Reviewer', email: 'reviewer@yourapp.com' },
    { uid: user2.uid, displayName: 'Priya Sharma', email: 'demo@yourapp.com' },
    { uid: user3.uid, displayName: 'Spam User', email: 'spamuser@yourapp.com' },
  ];

  for (const p of profiles) {
    await db.doc(`users/${p.uid}`).set({
      uid: p.uid,
      displayName: p.displayName,
      email: p.email,
      about: 'Hey there! I am using WhatsApp',
      online: false,
      lastSeen: admin.firestore.FieldValue.serverTimestamp(),
      createdAt: admin.firestore.FieldValue.serverTimestamp(),
      blockedUsers: [],
      reportCount: 0,
      isBanned: false,
      isHidden: false,
      consent: { essential: true, analytics: true, crashReports: true, consentVersion: '1.0', consentDate: new Date().toISOString() },
    }, { merge: true });
  }

  console.log('Creating demo chat...');

  // Create a 1:1 chat between reviewer and Priya
  const chatRef = db.collection('chats').doc('demo_chat_review');
  await chatRef.set({
    members: [user1.uid, user2.uid],
    memberNames: { [user1.uid]: 'App Reviewer', [user2.uid]: 'Priya Sharma' },
    isGroup: false,
    lastMessage: 'See you tomorrow at the cafe!',
    lastMessageAt: admin.firestore.FieldValue.serverTimestamp(),
    unreadCounts: { [user1.uid]: 1, [user2.uid]: 0 },
  });

  // Add messages
  const messages = [
    { senderId: user2.uid, text: 'Hi! Welcome to the app 👋', minutesAgo: 60 },
    { senderId: user1.uid, text: 'Hey Priya! Thanks, this is great.', minutesAgo: 58 },
    { senderId: user2.uid, text: 'Have you tried sending an image yet?', minutesAgo: 55 },
    { senderId: user1.uid, text: 'Not yet, let me try now...', minutesAgo: 53 },
    { senderId: user2.uid, text: 'The voice messages work too! Hold the mic button.', minutesAgo: 45 },
    { senderId: user1.uid, text: 'This is awesome. The messages appear instantly.', minutesAgo: 30 },
    { senderId: user2.uid, text: 'Yes! It uses real-time listeners.', minutesAgo: 28 },
    { senderId: user2.uid, text: 'Want to try a voice call?', minutesAgo: 15 },
    { senderId: user1.uid, text: 'Sure, let me finish this first.', minutesAgo: 10 },
    { senderId: user2.uid, text: 'See you tomorrow at the cafe!', minutesAgo: 5 },
  ];

  for (const msg of messages) {
    const createdAt = new Date(Date.now() - msg.minutesAgo * 60 * 1000);
    await chatRef.collection('messages').add({
      senderId: msg.senderId,
      text: msg.text,
      createdAt: admin.firestore.Timestamp.fromDate(createdAt),
      read: true,
    });
  }

  // Create spam chat (for block/report testing)
  const spamChatRef = db.collection('chats').doc('demo_chat_spam');
  await spamChatRef.set({
    members: [user1.uid, user3.uid],
    memberNames: { [user1.uid]: 'App Reviewer', [user3.uid]: 'Spam User' },
    isGroup: false,
    lastMessage: 'BUY CHEAP WATCHES NOW!!!',
    lastMessageAt: admin.firestore.FieldValue.serverTimestamp(),
    unreadCounts: { [user1.uid]: 3, [user3.uid]: 0 },
  });

  await spamChatRef.collection('messages').add({
    senderId: user3.uid,
    text: 'BUY CHEAP WATCHES NOW!!! Click here: spam-link.com',
    createdAt: admin.firestore.FieldValue.serverTimestamp(),
    read: false,
  });
  await spamChatRef.collection('messages').add({
    senderId: user3.uid,
    text: 'AMAZING DEALS!!! 90% OFF!!!',
    createdAt: admin.firestore.FieldValue.serverTimestamp(),
    read: false,
  });
  await spamChatRef.collection('messages').add({
    senderId: user3.uid,
    text: 'LAST CHANCE TO BUY!!!',
    createdAt: admin.firestore.FieldValue.serverTimestamp(),
    read: false,
  });

  console.log('✅ Demo accounts ready!');
  console.log('');
  console.log('Account 1: reviewer@yourapp.com / ReviewTest2026!');
  console.log('Account 2: demo@yourapp.com / DemoAccount2026!');
  console.log('Account 3: spamuser@yourapp.com / SpamTest2026!');
  console.log('');
  console.log('Chat history created between Account 1 and 2.');
  console.log('Spam messages created from Account 3 (for block/report testing).');
}

setupDemoAccounts().catch(console.error);

If you've completed every item in the checklist (Section 8), verified both demo accounts work on a fresh production build, and tested on airplane mode — you are ready.

Submit with confidence. The worst that happens is a rejection with a specific reason you can fix. Most indie messaging apps that follow this module pass on their first or second attempt.
