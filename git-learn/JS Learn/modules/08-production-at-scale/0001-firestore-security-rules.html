Production at Scale · Lesson 1

Firestore Security Rules

Field validation · Rate limiting · Storage rules · Emulator testing · Deployment ~60 min Hands-on
Why this matters for your WhatsApp clone

Right now, anyone with your Firebase config (which is in your app bundle — visible to anyone) could write anything to your database: fake messages from other users, 10MB text fields, messages at 100/second to spam a chat. Firestore Security Rules are the server-side bouncer — they run on Google's servers and reject bad requests before they touch your data. WhatsApp doesn't let you send messages as someone else, and neither should your app.

1. How security rules work

Security rules are a file (firestore.rules) that you deploy to Firebase. Every read or write from your app goes through these rules on the server. If the rule says deny, the request fails — no matter what the client code says.

// firestore.rules — the basic structure
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // This matches a specific collection
    match /messages/{messageId} {
      allow read: if request.auth != null;   // logged in?
      allow create: if request.auth != null; // logged in?
    }
  }
}

Key concepts

TermWhat it means
request.authThe user making the request (null if not logged in)
request.auth.uidTheir Firebase Auth user ID
request.resource.dataThe data being written (the incoming document)
resource.dataThe data already in the database (before this write)
get() / exists()Read another document during rule evaluation

Important: Rules are NOT filters. If you write allow read: if resource.data.senderId == request.auth.uid, it doesn't filter results — it rejects the entire query unless Firestore can guarantee every document in the result matches.

2. Protecting the users collection

Your users collection has profiles (name, phone, avatar URL). Without rules, anyone could change anyone's name or read all phone numbers.

match /users/{userId} {
  // Anyone logged in can read profiles (for chat list, contact search)
  allow read: if request.auth != null;

  // Only the owner can create their own profile
  allow create: if request.auth.uid == userId
    && request.resource.data.keys().hasAll(['name', 'createdAt'])
    && request.resource.data.name is string
    && request.resource.data.name.size() >= 1
    && request.resource.data.name.size() <= 50
    && request.resource.data.createdAt == request.time;

  // Only the owner can update, and they can't change createdAt or uid
  allow update: if request.auth.uid == userId
    && !request.resource.data.diff(resource.data).affectedKeys()
        .hasAny(['createdAt', 'uid'])
    && request.resource.data.name is string
    && request.resource.data.name.size() >= 1
    && request.resource.data.name.size() <= 50;

  // Nobody can delete profiles (use a 'disabled' field instead)
  allow delete: if false;
}

What this prevents

  • Priya can't change Rahul's name to something offensive
  • Nobody can create a profile with a 10MB name field
  • Nobody can backdate their createdAt timestamp
  • Profiles can never be deleted (avoiding orphaned references)

3. Securing chats and messages

Messages need the strictest rules — they're the core of a messaging app and the biggest abuse vector.

match /chats/{chatId} {
  // Only chat participants can read the chat document
  allow read: if request.auth.uid in resource.data.participants;

  // Chat creation: you must be in the participants list
  allow create: if request.auth.uid in request.resource.data.participants
    && request.resource.data.participants.size() >= 2
    && request.resource.data.participants.size() <= 256;

  // Updates (last message preview, unread count)
  allow update: if request.auth.uid in resource.data.participants;

  allow delete: if false;

  // Messages sub-collection
  match /messages/{messageId} {
    // Only participants of the parent chat can read messages
    allow read: if request.auth.uid in
      get(/databases/$(database)/documents/chats/$(chatId)).data.participants;

    // Create: sender must be themselves, text must be valid
    allow create: if request.auth.uid in
        get(/databases/$(database)/documents/chats/$(chatId)).data.participants
      && request.resource.data.senderId == request.auth.uid
      && request.resource.data.text is string
      && request.resource.data.text.size() >= 1
      && request.resource.data.text.size() <= 4096
      && request.resource.data.createdAt == request.time;

    // Only sender can delete their own messages
    allow delete: if resource.data.senderId == request.auth.uid;

    // No editing messages (WhatsApp doesn't allow it for regular users)
    allow update: if false;
  }
}

What this prevents

  • Nobody can read chats they're not part of
  • Nobody can send a message pretending to be someone else (senderId == request.auth.uid)
  • Messages can't exceed 4KB (prevents database abuse)
  • Timestamps are server-enforced (no backdating messages)
  • Only the sender can delete their own messages

4. Rate limiting writes

Without rate limits, a malicious user could send 1,000 messages per second and flood a chat. Firestore rules can enforce a cooldown using timestamps.

match /chats/{chatId}/messages/{messageId} {
  allow create: if request.auth.uid in
      get(/databases/$(database)/documents/chats/$(chatId)).data.participants
    && request.resource.data.senderId == request.auth.uid
    && request.resource.data.text is string
    && request.resource.data.text.size() >= 1
    && request.resource.data.text.size() <= 4096
    && request.resource.data.createdAt == request.time
    // Rate limit: check user's last write timestamp
    && (!exists(/databases/$(database)/documents/rateLimits/$(request.auth.uid))
        || request.time > get(/databases/$(database)/documents/rateLimits/$(request.auth.uid)).data.lastWrite + duration.value(1, 's'));
}

How the rate limit works

  1. When a user sends a message, your app also writes to rateLimits/{userId} with lastWrite: serverTimestamp()
  2. The rule checks: has 1 second passed since their last write?
  3. If not, the write is rejected — the user has to wait
// In your React Native code — update the rate limit doc on each send
import { doc, setDoc, serverTimestamp } from 'firebase/firestore';

async function sendMessage(chatId, text) {
  const userId = auth.currentUser.uid;
  const batch = writeBatch(db);

  // 1. Add the message
  const msgRef = doc(collection(db, 'chats', chatId, 'messages'));
  batch.set(msgRef, {
    senderId: userId,
    text: text.trim(),
    createdAt: serverTimestamp(),
  });

  // 2. Update rate limit tracker
  const rateLimitRef = doc(db, 'rateLimits', userId);
  batch.set(rateLimitRef, { lastWrite: serverTimestamp() });

  await batch.commit(); // Both writes happen atomically
}
// Rate limit document rules
match /rateLimits/{userId} {
  // Only the owner can read/write their own rate limit
  allow read, write: if request.auth.uid == userId;
}

5. Firebase Storage rules

Storage rules protect uploaded files (profile photos, image messages, voice notes). Without them, anyone could upload a 500MB file and blow up your bill.

// storage.rules
rules_version = '2';
service firebase.storage {
  match /b/{bucket}/o {

    // Profile photos: max 5MB, images only
    match /profilePhotos/{userId}/{fileName} {
      allow read: if request.auth != null;
      allow write: if request.auth.uid == userId
        && request.resource.size < 5 * 1024 * 1024  // 5MB
        && request.resource.contentType.matches('image/.*');
    }

    // Chat images: max 10MB, images only
    match /chatImages/{chatId}/{fileName} {
      allow read: if request.auth != null;
      allow write: if request.auth != null
        && request.resource.size < 10 * 1024 * 1024  // 10MB
        && request.resource.contentType.matches('image/.*');
    }

    // Voice notes: max 20MB, audio only
    match /voiceNotes/{chatId}/{fileName} {
      allow read: if request.auth != null;
      allow write: if request.auth != null
        && request.resource.size < 20 * 1024 * 1024  // 20MB
        && request.resource.contentType.matches('audio/.*');
    }

    // Block everything else
    match /{allPaths=**} {
      allow read, write: if false;
    }
  }
}

What this prevents

  • Uploading executables, scripts, or any non-media file
  • Uploading 500MB files that explode your Firebase bill
  • Uploading profile photos to someone else's path
  • Any access to paths you haven't explicitly allowed

6. Testing rules with the Firebase Emulator

Never deploy rules without testing them first. The Firebase Emulator lets you test rules locally — no real data at risk.

Step 1: Install and start the emulator

// In your project terminal
npm install -g firebase-tools
firebase init emulators   // Select Firestore + Storage
firebase emulators:start

Step 2: Write rule tests

// tests/firestore.rules.test.js
const { initializeTestEnvironment, assertSucceeds, assertFails }
  = require('@firebase/rules-unit-testing');

let testEnv;

beforeAll(async () => {
  testEnv = await initializeTestEnvironment({
    projectId: 'your-whatsapp-clone',
    firestore: { rules: fs.readFileSync('firestore.rules', 'utf8') },
  });
});

afterAll(async () => {
  await testEnv.cleanup();
});

test('logged-in user can read their own chat', async () => {
  const priyaDb = testEnv.authenticatedContext('priya123').firestore();

  // First, set up the chat document as admin
  await testEnv.withSecurityRulesDisabled(async (context) => {
    await context.firestore().doc('chats/chat1').set({
      participants: ['priya123', 'rahul456'],
      lastMessage: 'Hello!',
    });
  });

  // Now test: Priya should be able to read this chat
  await assertSucceeds(priyaDb.doc('chats/chat1').get());
});

test('user cannot read a chat they are not part of', async () => {
  const strangerDb = testEnv.authenticatedContext('stranger789').firestore();

  await assertFails(strangerDb.doc('chats/chat1').get());
});

test('user cannot send message as someone else', async () => {
  const priyaDb = testEnv.authenticatedContext('priya123').firestore();

  await assertFails(
    priyaDb.collection('chats/chat1/messages').add({
      senderId: 'rahul456',  // Priya pretending to be Rahul!
      text: 'Hacked message',
      createdAt: serverTimestamp(),
    })
  );
});

test('message text cannot exceed 4096 characters', async () => {
  const priyaDb = testEnv.authenticatedContext('priya123').firestore();
  const longText = 'A'.repeat(4097);

  await assertFails(
    priyaDb.collection('chats/chat1/messages').add({
      senderId: 'priya123',
      text: longText,
      createdAt: serverTimestamp(),
    })
  );
});

Step 3: Run the tests

// Run with the emulator
firebase emulators:exec "npx jest tests/firestore.rules.test.js"

7. The complete firestore.rules file

Here's the full rules file for your WhatsApp clone, combining everything above:

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // ─── Helper functions ─────────────────────
    function isLoggedIn() {
      return request.auth != null;
    }

    function isOwner(userId) {
      return request.auth.uid == userId;
    }

    function isParticipant(chatId) {
      return request.auth.uid in
        get(/databases/$(database)/documents/chats/$(chatId)).data.participants;
    }

    // ─── Users ────────────────────────────────
    match /users/{userId} {
      allow read: if isLoggedIn();
      allow create: if isOwner(userId)
        && request.resource.data.keys().hasAll(['name', 'createdAt'])
        && request.resource.data.name is string
        && request.resource.data.name.size() >= 1
        && request.resource.data.name.size() <= 50
        && request.resource.data.createdAt == request.time;
      allow update: if isOwner(userId)
        && !request.resource.data.diff(resource.data).affectedKeys()
            .hasAny(['createdAt', 'uid'])
        && request.resource.data.name is string
        && request.resource.data.name.size() <= 50;
      allow delete: if false;
    }

    // ─── Chats ────────────────────────────────
    match /chats/{chatId} {
      allow read: if isLoggedIn()
        && request.auth.uid in resource.data.participants;
      allow create: if isLoggedIn()
        && request.auth.uid in request.resource.data.participants
        && request.resource.data.participants.size() >= 2
        && request.resource.data.participants.size() <= 256;
      allow update: if isLoggedIn()
        && request.auth.uid in resource.data.participants;
      allow delete: if false;

      // Messages sub-collection
      match /messages/{messageId} {
        allow read: if isParticipant(chatId);
        allow create: if isParticipant(chatId)
          && request.resource.data.senderId == request.auth.uid
          && request.resource.data.text is string
          && request.resource.data.text.size() >= 1
          && request.resource.data.text.size() <= 4096
          && request.resource.data.createdAt == request.time;
        allow delete: if resource.data.senderId == request.auth.uid;
        allow update: if false;
      }
    }

    // ─── Rate Limits ──────────────────────────
    match /rateLimits/{userId} {
      allow read, write: if isOwner(userId);
    }

    // ─── Reports (from Module 7) ─────────────
    match /reports/{reportId} {
      allow create: if isLoggedIn()
        && request.resource.data.reporterId == request.auth.uid;
      allow read, update, delete: if false; // Admin-only via Cloud Functions
    }

    // ─── Block everything else ────────────────
    match /{document=**} {
      allow read, write: if false;
    }
  }
}

8. Deploying rules safely

Step 1: Deploy to Firebase

// Deploy Firestore rules only (not functions, hosting, etc.)
firebase deploy --only firestore:rules

// Deploy Storage rules
firebase deploy --only storage

Step 2: Monitor the rules in Firebase Console

Go to Firebase Console → Firestore → Rules to see:

  • Rules Playground — simulate a request and see if it passes or fails
  • Monitor tab — shows which rules are being hit and how many denials occur

Step 3: Gradual rollout strategy

  1. Test thoroughly in the emulator first
  2. Deploy rules to a staging Firebase project
  3. Run your app against staging — make sure nothing breaks
  4. Deploy to production
  5. Monitor denials for 24 hours — if they spike, something's wrong
⚠️ Common mistake: locking yourself out

If you deploy overly strict rules and your app starts failing, you can always redeploy looser rules immediately. Keep your previous working rules file in version control (git) so you can revert in 30 seconds.

9. Full working example — rules + client code together

Here's a complete App.js that demonstrates all the patterns working together — sending messages with proper fields so they pass the rules, rate limiting on the client side, and handling rule rejections gracefully.

// App.js — Firestore Security Rules Demo
// Replace your App.js with this to test rules in action

import React, { useState, useEffect } from 'react';
import {
  View, Text, TextInput, FlatList, Pressable,
  StyleSheet, Alert, ActivityIndicator, Platform,
  KeyboardAvoidingView,
} from 'react-native';
import { initializeApp } from 'firebase/app';
import {
  getAuth, signInWithEmailAndPassword,
} from 'firebase/auth';
import {
  getFirestore, collection, doc, addDoc, setDoc,
  query, orderBy, limit, onSnapshot, serverTimestamp,
  writeBatch,
} from 'firebase/firestore';

// ─── Firebase config (replace with yours) ──────
const firebaseConfig = {
  apiKey: 'YOUR_API_KEY',
  authDomain: 'your-app.firebaseapp.com',
  projectId: 'your-app',
  storageBucket: 'your-app.appspot.com',
  messagingSenderId: '123456789',
  appId: '1:123456789:web:abc123',
};

const app = initializeApp(firebaseConfig);
const auth = getAuth(app);
const db = getFirestore(app);

// ─── WhatsApp colours ──────────────────────────
const COLORS = {
  darkGreen: '#075E54',
  lightGreen: '#25D366',
  bubbleGreen: '#DCF8C6',
  chatBg: '#ECE5DD',
  white: '#FFFFFF',
};

// ─── Send message with proper fields for rules ──
async function sendMessage(chatId, text) {
  const userId = auth.currentUser.uid;
  const trimmed = text.trim();

  // Client-side validation (matches what rules enforce)
  if (trimmed.length === 0 || trimmed.length > 4096) {
    throw new Error('Message must be 1–4096 characters');
  }

  const batch = writeBatch(db);

  // 1. Create the message with required fields
  const msgRef = doc(collection(db, 'chats', chatId, 'messages'));
  batch.set(msgRef, {
    senderId: userId,        // Must match auth.uid (rule enforced)
    text: trimmed,           // 1–4096 chars (rule enforced)
    createdAt: serverTimestamp(), // Must equal request.time (rule enforced)
  });

  // 2. Update rate limit tracker
  const rateLimitRef = doc(db, 'rateLimits', userId);
  batch.set(rateLimitRef, { lastWrite: serverTimestamp() });

  // 3. Update chat's lastMessage preview
  const chatRef = doc(db, 'chats', chatId);
  batch.update(chatRef, {
    lastMessage: trimmed.substring(0, 100),
    lastMessageAt: serverTimestamp(),
  });

  try {
    await batch.commit();
  } catch (error) {
    if (error.code === 'permission-denied') {
      throw new Error(
        'Message blocked by security rules. ' +
        'Possible reasons: rate limited, not a participant, or invalid data.'
      );
    }
    throw error;
  }
}

// ─── Chat Screen Component ─────────────────────
function ChatScreen({ chatId }) {
  const [messages, setMessages] = useState([]);
  const [input, setInput] = useState('');
  const [sending, setSending] = useState(false);
  const [lastSentAt, setLastSentAt] = useState(0);

  // Listen to messages in real-time
  useEffect(() => {
    const q = query(
      collection(db, 'chats', chatId, 'messages'),
      orderBy('createdAt', 'desc'),
      limit(50)
    );

    const unsubscribe = onSnapshot(q, (snapshot) => {
      const msgs = snapshot.docs.map((doc) => ({
        id: doc.id,
        ...doc.data(),
      }));
      setMessages(msgs);
    });

    return unsubscribe;
  }, [chatId]);

  // Send with client-side rate limiting
  const handleSend = async () => {
    if (!input.trim()) return;

    // Client-side rate limit (1 message per second)
    const now = Date.now();
    if (now - lastSentAt < 1000) {
      Alert.alert('Slow down!', 'You can send 1 message per second.');
      return;
    }

    setSending(true);
    try {
      await sendMessage(chatId, input);
      setInput('');
      setLastSentAt(Date.now());
    } catch (error) {
      Alert.alert('Send failed', error.message);
    } finally {
      setSending(false);
    }
  };

  const userId = auth.currentUser?.uid;

  const renderMessage = ({ item }) => {
    const isMine = item.senderId === userId;
    return (
      <View style={[styles.bubble, isMine ? styles.myBubble : styles.theirBubble]}>
        <Text style={styles.messageText}>{item.text}</Text>
        <Text style={styles.timeText}>
          {item.createdAt?.toDate?.()
            ? item.createdAt.toDate().toLocaleTimeString([], {
                hour: '2-digit', minute: '2-digit'
              })
            : 'Sending...'}
        </Text>
      </View>
    );
  };

  return (
    <KeyboardAvoidingView
      style={styles.container}
      behavior={Platform.OS === 'ios' ? 'padding' : 'height'}
    >
      {/* Header */}
      <View style={styles.header}>
        <Text style={styles.headerTitle}>Priya</Text>
        <Text style={styles.headerSubtitle}>online</Text>
      </View>

      {/* Messages */}
      <FlatList
        data={messages}
        renderItem={renderMessage}
        keyExtractor={(item) => item.id}
        inverted
        style={styles.messageList}
        contentContainerStyle={{ paddingVertical: 10 }}
      />

      {/* Input bar */}
      <View style={styles.inputBar}>
        <TextInput
          style={styles.input}
          value={input}
          onChangeText={setInput}
          placeholder="Type a message"
          maxLength={4096}
          multiline
        />
        <Pressable
          style={[styles.sendBtn, sending && { opacity: 0.5 }]}
          onPress={handleSend}
          disabled={sending}
        >
          {sending
            ? <ActivityIndicator color={COLORS.white} size="small" />
            : <Text style={styles.sendText}>Send</Text>
          }
        </Pressable>
      </View>
    </KeyboardAvoidingView>
  );
}

10. Key takeaways

  • Rules run on the server — client code can't bypass them
  • Validate field types and sizes — prevent garbage data
  • Enforce ownership — senderId == request.auth.uid
  • Use request.time for timestamps — prevents backdating
  • Rate limit with a separate document — prevents spam floods
  • Storage rules = file size + MIME type — prevents bill explosions
  • Test with the Emulator before deploying — one bad rule locks everyone out
  • Keep rules in version control — so you can revert fast
