Production at Scale · Lesson 3

Offline Support & Network Handling

Firestore persistence · NetInfo · Offline queue · Connecting UI · Conflict resolution ~55 min Hands-on
Why this matters for your WhatsApp clone

Your users ride the metro, enter elevators, and live in areas with patchy signal. If your app shows a blank screen or crashes when offline, they'll switch to the real WhatsApp. The real WhatsApp works seamlessly offline: you can read old messages, type new ones, and they send automatically when connectivity returns. That's what we're building in this lesson — an app that feels alive even without internet.

1. Firestore offline persistence

Good news: Firestore has built-in offline support. Once enabled, it caches every document your app has read — so if the user goes offline, they can still see their messages.

Enabling persistence in React Native

// In your firebase config file (run this BEFORE any Firestore reads)
import { initializeFirestore, persistentLocalCache, persistentMultipleTabManager } from 'firebase/firestore';
import { initializeApp } from 'firebase/app';

const app = initializeApp(firebaseConfig);

// Enable persistent cache (data survives app restarts)
const db = initializeFirestore(app, {
  localCache: persistentLocalCache({
    tabManager: persistentMultipleTabManager(),
  }),
});

// That's it! Now:
// ✅ Previously loaded messages are available offline
// ✅ Writes queue up and sync when back online
// ✅ onSnapshot listeners fire from cache while offline

What happens automatically

SituationFirestore behaviour
User goes offlineReads come from local cache; writes queue locally
User comes back onlineQueued writes sync to server in order; listeners get fresh data
App is killed and reopened offlineCache persists on disk; data still available
Conflicting write while offlineLast-write-wins when syncing (more on this in Section 6)
Cache size

The default cache size is 100MB. For a messaging app, this is plenty — about 50,000 messages. You can increase it with cacheSizeBytes if needed, but the default works well.

2. Detecting network state with NetInfo

Firestore handles caching, but your UI needs to know the network state too — to show a "Connecting..." banner, disable the send button gracefully, or queue voice messages differently.

Install NetInfo

npx expo install @react-native-community/netinfo

Using NetInfo

import NetInfo from '@react-native-community/netinfo';
import { useState, useEffect } from 'react';

function useNetworkStatus() {
  const [isConnected, setIsConnected] = useState(true);
  const [connectionType, setConnectionType] = useState('unknown');

  useEffect(() => {
    // Subscribe to network state changes
    const unsubscribe = NetInfo.addEventListener((state) => {
      setIsConnected(state.isConnected);
      setConnectionType(state.type); // 'wifi', 'cellular', 'none', etc.
    });

    return unsubscribe;
  }, []);

  return { isConnected, connectionType };
}

// Usage in a component:
function ChatHeader({ contactName }) {
  const { isConnected } = useNetworkStatus();

  return (
    <View style={styles.header}>
      <Text style={styles.headerTitle}>{contactName}</Text>
      {!isConnected && (
        <View style={styles.offlineBanner}>
          <Text style={styles.offlineText}>Connecting...</Text>
        </View>
      )}
    </View>
  );
}

Network state values

state.typeMeaning
'wifi'Connected via WiFi
'cellular'Connected via mobile data (4G/5G)
'none'No internet connection
'unknown'State not yet determined (brief, on app start)

3. The "Connecting..." banner (WhatsApp style)

WhatsApp shows a subtle banner at the top of the chat list when offline. It disappears the moment connectivity returns. Here's how to build it:

import React, { useState, useEffect, useRef } from 'react';
import { View, Text, Animated, StyleSheet } from 'react-native';
import NetInfo from '@react-native-community/netinfo';

function ConnectingBanner() {
  const [isConnected, setIsConnected] = useState(true);
  const slideAnim = useRef(new Animated.Value(-40)).current; // starts hidden

  useEffect(() => {
    const unsubscribe = NetInfo.addEventListener((state) => {
      setIsConnected(state.isConnected);
    });
    return unsubscribe;
  }, []);

  useEffect(() => {
    // Slide down when offline, slide up when back online
    Animated.timing(slideAnim, {
      toValue: isConnected ? -40 : 0,
      duration: 300,
      useNativeDriver: true,
    }).start();
  }, [isConnected]);

  return (
    <Animated.View
      style={[
        styles.banner,
        { transform: [{ translateY: slideAnim }] },
      ]}
    >
      <Text style={styles.bannerText}>
        Connecting...
      </Text>
    </Animated.View>
  );
}

const styles = StyleSheet.create({
  banner: {

4. Offline message queue with pending indicators

When a user sends a message offline, Firestore queues it locally. But the user needs to see that it's pending — like WhatsApp's single grey tick (clock icon) that turns into ticks when delivered.

import { onSnapshot, doc } from 'firebase/firestore';

// When you send a message, Firestore returns immediately (from cache)
// But the serverTimestamp will be null until it syncs
function MessageBubble({ message, isMine }) {
  // A message without a createdAt timestamp hasn't synced yet
  const isPending = !message.createdAt;

  return (
    <View style={[styles.bubble, isMine ? styles.myBubble : styles.theirBubble]}>
      <Text style={styles.messageText}>{message.text}</Text>
      <View style={styles.metaRow}>
        <Text style={styles.timeText}>
          {isPending
            ? 'Sending...'
            : message.createdAt.toDate().toLocaleTimeString([], {
                hour: '2-digit', minute: '2-digit',
              })}
        </Text>
        {isMine && (
          <Text style={[styles.tick, isPending && styles.tickPending]}>
            {isPending ? '🕐' : '✓✓'}
          </Text>
        )}
      </View>
    </View>
  );
}

How serverTimestamp() behaves offline

  1. You call addDoc with createdAt: serverTimestamp()
  2. Firestore writes to local cache immediately — but createdAt is null
  3. Your onSnapshot fires with the cached doc (createdAt = null)
  4. When connectivity returns, the doc syncs and createdAt gets the real server time
  5. Your onSnapshot fires again with the real timestamp

This means you can use message.createdAt === null as a reliable "pending" indicator — no extra state needed!

5. Handling the send button while offline

Should you disable the send button when offline? No! WhatsApp lets you send messages offline — they queue and send later. But you should handle it differently for different content types:

function useSendMessage(chatId) {
  const { isConnected } = useNetworkStatus();

  async function send(text) {
    const trimmed = text.trim();
    if (!trimmed) return;

    // Text messages: always allow (Firestore queues them)
    const msgRef = doc(collection(db, 'chats', chatId, 'messages'));
    await setDoc(msgRef, {
      senderId: auth.currentUser.uid,
      text: trimmed,
      createdAt: serverTimestamp(),
    });
    // This returns immediately from cache — the message appears in the UI
  }

  async function sendImage(imageUri) {
    if (!isConnected) {
      // Images need upload — can't queue a file upload offline
      Alert.alert(
        'No connection',
        'Image will be sent when you reconnect.',
        [{ text: 'OK' }]
      );
      // Save to a local pending queue (we'll build this below)
      await savePendingUpload({ type: 'image', uri: imageUri, chatId });
      return;
    }

    // Upload normally when online...
  }

  async function sendVoiceNote(audioUri) {
    if (!isConnected) {
      Alert.alert(
        'No connection',
        'Voice note will be sent when you reconnect.'
      );
      await savePendingUpload({ type: 'voice', uri: audioUri, chatId });
      return;
    }

    // Upload normally when online...
  }

  return { send, sendImage, sendVoiceNote };
}

Pending uploads queue

import AsyncStorage from '@react-native-async-storage/async-storage';

const PENDING_KEY = 'pending_uploads';

// Save a pending upload to local storage
async function savePendingUpload(item) {
  const existing = await AsyncStorage.getItem(PENDING_KEY);
  const queue = existing ? JSON.parse(existing) : [];
  queue.push({ ...item, queuedAt: Date.now() });
  await AsyncStorage.setItem(PENDING_KEY, JSON.stringify(queue));
}

// Process pending uploads when back online
async function processPendingUploads() {
  const existing = await AsyncStorage.getItem(PENDING_KEY);
  if (!existing) return;

  const queue = JSON.parse(existing);
  const remaining = [];

  for (const item of queue) {
    try {
      if (item.type === 'image') {
        await uploadAndSendImage(item.chatId, item.uri);
      } else if (item.type === 'voice') {
        await uploadAndSendVoice(item.chatId, item.uri);
      }
      // Success — don't add to remaining
    } catch (error) {
      // Failed — keep in queue for next retry
      remaining.push(item);
    }
  }

  await AsyncStorage.setItem(PENDING_KEY, JSON.stringify(remaining));
}

// Trigger processing when network comes back
function useProcessPendingOnReconnect() {
  useEffect(() => {
    const unsubscribe = NetInfo.addEventListener((state) => {
      if (state.isConnected) {
        processPendingUploads();
      }
    });
    return unsubscribe;
  }, []);
}

6. Conflict resolution

What happens when two devices edit the same document while offline? For example, Priya changes her profile name on her phone (offline) and her tablet (also offline), then both come online.

Firestore's default: last-write-wins

Whoever syncs last overwrites the other. For most fields in a messaging app, this is fine:

Data typeConflict riskSolution
MessagesNone — each message is a new documentNo conflict possible
Profile nameLow — users rarely edit on two devicesLast-write-wins is fine
Unread countHigh — multiple devices updatingUse increment()
Typing indicatorNone — ephemeral, gets overwritten constantlyLast-write-wins is fine
Group members listMedium — two admins add/removeUse arrayUnion() / arrayRemove()

Using atomic operations to avoid conflicts

import { updateDoc, increment, arrayUnion, arrayRemove } from 'firebase/firestore';

// ❌ BAD — overwrites the count (conflict-prone)
await updateDoc(chatRef, { unreadCount: currentCount + 1 });

// ✅ GOOD — atomic increment (safe even offline/concurrent)
await updateDoc(chatRef, { unreadCount: increment(1) });

// ❌ BAD — overwrites the entire array
await updateDoc(chatRef, { participants: [...current, newUserId] });

// ✅ GOOD — adds to array without reading it first
await updateDoc(chatRef, { participants: arrayUnion(newUserId) });

// ✅ GOOD — removes from array without reading it first
await updateDoc(chatRef, { participants: arrayRemove(leftUserId) });

Rule of thumb: If a field is updated by multiple users or devices, never overwrite it — use increment(), arrayUnion(), or arrayRemove(). These are safe even when offline because Firestore replays them correctly on sync.

7. Firestore snapshot metadata — cache vs server

You can check whether data came from cache or the server:

import { onSnapshot } from 'firebase/firestore';

onSnapshot(messagesQuery, (snapshot) => {
  // Did this data come from cache or the server?
  const fromCache = snapshot.metadata.fromCache;

  if (fromCache) {
    // Data is from local cache — user might be offline
    // or the server hasn't responded yet
    console.log('Showing cached data');
  } else {
    // Fresh from the server
    console.log('Data is live from Firestore');
  }

  // You can also check if there are pending writes
  const hasPendingWrites = snapshot.metadata.hasPendingWrites;
  if (hasPendingWrites) {
    console.log('Some writes haven\'t synced yet');
  }
});

// To get metadata change events, pass includeMetadataChanges
onSnapshot(
  messagesQuery,
  { includeMetadataChanges: true }, // fires when metadata changes too
  (snapshot) => {
    // Now you'll get a callback when data transitions from cache → server
  }
);

When to use this

  • Show a subtle "cached" indicator on the chat list header
  • Change the tick colour from grey (pending) to blue (synced)
  • Log whether users are hitting cache or server for performance monitoring

// ─── Chat Screen ───────────────────────────────
function ChatScreen({ chatId }) {
  const [messages, setMessages] = useState([]);
  const [input, setInput] = useState('');
  const [sending, setSending] = useState(false);
  const [fromCache, setFromCache] = useState(false);
  const isConnected = useNetworkStatus();

  const userId = auth.currentUser?.uid;

  useEffect(() => {
    const q = query(
      collection(db, 'chats', chatId, 'messages'),
      orderBy('createdAt', 'desc'),
      limit(50)
    );

    // includeMetadataChanges: true → fires when cache/server status changes
    const unsubscribe = onSnapshot(
      q,
      { includeMetadataChanges: true },
      (snapshot) => {
        const msgs = snapshot.docs.map((d) => ({ id: d.id, ...d.data() }));
        setMessages(msgs);
        setFromCache(snapshot.metadata.fromCache);
      }
    );

    return unsubscribe;
  }, [chatId]);

  const handleSend = async () => {
    const trimmed = input.trim();
    if (!trimmed) return;

    setSending(true);
    try {
      const batch = writeBatch(db);

      const msgRef = doc(collection(db, 'chats', chatId, 'messages'));
      batch.set(msgRef, {
        senderId: userId,
        text: trimmed,
        createdAt: serverTimestamp(),
      });

      const chatRef = doc(db, 'chats', chatId);
      batch.update(chatRef, {
        lastMessage: trimmed.substring(0, 100),
        lastMessageAt: serverTimestamp(),
      });

      await batch.commit();
      setInput('');
    } catch (error) {
      Alert.alert('Send failed', error.message);
    } finally {
      setSending(false);
    }
  };

  return (
    <KeyboardAvoidingView
      style={styles.container}
      behavior={Platform.OS === 'ios' ? 'padding' : 'height'}
    >
      {/* Header */}
      <View style={styles.header}>
        <Text style={styles.headerTitle}>Priya</Text>
        <Text style={styles.headerSubtitle}>
          {!isConnected
            ? 'Waiting for network...'
            : fromCache
              ? 'Updating...'
              : 'online'}
        </Text>
      </View>

      {/* Connecting banner */}
      <ConnectingBanner />

      {/* Messages */}
      <FlatList
        data={messages}
        renderItem={({ item }) => (
          <MessageBubble message={item} isMine={item.senderId === userId} />
        )}
        keyExtractor={(item) => item.id}
        inverted
        style={styles.messageList}
        contentContainerStyle={{ paddingVertical: 10 }}
      />

      {/* Input bar */}
      <View style={styles.inputBar}>
        <TextInput
          style={styles.input}
          value={input}
          onChangeText={setInput}
          placeholder={isConnected ? 'Type a message' : 'Type a message (will send when online)'}
          maxLength={4096}
          multiline
        />
        <Pressable
          style={[styles.sendBtn, sending && { opacity: 0.5 }]}
          onPress={handleSend}
          disabled={sending}
        >
          {sending
            ? <ActivityIndicator color={COLORS.white} size="small" />
            : <Text style={styles.sendText}>Send</Text>
          }
        </Pressable>
      </View>
    </KeyboardAvoidingView>
  );
}

9. Key takeaways

  • Enable persistentLocalCache — one line gives you offline reads and write queueing
  • @react-native-community/netinfo — detects WiFi/cellular/none in real-time
  • "Connecting..." banner — animate in/out based on network state
  • serverTimestamp() is null while offline — use this as your "pending" indicator
  • Text messages work offline — Firestore queues them automatically
  • File uploads need a manual queue — save to AsyncStorage, process on reconnect
  • Use increment() and arrayUnion() — avoids conflicts on shared fields
  • snapshot.metadata.fromCache — tells you if data is cached or fresh
