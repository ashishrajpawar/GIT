Capstone

The Token Issuer

Module 1 finale ~90 min build Nothing new — everything used
Why this matters for Token

Twelve lessons of examples end here, in the first code that stays. You are going to build the part of Token that decides everything: it makes a code, remembers it, applies the rules the owner set, and kills it on request. Generate, store, rule, revoke.

It runs in Node with no framework, no database and no network — about two hundred lines. The version in api/ will be backed by Postgres and reached over HTTP, and it will make the same four decisions this one makes. That is why it is worth making them carefully now, while the whole thing fits on a screen and a mistake costs a re-read instead of a migration.

There is no new syntax in this lesson. Everything you need has already been taught — which is the point. This is the difference between having read about closures and being able to reach for one.

Before you start — five from the module

Each of these is a tool you are about to use for real. If one does not land, the lesson it came from is worth ten minutes before you carry on.

What you are building

One file, issuer.mjs, exporting four things:

generateCode()                 // "MERC-8GH2-KP4X" — a fresh code
isValidCode(raw)               // could this string have been issued by us?
DENIED_MESSAGE                 // the one thing every rejected holder is told
createIssuer()                 // one person's set of tokens

And what an issuer can do:

const issuer = createIssuer();

const token = issuer.issue({ label: "Grocery delivery", maxUses: 3 });
token.code                     // "MERC-8GH2-KP4X" — give this to the shop

issuer.redeem("merc-8gh2-kp4x")  // { ok: true, label: "Grocery delivery", usesLeft: 2 }
issuer.revoke(token.code)        // { ok: true }
issuer.redeem(token.code)        // { ok: false, message: "That code can't be used." }

issuer.list()                    // what the owner sees
issuer.events()                  // what happened, including the failed attempts

Stage 1 — a code nobody can guess

The alphabet is fixed and it is not negotiable:

23456789ABCDEFGHJKMNPQRSTUVWXYZ     // 31 characters

That is the 36 letters and digits, minus five: 0, O, 1, I and L. They are gone because a token code gets read aloud down a phone line, printed on a card, and typed by someone who has never seen it written down. A person who cannot tell 0 from O is not making a mistake — the two are the same shape in most fonts. Removing them costs you 5 characters of alphabet and saves you every support conversation that starts "it says invalid code".

The cost of that decision, since it is a real one: 31 characters instead of 36 makes the keyspace smaller. Twelve characters of a 31-letter alphabet is 3112, about 7.9 × 1017 codes. At a million guesses a second — far more than any server would ever answer — working through them takes roughly 25,000 years. The five characters were not missed.

Try it yourself

Try it yourself — this one is broken on purpose

The obvious way to turn a random byte into a letter is to use it as an index. Run this and read what comes out before you fix it.

Nothing threw. That is the interesting part: ALPHABET[200] is undefined, and adding undefined to a string gives you the six letters undefined rather than an error. A bug that produces confident garbage is worse than one that crashes, and this is the shape of most of them.

The fix is % — the remainder operator — which folds any number back into the range 0 to 30:

ALPHABET[byte % ALPHABET.length]     // always a real character

Where % alone goes wrong

That fix has a flaw, and it is worth the paragraph because it is invisible in testing and permanent in production.

A byte is 0 to 255 — 256 values. Divide by 31: 256 / 31 = 8 remainder 8. So the bytes 0–247 spread evenly, eight per letter, and then there are 8 left over: 248 to 255. Those wrap around onto the first eight letters of the alphabet a ninth time.

byte 0   -> "2"      byte 248 -> "2"     ninth chance for "2"
byte 1   -> "3"      byte 249 -> "3"     ninth chance for "3"
...                  ...
byte 7   -> "9"      byte 255 -> "9"     ninth chance for "9"
byte 8   -> "A"      (nothing extra)     "A" only ever gets eight

2 3 4 5 6 7 8 9 come up 9 times per 256 bytes and the other 23 characters come up 8 times: those eight are 12.5% more likely than the rest, in every code, forever. No test notices. Nobody reports it. It simply makes the codes slightly easier to guess than the arithmetic above claims, and there is no way to fix it later for codes already issued.

The fix costs one line: throw away any byte of 248 or more and draw another.

const byte = nextByte();
if (byte >= 248) continue;           // biased range — draw again
letters += ALPHABET[byte % 31];

Roughly 3% of draws are discarded. In exchange every character is exactly as likely as every other.

Try it yourself

Where the bytes come from

Math.random() is the function you have used all module, and it is the wrong one here. It is fast and it is fine for shuffling a list or picking a demo colour, but it is predictable: it is a formula with a hidden counter, and someone who sees enough of its output can work out the counter and produce the rest. For a capability that grants access to a person, that is fatal.

The right one is built into every browser and into Node, and it is one line:

const bytes = new Uint8Array(1);
crypto.getRandomValues(bytes);       // cryptographically random
console.log(bytes[0]);               // 0 to 255

Uint8Array is an array whose slots hold one byte each; getRandomValues fills it in place, which is why nothing is assigned from it. There is no counter to work out and no sequence to predict.

The habit worth taking from this stage

Notice what the exercise asks for: generateCode(nextByte) takes its source of randomness as an argument, with a real one as the default. That is not decoration. Randomness you cannot control is randomness you cannot test — the only way to check an unbiased generator is to run it thousands of times and squint at the totals. Hand the bytes in and the same test becomes exact and instant. You will do the same thing with the clock in stage 3.

Stage 2 — somewhere to keep them

A code on its own is a string. A token is a code plus everything the owner decided about it:

{
  code:      "MERC-8GH2-KP4X",
  label:     "Grocery delivery",   // how the owner recognises it later
  issuedAt:  1755300000000,
  expiresAt: 1755321600000,        // or null for no expiry
  maxUses:   3,                    // or null for unlimited
  uses:      0,
  revokedAt: null
}

Where does that live? The obvious answer is an array at the top of the file, and the obvious answer is wrong for a reason worth understanding.

// Anyone can reach this. Anyone can change it.
export const tokens = [];

An exported array is a shared, writable global. Any file that imports it can push a token nobody issued, or set revokedAt back to null on a token the owner killed. Nothing enforces the rules, because the rules live in functions the caller can simply go around.

Lesson 6's closure is the answer. A variable declared inside createIssuer lives as long as the functions that use it, and there is no expression anywhere that reaches it:

function createIssuer() {
  const tokens = [];               // private, permanently

  return {
    issue(options, now) { /* can see tokens */ },
    list(now)           { /* can see tokens */ }
  };
}

Try it yourself

Try it yourself — this one is broken on purpose

Privacy through a closure is easy to build and easy to hand away by accident. This issuer keeps its store private and then leaks it in the last place you would look.

The store was never reachable by name — and it did not need to be, because list() returned the array itself. Every caller got a live handle on the owner's data, and a .pop() written for a display list deleted a real token. list() must return copies:

list() {
  return tokens.map((t) => ({ ...t }));    // a new array of new objects
}

That is lesson 10's spread, doing the job it exists for. A shallow copy is enough here only because a token record is flat — every value in it is a string, a number or null. Add a nested object to that record later and the copy stops protecting it, exactly as lesson 10's pg-shallow showed.

Status is derived, never stored

A token can be active, revoked, expired or exhausted. It is tempting to keep that as a field and update it. Do not.

A stored status has to be maintained by somebody. Who sets status = "expired"? Nothing happens at the moment a token expires — no code runs, because time passing is not an event. You would need a job sweeping every token every minute, and a token whose status was written by a sweep that has not run yet is simply wrong.

Derived status has none of that. It is a question you answer when someone asks:

function statusOf(token, now) {
  if (token.revokedAt !== null) return "revoked";
  if (token.expiresAt !== null && now >= token.expiresAt) return "expired";
  if (token.maxUses !== null && token.uses >= token.maxUses) return "exhausted";
  return "active";
}

Note now is a parameter, not a call to Date.now() inside the function. Same argument as the bytes in stage 1: a function that reads the clock itself can only be tested by waiting.

Try it yourself

When to throw and when to return

Lesson 12's distinction lands here for real. The issuer has two kinds of caller:

  • issue() is called by our own app. If the label is missing, that is a bug in a screen we wrote — nobody outside can cause it. It should throw, loudly, in development, where it gets fixed.
  • redeem() is called with whatever a stranger typed. There is no bug to report. It must never throw — it returns a result, always.

Same file, two opposite policies, and both are right.

Stage 3 — the rules, and the off switch

Redemption is four questions in a row, and the order does not matter because the answer to any of them is the same. Is this even a code we could have issued? Do we have it? Is it still alive? Then — and only then — yes.

Write that as a list of ways to say no and you have built the wrong thing:

// Deny-list thinking — do not do this
if (token.revokedAt !== null) return denied();
if (token.expiresAt !== null && now >= token.expiresAt) return denied();
return allowed();                   // everything else gets in

That code grants access to every state you have not thought of yet. Add maxUses next month and forget one line here, and exhausted tokens quietly keep working. Deny-by-default inverts it — one way in, and it has to be earned:

if (statusOf(token, now) !== "active") return denied();
return allowed();

Now a new status is denied until somebody deliberately adds it to statusOf as an allowed one. This is the product's whole premise expressed in two lines: nobody reaches the user unless the user issued them something that is still good.

Try it yourself — this one is broken on purpose

The answer that has to be vague

Lesson 12 ended on this and the capstone is where it becomes a rule of the system rather than a rule of one function.

A holder whose redemption fails could be told exactly why: no such code, that one was revoked, that one is out of uses. It reads better. It is also a yes/no oracle — type codes until the wording changes, and the wording tells you when you have found a real one. The 25,000 years of keyspace assumes the answer carries no information; different messages hand out one bit per guess, and a bit per guess is what a search needs.

So every denial returns the identical string, and the reason goes somewhere the holder cannot see:

record({ type: "denied", code, at: now, reason: "revoked" });   // owner's log
return { ok: false, message: DENIED_MESSAGE };                  // holder's screen

The log is not a consolation prize. It is the other half of the defence: a uniform message means a guesser learns nothing, and the log means the owner sees them trying. A hundred unknown denials in a row is a shape you can act on.

Try it yourself

What a successful redemption gives back

The last privacy decision in the file, and the easiest one to get wrong by being generous:

return { ok: true, label: token.label, usesLeft: ... };

The holder gets the label the owner chose for them and nothing else. Not the owner's name, not the other tokens, not when this one was issued. Every extra field here is something a stranger learns about a person who deliberately did not give them a phone number — and once a field is in a response, removing it breaks whatever started depending on it.

The test file is the point

You have been running self-checks all module and they have been written for you. test.mjs is the same check(label, passed, detail) helper in a file you own, and it is the first thing in this project that will still be running in a year.

Its best test is the one you cannot do by reading:

const counts = {};
for (const ch of ALPHABET) counts[ch] = 0;
const nextByte = sequentialBytes();          // 0, 1, 2, ... 255, 0, 1, ...
for (let i = 0; i < 1000; i++) {
  for (const ch of generateCode(nextByte).replace(/-/g, "")) counts[ch]++;
}

check("the alphabet is used evenly — no modulo bias",
      Math.max(...tallies) - Math.min(...tallies) <= 1, ...);

Take the if (byte >= 248) continue; line out of issuer.mjs and that check reports letter counts running from 375 to 422 — the 12.5% from stage 1, measured. Put it back and the spread is at most 1. A bias no human could see in the output is now a line of output that says FAIL.

What this deliberately does not do

It does not persist — restart the process and every token is gone. It has no users, no authentication and no network. Those are not oversights; they are Track B, and each one is a module. What it does have is the four decisions that survive the move to Postgres: unbiased codes, one denial message, injected time, and no references handed out into the store. The data structure gets thrown away. The decisions do not.
