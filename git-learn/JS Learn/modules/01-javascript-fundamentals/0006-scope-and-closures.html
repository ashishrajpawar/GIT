Lesson 6

Scope & Closures

Foundations ~25 min read Beginner
Why this matters for your WhatsApp clone

Imagine you're building a chat screen. You write a variable called messages inside one function to hold the current chat's messages — and then later, a completely unrelated function accidentally overwrites it with data from a different chat. Your UI shows the wrong conversation. The user is confused. You have no idea why.

That kind of bug — where a variable "leaks" into a place it was never meant to be — is one of the most frustrating things to track down in a growing app. Scope is the rule that prevents this. Understanding it means you will always know exactly where a variable lives, who can see it, and who cannot. It is not optional knowledge — it is how JavaScript works, all the time, under the hood.

Closures take this one step further. They are the mechanism behind React hooks like useState and useEffect — the very tools you will use to manage your chat app's state. By the end of this lesson, you will understand what is really happening when React "remembers" your app's data between renders.

What is scope?

Scope is the set of rules that determines which variables are visible (accessible) from a given point in your code. A variable exists inside its scope. Outside its scope, it simply does not exist — trying to read it will throw a ReferenceError.

Think of scope like rooms in a building. A whiteboard in the conference room is visible to everyone in that room. Someone standing in the kitchen cannot see it. If they walk into the conference room, they can. Variables work the same way.

There are two broad categories to start with: global scope and local scope.

Global scope

A variable declared at the top level of a script — outside any function or block — is in the global scope. Every piece of code in that file can see it.

const APP_NAME = "ChatApp"; // global — visible everywhere in this file

function showWelcome() {
  console.log("Welcome to " + APP_NAME); // can see APP_NAME — it's global
}

showWelcome(); // "Welcome to ChatApp"

Local scope

A variable declared inside a function or a block ({ }) is in local scope. It only exists inside that function or block. The outside world cannot see it.

function loadMessages() {
  const messages = ["Hey!", "How are you?", "On my way."]; // local to loadMessages
  console.log(messages.length); // 3 — fine, we're inside the function
}

loadMessages();
console.log(messages); // ReferenceError: messages is not defined
                       // Outside the function, messages does not exist
In your WhatsApp clone

Your app-wide configuration — API keys, server URLs, your app's name — belongs in global (or module-level) scope. The messages array for a specific chat screen belongs inside that screen's component function. This separation means two different chat screens can each have their own messages variable with no conflict. Scope is what makes that work.

Block scope — how let and const work

A block is any pair of curly braces { }. That includes the bodies of if statements, for loops, while loops, and even a standalone pair of braces you write yourself. Variables declared with let or const are block-scoped — they only exist inside the block where they were declared.

function processNewMessage(messageText) {
  if (messageText.length > 0) {
    const trimmed = messageText.trim(); // block-scoped to this if-block
    console.log("Sending:", trimmed);
  }

  console.log(trimmed); // ReferenceError: trimmed is not defined
                        // We left the if-block — trimmed no longer exists
}

This is a feature, not a limitation. By keeping trimmed inside the if block, you signal clearly: "this value is only relevant here." Anyone reading the code instantly knows its purpose is narrow.

The old way: why var causes problems

The old keyword var is not block-scoped — it is function-scoped, and it has an additional behaviour called hoisting that makes it behave in deeply confusing ways. This is exactly why modern JavaScript introduced let and const and why you should never use var.

The var hoisting gotcha — why var is dangerous

With var, you can read a variable before you have even declared it. JavaScript silently moves (hoists) the declaration to the top of its function scope, but leaves the assignment in place. The variable exists, but its value is undefined — which looks like it worked, but gives you the wrong value. This causes silent bugs that are extremely hard to find.

// What you wrote:
console.log(status); // undefined — no error, but the value is wrong!
var status = "online";
console.log(status); // "online"

// What JavaScript actually ran (behind the scenes):
var status;           // hoisted to the top — value is undefined
console.log(status); // undefined
status = "online";
console.log(status); // "online"

With let or const, that first console.log would throw a ReferenceError immediately — a clear, honest error instead of a mystery. Always use let or const. Never use var.

Here is the same scenario written correctly with let:

// With let — block scoped, honest, safe
function processNewMessage(messageText) {
  if (messageText.length > 0) {
    let trimmed = messageText.trim(); // only lives in this block
    console.log("Sending:", trimmed);
  }
  // trimmed is gone here — no bleed, no confusion
}
In your WhatsApp clone

In React Native, inside a loop that renders chat messages, you might create a temporary variable to format a timestamp. With const or let, that variable stays inside the loop iteration where it was created. It cannot accidentally contaminate the next iteration or a completely different part of your screen. Block scope is your safety net.

Function scope

Variables declared inside a function — whether with let, const, or even as a function parameter — are function-scoped. They are created when the function runs and destroyed when the function finishes. They are completely invisible outside the function.

function formatMessage(text, sender) {
  // 'text' and 'sender' are parameters — also function-scoped
  const timestamp = new Date().toLocaleTimeString(); // function-scoped
  const formatted = `[${timestamp}] ${sender}: ${text}`;
  return formatted;
}

const result = formatMessage("See you soon!", "Riya");
console.log(result); // "[10:42:31 AM] Riya: See you soon!"

// These variables do not exist outside the function:
console.log(timestamp); // ReferenceError
console.log(formatted); // ReferenceError
console.log(sender);    // ReferenceError

This is exactly what you want. The timestamp and formatted variables are intermediate steps in building the output. They are implementation details of formatMessage. Nobody else needs to know they exist.

In your WhatsApp clone

Your app will have dozens of helper functions: one to format a message timestamp, one to validate a phone number, one to compress a photo before sending. Each of these functions will have internal variables — intermediate values that are only meaningful during that function's work. Function scope means those internals are private and protected. Two functions can each have a variable called result without any conflict.

Nested scope and the scope chain

Functions can be defined inside other functions. When they are, the inner function has access to everything in its own scope plus everything in the outer function's scope plus everything in global scope. This lookup path is called the scope chain.

The rule is simple: inner scopes can look outward; outer scopes cannot look inward.

function createChatRoom(roomName) {
  const members = ["Ashish", "Riya", "Dev"]; // outer function's variable

  function sendMessage(text) {
    // Inner function — can access 'roomName' and 'members' from outer scope
    const message = {
      room: roomName,        // from outer scope — works fine
      recipients: members,   // from outer scope — works fine
      content: text,
      sentAt: new Date()
    };
    console.log(message);
  }

  sendMessage("Hey everyone!");
  // 'message' is NOT accessible here — it's inside sendMessage's scope
}

When sendMessage uses roomName, JavaScript first looks in sendMessage's own scope — not found. It then looks in the enclosing createChatRoom scope — found. It stops there. This outward-walking lookup is the scope chain.

createChatRoom("Weekend Plans");
// {
//   room: "Weekend Plans",
//   recipients: ["Ashish", "Riya", "Dev"],
//   content: "Hey everyone!",
//   sentAt: ...
// }
In your WhatsApp clone

React Native components are functions. Event handlers (like what happens when you tap Send) are often functions inside those component functions. The handler can read the component's messages array, the current user object, and the chatId — all because of the scope chain. You will use this pattern constantly, often without realising it has a name.

Closures — functions that remember

A closure is created when a function is defined inside another scope and — crucially — is returned (or otherwise kept alive) so that it continues to exist even after the outer scope has finished running.

The inner function closes over the variables from its outer scope. It carries those variables with it, holding onto them for as long as the inner function itself exists. Even after the outer function's execution is complete, the inner function still has access to those outer variables.

This sounds abstract, so let's build it step by step.

Step 1: A simple counter function

function makeCounter() {
  let count = 0; // This variable lives in makeCounter's scope

  function increment() {
    count = count + 1; // increment can see 'count' via scope chain
    return count;
  }

  return increment; // We return the inner function itself
}

const counter = makeCounter(); // makeCounter runs, returns 'increment'
                               // makeCounter is now finished — but...

console.log(counter()); // 1 — count is still alive!
console.log(counter()); // 2 — same count, incremented again
console.log(counter()); // 3

Notice what happened: makeCounter ran and finished. Normally, count would be destroyed at that point. But because increment — which references count — was returned and stored in counter, JavaScript kept count alive. The increment function closed over count. That is a closure.

And each call to makeCounter() creates a completely independent closure — its own private count:

const counterA = makeCounter();
const counterB = makeCounter(); // completely separate closure

console.log(counterA()); // 1
console.log(counterA()); // 2
console.log(counterB()); // 1 — counterB has its own independent 'count'
console.log(counterA()); // 3 — counterA is unaffected by counterB

Step 2: A real chat example — makeUnreadCounter

Now let's make this directly relevant to your WhatsApp clone. In WhatsApp, each chat has its own unread message count. The count for "Riya" is separate from the count for "Work Group". Each chat needs its own private counter that remembers its own state.

Closures are the perfect tool for this:

function makeUnreadCounter(chatName) {
  let unreadCount = 0; // private to this specific chat

  function addUnread() {
    unreadCount = unreadCount + 1;
    console.log(`${chatName} has ${unreadCount} unread message(s)`);
    return unreadCount;
  }

  function markAllRead() {
    unreadCount = 0;
    console.log(`All messages in "${chatName}" marked as read`);
  }

  function getCount() {
    return unreadCount;
  }

  // Return an object with methods — each closes over the same 'unreadCount'
  return { addUnread, markAllRead, getCount };
}

// Create independent counters for each chat
const riyaChat   = makeUnreadCounter("Riya");
const workGroup  = makeUnreadCounter("Work Group");
const mumChat    = makeUnreadCounter("Mum");

riyaChat.addUnread();   // "Riya has 1 unread message(s)"
riyaChat.addUnread();   // "Riya has 2 unread message(s)"
workGroup.addUnread();  // "Work Group has 1 unread message(s)"
workGroup.addUnread();  // "Work Group has 2 unread message(s)"
workGroup.addUnread();  // "Work Group has 3 unread message(s)"

console.log(riyaChat.getCount());  // 2
console.log(workGroup.getCount()); // 3
console.log(mumChat.getCount());   // 0

riyaChat.markAllRead(); // "All messages in "Riya" marked as read"
console.log(riyaChat.getCount());  // 0 — only Riya's count was reset
console.log(workGroup.getCount()); // 3 — Work Group is unchanged

Each call to makeUnreadCounter creates a brand new, independent unreadCount variable. The three returned objects (riyaChat, workGroup, mumChat) each hold functions that close over their own separate unreadCount. They never interfere with each other.

In your WhatsApp clone

This pattern — a factory function that returns methods closing over private state — is exactly what React's useState hook does for your components. Each component instance has its own private piece of state. When you call const [messages, setMessages] = useState([]) in your chat screen component, React gives your component a closure over its own messages array. That is why one chat screen's messages don't bleed into another chat screen's messages.

Why closures matter in React Native

When you start building your WhatsApp clone in React Native, you will write components using React's hooks — functions like useState, useEffect, and useCallback. You will not need to understand closures deeply to use hooks. But knowing this foundation will save you hours of confusion.

Here is what a chat input component will look like in React Native (you'll learn the full syntax in Lesson 12 — for now, just read the shape of it):

// A React Native component — you'll write this in Lesson 12
function ChatInput({ chatId, onSend }) {
  const [messageText, setMessageText] = useState(""); // React manages this value

  // This function is a closure — it 'remembers' messageText and chatId
  function handleSend() {
    if (messageText.trim().length === 0) return;

    // Both 'messageText' and 'chatId' are from the outer component scope
    // handleSend closes over them — this is a closure
    onSend({ chatId: chatId, text: messageText.trim() });
    setMessageText(""); // clear the input after sending
  }

  return (
    // ... the input field and send button would go here
  );
}

The handleSend function is a closure. It closes over messageText and chatId from the component's scope. Every time the component re-renders with a new value of messageText, a new version of handleSend is created that closes over the current messageText. If you have ever encountered a bug in React where a function seems to use a "stale" old value instead of the current one — that is a closure issue, and you now have the vocabulary to diagnose it.

Common scope bugs to watch out for

Bug 1: Variable shadowing

Shadowing happens when you declare a variable with the same name in an inner scope as a variable in an outer scope. The inner variable "shadows" (hides) the outer one. This is technically valid JavaScript, but it causes bugs when you meant to update the outer variable and instead created a new inner one by accident.

let currentUser = "Ashish"; // outer variable

function switchAccount(newUser) {
  let currentUser = newUser; // BUG: shadows the outer 'currentUser'
                             // This creates a NEW variable — the outer one is untouched

  console.log("Switched to:", currentUser); // shows newUser — seems to work
}

switchAccount("Riya");
console.log(currentUser); // "Ashish" — the outer variable was NEVER changed!
                          // This is probably not what you wanted
Shadowing bug — easy to miss

The code above has no error — JavaScript allows it. But it silently does the wrong thing. If your intent was to update the outer currentUser, you accidentally created a local copy instead. The fix: remove let from inside the function so you reassign the outer variable rather than declaring a new one — or, better, return the new value and let the caller handle the assignment.

// Correct version — no inner let, so we write to the outer variable
let currentUser = "Ashish";

function switchAccount(newUser) {
  currentUser = newUser; // no 'let' — reassigns the existing outer variable
  console.log("Switched to:", currentUser);
}

switchAccount("Riya");
console.log(currentUser); // "Riya" — correct!

Bug 2: Forgetting block scope in loops — the classic closure trap

This is one of the most famous JavaScript interview questions, and it is directly relevant to anything you build with lists of items — like a list of chat conversations.

const chats = ["Riya", "Work Group", "Mum"];

// Using let — correct, block-scoped, each iteration gets its own 'i'
for (let i = 0; i < chats.length; i++) {
  setTimeout(function() {
    console.log("Chat", i, ":", chats[i]);
  }, i * 1000);
}
// After 0s: "Chat 0 : Riya"
// After 1s: "Chat 1 : Work Group"
// After 2s: "Chat 2 : Mum"  ← correct! Each callback closes over its own 'i'
// Using var — BROKEN, function-scoped, all iterations share one 'i'
for (var i = 0; i < chats.length; i++) {
  setTimeout(function() {
    console.log("Chat", i, ":", chats[i]); // BUG: 'i' is shared
  }, i * 1000);
}
// After 0s: "Chat 3 : undefined"  ← wrong! i is already 3 by the time this runs
// After 1s: "Chat 3 : undefined"  ← wrong!
// After 2s: "Chat 3 : undefined"  ← wrong!

With var, there is only one i shared across all loop iterations (because var ignores block boundaries). By the time the callbacks run, the loop has finished and i is 3. With let, each iteration gets its own i — a new block scope per iteration — so each closure captures the correct value. This is another reason to always use let or const.

In your WhatsApp clone

When you render a list of chat conversations and attach a tap handler to each one — "open this chat when tapped" — you are creating a closure inside a loop. Using let (or the modern for...of loop) ensures each tap handler captures the correct chat, not whatever chat happened to be last in the list.
