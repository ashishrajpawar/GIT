Lesson 9

Promises & Async/Await

Browser JS ~25 min read Beginner
Why this matters for your WhatsApp clone

Every time your app opens a chat, it has to go to a server, ask for messages, wait for the reply, and then show them on screen. That round trip takes time — maybe 200 ms, maybe 2 seconds on a slow connection. JavaScript does not stop and wait for it. While your fetch is in flight, JS keeps running other code. Async/await is the tool that lets you say: "Start fetching messages — and when they arrive, do this." Without it you cannot build a real chat app.

1. The problem: synchronous vs asynchronous

JavaScript normally runs code line by line, top to bottom. That is called synchronous execution. Each line finishes before the next one begins.

That works fine for maths and string manipulation, but it breaks down the moment you need to wait for something outside your own code — a database, an HTTP server, a file on disk. Those operations take unpredictable amounts of time.

A restaurant analogy

Imagine two restaurants:

  • Synchronous restaurant: the cashier takes your order, walks to the kitchen, stands there watching the chef cook, carries the food back, and only then serves the next customer. Everyone else queues. The whole restaurant grinds to a halt for every order.
  • Asynchronous restaurant: the cashier takes your order, gives you a buzzer, and immediately serves the next customer. When your food is ready the kitchen presses a button on your buzzer. You walk up and collect it. Nobody waits for anyone else.

JavaScript is the asynchronous restaurant. When you ask it to fetch messages from a server, it kicks off the request and moves on. You have to give it a way to know what to do when the food is ready.

Here is the core problem shown in code. This does not work:

// BROKEN — this cannot work the way you'd expect
function getMessages(chatId) {
  // Pretend this sends a network request...
  // but the network request takes 500 ms
  // By the time the data arrives, this function has already returned!
  const messages = fetchFromServer(chatId); // takes time
  return messages; // returns undefined, not messages
}

const msgs = getMessages("chat-001");
console.log(msgs); // undefined — the data hasn't arrived yet!
The key insight

A network request is not instant. By the time your function returns, the data does not exist yet. You need a way to register a callback for when it does — that is exactly what Promises and async/await give you.

2. Callbacks — the original solution

The first solution JavaScript developers reached for was callbacks: pass a function as an argument, and call it when the work is done.

function loadMessages(chatId, onDone) {
  // Simulate a 500 ms network delay
  setTimeout(function() {
    const messages = [
      { sender: "Priya", text: "Hey, still on for tonight?" },
      { sender: "Ashish", text: "Yes! 8pm works?" }
    ];
    onDone(messages); // call the function we were given
  }, 500);
}

loadMessages("chat-001", function(messages) {
  console.log("Messages loaded:", messages);
});

That works for one step. But a real chat app has many steps: load the user profile, then load their chats, then load the selected chat's messages, then check for unread notifications. With callbacks each step nests inside the previous one:

// CALLBACK HELL — real code that developers actually wrote
loadUser("ashish", function(user) {
  loadChats(user.id, function(chats) {
    loadMessages(chats[0].id, function(messages) {
      loadUnreadCount(user.id, function(count) {
        // Finally have everything — but the indentation is a nightmare
        // and error handling is a mess
        console.log(user, chats, messages, count);
      });
    });
  });
});
Callback hell is a real problem

This pattern — deeply nested callbacks — became known as "callback hell" or the "pyramid of doom." It is hard to read, hard to debug, and error handling requires checking for errors in every single callback. The JavaScript community built Promises specifically to escape it.

Historical context

Callbacks are not wrong — they are still used in many places. But for chaining multiple async operations one after another, Promises and async/await are far cleaner. You will still encounter callbacks in React Native event handlers and timers, so it is important to understand how they work.

3. Promises

A Promise is an object that represents the eventual result of an asynchronous operation. Think of it like a ticket at a deli counter: you do not have your order yet, but you have a promise that it will arrive, and you can tell the system what to do when it does.

A Promise is always in one of three states:

  • Pending — the operation is still in progress (the fetch is running)
  • Fulfilled — the operation succeeded and has a result value
  • Rejected — the operation failed and has an error reason

Once a Promise moves from pending to either fulfilled or rejected, it never changes state again.

Creating and consuming a Promise

// Creating a Promise — simulating loading messages from a server
function loadMessages(chatId) {
  return new Promise(function(resolve, reject) {
    // Simulate a 600 ms network request
    setTimeout(function() {
      if (chatId) {
        // Success — call resolve() with the data
        resolve([
          { sender: "Priya", text: "Are you coming tonight?" },
          { sender: "Ashish", text: "Yes, on my way!" }
        ]);
      } else {
        // Failure — call reject() with an error
        reject(new Error("chatId is required"));
      }
    }, 600);
  });
}

// Consuming a Promise with .then() and .catch()
loadMessages("chat-001")
  .then(function(messages) {
    // This runs when the Promise fulfils
    console.log("Got messages:", messages);
  })
  .catch(function(error) {
    // This runs if the Promise rejects
    console.error("Failed to load:", error.message);
  });

Chaining .then() calls

Promises can be chained — each .then() returns a new Promise, so you can attach another .then() to it. This avoids the deep nesting of callback hell:

loadUser("ashish")
  .then(function(user) {
    return loadChats(user.id); // return a new Promise
  })
  .then(function(chats) {
    return loadMessages(chats[0].id); // return another Promise
  })
  .then(function(messages) {
    console.log("Messages:", messages);
  })
  .catch(function(error) {
    // One catch handles errors from any step above
    console.error("Something went wrong:", error.message);
  });
In your WhatsApp clone

Every time you call a Firebase or REST API function from React Native, it returns a Promise. Understanding that is what lets you handle the response correctly and show a loading spinner while waiting.

4. async/await — the modern syntax

Promises solved callback hell, but chains of .then() can still be verbose. In 2017, JavaScript gained async/await — special syntax that lets you write asynchronous code that looks like ordinary synchronous code.

Two keywords to learn:

  • async — put this in front of a function keyword. It marks the function as asynchronous, and makes it always return a Promise.
  • await — put this in front of any expression that returns a Promise. It pauses execution inside the function until the Promise resolves, then gives you the resolved value. It does not block the rest of the program.
// The same loadMessages() from before (still returns a Promise)
function loadMessages(chatId) {
  return new Promise(function(resolve, reject) {
    setTimeout(function() {
      resolve([
        { sender: "Priya", text: "Are you coming tonight?" },
        { sender: "Ashish", text: "Yes, on my way!" }
      ]);
    }, 600);
  });
}

// Now consuming it with async/await — reads like normal code
async function showChat(chatId) {
  const messages = await loadMessages(chatId); // pauses here until done
  console.log("Messages:", messages);          // then continues here
}

showChat("chat-001");

Compare that to the .then() version — the async/await version reads from top to bottom like plain synchronous code. No nesting, no callbacks.

async functions always return a Promise

This is important: even if your async function returns a plain value, the caller gets a Promise back. The value you return becomes the resolved value of that Promise.

async function getGreeting(name) {
  return "Hello, " + name; // returns a plain string
}

// But the caller gets a Promise!
const result = getGreeting("Ashish");
console.log(result); // Promise { "Hello, Ashish" }

// To get the actual string, you await it:
async function main() {
  const greeting = await getGreeting("Ashish");
  console.log(greeting); // "Hello, Ashish"
}

main();
Common mistake: forgetting await

If you forget to write await in front of a Promise-returning function, you get the Promise object itself — not the data inside it.

async function showChat(chatId) {
  const messages = loadMessages(chatId); // MISSING await!
  console.log(messages); // Promise { <pending> } — not useful
}

Always ask yourself: "Does this function return a Promise?" If yes, add await.

await can only be used inside an async function

You cannot write await at the top level of a regular script (outside any function). It must be inside a function marked async. If you need to run async code at the top level, wrap it: async function main() { ... } main();

5. Error handling with try/catch

With .then() you used .catch() to handle errors. With async/await you use the standard JavaScript try/catch block — the same syntax used for synchronous errors. This makes your error-handling code consistent across the whole app.

async function loadChatMessages(chatId) {
  try {
    const messages = await loadMessages(chatId);
    console.log("Loaded", messages.length, "messages");
    return messages;
  } catch (error) {
    // Runs if the Promise rejects — e.g. network failure, server error
    console.error("Could not load messages:", error.message);
    return []; // return empty array so the UI doesn't crash
  }
}

loadChatMessages("chat-001");

If the network is down, loadMessages() rejects its Promise. The await turns that rejection into a thrown error, which catch intercepts — exactly as if it were a synchronous throw.

What happens without try/catch

async function badExample(chatId) {
  const messages = await loadMessages(chatId); // if this rejects...
  console.log(messages); // ...this line is never reached
  // And nothing handles the error — it becomes an unhandled rejection
}

badExample(""); // passes empty chatId — loadMessages rejects
Unhandled Promise rejections

If an async function throws (or an await rejects) and nothing catches it, you get an UnhandledPromiseRejection error. In a React Native app this can silently swallow errors and leave the user staring at a blank screen. Always wrap await calls in try/catch, or attach a .catch() to the returned Promise.

Pattern: show an error message to the user
async function loadChatScreen(chatId) {
  try {
    const messages = await loadMessages(chatId);
    displayMessages(messages);
  } catch (error) {
    showErrorBanner("Couldn't load messages. Check your connection.");
  }
}

In your WhatsApp clone, every data-loading function should follow this pattern: try to load, catch errors, and show a user-friendly message instead of crashing.

6. Promise.all — running multiple async operations in parallel

Sometimes you need several independent pieces of data at the same time. For example, when opening a chat you might need:

  • The messages for that chat
  • The other user's profile (name, avatar, online status)

You could await them one after another — but that means waiting for the first to finish before even starting the second. If each takes 400 ms, sequential fetching takes 800 ms total.

Promise.all lets you start both at the same time and wait for both to finish. Total time is just the time of the slowest one — not the sum.

async function loadProfileAndMessages(chatId, userId) {
  // Both requests START at the same time
  const [messages, userProfile] = await Promise.all([
    loadMessages(chatId),
    loadUserProfile(userId)
  ]);

  // Both are done — we have both results
  console.log("Messages:", messages);
  console.log("Profile:", userProfile);
}

Promise.all takes an array of Promises and returns a single Promise. That Promise:

  • Fulfils when all the input Promises have fulfilled — with an array of their results, in the same order.
  • Rejects immediately if any of the input Promises rejects. The other Promises are ignored.
// Simulated helper functions
function loadMessages(chatId) {
  return new Promise(function(resolve) {
    setTimeout(function() {
      resolve([
        { sender: "Priya", text: "Ready?" },
        { sender: "Ashish", text: "2 mins!" }
      ]);
    }, 400);
  });
}

function loadUserProfile(userId) {
  return new Promise(function(resolve) {
    setTimeout(function() {
      resolve({ name: "Priya Sharma", avatar: "priya.jpg", online: true });
    }, 300);
  });
}

// Both start together — total wait ≈ 400 ms (not 700 ms)
async function openChat(chatId, userId) {
  try {
    const [messages, profile] = await Promise.all([
      loadMessages(chatId),
      loadUserProfile(userId)
    ]);
    console.log("Chat partner:", profile.name);
    console.log("First message:", messages[0].text);
  } catch (error) {
    console.error("Failed to open chat:", error.message);
  }
}

openChat("chat-001", "user-priya");
Performance wins in your WhatsApp clone

Any time you need two or more unrelated pieces of data on the same screen, reach for Promise.all. It makes your app feel noticeably faster because the network requests overlap instead of stacking.

async inside forEach does not work as expected

A common mistake is using async callbacks inside forEach:

const chatIds = ["chat-001", "chat-002", "chat-003"];

// BROKEN — forEach does not await the async callbacks
chatIds.forEach(async function(chatId) {
  const messages = await loadMessages(chatId);
  console.log(messages); // order is unpredictable, errors are swallowed
});

forEach fires all callbacks but does not wait for the Promises they return. Your code after the forEach runs before any of the fetches complete. Instead, use for...of with await:

// CORRECT — for...of respects await
async function loadAllChats(chatIds) {
  for (const chatId of chatIds) {
    const messages = await loadMessages(chatId);
    console.log("Loaded:", chatId, messages.length, "messages");
  }
}

// Or, if order doesn't matter, load them all in parallel:
async function loadAllChatsParallel(chatIds) {
  const allMessages = await Promise.all(
    chatIds.map(function(chatId) { return loadMessages(chatId); })
  );
  console.log("All loaded:", allMessages);
}

7. A complete WhatsApp example

Let's put everything together. When a user taps on a contact in your app, you want to open the chat screen. That means loading messages and the user's profile in parallel, showing both, and handling any network failure gracefully.

// ─── Simulated API layer ───────────────────────────────────────────────────

function fetchMessages(chatId) {
  return new Promise(function(resolve, reject) {
    setTimeout(function() {
      if (!chatId) {
        reject(new Error("Invalid chatId"));
        return;
      }
      resolve([
        { id: "m1", sender: "Priya",  text: "Hey! Did you see the match?",    time: "10:02" },
        { id: "m2", sender: "Ashish", text: "Yes! What a final 10 minutes.",   time: "10:04" },
        { id: "m3", sender: "Priya",  text: "I almost had a heart attack lol", time: "10:05" }
      ]);
    }, 450);
  });
}

function fetchUserProfile(userId) {
  return new Promise(function(resolve, reject) {
    setTimeout(function() {
      if (!userId) {
        reject(new Error("Invalid userId"));
        return;
      }
      resolve({
        id:     userId,
        name:   "Priya Sharma",
        avatar: "priya-avatar.jpg",
        status: "online",
        lastSeen: null
      });
    }, 280);
  });
}

// ─── UI helpers (would be React Native components in your real app) ─────────

function displayChatHeader(profile) {
  console.log("─── Chat Header ────────────────────────");
  console.log("Name:   ", profile.name);
  console.log("Status: ", profile.status === "online" ? "Online" : "Last seen " + profile.lastSeen);
}

function displayMessages(messages) {
  console.log("─── Messages ───────────────────────────");
  for (const msg of messages) {
    console.log("[" + msg.time + "] " + msg.sender + ": " + msg.text);
  }
}

function showLoadingSpinner() {
  console.log("Loading chat...");
}

function hideLoadingSpinner() {
  console.log("Done loading.");
}

function showErrorScreen(message) {
  console.log("ERROR: " + message);
}

// ─── Main function: called when user taps a contact ─────────────────────────

async function loadChatScreen(chatId, userId) {
  showLoadingSpinner();

  try {
    // Fetch messages AND profile at the same time — not one after the other
    const [messages, profile] = await Promise.all([
      fetchMessages(chatId),
      fetchUserProfile(userId)
    ]);

    hideLoadingSpinner();

    // Both fetches succeeded — render the screen
    displayChatHeader(profile);
    displayMessages(messages);

  } catch (error) {
    hideLoadingSpinner();
    showErrorScreen("Could not load chat. Please check your connection.");
    console.error("loadChatScreen failed:", error.message);
  }
}

// ─── Entry point ─────────────────────────────────────────────────────────────
loadChatScreen("chat-priya-001", "user-priya-002");

Run this in your browser console (F12) and you'll see the spinner message, then the header and messages — loaded in parallel in under 500 ms total.

What this pattern gives you
  • Loading spinner while both fetches run in parallel
  • A single catch block handles any failure from either fetch
  • User sees a friendly error message, not a crash
  • The async/await syntax reads almost like a step-by-step recipe

In your WhatsApp clone, every screen that loads remote data will follow this exact shape: showSpinner → Promise.all → hideSpinner + render, wrapped in try/catch.
