Lesson 9

Promises & Async/Await

Core JS ~40 min read Intermediate
Why this matters for Token

Nothing in Token happens instantly. Issuing a token is a round trip to your API. Opening the token list is a round trip. Redeeming a code, sending a message, revoking access — all round trips, each taking anywhere from 40 milliseconds on wifi to several seconds on a bad mobile connection in a lift.

JavaScript runs your code on one thread. If waiting for the network blocked that thread, the entire app would freeze — no scrolling, no typing, no cancel button — until the server replied. So JavaScript does not wait. It starts the request, carries on, and comes back to you when the answer arrives.

This lesson is about how you write code that comes back later. It is also where a specific bug is born: forgetting one await and getting a Promise where you expected a token. You will meet that bug deliberately, in a playground, rather than at midnight.

1. Synchronous vs asynchronous

Synchronous code runs top to bottom, each line finishing before the next begins. That is every program you have written so far.

The problem is that one thread means one queue. While a synchronous line is running, nothing else can — no click handler, no repaint, nothing.

Try it yourself — feel the freeze

The loop below does nothing for 400 milliseconds, on purpose. Notice that the "meanwhile" message cannot print during it, even though it was scheduled first.

400 ms is already a visible stutter. A network request is routinely ten times that. Blocking the thread on one is not a performance problem, it is a broken app.

2. Callbacks — the original answer

The first solution was to hand over a function to be called when the work finishes:

fetchToken("MERC-8GH2-KP4X", function (token) {
  console.log("got", token.code);
});

That works. It stops working well when one result feeds the next.

Try it yourself — callback hell

Three steps, three levels of indentation, and the error handling has to be repeated at every level. Six steps would run off the side of the screen. This shape has a name — the pyramid of doom — and Promises exist because of it.

3. Promises

A Promise is an object representing a value that is not available yet. It is in one of three states:

  • pending — the work is still going
  • fulfilled — it finished, and there is a value
  • rejected — it failed, and there is an error

It settles once. A fulfilled Promise never becomes rejected, and a settled Promise never changes value — which is what makes it safe to hand around.

function fetchToken(code) {
  return new Promise(function (resolve, reject) {
    setTimeout(function () {
      if (code === "") {
        reject(new Error("No code given"));
        return;
      }
      resolve({ code: code, issuedTo: "Corner Store", revoked: false });
    }, 300);
  });
}

fetchToken("MERC-8GH2-KP4X")
  .then(function (token) { console.log("got", token.code); })
  .catch(function (error) { console.log("failed:", error.message); });

Try it yourself

Chaining

The payoff: .then() returns a new Promise, so each step's return value becomes the next step's input, and one .catch() at the end covers every step above it.

Try it yourself

4. async / await

Chaining is a big improvement on nesting, but it still does not read like the sequence it is. async/await is syntax over exactly the same Promises:

  • async before a function means it always returns a Promise
  • await pauses inside that function until a Promise settles, and gives you the value
async function showToken(code) {
  const token = await fetchToken(code);
  console.log("got", token.code);
}

"Pauses" is worth being precise about: it pauses that function, not the thread. Everything else on the page keeps running. That is the whole difference between await and the blocking loop in section 1.

Try it yourself

async functions always return a Promise

Even when you return a plain string:

async function getCode() {
  return "MERC-8GH2-KP4X";
}

console.log(typeof getCode());   // "object" — a Promise, not a string
The forgotten await — the bug you will actually write

Leave out one await and you get a Promise where you expected a value. Nothing throws. The variable is simply an object, and every property you read off it is undefined.

It is worth meeting this on purpose, because the symptom — undefined appearing three functions away from the missing keyword — points nowhere near the cause.

Try it yourself — this one is broken on purpose

Run it and look at what token.code gives you. Then add the missing await on the marked line and run again.

5. Error handling

With await, a rejected Promise throws — so ordinary try/catch works:

async function showToken(code) {
  try {
    const token = await fetchToken(code);
    console.log("got", token.code);
  } catch (error) {
    console.log("failed:", error.message);
  }
}
An unhandled rejection is not a crash you will notice

Forget the try/catch and the Promise rejects with nobody listening. In Node that terminates the process. In a browser it logs to the console and the app carries on in a half-built state — the spinner spins forever and no error is ever shown to the user.

Try it yourself

6. Promise.all — waiting for several at once

The token detail screen needs two things: the token itself, and its redemption history. They do not depend on each other, so waiting for one before starting the other doubles the time on screen for no reason.

// Sequential — 300ms then 200ms = 500ms
const detail      = await fetchDetail(code);
const redemptions = await fetchRedemptions(code);

// Parallel — both start now, done in 300ms
const [detail, redemptions] = await Promise.all([
  fetchDetail(code),
  fetchRedemptions(code)
]);

Promise.all takes an array of Promises and returns one Promise, which fulfils with an array of all the values — in the order you passed them in, not the order they finished. If any one of them rejects, the whole thing rejects immediately with that error.

Try it yourself

Watch the order the log lines come out in. Both requests start before either finishes — that is what parallel means here.

When not to use it

Promise.all is all-or-nothing: one failure discards every other result. That is right for a screen that cannot render without both pieces. It is wrong when the pieces are independent and you would rather show what you have — for that there is Promise.allSettled, which waits for every Promise and reports each outcome separately.

What to notice
  • The spinner goes up before the await, and the try starts before it too. Both are deliberate: the user sees something immediately, and every failure lands in one place.
  • One catch handles a failure from either request, because Promise.all rejects as soon as any of them does.
  • The error path renders a message. Compare with forgetting the catch: the spinner would spin forever and the only sign of trouble would be in the console.
  • Every screen in Token that loads remote data has this shape: show spinner → Promise.all → render, wrapped in try/catch.

Bridge to React Native: the same shape, held in state

In the app the three outcomes — loading, loaded, failed — become state, and the render is React's job:

function TokenDetailScreen({ code }) {
  const [state, setState] = React.useState({ status: "loading" });

  React.useEffect(function () {
    let cancelled = false;

    async function load() {
      try {
        const [detail, redemptions] = await Promise.all([
          api.fetchDetail(code),
          api.fetchRedemptions(code)
        ]);
        if (!cancelled) setState({ status: "ok", detail, redemptions });
      } catch (error) {
        if (!cancelled) setState({ status: "error", message: error.message });
      }
    }

    load();
    return function () { cancelled = true; };   // cleanup, as in lesson 8
  }, [code]);

  if (state.status === "loading") return <Spinner />;
  if (state.status === "error")   return <ErrorView message={state.message} />;
  return <TokenDetail detail={state.detail} redemptions={state.redemptions} />;
}

The cancelled flag is the async version of lesson 8's removeEventListener. If the user leaves the screen while the requests are in flight, the responses still arrive — and calling setState on a screen that is gone is a bug. The cleanup function does not cancel the network request; it makes the answer irrelevant when it lands.

Now build it yourself

This is the loader from the mini-project, on its own. It is worth writing by hand once, because every data-loading screen in Token is a variation of it — and because the two easy mistakes here (running the requests one after another, and letting a rejection escape) are both invisible when everything works.
