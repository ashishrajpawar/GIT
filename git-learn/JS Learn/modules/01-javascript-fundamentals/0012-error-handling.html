Lesson 12

Error Handling

Core JavaScript ~20 min read Beginner–Intermediate
Why this matters for your WhatsApp clone

Your app will talk to Firebase over the internet — and the internet is unreliable. A user's phone will lose signal mid-message. Firebase will occasionally return an error. A user will type something unexpected. Without error handling, any of these events crash your app and leave the user staring at a blank screen. Error handling is what separates a hobby project from an app people actually trust. After this lesson you'll know exactly how to catch failures gracefully and show a helpful message instead.

1. What is an error?

An error is JavaScript's way of saying "something went wrong and I can't continue." When an unhandled error occurs, JavaScript stops executing your code at that point. In a browser this shows up in the console. In a React Native app it typically crashes the screen.

There are two main kinds of errors you'll deal with:

  • Runtime errors — errors that happen while the code is running, usually because something unexpected occurred (network failure, missing data, wrong type).
  • Logic errors — code that runs without crashing but produces the wrong result. Error handling won't help here — you need debugging skills for these.

Common runtime errors you'll see in your WhatsApp clone:

// TypeError — accessing a property on null or undefined
const user = null;
console.log(user.name); // TypeError: Cannot read properties of null

// ReferenceError — using a variable that doesn't exist
console.log(unknownVariable); // ReferenceError: unknownVariable is not defined

// Network error — fetch/Firebase call fails
const data = await firebase.firestore().collection("chats").get();
// Could throw: FirebaseError: Failed to get documents from the server

2. try/catch — the core tool

The try/catch block is the fundamental tool for handling errors. You put the code that might fail inside try. If an error occurs, JavaScript jumps to catch instead of crashing.

try {
  // Code that might throw an error
  const result = someRiskyOperation();
  console.log(result);
} catch (error) {
  // This block runs only if an error was thrown above
  console.error("Something went wrong:", error.message);
}

// Code here continues regardless of whether an error occurred

The error object

The error variable in the catch block is an object with useful properties:

try {
  const user = null;
  console.log(user.name); // throws TypeError
} catch (error) {
  console.log(error.name);    // "TypeError"
  console.log(error.message); // "Cannot read properties of null (reading 'name')"
  console.log(error.stack);   // Full stack trace — useful for debugging
}

try/catch/finally

The optional finally block runs always — whether an error occurred or not. It's the right place to put cleanup code like hiding a loading spinner.

async function loadMessages(chatId) {
  showLoadingSpinner(); // start spinner before trying

  try {
    const messages = await fetchFromFirebase(chatId);
    displayMessages(messages);
  } catch (error) {
    showErrorBanner("Couldn't load messages. Check your connection.");
    console.error("loadMessages failed:", error.message);
  } finally {
    hideLoadingSpinner(); // ALWAYS hide the spinner — success or failure
  }
}
finally is perfect for loading spinners

Without finally, you'd have to call hideLoadingSpinner() in both the try and the catch block. With finally you write it once and it runs no matter what. Use this pattern for every async data load in your app.

3. Throwing your own errors

You can throw your own errors using the throw keyword. This is useful for validating input and signaling problems in your own functions.

function sendMessage(chatId, text) {
  // Validate inputs before doing anything
  if (!chatId) {
    throw new Error("chatId is required to send a message");
  }
  if (!text || text.trim() === "") {
    throw new Error("Message text cannot be empty");
  }
  if (text.length > 4096) {
    throw new Error("Message is too long (max 4096 characters)");
  }

  // If we get here, inputs are valid — proceed
  return saveMessageToFirebase(chatId, text);
}

// The caller handles the error
try {
  await sendMessage("chat-001", ""); // empty text — will throw
} catch (error) {
  console.error(error.message); // "Message text cannot be empty"
  showToast(error.message);     // show it to the user
}
Always throw Error objects, not strings

You can technically throw "something went wrong" but don't — throw new Error("something went wrong") instead. The Error object includes a stack trace, which tells you exactly which line threw the error. That's invaluable when debugging.

4. Error handling with async/await

You saw this briefly in Lesson 9. Here's the full picture with all the patterns you'll use in your app.

Basic pattern — wrap every await in try/catch

async function openChat(chatId, userId) {
  try {
    const [messages, profile] = await Promise.all([
      fetchMessages(chatId),
      fetchUserProfile(userId)
    ]);

    renderChatScreen(messages, profile);

  } catch (error) {
    // This catches errors from EITHER fetchMessages or fetchUserProfile
    showErrorScreen("Failed to open chat. Please try again.");
    console.error("openChat error:", error.message);
  }
}

Different errors need different responses

Sometimes you want to respond differently depending on what went wrong — a network error vs a "not found" error vs a permissions error.

async function loadUserProfile(userId) {
  try {
    const profile = await fetchProfile(userId);
    return profile;

  } catch (error) {
    // Check the error message or type to decide what to do
    if (error.code === "permission-denied") {
      // Firebase-specific error code
      showToast("You don't have permission to view this profile.");
      return null;
    }

    if (error.message.includes("network")) {
      showToast("No internet connection. Please check your signal.");
      return null;
    }

    // Unknown error — log it and show a generic message
    console.error("Unexpected error in loadUserProfile:", error);
    showToast("Something went wrong. Please try again.");
    return null;
  }
}

Don't swallow errors silently

// BAD — catches the error but does nothing with it
async function badExample(chatId) {
  try {
    const messages = await fetchMessages(chatId);
    displayMessages(messages);
  } catch (error) {
    // Silent! The user sees nothing, you learn nothing.
  }
}

// GOOD — always at minimum log the error
async function goodExample(chatId) {
  try {
    const messages = await fetchMessages(chatId);
    displayMessages(messages);
  } catch (error) {
    console.error("fetchMessages failed:", error); // log for debugging
    showErrorBanner("Couldn't load messages.");     // inform the user
  }
}

5. Firebase-specific error handling

Firebase has its own error codes that give you precise information about what went wrong. Knowing the common ones will save you hours of debugging.

import { signInWithEmailAndPassword } from "firebase/auth";

async function loginUser(email, password) {
  try {
    const userCredential = await signInWithEmailAndPassword(auth, email, password);
    return userCredential.user;

  } catch (error) {
    // Firebase puts the error code in error.code
    switch (error.code) {
      case "auth/user-not-found":
        showError("No account found with this email address.");
        break;

      case "auth/wrong-password":
        showError("Incorrect password. Please try again.");
        break;

      case "auth/too-many-requests":
        showError("Too many attempts. Please wait a few minutes.");
        break;

      case "auth/network-request-failed":
        showError("No internet connection. Please check your signal.");
        break;

      default:
        showError("Login failed. Please try again.");
        console.error("Unexpected login error:", error.code, error.message);
    }

    return null;
  }
}
Common Firebase error codes to know
  • auth/user-not-found — no account with that email
  • auth/wrong-password — incorrect password
  • auth/email-already-in-use — registration with existing email
  • auth/network-request-failed — no internet connection
  • permission-denied — Firestore security rules blocked the read/write
  • unavailable — Firestore is temporarily unavailable

6. Validating user input — prevent errors before they happen

The best error is the one that never happens. Validating user input before sending it to Firebase prevents a whole class of errors.

function validateMessage(text) {
  const errors = [];

  if (!text || text.trim() === "") {
    errors.push("Message cannot be empty.");
  }

  if (text.length > 4096) {
    errors.push(`Message is too long (${text.length}/4096 characters).`);
  }

  return errors; // empty array means valid
}

function validateEmail(email) {
  // Simple regex check — good enough for basic validation
  const emailRegex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
  return emailRegex.test(email);
}

// Usage in a send-message handler
async function handleSendMessage(chatId, text) {
  const errors = validateMessage(text);

  if (errors.length > 0) {
    showValidationError(errors[0]); // show the first error to the user
    return; // stop here — don't send to Firebase
  }

  try {
    await sendMessageToFirebase(chatId, text.trim());
  } catch (error) {
    showToast("Couldn't send message. Please try again.");
    console.error("sendMessage error:", error);
  }
}

7. A complete WhatsApp example — sign in with full error handling

// ─── Validation ───────────────────────────────────────────────────────────

function validateLoginForm(email, password) {
  if (!email || email.trim() === "") {
    throw new Error("Please enter your email address.");
  }

  const emailRegex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
  if (!emailRegex.test(email)) {
    throw new Error("Please enter a valid email address.");
  }

  if (!password || password.length < 6) {
    throw new Error("Password must be at least 6 characters.");
  }
}

// ─── Firebase error mapper ─────────────────────────────────────────────────

function getLoginErrorMessage(firebaseError) {
  switch (firebaseError.code) {
    case "auth/user-not-found":
      return "No account found with this email. Would you like to sign up?";
    case "auth/wrong-password":
      return "Incorrect password. Please try again.";
    case "auth/too-many-requests":
      return "Account temporarily locked due to too many attempts. Try again in a few minutes.";
    case "auth/network-request-failed":
      return "No internet connection. Please check your signal and try again.";
    default:
      return "Sign in failed. Please try again.";
  }
}

// ─── Main login function ───────────────────────────────────────────────────

async function handleLogin(email, password) {
  // 1. Validate inputs first — before touching Firebase
  try {
    validateLoginForm(email, password);
  } catch (validationError) {
    showFormError(validationError.message);
    return; // stop here
  }

  // 2. Show loading state
  setButtonLoading(true);

  // 3. Attempt Firebase login
  try {
    const userCredential = await signInWithEmailAndPassword(auth, email.trim(), password);
    const user = userCredential.user;

    console.log("Logged in as:", user.email);
    navigateToChatList(); // go to the main screen

  } catch (firebaseError) {
    const message = getLoginErrorMessage(firebaseError);
    showFormError(message);
    console.error("Login error:", firebaseError.code, firebaseError.message);

  } finally {
    setButtonLoading(false); // always re-enable the button
  }
}

// ─── Simulate running it ───────────────────────────────────────────────────

// Test 1: Empty email
handleLogin("", "password123");
// Shows: "Please enter your email address."

// Test 2: Valid form, wrong password (would return Firebase error in real app)
handleLogin("ashish@example.com", "wrongpassword");
// Would show: "Incorrect password. Please try again."

This is a production-quality login handler. Every React Native app you ever build will follow this exact structure: validate → show loading → try Firebase → catch specific errors → finally hide loading.
