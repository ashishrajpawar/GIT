Lesson 12

Error Handling

Core JS ~35 min read Beginner
Why this matters for Token

Failure is the normal case, not the exception. A token holder types a code with a typo. The token was revoked an hour ago. The phone is on a train and the request never lands. The server is mid-deploy.

In every one of those the code has to answer a question: what do we tell the person holding the token? That answer is the feature. A redemption page that says "something went wrong" for all four gives someone standing at a shop counter no idea whether to retype the code, ask for a new one, or move to a window with better signal.

And one of those answers has to be deliberately vague. Telling a stranger "that code doesn't exist" versus "that code was revoked" sounds more helpful — and it hands them a way to test codes until they find a real one. This lesson ends with that trade-off, because it is the one that is genuinely specific to a system built on secret codes.

1. What an error actually is

An error is an ordinary object with a few standard properties. When something throws, that object is what your catch receives.

const error = new Error("Token not found");

console.log(error.name);      // "Error"
console.log(error.message);   // "Token not found"
console.log(error.stack);     // where it was created, as text

JavaScript has several built-in types, and the name tells you which:

  • TypeError — reading a property of undefined, calling something that is not a function
  • ReferenceError — using a variable that does not exist
  • SyntaxError — the code did not parse
  • RangeError — a number outside its allowed range

You have met most of those already in this module, usually as the second half of a trap: querySelector returns null, and the TypeError lands on the next line.

Try it yourself

2. try / catch / finally

You used try/catch around await in lesson 9. Here is the whole shape, including the part that lesson did not cover.

try {
  const session = await api.redeem(code);
  showConversation(session);
} catch (error) {
  showError(error.message);
} finally {
  hideSpinner();          // runs whether it worked or not
}

finally runs on every path out of the block — success, failure, and even an early return from inside the try. That makes it the right home for cleanup that must happen regardless: hiding a spinner, re-enabling a button, closing a connection.

Why not just put the cleanup after the try/catch?

Often you can, and should. finally earns its place when the try block can return — then the code after the block never runs, and the spinner stays on screen forever. It is also the only version that survives someone later adding a return to the catch.

Try it yourself

3. Throwing your own

throw stops the current function immediately and hands an error to the nearest catch up the call stack.

function parseCode(raw) {
  const clean = raw.trim().toUpperCase();

  if (clean === "") {
    throw new Error("No code entered");
  }

  if (clean.length !== 14) {
    throw new Error("A token code is 12 characters in three groups");
  }

  return clean;
}
Always throw an Error, never a string

throw "something went wrong" is legal JavaScript and it is a trap. A thrown string has no .message, no .name and no .stack — so the catch that logs error.message logs undefined, and you have thrown away the one thing that would have told you where it came from.

Try it yourself

4. Custom error types — so the caller can tell them apart

This is the section that changes how you write the rest of the app.

A catch block receives every failure the same way. But "the code was mistyped", "the token was revoked" and "the network is down" need three completely different responses — retype, ask for a new token, try again in a moment. If all your errors are plain Error objects, the only way to tell them apart is to read the message text, and matching on prose breaks the first time someone rewords it.

So give them types:

class TokenError extends Error {
  constructor(message) {
    super(message);
    this.name = "TokenError";
  }
}

class NotFoundError extends TokenError {
  constructor(message) {
    super(message);
    this.name = "NotFoundError";
  }
}

class NetworkError extends TokenError {
  constructor(message) {
    super(message);
    this.name = "NetworkError";
    this.retryable = true;      // custom errors can carry data, too
  }
}

Now the caller can branch on the type rather than the wording:

try {
  await api.redeem(code);
} catch (error) {
  if (error instanceof NetworkError) {
    showRetry("Couldn't reach the server.");
  } else if (error instanceof TokenError) {
    showMessage(error.message);
  } else {
    throw error;               // not ours - let it go up
  }
}
That last else is the important one

If the try block contains a typo of your own — a TypeError from a misspelt property — you do not want to catch it and show the user "couldn't reach the server". Re-throwing anything you did not expect keeps your own bugs visible instead of disguising them as network problems.

5. Errors that cross the network

Token's API is a separate program on a separate machine. When redemption fails there, the failure arrives as an HTTP status and a JSON body — and turning that back into a typed error is the client's job.

async function redeem(code) {
  let response;

  try {
    response = await fetch("/api/redeem", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ code: code })
    });
  } catch (cause) {
    // fetch only rejects when the request never completed at all
    throw new NetworkError("Could not reach the server");
  }

  if (response.ok) {
    return response.json();
  }

  const body = await response.json().catch(function () { return {}; });

  if (response.status === 404) throw new NotFoundError(body.message ?? "Unknown code");
  if (response.status === 410) throw new RevokedError(body.message ?? "Token revoked");
  if (response.status === 429) throw new RateLimitedError("Too many attempts");

  throw new TokenError(body.message ?? "Redemption failed");
}
fetch does not reject on 404

A common surprise: fetch only rejects when the request could not be made at all — no connection, DNS failure, request cancelled. A response of 404, 500 or 403 is a successful request that happens to carry a bad status, so it lands in the try as a normal result. You have to check response.ok yourself, which is why the code above does.

The one where being helpful is the bug

The four errors above are not equally safe to show a stranger.

A token code is 12 characters from a 31-character alphabet, so guessing one at random is hopeless. But that argument only holds while a guess tells the attacker nothing. If the redemption page answers "no such token" for a made-up code and "this token has been revoked" for a real one, then every guess returns one bit of information — and the page has become a tool for finding which codes exist.

// LEAKS: the two answers distinguish a real code from an invented one
if (error instanceof NotFoundError) return "No token with that code.";
if (error instanceof RevokedError)  return "That token has been revoked.";

// SAFE: a stranger learns only that it did not work
if (error instanceof NotFoundError) return "That code can't be used.";
if (error instanceof RevokedError)  return "That code can't be used.";
The distinction is still useful — just not to the holder

Your own logs should absolutely record which of the two it was; that is how you diagnose a support ticket. The rule is about what crosses back to a person you have not authenticated. Keep the detail server-side, and give the holder one message.

The same reasoning is why a sign-in form says "email or password is incorrect" rather than telling you which one was wrong.

6. Validate before you call

The cheapest error is the one that never reaches the network. If a code is obviously malformed, there is no point spending a round trip — and a rate limiter on the server counts that attempt against the holder.

const ALPHABET = /^[23456789ABCDEFGHJKMNPQRSTUVWXYZ]{4}(-[23456789ABCDEFGHJKMNPQRSTUVWXYZ]{4}){2}$/;

function validateCode(raw) {
  const clean = raw.trim().toUpperCase();

  if (clean === "")            return { ok: false, reason: "Enter the code from your invitation." };
  if (!ALPHABET.test(clean))   return { ok: false, reason: "That code doesn't look right — check for typos." };

  return { ok: true, code: clean };
}
Returning a result versus throwing

Both are correct, and the choice is about who the failure is for. A user typing a malformed code is an expected outcome you want to render, so returning a result object is natural. A programmer calling your function wrongly is a bug, and throwing is right — it should be loud.

    // ── Error types ────────────────────────────────────────────────────
    class TokenError extends Error {
      constructor(message) { super(message); this.name = "TokenError"; }
    }
    class NotFoundError extends TokenError {
      constructor(m) { super(m); this.name = "NotFoundError"; }
    }
    class RevokedError extends TokenError {
      constructor(m) { super(m); this.name = "RevokedError"; }
    }
    class NetworkError extends TokenError {

    }

    // ── A fake API you can steer ───────────────────────────────────────
    let mode = "ok";
    const wait = (ms) => new Promise((r) => setTimeout(r, ms));

    async function apiRedeem(code) {
      await wait(400);
      if (mode === "notFound") throw new NotFoundError("no such token: " + code);
      if (mode === "revoked")  throw new RevokedError("token revoked");
      if (mode === "network")  throw new NetworkError("connection failed");

      const clean = String(raw ?? "").trim().toUpperCase();
      if (clean === "") return { ok: false, reason: "Enter the code from your invitation." };
      if (!ALPHABET.test(clean)) {
        return { ok: false, reason: "That code doesn't look right — check for typos." };

      return { ok: true, code: clean };

    const inputEl = document.getElementById("code");
    const submitEl = document.getElementById("submit");

      box.className = "msg " + kind;

      if (retryable) {

        again.className = "retry";
        again.textContent = "Try again";
        again.addEventListener("click", redeem);
        outEl.appendChild(again);
      }

      const check = validateCode(inputEl.value);
      if (!check.ok) {
        show("error", check.reason, false);
        return;                        // never reached the network

      submitEl.disabled = true;
      show("ok", "Checking…", false);

What to notice
  • notFound and revoked produce an identical message on screen, and different detail in the console. That is the security point of section 5, working.
  • network is the only one that offers a Try again button, because it is the only one where trying again could plausibly help.
  • bug shows an honest message and re-throws, so the real TypeError still reaches the console. Swallowing it would have made a typo look like a server problem forever.
  • Typing ABC never reaches the API at all — validation catches it, and the holder is not charged an attempt against the rate limit.
  • finally re-enables the button on every path, including the one that re-throws. Without it, the bug case would leave the form permanently disabled.

Bridge to React Native: errors as state

The pattern from lesson 9 again, with the error kept as data rather than shown from inside the handler:

const [state, setState] = React.useState({ status: "idle" });

async function onRedeem(raw) {
  const check = validateCode(raw);
  if (!check.ok) {
    setState({ status: "error", message: check.reason, retryable: false });
    return;
  }

  setState({ status: "loading" });

  try {
    const result = await api.redeem(check.code);
    setState({ status: "ok", session: result.session });
  } catch (error) {
    if (error instanceof NetworkError) {
      setState({ status: "error", message: "Couldn't reach the server.", retryable: true });
    } else if (error instanceof TokenError) {
      setState({ status: "error", message: "That code can't be used.", retryable: false });
    } else {
      setState({ status: "error", message: "Something went wrong.", retryable: false });
      throw error;
    }
  }
}

React also has error boundaries — components that catch a crash during rendering and show a fallback instead of a blank screen. They catch render-time errors only, not the ones from an await in an event handler, so they complement the try/catch above rather than replacing it. You will build both in Track A.

The redemption flow's decision layer, on its own: given a code and an API that can fail in several ways, decide what the holder is told.
