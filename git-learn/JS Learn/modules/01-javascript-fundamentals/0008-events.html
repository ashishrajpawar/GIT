Lesson 8

Events

Browser JS ~35 min read Beginner
Why this matters for Token

Lesson 7 gave you a page you can change. This lesson is what makes it change when somebody does something.

Every action in Token is an event. Tapping Revoke on a token. Typing into the redemption page's message box. Pressing Enter to send. Tapping a row to open it. Without events your app is a photograph.

One pattern in this lesson matters more than the rest, and it is the one this lesson's exercise is built around: event delegation. A token list is not a fixed thing — rows appear when a token is issued and disappear when one is deleted. If every row carries its own listener, every new row needs wiring up and every removed row leaks one. One listener on the list, which works out which row was clicked, is the pattern that survives contact with a list that changes.

What is an event?

The browser constantly watches what happens — clicks, key presses, form submissions, timers going off. When something happens, it fires an event: a signal saying "this just happened".

Your job is to say: "when that event fires, run this function." That function is an event handler. The browser calls it for you, at the moment the event fires.

The important consequence: your code does not sit and wait. You register a handler and your code finishes. Later — maybe a second later, maybe never — the browser calls back into it. That inversion is what makes UI programming different from the scripts you have written so far.

addEventListener — attaching a handler

element.addEventListener(eventType, handlerFunction);

With a real example — the Revoke button on a token's detail screen:

const revokeBtn = document.getElementById("revoke-btn");

function handleRevokeClick() {
  console.log("Revoke tapped");
}

revokeBtn.addEventListener("click", handleRevokeClick);

The event types you will use constantly:

  • "click" — button pressed
  • "input" — a text field's value changed (fires on every keystroke)
  • "keydown" — a key went down (fires before the character appears)
  • "submit" — a form was submitted
  • "focus" / "blur" — a field gained / lost focus
No parentheses — this is the bug you will write

handleRevokeClick is the function. handleRevokeClick() is the result of running it right now.

// WRONG — runs immediately, registers its return value (undefined)
revokeBtn.addEventListener("click", handleRevokeClick());

// RIGHT — hands over the function itself
revokeBtn.addEventListener("click", handleRevokeClick);

The wrong version is nasty because it is not silent — the handler does run, once, immediately, at page load. So you see your log line and assume it worked. Then clicking does nothing forever.

Try it yourself — this one is broken on purpose

Run it as-is and read the output carefully: the message appears, but it appears before the click. Then remove the parentheses on the marked line and run again.

The React Native parallel

In the app you will write <TouchableOpacity onPress={handleRevokeClick}> instead of addEventListener("click", ...). Note that it is {handleRevokeClick}, not {handleRevokeClick()} — the exact same distinction, and the exact same bug.

The event object

When the browser calls your handler it passes one argument: the event object, carrying the details of what happened.

revokeBtn.addEventListener("click", function (event) {
  console.log(event.type);     // "click"
  console.log(event.target);   // the element that was clicked
});

event.target — what it happened to

The element the event actually started on. With one handler covering many elements, this is how you tell which one.

event.currentTarget — what is listening

The element whose listener is running right now. These differ the moment an event travels upward, which is the next section — and confusing them is the usual reason a delegation handler acts on the wrong element.

event.key — which key

On keyboard events: "Enter", "Backspace", "a", and so on.

event.preventDefault() — stop the browser's own behaviour

Some events have a built-in browser action attached. Submitting a form navigates the page. Clicking a link follows it. preventDefault() cancels that, leaving your handler in charge.

const composeForm = document.getElementById("compose-form");

composeForm.addEventListener("submit", function (event) {
  event.preventDefault();   // without this, the page reloads
  sendMessage();
});
Forgetting preventDefault on a form

A form submit reloads the page by default. On the redemption page that throws away the conversation and re-runs everything from scratch — and because the reload looks like a flicker, it reads as "my code randomly does nothing" rather than as a page load.

Input events — reacting as they type

The "input" event fires every time a field's value changes — every keystroke, every paste, every deletion.

const messageInput = document.getElementById("message-input");

messageInput.addEventListener("input", function (event) {
  const text = event.target.value;
  console.log("now:", text);
});

Note event.target.value: the target is the input element, and .value is its current text — the property from lesson 7.

Setting .value from code does not fire it

"input" means "a person changed this". Assigning messageInput.value = "" in your own code changes the field but fires nothing — which is exactly what you want when clearing the box after sending, and exactly what confuses you the first time you expect a handler to run.

Try it yourself

Keyboard events — Enter to send

messageInput.addEventListener("keydown", function (event) {
  if (event.key === "Enter" && !event.shiftKey) {
    event.preventDefault();       // no newline in the box
    sendMessage(messageInput.value.trim());
    messageInput.value = "";
  }
  // Shift+Enter falls through, so it inserts a newline as usual
});

event.shiftKey is true when Shift was held. The pattern above — Enter sends, Shift+Enter makes a new line — is what every messaging app does, and users notice immediately when it is missing.

Try it yourself

Event delegation — one listener for a changing list

Here is the problem. A token list has 40 rows, each with a Revoke button. Attach a listener to each button and you have 40 listeners — and the moment a new token is issued, its button has none, because your setup code ran before that row existed.

The fix comes from how events travel. An event fires on the element it happened to, then bubbles upward through every ancestor. So a click on a button inside a row inside a list also reaches the list. One listener there sees every click in the whole list, including in rows that did not exist when you attached it.

const list = document.getElementById("token-list");

list.addEventListener("click", function (event) {
  // Which row did this click land in?
  const row = event.target.closest(".token-row");
  if (row === null) return;          // clicked the list, but not a row

  // Was it the Revoke button specifically?
  if (!event.target.classList.contains("revoke-btn")) return;

  console.log("revoking", row.dataset.tokenCode);
});

Two pieces make this work:

  • event.target.closest(".token-row") walks up from whatever was clicked until it finds a matching ancestor. That matters because the click might land on a <span> inside the button, not the button itself.
  • row.dataset.tokenCode reads the data-token-code attribute. Attaching the identity to the element in markup means the handler never has to guess which token a row represents.
target vs currentTarget, concretely

Inside that handler, event.currentTarget is always the list — the element listening. event.target is the button, or the span inside it, or whatever was actually clicked. Use target to find out what happened; use currentTarget when you want the container.

Not every event bubbles. focus and blur do not, so they cannot be delegated this way.

Try it yourself

Note the last part: a row is added after the listener was attached, and it works anyway. That is the entire point.

Removing listeners

Listeners do not disappear on their own. removeEventListener takes them off — and it needs the same function reference you added:

function handleKeydown(event) { /* ... */ }

messageInput.addEventListener("keydown", handleKeydown);
messageInput.removeEventListener("keydown", handleKeydown);   // works
An anonymous handler can never be removed

Every time you write a function expression you create a new function object. So the one you pass to removeEventListener is never the one you added, and the call quietly does nothing — no error, no warning.

// Cannot ever be removed — these are two different functions
input.addEventListener("keydown", function (e) { /* ... */ });
input.removeEventListener("keydown", function (e) { /* ... */ });

Try it yourself — one of these removals silently fails

Where this goes in the app

In React you will do this in a useEffect cleanup — the function you return runs when the component unmounts:

useEffect(() => {
  socket.on("token:revoked", handleRevoked);

  return () => {
    socket.off("token:revoked", handleRevoked);
  };
}, []);

Same rule, same trap: it has to be the same function reference both times. This is why the handler is a named value rather than an inline arrow.

    const form      = document.getElementById("compose-form");

    const list      = document.getElementById("message-list");

    let nextId = 1;
    let typingTimer = null;

    // 1. Typing indicator, driven by the input event
    input.addEventListener("input", function (event) {
      const text = event.target.value;

      if (text === "") {
        indicator.textContent = "";
        return;
      }

      indicator.textContent = "typing…";
      clearTimeout(typingTimer);
      typingTimer = setTimeout(function () {
        indicator.textContent = "";

      const text = input.value.trim();

      input.value = "";          // note: this does NOT fire the input event
      indicator.textContent = "";
      clearTimeout(typingTimer);
      input.focus();

      // Pretend the other side replies
      setTimeout(function () {
        appendMessage("Got it — thanks.", "incoming");
      }, 1400);
    }

    function appendMessage(text, direction) {
      const el = document.createElement("li");
      el.classList.add("message");
      el.classList.add(direction);
      el.dataset.messageId = nextId;
      nextId = nextId + 1;

      el.textContent = text;     // text, never innerHTML — a stranger typed it

      list.appendChild(el);
      list.scrollTop = list.scrollHeight;
    }

    appendMessage("Hi — I got your token.", "incoming");

What to notice
  • There are two ways to send — Enter and the Send button — and they share one sendMessage(). Duplicating that logic is how the two paths drift apart.
  • The click listener is on the list, not on each message, so the reply that arrives 1.4 seconds later is clickable without any extra wiring.
  • input.value = "" does not re-fire the input handler, which is why the indicator has to be cleared by hand.
  • textContent, not innerHTML, for the message body. Same reason as lesson 7: a stranger typed it.

Bridge to React: handlers as props

React does not use addEventListener. You hand a function to the element as a prop and React manages attaching and removing it:

function TokenRow({ token, onRevoke }) {
  return (
    <li className="token-row">
      <span>{token.code}</span>
      <button onClick={() => onRevoke(token.code)}>Revoke</button>
    </li>
  );
}

Notice what this replaces. There is no delegation here and no dataset, because the row already knows which token it is — token.code is right there in scope. That is the closure from lesson 6 doing the job that data-token-code does in plain DOM code.

And no removeEventListener: React attaches and detaches as rows appear and disappear. The cleanup problem does not vanish, it moves — to useEffect, for the things React does not manage for you, like sockets and timers.
