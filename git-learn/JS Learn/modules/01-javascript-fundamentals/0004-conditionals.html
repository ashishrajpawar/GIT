Lesson 4

Conditionals

Foundations ~20 min read Beginner
Why this matters for your app

Every decision your WhatsApp clone makes is a conditional. Should the contact badge show a green dot? Only if the user is online. Should the message show two blue ticks? Only if the message has been read. Should a notification sound play? Only if the chat is not muted. Conditionals are the mechanism that lets your code look at a situation and choose what to do. Without them, your app would treat every message, every user, and every state exactly the same — it would be useless.

if / else — the fundamental decision

An if statement says: "if this condition is true, run this block of code." You can follow it with an optional else block that runs when the condition is false.

if (condition) {
  // runs when condition is true
} else {
  // runs when condition is false
}

Here is the simplest real example — deciding whether to show a green dot next to a contact's name:

const isOnline = true;

if (isOnline) {
  console.log("Show green dot");
} else {
  console.log("Show grey dot");
}
// Output: "Show green dot"

Change isOnline to false and the output switches to "Show grey dot". The code picks a path based on the value of the variable.

Truthy and falsy

JavaScript doesn't require a strict true or false inside an if. It evaluates the condition and decides whether it is truthy (counts as true) or falsy (counts as false).

These values are falsy — an if treats them as false:

  • false
  • 0
  • "" (empty string)
  • null
  • undefined
  • NaN

Everything else is truthy. So a non-empty string, any number other than 0, any object or array — all truthy.

const unreadCount = 3;

if (unreadCount) {
  console.log("Show badge with count");
} else {
  console.log("No badge needed");
}
// unreadCount is 3, which is truthy → "Show badge with count"

const mutedChats = 0;

if (mutedChats) {
  console.log("Some chats are muted");
} else {
  console.log("Nothing is muted");
}
// mutedChats is 0, which is falsy → "Nothing is muted"

Try it yourself

Rather than memorising the falsy list, run it. Each line prints the value and whether JavaScript treats it as true or false. Then add some values of your own to the array — "0" as a string is a good one to try, and so is an empty array.

In your WhatsApp clone

The truthy/falsy shorthand is everywhere in React Native. Instead of writing if (unreadCount > 0) you can write if (unreadCount) — because zero is falsy and any positive number is truthy. You'll use this constantly when deciding whether to render a badge or a typing indicator.

else if — chaining multiple conditions

Sometimes there are more than two possible situations. else if lets you chain as many conditions as you need:

if (firstCondition) {
  // runs if firstCondition is true
} else if (secondCondition) {
  // runs if firstCondition was false AND secondCondition is true
} else if (thirdCondition) {
  // runs if the previous two were false AND thirdCondition is true
} else {
  // runs if none of the above were true
}

JavaScript works through the chain from top to bottom and stops at the first condition that is true. Only that block runs — the rest are skipped.

Here is a practical example — deciding what label to show for a contact's status:

const lastSeen = "2 minutes ago";   // could be a timestamp in a real app
const isOnline = false;
const isTyping = true;

let statusLabel;

if (isTyping) {
  statusLabel = "typing...";
} else if (isOnline) {
  statusLabel = "online";
} else {
  statusLabel = `last seen ${lastSeen}`;
}

console.log(statusLabel);   // "typing..."

Change isTyping to false and isOnline to true and you get "online". Change both to false and you get the last-seen text. One chain, three possible outcomes.

Avoid deep nesting

It is tempting to put if blocks inside if blocks inside if blocks. Resist it. Code that is three or four levels deep becomes very hard to read and debug. If you find yourself nesting, look for ways to flatten the logic using else if, early returns (covered in the functions lesson), or helper functions. One sign that your code is doing too much nesting: you have to scroll right to read the lines.

Comparison operators — asking questions about values

The condition inside an if is usually a comparison. JavaScript has six comparison operators, all of which return true or false:

Operator Meaning Example Result
=== Strictly equal (value and type) 5 === 5 true
!== Strictly not equal 5 !== 6 true
> Greater than 10 > 3 true
< Less than 3 < 10 true
>= Greater than or equal 5 >= 5 true
<= Less than or equal 4 <= 5 true

In practice, inside your chat app:

const unreadCount = 5;

if (unreadCount > 0) {
  console.log("Show red badge on app icon");
}

if (unreadCount >= 99) {
  console.log("Show '99+' instead of the actual number");
}

const messageStatus = "read";

if (messageStatus === "read") {
  console.log("Show blue ticks");
}

if (messageStatus !== "read") {
  console.log("Show grey ticks");
}
Always use === not ==

JavaScript has two equality operators: === (strict) and == (loose). The loose == tries to convert types before comparing, which leads to deeply unintuitive results:

console.log(0 == false);    // true  ← surprising
console.log(0 === false);   // false ← correct
console.log("" == false);   // true  ← surprising
console.log("" === false);  // false ← correct
console.log(1 == "1");      // true  ← dangerous
console.log(1 === "1");     // false ← correct

Always use === and !==. Never use == or !=. This is one of the most important habits in JavaScript.

Try it yourself

Run this and read both columns side by side. Every row where the two differ is a bug waiting to happen in code that used ==. Seeing them is worth more than being told.

Logical operators — combining conditions

Often a decision depends on more than one thing at once. Logical operators let you combine multiple conditions into a single expression.

&& — AND (both must be true)

condition1 && condition2 is true only when both conditions are true. If either is false, the whole expression is false.

const isOnline = true;
const isMuted = false;

if (isOnline && !isMuted) {
  console.log("Show green dot and enable sound alerts");
}
// isOnline is true AND !isMuted is true → block runs
// Should we display a "deliver" animation?
const isSent = true;
const isConnected = true;

if (isSent && isConnected) {
  console.log("Animate the sent tick to delivered");
}

|| — OR (at least one must be true)

condition1 || condition2 is true when at least one condition is true. It is only false when both are false.

const isAdmin = false;
const isGroupOwner = true;

if (isAdmin || isGroupOwner) {
  console.log("Show 'Edit group info' button");
}
// isGroupOwner is true → block runs even though isAdmin is false
// Show a notification sound if the message is urgent OR it is from a favourite contact
const isUrgent = false;
const isFavourite = true;

if (isUrgent || isFavourite) {
  console.log("Play notification tone");
}

! — NOT (inverts the value)

!value flips true to false and false to true. It is a quick way to ask "is this condition not the case?"

const isMuted = false;

if (!isMuted) {
  console.log("Play the notification sound");
}
// !false === true → block runs
const isBlocked = true;

if (!isBlocked) {
  console.log("Allow message to be sent");
} else {
  console.log("Cannot send — this contact is blocked");
}
// !true === false → else block runs

Combining all three

You can combine &&, ||, and ! together. Use parentheses to make the grouping explicit and easy to read:

const isOnline = true;
const isMuted = false;
const isBlocked = false;

// Show the green dot only if online, not muted, and not blocked
if (isOnline && !isMuted && !isBlocked) {
  console.log("Show presence indicator");
}
In your WhatsApp clone

You will write conditions like these every single day:

  • isMuted && !isArchived — show muted icon but only in the active list
  • isDelivered || isRead — show double ticks (grey or blue)
  • !isOnline && lastSeen — show last seen text only when offline and timestamp exists

Ternary operator — the one-liner shorthand

The ternary operator is a compact way to write a simple if / else on a single line. The word "ternary" means "three parts" — and that's exactly what it has:

const result = condition ? valueIfTrue : valueIfFalse;

Read it as: "if condition, give me valueIfTrue; otherwise give me valueIfFalse."

Compare the two forms — they do exactly the same thing:

// if / else version
let tickColor;
if (isRead) {
  tickColor = "blue";
} else {
  tickColor = "grey";
}

// Ternary version — same result, one line
const tickColor = isRead ? "blue" : "grey";

More real-world examples from a chat UI:

const isOnline = true;
const statusDot = isOnline ? "green" : "grey";
console.log(statusDot);   // "green"

const unreadCount = 7;
const badgeLabel = unreadCount > 99 ? "99+" : String(unreadCount);
console.log(badgeLabel);  // "7"

const isTyping = false;
const subheading = isTyping ? "typing..." : "last seen today at 10:30";
console.log(subheading);  // "last seen today at 10:30"
In your WhatsApp clone

Ternary operators are used heavily in React Native JSX. When you want a component to render one thing or another, the ternary is the standard tool: {isRead ? <BlueTickIcon /> : <GreyTickIcon />}. You will write this pattern dozens of times. The if/else syntax cannot be used directly inside JSX — the ternary can.

Don't chain ternaries

You can nest ternaries inside ternaries, but don't. It becomes unreadable very quickly. If you need more than two outcomes, use if / else if / else or a switch statement instead.

// Hard to read — avoid this
const label = a ? "x" : b ? "y" : c ? "z" : "default";

// Much better — use else if
let label;
if (a)      { label = "x"; }
else if (b) { label = "y"; }
else if (c) { label = "z"; }
else        { label = "default"; }

switch — handling many specific cases

When you have one variable that could be many specific values and you want different code for each, a switch statement is cleaner than a long chain of else ifs.

switch (value) {
  case "option1":
    // code for option1
    break;
  case "option2":
    // code for option2
    break;
  default:
    // code when nothing matched
}

Three things to know:

  • case — each possible value you want to handle
  • break — stops execution after a matching case runs; without it, JavaScript "falls through" to the next case (almost always a bug)
  • default — like the else at the end — runs when none of the cases matched

A perfect real example is message delivery status. In WhatsApp, a message can be 'sending', 'sent', 'delivered', or 'read'. Each state maps to a different tick icon:

const status = "delivered";

switch (status) {
  case "sending":
    console.log("Show clock icon (pending)");
    break;
  case "sent":
    console.log("Show single grey tick");
    break;
  case "delivered":
    console.log("Show double grey tick");
    break;
  case "read":
    console.log("Show double blue tick");
    break;
  default:
    console.log("Unknown status — show nothing");
}
// Output: "Show double grey tick"

Compare that to the else if equivalent — both work, but the switch reads more clearly when the cases are distinct and specific:

// else if version — same logic, less readable for many cases
if (status === "sending") {
  console.log("Show clock icon");
} else if (status === "sent") {
  console.log("Show single grey tick");
} else if (status === "delivered") {
  console.log("Show double grey tick");
} else if (status === "read") {
  console.log("Show double blue tick");
} else {
  console.log("Unknown status");
}
In your WhatsApp clone

Use switch when a single value drives many different outcomes. Message status, notification type, call state ('ringing', 'connected', 'ended'), media type ('image', 'video', 'audio', 'document') — all great candidates for a switch.

A complete WhatsApp example

Let's put everything together into two functions you could actually use in your app. You learned about functions in Lesson 3 — here they show up again, this time with conditional logic inside them.

getTickColor(status) — what colour should the ticks be?

function getTickColor(status) {
  switch (status) {
    case "sending":
      return "none";       // No ticks yet — just a clock
    case "sent":
      return "grey";       // Single grey tick
    case "delivered":
      return "grey";       // Double grey tick
    case "read":
      return "blue";       // Double blue tick
    default:
      return "none";
  }
}

console.log(getTickColor("delivered"));   // "grey"
console.log(getTickColor("read"));        // "blue"
console.log(getTickColor("sending"));     // "none"

shouldShowNotification(chat) — should this chat fire a notification?

This function takes a chat object and decides whether to trigger a notification sound and banner. It uses comparison operators, logical operators, and if/else together:

function shouldShowNotification(chat) {
  // Never notify for a muted chat
  if (chat.isMuted) {
    return false;
  }

  // Never notify if the user is already inside that chat (they can see it)
  if (chat.isCurrentlyOpen) {
    return false;
  }

  // Always notify if it is a direct message from a favourite contact
  if (!chat.isGroup && chat.isFavourite) {
    return true;
  }

  // For group chats, only notify if the user was mentioned
  if (chat.isGroup && chat.mentionsCurrentUser) {
    return true;
  }

  // For regular chats, notify if there are any new unread messages
  return chat.unreadCount > 0;
}

// Example usage
const chatWithAli = {
  isMuted: false,
  isCurrentlyOpen: false,
  isGroup: false,
  isFavourite: true,
  mentionsCurrentUser: false,
  unreadCount: 1
};

const mutedGroupChat = {
  isMuted: true,
  isCurrentlyOpen: false,
  isGroup: true,
  isFavourite: false,
  mentionsCurrentUser: true,
  unreadCount: 5
};

console.log(shouldShowNotification(chatWithAli));     // true  — favourite contact, not muted
console.log(shouldShowNotification(mutedGroupChat));  // false — muted always wins

Notice how the function uses early return statements to handle the simplest cases first — muted? Stop immediately. Already open? Stop immediately. This is called a "guard clause" pattern and it keeps the logic readable by eliminating deep nesting. Each early return means one less level of indentation for everything that comes after.
