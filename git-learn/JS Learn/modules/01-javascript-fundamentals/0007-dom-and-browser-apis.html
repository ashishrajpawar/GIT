Lesson 7

DOM & Browser APIs

Browser JS ~35 min read Beginner
Why this matters for Token

Token has two front ends, and this lesson is about the one people forget.

The app is React Native. But the person redeeming your token cannot be asked to install an app first — that would defeat the whole point. So when someone opens tokn.app/t/MERC-8GH2-KP4X, they get a web page. That page is the web/ folder in your repo, and it is the only part of Token a stranger ever touches.

A web page is a tree of elements that JavaScript can read and change. That tree is called the DOM — the Document Object Model. Everything the redemption page does (show the token's status, reveal the message box, grey it out when the token is revoked) is a change to that tree.

You will build that page with React, not by hand. But React's entire job is doing what you are about to do manually. Learn the tree first and React stops being magic — it becomes a labour-saving device you can reason about, and debug.

From loops, closures and functions. As before these are not random: this lesson's exercise loops over a list of tokens and builds one element per token, so the array habits from lesson 5 are about to do real work.

What is the DOM?

When a browser loads an HTML page, it reads the tags and builds a tree structure in memory. That tree is the Document Object Model.

Every element — a heading, a button, an input — becomes a node in the tree. Each node has a parent, may have children, and may have siblings. The whole page is one tree, with document at the root.

Here is a stripped-down version of Token's redemption page, and the tree it creates:

<!-- The HTML -->
<div id="redeem-screen">
  <h2 id="token-code">MERC-8GH2-KP4X</h2>
  <p id="token-status">Active</p>
  <div id="message-list"></div>
  <input id="message-input" type="text" />
  <button id="send-btn">Send</button>
</div>

/* The tree the browser builds:
   document
     └── <div id="redeem-screen">
           ├── <h2 id="token-code"> "MERC-8GH2-KP4X"
           ├── <p id="token-status"> "Active"
           ├── <div id="message-list">
           ├── <input id="message-input">
           └── <button id="send-btn"> "Send"
*/

JavaScript can reach into this tree at any point — read a node's text, change its colour, add children, remove it entirely. That is the whole of DOM programming.

The React Native parallel

In the mobile app your component tree looks almost identical:

<View>                      {/* like <div> */}
  <Text>MERC-8GH2-KP4X</Text>   {/* like <h2> */}
  <ScrollView>...</ScrollView>  {/* like #message-list */}
  <TextInput />              {/* like <input> */}
  <TouchableOpacity>         {/* like <button> */}
    <Text>Send</Text>
  </TouchableOpacity>
</View>

Same tree shape, different names. The DOM gives you the mental model for both.

Selecting elements

Before you can change anything you have to select the element you want.

document.getElementById()

The most direct method. If an element has an id, you can grab it instantly:

const codeEl   = document.getElementById("token-code");
const statusEl = document.getElementById("token-status");
const sendBtn  = document.getElementById("send-btn");

console.log(codeEl);   // <h2 id="token-code">MERC-8GH2-KP4X</h2>

document.querySelector()

More flexible. It takes any CSS selector and returns the first match:

// By id — same as getElementById, but with a # prefix
const sendBtn = document.querySelector("#send-btn");

// By class — with a dot prefix
const firstToken = document.querySelector(".token-card");

// By element type
const firstInput = document.querySelector("input");

// By attribute
const textInput = document.querySelector("input[type='text']");

document.querySelectorAll()

Same idea, but returns all matches as a NodeList:

const allTokens = document.querySelectorAll(".token-card");

allTokens.forEach(function (cardEl) {
  console.log(cardEl.textContent);
});

// How many tokens has this user revoked?
const revoked = document.querySelectorAll(".token-card.revoked");
console.log("Revoked:", revoked.length);
A NodeList is not an array

It has length and forEach, which covers most of what you need. It does not have map, filter or reduce. When you want those, convert first:

const codes = Array.from(document.querySelectorAll(".token-card"))
  .map(function (el) { return el.textContent; });

Try calling .map() on a NodeList in the playground below — the practice page will tell you exactly this.

Try it yourself

querySelector returns null when nothing matches

It does not throw, and it does not return an empty thing you can safely poke at. It returns null — and the crash arrives on the next line, which is why the error message often points at code that is perfectly correct.

const el = document.querySelector("#toekn-status");   // typo — no match

el.textContent = "Revoked";
// TypeError: Cannot set properties of null (setting 'textContent')

Safe version:

const el = document.querySelector("#token-status");

if (el !== null) {
  el.textContent = "Revoked";
}

Try it yourself — this one crashes on purpose

Press Run and read the error before you fix anything. Getting familiar with this exact message is worth more than avoiding it, because you will meet it constantly — it is what a mistyped selector always looks like. Then fix the typo and run it again.

Reading and changing content

.textContent — plain text

The safest and most common property. It reads or sets the plain text inside an element:

const statusEl = document.querySelector("#token-status");
console.log(statusEl.textContent);   // "Active"

// The user just revoked this token
statusEl.textContent = "Revoked";

.innerHTML — HTML content

innerHTML reads or sets the full HTML inside an element, tags included:

const noticeEl = document.querySelector("#notice");
noticeEl.innerHTML = "<strong>This token expires</strong> in 2 days.";
XSS — never put untrusted text through innerHTML

innerHTML parses its string as HTML. Hand it something a stranger typed and you are handing a stranger the ability to run code on your page. This is Cross-Site Scripting (XSS).

On Token's redemption page this is not hypothetical. The whole design is that anyone with a code can open that page and type into it — the page's entire audience is people you have never met.

// DANGEROUS — whatever they typed gets parsed as HTML:
messageEl.innerHTML = whatTheyTyped;

// SAFE — it stays text, whatever it contains:
messageEl.textContent = whatTheyTyped;

Rule: textContent for anything a person typed. innerHTML only for static markup you wrote yourself.

Try it yourself — the same string, two properties

This is the clearest way to see the difference. Watch what happens to the document.body box in each case.

.value — reading input fields

Inputs and textareas do not use textContent. Their current text is in .value:

const inputEl = document.querySelector("#message-input");

const typed = inputEl.value;      // read what they typed
console.log("They typed:", typed);

inputEl.value = "";               // clear the box after sending
Why .textContent on an input is always empty

An <input> has no children — it cannot have any. The text you see in it is not inside it in the tree sense; it is the element's value. So inputEl.textContent returns "" no matter what is on screen. It is a quiet failure rather than an error, which is what makes it worth memorising now.

Changing styles and classes

Direct style with .style.property

Every element has a .style object. CSS property names become camelCase:

const card = document.querySelector(".token-card");

card.style.backgroundColor = "#FEE2E2";   // css: background-color
card.style.opacity = "0.6";
card.style.display = "none";              // hide it entirely

Classes with .classList

Usually better: keep the styling in CSS and toggle class names from JavaScript.

const card = document.querySelector(".token-card");

card.classList.add("revoked");        // now: "token-card revoked"
card.classList.remove("active");
card.classList.toggle("selected");    // add if absent, remove if present

if (card.classList.contains("revoked")) {
  console.log("This token no longer works");
}

A realistic example — revoking a token updates the card in place:

function markRevoked(tokenCode) {
  const card = document.querySelector("#token-" + tokenCode);

  if (card !== null) {
    card.classList.remove("active");
    card.classList.add("revoked");
  }
}
classList over style

When the look lives in CSS classes, changing it means editing a stylesheet. When it lives in .style calls scattered through your JavaScript, changing it means hunting through your JavaScript. Reach for classList first.

Try it yourself

Creating and removing elements

Showing a new token in a list means creating an element and inserting it.

document.createElement()

Creates an element in memory. It is not on the page until you insert it:

const card = document.createElement("li");

card.textContent = "CAFE-2BN7-4KQ9";
card.classList.add("token-card");
card.classList.add("active");

appendChild()

Inserts it as the last child of a parent:

const list = document.querySelector("#token-list");
list.appendChild(card);      // now it is on the page

element.remove()

function deleteToken(tokenCode) {
  const card = document.querySelector("#token-" + tokenCode);
  if (card !== null) {
    card.remove();
  }
}

The whole pattern in one place:

function addTokenToUI(tokenCode, issuedTo, isRevoked) {
  // 1. Create
  const card = document.createElement("li");

  // 2. Set text safely — issuedTo may have come from a stranger
  card.textContent = tokenCode + " — " + issuedTo;

  // 3. Style by state
  card.classList.add("token-card");
  card.classList.add(isRevoked ? "revoked" : "active");

  // 4. Insert
  document.querySelector("#token-list").appendChild(card);
}

Try it yourself

Browser storage: localStorage

The DOM is the page. localStorage is the other half of "browser APIs" — a small key–value store that survives a page reload and a closed tab.

localStorage.setItem("lastRedeemed", "MERC-8GH2-KP4X");

const code = localStorage.getItem("lastRedeemed");
console.log(code);                    // "MERC-8GH2-KP4X"

console.log(localStorage.getItem("nothingHere"));   // null

localStorage.removeItem("lastRedeemed");
It only stores strings

Every value is converted to a string on the way in. Hand it an object and you get the useless "[object Object]" back:

localStorage.setItem("counts", { total: 5 });
console.log(localStorage.getItem("counts"));   // "[object Object]"

So arrays and objects go through JSON both ways:

// Saving
localStorage.setItem("tokens", JSON.stringify(["CAFE-2BN7-4KQ9", "RENT-2WX7-JP8N"]));

// Loading
const tokens = JSON.parse(localStorage.getItem("tokens"));
console.log(tokens.length);   // 2

Try it yourself

Token rule: a code is capability material

Worth stating plainly, because it decides what the real redemption page is allowed to do.

A token code is not a username. It is the capability itself — whoever holds MERC-8GH2-KP4X can use it, and the system has no other way to tell them apart from the rightful holder. That is the design, and it is what makes tokens revocable and anonymous.

It also means storage is a real decision, not a convenience:

  • localStorage is not encrypted, is readable by any JavaScript running on that origin, and persists until something explicitly clears it.
  • So the real redemption page keeps a short-lived session reference there — never the code itself. Losing a session reference means signing in again. Losing a code means someone else has your capability.
  • On the mobile side the same rule is sharper still: private keys go in expo-secure-store (the iOS Keychain and Android Keystore), never in AsyncStorage. You will do this properly in module A10.

The practice pages in this lesson use a fake localStorage that forgets everything when you leave, so nothing you type here is stored anywhere.

<body>

  <div id="panel">
    <div id="panel-header">Your tokens</div>
    <ul id="token-list"></ul>
    <div id="issue-row">
      <input id="issued-to-input" type="text" placeholder="Who is this for? e.g. Corner Store" />
      <button id="issue-btn">Issue</button>
    </div>

  <script>
    // Token's alphabet: 36 alphanumerics minus 0, O, 1, I and L, which are
    // too easy to confuse when a code is read aloud or copied off a card.
    const ALPHABET = "23456789ABCDEFGHJKMNPQRSTUVWXYZ";

    const listEl     = document.getElementById("token-list");
    const inputEl    = document.getElementById("issued-to-input");
    const issueBtnEl = document.getElementById("issue-btn");

    // The whole app state: one array. The UI is redrawn from it.
    let tokens = [];

    function randomGroup(length) {
      let out = "";
      for (let i = 0; i < length; i++) {
        const index = Math.floor(Math.random() * ALPHABET.length);
        out = out + ALPHABET[index];
      }
      return out;
    }

    function generateCode() {
      return randomGroup(4) + "-" + randomGroup(4) + "-" + randomGroup(4);
    }

    function render() {
      // Redraw from scratch. Simple, and it is what React does for you later.
      listEl.innerHTML = "";

      if (tokens.length === 0) {
        const note = document.createElement("li");
        note.id = "empty-note";
        note.textContent = "No tokens yet. Issue one below.";
        listEl.appendChild(note);
        return;
      }

      for (const token of tokens) {
        const card = document.createElement("li");
        card.classList.add("token-card");
        card.classList.add(token.revoked ? "revoked" : "active");

        const codeEl = document.createElement("span");
        codeEl.classList.add("token-code");
        codeEl.textContent = token.code;

        // issuedTo is typed by a person, so it must never go through innerHTML
        const whoEl = document.createElement("span");
        whoEl.classList.add("token-issued-to");
        whoEl.textContent = token.issuedTo;

        const revokeBtn = document.createElement("button");
        revokeBtn.classList.add("revoke-btn");
        revokeBtn.textContent = token.revoked ? "Restore" : "Revoke";
        revokeBtn.addEventListener("click", function () {
          token.revoked = !token.revoked;
          render();
        });

        const deleteBtn = document.createElement("button");
        deleteBtn.classList.add("delete-btn");
        deleteBtn.textContent = "Delete";
        deleteBtn.addEventListener("click", function () {
          tokens = tokens.filter(function (t) { return t !== token; });
          render();
        });

        card.appendChild(codeEl);
        card.appendChild(whoEl);
        card.appendChild(revokeBtn);
        card.appendChild(deleteBtn);
        listEl.appendChild(card);
      }
    }

    function issueToken() {
      const issuedTo = inputEl.value.trim();
      if (issuedTo === "") {
        return;
      }

      tokens.push({ code: generateCode(), issuedTo: issuedTo, revoked: false });
      inputEl.value = "";
      render();
    }

    issueBtnEl.addEventListener("click", issueToken);

    inputEl.addEventListener("keydown", function (event) {
      if (event.key === "Enter") {
        issueToken();
      }
    });

    render();
  </script>

What you just built

Every concept in this lesson, doing something real:

  • getElementById to grab the list, input and button
  • .value to read and clear the input
  • createElement and appendChild to build each card
  • classList.add to style revoked tokens differently
  • .textContent — never innerHTML — for the name someone typed
  • .remove() via a redraw, and filter from lesson 5 to drop one from the array
  • the real code alphabet, so every code it generates is one Token could actually issue

Notice render(): state lives in the tokens array, and the UI is rebuilt from it after every change. That is not a browser trick — it is the idea React is built on, written by hand.

Bridge to React: the same idea, different words

What you did in this lesson is imperative DOM work. You spell out each step: find this element, change its text, append this child.

React and React Native are declarative. You describe what the UI should look like for a given piece of data, and React works out which nodes to create, update or remove. You never write appendChild.

// The same token list, in React Native:
const [tokens, setTokens] = React.useState([
  { code: "CAFE-2BN7-4KQ9", issuedTo: "Corner Store", revoked: false },
  { code: "RENT-2WX7-JP8N", issuedTo: "Landlord",     revoked: true  }
]);

function issueToken(issuedTo) {
  setTokens(function (prev) {
    return [...prev, { code: generateCode(), issuedTo: issuedTo, revoked: false }];
  });
}

// React re-renders the list. No createElement, no appendChild.

The difference in one line each:

  • DOM: you change the tree yourself, step by step
  • React: you change the data, and React changes the tree for you

Look back at render() in the mini-project. It throws the list away and rebuilds it from the array on every change — which is exactly React's model, minus the part where React works out the smallest set of changes instead of rebuilding everything.

The payoff

When setTokens() makes a row appear on screen and you want to know why, you will already know: something is running the createElement and appendChild calls you just wrote by hand. That is also how you will debug it when it does not appear.

Now build it yourself

If it reaches the page through innerHTML, a token label becomes a way to run code in someone else's browser.
