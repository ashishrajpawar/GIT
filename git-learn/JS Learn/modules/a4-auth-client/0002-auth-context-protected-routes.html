Auth Context & Protected Routes

A4 — Lesson 2 of 3 ~50 min
Why this matters for Token

Every screen in Token needs to know: is the user logged in? What's their name? What's their ID? Passing this through props would mean threading auth data through 10 layers of components. React Context solves this — define auth state once at the top, access it from any component with a hook. And the navigator automatically shows Login vs Main screens based on auth state.

React Context — the concept

Context provides values to an entire component tree without prop drilling:

// 1. Create the context
const AuthContext = createContext(defaultValue);

// 2. Wrap your app in a Provider (supplies the value)
<AuthContext.Provider value={authState}>
  <App />
</AuthContext.Provider>

// 3. Any nested component reads it with useContext
const auth = useContext(AuthContext);

Token's AuthContext

// app/src/auth/AuthContext.tsx
import { createContext, useContext, useState, useEffect, useMemo, ReactNode } from 'react';
import * as SecureStore from 'expo-secure-store';
import { api, ApiError } from '../api';        // the shared client from A3.2
import { setAccessToken, clearTokens } from './store';

interface User {
  id: number;
  email: string;
  displayName: string;
}

interface AuthState {
  user: User | null;
  isLoading: boolean;
  isOffline: boolean;
  login: (email: string, password: string) => Promise<void>;
  register: (email: string, password: string, displayName: string) => Promise<void>;
  logout: () => Promise<void>;
}

const AuthContext = createContext<AuthState | null>(null);

export function AuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<User | null>(null);
  const [isLoading, setIsLoading] = useState(true);
  const [isOffline, setIsOffline] = useState(false);

  // Check for existing session on app launch
  useEffect(() => {
    restoreSession();
  }, []);

  async function restoreSession() {
    const refreshToken = await SecureStore.getItemAsync('refreshToken');
    if (!refreshToken) {
      setIsLoading(false);           // genuinely logged out
      return;
    }

    try {
      const { data } = await api.refresh(refreshToken);
      setAccessToken(data.accessToken);
      await SecureStore.setItemAsync('refreshToken', data.refreshToken);
      setUser(data.user);
    } catch (err) {
      // Two very different failures, and treating them the same is what
      // makes an app log you out on a train.
      if (err instanceof ApiError && err.retryable) {
        setIsOffline(true);          // could not ask - we still have the token
      } else {
        await clearTokens();          // the server said no - really logged out
      }
    } finally {
      setIsLoading(false);
    }
  }

  // One place that turns "a server said yes" into "we are signed in".
  async function adoptSession(data: SessionResponse) {
    setAccessToken(data.accessToken);
    await SecureStore.setItemAsync('refreshToken', data.refreshToken);
    setUser(data.user);
  }

  async function login(email: string, password: string) {
    const { data } = await api.login({ email, password });
    await adoptSession(data);
  }

  // Register returns a session directly. Registering and then logging in is
  // two round trips, re-sends the password, and can leave the account created
  // but the user staring at an error - the login limiter is a separate one.
  async function register(email: string, password: string, displayName: string) {
    const { data } = await api.register({ email, password, displayName });
    await adoptSession(data);
  }

  async function logout() {
    const refreshToken = await SecureStore.getItemAsync('refreshToken');

    // The refresh token is what must be revoked, and it goes in the BODY.
    // The Authorization header carries the access token - putting the
    // refresh token there means the server rejects the call, and because
    // the failure is swallowed, logout silently becomes local-only while
    // the refresh token stays valid on the server.
    try {
      await api.logout({ refreshToken });
    } catch {
      // Best effort: the user asked to be logged out, so log them out
      // locally regardless. Worth queueing a retry - see "When this breaks".
    }

    await clearTokens();
    setUser(null);
  }

  // Without useMemo this object is new on every render of the provider, so
  // every consumer in the tree re-renders whenever anything here changes -
  // including screens that only read `user` and never touch the functions.
  const value = useMemo(
    () => ({ user, isLoading, isOffline, login, register, logout }),
    [user, isLoading, isOffline]
  );

  return (
    <AuthContext.Provider value={value}>
      {children}
    </AuthContext.Provider>
  );
}

// Custom hook for easy access
export function useAuth(): AuthState {
  const context = useContext(AuthContext);
  if (!context) throw new Error('useAuth must be used within AuthProvider');
  return context;
}

Conditional navigation based on auth state

// app/src/navigation/RootNavigator.tsx
import { NavigationContainer } from '@react-navigation/native';
import { createNativeStackNavigator } from '@react-navigation/native-stack';
import { useAuth } from '../auth/AuthContext';
import { LoginScreen } from '../screens/LoginScreen';
import { RegisterScreen } from '../screens/RegisterScreen';
import { MainTabs } from './MainTabs';
import { LoadingSpinner } from '../components/LoadingSpinner';

const Stack = createNativeStackNavigator();

export function RootNavigator() {
  const { user, isLoading } = useAuth();

  if (isLoading) {
    return <LoadingSpinner message="Starting Token..." />;
  }

  return (
    <NavigationContainer>
      <Stack.Navigator screenOptions={{ headerShown: false }}>
        {user ? (
          // Authenticated — show main app
          <Stack.Screen name="Main" component={MainTabs} />
        ) : (
          // Not authenticated — show auth screens
          <>
            <Stack.Screen name="Login" component={LoginScreen} />
            <Stack.Screen name="Register" component={RegisterScreen} />
          </>
        )}
      </Stack.Navigator>
    </NavigationContainer>
  );
}

When user changes from null to a User object (login success), React Navigation automatically swaps the screen stack. No manual navigation.replace() needed — the conditional rendering handles it.

App entry point

// app/App.tsx
import { AuthProvider } from './src/auth/AuthContext';
import { RootNavigator } from './src/navigation/RootNavigator';

export default function App() {
  return (
    <AuthProvider>
      <RootNavigator />
    </AuthProvider>
  );
}

Wiring the client's refresh to this context

A3.2 built the API client with an onUnauthorized hook and a refreshOnce helper. This is where they get connected — and the connection has to be made once, outside React, because a 401 can arrive while no component is mounted: 

// app/src/api/index.ts
import { createApiClient, createTokenApi } from '@token/shared/api';
import { refreshOnce } from '@token/shared/auth-refresh';
import * as SecureStore from 'expo-secure-store';
import { getAccessToken, setAccessToken, clearTokens } from '../auth/store';

let onSessionLost: () => void = () => {};
export function setSessionLostHandler(fn: () => void) { onSessionLost = fn; }

const client = createApiClient({
  baseUrl: process.env.EXPO_PUBLIC_API_URL!,   // never a hardcoded localhost
  getAccessToken,
  onUnauthorized: () => refreshOnce(async () => {
    const refreshToken = await SecureStore.getItemAsync('refreshToken');
    if (!refreshToken) return onSessionLost();

    try {
      const { data } = await rawRefresh(refreshToken);
      setAccessToken(data.accessToken);
      await SecureStore.setItemAsync('refreshToken', data.refreshToken);
    } catch {
      await clearTokens();
      onSessionLost();          // the provider sets user to null; the
    }                            // navigator swaps to Login on its own
  }),
});

AuthProvider calls setSessionLostHandler(() => setUser(null)) on mount. The client never imports React, the context never imports fetch, and there is exactly one refresh in flight no matter how many screens hit a 401 at once.

Why this way (and what was rejected)

The context calls the API client, not fetch

The version this lesson shipped called fetch('http://localhost:3000/api/auth/login') directly. Three separate problems, and the first one ships to users: that URL is in the production build. Every install would try to reach a server on the phone itself and fail with a network error that looks like an outage.

The other two are quieter. Requests made outside the client get no timeout, so a login on a stalled connection hangs forever; and they get no 401 handling, which is fine for login itself and wrong for everything the context does afterwards. Auth is not a special case that deserves its own networking — it is the part most worth doing consistently.

Register returns a session; it does not log in afterwards

"Create the account, then call login" reads naturally and has a failure mode that is hard to explain to a user: registration and login are separately rate limited (B4.3), so the register can succeed and the follow-up login be refused. The account now exists, the user saw an error, and their next move is to try registering again — which fails, because the email is taken.

One request that returns a session removes the window entirely, and sends the password once instead of twice.

The refresh token lives in SecureStore, not AsyncStorage

AsyncStorage is an unencrypted file in the app's sandbox. That sandbox is a real boundary on a healthy device and no boundary at all on a rooted or jailbroken one, or against a full device backup. expo-secure-store puts the value in the iOS Keychain or the Android Keystore, where the key material is held by hardware and does not leave it.

The access token stays in memory only. It lives about fifteen minutes and writing it to disk buys nothing but another copy to steal.

When this breaks

Offline is not logged out

The original restoreSession caught every error the same way and then set isLoading to false, so a user opening the app on a train — refresh request never answered — arrives at the Login screen. Their session was fine. They now have to type a password on a moving train to get back to where they already were.

"The server said this token is dead" and "I could not reach the server" are different answers and only one of them means log out. The retryable flag added to ApiError in A3.2 is what makes the distinction available here.

Logout that does not log out

The original sent the refresh token in the Authorization header, where the server expects an access token. The call fails, the failure is swallowed by catch {}, and the local tokens are cleared — so it looks like it worked. The refresh token stays valid on the server.

Anyone holding a copy of it — from a backup, a stolen device, a shared computer — keeps a working session for its full lifetime, and the user who pressed "Log out" believes they are protected. Local logout on a network failure is still right; what is wrong is not knowing it happened. Queue the revocation and retry it, or accept it explicitly.

A new context object on every render

value={{ user, isLoading, login, register, logout }} builds a fresh object each time the provider renders, and useContext compares by identity. Every screen reading useAuth() — the whole tree — re-renders whenever anything in the provider changes, even a screen that only ever reads user.displayName. Wrapping it in useMemo costs one line.

The client believes it is logged in until something fails

user is a snapshot taken at login. If the account is deleted, locked, or its sessions revoked from another device, this app keeps rendering the main tabs until the next request happens to fail. That is usually acceptable — the failure comes quickly, because everything needs the API — but it means the UI is not the authority. Every screen must handle "the server disagrees" rather than assuming user being non-null makes an action permitted.

What this costs you

DecisionWhat you pay
Auth in Context Every consumer re-renders when the value changes, which is why the useMemo is not optional. And Context is not a state manager: putting token lists or messages here too would re-render the app on every incoming message.
The module-level session-lost handler A mutable global bridging non-React code into React. It is the price of a client that can refresh without a component mounted, and it needs care in tests — set it, and reset it, or one test's provider outlives its describe block.
Distinguishing offline from logged out A third state to design for. Every screen that assumed "user or no user" now has "user, no user, or we do not know yet", and the offline case needs its own UI rather than falling through to Login.
SecureStore Async on both platforms, so session restoration is genuinely asynchronous and the app has a loading state at launch it cannot skip. On Android the Keystore is unavailable while the device is locked, so a background refresh can fail for a reason that has nothing to do with the network.
The conditional navigator Swapping the whole stack on logout unmounts every screen and discards their state — which is correct for logout and surprising the first time a refresh failure triggers it mid-typing.

First, which screens exist at all

The navigator above is three lines of JSX around one decision: given the auth state, which screens should the stack contain? Not which one is on top — which ones exist. That distinction is the whole pattern, and it is why navigation.replace() disappears.

Write it as a function returning a list of names, and the JSX afterwards is just rendering.
