Loading, Empty & Error States

A3 — Lesson 3 of 4 ~45 min
Why this matters for Token

A user opens the app. The token list takes 800ms to load. Without a loading state, they see a blank screen and think the app is broken. The API returns an error — without an error state, the app crashes. They have no tokens yet — without an empty state, there's no guidance to create their first one. Every data-fetching screen needs all three states handled explicitly.

The three states every screen has

// Every screen that fetches data exists in one of these states:
type ScreenState =
  | { status: 'loading' }                    // waiting for data
  | { status: 'error'; message: string }     // something went wrong
  | { status: 'empty' }                      // success but no data
  | { status: 'success'; data: T }           // success with data

Basic pattern

function TokenListScreen() {
  const [tokens, setTokens] = useState<TokenListItem[]>([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    api.listTokens()
      .then(res => setTokens(res.data.items))
      .catch(err => setError(err.message))
      .finally(() => setLoading(false));
  }, []);

  if (loading) return <LoadingSpinner />;
  if (error) return <ErrorMessage message={error} onRetry={() => { ... }} />;
  if (tokens.length === 0) return <EmptyState />;

  return <FlatList data={tokens} ... />;
}

Request cancellation with AbortController

When a user navigates away from a screen before the request finishes, cancel it to avoid state updates on unmounted components:

function TokenDetailScreen({ route }: Props) {
  const [token, setToken] = useState<Token | null>(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    const controller = new AbortController();

    fetch(`${API_URL}/tokens/${route.params.id}`, {
      headers: { Authorization: `Bearer ${accessToken}` },
      signal: controller.signal,  // link the abort signal
    })
      .then(r => r.json())
      .then(json => setToken(json.data))
      .catch(err => {
        if (err.name !== 'AbortError') {
          setError(err.message);
        }
      })
      .finally(() => setLoading(false));

    // Cleanup: cancel on unmount
    return () => controller.abort();
  }, [route.params.id]);
}

Retry with exponential backoff

async function fetchWithRetry<T>(
  fn: () => Promise<T>,
  maxRetries = 3
): Promise<T> {
  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      if (attempt === maxRetries) throw err;

      // Ask the error, don't guess from the status code. The client in A3.2
      // already worked this out: 5xx and network failures are retryable, 4xx
      // is not — EXCEPT 429, which is a 4xx that explicitly invites a retry.
      // `err.status < 500` would silently give up on every rate limit.
      if (err instanceof ApiError && !err.retryable) throw err;

      // If the server said when to come back, believe it. Backing off
      // exponentially against a Retry-After of 12s just means failing sooner.
      const delay = err.retryAfterSeconds != null
        ? err.retryAfterSeconds * 1000
        : Math.pow(2, attempt) * 1000;      // otherwise 1s, 2s, 4s
      await new Promise(resolve => setTimeout(resolve, delay));
    }
  }
  throw new Error('Max retries exceeded');
}

// Usage:
const tokens = await fetchWithRetry(() => api.listTokens());

Custom hook: useApi

// app/src/hooks/useApi.ts
import { useState, useEffect, useCallback } from 'react';

interface UseApiResult<T> {
  data: T | null;
  loading: boolean;
  error: string | null;
  refetch: () => void;
}

export function useApi<T>(fetcher: () => Promise<T>, deps: any[] = []): UseApiResult<T> {
  const [data, setData] = useState<T | null>(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  const load = useCallback(async () => {
    setLoading(true);
    setError(null);
    try {
      const result = await fetcher();
      setData(result);
    } catch (err: any) {
      setError(err.message || 'Something went wrong');
    } finally {
      setLoading(false);
    }
  }, deps);

  useEffect(() => { load(); }, [load]);

  return { data, loading, error, refetch: load };
}

// Usage in a component:
function TokenListScreen() {
  const { data, loading, error, refetch } = useApi(
    () => api.listTokens().then(r => r.data.items),
    []
  );

  if (loading) return <LoadingSpinner />;
  if (error) return <ErrorMessage message={error} onRetry={refetch} />;
  if (!data || data.length === 0) return <EmptyTokenList ... />;

  return <FlatList data={data} ... />;
}

First, the decision underneath the retry loop

The loop above is plumbing. The judgement is in two lines of it: should this failure be retried at all, and if so, when? Get that wrong and you either hammer a server that already told you to stop, or you give up instantly on a blip that would have cleared.

It is worth writing on its own, because it is the part with no await in it and no screen around it.
