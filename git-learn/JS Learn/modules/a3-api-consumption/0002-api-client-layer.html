API Client Layer

A3 — Lesson 2 of 4 ~50 min
Why this matters for Token

Both the mobile app and the redemption web page call the same API. Instead of writing raw fetch calls in every component, you build a typed API client in shared/ that both clients import. One change to the client layer propagates everywhere. Types from your Zod schemas flow through — if the API changes, TypeScript flags every call site that needs updating.

The problem with raw fetch everywhere

// Bad: duplicated fetch logic across 30 components
// TokenListScreen.tsx
const res = await fetch(API_URL + '/tokens', {
  headers: { Authorization: 'Bearer ' + token, 'Content-Type': 'application/json' },
});

// TokenDetailScreen.tsx
const res = await fetch(API_URL + '/tokens/' + id, {
  headers: { Authorization: 'Bearer ' + token, 'Content-Type': 'application/json' },
});

// Every component repeats: base URL, headers, error handling, JSON parsing

Building the API client

// shared/api-client.ts
import type { ApiResponse, Paginated } from './api-types';

type HttpMethod = 'GET' | 'POST' | 'PATCH' | 'DELETE';

interface ApiClientConfig {
  baseUrl: string;
  getAccessToken: () => string | null;
  onUnauthorized: () => Promise<void>;   // refresh, or log out - see below
  timeoutMs?: number;                     // default 15s
}

export function createApiClient(config: ApiClientConfig) {
  async function request<T>(
    method: HttpMethod,
    path: string,
    body?: unknown
  ): Promise<T> {
    const headers: Record<string, string> = {
      'Accept': 'application/json',
    };

    const token = config.getAccessToken();
    if (token) {
      headers['Authorization'] = `Bearer ${token}`;
    }

    if (body) {
      headers['Content-Type'] = 'application/json';
    }

    // A phone on a train does not get a connection error - it gets nothing,
    // forever. Without a deadline the screen spins until the app is killed.
    const abort = new AbortController();
    const timer = setTimeout(() => abort.abort(), config.timeoutMs ?? 15000);

    let response: Response;
    try {
      response = await fetch(config.baseUrl + path, {
        method,
        headers,
        body: body !== undefined ? JSON.stringify(body) : undefined,
        signal: abort.signal,
      });
    } catch (err: any) {
      if (err?.name === 'AbortError') throw new ApiError(0, 'The request timed out.', true);
      throw new ApiError(0, 'Could not reach the server.', true);
    } finally {
      clearTimeout(timer);
    }

    if (response.status === 401) {
      await config.onUnauthorized();
      throw new ApiError(401, 'Authentication required');
    }

    if (response.status === 429) {
      // The server said how long to wait. Passing it up lets the screen say
      // "try again in 12 minutes" instead of inviting another attempt.
      const reset = Number(response.headers.get('RateLimit-Reset'));
      throw new ApiError(429, 'Too many attempts.', true,
                         Number.isFinite(reset) ? reset : undefined);
    }

    if (response.status === 204) {
      return null as T;
    }

    // A 502 from the proxy is an HTML page, not JSON. Parsing it blind turns
    // a useful "server error" into "Unexpected token < in JSON".
    let json: any = null;
    if ((response.headers.get('content-type') || '').includes('application/json')) {
      try { json = await response.json(); } catch { json = null; }
    }

    if (!response.ok) {
      throw new ApiError(
        response.status,
        json?.error || 'Request failed',
        response.status >= 500        // 5xx is worth retrying, 4xx is not
      );
    }

    return json as T;
  }

  return {
    get: <T>(path: string) => request<T>('GET', path),
    post: <T>(path: string, body?: unknown) => request<T>('POST', path, body),
    patch: <T>(path: string, body?: unknown) => request<T>('PATCH', path, body),
    delete: (path: string) => request<null>('DELETE', path),
  };
}

// Carries the two things a screen needs in order to decide what to show:
// whether trying again could possibly help, and when.
export class ApiError extends Error {
  status: number;
  retryable: boolean;
  retryAfterSeconds?: number;

  constructor(status: number, message: string, retryable = false, retryAfterSeconds?: number) {
    super(message);
    this.status = status;
    this.retryable = retryable;
    this.retryAfterSeconds = retryAfterSeconds;
  }
}

Typed endpoint functions

Build a layer on top of the generic client with Token-specific functions:

// shared/api.ts
import { createApiClient } from './api-client';
import type {
  ApiResponse, Paginated, Token, CreateTokenInput,
  UpdateTokenInput, TokenListItem, Conversation, Message
} from './api-types';

export function createTokenApi(client: ReturnType<typeof createApiClient>) {
  return {
    // Tokens
    listTokens(cursor?: string) {
      const params = cursor ? `?cursor=${cursor}` : '';
      return client.get<ApiResponse<Paginated<TokenListItem>>>(`/tokens${params}`);
    },

    getToken(id: number) {
      return client.get<ApiResponse<Token>>(`/tokens/${id}`);
    },

    // The code comes back once, at creation. This is how the owner sees it
    // again - decrypted server-side, one token at a time, and logged.
    revealCode(id: number) {
      return client.get<ApiResponse<{ code: string }>>(`/tokens/${id}/code`);
    },

    createToken(input: CreateTokenInput) {
      return client.post<ApiResponse<Token>>('/tokens', input);
    },

    updateToken(id: number, input: UpdateTokenInput) {
      return client.patch<ApiResponse<Token>>(`/tokens/${id}`, input);
    },

    // POST, not DELETE: the row stays and keeps recording attempts.
    revokeToken(id: number) {
      return client.post(`/tokens/${id}/revoke`);
    },

    pauseToken(id: number) {
      return client.post<ApiResponse<Token>>(`/tokens/${id}/pause`);
    },

    resumeToken(id: number) {
      return client.post<ApiResponse<Token>>(`/tokens/${id}/resume`);
    },

    // Conversations
    listConversations(cursor?: string) {
      const params = cursor ? `?cursor=${cursor}` : '';
      return client.get<ApiResponse<Paginated<Conversation>>>(`/conversations${params}`);
    },

    getMessages(conversationId: number, cursor?: string) {
      const params = cursor ? `?cursor=${cursor}` : '';
      return client.get<ApiResponse<Paginated<Message>>>(
        `/conversations/${conversationId}${params}`
      );
    },

    markRead(conversationId: number) {
      return client.post(`/conversations/${conversationId}/read`);
    },
  };
}

Using the client in the mobile app

// app/src/api/index.ts
import { createApiClient, createTokenApi } from '@token/shared/api';
import { getAccessToken } from '../auth/store';

const client = createApiClient({
  baseUrl: __DEV__ ? 'http://localhost:3000/api' : 'https://api.tokn.app/api',
  getAccessToken,
  onUnauthorized: () => {
    // Trigger token refresh or navigate to login
  },
});

export const api = createTokenApi(client);
// Using it in a component:
import { api } from '../api';

function TokenListScreen() {
  const [tokens, setTokens] = useState<TokenListItem[]>([]);

  useEffect(() => {
    api.listTokens().then(res => {
      setTokens(res.data.items);
    });
  }, []);

  const handleRevoke = async (id: number) => {
    await api.revokeToken(id);
    setTokens(prev => prev.filter(t => t.id !== id));
  };
}

The same client in the web page

// web/src/api/index.ts
import { createApiClient } from '@token/shared/api-client';

const client = createApiClient({
  baseUrl: '/api',  // same origin, proxied by Vite in dev
  getAccessToken: () => sessionStorage.getItem('accessToken'),
  onUnauthorized: () => { window.location.href = '/login'; },
});

export { client };

Same createApiClient, different config. The web page uses session storage (short-lived) and redirects on auth failure. The mobile app uses secure storage and triggers a refresh flow.

Error handling in the client

import { ApiError } from '@token/shared/api-client';

async function handleCreateToken() {
  try {
    // maxUses: null means unlimited. 0 would be a token nobody can use,
    // and the server rejects it.
    const result = await api.createToken({ label: inputValue, maxUses: null });
    navigation.navigate('TokenDetail', { tokenId: result.data.id });
  } catch (err) {
    if (err instanceof ApiError) {
      if (err.status === 400) {
        // Validation error — show to user
        setError(err.message);
      } else if (err.status === 409) {
        // Conflict — token code collision (retry)
        setError('Please try again');
      } else {
        setError('Something went wrong');
      }
    }
  }
}

Why this architecture works

  • Types flow end-to-end — Zod schema → TypeScript type → API client → component. Change in one place, compiler shows all affected code.
  • One place to add auth headers — the client handles it; components don't know about tokens.
  • Shared between app and web — shared/api-client.ts works in both, only config differs.
  • Testable — mock the client in tests, not fetch globally.

Why this way (and what was rejected)

Ids in paths, because the client is the other half of that decision

B3.3 took token codes out of URLs, because a path is written into the proxy's access log, browser history, the Referer header and every crash report. That decision is only worth anything if the client respects it: a server that accepts /tokens/:id and a client that builds /tokens/MERC-8GH2-KP4X gives you the logging problem back, and this file is where 30 screens get their URLs from.

It also means the app holds ids, not codes. The code is returned once, at creation, and after that it has to be asked for explicitly — which is what revealCode() is, and why it is a separate call rather than a field on the token.

One refresh, not one per request

The obvious implementation of onUnauthorized is "refresh the access token". The obvious implementation is a serious bug, and it only appears when the app is doing something real.

A token list screen fires six requests at once. The access token has just expired, so all six come back 401, and all six call onUnauthorized — six simultaneous refreshes with the same refresh token. Refresh rotation (B4.2) invalidates the old refresh token the moment one succeeds, so the other five present a token that is now revoked. A rotation scheme worth having treats that as theft and kills the session. The user is logged out by opening a screen. 

// shared/auth-refresh.ts — one in-flight refresh, shared by every caller
let inFlight: Promise<void> | null = null;

export function refreshOnce(doRefresh: () => Promise<void>): Promise<void> {
  if (!inFlight) {
    inFlight = doRefresh().finally(() => { inFlight = null; });
  }
  return inFlight;          // the other five await the first one's result
}

Six callers, one network request, one rotation. The five that arrived late await the same promise and then retry with the token it produced.

A timeout, because the network does not always answer

fetch has no default timeout. On a train, in a lift, on a phone that has switched from wifi to mobile mid-request, the promise simply never settles — no error, no rejection, nothing to catch. Every loading spinner in the app is waiting on it.

15 seconds is a deliberate choice for the Indian mobile networks this app is for: long enough that a slow 3G handshake completes, short enough that the user gets an answer while still holding the phone.

When this breaks

Retrying a POST creates two of something

A timeout means "no answer", not "it did not happen". The request may have reached the server, created a token, and had its response lost on the way back. Retry that automatically and the user has two tokens, one of which they will never see the code for.

So retryable is a hint to the screen, not a licence for the client to retry by itself. GET is safe to retry; POST is not, unless the request carries an idempotency key the server can recognise as a repeat. That is a real feature with a table behind it, and it is deliberately not in this lesson — what belongs here is knowing that "retry on failure" is wrong for exactly the requests that matter most.

The 502 that says "Unexpected token <"

When the API container is restarting, Coolify's proxy answers with an HTML error page. The original client called response.json() on every response, so the user saw a JSON parse error and the actual status — 502, the server is briefly down — never reached the screen. Checking content-type before parsing is two lines and it is the difference between "we're having trouble, try again" and gibberish.

Ignoring 429 makes the lockout longer

A screen that retries on failure, against an endpoint that is rate limited, extends its own window every time it tries. The client now reads RateLimit-Reset and passes it up, so the UI can disable the button and count down instead of guessing.

Web storage is readable by any script on the page

The web config reads the access token from sessionStorage. That is convenient and it means any injected script — a compromised dependency, an XSS in a rendered label — can read the token and use it elsewhere. The safer shape is the access token in a JavaScript variable (gone on reload, unreachable from other origins) and the refresh token in an httpOnly cookie the page's own code cannot read at all. A8 builds the redemption page; make the decision there deliberately rather than inheriting this line.

What this costs you

DecisionWhat you pay
A shared client layer One more layer between a screen and the network, and a bug in it is a bug in every screen at once. The trade is that a fix is also a fix everywhere at once — but it means this file deserves tests, not just care.
A single in-flight refresh Module-level mutable state in something that otherwise looks purely functional. It has to be reset in a finally, or one failed refresh leaves every future request waiting on a promise that will never resolve.
A 15-second timeout Requests that would have succeeded at 20 seconds now fail. On a bad connection the app gives up on work the network was still doing — and the user's retry starts from zero. There is no setting that is right for both a fibre connection and a crowded cell tower.
Types shared with the server The one that bites mobile specifically: you cannot force an app update. Someone will be running last year's build in two years, holding types from last year. The API has to keep working for it, which means additive changes only — new optional fields, never renamed or removed ones — for far longer than feels necessary.
Ids instead of codes in the client Screens must carry ids through navigation params, and a support conversation cannot start from a URL. Revealing a code is now a deliberate, logged network call rather than reading a field you already had.
Every generic on this page is a promise you have not checked

client.get<ApiResponse<Paginated<TokenListItem>>>('/tokens') reads like a guarantee and is a type assertion. Underneath, res.json() returns any, and that generic renames it. Nothing at runtime looks at what actually arrived.

const res = await client.get<ApiResponse<Token>>('/tokens/7');
res.data.label.toUpperCase();   // TypeError: undefined

The beginner reading — I said it is a Token, so it is a Token — is exactly backwards. The compiler proved things about code it could see, and the response body is the one value in the whole app it could not. What arrives is whatever the server sent: an older shape, a field renamed last Tuesday, an error envelope, or null. And the failure never surfaces here — it surfaces three screens later, in code that is not wrong.

This is the boundary. One function, at the point the data enters, that checks what came back and refuses what it cannot understand. Everything inside the app is then genuinely typed; everything outside it was always a guess. a2/0001's isToken is the per-item half — this lesson is where it gets used.

Two things the boundary must decide, and they pull in different directions:

  • An unknown extra field is fine. A server that ships a new column before the app knows about it must not break every client. That is forward compatibility, and refusing it turns a routine deploy into an outage.
  • A field you know must never arrive is not fine. GET /tokens returns no code — ADR-0007 — so one turning up means something upstream is wrong, and rendering it would put a live capability on a list screen and into a React key. Tolerating what you do not know is not the same as tolerating what you know is wrong.

Now build it yourself

The client, the screens and the refresh queue all need a running API. The boundary does not — and it is the only code here that decides whether the types on the rest of the page mean anything.
